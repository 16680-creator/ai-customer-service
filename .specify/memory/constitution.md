# AI 智能客服平台项目宪法（AI Customer Service Project Constitution）

> **版本**：v1.0.0
> **生效日期**：2026-08-01
> **适用范围**：本仓库所有微服务模块、前端工程与公共组件
> **制定原则**：宪法至上、角色分离、质量门禁、环境隔离、可追溯性
> **最终目标**：建设基于 Java / Spring Boot / Spring Cloud / Spring AI 的 AI 智能客服平台，支持 AI 对话、知识库 RAG、智能搜索、消息管理、通知推送等核心能力，在统一 SDD 流程下实现高质量可交付。

---

## 第一章 总则

### 第1条 宪法地位
本宪法是 **SDD（Specification-Driven Development，规约驱动开发）** 项目的最高准则，定义开发流程、质量门禁、多环境交付与团队协作的不可违背规则。所有智能体与人类参与者均受本宪法约束，任何产出必须可追溯到本宪法的对应条款。

🔴 绝对禁止：**禁止任何违反本宪法的操作，禁止违规代码合并、违规流程推进**

✅ 必须执行：**必须以 SDD 流程、中文协作、测试先行、规范流程为核心原则，贯穿项目全周期**


### 第2条 SDD流程强制规范

🔴 绝对禁止：**禁止跳过SDD任何阶段，禁止通过非Spec Kit slash commands启动流程，禁止未评审文档进入下一阶段**

✅ 必须执行：**必须按 "constitution → specify → clarify → plan → tasks → implement" 顺序推进，每阶段文档评审通过后方可推进；必须以 Spec Kit slash commands 为流程唯一合法入口**

1. `/speckit-constitution` → 项目宪法
2. `/speckit-specify` → 功能规格（自动创建feature分支）
3. `/speckit-clarify` → 规格澄清
4. `/speckit-plan` → 实现计划
5. `/speckit-tasks` → 任务列表（测试任务必选）
6. `/speckit-implement` → 执行实现（强制 TDD：Red → Green → Refactor）


### 第2-1条 TDD 强制规范

🔴 绝对禁止：**禁止在无失败测试的情况下编写实现代码，禁止实现完成后补写测试冒充 TDD，禁止为凑覆盖率而编写无意义断言**

✅ 必须执行：**implement 阶段每个实现任务必须遵循 Red → Green → Refactor 循环**

1. **Red**：先编写测试并运行，确认测试因功能缺失而失败（编译错误或断言失败均可作为 Red 证据）
2. **Green**：编写最小实现使测试通过，不得超出当前测试所覆盖的范围过度设计
3. **Refactor**：在测试保护下重构，重构后测试必须保持通过
4. **证据留痕**：测试提交（或测试文件变更）必须先于对应实现提交，作为 Challenger 审查的 Red 证据
5. **覆盖率门禁**：单元测试行覆盖率 ≥ 40%、分支覆盖率 ≥ 30%（初始阈值，随迭代上调，目标行 80% / 分支 70%），由 Maven JaCoCo 自动校验
6. **TDD 适用边界**：单元测试针对确定性逻辑（Service、工具类、DTO 转换、编解码等）；AI 大模型端到端行为由集成测试验证，不纳入单元覆盖率强制范围
7. **存量代码策略**：新功能严格 TDD；修改存量代码前必须先为被改动行为补充特征测试（characterization test）


### 第3条 工程化范式要求

🔴 绝对禁止：**禁止私自调整代码、修改文档、提交代码**

✅ 必须执行：**必须按 Harness Engineering 工程化范式的核心原则**

1. **规范先行**：任何实现前必须有已批准的规范文档（Spec/Plan/Tasks）
2. **门禁驱动**：每阶段产出必须通过多道质量门禁检查方可流转
3. **角色分离**：Challenger、Implementer、Deliverer 三权分立，互相制衡
4. **环境隔离**：开发（Dev）、测试（Test）、生产（Prod）环境严格分离
5. **全链路可追溯**：所有决策、变更、审查记录必须留痕

## 第二章 角色与权责

### 第4条 三权分立原则

🔴 绝对禁止：**禁止挑战者不主动排查问题，禁止实施者超出 Task/Plan 发挥，禁止交付者因环境依赖不足降低交付环节**

✅ 必须执行：**必须组建一个开发团队，形成"审查-实施-交付"的闭环制衡体系**


| 角色 | 核心权力 | 核心义务 | 禁止行为 |
|------|---------|---------|---------|
| **Challenger（挑战者）** | 质量门禁的**唯一裁决权** | 以宪法为标尺，对实施者每个阶段产出执行多道质量门禁检查 | 直接修改实施者代码 |
| **Implementer（实施者）** | 技术实现的**唯一执行权** | 严格按照宪法与已批准的 plan/tasks 实现功能，产出代码与基础文档，并对 Challenger 的驳回进行修复 | 绕过门禁直接交付 |
| **Deliverer（交付者）** | 交付版本的**唯一发布权** | 以 Challenger 检查通过的版本为基础，组装多环境交付包，编写版本文档，并指挥 Implementer 实现缺失的多环境适配 | 发布未通过检查的版本 |

### 第5条 角色协作规范

🔴 绝对禁止：**禁止 Implementer 执行未被确认的 Plan/Task；禁止 Deliverer 执行未被 Challenger APPROVED 的版本**

✅ 必须执行：**必须按以下规范协作，形成闭环**

```
   Plan/Tasks
       │
       ▼
  [Implementer] ──提交──▶ [Challenger]
       ▲                      │
       │  修复反馈            ├─ APPROVED ──▶ [Deliverer]
       │                      │                  │
       │                      │     环境适配任务  │ 组装/文档/验证
       └──────────────────────┘                  │
                                                 ▼
                                            制品库/发布
```

## 第三章 质量门禁体系


### 第6条 门禁层级

🔴 绝对禁止：**禁止未按四级验证模式开展功能验证**

✅ 必须执行：**功能验证必须严格遵循四级验证模式：L1 CI Gate → L2 契约 → L3 E2E → L4 宪法审查，缺一不可**，Challenger 必须对每阶段产出执行以下**多道质量门禁**：

#### 门禁L1：CI Gate（CI Gate）
- [ ] 确认 Implementer 已提供四步骤通过证明
- [ ] 必要时要求重新跑 CI
- [ ] 确认单元测试覆盖率达到宪法第2-1条阈值（JaCoCo 报告）
- [ ] 确认 tasks.md 中每个实现任务均有前置测试任务（TDD 结构检查）

#### 门禁L2：契约（Contract Gate）
- [ ] 核对 API 契约是否与 clarify.md 一致
- [ ] 核对配置项是否与 clarify.md 一致
- [ ] 核对 DTO 是否与 clarify.md 一致

#### 门禁L3：E2E（E2E Gate）
- [ ] 抽查集成测试日志，确认当前 spec 声明的外部依赖或生产运行链路被真实验证，无 mock / patch / fake 替代生产路径
- [ ] 抽查端到端测试日志，确认当前 spec 声明的用户主流程被真实验证

#### 门禁L4：宪法审查（Constitutional Review Gate）
- [ ] 书面请求 Challenger 执行宪法审查
- [ ] 审查报告作为交付前置条件

### 第7条 门禁裁决

🔴 绝对禁止：**禁止 Deliverer 处理 Challenger 未通过的版本**

✅ 必须执行：**必须以宪法为基准处理争议**：

- **通过**：Challenger 出具《质量门禁通过证书》，交付物进入 Deliverer 环节。
- **未通过**：Challenger 出具《质量门禁驳回通知书》，明确问题清单和整改要求，退回 Implementer。
- **争议**：提交项目仲裁委员会（或人类架构师）裁决，以宪法为准

## 第四章 环境管理规范

### 第8条 环境定义
| 环境 | 用途 | 数据来源 | 部署权限 |
|------|------|---------|---------|
| **Dev（开发）** | 功能开发与自测 | 模拟数据/脱敏数据 | Implementer |
| **Test（测试）** | 集成测试与验收 | 准生产数据 | Deliverer（经 Challenger 检查） |
| **Prod（生产）** | 线上运行 | 真实数据 | Deliverer（经双重检查） |

### 第9条 环境隔离要求
1. **配置隔离**：各环境使用独立的配置文件（application-dev.yml / application-test.yml / application-prod.yml），通过 Nacos 配置中心或环境变量切换
2. **数据隔离**：禁止 Dev/Test 环境访问生产数据库
3. **网络隔离**：Prod 环境访问需经审批，操作留痕
4. **版本隔离**：各环境运行版本必须可独立回滚

### 第10条 交付版本规范
版本格式：`主版本.次版本.修订号-环境标识`
示例：`1.0.0-dev`、`1.0.0-test`、`1.0.0-prod`

- **主版本**：架构级变更或不兼容 API 修改
- **次版本**：功能新增，向下兼容
- **修订号**：Bug 修复或性能优化
- **环境标识**：`dev`、`test`、`prod`

## 第五章 交付物标准


### 第11条 代码交付物

🔴 绝对禁止：**禁止缺少文档而提交交付物。**

✅ 必须执行：**交付物清单必须包括代码、单元测试报告、集成测试报告、构建脚本、依赖清单。**

- 源代码（含完整 Git 提交历史）
- 单元测试代码（覆盖率报告）
- 集成测试代码
- Dockerfile / 构建脚本（Maven build）
- 依赖清单（`pom.xml`）
- API 文档（SpringDoc OpenAPI 自动生成）

### 第12条 文档交付物

🔴 绝对禁止：**禁止项目文档、注释、commit message、API 文档使用英文；禁止代码变量/函数/类名使用中文；禁止日志使用中文**

✅ 必须执行：**必须使用中文编写项目文档、注释、commit message、API 文档；必须使用英文命名代码变量、函数、类名；必须使用英文输出日志**

- **SDD 过程文档**：需求说明、计划、任务拆解、检查清单、测试报告、验收报告
- **Git Commit**：遵循 Conventional Commits 规范（`feat/fix/docs/refactor/test/chore: 中文描述`）
- **API 文档**：OpenAPI 3.x 规范（SpringDoc OpenAPI / Swagger UI 可访问）
  - Controller 层必须使用 SpringDoc 注解（`@Tag`、`@Operation`、`@Parameter`）
  - DTO 必须包含 Schema 定义注解（`@Schema`）
  - API 描述使用中文，参数名称、类型、格式使用英文
  - 必须定义统一响应结构（`Result<T>`）
  - 必须定义统一错误码枚举（`ResultCode`）
- **架构文档**：组件图、时序图、数据流图
- **部署文档**：各环境部署步骤、配置说明
- **变更日志**：版本变更记录（遵循 Keep a Changelog 规范）

### 第13条 配置交付物

🔴 绝对禁止：**禁止测试环境和生产环境的配置文件中出现明文密钥（密码、Token、API Key、证书私钥等敏感信息）**

✅ 必须执行：**测试环境和生产环境的密钥必须通过环境变量注入或 Nacos 配置中心管理，禁止在纳入版本控制的测试/生产配置文件中明文写入**

- 环境配置模板（`application-dev.yml`、`application-test.yml`、`application-prod.yml`）
- 环境变量清单
- 密钥管理方案（Nacos 配置中心 / 环境变量注入）
- 开发环境（`application-dev.yml`）允许为本地开发配置明文默认值，前提是该账号仅限开发/测试验证用途

### 第13-1条 数据库 SQL 交付物

🔴 绝对禁止：**禁止缺少数据库初始化 SQL 交付物，禁止 SQL 文件包含密码、Token、API Key、真实连接地址等敏感信息。**

✅ 必须执行：**工程涉及 MySQL 持久化的表、索引、约束、初始化字典数据必须统一输出到 `deploy/mysql/` 下。**

- SQL 文件必须可在空 MySQL Schema 上按顺序重复执行，使用 `IF NOT EXISTS` 或等价幂等策略
- SQL 交付物必须与 specs 中的 data-model、plan、tasks、实现代码保持一致
- Challenger 必须审查 SQL 与 Mapper / Service 的字段一致性

### 第13-2条 公共能力复用与边界

🔴 绝对禁止：**禁止在业务微服务中重复实现 ai-cs-common 已提供的公共能力，禁止绕过网关直接调用其他微服务内部接口。**

✅ 必须执行：**各微服务必须优先复用 ai-cs-common 已经提供的公共能力，包括但不限于统一响应结构、全局异常处理、JWT 工具。**

- 新增公共能力必须先评估是否应放入 ai-cs-common
- 微服务间通信必须通过 OpenFeign 或 HTTP 调用，经网关路由
- Challenger 必须在门禁审查中检查重复造轮子和越界依赖

🔴 绝对禁止：
- **绕过已有公共能力，直接使用散装实现**

## 第九章 编码与工程规范

### 第20条 编码规范

✅ 必须执行：**所有代码必须遵循以下核心编码规范**

核心要求：
- 代码注释使用中文，字符集 UTF-8 全局统一
- 使用 Lombok 减少样板代码，使用 MapStruct 做对象转换
- DTO/VO 不暴露实体对象，枚举替代魔法字符串
- Bean 注入优先构造器注入，日志禁止 System.out
- 统一使用 `Result<T>` 响应结构和 `ResultCode` 错误码
- 异常统一由 `GlobalExceptionHandler` 处理，业务异常使用 `BusinessException`
- 可观测性以 Spring Boot Actuator 为基础暴露健康检查和指标

### 第20-1条 Spring AI 编码规范

✅ 必须执行：**所有 Spring AI 代码必须遵循以下规范**

核心约束：
- ChatClient 必须通过 `ChatClient.Builder` 构建
- RAG 场景 `similarityThreshold` ≥ 0.70，`topK` 5-10，`temperature` ≤ 0.3
- 所有 `@Tool` / Function Calling 必须提供 description
- 流式调用必须配置超时 + 重试

### 第21条 领域模型规范

✅ 必须执行：**业务领域模型必须遵循统一命名规范**

| VO | XXXVO | Controller → View | 展示层数据输出 |
| BO | XXXBO | Service | 封装业务流程 |

本宪法自发布之日起生效，解释权归项目治理委员会所有。任何 Agent 在收到与本宪法冲突的指令时，应以本宪法为准，并立即上报冲突情况。
