## 一、一句话定位

> 一个 **12 模块的 Spring Cloud 微服务系统**，主线是「AI 智能客服 + 电商交易」：
> AI 侧能对话、查知识库、走售后 Agent；交易侧有商品、购物车、订单、支付、售后退款，两条线通过 Feign 打通。

**三块能讲深的能力**：

| 能力 | 关键词 | 证据 |
|---|---|---|
| 流量入口 | 网关路由、JWT 鉴权、Redis 分布式令牌桶、最少连接负载均衡、熔断 | [RouteConfig](../ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java)、[LeastConnectionsLoadBalancer](../ai-cs-gateway/src/main/java/com/aics/gateway/loadbalancer/LeastConnectionsLoadBalancer.java) |
| 交易一致性 | 分布式锁、Seata AT、幂等、状态机、事务消息、补偿对账 | [OrderServiceImpl](../ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java)、[PayNotifyService](../ai-cs-pay/src/main/java/com/aics/pay/service/PayNotifyService.java) |
| AI 工程化 | Spring AI、RAG（混合检索/Rerank/溯源）、Agent 状态机、模型路由、可观测 | [ai-cs-chat](../ai-cs-chat/src/main/java/com/aics/chat/) |

```mermaid
    CHAT -. "Feign" .-> NOTIFY
    ORDER -. "Feign" .-> PRODUCT
    ORDER -. "Feign" .-> PAY
```

**规则**（与 [CLAUDE.md](../CLAUDE.md) 一致）：

1. 服务之间**不直接依赖 jar**，只通过网关或 Feign/HTTP 调用；
2. `common` 不依赖任何业务模块（避免循环依赖）；
3. 网关只做「路由 + 鉴权 + 限流 + 熔断」，不写业务逻辑。

**这张图能回答**："为什么这么拆""拆完怎么保证不互相拖死"。

## 五、核心链路一：下单 → 支付 → 回调 → 对账

```mermaid
sequenceDiagram
    autonumber
    participant FE as 前端
    participant GW as 网关
    participant O as order
    participant P as product
    participant PAY as pay
    participant CH as 支付渠道
    participant MQ as RocketMQ
    participant N as notify

    FE->>GW: POST /api/order/create
    GW->>O: 转发（X-User-Id）
    O->>O: Redisson 分布式锁（按 userId 防重）
    Note over O: 锁在事务外，避免锁内空占事务资源
    O->>P: Feign 扣库存（Seata XID 透传）
    P-->>O: 扣减成功（分支事务，undo_log）
    O->>O: 计算价格/优惠 → 写订单+明细 → 核销优惠券
    O->>MQ: 发送延迟消息（30min 超时取消）
    O-->>FE: orderNo + 应付金额

    FE->>GW: POST /api/pay/create
    GW->>PAY: 创建支付
    PAY->>CH: 统一下单
    CH-->>PAY: 支付参数/二维码
    PAY-->>FE: 支付参数

    CH->>PAY: 异步回调 /pay/callback/{method}
    PAY->>PAY: parseNotify 验签 + 流水落库（事务消息半消息）
    PAY->>MQ: 事务消息：支付成功
    MQ->>O: PaySuccessListener 消费
    O->>O: confirmPay（幂等：已支付直接返回）
    O->>O: 状态机：待支付 → 已支付
    O->>O: 发布 OrderPaidEvent
    Note over O: @TransactionalEventListener(AFTER_COMMIT)<br/>回滚则不推送
    O->>N: WebSocket 通知用户

    Note over PAY,O: 兜底三层：回调重试 → 主动查单 syncByQuery → 对账补偿
```

**这张图能回答**：

- "支付回调丢了怎么办？" → 渠道重试 + `syncByQuery` 主动查单 + 补偿对账；
- "消息重复消费怎么办？" → `confirmPay` 幂等 + 状态机只允许合法迁移；
- "为什么用事务消息不直接 Feign？" → 本地流水落库与消息发送原子化，避免"钱到了订单没改"。

## 六、核心链路二：Agent 一轮对话

```mermaid
sequenceDiagram
    autonumber
    participant FE as 前端
    participant GW as 网关
    participant A as chat / AgentController
    participant S as SafetyGuard
    participant I as IntentClassifier
    participant SM as AgentStateMachine
    participant T as 工具集
    participant C as ConfirmationService
    participant O as order
    participant K as knowledge
    participant N as notify
    participant TR as 轨迹

    FE->>GW: POST /api/agent/chat
    GW->>A: 转发（X-User-Id）
    A->>S: 输入安全检查（注入/违规）
    S-->>A: 通过 / 拦截
    A->>I: 意图识别（LLM 结构化 + 规则兜底）
    I-->>A: intent + 槽位
    A->>SM: 进入状态机（INIT → ...）
    SM->>T: 按状态允许的工具集执行
    T->>O: OrderLocator：查订单（Feign）
    T->>K: PolicyCheck：售后规则检索（RAG）
    T->>T: ProductRecommend：同价位/相似商品
    alt 写操作（创建售后）
        T->>C: 生成确认 Token + 摘要（带超时）
        C-->>FE: 回复 + 确认凭证
        FE->>A: POST /api/agent/confirm
        A->>C: 校验 Token / 摘要 / 时效
        C-->>A: 通过
        A->>T: CreateAfterSale（幂等键 = runId + 动作）
        T->>O: 创建售后申请
    else 转人工
        A->>N: POST /api/notify/handoff
        N-->>FE: WebSocket 推送客服接入
    end
    A->>TR: 记录 run/step（摘要化，敏感参数脱敏）
    A-->>FE: 回复 + 下一步提示
```

**这张图能回答**："Agent 跑飞了怎么办"——状态机限定每步可用的工具、写操作必须二次确认、步数/超时上限、全程轨迹可审计。

## 九、怎么用这几张图（面试脚本）

| 时长 | 讲什么 | 用哪张图 |
|---|---|---|
| 30 秒 | "12 模块，AI 客服 + 电商交易两条主线，三块能力：网关流量、交易一致性、AI 工程化" | 第二节上下文图 |
| 3 分钟 | 背景 → 挑战（一致性/可溯源/写操作安全）→ 方案（三层兜底/状态机/确认）→ 结果 | 第二 + 五 + 六节 |
| 10 分钟 | 架构 → 一条主链路 → 一个难点 → 一个取舍 → 一个反思 | 第五或第六节 |

**取舍素材**（面试官最爱问）：

- 为什么消息最终一致而不是全链路 Seata AT？
- 为什么 Agent 用状态机而不是纯 ReAct 循环？
- 为什么网关限流按用户而不是全局？

## 十、维护规则

1. 改模块/端口/依赖关系 → 同步改第二、三、四节；
2. 改主链路 → 同步改对应时序图；
3. 图里的每个组件都必须能在仓库里找到（类名或配置），**不画没有落地的组件**；
4. 新增图优先用 Mermaid（可 diff、可 review），不提交截图。
