# AI 开发模式全景对比

> 整理时间：2026-08-02  
> 基于 AI 辅助编码实践总结，涵盖当前主流 AI 开发模式

---

## 一、主流 AI 开发模式

### 1. TDD（测试驱动开发）

**核心流程**：Red → Green → Refactor

先写失败的测试，再写最少代码让测试通过，最后重构。AI 负责根据测试描述自动生成实现代码。

**人的角色**：定义"正确"的标准（测试用例）  
**AI 的角色**：实现代码、修复失败、重构优化

---

### 2. SDD（规格驱动开发）

**核心流程**：specify → clarify → plan → tasks → implement → analyze

多阶段门禁，每步产出文档，人审批后才进入下一步。强调需求对齐和文档留痕。

**人的角色**：审批者、需求澄清者  
**AI 的角色**：生成规格文档、拆分任务、逐步实现

---

### 3. Vibe Coding（氛围编程）

**核心流程**：自然语言描述 → AI 全权生成 → 看效果 → 继续描述

由 Andrej Karpathy（OpenAI 联合创始人）于 2025 年提出。开发者完全用自然语言"指挥"AI，甚至不阅读生成的代码，只关注最终效果。

**人的角色**：需求描述者、效果验收者  
**AI 的角色**：全权负责代码生成、调试、修复

**典型工具**：Cursor Composer、Bolt.new、v0.dev

---

### 4. Plan-First（计划驱动开发）

**核心流程**：需求 → AI 生成计划 → 人审核 → 逐步执行 → 验证

先让 AI 输出完整的实施计划（分步骤、分模块、标注文件路径），人审核确认后再逐步执行。

**人的角色**：计划审核者、方向把控者  
**AI 的角色**：规划、执行、验证

**与 SDD 的区别**：Plan-First 更轻量，不一定有完整的 spec/clarify 阶段，适合中等复杂度任务。

---

### 5. Agentic Coding（Agent 自主编码）

**核心流程**：设定目标 → Agent 自主规划 → 搜索/编写/测试/修复循环 → 交付

给 AI Agent 一个高层目标，Agent 自主决定如何完成：搜索代码库、编写代码、运行测试、修复错误，循环直到目标达成。

**人的角色**：目标设定者、最终验收者  
**AI 的角色**：完全自主的规划者和执行者

**典型工具**：Devin、OpenHands、Qoder Agent、Claude Code

---

### 6. BDD + AI（行为驱动 + AI）

**核心流程**：编写 Gherkin 场景 → AI 生成步骤定义 → AI 实现代码 → 运行验证

用 Given/When/Then 格式描述业务行为，AI 据此生成测试步骤和实现代码。

```gherkin
Feature: 购物车结算
  Scenario: 正常下单
    Given 购物车中有 2 件商品
    When 用户点击结算
    Then 生成订单并扣减库存
```

**人的角色**：业务行为定义者  
**AI 的角色**：将行为描述转化为代码和测试

---

### 7. Rules-Driven（规则驱动开发）

**核心流程**：编写规则文件 → AI 编码时自动遵循 → 持续迭代

通过项目级规则文件（如 `.cursorrules`、`CLAUDE.md`、`QODER.md`）定义编码规范、架构约束、命名约定等，AI 在生成代码时自动遵循这些规则。

**人的角色**：规则制定者  
**AI 的角色**：规则遵循者

**特点**：通常作为其他模式的**补充层**，而非独立使用。

---

### 8. Conversational / Iterative（对话迭代式）

**核心流程**：描述需求 → AI 生成 → 反馈修改 → 再生成 → 直到满意

最朴素的模式。和 AI 多轮对话，逐步描述、修改、完善代码。没有严格流程，靠人把控方向。

**人的角色**：全程引导者  
**AI 的角色**：响应式代码生成器

**适用**：小改动、探索性开发、学习新技术

---

### 9. RAG-Augmented Development（检索增强开发）

**核心流程**：构建知识库 → 编码时检索相关上下文 → AI 基于上下文生成代码

让 AI 在编码前先从知识库、文档、代码库中检索相关信息，再基于检索结果生成更准确的代码。

**人的角色**：知识库维护者  
**AI 的角色**：检索 + 生成

**适用**：大型代码库、企业级项目、需要遵循内部规范的场景

## 二、多维度对比

### 核心维度对比表

| 维度 | TDD | SDD | Vibe Coding | Plan-First | Agentic | BDD+AI | Rules-Driven | 对话迭代 |
|------|-----|-----|-------------|------------|---------|--------|--------------|---------|
| **人的参与度** | 中 | 高 | 低 | 中 | 低 | 中 | 低（前期高） | 高 |
| **AI 自主度** | 中 | 中 | 高 | 中 | 最高 | 中 | 低 | 低 |
| **流程严格度** | 中 | 最高 | 无 | 中 | 低 | 中 | 低 | 无 |
| **文档产出** | 测试代码 | 完整文档链 | 无 | 计划文档 | 无 | 场景文件 | 规则文件 | 无 |
| **代码质量保障** | 高（测试覆盖） | 高（多阶段审查） | 低 | 中 | 中 | 高 | 中 | 低 |
| **迭代速度** | 快 | 慢 | 最快 | 中 | 快 | 中 | 快 | 快 |
| **适合团队规模** | 任意 | 大团队 | 个人 | 小团队 | 个人/小团队 | 任意 | 任意 | 个人 |
| **可维护性** | 高 | 最高 | 低 | 中 | 中 | 高 | 高 | 低 |

### 适用场景对比

| 模式 | 最佳场景 | 不适合场景 |
|------|---------|-----------|
| **TDD** | 需求明确的功能开发、Bug 修复、重构 | 需求模糊、架构决策 |
| **SDD** | 复杂功能、跨团队协作、合规项目 | 简单改动、快速原型 |
| **Vibe Coding** | 原型验证、个人项目、创意探索 | 生产环境、团队协作 |
| **Plan-First** | 中等复杂度功能、多文件修改 | 一行代码的小改动 |
| **Agentic** | 明确可验证的独立任务 | 需要频繁人工决策的场景 |
| **BDD+AI** | 业务逻辑复杂、需要非技术人员参与 | 纯技术重构 |
| **Rules-Driven** | 团队规范统一、长期维护项目 | 一次性脚本 |
| **对话迭代** | 学习探索、小修改、调试 | 大型功能开发 |

### 复杂度-控制力象限图

```
控制力（流程严格度）
    高 │        SDD
       │       ╱
       │  BDD ╱   Plan-First
       │     ╱  TDD
       │    ╱  Rules-Driven
       │   ╱
       │  ╱  Agentic
       │ ╱
       │╱  对话迭代
    低 │──────────────────── Vibe Coding
       └──────────────────────────────────
       低          任务复杂度          高
```

## 三、组合使用策略

实际项目中，这些模式很少单独使用，通常是**分层组合**：

```
┌─────────────────────────────────────────────────┐
│  Rules-Driven（底层规范保障）                      │
├─────────────────────────────────────────────────┤
│  SDD / Plan-First（需求分析 + 架构设计）           │
├─────────────────────────────────────────────────┤
│  TDD / BDD（具体功能实现 + 质量保障）              │
├─────────────────────────────────────────────────┤
│  Agentic / Vibe Coding（快速原型 + 探索）         │
└─────────────────────────────────────────────────┘
```

### 本项目实际组合

```
Rules-Driven：QODER.md / CLAUDE.md 定义项目规范
       ↓
SDD：购物车结算流程（specify → clarify → plan → tasks → implement）
       ↓
TDD：商品服务开发（Red → Green → Refactor）
       ↓
Plan-First：日常中等复杂度任务
```

## 四、选型建议

### 快速决策树

```
你的任务是什么？
│
├─ 需求模糊 / 需要对齐 / 多人协作？
│  └─ → SDD
│
├─ 需求明确 / 需要质量保障？
│  └─ → TDD
│
├─ 只是快速验证想法？
│  └─ → Vibe Coding
│
├─ 中等复杂度 / 多文件修改？
│  └─ → Plan-First
│
├─ 目标明确 / 可自动验证？
│  └─ → Agentic
│
├─ 业务人员需要参与定义行为？
│  └─ → BDD + AI
│
└─ 小改动 / 学习探索？
   └─ → 对话迭代
```

### 一句话总结

> **想清楚用 SDD，做扎实用 TDD，跑得快用 Vibe Coding，放手让 AI 干用 Agentic，守住底线用 Rules-Driven。**

## 五、趋势展望

| 趋势 | 说明 |
|------|------|
| **Agent 自主性增强** | 从"人指挥 AI 写代码"走向"人定目标 AI 自主完成" |
| **模式融合** | 工具层面自动选择最优模式组合（如 Qoder 的 Agent/Plan/Debug 多模式） |
| **验证闭环** | AI 不仅生成代码，还自动运行测试、部署验证、性能检测 |
| **知识沉淀** | 项目级 Memory / Knowledge 让 AI 越用越懂项目 |
| **人机边界模糊** | Vibe Coding 和 Agentic 的边界越来越模糊，最终走向"意图驱动开发" |
