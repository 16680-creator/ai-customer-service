## 一、结论摘要

当前项目已经不再是“基础聊天 + 简单 RAG”的入门项目，而是具备下列能力的 **AI 客服与 RAG 工程实践平台**：

- Spring AI 对话、SSE 流式输出、会话历史持久化与摘要压缩
- 向量检索、ES BM25、RRF 混合检索、Rerank、引用溯源、查询改写
- RAG 评估、LLM-as-Judge、Golden Dataset、CI 质量门禁
- Tool Calling、订单查询、NL2SQL、自然语言结论与 ECharts 图表
- GraphRAG 实验能力、知识问题聚类、知识缺口检测、FAQ 反哺
- 图片对话、商品图片描述、文图联合向量推荐
- RocketMQ 驱动的知识库增量同步
- Resilience4j 超时、重试、熔断和降级

下一阶段不应继续堆叠孤立 Demo，而应沿四条主线推进：

1. **智能客服 Agent 闭环**：意图路由、多工具编排、状态机、人工转接。
2. **安全与生产治理**：Prompt 注入防护、PII 脱敏、内容安全、工具权限与审计。
3. **可观测与成本治理**：模型调用链追踪、Token/延迟/费用统计、模型路由与缓存。
4. **真实业务智能化**：售后 Agent、智能质检、主动服务、个性化推荐、语音客服。

## 三、真正值得继续落地的 AI 功能

### 3.1 P0：智能客服 Agent 编排与人工转接

> ✅ **已实现（2026-08-14）**：见 [specs/005-after-sales-agent/](../specs/005-after-sales-agent/spec.md)。
> 交付：ai-cs-chat 新增 `com.aics.chat.agent`（安全检查、意图识别、状态机、工具注册、确认、编排、轨迹）；
> ai-cs-order 新增售后申请命令（幂等）；ai-cs-product 新增同价位召回；ai-cs-message 新增执行轨迹四表；
> ai-cs-notify 新增转人工通知。目标场景"我昨天买的耳机坏了，想换货，另外帮我看看有没有同价位降噪更好的"
> 已在集成测试中走通全链路（意图识别 Macro-F1 ≥ 0.90 由固定数据集测试保障）。

这是当前项目最值得做的下一项综合实战。项目已有 RAG、订单工具、消息、通知、用户和订单微服务，只缺可靠的业务编排层。

#### 目标场景

用户输入：

> “我昨天买的耳机坏了，想换货，另外帮我看看有没有同价位降噪更好的。”

期望系统自动完成：

```text
输入安全检查
    ↓
意图识别：售后 + 商品推荐
    ↓
订单工具：定位当前用户订单
    ↓
售后规则 RAG：判断是否满足换货条件
    ↓
商品检索工具：召回同价位降噪耳机
    ↓
风险判断：写操作前要求用户确认
    ↓
创建换货申请 / 转人工
    ↓
生成结果摘要并留审计记录
```

#### 推荐技术

- **显式工作流/状态机**：售后、退款等场景使用固定状态，不只依赖模型自由 ReAct。
- **Tool Calling**：复用订单、商品、用户、消息和通知服务。
- **结构化输出**：意图、参数、下一动作使用 Java Record/JSON Schema 接收。
- **Human-in-the-loop**：退款、换货、修改地址等写操作必须二次确认。
- **幂等与补偿**：每次 Agent 执行生成 `runId`，写操作携带幂等键。

#### 代码落点建议

| 模块 | 建议职责 |
|---|---|
| `ai-cs-chat` | Agent 路由、工作流状态、工具注册、回复生成 |
| `ai-cs-order` | 售后资格校验、退款/退货/换货命令 |
| `ai-cs-product` | 商品筛选、对比、推荐解释 |
| `ai-cs-message` | Agent 执行轨迹和会话摘要持久化 |
| `ai-cs-notify` | 转人工、风险告警、处理进度通知 |

#### 验收指标

- 意图分类 Macro-F1 ≥ 0.90
- 工具参数正确率 ≥ 95%
- 高风险写操作未经确认执行次数 = 0
- Agent 最大步骤数、超时、失败降级均可配置
- 转人工时携带订单、情绪、问题摘要和已执行步骤

### 3.2 P0：AI 安全网关与 Guardrails

项目已能调用真实业务服务，安全优先级应高于继续增加模型能力。

| 能力 | 实战内容 |
|---|---|
| Prompt 注入检测 | 识别“忽略系统指令”“输出知识库原文”“调用任意工具”等攻击 |
| 工具调用授权 | 工具端重新校验用户、资源归属、角色和操作权限，不能只信模型参数 |
| PII 识别与脱敏 | 手机号、身份证、银行卡、地址在日志和模型请求前脱敏 |
| 内容安全 | 输入和输出分别审核，违规内容拒答或转人工 |
| RAG 数据防泄漏 | 按租户、角色、文档 ACL 在检索阶段过滤 |
| SQL 安全 | NL2SQL 只读账户、表字段白名单、AST 校验、行数和耗时限制 |
| 审计留痕 | 保存 Prompt 版本、模型、工具参数摘要、审批人和最终结果 |

推荐顺序：

1. 在 `ai-cs-gateway` 做限流、身份可信透传和敏感输入初筛。
2. 在 `ai-cs-chat` 增加模型输入/输出 Guardrail 链。
3. 在各业务工具内部做资源级授权，杜绝越权操作。
4. 为 NL2SQL 增加 AST 解析和只读数据库账号双保险。

### 3.3 P0：LLM 可观测性、评估与成本治理

> ✅ **已实现（2026-08-14）**：见 [docs/25-LLM可观测性评估与成本治理实现文档](25-LLM可观测性评估与成本治理实现文档.md) 与 OpenSpec 变更 `2026-08-14-llm-observability-cost-governance`。
> 交付：ai-cs-chat 新增 `com.aics.chat.observability`（TraceContext 贯穿的 span 模型、Micrometer Observation 统一埋点、
> OTLP 可选导出、请求拦截器、调用链落库、Token/费用计量、配额检查、线上采样评估、用户反馈接口）；
> ai-cs-message 新增 5 张表（llm_trace / model_usage / model_usage_quota / online_eval_record / user_feedback）与持久化接口；
> RAG 评估门禁扩展 P95 延迟与单请求平均 Token 上限。可观测、计量、评估落库失败均只告警不阻断主链路。

现有 RAG 评估解决了“回答质量是否退化”，但还没有解决“线上一次请求到底发生了什么”。

```text
requestId / userId / sessionId
  ├─ intent: 类型、置信度、路由结果
  ├─ retrieval: query、召回数、文档 ID、分数、耗时
  ├─ rerank: 模型、前后排序、耗时
  ├─ llm: provider、model、tokens、首 Token、总耗时、重试
  ├─ tools: 工具名、参数摘要、结果状态、耗时
  └─ answer: 引用数、安全结果、用户反馈
```

技术实战：

- 使用 Micrometer Observation + OpenTelemetry 统一埋点。
- 接入 Langfuse、Phoenix 或兼容 OTLP 的追踪后端之一。
- 建立 `model_usage` 日志/表，按用户、场景、模型统计 Token 和估算费用。
- 将离线 RAG 评估扩展为线上采样评估和用户反馈闭环。
- CI 门禁除正确率外，增加 P95 延迟和单请求平均 Token 上限。

### 3.4 P1：多模型路由与语义缓存

| 任务 | 推荐模型策略 |
|---|---|
| 意图分类、摘要、实体抽取 | 小模型或本地模型 |
| 普通 FAQ | 缓存命中优先，其次低成本模型 |
| RAG 综合回答 | 中等模型 + 引用约束 |
| NL2SQL、复杂售后推理 | 强推理模型 |
| 图片理解 | VLM |
| Embedding/Rerank | 独立专用模型 |

实战要点：

- 建立统一 `ModelRouter`，按场景、复杂度、预算和健康状态选模型。
- 建立模型能力注册表：上下文长度、图片/工具支持、成本和超时。
- 使用 Redis 实现 FAQ 精确缓存和语义缓存。
- 缓存键包含知识库版本、Prompt 版本、权限范围和模型版本。
- 模型故障时支持同能力模型降级，而不是只返回固定兜底文案。

### 3.5 P1：智能质检与客服运营分析

该功能可直接复用会话持久化、LLM Judge、聚类和图表能力，投入产出较高。

- 自动识别服务态度、解决度、事实准确性、合规性和用户情绪。
- 检测承诺过度、答非所问、未引用依据和敏感信息泄漏。
- 对低分会话生成改进建议和主管复核任务。
- 按客服、渠道、问题类型、商品和时间形成看板。
- 将用户差评和人工复核结果加入评估数据集。

验收建议：人工标注 200～500 条会话，计算分类准确率、严重问题召回率及与人工评分的相关性。

### 3.6 P1：主动服务与下一最佳动作

| 业务事件 | AI 动作 |
|---|---|
| 物流长时间未更新 | 解释状态和预计时效，提供催件入口 |
| 支付失败 | 判断常见原因，推荐重试或其他支付渠道 |
| 库存恢复 | 根据收藏、浏览和咨询记录发送个性化通知 |
| 退款状态变化 | 自动总结进度和下一步时间点 |
| 连续搜索无结果 | 推荐替代商品或邀请人工选品 |

可由 RocketMQ 消费业务事件，调用策略引擎决定是否触达，再由 LLM 生成受模板约束的个性化消息。

### 3.7 P2：语音客服

```text
麦克风/电话音频
    ↓ ASR
文本 + 说话人 + 时间戳
    ↓ Agent/RAG/Tool
结构化回答
    ↓ TTS
流式语音播放
```

实战重点不是简单接 ASR/TTS API，而是流式识别、打断、端点检测、降噪、脱敏、低延迟和人工接管。建议先做 Web 端按住说话，再评估电话渠道。

### 3.8 P2：个性化推荐与对话式导购

现有 `ProductVectorService` 主要解决“内容相似”，下一阶段可加入用户行为和业务约束：

- 候选召回：向量相似、协同过滤、热销、新品、规则召回。
- 排序特征：点击、加购、购买、价格偏好、品牌偏好、库存和毛利。
- 对话约束：预算、用途、尺寸、颜色、禁忌条件。
- 推荐解释：必须基于真实商品属性，不允许模型编造参数。
- 在线反馈：点击、加购、购买、跳过作为隐式反馈。

建议先实现“多路召回 + 规则排序 + LLM 解释”，数据量足够后再训练 Learning-to-Rank 或深度推荐模型。

## 四、仍存在的技术缺口

| 技术方向 | 当前判断 | 优先级 | 原因 |
|---|---|---|---|
| Agent 状态机与多步编排 | ✅ 已实现（005） | P0 | 售后 Agent 显式状态机 + 工具注册中心 + 轨迹审计，见 specs/005-after-sales-agent |
| 人工转接与 Human-in-the-loop | ✅ 已实现（005） | P0 | 写操作二次确认 + 转人工工单（订单/情绪/摘要/已执行步骤） |

| PII/内容安全/审计 | 缺失 | P0 | 上线客服系统的基础要求 |
| LLM 全链路可观测 | ✅ 已实现 | P0 | 请求级 requestId 贯穿各环节 + llm_trace 落库 + OTLP 可选导出，见 docs/25 |

| ASR/TTS | 缺失 | P2 | 适合扩展语音客服渠道 |
| 生产级向量库治理 | 部分缺失 | P2 | Chroma 适合实践，规模化后再评估迁移 |
| 领域微调 | 暂不推荐 | P3 | 应先完成数据治理、评估和 Prompt/RAG 优化 |

## 五、推荐实战：售后服务 Agent

如果只选择一个新功能进行 AI 技术实战，推荐实现 **“售后服务 Agent + 人工转接”**。它能把当前分散的 AI 与微服务能力串成完整产品链路。

### 5.1 MVP 范围

1. 用户描述商品问题，Agent 识别退款、退货、换货或投诉意图。
2. Agent 从当前用户订单中定位目标订单；不确定时列出候选。
3. Agent 结合售后规则知识库判断资格并引用具体规则。
4. Agent 收集原因、商品、数量、图片等必要参数。
5. 提交前展示操作摘要并要求用户确认。
6. 确认后调用订单服务创建售后申请。
7. 不满足规则、用户愤怒或执行失败时转人工，并携带完整上下文。

### 5.2 状态设计

```text
START
  ↓
CLASSIFY_INTENT
  ↓
LOCATE_ORDER ──找不到──> ASK_ORDER
  ↓
CHECK_POLICY ──不满足──> EXPLAIN_OR_HANDOFF
  ↓
COLLECT_EVIDENCE
  ↓
CONFIRM_ACTION ──拒绝──> CANCELLED
  ↓
EXECUTE_AFTER_SALE
  ├─成功──> COMPLETED
  └─失败──> RETRY_OR_HANDOFF
```

### 5.3 数据模型建议

| 对象 | 关键字段 |
|---|---|
| `agent_run` | runId、sessionId、userId、intent、status、currentStep、promptVersion |
| `agent_step` | runId、stepNo、type、toolName、inputDigest、outputDigest、duration、status |
| `agent_confirmation` | runId、action、payloadDigest、confirmedBy、confirmedAt |
| `handoff_ticket` | runId、reason、priority、summary、assignedAgent、status |

敏感参数不应原样进入普通日志；保留摘要、密文或受权限保护的审计数据。

### 5.4 测试策略

- 单元测试：意图路由、状态迁移、参数校验、权限决策、幂等。
- 契约测试：订单、商品、消息和通知服务的工具接口。
- 模型评估：固定售后数据集，评价意图、参数、规则引用和最终动作。
- 对抗测试：Prompt 注入、越权订单号、伪造 userId、重复确认、超长输入。
- 故障测试：模型超时、订单服务异常、MQ 重复投递、执行后响应丢失。

### 5.5 MVP 验收标准

- 退款/退货/换货三类意图识别准确率 ≥ 95%。
- 订单归属校验覆盖率 100%。
- 所有写操作均经过用户确认并具备幂等键。
- 规则回答必须返回引用；无依据时不得编造。
- 任一步骤失败均可解释、重试或转人工。
- 完整执行链可按 `runId` 检索和回放。

## 六、分阶段落地路线

### 阶段 A：生产安全底座（1～2 周）

- Prompt 注入基础检测
- PII 脱敏和内容审核
- 工具权限校验与 NL2SQL AST 防护
- 模型调用 Token、延迟、错误率埋点
- Prompt 外置、版本号和审计字段

### 阶段 B：售后 Agent MVP（2～4 周）

- 意图结构化分类
- 订单定位和售后规则 RAG
- 显式状态机与工具编排
- 用户确认、幂等执行、失败补偿
- 转人工上下文移交

### 阶段 C：质量与成本闭环（2～3 周）

- Agent Golden Dataset 与自动评估
- LLM Trace 看板
- 多模型路由和故障切换
- FAQ/语义缓存
- 用户反馈和人工复核回流

### 阶段 D：扩展业务智能（持续）

- 智能质检和运营看板
- 主动服务
- 对话式导购与个性化推荐
- Web 语音客服
- 多租户知识权限与生产级向量库评估

## 七、不建议当前优先投入的方向

| 方向 | 原因 |
|---|---|
| 直接训练领域大模型 | 数据质量、评估、成本治理尚未完善，收益不确定 |
| 完全自主的开放式 Agent | 客服写操作风险高，应优先显式工作流和人工确认 |
| 为使用技术而引入多 Agent | 单 Agent + 路由 + 状态机足以覆盖首期场景 |
| 全量替换 Chroma | 先以容量、延迟、可用性指标证明迁移必要性 |
| 独立训练情感模型 | MVP 可先用结构化 LLM 分类，积累标注数据后再比较 |
| 图像生成营销素材 | 与客服主链路关联较弱，优先级低于安全、Agent 和质检 |
