# TDD vs SDD 适用场景对比

> 整理时间：2026-08-01  
> 基于项目实际使用经验总结

---

## 一、TDD（测试驱动开发）

### 核心特征

你提需求 → 我直接跑完 **Red → Green → Refactor** → 交付结果，中间不打断你。

### 适合场景

| 场景 | 示例 |
|------|------|
| **需求明确的功能模块** | "用 TDD 开发商品服务" — 你清楚要什么，我直接交付 |
| **新增 API / 微服务** | "给订单服务加一个退款接口" |
| **Bug 修复 + 回归保护** | "修复购物车数量计算错误，加测试防回归" |
| **重构已有代码** | "把 CartService 的库存校验逻辑提取出来" |
| **补充测试覆盖** | "给 OrderService 的超时取消补上测试" |
| **小范围迭代** | "给商品列表加一个按价格排序的功能" |
| **性能优化** | "把商品详情查询加缓存，用 TDD 保证行为不变" |

### 不适合

- 需求模糊、多方对齐的场景
- 涉及重大架构决策（需要评审和讨论）
- 需要产出需求文档给团队其他成员

### 项目实例

本次 `ai-cs-product` 商品服务开发：一句"用 TDD 开发商品服务"，自动完成了 26 个测试 + 完整实现 + 部署配置。

---

## 二、SDD（规格驱动开发）

### 核心特征

多阶段门禁，每步产出文档，你审批后才进入下一步：

```
specify → clarify → plan → tasks → implement → analyze
```

### 适合场景

| 场景 | 示例 |
|------|------|
| **复杂功能（需要需求对齐）** | "实现完整的电商结算流程" — 需求模糊，需要 clarify |
| **跨团队协作** | 产出 spec.md / plan.md 给前端、后端、测试对齐 |
| **重大架构决策** | "把单体拆微服务" / "从 MySQL 迁移到 MongoDB" |
| **需要审计/追溯** | 合规项目要求每个功能都有 spec → plan → tasks 记录 |
| **需求不明确** | "做一个用户反馈系统" — 到底要哪些字段？哪些流程？ |
| **多人并行开发** | tasks.md 拆成独立任务，多人认领不冲突 |
| **对外交付的项目** | 客户需要看 spec 和 plan 才能验收 |

### 不适合

- 简单功能、小改动（杀鸡用牛刀）
- 个人项目快速迭代
- 已经很明确只需要写代码的场景

### 项目实例

上次会话的 `001-cart-checkout` 购物车结算流程：经过 specify → clarify → plan → tasks → implement → analyze 六个阶段，产出完整规格文档后逐 task 实现。

## 三、对比总结

```
需求复杂度低 ──────────────────────────────── 需求复杂度高
团队规模小 ────────────────────────────────── 团队规模大
快速迭代   ────────────────────────────────── 需要文档追溯

     ◄── TDD ──►                    ◄── SDD ──►
  "说清楚要什么就行"            "需要讨论、对齐、留痕"
```

| 维度 | TDD | SDD |
|------|-----|-----|
| **交互方式** | 委托式：提需求后直接交付 | 协作式：多阶段门禁，每步确认 |
| **流程** | Red → Green → Refactor | specify → clarify → plan → tasks → implement → analyze |
| **主要产物** | 测试 + 实现代码 | spec.md、plan.md、tasks.md + 代码 |
| **迭代速度** | 快（一口气完成） | 慢（逐步推进，但更扎实） |
| **文档产出** | 无（代码即文档） | 有（规格/计划/任务文档） |
| **适合阶段** | 开发实施阶段 | 需求分析 + 设计阶段 |

## 四、组合使用

实际项目中两者可以**组合使用**：

```
SDD 负责"想清楚"               TDD 负责"做扎实"

specify → clarify → plan         Red → Green → Refactor
        ↓                               ↓
    tasks.md ──── 每个 task ───────► TDD 实现
```

**典型工作流**：

1. 用 **SDD** 完成需求对齐和架构设计（产出 spec.md、plan.md、tasks.md）
2. 每个 task 内部用 **TDD** 编写测试 + 实现代码
3. 最后用 SDD 的 `analyze` 阶段做一致性检查

这样既有需求对齐的文档，又有测试覆盖的保障。
