# 国内主流支付方式分析与本地项目接入方案

> 版本：v1.0　适用项目：ai-customer-service（Spring Cloud 微服务电商）
> 文档定位：分析国内常用支付渠道，给出可接入本地项目的落地方案与实施步骤。
> 说明：文中费率为常见参考值，实际以各渠道官方最新签约费率为准。

---

## 1. 背景与目标

本地商城已具备完整交易链路：**商品商城（/shop）→ 购物车 → 结算下单 → 订单（PENDING_PAY）→ 支付（当前为占位接口）**。
订单模块已预留：

- `POST /api/pay/create`（占位：支付下单）
- `GET /api/pay/status/{orderNo}`（占位：支付状态查询）
- `POST /api/pay/callback/{paymentMethod}`（已有回调入口，验签为 mock）
- `PaymentService` 策略接口 + `PaymentServiceImpl`（当前返回模拟 payUrl）

本文目标：分析国内常用支付方式，设计一套可替换占位实现、可逐步接入真实渠道的支付方案。

### 2.1 按接入方式（产品形态）理解

- **Native（扫码）**：商户生成二维码，用户手机扫码支付。适合 PC 网站、线下门店。本项目 PC 商城首选。
- **JSAPI（公众号/小程序）**：在微信内部支付，需要服务号/小程序 APPID，且网页需在微信内打开。适合公众号商城。
- **H5（手机网站）**：微信外浏览器唤起支付，**要求域名 ICP 备案 + 微信支付 H5 域名配置**，且部分手机浏览器有拦截。
- **APP 支付**：App 内拉起收银台，需要 App 包名/签名，适合移动端 App。
- **付款码/条码（被扫）**：用户出示付款码，商户扫码收款，适合线下收银。
- **合单支付**：电商平台模式，用户一次支付多商家子单，资金分别结算给子商户（微信「平台收付通」/支付宝「合单支付」）。适合平台型多商家电商。

> 本地项目是单商户 PC Web 商城，**微信 Native + 支付宝电脑网站/当面付** 即覆盖主要场景；若以后做多商家平台，再演进到合单支付/分账。

## 3. 各渠道要点

### 3.1 支付宝（推荐首选联调）
- **产品**：电脑网站支付（返回 form 表单/跳转 URL）、当面付（预下单返回二维码串 qr_code）、手机网站、APP、小程序。
- **开放平台**：https://open.alipay.com
- **沙箱**：开放平台「沙箱环境」免费申请，提供沙箱 AppID、应用私钥/支付宝公钥、沙箱买家账号，本地开发最友好。
- **技术要点**：
  - 官方 SDK：`com.alipay.sdk:alipay-sdk-java`（或 IJPay 封装）。
  - 签名：RSA2（应用私钥签名，支付宝公钥验签）。
  - 金额单位：**元**（BigDecimal）。
  - 回调：`notify_url` POST 表单，需验签后返回 `success` 字符串。
- **本地联调**：沙箱回调地址需公网可访问，可用内网穿透（ngrok/cpolar 等）把本地 8087 映射出去，或在沙箱里配置回调为穿透域名。

### 3.2 微信支付
- **产品**：Native（`code_url` 生成二维码）、JSAPI、H5、APP、付款码、合单支付、商家转账/分账。
- **商户号**：企业/个体工商户（营业执照 + 对公账户 + 法人身份证）；**个人无法直接申请 API 收款商户号**（小微商户或无照场景走聚合/收单服务商）。
- **APIv3（推荐）**：官方 Java 库 `com.github.wechatpay-apiv3:wechatpay-java`，自动签名/验签/解密。
- **技术要点**：
  - 证书：商户 API 证书 + 商户私钥；APIv3 密钥；平台证书（动态获取）。
  - 回调：`POST` JSON，需验签（Wechatpay-Signature）+ 解密（AES-256-GCM，resource 字段）。
  - 金额单位：**分**（long/Integer）。
  - 沙箱：微信支付提供沙箱环境（需在商户平台开通/申请），也可用 1 分钱小额真实支付做联调。

### 3.3 银联 / 云闪付
- 一般通过收单机构（银联商务、银行）或聚合服务商接入；银联二维码费率在 2025 年调整后较低（借记卡约 0.2%、贷记卡约 0.5%），适合线下场景。
- 对纯 Web 电商项目，直接接入成本高、周期长，通常不作为首选。

### 3.4 聚合支付（第四方）
- 代表：Ping++（去支付）、收钱吧、拉卡拉、汇付天下、通联支付、易宝支付、富友等。
- **优势**：一个 API/一套回调覆盖微信+支付宝+云闪付，统一下单/退款/对账，接入周期短；扫码费率约 0.38%（收钱吧参考）。
- **代价**：技术年费/接入费（如 Ping++ 渠道费 + 年费），资金经由服务商结算。
- **适合**：追求快速上线、不想分别维护多渠道对接的中小项目。

## 4. 本地项目现状与接入切入点

| 现有代码 | 现状 | 需要改动 |
|----------|------|----------|
| `OrderServiceImpl.createOrder` | 下单后调用 `paymentService.createPayment` 生成模拟 payUrl | 改为调用渠道适配器，返回真实支付参数（code_url / 跳转 form） |
| `PaymentService` / `PaymentServiceImpl` | 策略接口 + mock 实现 | 保留接口，新增 `PayChannel` 抽象，实现支付宝/微信/聚合渠道 |
| `PayController`（/pay/create、/pay/status） | 占位返回 | 对接渠道下单/查询；保持对外契约不变 |
| `PayCallbackController`（/pay/callback/{method}） | 验签 mock | 实现微信 v3 验签+解密、支付宝 RSA2 验签；幂等更新订单状态 |
| `OrderStatus` / 超时取消（RocketMQ 延迟消息） | 已实现 PENDING_PAY→CANCELLED | 保持不变，支付成功回调走 PENDING_PAY→PAID |
| 前端 `/shop` | 「去支付」调用占位接口 | 新增二维码/跳转 + 状态轮询 + 支付结果页 |
| Nacos `aics-shared.yml` | 无支付配置 | 新增渠道配置（appId/密钥/商户号/回调地址/沙箱开关） |

## 5. 推荐方案与选型

### 方案 A（推荐）：支付宝 + 微信 Native 双通道直连
- **支付宝**：电脑网站支付（PC 跳转）+ 当面付（扫码），先走**沙箱**联调。
- **微信支付**：Native 扫码（PC 商城），申请商户号后接入。
- 优点：无中间商，费率透明，资金直达商户，合规清晰；支付宝沙箱可先行完成全流程开发。
- 缺点：需要分别维护两套 SDK/验签；微信需要营业执照商户号。

### 方案 B：聚合支付（Ping++ / 收钱吧）
- 一套 API 覆盖微信/支付宝/云闪付，统一回调、退款、对账。
- 优点：开发量最小、上线最快、一个适配器即可。
- 缺点：引入服务商费率与年费；依赖第三方稳定性。

### 选型建议
- **本地开发/演示**：方案 A，先用**支付宝沙箱**跑通全链路，微信商户号下来后补 Native。
- **快速上线**：方案 B，聚合渠道一个接口搞定。
- 架构上两种方案可共存：**先定义 `PayChannel` 抽象，支付宝/微信/聚合各实现一个适配器**，后续切换只是加一个实现类。

## 6. 技术架构设计

### 6.1 支付渠道抽象

```text
PayChannel (interface)
├── createPayment(orderNo, amount, subject, paymentMethod) -> PayResult(codeUrl | form | jumpUrl)
├── queryPayment(orderNo) -> PayStatus
├── refund(orderNo, amount) -> RefundResult
├── closeOrder(orderNo)
└── verifyNotify(raw, headers, body) -> NotifyResult(orderNo, success)

PayChannelFactory
└── getChannel(paymentMethod): PayChannel   // ALIPAY / WECHAT / UNIONPAY / AGGREGATE
```

- 复用现有 `PaymentService` 策略语义，内部委托给 `PayChannelFactory` 选中的渠道。
- 新增 `payment_method` 与渠道映射：`ALIPAY→AlipayChannel`、`WECHAT→WechatNativeChannel` 等。

### 6.2 时序（Native 扫码为例）

```text
前端 /shop 点击去支付
  └─> POST /api/pay/create {orderNo, paymentMethod: WECHAT}
       └─> OrderService 校验订单（PENDING_PAY）
            └─> WechatNativeChannel.createPayment
                 ├─> 微信 Native 下单（out_trade_no=orderNo, amount=分）
                 └─> 返回 code_url
       <-- {payType: QRCODE, codeUrl, orderNo}
前端渲染二维码 + 每 3~5s 轮询 GET /api/pay/status/{orderNo}
  └─> 用户微信扫码支付
       └─> 微信异步回调 POST /api/pay/callback/WECHAT（验签+解密）
            └─> 幂等：订单 PENDING_PAY -> PAID，更新 pay_time
                 └─> 投递 RocketMQ notify-topic（前端 WebSocket 收到"支付成功"）
前端轮询到 PAID -> 跳转订单详情/支付成功页
```

### 6.3 关键实现要点

1. **回调验签**（安全红线）
   - 支付宝：RSA2 验签（支付宝公钥），响应 `success`/`fail`。
   - 微信 v3：`Wechatpay-Signature` 验签 + `resource` AES-256-GCM 解密。
2. **幂等与状态机**
   - 回调处理加锁/唯一约束（order_no + 状态判断），重复回调直接返回成功。
   - 状态流转：`PENDING_PAY → PAID`（回调/查询兜底）；超时 `PENDING_PAY → CANCELLED`（已有 RocketMQ 延迟消息）。
3. **金额与单位**
   - 支付宝：元（`BigDecimal`）；微信：分（`long`）。统一在渠道适配器内换算，业务层只用元。
4. **回调地址**
   - 生产：`https://{域名}/api/pay/callback/{method}`，需在渠道后台配置；H5/JSAPI 还要求域名备案。
   - 本地联调：支付宝沙箱 + 内网穿透；微信 Native 扫码可用回调到穿透域名。
5. **订单超时**：沿用现有 30 分钟延迟消息取消；同时支付查询接口兜底（轮询发现已支付但未收到回调时主动更新）。
6. **退款/对账（二期）**：预留 `refund`/`queryRefund`；日终对账下载渠道账单与本地订单比对。
7. **配置中心**：所有渠道密钥放 Nacos `aics-shared.yml`（不提交 git），并支持 `pay.sandbox=true/false` 一键切换沙箱/生产。
8. **日志与监控**：渠道请求/回调/退款全链路日志（已有 slf4j），失败告警可走 notify 服务。

## 7. 落地实施步骤

### 阶段一：渠道接入准备（约 1~2 天）
- [ ] 注册支付宝开放平台账号，创建网页/移动应用，申请**沙箱**（appid、应用私钥、支付宝公钥、沙箱买家）。
- [ ] （可选）申请微信商户号（需营业执照 + 对公账户），开通 Native 支付，生成 APIv3 密钥与商户证书。
- [ ] Nacos `aics-shared.yml` 新增 `aics.pay.*` 配置（支付宝/微信/沙箱开关/回调地址）。

### 阶段二：渠道适配器开发（约 2~3 天）
- [ ] 引入依赖：`alipay-sdk-java`、`wechatpay-java`（或 IJPay 统一封装）。
- [ ] 定义 `PayChannel` 接口 + `PayChannelFactory`。
- [ ] 实现 `AlipayChannel`（电脑网站 + 当面付）、`WechatNativeChannel`。
- [ ] 改造 `PaymentServiceImpl` 委托渠道工厂；`PayController` 的 create/status 对接真实下单/查询。

### 阶段三：回调与订单状态闭环（约 2 天）
- [ ] `PayCallbackController` 实现支付宝验签、微信 v3 验签+解密。
- [ ] 幂等更新订单状态（PENDING_PAY→PAID）+ 投递 RocketMQ 通知。
- [ ] 补单元测试：验签、幂等、状态机、金额换算（遵循项目 TDD/覆盖率门禁）。

### 阶段四：前端接入（约 1~2 天）
- [ ] `/shop`「去支付」根据 `payType` 渲染二维码（qrcode 组件）或跳转支付宝收银台。
- [ ] 支付状态轮询 `GET /api/pay/status/{orderNo}`，成功后跳转订单详情。
- [ ] 订单详情页「立即支付」改为调用真实渠道。

### 阶段五：收尾（约 1~2 天）
- [ ] 退款接口（预留实现）、异常补偿（回调丢失→查询兜底）。
- [ ] 对账任务（可选）、生产配置切换验证（沙箱→正式 1 分钱测试）。
- [ ] 文档 + 联调记录。

## 8. 资质与合规清单

| 事项 | 说明 |
|------|------|
| 营业执照 | 微信/支付宝直连必须（企业或个体工商户），个人无法直接申请 API 收款 |
| 对公账户 | 商户结算账户，微信/支付宝要求对公（个体户可用法人账户） |
| 域名备案 | JSAPI/H5 支付与回调域名需 ICP 备案；Native/电脑网站支付相对宽松，但建议备案 |
| 协议与费率 | 以签约协议为准；费率与结算周期（T+1 常见） |
| 隐私与安全 | 密钥/证书不入库 git；回调验签必做；金额以服务端为准 |
| 无照场景 | 可用聚合服务商或第三方收单（小微进件），或先仅用支付宝沙箱做演示 |

## 9. 风险与注意事项

1. **沙箱≠生产**：支付宝沙箱仅限开发联调，上线前必须在正式环境完整回归（1 分钱实测）。
2. **微信 Native 无同步结果**：Native 只有异步回调，前端必须轮询状态，且回调可能延迟/丢失，查询接口兜底。
3. **金额精度**：BigDecimal 运算，分/元换算统一在适配器，避免精度丢失。
4. **回调重放**：渠道会重试回调，幂等必须做（状态判断 + 唯一约束）。
5. **费率变动**：本文费率是参考值，签约/入网时以官方最新标准为准。

---

## 10. 结论

- 国内商城项目最常对接的是**支付宝 + 微信支付**双通道，云闪付/银联通过聚合渠道间接覆盖。
- 本地项目推荐**方案 A**：支付宝（沙箱先行）+ 微信 Native，抽象 `PayChannel` 适配器，把现有 `/pay/create`、`/pay/callback` 占位实现替换为真实渠道。
- 若追求最快上线，选**方案 B 聚合支付**，开发量最小。
- 两种方案都只需在订单模块内完成，对现有商品/购物车/订单链路无侵入。

> 后续可直接在本项目 ai-cs-order 模块落地：新增 `pay.channel` 包，实现支付宝/微信适配器，并改造现有 `PaymentServiceImpl` 与 `PayCallbackController`。
