## 三、指标口径（先说清楚"s 是多少"）

| 指标 | 定义 | 在本项目怎么取 |
|---|---|---|
| **吞吐** | 单位时间完成的请求数 | `http_reqs / duration` |
| **P95 / P99** | 95%/99% 请求的耗时上界 | k6 内置 `http_req_duration` 趋势 |
| **首 token 时延（TTFB 近似）** | 从发请求到收到第一个字节 | k6 的 `http_req_waiting`；SSE 场景它就是"首 token"的近似值 |
| **整流时长** | 整条 SSE 流读完的时间 | `http_req_duration`（k6 会等流结束才返回） |
| **错误率** | 非预期响应占比 | `http_req_failed`（429 需单独看 `checks`，不算失败） |
| **限流放行率** | 2xx 占比 | 自定义 `checks` 统计 |

**三个必须说明的边界**：

1. **单机压测 ≠ 生产性能**：压测机与被测机同机时，CPU/内存互相挤压，数据只能做相对比较。
2. **LLM 链路不是本项目可控**：`/chat/stream` 的耗时大头是模型生成，测出来的是"端到端体验"，不是"Java 服务性能"。
3. **429 是预期产物**：限流场景下 429 不是错误，恰恰是验证点；阈值里不能把 429 算失败。

## 四、静态基线（可从配置直接算出，✅ 已完成）

### 4.1 网关限流

| 参数 | 值 | 出处 | 解读 |
|---|---|---|---|
| 分布式令牌桶补充速率 | **5 token/s/用户** | [ai-cs-gateway/application.yml:47-49](../ai-cs-gateway/src/main/resources/application.yml) | 持续速率上限 |
| 桶容量（突发） | **10** | 同上 | 允许瞬间 10 个请求 |
| 实现 | Redis + Lua（`RedisRateLimiter`） | [RouteConfig.java:51-53](../ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java) | 多实例共享配额 |
| 本地内存限流（兜底） | 关闭；滑动窗口 60 请求 / 60 秒 | [application.yml:40-46](../ai-cs-gateway/src/main/resources/application.yml) | Redis 不可用时切回 |
| 限流键 | 按用户（`userKeyResolver`） | [RouteConfig](../ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java) | 每用户独立配额 |

**理论计算结果**（30 req/s 持续 30 秒 = 900 请求）：

```text
放行上限 = 桶容量 + 补充速率 × 时长 = 10 + 5 × 30 = 160
拒绝数量 ≈ 900 - 160 = 740
429 比例 ≈ 82.2%
放行请求的平均到达间隔 ≈ 1/5 = 200ms（令牌桶平滑后）
```

> 这就是 [gateway-rate-limit.js](../scripts/loadtest/k6/gateway-rate-limit.js) 跑完后**应该看到**的结果。
> 若实测 429 比例显著偏离 82%，说明：① 限流没生效（Redis 不可用/路由未挂 filter）；② 限流键不是用户维度；③ 脚本并发没打满。

### 4.2 弹性容错（chat 服务）

| 配置 | 值 | 出处 | 影响 |
|---|---|---|---|
| 非流式 LLM 超时 | **30s** | [ai-cs-chat/application.yml:71-73](../ai-cs-chat/src/main/resources/application.yml) | 单次调用上限 |
| SSE 流式超时 | **60s** | 同上:75-77 | 首 token 等待上限 |
| 视觉模型超时 | **5s** | 同上:79-81 | 图片理解上限 |
| LLM 重试 | **3 次**，退避 1s × 2 | 同上:85-88 | 最坏耗时 ≈ 30×3 + 1 + 2 = **93s** |
| 熔断窗口 | 10 次调用，≥3 次开始统计，失败率 50% 打开，30s 后半开 3 次 | 同上:111-117 | 故障时快速失败 |
| 忽略异常 | `BusinessException` / `IllegalArgumentException` 不计入失败 | 同上:94-96 | 业务异常不触发重试/熔断 |

**这组数字的面试用法**：

> "LLM 调用我们配了 30s 超时 + 3 次指数退避重试 + 熔断（50% 失败率、30s 半开）。
> 为什么重试要排除 BusinessException？因为参数错误重试三次也没用，只会放大延迟。"

### 4.3 资源与线程池

| 项 | 值 | 出处 | 解读 |
|---|---|---|---|
| 每服务 HikariCP 最大连接 | **10** | `tools/nacos-config/ai-cs-*.yml`（如 `ai-cs-order.yml:14`） | 单服务连接上限；多服务叠加后要核算 MySQL `max_connections` |
| 使用量上报线程池 | core 1 / max 4 / queue 1000 | `ObservabilityExecutorConfig.java:27-39` | 异步、可丢弃 |
| 在线评测线程池 | core 1 / max 2 / queue 500 | 同上:47-58 | 低优先级 |
| 网关优雅停机 | 30s | [gateway/application.yml:5-7](../ai-cs-gateway/src/main/resources/application.yml) | 滚动发布不丢请求 |
| Nacos 容器堆 | Xms 256m / Xmx 512m | `docker-compose.yml:71-72` | 本地开发配置 |
| RocketMQ Broker 堆 | Xms 512m / Xmx 512m | `docker-compose.yml:137` | 同上 |

### 4.4 静态基线的结论（可以直接写进简历的部分）

- **限流是"每用户 5 QPS、允许 10 个突发"**，不是"全局限流"——这点能讲清就已经超过多数候选人。
- **两层限流分工**：网关边缘限流（保护后端）+ 应用内 Sentinel（保护自身），不是重复建设。
- **LLM 链路有完整的超时/重试/熔断/降级**，而不是"调不通就报错"。

> ⚠️ 方式 B 会真实消耗模型 token。先用 1 VU 跑通再放大；没有 API Key 时只能跑方式 A 或跳过。

## 八、已知风险与限制

1. **单机**：压测机与被测机同机，CPU 争抢会放大 P95。
2. **LLM 外部依赖**：模型厂商限流/网络抖动会污染 SSE 数据，需标注"是否走真实模型"。
3. **Redis 单点**：限流依赖 Redis，Redis 抖动会直接影响放行率。
4. **限流键维度**：脚本默认不带用户标识，实际网关按 `X-User-Id`/IP 分桶；跑测时需确认键解析逻辑，否则所有请求共享一个桶。
5. **脚本未覆盖的链路**：下单、支付、RAG 检索没有压测脚本，需要时按 [08/05 方法论](../learning-docs/08-测试/05-性能压测实战-k6与JMeter.md) 补 JMeter 脚本。
