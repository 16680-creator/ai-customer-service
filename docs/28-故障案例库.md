## C1：订单创建的事务注解失效（自调用）—— 已修复

> **状态：✅ 已修复（2026-10-18）**。修复前有可复现的 RED 测试，修复后 GREEN，order 模块 85 个测试全绿。

### 现象

设计意图是"**分布式锁包住事务**"：先加锁防重复下单，再在锁内开启事务与全局事务。
但按 Spring AOP 语义推演，锁内调用的方法**根本没有事务**（已由集成测试证实）。

### 代码证据

```text
ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java

 73  public OrderVO createOrder(Long userId, List<Long> cartItemIds, Long couponId, String paymentMethod) {
 74      return orderCreateLockService.withCreateLock(userId,
 75          () -> doCreateOrder(userId, cartItemIds, couponId, paymentMethod));   // ← 同类内部调用
 76  }
 78  @GlobalTransactional(rollbackFor = Exception.class, name = "order-create")
 79  @Transactional(rollbackFor = Exception.class)
 92  public OrderVO doCreateOrder(...) { ... }
```

### 根因

Spring 的声明式事务与 Seata 的全局事务都依赖**代理对象**：

```text
外部调用方 → 代理对象(加事务) → 目标对象.createOrder()
                                   └─ this.doCreateOrder()   ← 走的是原始对象，没有代理，注解不生效
```

`createOrder` 本身没有事务注解，`doCreateOrder` 的注解又因为自调用被绕过，于是：
**本地事务与全局事务都可能没开**。锁在事务外是设计目标，但"事务"这一半丢了。

> 同类问题排查方法：全仓搜索"入口方法调用本类带注解方法"的调用点。
> 这也是 [02/15 §5.2](../learning-docs/02-Spring微服务/15-SpringAOP与声明式事务原理.md) 里讲的"事务失效七查"的第一查。

### 影响

| 场景 | 没有事务时会发生什么 |
|---|---|
| 下单主表插入成功、明细插入失败 | 订单头存在但无明细（脏数据） |
| 本地扣减成功、远程库存扣减失败 | 本地已扣、远程未扣（资损） |
| 后续环节抛异常 | 前面的写入不回滚 |

### 为什么单测没暴露

`OrderServiceTest` 用 `@InjectMocks` 创建的是**裸实例**，没有 Spring 代理，自然测不出"注解没生效"。
**只有集成测试（真实 Spring 上下文 + 事务状态断言）才能暴露**——这也是本次补测试的直接动机。

### 验证（已做，2026-10-18）

新增集成测试 `ai-cs-order/src/test/java/com/aics/order/service/impl/OrderCreateTxWiringTest.java`：
用最小 Spring 上下文（`@EnableTransactionManagement` + H2）真实走一遍事务代理，
在 `orderMapper.insert` 被调用的瞬间断言 `TransactionSynchronizationManager.isActualTransactionActive()`。

```text
修复前（RED）：
  OrderCreateTxWiringTest.createOrder_shouldExecuteInsideTransaction
  Expecting value to be true but was false        ← 证明 doCreateOrder 没有事务
修复后（GREEN）：
  Tests run: 1, Failures: 0, Errors: 0
order 模块全量：Tests run: 85, Failures: 0, Errors: 0, BUILD SUCCESS
```

> 这个测试的价值不只是"证明修好了"：它是全仓**第一个**真正的 Spring 上下文集成测试，
> 补上了"143 个单测无法验证注解是否生效"的盲区。

### 采纳的修复

把事务方法拆到独立 Bean（下表第一种方案），`OrderServiceImpl.createOrder` 通过注入的代理调用：

```text
新增  ai-cs-order/.../service/impl/OrderCreateTxService.java
      @GlobalTransactional + @Transactional 的 doCreateOrder（含库存扣减/订单落库/优惠券/延迟消息）
修改  ai-cs-order/.../service/impl/OrderServiceImpl.java
      createOrder → orderCreateTxService.doCreateOrder(...)
      （移除已迁出的 doCreateOrder、generateOrderNo、SEQUENCE 与对应依赖）
修改  ai-cs-order/.../service/OrderServiceTest.java
      注入 OrderCreateTxService mock，委托真实实例执行，原有 9 条业务断言不变
```

**备选方案**（未采用）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **拆 Bean**（推荐） | 把 `doCreateOrder` 挪到 `OrderCreateTxService`，`createOrder` 注入并调用它 | 语义清晰、代理生效 | 多一个类 |
| 注入自身代理 | `@Lazy OrderService self` 或 `AopContext.currentProxy()` | 改动小 | 隐蔽、容易再踩 |
| 编程式事务 | `TransactionTemplate` 包裹 | 不依赖代理 | 代码变长、Seata 集成需另配 |

### 面试话术（三层）

```text
第一层：我们下单是"先加分布式锁、再开事务"，但事务注解加在了被同类内部调用的方法上。
第二层：Spring 事务靠代理，外部调用才经过代理；this.doCreateOrder() 绕过了代理，注解等于没写。
        单测用 @InjectMocks 是裸对象，所以测不出来。
第三层：我们最后把事务方法拆到独立 Bean（OrderCreateTxService），
        并补了一个最小 Spring 上下文 + H2 的集成测试：修复前断言失败（证明真的没事务），修复后通过。
        这件事之后我 review 代码会专门搜"本类方法调本类带注解方法"。
```

## C2：从库复制过滤漏了订单库

### 现象

`deploy/mysql/slave.cnf` 用 `replicate-do-db` 做白名单，但白名单里**没有订单库和商品库**。
结果两台从库只有用户、知识库、会话、Nacos 四个库，**订单和商品数据一条都不过去**。

### 代码证据

```text
deploy/mysql/slave.cnf
 15  replicate-do-db=user_db
 16  replicate-do-db=knowledge_db
 17  replicate-do-db=chat_db
 18  replicate-do-db=nacos_config
     ← 缺 ai_customer_service（订单库）、product_db（商品库）
```

### 影响

1. **读写分离对订单域无效**：所有订单查询仍然打主库。
2. **从库备份不完整**：以为"有从库就安全"，实际订单数据没有副本。
3. **故障切换丢数据**：主库挂了切从库，订单/商品数据缺失。

> 这条最值得讲，因为它把"**冗余 ≠ 备份**"这句话变成了一个具体事故。

### 修复方案

| 方案 | 做法 | 注意 |
|---|---|---|
| 补白名单 | 加 `replicate-do-db=ai_customer_service`、`product_db`，重启从库 | 需要 `STOP SLAVE` → 改配置 → `START SLAVE` |
| 去掉过滤 | 注释掉所有 `replicate-do-db`，复制全量 | 简单，但会把不需要的库也复制过去 |
| 重建复制 | 用 `mysqldump --single-transaction` 重新做全量 + 指定位点 | 最彻底，停机窗口最长 |

### 面试话术

```text
我们做 MySQL 主从时配了 replicate-do-db 白名单，后来盘点发现白名单里漏了订单库和商品库——
从库上根本没有订单数据。这意味着"读写分离"对订单域是失效的，而且从库备份也是不完整的。
这件事让我记住两点：① 冗余不等于备份，备份要单独验证；② 复制过滤这种配置要写进上线检查单。
```

## C3：`pay.sandbox` 死配置

### 现象

Nacos 的支付配置里有 `pay.sandbox: true`，但**全仓没有任何 Java 代码读取这个键**。
改它不会有任何效果，却会让读配置的人以为"沙箱模式已开启"。

### 代码证据

```text
tools/nacos-config/ai-cs-pay.yml:19    sandbox: true
tools/nacos/data/.../ai-cs-pay.yml:19  sandbox: true
代码侧：grep "pay.sandbox" 零命中
```

### 根因

配置演进过程中加了键，但消费代码没跟上（或后来删了代码没删配置）。
**没有"配置键引用检查"这道门禁。**

### 影响

- 误判运行环境（以为在沙箱，实际在真实渠道）；
- 改配置不生效，排查时浪费时间；
- 新人按配置理解系统，形成错误认知。

### 修复方案

1. 要么补消费：`@ConfigurationProperties(prefix = "pay")` 里加字段并在渠道选择处使用；
2. 要么删除该键；
3. CI 增加"配置键引用检查"：把 Nacos 配置的 key 与代码里的 `@Value`/`@ConfigurationProperties` 做差集，孤儿键报警。

### 面试话术

```text
我们盘配置时发现一个 pay.sandbox 的键，Nacos 里有、代码里没人读。这种"死配置"比缺配置更危险，
因为它会让人误判环境。后来我们的做法是把配置键和代码引用做差集检查，孤儿键在 CI 里就报出来。
```

## C4：K8s 清单缺 3 个服务

### 现象

`deploy/k8s/services/` 只有 8 份 manifest，而系统有 11 个业务服务——**order / pay / mq 没有 K8s 部署文件**。
按现有清单部署，K8s 环境跑不起来完整的交易链路。

### 代码证据

```text
deploy/k8s/services/
├── ai-chat-service.yaml
├── api-gateway.yaml
├── knowledge-service.yaml
├── message-service.yaml
├── notify-service.yaml
├── product-service.yaml
├── search-service.yaml
└── user-service.yaml          ← 8 个；缺 order / pay / mq
```

### 根因

新增服务时只补了 Dockerfile 和 compose，没同步 K8s manifest；
Jenkins 的部署服务列表也没有覆盖全量，**环境间发生漂移**。

### 影响

- K8s 环境无法全量部署；
- CI/CD 显示的"部署成功"只覆盖 8 个服务，产生虚假安全感；
- 本地 compose 能跑、K8s 跑不通，排查成本高。

### 修复方案

1. 按现有模板补 3 份 manifest（Deployment + Service + 探针 + 资源限制）；
2. Jenkins 部署列表扩容到 11 个；
3. 加一条门禁：**服务清单（pom modules）与 K8s manifest 数量不一致时构建失败**。

> 参考：[16/08 补全 order/pay/mq 的 K8s 清单](../learning-docs/16-云原生与GitOps/08-补全order-pay-mq的K8s清单.md)（方案已写，落地待做）。

### 面试话术

```text
我们本地用 docker-compose 能起 11 个服务，但 K8s 清单只有 8 个，缺订单、支付、MQ。
这是典型的环境漂移：CI 显示部署成功，其实核心交易链路根本没上去。
后来我们加了"模块清单 vs manifest 清单"的一致性检查，避免再漏。
```

## 二、怎么把案例讲成面试故事

### 2.1 四段式模板

```text
1. 背景（20 秒）：我在做什么功能，为什么会碰到这个问题。
2. 现象（30 秒）：出现了什么异常/我发现了什么不一致。
3. 定位（1 分钟）：我怎么缩小范围（日志/断点/对比配置/写测试复现）。
4. 根因 + 修复 + 验证（1 分钟）：根因是什么、怎么修、怎么证明修好了。
```

### 2.2 三个加分动作

| 动作 | 效果 |
|---|---|
| 说出**排查路径**而不是直接说答案 | 证明你会定位，不是背题 |
| 说出**为什么单测没发现** | 证明你理解测试的边界（C1 的加分点） |
| 说出**怎么防止再发生** | 从"修 bug"升级到"改流程"（C3/C4 的加分点） |

### 2.3 不要做的事

- 不要把"待验证"说成"已修复"（C1）；
- 不要编造故障时长、影响用户数；
- 不要把别人的故障说成自己主导的。
