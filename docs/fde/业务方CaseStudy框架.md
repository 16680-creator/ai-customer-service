# 业务方 Case Study 写作框架

> **这是什么**：FDE 求职与交付中最重要的一份"非技术文档"。客户业务负责人、采购、下一个潜在客户看的都是它，而不是你的架构图。
>
> **和交付手册的分工**：
> - 交付手册 = 给**已经在合作**的客户，回答"怎么装、怎么验、怎么运维"。
> - Case Study = 给**还没合作**的人，回答"你解决过类似我的问题吗、效果如何"。
>
> **写完的检验标准**：把这份 Case Study 念给一个完全不懂技术的人听，他能复述出"你帮谁、解决了什么、好到什么程度"，就算合格。

---

## 一、三条铁律

**1. 不出现技术名词。**
读者不关心 Spring Cloud、RAG、向量库。出现一次技术名词，你就从"能解决问题的人"降级成"写代码的人"。

**2. 每个结论必须带数字，每个数字必须能追溯来源。**
"效果显著提升"是废话；"平均首次响应从 4 分 12 秒降到 38 秒（来源：客服系统周报，连续 4 周均值）"才是证据。
**没有测量方法支撑的数字，比没有数字更糟**——被追问一句就崩了。

**3. 写客户的胜利，不写你的辛苦。**
"我加班两周重构了检索层"没有价值；"上线后客服不再需要记 12 份手册"才有价值。

---

## 二、框架（9 段，全文控制在 2 页内）

### 段 1｜一句话结论

> 【格式】为 `{客户类型}` 解决了 `{具体问题}`，`{核心指标}` 从 `{前}` 改善到 `{后}`。

示例：
> 为一家日均 800 通咨询的电商客服团队，解决了重复政策问题占用大量人力的问题，首次响应时长从 4 分 12 秒降至 38 秒，新客服独立接待的准备周期从 2 周缩短到 3 天。

### 段 2｜客户与场景

| 项 | 内容 |
|---|---|
| 客户类型 | 【填写】行业 + 规模，可匿名（如"某跨境电商，客服团队 12 人"） |
| 业务场景 | 【填写】一段话，说清他们在做什么生意 |
| 决策链 | 【填写】谁提的需求、谁批的预算（体现你理解客户的决策机制） |

> 【填写指引】客户名称能不能写要提前问。不能写就用"某 XX 行业客户"，但规模和业务量要写实，否则读者无法判断相关性。

### 段 3｜问题与代价（最重要的一段）

> 【填写指引】这一段决定读者会不会往下看。必须把"痛"翻译成**钱、时间、人力、风险**四种语言中的至少两种。

| 现状 | 具体表现 | 代价 |
|---|---|---|
| 【填写】 | | 每月约 `N` 人天 / `N` 元 / `N` 次客诉 |

示例：
| 现状 | 具体表现 | 代价 |
|---|---|---|
| 重复问题占大头 | 退换货政策、物流时效、发票三类问题约占总咨询量 6 成 | 约 5 名客服人力被低价值问题占用 |
| 答案不统一 | 政策分散在 12 份文档中，不同客服口径不一致 | 每月约 15 起口径不一致投诉 |
| 新人上手慢 | 培训 2 周才能独立接待 | 旺季无法快速扩编，峰值排队时长超 8 分钟 |

> 【填写指引】数字从哪来？**必须写清来源**：「来源：客户客服系统 2026 年 3 月周报」。写不出来源就删掉这一行，不要编。

### 段 4｜为什么是现在 / 为什么是这套方案

> 【填写指引】回答"为什么不能继续凑合"和"为什么选这条路而不是别的路"。这一段展示专业性，但用业务语言。

- 为什么现在：【填写】触发事件（旺季将至 / 老系统到期 / 人力成本上涨）
- 为什么这个方案：【填写】对比过的其他选择及放弃原因，例如"考虑过直接外包呼叫中心，成本更高且口径仍不统一"
- 关键取舍：【填写】你放弃了什么，为什么可以放弃，例如"暂不做全自动回复，先做辅助人工，避免错误答复带来的合规风险"

> 【填写指引】写出"取舍"是专业度的最强信号。只会罗列功能的人看起来像销售，能说清放弃什么的人才像顾问。

### 段 5｜方案（用人话讲，3 步以内）

【填写指引】用业务动作描述，不用技术动作。每步格式：**谁 + 做什么 + 得到什么**。

示例：
> 1. **运营自己维护知识**：把政策文档上传到后台，当天生效，不需要研发介入。
> 2. **客服得到辅助**：客户提问时，系统实时给出标准答案和出处链接，客服确认后一键发送。
> 3. **答不上来时转人工**：系统判断无法回答或客户情绪激烈时，自动转人工，并把前面的对话一并带过去。

### 段 6｜落地过程与关键决策（展示专业度）

> 【填写指引】挑 2-3 个"差点翻车"的真实时刻。**不要写成顺利的项目**——顺利的项目不可信，也学不到东西。

| 阶段 | 遇到的问题 | 我们的判断 | 采取的action | 结果 |
|---|---|---|---|---|
| 试运行 | 【填写】例：首周准确率只有 58% | 判断不是模型问题，而是政策文档存在多个过期版本 | 先做文档清理专项，再调检索 | 第二周升至 86% |

示例（本项目真实素材，可直接改写使用）：
| 阶段 | 问题 | 判断 | action | 结果 |
|---|---|---|---|---|
| 联调 | 向量库连接持续失败，报"接口已废弃" | 定位为远端向量库只提供新版接口，旧版客户端不兼容 | 升级客户端版本并补齐租户/库名配置 | 入库与检索全部恢复 |
| 联调 | 集合明明存在却报不存在 | 定位为客户端版本的消息匹配缺陷 | 同为版本升级修复，并补进《常见部署失败表》 | 同类问题不再复发 |

### 段 7｜结果（前后对比）

| 指标 | 上线前 | 上线后 | 变化 | 测量方式 |
|---|---|---|---|---|
| 【填写】挑 3 个核心指标，多了反而不可信 | | | | 【填写】工具 + 样本量 + 时间窗 |

示例：
| 指标 | 上线前 | 上线后 | 变化 | 测量方式 |
|---|---|---|---|---|
| 平均首次响应时长 | 4 分 12 秒 | 38 秒 | -85% | 客服系统周报，连续 4 周均值 |
| 新人独立接待准备周期 | 2 周 | 3 天 | -79% | 培训负责人记录 |
| 口径不一致投诉 | 约 15 起/月 | 2 起/月 | -87% | 客诉台账 |

> 【填写指引】一定至少留一个"没达到预期"的指标，并说明原因和计划。全是漂亮数字的 Case Study 会被专业读者直接判定为营销材料。

### 段 8｜客户证言

> 【填写指引】一句原话，注明职位（可匿名）。**不要自己写替客户说**，会被要求核实。

示例：
> "以前新人第一周基本只能旁听，现在第三天就敢独立接单了。"
> —— 客户客服中心负责人

### 段 9｜可复制性与下一步

- 这套方案的适用条件：【填写】什么样的客户能复用（业务特征，不是技术特征）
- 不适用的场景：【填写】诚实说明边界，反而提高可信度
- 客户下一步计划：【填写】

## 三、技术语言 → 业务语言 对照表

> 【填写指引】写完后逐句扫一遍，左边这类句子全部找出来换掉。

| ❌ 技术自嗨写法 | ✅ 业务方看得懂的写法 |
|---|---|
| 基于 Spring Cloud 微服务架构 + Spring AI 框架 | 系统拆成 11 个独立模块，任意一个升级或故障不影响其他模块继续服务 |
| 引入 RAG 检索增强生成，接入 Chroma 向量数据库 | 客户问"怎么退钱"和"退款流程是什么"，都能命中同一条政策，不用记准确说法 |
| 支持 SSE 流式输出 | 答案是一个字一个字显示出来的，客服不用干等 5 秒 |
| 实现多轮对话上下文管理 | 客户不用重复描述问题，第二句可以直接问"那运费谁出" |
| 集成 RocketMQ 实现异步解耦 | 高峰期咨询量突增时，消息先排队不会丢，系统不会被压垮 |
| 支持 Function Calling 工具调用 | 客户问"我的订单到哪了"，系统能直接查订单并回答，而不是让客户自己去查 |
| 单元测试覆盖率 40%+，JaCoCo 门禁 | 每次改动上线前有自动化检查，避免"改一个功能坏一个功能" |
| 提供 Prometheus + Grafana 可观测性 | 出问题能在 1 分钟内定位到是哪个环节慢，而不是靠客服反馈"系统卡了" |
| 三节点高可用部署，MySQL 一主二从 | 单台机器故障时系统仍可用，数据不丢，恢复时间从小时级降到分钟级 |
| 已交付 8 个微服务、200+ 接口 | 已经覆盖客服、知识库、订单、商品、支付全流程，客户不用再单独采购 |
| 采用 SDD/TDD 规范开发 | 需求变更时可快速评估影响范围，改动的风险和时间都更可控 |

**三条替换原则**
1. **技术名词 → 它带来的用户可见变化**（"向量检索" → "换个说法也能搜到"）。
2. **能力清单 → 客户收益**（"支持 X 功能" → "你不用再做 Y"）。
3. **数量指标 → 业务指标**（"200 个接口"没有意义，"覆盖全流程"才有）。

## 四、发布前自检清单

- [ ] 全文无技术名词（或出现时括号里做了业务解释）
- [ ] 段 1 的一句话结论里带数字
- [ ] 每个数字都标注了来源与测量方式
- [ ] 至少一个指标"没达到预期"，并说明了原因
- [ ] 段 6 有至少一个"差点翻车"的真实故事
- [ ] 客户证言已获客户确认（含匿名的措辞）
- [ ] 全文 2 页以内，去掉所有形容词后信息量不变
- [ ] 交给一个非技术朋友读，他能复述"帮谁解决了什么、好到什么程度"
- [ ] 敏感信息已脱敏（内网地址、密钥、客户真实名称、数据样例）

## 五、常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| 写成产品功能介绍 | 读者不知道你能解决他的什么问题 | 每段功能后面补一句"所以客户可以……" |
| 数字全部完美 | 被判定为营销材料，失去信任 | 留一个未达标指标 + 原因 + 计划 |
| 没有客户证言 | 可信度不足 | 交付时就把证言作为交付物之一提前要到 |
| 写"我一个人完成了全部" | 显得不可协作，且不可信 | 写清团队构成与你的具体职责 |
| 技术栈罗列 | 只有同行看得懂，决策者看不懂 | 换成"它带来的可见变化" |
| 没有适用边界 | 后续对接会踩坑，交付预期失控 | 明确写"不适用什么场景" |

## 附：本项目可用的原始素材（改写成业务语言前）

以下都是 `ai-customer-service` 仓库里真实存在的能力与踩坑记录，改写时直接取用：

| 素材 | 出处 | 改写方向 |
|---|---|---|
| 11 个微服务、网关统一入口 | `pom.xml` 模块列表 | 模块化交付能力、单点故障不影响全局 |
| RAG + 向量检索 + 语义缓存 | `ai-cs-chat` 缓存三层设计 | 换个说法也能搜到；高频问题秒回 |
| 热门问答 / 语义 / 向量三级缓存 | `ai-cs-chat/application.yml` | 相同问题不再重复付费调用模型，成本可控 |
| 限流 / 熔断 / 重试 | `resilience4j` 配置 | 模型服务抖动时系统不雪崩，自动退避重试 |
| 人工转接机制 | `specs/005-after-sales-agent` | AI 答不上来时带上下文转人工，客户不用重复描述 |
| 三节点 K8s + 一主二从 + Jenkins 流水线 | `deploy/k8s`、`Jenkinsfile-k8s` | 单机故障不影响服务；发版从小时级到分钟级 |
| 一键自检脚本 | `deploy/scripts/check-local.ps1` | 现场 2 分钟给出全链路健康结论，问题定位不再靠猜 |
| Chroma v1 API 410 / 版本兼容缺陷 | `SPRING-AI-UPGRADE-TASKS.md` | 段 6 的"差点翻车"故事；也证明有真实交付经验 |
| 可观测性栈 | `deploy/observability` | 出问题 1 分钟内定位到具体环节 |
