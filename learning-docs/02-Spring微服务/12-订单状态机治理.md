# 12-订单状态机治理（01-P6 落地记录）

> 2026-08 落地：order 从散落的状态 `if` 校验迁为 Spring StateMachine 4.0 集中迁移表，
> 订单数据库 status 仍是唯一事实来源，状态机不做内存持久化。

## 一、原问题：状态迁移散落

原来 `OrderServiceImpl` 中存在多处：

```java
if (!PENDING_PAY.equals(order.getStatus())) return;
order.setStatus(PAID);
```

支付、手动取消、超时取消、退款确认各自判断；状态一旦增加（如配送中、部分退款）
就会出现漏校验、非法跳转（CANCELLED→PAID）或不同接口规则不一致。

## 二、状态与事件矩阵

```text
PENDING_PAY --PAY-----> PAID --REFUND_REQUEST--> REFUNDING --REFUND_SUCCESS--> REFUNDED
     |
     +--CANCEL/TIMEOUT--> CANCELLED
```

| 当前状态 | 事件 | 目标状态 |
|----------|------|----------|
| PENDING_PAY | PAY | PAID |
| PENDING_PAY | CANCEL | CANCELLED |
| PENDING_PAY | TIMEOUT | CANCELLED |
| PAID | REFUND_REQUEST | REFUNDING |
| REFUNDING | REFUND_SUCCESS | REFUNDED |

未出现在表里的任何组合都拒绝，抛 `BusinessException(BAD_REQUEST)`。

## 三、轻量 DB 事实源模式

本项目选择不使用 `StateMachinePersister`：

```text
DB order.status（唯一事实）
 → 每次请求 reset StateMachine 到 DB 当前态
 → sendEvent
 → 得到目标状态
 → 在现有 @Transactional 内落 DB + 执行业务副作用
```

理由：服务多实例时内存 persister 不共享，反而可能让不同 Pod 看到不同状态；
订单表本来就是可靠持久化事实源。`OrderStateTransitionService` 对单例 StateMachine 加锁，
防止两个线程同时 reset 同一实例串态；高并发升级路径是 `StateMachineFactory` 每次取新实例。

## 四、业务副作用与状态机分离

状态机只做**合法性与目标态计算**，不在 action 里调用 product/pay/MQ：

- PAY：PAID 后发布 `OrderPaidEvent`（AFTER_COMMIT 通知）
- CANCEL/TIMEOUT：CANCELLED 后回补库存、关支付渠道、退优惠券
- REFUND：先 `PAID→REFUNDING`，库存回补成功后 `REFUNDING→REFUNDED`

所有步骤仍在已有 `@Transactional` 中；任一副作用失败则本地事务回滚，不留中间 REFUNDING。
跨服务库存补偿由 Seata AT 承担（见 06/07 Seata 文档）。

## 六、验证

`OrderStateTransitionServiceTest` 覆盖：

- 待支付的 PAY/CANCEL/TIMEOUT 三条合法路径
- 已支付→退款中→已退款链
- 已取消支付、待支付直接退款成功等非法路径拒绝

`mvn -pl ai-cs-order verify`：84 tests 全绿，JaCoCo 门禁通过。

## 七、面试要点

- 状态机解决什么：合法迁移集中声明、拒绝非法跳转、迁移图可视化
- guard/action/builder：本项目只用 builder；未来库存阈值等前置条件可加 guard，副作用可加 action
- 为什么不用工作流引擎：5 态订单线性流转用状态机足够；跨人审批、多分支长流程才考虑 Flowable
- 为什么 DB 是事实源：多实例下内存状态不可靠；每次 reset 的成本换取一致性与简单性
