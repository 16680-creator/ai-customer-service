## 一、P1：Seata XID 传播修复 + 调用方式统一｜3 天 ⚠️ 正确性优先

### 现状锚点与缺陷推理链

```
OrderServiceImpl.createOrder（@GlobalTransactional）
  → ProductStockClient.deductStock()   // RestTemplate，无 TransactionContextInterceptor
  → 裸 RestTemplate 发出的请求【不带 TX_XID 头】
  → product 扣库存的 @Transactional 是独立本地事务，直接提交
  → 全局事务回滚时，AT 补偿【覆盖不到】product 的扣减
  → 实际靠 ProductStockClient javadoc 描述的手工回补兜底（旧机制仍在跑）
```

即：Seata 学习文档（06-Seata分布式事务AT模式.md）声称「已改 AT、XID 自动传播」，
代码现实是**文档漂移**——双机制并存，且 AT 的下游分支实际未生效。测试可能因为手工回补
「看起来回滚了」而掩盖了缺陷。

### 方案

1. **order 迁 Feign**（对齐 chat 的成熟模式）：引入 `spring-cloud-starter-openfeign`
   （loadbalancer 已在依赖里），照 chat 的 11 个 FeignClient 样板写
   `ProductClient` / `PayClient`；删除 `RestTemplateConfig`、`ProductStockClient`、
   `OrderPayClient`，迁移 `CartServiceImpl` 里的服务名调用
2. Seata 对 Feign 有自动 XID 传播（`SeataFeignClient` 拦截器），迁移后 XID 自动随请求头走
3. 核对下游接收侧：product/pay 是 seata-spring-boot-starter，MVC 的
   `SeataHandlerInterceptor`（读 `TX_XID` 头绑定/解绑上下文）1.7.x 默认注册——
   在测试环境打印日志验证，若未注册则显式开启
4. **收敛为单一路径**：迁移后删除手工回补循环（或降级为 `@GlobalTransactional` 失败后的
   显式补偿注解说明），避免双机制并存掩盖问题
5. 修正 06-Seata 文档与 `ProductStockClient` javadoc 的漂移描述

### 任务清单（✅ 2026-08 已落地，技术文档见 [02-Spring微服务/07](../../02-Spring微服务/07-服务调用统一与SeataXID传播.md)）

- [x] order 引入 openfeign，新建 ProductClient/PayClient（旧 RestTemplate 客户端与配置类删除）
- [x] 迁移 OrderServiceImpl / CartServiceImpl 全部调用点（closePayChannel 收敛为单一 try/catch）
- [x] `mvn -pl ai-cs-order verify` 全绿（74 测试 + JaCoCo 门禁通过）
- [ ] 端到端 XID 故障注入验证 → 依赖 Testcontainers（01-P3）就绪后补
      （product 已补 seata-http 依赖，`SeataHttpAutoConfiguration` 的 MVC 绑定条件已具备）
- [x] 修正文档漂移（旧 javadoc 随类删除；OrderServiceImpl/06-Seata 文档描述与实现一致）

### 验收标准

关掉手工回补后，故障注入场景下数据依然一致（这才证明 Seata AT 真正生效）；
order 模块 grep 无 RestTemplate 服务间调用残留。

### 面试要点

XID 传播的完整链路（发起方 RootContext → `SeataFeignClient` 注入 `TX_XID` 头 →
下游 `SeataHandlerInterceptor` 绑定）；RestTemplate 与 Feign 在分布式事务下的差异
（这是「为什么微服务统一用 Feign」的最好论据）；双机制并存如何掩盖缺陷。

## 二、P2：熔断降级体系铺到交易链路｜2~3 天

### 现状锚点

- chat 已有 Resilience4j（`resilience4j-spring-boot3` + timelimiter）+ Sentinel 可抄模式
- 11 个 FeignClient 无任何 `fallbackFactory`；order→product 的同步扣库存没有熔断保护，
  product 挂掉时下单线程池会被拖死

### 方案

1. 统一 Feign 降级：`@FeignClient(fallbackFactory = XxxFallbackFactory.class)`，
   写一个通用模板（记录异常 + 区分降级语义）：
   **查询类**返回兜底数据（如推荐列表空页）；**写类**（扣库存/支付）快速失败抛业务异常，
   绝不返回假成功
2. Resilience4j 铺 order（deductStock 调用加 CircuitBreaker + TimeLimiter）、product、pay；
   阈值先抄 chat 再压测调参
3. Sentinel 规则与 02 计划 P1 的 Dashboard/Nacos 持久化衔接

### 任务清单（✅ 2026-08 代码落地，技术文档见 [02-Spring微服务/08-Feign熔断与降级语义](../../02-Spring微服务/08-Feign熔断与降级语义.md)）

- [x] FallbackFactory 降级语义落地（order 的 ProductClient/PayClient）：
      deductStock/getProduct 快速失败抛业务异常，restoreStock/closeOrder 尽力而为降级
      返回 fail + 告警；4 个降级语义单测，`mvn verify` 78 测试全绿 + 门禁通过
- [x] 熔断接入：`spring.cloud.openfeign.circuitbreaker.enabled: true` 自动包裹全部 Feign 调用
      （比逐方法 @CircuitBreaker 更轻）
- [ ] chat 的 11 个 FeignClient 补 fallbackFactory → 后续批次（chat 侧已有 Resilience4j 方法级熔断
      保护，优先级降低）
- [ ] 真实故障演练（product 宕机 → 3s 快速失败 + CB open）需两服务联调环境，后补
- [ ] 压测调参记录 → 随故障演练一起补

### 面试要点

熔断三态转换与半开探测；读类降级 vs 写类降级的语义红线；Sentinel 与 Resilience4j
在本项目「网关层/调用层」的双层分工。

## 三、P3：网关韧性增强（分布式限流 + 熔断重试）｜2 天

### 现状锚点

- `RateLimitFilter` 是本地内存限流（实例字段），网关多实例时配额互不共享、形同虚设
- 下游挂掉时网关直接透传 500，无统一降级响应

### 方案

1. 替换为 Spring Cloud Gateway 内置 `RequestRateLimiter` filter + Redis 令牌桶
   （`spring-boot-starter-data-redis-reactive`，Lua 原子脚本，多实例配额共享）；
   key 用 `X-User-Id`；旧 `RateLimitFilter` 保留一个版本做对照后下线
2. `CircuitBreaker` filter（对下游服务分组，熔断时路由到 fallback URI 返回统一 `Result`）
3. `Retry` filter：只对幂等 GET 启用（POST 绝不重试，写成网关路由约定）

### 任务清单（✅ 2026-08 代码落地，技术文档见 [02-Spring微服务/04 第九节](../../02-Spring微服务/04-SpringCloudGateway网关.md)）

- [x] RequestRateLimiter + Redis 配置（自定义 `redisRateLimiter` Bean，速率进 `RateLimitProperties`；
      键策略与旧实现一致 = 可信用户ID/IP）；双实例配额共享压测需集群环境，后补
- [x] CircuitBreaker/Retry filter 配置（每路由独立 CB 命名 + 统一降级端点
      `GatewayFallbackController`；Retry 仅幂等 GET）；下游宕机端到端降级测试需集群，后补
- [x] 限流参数进 Nacos 动态生效路径（`@ConfigurationProperties` 重绑定，P4 已落地）
- [x] gateway 测试 29 全绿（新增 KeyResolver×3、FallbackController×1）；
      旧 `RateLimitFilter` 保留为 Redis 故障兜底开关（默认关闭）

### 面试要点

Redis + Lua 令牌桶为什么能跨实例一致；网关层熔断（粗粒度/服务级）与调用层熔断
（细粒度/方法级）的分层设计；重试安全性与幂等的关系。

## 四、P4：配置动态化 + 优雅停机（快赢）｜1 天

### 现状锚点

- `@RefreshScope` 仅 1 处；网关限流参数、Sentinel 规则、chat 模型路由参数改一次重启一次
- 全部服务无 `server.shutdown: graceful`，k8s 滚动更新会切断在途请求

### 方案

1. 配置动态化两套机制写清楚（规范文档）：
   - `@ConfigurationProperties` 类：ContextRefresher 刷新后**自动重绑定**，无需额外注解
     （把网关 `aics.gateway.rate-limit.*`、chat `aics.model-router.*` 迁到此模式）
   - `@Value` 字段：必须加 `@RefreshScope`（注意静态字段/构造期读取会失效的坑）
2. 全部 11 个服务加：
   ```yaml
   server:
     shutdown: graceful
   spring:
     lifecycle:
       timeout-per-shutdown-phase: 30s
   ```
3. k8s 侧核对 `preStop` sleep 与 readinessProbe 的摘流时序

### 任务清单（✅ 2026-08 已落地）

- [x] 限流参数迁 `@ConfigurationProperties`（新增 `RateLimitProperties`，gateway 25 测试全绿）；
      chat `ModelRouterProperties` 已是 `@ConfigurationProperties`（其 `@RefreshScope` 属冗余可留）
- [x] 全部 11 个服务加 `server.shutdown: graceful` + `timeout-per-shutdown-phase: 30s`
      （键唯一性校验通过）
- [ ] k8s 滚动更新零丢失压测 → 需集群环境；核对要点已写入运维文档
- [x] 《动态配置的两种机制》补进 [03-Nacos注册与配置中心](../../02-Spring微服务/03-Nacos注册与配置中心.md)；
      优雅停机新文档 [07-运维部署/06-优雅停机与零丢失滚动更新](../../07-运维部署/06-优雅停机与零丢失滚动更新.md)

### 面试要点

`@RefreshScope` 的原理（RefreshScope 缓存销毁重建代理）vs `@ConfigurationProperties`
重绑定（直接重新 bind 现有 Bean）——后者更轻的原因；优雅停机的「摘流 → 等待 → 关闭」三段。

## 六、P6：统一分布式 ID 规范｜1 天（✅ 2026-08 落地，规范文档见 [03-数据库与ORM/04-分布式ID规范](../../03-数据库与ORM/04-分布式ID规范.md)）

### 现状锚点（盘点结论）

- order 所有实体 `@TableId(type = IdType.AUTO)`（DB 自增）；user 分片表用「ID 后四位取模」
  （实体已是 `ASSIGN_ID` ✓）
- 隐患：任何人给新分片表配 AUTO 就是主键冲突事故；且跨库无全局唯一 ID

### 落地记录

1. [x] 规范文档：新增表一律 `IdType.ASSIGN_ID`（MyBatis-Plus 内置雪花）、分片表禁用 AUTO、
       业务主键用 INPUT；存量 AUTO 表不强制迁移（风险边界写明：未分片前单库自洽，
       分片时雪花与存量自增空间不重叠）
2. [x] 规则用守护测试锁死（代替 review checklist 的人肉检查）：
       `ai-cs-user/.../ShardedEntityIdTypeTest` 反射扫描 user.entity 全包，
       断言无 `IdType.AUTO` + User 必须 ASSIGN_ID——2 测试通过
3. [x] 雪花 ID 与分片路由兼容性：ASSIGN_ID 生成 19 位 long，后四位取模路由依旧成立，
       均匀性论证进规范文档第 2.3 节（雪花序列号随机性足以保证末位分布均匀）

### 面试要点

雪花结构（时间戳+机器位+序列）、时钟回拨的两种应对；号段模式 vs 雪花；为什么分片表
不能用数据库自增。
