# 镜像构建优化与安全扫描

> 对应项目：`ai-cs-chat/Dockerfile`（21 行，JAVA_OPTS 可注入）、`ai-cs-order/Dockerfile`（21 行，无 JAVA_OPTS 展开）。

## 一、现状盘点：两份真实 Dockerfile 的同与不同

```dockerfile
# ai-cs-chat/Dockerfile（:1-21，节选关键行）
FROM maven:3.9-eclipse-temurin-17 AS builder            # :3 阶段一
COPY pom.xml .
COPY ai-cs-common/pom.xml ai-cs-common/
COPY ai-cs-chat/pom.xml ai-cs-chat/
RUN mvn dependency:go-offline -B -pl ai-cs-chat -am     # :10 先锁依赖层
COPY ai-cs-common/ ai-cs-common/
COPY ai-cs-chat/ ai-cs-chat/
RUN mvn package -pl ai-cs-chat -am -DskipTests -B       # :14 源码层
FROM eclipse-temurin:17-jre-jammy                       # :17 阶段二
COPY --from=builder /build/ai-cs-chat/target/*.jar app.jar
EXPOSE 8083
ENTRYPOINT ["sh", "-c", "java ${JAVA_OPTS:-} -jar app.jar"]   # :21 JAVA_OPTS 可注入
```

```dockerfile
# ai-cs-order/Dockerfile（:16-21）
FROM eclipse-temurin:17-jre-jammy
COPY --from=builder /build/ai-cs-order/target/*.jar app.jar
EXPOSE 8087
ENTRYPOINT ["java", "-jar", "app.jar"]                  # :21 没有 JAVA_OPTS！
```

| 观察点 | chat | order | 影响 |
|---|---|---|---|
| 多阶段构建 | ✅ | ✅ | builder 层不进最终镜像（07-运维部署/01 已讲） |
| 依赖层先行 `dependency:go-offline` | ✅ | ✅ | 改源码不重拉依赖，缓存命中 |
| `EXPOSE` | 8083 | 8087 | 与 application.yml:3 端口一致 |
| **JAVA_OPTS 展开** | ✅ `sh -c` | ❌ 直接 `java -jar` | **manifest 里给 order 配 JAVA_OPTS 会被静默忽略**（9 份里 order/product 两份如此） |
| 运行用户 | root（无 USER 指令） | root | 见 §四 |
| 基础镜像 | 完整 JRE（jammy ~300MB 量级） | 同左 | 见 §三 |

**先修一致性，再谈优化**：9 份 Dockerfile 两种 ENTRYPOINT 风格并存，这本身就是漂移（[07 篇](./07-多环境配置与漂移治理.md)）。统一成 `sh -c` 形式是所有后续优化的前置。

一份镜像的体积分层账（chat 实测口径，量级参考）：

| 层 | 内容 | 量级 |
|---|---|---|
| 基础层 | eclipse-temurin:17-jre-jammy 的 JRE + 系统 | ~200-250MB |
| 应用层 | Spring Boot fat jar（依赖树 + 业务类） | ~60-120MB |
| 可省部分 | JRE 未用模块（jlink）、OS 冗余包（alpine/distroless）、构建工具链（多阶段已剔除） | 合计可减一半以上 |

先量再优化：`docker images` + `docker history <image>` 看每层占比，优化打在最大层上才有意义。

## 二、层缓存：顺序即性能

### 2.1 现状做对了什么

`COPY pom.xml` → `go-offline` → `COPY 源码` → `package`：把"变化频率低"的层放前面。只改一行业务代码时，依赖层全部命中缓存，重建只花编译时间。这是 07-运维部署/01 §2.2 讲过的"三个关键设计"之一，此处只补两个纵深点。

### 2.2 纵深点一：单文件 COPY vs 目录 COPY

```dockerfile
COPY ai-cs-chat/ ai-cs-chat/      # 现状：源码目录整体 COPY，任何文件变动都击穿该层
```

Java 场景下源码整体变动本来就必然重新编译，这一层没什么可抠。真正值得抠的是**构建上下文**：`docker build .` 在仓库根执行（`deploy/scripts/k8s-build-push.sh:32-36` 用 `-f ${service}/Dockerfile` + 根上下文），根目录的 `reports/`、`logs/`（仓库里确实有 `green-svc.log` 等文件）都会进上下文，**首传上下文慢且可能把敏感文件带进镜像层**。改进：根 `.dockerignore` 排除 `logs/ reports/ learning-docs/ fun/ tools/` 等。

### 2.3 纵深点二：BuildKit 缓存挂载（编译产物级缓存）

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=cache,target=/root/.m2 \
    mvn package -pl ai-cs-chat -am -DskipTests -B
```

比 `go-offline` 更进一步：本地仓库 `~/.m2` 跨构建持久化，连"新增一个依赖"都不用重新全量下载。CI 高频构建时收益最大。

## 三、jlink：定制运行时，把 300MB 瘦到几十 MB

### 3.1 原理

`eclipse-temurin:17-jre-jammy` 带**全量 JRE**（所有模块），而一个 Spring Boot 服务实际只用一部分。jlink 按 `jdeps` 分析出的模块清单生成定制运行时：

```bash
# ① 用 jdeps 分析依赖（在 builder 阶段对 fat jar 执行）
jdeps --ignore-missing-deps --print-module-deps --multi-release 17 app.jar
#   典型输出：java.base,java.logging,java.naming,java.management,java.security.jgss,java.sql,java.xml,jdk.unsupported

# ② jlink 生成精简运行时（JVM 17 内置 jlink）
jlink \
  --add-modules java.base,java.logging,java.naming,java.management,java.security.jgss,java.sql,java.xml,jdk.unsupported,java.desktop,jdk.crypto.ec \
  --strip-debug --no-header-files --no-man-pages --compress=2 \
  --output /javaruntime
```

```dockerfile
# 三阶段：builder → jlink → runtime（目标态示意）
FROM maven:3.9-eclipse-temurin-17 AS builder
# ... 现有构建步骤不变，追加：
RUN jlink --add-modules $(jdeps --ignore-missing-deps --print-module-deps \
      --multi-release 17 ai-cs-chat/target/*.jar) \
      --strip-debug --compress=2 --output /javaruntime

FROM debian:bookworm-slim        # 或 gcr.io/distroless/base
COPY --from=builder /javaruntime /usr/java
COPY --from=builder /build/ai-cs-chat/target/*.jar app.jar
ENTRYPOINT ["sh", "-c", "/usr/java/bin/java ${JAVA_OPTS:-} -jar app.jar"]
```

### 3.2 收益与代价

| 维度 | 全量 JRE（现状） | jlink 运行时 | 说明 |
|---|---|---|---|
| 镜像体积 | ~300MB 量级（jammy JRE + jar） | 减 100~200MB（量级估算，以实测为准） | 拉取/推送/启动解压都快 |
| 攻击面 | 全模块都在 | 只留用到的模块 | 漏洞扫描项更少（§六受益） |
| 代价 | — | 模块清单要维护；动态加载（SPI/反射）可能漏模块导致运行时 `NoClassDefFoundError` | 建议先在 dev 环境全量回归 |

**务实建议**：本项目先做"零风险的替换"——`eclipse-temurin:17-jre-alpine`（或 distroless java）一步减半；jlink 作为进阶项，因为漏模块的排障成本对学习项目偏高。

## 四、非 root 运行

**现状**：9 份 Dockerfile 均无 `USER` 指令 → 容器内 root。K8s 里若节点未开 `runAsNonRoot` 强制，root 容器逃逸风险更高（容器内 root = 节点 root 的能力大半还在）。

```dockerfile
# 目标态（三行搞定）
RUN groupadd -r app && useradd -r -g app app \
    && mkdir /app && chown -R app:app /app
USER app                          # 之后的一切以 app 身份运行
```

配套检查清单：

| 检查点 | 说明 |
|---|---|
| 监听端口 >1024 | 本项目 8080-8090 全部 >1024，无特权端口问题 ✅ |
| 写文件路径 | Spring 临时目录 `/tmp`、日志路径需 chown（`/tmp` 由 tmpfs 兜底，见 §五） |
| K8s 侧 | `securityContext.runAsNonRoot: true` + `runAsUser: 10001`，双保险防镜像忘了 USER |
| distroless | 若用 distroless 基础镜像自带非 root（`nonroot` tag），USER 行可省 |

## 五、只读根文件系统

K8s 层一行开关（配合 §四）：

```yaml
securityContext:
  runAsNonRoot: true
  readOnlyRootFilesystem: true     # 根文件系统只读：被攻破也写不进 webshell
  allowPrivilegeEscalation: false
  capabilities: { drop: ["ALL"] }
volumeMounts:
  - { name: tmp, mountPath: /tmp }  # JVM 必需：hsperfdata、临时文件
volumes:
  - { name: tmp, emptyDir: {} }
```

**为什么 Java 应用要留 /tmp**：JVM 性能计数文件（`/tmp/hsperfdata_<user>`）、`java.io.tmpdir` 默认路径、部分库解包 native 库——只读根 fs 后这些写操作会失败，所以挂 `emptyDir` 到 `/tmp` 是标准做法。Spring Boot 侧再显式 `java.io.tmpdir` 指向该卷更稳。

改造路径（风险递增，逐个服务灰度）：非 root → allowPrivilegeEscalation=false → drop ALL → 只读根 fs。每步都用 [07-运维部署/08-测试](../08-测试/) 思路回归（起服务、发消息、支付回调）。

## 六、Trivy 扫描与 SBOM

### 6.1 Trivy 镜像扫描（CI 集成点）

```bash
# 阻断式扫描：HIGH/CRITICAL 即失败（CI 里用）
trivy image --exit-code 1 --severity HIGH,CRITICAL \
  192.168.56.12:5000/aics/ai-chat-service:23

# 报告式扫描：只出报告不阻断（观察期用）
trivy image --format table 192.168.56.12:5000/aics/ai-chat-service:23
```

**本项目集成点**：`deploy/scripts/k8s-build-push.sh:31-43` 的循环里，`docker push` 之前插入 trivy 扫描——push 被阻断，坏镜像进不了仓库。起步配置：先观察期跑两周（记录基线漏洞数），再开 `--exit-code 1`，并配 `--ignore-unfixed`（基础镜像没出补丁的漏洞阻断会卡死流水线）。

### 6.2 SBOM（软件物料清单）

```bash
trivy image --format cyclonedx --output sbom.json 192.168.56.12:5000/aics/ai-chat-service:23
```

SBOM = 镜像里"有什么"的机器可读清单（依赖树 + 版本）。价值场景：Log4Shell 类事件爆发时，`grep` 一下全服务 SBOM 就知道谁中招——比逐个 `mvn dependency:tree` 快一个量级。本项目 11 个 Java 服务共用 Spring Boot 3.2.5 + SCA 2023.0.1.0 依赖树（见缺口文档盘点），SBOM 还能监控公共依赖升级的传播面。

再补两个供应链动作（进阶，按需排期）：

```bash
# 镜像签名（cosign）：push 后签名，集群/K8s 准入策略验签后才允许运行
cosign sign --key cosign.key 192.168.56.12:5000/aics/ai-chat-service:23

# 基础镜像固定 digest（digest 不可变，杜绝同 tag 内容漂移）
FROM eclipse-temurin:17-jre-jammy@sha256:<digest>
```

签名的价值与 Registry 的 HTTP 私仓特性相关：`192.168.56.12:5000` 是内网 HTTP 仓库（`Jenkinsfile:11`），谁能推镜像没有准入控制——签名+验签是把"镜像从哪来"变成可校验问题的最短路径。digest 固定则解决 `:latest` 的同 tag 异内容问题（[01 篇](./01-Helm从零到参数化.md) 练习 5 的根治版）。

### 6.3 供应链链条全景（各环节现状）

| 环节 | 现状 | 缺口 |
|---|---|---|
| 源码 → 镜像 | 多阶段 Dockerfile ✅ | pay/mq 缺 Dockerfile；jlink/alpine 可选 |
| 镜像 → 仓库 | `k8s-build-push.sh` 双 tag push（版本号 + latest） | 无扫描、无准入 |
| 仓库 → 集群 | `kubectl set image`，Registry 是 HTTP 私仓（Jenkinsfile:11） | 无签名验签（cosign 为进阶项）；`:latest` tag 有静默升级风险（见 [01 篇](./01-Helm从零到参数化.md) 练习 5） |
| 运行时 | root、可写根 fs | §四/§五 的 securityContext |

## 面试高频问答

**Q1：多阶段构建解决什么问题？**
A：把编译工具链（Maven/JDK）和运行时分离，最终镜像只含 JRE + jar。07-运维部署/01 已精讲本项目实现（builder + jre-jammy 两阶段），此处补充：阶段间 COPY 是唯一数据通道，builder 的任何东西没被 COPY 就不进最终镜像。

**Q2：Docker 层缓存的命中规则是什么？怎么设计层顺序？**
A：逐层比对"指令文本 + 上下文文件内容哈希"，任一变化则该层及之后全部重建。所以按变化频率升序排层：依赖清单 → 依赖下载 → 源码 → 打包。本项目 `go-offline` 先行正是这个原理。

**Q3：jlink 是什么？有什么风险？**
A：JDK 9+ 的运行时裁剪工具，按 jdeps 分析的模块依赖生成最小 JRE。风险是动态加载（反射/SPI）依赖的模块 jdeps 分析不到，运行时才报 NoClassDefFoundError——需要全量回归，建议先上 alpine/distroless 这类零风险瘦身。

**Q4：容器里跑 root 有什么问题？怎么改？**
A：容器内 root 对内核攻击面（提权/逃逸）贡献最大，且 K8s 的 runAsNonRoot 会直接拒绝它启动。改法：Dockerfile 加 USER 指令 + K8s securityContext.runAsNonRoot 双保险；注意监听端口须 >1024、可写路径要单独处理。本项目 9 份 Dockerfile 全是 root，属待改进项。

**Q5：readOnlyRootFilesystem 对 Java 应用的影响？**
A：根 fs 只读后，JVM 写 /tmp/hsperfdata、java.io.tmpdir、解包 native 库都会失败。标准做法是 emptyDir 挂载 /tmp，必要时显式 -Djava.io.tmpdir。收益是被攻破后无法落 webshell/写持久化载荷。

**Q6：Trivy 扫描怎么接入 CI 才不拖垮流水线？**
A：三步走：先观察期（只报告记基线）→ 开 --ignore-unfixed 后阻断 HIGH/CRITICAL（基础镜像无补丁的漏洞不背锅）→ 基础镜像定期升级消化存量。放在 docker push 之前，坏镜像进不了仓库。

**Q7：什么是 SBOM？什么场景下有用？**
A：软件物料清单，机器可读的镜像依赖清单（CycloneDX/SPDX 格式）。核心场景：新 CVE 爆发时秒级定位受影响服务与版本，以及对外交付时的合规证明。本项目 11 服务共享统一依赖树，SBOM 能直观显示公共组件升级的影响面。

**Q8：你们项目的镜像有哪些"供应链级"缺口？**
A：① pay/mq 服务无 Dockerfile；② 9 份 Dockerfile 两种 ENTRYPOINT 风格并存（order/product 不支持 JAVA_OPTS）；③ 全部 root 运行、可写根 fs；④ push 前无扫描无 SBOM；⑤ HTTP 私仓无镜像签名。按"一致性 → 非 root → 扫描 → 只读 fs → 签名"的顺序补。

## 动手练习

1. 复核一致性：`grep -H ENTRYPOINT ai-cs-*/Dockerfile`，确认恰好两份（order/product）不支持 JAVA_OPTS；给 order 补一个 `sh -c` 形式的改法（可对照 08 篇），并用 `docker run -e JAVA_OPTS=-Xmx256m ...` 验证生效。
2. 写仓库根 `.dockerignore`（排除 logs/reports/learning-docs/fun/tools），对比构建上下文传输体积：`docker build` 前后的 `Sending build context` 输出。
3. 在 ai-cs-chat 上实测两版基础镜像体积差：`eclipse-temurin:17-jre-jammy` vs `eclipse-temurin:17-jre-alpine`，记录数字并解释差异来源（musl/glibc、包管理器）。
4. 用 Trivy 扫描本地已构建镜像（`trivy image 192.168.56.12:5000/aics/ai-chat-service:latest`），列出 TOP5 CRITICAL 漏洞及其来源层（基础镜像 or 应用依赖），给出各自修复路径（升级基础镜像 or 升级依赖）。
5. 给 ai-cs-chat 的 K8s 部署加 `securityContext`（runAsNonRoot + readOnlyRootFilesystem + emptyDir /tmp）逐步灰度，观察启动失败就排障（大概率是 /tmp 或日志路径），直到全功能回归通过。
