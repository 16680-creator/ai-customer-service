## 一、什么是配置漂移：成因四分类

**漂移 = 声明的状态与实际运行的状态不一致，且没有机制发现它。** 按层分类：

| 类型 | 含义 | 本项目示例预告 |
|---|---|---|
| ① 交付面漂移 | 该部署的没部署 / 清单间互相矛盾 | order/pay/mq 缺 K8s manifest |
| ② 配置面漂移 | 同一配置在多处定义且值不同 | Nacos 配置写死公网 IP vs compose 服务名 |
| ③ 代码契约漂移 | 注入的配置键，代码根本不消费 | manifest 的 `MYSQL_HOST` 全仓零消费 |
| ④ 密钥面缺口 | 密钥明文散落、无加密无轮换 | Nacos 配置里的明文 API Key |

关键认知：**漂移不是"错误"，是"没有对账机制"的必然结果**——每个漂移点单看都是小事，叠加起来就是"环境间行为莫名不一致"的生产事故源。

## 二、项目实证：六处漂移逐一立案

> 以下全部经 grep/逐行核实，file:line 真实。这节就是 [05-技术缺口分析与补全计划](../00-学习路线总览/05-技术缺口分析与补全计划.md) 文末两个"顺带发现"的展开 + 本次新增发现。

### 2.1 交付面漂移（缺口文档原文立案："K8s 部署缺口"行）

```text
docker-compose.yml  → 12 个中间件服务（mysql/redis/nacos/es/rocketmq×2/minio/
                      mongodb/chroma/neo4j/xxl-job-admin/sentinel-dashboard）
deploy/k8s/services → 8 份业务清单（gateway/user/knowledge/chat/search/
                      message/notify/product）
部署脚本映射        → 只有 7 个服务（k8s-deploy-services.sh:9-20 的 case 表
                      没有 product/order/pay/mq）
```

三层清单互相**对不齐**：

| 差异 | 证据 | 后果 |
|---|---|---|
| order/pay/mq 无 K8s manifest | `deploy/k8s/services/` 目录 ls 实证；缺口文档第三节"K8s 部署缺口"行 | K8s 环境跑不全量 11 服务 |
| product 有 manifest 却没人部署 | `Jenkinsfile:15` 的 `SERVICES` 默认值只有 7 个；`k8s-build-push.sh:8-19`、`k8s-deploy-services.sh:9-20` 的映射表同样没有 product | 清单成了死文件，改了也没人应用 |
| pay/mq 连 Dockerfile 都没有 | `ls ai-cs-pay/`、`ls ai-cs-mq/` 只有 pom.xml + src | 镜像化先于清单化的前置缺口 |

修复交付：[08-补全order-pay-mq的K8s清单](./08-补全order-pay-mq的K8s清单.md)（三份 manifest + Dockerfile 方案 + 脚本映射扩容，全部只写在文档里）。

### 2.2 namespace 漂移（同批清单两种命名空间）

```yaml
# product-service.yaml:5
namespace: aics            # ⚠️ 其余 7 份全部是 ai-customer-service（如 user-service.yaml:6）
```

后果：`kubectl apply -f deploy/k8s/services/` 整目录应用时（`k8s-deploy-services.sh:31`），product 落在另一个 namespace；Jenkins 的 `$NAMESPACE` 参数（`Jenkinsfile:12`）对它不生效，"部署验证"阶段的 `kubectl get pods -n ai-customer-service`（`Jenkinsfile:144`）看不到它。

### 2.3 代码契约漂移：manifest 注入的环境变量，代码不认（本篇核心发现）

manifest 注入 vs 代码真实占位的比对结果（对 8 个服务 src/main 全量 grep）：

| manifest 注入 | 出现于 | 代码真实契约 | 判定 |
|---|---|---|---|
| `MYSQL_HOST/PORT/DB/USER/PASSWORD` | ai-chat/knowledge/message/user 四份清单 | **全仓零消费**（grep 仅命中 manifest 自身） | 死键 ×5。真实数据源在 Nacos 配置里 |
| `ROCKETMQ_NAMESRV` | message-service.yaml:57、notify-service.yaml:47 | `ROCKETMQ_NAME_SERVER`（差两个字母！）见 `ai-cs-notify/src/main/resources/application.yml:27`、chat:61、search:50 | 死键；真实变量名应为 `ROCKETMQ_NAME_SERVER` |
| `MINIO_ENDPOINT/ACCESS_KEY/SECRET_KEY` | knowledge-service.yaml:57-62 | 属性前缀是 `aics.minio.*`（`ai-cs-common/.../storage/MinioProperties.java:10`），宽松绑定需 `AICS_MINIO_ENDPOINT` 形式 | 死键 ×3；且 minioadmin 明文写在清单里 |
| `ELASTICSEARCH_URIS` | search-service.yaml:47 | 代码读 `spring.elasticsearch.uris`（`ai-cs-search/.../config/ElasticsearchConfig.java:37`），宽松绑定需要 `SPRING_ELASTICSEARCH_URIS` | 死键；ES 地址实际走默认值 localhost:9200 |
| `NACOS_NAMESPACE` | 8 份清单全有 | 各服务 application.yml 硬编码 `namespace: aics`（如 `ai-cs-user/src/main/resources/application.yml:19`） | 死键；namespace 实际不随环境变 |
| `REDIS_HOST/PORT` | ai-chat/message 清单 | **有消费**（`ai-cs-chat/src/main/resources/application.yml:51`、gateway:15、product:12） | ✅ 活键（对照组：注入有效的长什么样） |

**规律**：8 份清单里注入了约 20 个业务环境变量，**活键不到 1/4**。原因：早期清单按"服务要连什么中间件"想象编写，而真实配置逐渐迁移进了 Nacos（`config.import` 机制，如 `ai-cs-order/src/main/resources/application.yml:22-24`），清单没跟上。这就是"配置中心化"过程中**代码契约漂移**的典型案例。

### 2.4 死 Nacos 键：`pay.sandbox`（缺口文档"顺带发现"原文立案）

```yaml
# tools/nacos-config/ai-cs-pay.yml:18-19
pay:
  sandbox: true          # ← 无任何 Java 代码消费（@Value/@ConfigurationProperties/占位符全查，零命中）
```

三重问题：① **死键**：发布/回滚/排障的人都会以为它生效；② **双份拷贝**：`tools/nacos/data/tenant-config-data/aics/DEFAULT_GROUP/ai-cs-pay.yml:19` 还有同一份（Nacos 导入数据源），改一处忘另一处就是新的漂移；③ 对照组：同文件 `aics.pay.mock.cashier-url`（:14-17）有真实消费。修复：删除死键（本篇不动工程，仅立项），并把检查做成机制（§四）。

### 2.5 配置面漂移：Nacos 配置写死了环境地址

| 写死的值 | 位置 | 与哪个环境冲突 |
|---|---|---|
| Redis `123.60.31.79` | `tools/nacos-config/aics-shared.yml:7` | compose 里 Redis 是服务名 `redis`（docker-compose.yml:34）；K8s 里是 Service `redis` |
| MySQL `123.60.31.79` | `aics-shared.yml:17`、`ai-cs-order.yml:9`、`ai-cs-pay.yml:3` | compose 里 mysql 服务名 / K8s 里 StatefulSet + Service |
| RocketMQ `127.0.0.1:9876` | `aics-shared.yml:14`、`ai-cs-mq.yml:2` | K8s Pod 里的 127.0.0.1 是 Pod 自己 → **在 K8s 里必然连不上** |
| 例外对照 | `ai-cs-pay.yml:23` 用了 `${ROCKETMQ_ADDR:127.0.0.1:9876}` 占位 | ✅ 活键（可被环境变量覆盖）——正确形态 |

同一份配置要在 compose/本地/K8s 三种环境通用，地址必须参数化（`${...}` 占位 + 环境变量注入）——pay 的写法是项目内已有的正确答案。

### 2.6 双 Jenkinsfile 漂移（同仓库两份流水线，参数默认值不一致）

| 差异点 | Jenkinsfile | Jenkinsfile-k8s | 风险 |
|---|---|---|---|
| `OPENAI_API_KEY` 参数类型 | `string`（:22，值进构建日志） | `password`（:22，脱敏） | 用错文件则密钥泄漏到日志 |

## 交付面
- [ ] compose 服务清单 ⊆ K8s infra 清单？（中间件逐一比对）

- [ ] Nacos 配置里无写死的环境地址？（搜 127.0.0.1 / 具体公网 IP / http://）

## 四、键引用检查：把清单变成可执行动作

### 4.1 三张集合的对账模型

```text
A = 代码真实消费的配置键   （@Value / @ConfigurationProperties / application.yml 占位符）
B = Nacos 配置提供的键     （tools/nacos-config/*.yml）
C = K8s manifest 注入的环境变量（宽松绑定后对应的属性名）

结论 = A ∩ B ∩ C 交集之外的都是问题：
  B - A = 死配置键   （如 pay.sandbox）
  C - A = 死环境变量 （如 MYSQL_HOST、ROCKETMQ_NAMESRV）
  A - B = 缺失配置   （靠代码默认值硬扛，环境敏感项会炸）
```

### 4.2 落地脚本（示例，可放 `scripts/` 演进为 CI 检查）

```bash
#!/usr/bin/env bash
# check-config-drift.sh —— 键引用检查的最小实现（思路示例，非工程交付）
set -euo pipefail

echo "== A：代码消费的配置键 =="
grep -rhoE '@Value\("\$\{[^}]+\}"\)' ai-cs-*/src/main --include="*.java" \
  | sed -E 's/@Value\("\$\{([^}:]+).*/\1/' | sort -u > /tmp/keys_code.txt
grep -rhoE '\$\{[a-z][^}]*\}' ai-cs-*/src/main/resources/*.yml \
  | sed -E 's/\$\{([^}:]+).*/\1/' | sort -u >> /tmp/keys_code.txt

echo "== B：Nacos 配置提供的键（展开成属性路径） =="
yq 'paths | join(".")' tools/nacos-config/*.yml 2>/dev/null | sort -u > /tmp/keys_nacos.txt

echo "== C：manifest 注入的环境变量（宽松绑定转属性名） =="
grep -rhoE 'name: [A-Z_0-9]+' deploy/k8s/services/ \
  | sed -E 's/name: //; s/_(.)/\L\1/g; s/_/./g' | tr 'A-Z' 'a-z' | sort -u > /tmp/keys_manifest.txt

echo "── 死 Nacos 键（B-A，人工复核后删除）:"
comm -23 /tmp/keys_nacos.txt /tmp/keys_code.txt
echo "── 死环境变量（C-A，人工复核后修正/删除）:"
comm -23 /tmp/keys_manifest.txt /tmp/keys_code.txt
```

**工程判断**：脚本输出是**待人工复核的候选**而非自动删除依据——宽松绑定（`aics.minio.endpoint` ← `AICS_MINIO_ENDPOINT`）与默认值 `${X:default}` 都会产生灰区。把它挂进 CI（哪怕每周跑一次出报告），漂移就从"没人发现"变成"每周对账"。

### 4.3 对账的优先级

1. **先治 C - A**（死环境变量）：manifest 是部署行为的直接描述，错误最直接（ROCKETMQ_NAMESRV 这类拼写漂移修一行就活）。
2. **再治 B - A**（死配置键）：pay.sandbox 直接删。
3. **最后治理 A - B**（缺配置）：需要逐键判断"默认值是否可依赖"，与压测/演练联动。

## 面试高频问答

**Q1：什么是配置漂移？有哪些典型成因？**
A：声明的配置/交付状态与实际运行不一致且无对账机制。典型成因：多环境手工操作各改各的、同一配置多处定义、配置中心化后旧注入点没清理、密钥与地址硬编码。按层分：交付面、配置面、代码契约面、密钥面。

**Q2：怎么系统性发现死配置键？**
A：三集合对账：代码消费键（@Value/@ConfigurationProperties/占位符）、配置中心提供键、K8s 注入环境变量（宽松绑定归一后）分别提取，差集即候选死键/缺失键，人工复核后处置。核心是把"感觉有多余配置"变成可执行脚本。

**Q3：Spring Boot 宽松绑定对环境变量注入有什么影响？**
A：环境变量按规则映射到属性：`AICS_MINIO_ENDPOINT` → `aics.minio.endpoint`，`SPRING_ELASTICSEARCH_URIS` → `spring.elasticsearch.uris`。变量名不带对前缀就会变成死键——本项目 MINIO_*（实际属性前缀 aics.minio）与 ELASTICSEARCH_URIS（实际属性 spring.elasticsearch.uris）都踩了这个坑。

**Q4：配置中心（Nacos）和 K8s ConfigMap/环境变量，配置该放哪边？**
A：原则：业务配置（数据源、第三方密钥、业务参数）放配置中心支持动态刷新与集中审计；部署形态相关（副本、资源、探针、服务地址）放 K8s 层。要避免的是两边都放同一项——本项目 MYSQL_* 的教训就是配置中心化后清单注入点成了死键。

**Q5：为什么说"进过 git 历史的密钥必须轮换而不是仅删除"？**
A：git 历史不可变，克隆/备份里仍可回溯提取。正确处置是：立即轮换密钥 → 再从当前版本删除明文 →（可选）历史清洗。本项目 Nacos 配置里的明文 API Key 已在 git 历史中，处置路径就是轮换优先。

**Q6：GitOps 能解决配置漂移吗？**
A：只解决交付层（K8s 资源）的：集群实际态 vs git 声明态可检测可自愈。Nacos 内容、数据库数据不在其管辖内，需要配套"配置进 git + 发布工具推送 + 键引用检查"。两层机制互补，不要指望一个方案覆盖全部漂移。

**Q7：多环境（dev/test/prod）配置管理的最佳实践是什么？**
A：① 环境差异全部参数化（${VAR:default}），配置文件本身环境无关；② 配置随代码进 git，有版本有评审；③ 环境间差异收敛到最小集合（一份差异清单文件）；④ 定期跑环境一致性对账。反模式：每个环境复制一套配置文件、靠人肉保持同步。

**Q8：如果让你接手这个项目做配置治理，第一批做什么？**
A：不动业务代码，先建立"看见"能力：① 跑一遍三集合对账脚本，产出死键/死环境变量清单（本项目实证约 15 个死键）；② 修复成本最低的（manifest 变量名拼写、namespace 统一）；③ 检查清单挂 CI。然后再排 Helm 化与密钥轮换的大动作。
