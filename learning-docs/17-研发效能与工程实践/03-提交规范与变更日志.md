# 提交规范与变更日志

> 对应项目：`git log --oneline -40`（205 条提交的真实 type 分布与不规范样本，本篇 §三 全部为实测数据）、`ai-cs-frontend/package.json`（npm 项目，是 husky 的天然挂载点）、仓库根（无 `.husky/`、无 commitlint 配置，全仓 grep 零命中）。
> 相关：[01-Git工作流与分支模型](./01-Git工作流与分支模型.md)（PR 标题即提交标题）、[06-技术文档写作](./06-技术文档写作.md)（CHANGELOG 是文档的一种）。

## 一、Conventional Commits 完整规范

### 1.1 消息结构

```
<type>(<scope>): <subject>     ← 标题行，≤72 字符，祈使句，结尾不加句号
                                ← 空行
<body>                          ← 可选：写"为什么"，而不是"改了什么"
                                ← 空行
<footer>                        ← 可选：BREAKING CHANGE / Refs / Closes
```

**一行代码看清全貌**：

```
feat(pay): 新增支付宝回调验签

渠道回调先验签再落库，防止伪造通知重复入账。
未通过验签返回 400 并记录审计事件。

BREAKING CHANGE: PayCallbackRequest 移除 sign 字段，改用 SignHeader
Refs: #128
```

### 1.2 type 全集

| type | 含义 | 影响 semver | 本仓库使用频率（205 条实测） |
|---|---|---|---|
| `feat` | 新功能 | **minor**（次版本 +1） | 84 条（41%） |
| `fix` | 缺陷修复 | **patch**（修订号 +1） | 20 条（10%） |
| `feat!` / footer 含 `BREAKING CHANGE:` | 破坏性变更 | **major**（主版本 +1） | 0 条（见 §三） |
| `docs` | 仅文档变更 | 不发版 | 58 条（28%） |
| `chore` | 构建/工具/杂务 | 不发版 | 27 条（13%） |
| `refactor` | 不改行为的重构 | 不发版 | 2 条（1%） |
| `test` | 测试相关 | 不发版 | 4 条（2%） |
| `style` | 格式调整（不影响语义） | 不发版 | 3 条（1.5%） |
| `perf` | 性能优化 | 通常 patch | 0 条（并入 chore(perf) 了） |
| `build` / `ci` | 构建系统 / CI 配置 | 不发版 | 0 条 |

### 1.3 scope 与 breaking 的写法

- **scope**：影响的模块名，与代码结构对应。本仓库已自发形成与微服务一致的 scope：`chat`(11)、`frontend`(10)、`model-router`(9)、`order`(7)、`product`(5)、`gateway`、`tools`、`learning` 等——这是很好的基础，规范只需把它固化下来。
- **breaking 的两种表达**（任选其一，推荐都写）：
  1. 标题加 `!`：`feat(chat)!: 重构 SSE 事件协议`
  2. footer 写 `BREAKING CHANGE: <迁移说明>`——机器解析版本号看 footer，人看迁移说明，所以最好两个都有。

### 1.4 什么样的 subject 是好的

| 反例 | 问题 | 改进 |
|---|---|---|
| `fix: 修复bug` | 没说修了什么 | `fix(order): 30 分钟未支付订单未自动取消` |
| `feat: 新增功能` | 零信息量 | `feat(chat): 语义缓存命中后跳过 Embedding 调用` |
| `1111111111111111111111111` | 完全无意义（本仓库真实存在，sha `db800ed`） | 无法解释就删掉重来 |
| `update` / `修改` / `1` | 排查时毫无线索 | 说清"哪层、什么行为、为什么" |

## 二、与 semver 的关系：提交消息驱动版本号

**语义化版本** `MAJOR.MINOR.PATCH`：

| 版本位 | 何时 +1 | 由哪类提交触发 |
|---|---|---|
| MAJOR | 不兼容的 API 变更 | `BREAKING CHANGE` / `!` |
| MINOR | 向后兼容的新功能 | `feat` |
| PATCH | 向后兼容的缺陷修复 | `fix` |

两个工程要点：

1. **`0.x` 阶段的约定**：MAJOR 为 0 表示"API 不稳定"，此时 breaking 常降级用 minor 表达（`0.3.0` → `0.4.0` 可以含破坏）。本仓库前端 `package.json` 版本号为 `0.0.0` 且未参与发版，处于这个阶段。
2. **自动化的意义**：type 决定版本号、版本号决定 CHANGELOG 分组、tag 触发发布——整条链路可以零人工（§五），前提只有一个：**每条提交消息都符合规范**。这是"为什么要求每一条都规范"的最终答案。

## 三、本仓库 205 条提交的真实分析（实测）

```bash
git rev-list --count HEAD            # 205
git log --pretty=format:"%s" | grep -oE "^[a-zA-Z]+" | sort | uniq -c | sort -rn
```

### 3.1 type 分布

| type | 条数 | 占比 | 评价 |
|---|---|---|---|
| feat | 84 | 41% | 主力，符合"功能开发期"特征 |
| docs | 58 | 28% | 学习文档驱动，风格统一（多为 `docs(learning)`） |
| chore | 27 | 13% | 含脚本/清理，部分承担了 build/ci 的职责 |
| fix | 20 | 10% | 占比偏低——配合"test 仅 2%"看，说明修复多靠手测回归 |
| test | 4 | 2% | ⚠️ 明显偏低（测试多打包进 feat 提交里，见下） |
| style / refactor | 5 | 2.5% | |
| merge / Merge | 3 | 1.5% | 含 `4da4838 merge: ...`——`merge` 不是规范 type |

### 3.2 四类真实的不规范样本（如实记录，sha 可查）

| 样本 | sha | 问题 |
|---|---|---|
| `1111111111111111111111111` | `db800ed`、`be28767` | 占位/无意义标题，bisect 与 CHANGELOG 均不可用 |
| `﻿重构部署架构：从镜像仓库推送改为 tar 包分发` | `d36eeed` | 无 type 前缀，且标题带 BOM 字符（编码产物） |
| `[Spec Kit] feat(001-cart-checkout): implement cart, promotion, order & payment` | `416384e` | type 前多了前缀，commitlint/解析器直接判不合法 |
| `fix(gateway): 淇叜鍙嶉璺敱鍓嶇紑骞…` | `ca34864` | **标题乱码**——提交时终端编码非 UTF-8（GBK）所致 |

另有结构性问题：`fix(tools): 统一后端进程UTF-8启动编码`（`e6809c2`）的出现，与 `ca34864` 的乱码是同一根源——**Windows 下提交与运行环境的编码没统一**；`2390423 docs(report)` 随后 `871d191 chore(finance)` 删除，说明误提交靠"事后删文档"补救，而规范的本意是把审查提前到提交时刻。

### 3.3 scope 分布实测（带 scope 的 100 余条中）

```bash
git log --pretty=format:"%s" | grep -oE "^[a-z]+\(([a-z/-]+)\)" | sort | uniq -c | sort -rn | head
```

| scope | 条数 | 对应模块 | 评价 |
|---|---|---|---|
| chat | 11 | ai-cs-chat | 与微服务命名一致，可直接映射 |
| frontend | 10 | ai-cs-frontend | |
| model-router | 9 | ai-cs-chat 内的子模块 | scope 粒度不一致的样本：同为 chat 的改动，有时 scope=chat 有时 scope=model-router |
| learning | 9 | learning-docs | 文档类提交自成序列 |
| order / product / ai-core / rag | 7/5/4/4 | 对应服务/主题 | |

两个可固化的约定：**scope 枚举 = 服务名清单 + `tools`/`learning`/`specs` 等横切域**（§四 `.commitlintrc.json` 的 `scope-enum` 就是照这份清单写的）；**子模块贡献大的（如 model-router）要么升格为正式 scope，要么统一回父域 chat**——二选一，避免两种粒度并存。

### 3.4 本仓库规范基线总结

**已有资产**：`type(scope): 中文描述` 风格整体成形（前 30 条提交 100% 带 type）、scope 与微服务模块对齐、`docs(learning)` 系列高度一致。
**主要欠账**：① 无工具卡点，乱码/占位提交混入；② test/refactor 使用率低，测试未独立成提交；③ 无 breaking 标记习惯（Spring Boot 3 升级这类改动确实存在，见根目录 `SPRING-AI-UPGRADE-TASKS.md`）。

## 四、commitlint + husky 落地步骤（⚠️ 工程未落地，本节为目标态）

> 现状：全仓无 `.husky/`、无 `commitlint.config.*`、无 `.pre-commit-config.yaml`；`ai-cs-frontend/package.json` 的 scripts 只有 dev/build/preview。以下为可选挂载点一（前端目录，推荐）与挂载点二（纯 Git hook）。

### 4.1 方案 A：husky + commitlint（前端目录已有 package.json）

```bash
cd ai-cs-frontend
npm install -D @commitlint/cli @commitlint/config-conventional husky
npx husky init                       # 生成 .husky/ 并把 prepare 脚本挂进 package.json
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg
```

`.commitlintrc.json`（贴合本仓库约定：允许中文 subject、约束 scope）：

```json
{
  "extends": ["@commitlint/config-conventional"],
  "rules": {
    "type-enum": [2, "always",
      ["feat","fix","docs","chore","style","refactor","test","perf","build","ci","revert"]],
    "scope-enum": [1, "always",
      ["chat","gateway","user","order","product","pay","message","notify","mq",
       "knowledge","search","common","frontend","py-chat","tools","learning","specs"]],
    "subject-empty": [2, "never"],
    "header-max-length": [2, "always", 100]
  }
}
```

验证：

```bash
echo "fix: 修复订单超时未取消" | npx commitlint     # ✔ 通过
echo "1111111" | npx commitlint                     # ✘ 拒绝（type-enum + subject 规则）
```

### 4.2 方案 B：纯 Git hook（不引 Node，适合 Java 侧）

```bash
cat > .git/hooks/commit-msg <<'EOF'
#!/bin/sh
# 标题必须以合法 type 开头（简版卡点，无 Node 依赖）
head -1 "$1" | grep -qE '^(feat|fix|docs|chore|style|refactor|test|perf|build|ci|revert)(\(.+\))?(!)?: .{1,100}' \
  || { echo "✘ 提交标题需符合 type(scope): 描述（见 learning-docs/17/03）"; exit 1; }
EOF
chmod +x .git/hooks/commit-msg
git commit -m "1111" 2>&1 | head -1    # ✘ 被拒绝
```

**两方案的取舍**：husky 配置入库、团队共享，但依赖 Node；`.git/hooks` 零依赖但**不入库**（每台机器手动装）——这正是 husky 存在的理由。Java 侧的格式化/编译卡点见 [08-质量门禁与自动化](./08-质量门禁与自动化.md)。

## 五、CHANGELOG 自动生成（⚠️ 工程未落地，本节为目标态）

两条主流路线对比：

| 工具 | 机制 | 产物 | 适合 |
|---|---|---|---|
| **conventional-changelog**（`conventional-changelog-cli`） | 从提交历史**生成** CHANGELOG.md，不管理版本 | Markdown 变更文件 | 只想要变更日志 |
| **release-please**（GitHub Action） | 提交历史 → 自动开"release PR"（版本号 + CHANGELOG）→ 合并时打 tag | 版本 PR + CHANGELOG + tag | 要全自动发版 |

### 5.1 conventional-changelog 最小落地

```bash
cd ai-cs-frontend
npm install -D conventional-changelog-cli
npx conventional-changelog -p conventional -i CHANGELOG.md -s   # 追加式写入
git diff CHANGELOG.md | head -20    # 按 type 分组、按 scope 归纳
```

### 5.2 版本号如何被自动决定（回顾 §二）

```
feat  → minor    fix → patch    BREAKING CHANGE → major
      └── standard-version / release-please 读取提交自动 bump ──┘
```

对本仓库的预期效果：`docs(learning)` 系列自动进 "Documentation" 分组、`feat(chat)` 进 "Features"、`fix(order)` 进 "Bug Fixes"——205 条提交中约 97% 可被自动归类，只剩 `db800ed` 这类样本被过滤为无效。

### 5.2 release-please 路线（全自动发版，GitHub 原生）

`.github/workflows/release-please.yml`：

```yaml
# ⚠️ 目标态示例：合并即由机器人维护版本与 CHANGELOG
on:
  push:
    branches: [master]
jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          release-type: node        # 本仓库前端为 npm 项目
```

工作方式：机器人读取 master 上新增的提交 → 按 §二 的 type→semver 规则计算下一个版本 → **开一个 "chore(release): x.y.z" 的 PR**（内含更新的 `package.json` 版本号与 `CHANGELOG.md`）→ 人工合并该 PR 时自动打 tag。相比 conventional-changelog 的"手动跑命令"，它把发版也变成了 PR 评审的对象。

**本仓库的适用判断**：`ai-cs-frontend` 是唯一的 npm 包且版本停在 `0.0.0`（未参与发版），Java 侧由父 POM 统一管理版本（`pom.xml:9` 当前为 `1.0.0-SNAPSHOT`）——所以 §5.1 的"只生成 CHANGELOG"是更贴合现状的第一步，release-please 留给"开始对外发版"的那一天。

## 六、面试高频问答

**Q1：为什么提交消息要有一套规范？**
A：三个收益随规模放大：① `git log`/`bisect`/`revert` 时提交本身就是索引；② type 驱动 semver 与 CHANGELOG 自动化，发布零人工整理；③ 评审者与后来者从标题就知道改动意图。单人项目同样受益——本仓库 205 条提交里 28% 是 docs，半年后检索全靠标题。

**Q2：Conventional Commits 的完整格式？**
A：`type(scope)!: subject` + 空行 + body + footer。type 是固定枚举（feat/fix/docs/chore/style/refactor/test/perf/build/ci/revert）；scope 可选，写影响模块；`!` 与 footer 的 `BREAKING CHANGE:` 声明破坏性变更；标题行控制在 72~100 字符内、祈使句、不加句号。

**Q3：提交类型与 semver 怎么映射？**
A：feat → MINOR，fix → PATCH，BREAKING CHANGE → MAJOR，其余 type 不触发发版。`0.x` 阶段 API 未稳定，breaking 可用 minor 表达。版本号不该人肉决定——由提交历史机器推导，人只保证每条提交的类型准确。

**Q4：你们怎么保证提交消息合规？**
A：如实回答现状 + 目标态：目前靠约定与自觉（存在乱码与占位提交的真实案例）；落地方案是 commit-msg hook 挂 commitlint（Node 项目用 husky 共享配置，纯 Java 仓库用 `.git/hooks/commit-msg` 正则卡点），规则里固化 type 枚举与 scope 枚举。要点：**卡点放在提交时刻**，事后清洗成本高得多。

**Q5：一条提交应该多大？**
A：原子性——一个提交只做一件事，且该提交独立可构建、可测试。判据：`revert` 这条不会带崩别的功能；bisect 停在这条上能正常跑。反例是把"新功能 + 顺手修 bug + 格式化 30 个文件"混一条，revert 和 bisect 都会被它污染。

**Q6：CHANGELOG 自动生成的原理？**
A：提交历史本身就是结构化数据——解析每条的 type/scope/subject/footer，按 semver 规则计算版本号，按 type 分组渲染 Markdown。conventional-changelog 只生成文档；release-please 更进一步，用"机器人 PR"管理版本与 CHANGELOG，合并即打 tag 触发发布。前提完全依赖提交规范。

**Q7：merge 提交的消息怎么写？**
A：Conventional Commits 没有定义 `merge` type。建议：合并走平台（PR merge）时用平台默认消息（含 PR 编号）；手动合并时用 `chore(release): 合并 xxx 到 master` 这类合法 type，或干脆用 `git merge --squash` 让合并只留下一个规范标题的功能提交——本仓库 `4da4838 merge: 合并 005-after-sales-agent 到 master` 就属于会被 commitlint 拒绝的写法。
