## 一、评审的价值与四个维度

评审不是"找错大会"，而是三层收益：**拦截缺陷**（机器测不出的逻辑与设计问题）、**传播知识**（至少两人懂这段代码）、**保持一致性**（风格与约定靠人眼校准）。效率前提：**机器能查的交给门禁**（格式、覆盖率、静态扫描，见 [08](./08-质量门禁与自动化.md)），人只看机器不懂的东西。

| 维度 | 人不可替代的原因 | 典型问题 |
|---|---|---|
| 正确性 | 业务语义与边界条件机器无法推断 | 空值、并发、事务边界、幂等 |
| 安全 | 攻击面需要人结合场景想象 | 越权、注入、密钥泄漏、日志泄敏 |
| 性能 | 成本感知需要业务量级判断 | N+1、无界集合、同步长调用 |
| 可读性 | "六个月后的自己"是想象题 | 命名、嵌套深度、注释说了什么 |

## 二、正确性维度检查清单

- [ ] **空值与边界**：入参为 null/空集合/0/负数时行为是什么？（对照 `specs/001 spec.md` 验收场景 4："数量修改为 0 或负数"——需求已写明，代码就必须覆盖）
- [ ] **并发与原子性**：check-then-act 两步是否会被并发穿透？（Redis 查重后写库、库存先查后扣）
- [ ] **事务边界**：`@Transactional` 覆盖了所有写操作吗？事务里有没有 RPC/MQ/HTTP 等长调用（回滚不了还拖长事务）？
- [ ] **幂等**：写操作被重放两次会怎样？回调/消费入口有幂等键吗？（本仓库已有 `@Idempotent` 组件，新写入口是否接入）
- [ ] **异常路径**：失败时状态回滚了吗？部分成功怎么办？（下单成功但发消息失败的补偿）
- [ ] **资源释放**：流、连接、锁是否在 finally/try-with-resources 中关闭？
- [ ] **时间与金额**：金额用 BigDecimal 了吗？时区、时间戳单位（秒/毫秒）一致吗？

## 三、安全维度检查清单

- [ ] **越权**：接口校验了资源归属吗？（`orderId` 能否查别人的订单——本仓库 `specs/005 spec.md` 明确"订单归属校验覆盖率 100%"，这是需求级红线）
- [ ] **密钥与凭据**：代码/配置/日志里有没有明文密钥、密码、token？（见 §六案例 2——本仓库真实存在）
- [ ] **注入**：SQL 拼接、动态表名、日志注入（`log.info(userInput)` 带换行伪造日志）。
- [ ] **日志泄敏**：手机号/身份证是否经 `PiiMasker` 脱敏后再打印？（本仓库 `ai-cs-chat/.../util/PiiMasker.java` 已有现成工具）
- [ ] **输入信任链**：前端传来的数量/金额/ID 是否在服务端重新校验？
- [ ] **依赖漏洞**：新增依赖是否引入已知 CVE（只加必要的依赖）。

## 四、性能维度检查清单

- [ ] **N+1 查询**：循环里有没有逐条查库/RPC？
- [ ] **无界集合**：缓存/队列/Map 有没有上限与淘汰？（对照 `VectorCacheStore` 的 L1 上限设计）
- [ ] **同步长调用**：请求线程里有没有秒级外部调用（LLM/支付渠道）？有没有超时与降级？
- [ ] **数据量级假设**：代码在 100 条和 100 万条时行为是否一样？"现在量小"不是理由，要写清假设。
- [ ] **连接池与线程池**：新增的池有拒绝策略吗？默认值是多少？

## 五、可读性维度检查清单

- [ ] **命名说真话**：`map3`、`temp2`、名实不符的方法名；布尔名不带 `is` 前缀的返回值。
- [ ] **嵌套深度**：超过 3 层的 if/for 有没有卫语句/提前返回化？
- [ ] **注释层次**：注释解释"为什么"而非复述"做了什么"。（正面样本：`Idempotent.java` 的类注释先讲语义分层——"Redis SET NX 是加速挡，DB 唯一键仍是终审"，再讲 fail-open 决策——这正是评审希望看到的注释）
- [ ] **方法长度**：一个方法是否只做一件事；超过一屏考虑拆分。
- [ ] **魔法值**：`300`、`0.4` 这类裸常量有没有命名并解释来源？
- [ ] **一致性与项目约定**：错误码、Result 包装、日志格式是否沿用现有约定。

## 六、真实评审意见示例（本仓库代码，行号可核对）

### 案例 1：健壮性——`Wait-Port` 的返回值被丢弃

**被评审代码**（`tools/start-app.ps1`）：

```powershell
# 第 44 行附近（全部启动分支）：
foreach ($svc in $services) { Start-BackendService $svc }
foreach ($svc in $services) { Wait-Port $svc.port 180 $svc.name | Out-Null }   # ← 返回值被丢弃

# tools/lib/common.ps1 第 49-60 行：Wait-Port 超时只 Write-Warning 并返回 $false
```

**差评（不推荐）**："这里不对，失败应该退出。"

**问句式建议（推荐）**：

> 这个 `| Out-Null` 把 `Wait-Port` 的返回值丢掉了——`common.ps1:49` 的实现超时只是 `Write-Warning` + 返回 `$false`，所以服务没起来时脚本会继续跑完、退出码还是 0。这是有意的"尽力而为"设计（反正结尾有 Summary 的 UP/DOWN 汇总），还是希望一键启动在关键服务没起来时以非零码失败？如果是前者，建议把"失败不阻断"写进 `Wait-Port` 的注释；如果是后者，可以收集 `$false` 结尾统一 `throw`。

**这个意见好在哪**：先陈述事实（带 file:line），再用问句确认设计意图而不是断言错误，最后两个分支都给出可执行动作。评审者可能不知道"启动脚本是给人用的，失败汇总已经够用"这个背景——问句给了作者解释空间。

### 案例 2：安全——提交进仓库的明文密码默认值

**被评审代码**（`tools/lib/common.ps1` 第 24 行，值为占位示意）：

```powershell
$DB_PASSWORD = "<明文密码>"     # 真实文件中此处是一个写死的数据库密码，且该文件随仓库提交
```

而 `tools/env.ps1` 第 21-23 行自己就写着分离原则："LLM API keys：**不要写在本文件（本文件会提交到仓库）**。请复制 tools/env.local.ps1 模板填入真实密钥，该文件已被 .gitignore 排除"。

**问句式建议**：

> `common.ps1:24` 给 `$DB_PASSWORD` 设了默认值，而 `env.ps1` 里已明确"密钥不写进入库文件、用 env.local.ps1 分离"的原则——数据库密码是不是也应该走同一条路？建议默认值改为空字符串 + 为空时 fail-fast 提示配置，真实值放 `env.local.ps1`（已 gitignore）或机器级环境变量。另外注意：即使现在改掉，密码已留在 git 历史里，需要轮换（配合仓库已有的泄露扫描脚本 `tools/` 下密钥扫描复核一遍）。

**这个意见好在哪**：① 引用项目**自己的约定**作为标准，评审不再是个人偏好；② 指出"历史泄漏 ≠ 当前文件干净"，给出轮换与扫描的收尾动作；③ 全程没有猜测是谁写的。

> 推而广之：本仓库 `git log` 中出现过标题乱码的提交与 `e6809c2 fix(tools): 统一后端进程UTF-8启动编码`——评审 PowerShell/脚本改动时，"编码与密钥"应作为固定检查项。

### 案例 3：可读性——正面反馈同样要具体

**被评审代码**（`ai-cs-common/src/main/java/com/aics/common/idempotent/Idempotent.java`，类注释节选）：

```java
/**
 * 幂等注解：标注在回调/消费/写操作方法上，以 Redis SET NX 挡住并发重放与重复投递。
 *
 * <p>语义（三层幂等中的第一层"加速挡"，DB 唯一键仍是终审）：
 * ...
 * <li>Redis 故障：fail-open 放行——幂等降级，不能因为去重层故障阻断业务。</li>
 */
```

**好评语（推荐）**：

> 这段类注释是我想在别处复制的标准：先给语义定位（"第一层加速挡，DB 唯一键仍是终审"——读者立刻知道 Redis 挂了也不丢数据的原因），再逐条列出四种调用的行为（含 fail-open 的取舍理由）。建议仓库后续新增的横切注解类组件都照此模板写类注释。

**为什么正面反馈也要写**：① 它定义了"什么是好"，比十条"不要这样"更省沟通成本；② 被点名具体的代码会保持水准（泛泛的 LGTM 对行为没有塑造作用）；③ 评审清单里的"正面规则"（见 §十练习 5）就是这么沉淀出来的。注意好评语同样**要具体到行为**，"写得不错"四个字没有信息量。

## 七、PR 大小控制

### 7.1 为什么 >400 行评审质量骤降

业界多项研究（SmartBear/Cisco 的代码评审数据是常被引用的来源）共同指向：**单次评审超过约 400 行后，缺陷发现率显著下降**——评审者从"逐行理解"退化为"大致扫过"，前 200 行的评论密度远高于后面。机制上有三个原因：

1. **工作记忆有限**：人无法同时持有几百行代码的上下文模型；
2. **注意力衰减**：长 diff 后半段的每个问题都会被"先记着，最后一起看"然后忘掉；
3. **反馈延迟**：大 PR 的评论往往在作者已切换到下一个任务后到达，修复意愿与质量都最低。

### 7.2 本仓库的真实反例与拆分法

`feature/ai-chat-and-frontend` 领先 master **63 个提交**（含前端 P1/P2 页面、Agent 编排、网关路由、可观测性等多主题）——这个体量一次性评审等于不评审。拆分依据现成：**`specs/` 的用户故事就是天然的 PR 边界**（`005/tasks.md` 按 ai-cs-order / ai-cs-product / Agent 编排分阶段，每阶段一个"独立测试"描述）。

| 手法 | 做法 |
|---|---|
| 竖切 | 一个用户故事一个 PR（含它的测试），见 [05](./05-需求拆解与估时.md) 的 US 分组 |
| 分层提交 | 基础层（SQL/枚举/DTO）与业务实现分开评 |
| 特性开关 | 未完成功能用开关藏住，先合骨架 |
| 机械改动单独走 | 格式化、重命名、依赖升级独立 PR 且标注"无需细看" |

### 7.3 评审视角的拆分演练（承接 [01](./01-Git工作流与分支模型.md) §4.5 的分支映射）

分支切好之后，每个 PR 的**评审要点与体量预估**应写在 PR 描述里，评审者按此分配注意力：

| 假想 PR（源自 specs/005 任务阶段） | 预估 diff | 评审侧重 | 必附证据 |
|---|---|---|---|
| 基础层：错误码 + 建表 SQL | 小（<200 行） | SQL 幂等性、错误码段位不冲突 | H2 schema-test.sql 与 deploy SQL 一致 |
| T003-T008 售后命令（测试+实现） | 中（200~400 行） | 归属校验、幂等键设计、事务边界 | AfterSaleServiceTest 全绿 + jacoco check 通过 |
| T011-T015 商品推荐 | 小 | 排序与空结果行为 | ProductRecommendServiceTest |
| Agent 编排与转人工 | 大（需再拆：状态机 / 工具编排 / SSE） | 状态迁移完备性、确认环节不可跳过 | 状态机单测 + SSE 契约测试 |

**规律**：评审侧重跟着该阶段的"独立测试"描述走（`specs/005/tasks.md` 每阶段都有），而不是每次都全套四维清单从头扫——**PR 描述里写"请重点看 X"，是作者对评审者的最大善意**。

## 八、语气、SLA 与小型团队轻量流程

### 8.1 评论语气（对事不对人）

| 场景 | 不要这样写 | 推荐写法 |
|---|---|---|
| 发现问题 | "这里写错了" | "这里在 X 情况下会 Y，你看是否需要处理？" |
| 有更强方案 | "为什么不直接用 Z，这样多绕" | "用 Z 会不会更简单？比如……，主要是出于……的考虑" |
| 明确阻塞项 | "这个不行" | "这个必须改：A 场景会丢数据。其他都 LGTM" |
| 提建议 | "你应该…" | "建议…" / "考虑…"，并用 `nit:` 前缀区分"必须改/随口提" |

**标记约定**（让作者不用猜严重度）：`[blocking]` 必须改才能合 / `[nit]` 可选 / `[question]` 仅求解释。

### 8.2 SLA 与流程（小型团队轻量版）

| 项 | 建议 | 理由 |
|---|---|---|
| 首次响应 | 1 个工作日内（哪怕只回"明天看"） | 作者最大的痛是"不知道要等多久" |
| 单轮评审 | <24h 完成；大 PR 先给拆分建议 | 防止评审积压阻塞主线 |
| 轮次上限 | 目标 2 轮内收敛 | 无限拉扯说明应该开会而不是评论 |
| 评审人数 | 1 人主评 + 相关方可选 | 小团队全员评审是伪需求 |
| 逃生通道 | 紧急修复可先合后补评（留 issue 记录） | 评审不能成为线上事故的阻塞 |
| 知识沉淀 | 重复出现 3 次的意见 → 写进清单/门禁（升级到 [08](./08-质量门禁与自动化.md) 的机器检查） | 人眼只看新问题 |

### 8.3 评审反模式清单（出现即纠偏）

| 反模式 | 危害 | 对策 |
|---|---|---|
| 只抓格式不抓逻辑 | 人眼干机器的活，真问题漏掉 | 格式问题降级给 Spotless（[08](./08-质量门禁与自动化.md) §五） |
| 只回 "LGTM" | 等于没评审，还留下"已审"假象 | 至少指出一个"我看懂了 X，Y 我按 Z 理解的"确认点 |
| 临合并才评审 | 大批量意见让作者抵触，修复质量差 | PR 开出即评审（草稿 PR 模式先对齐方向） |
| 评审当权力（卡人立威） | 团队学会"绕过评审"而非"通过评审" | SLA 明示轮次上限，争议走第三方仲裁 |
| 意见只留在评审里 | 同样的意见下周再提一遍 | 复现 3 次的意见升级为清单/门禁规则 |
| 只在 diff 里看代码 | 看不到调用方与数据流，误判边界影响 | 追一遍"谁调用它、它调用谁"再下结论 |
| 用"建议"表达强制 | 作者当成可选，问题照样合入 | 强制项用 `[blocking]` 明示，不含糊 |

### 8.4 小团队一页纸评审流程（可直接照做）

```
① 作者：按用户故事竖切 → 开 PR → 描述里写"改动意图 + 请重点看 X + 自测证据"
② 评审者：1 个工作日内响应；先读描述再读 diff；意见全部带 [blocking]/[nit]/[question] 前缀
③ 作者：逐条回应（不接受的意见写明理由，不默许消失）；[blocking] 全部修复
④ 评审者：确认修复后批准（说明"我确认了什么"，而非只点按钮）
⑤ 合并：squash + Conventional Commits 标题；PR 里的关键取舍摘录进 spec 或文档
⑥ 收尾：复现 3 次的评审意见 → 升级为清单/门禁规则（回到 [08](./08-质量门禁与自动化.md)）
```

六步里的关键设计：**②先读描述**（评审者先建立"作者想干什么"的模型，再检验 diff 是否兑现）、**④写明确认内容**（批准是一份微型评审报告，不是点赞）。

## 九、面试高频问答

**Q1：Code Review 到底在评审什么？**
A：四个维度——正确性（边界/并发/事务/幂等）、安全（越权/密钥/注入/泄敏）、性能（N+1/无界集合/同步长调用）、可读性（命名/嵌套/注释层次）。前提是把格式、覆盖率这类机器能查的交给自动化门禁，人只看机器不懂的业务语义。

**Q2：为什么 PR 超过 400 行评审质量会下降？**
A：评审研究普遍发现超过约 400 行后缺陷发现率显著下降：人的工作记忆无法一次持有大 diff 的完整上下文，注意力随行数衰减，且评论到达时作者往往已切走。对策是按用户故事竖切 PR、基础层与业务分层提交、机械改动单独走。

**Q3：评审意见怎么写更容易被接受？**
A：对事不对人 + 问句式：先陈述可核对的事实（带 file:line），再用问句确认设计意图，最后两个分支都给可执行动作。用 `[blocking]/[nit]/[question]` 标注严重度。引用项目自己的约定作为标准，避免"个人偏好"之争。

**Q4：评审发现的问题反复出现怎么办？**
A：升级为机器检查——同一意见出现三次就该进 checklist、linter 规则或 CI 门禁，而不是继续靠人眼。人评的价值在于业务语义（归属校验、补偿逻辑），而非重复抓格式问题。

**Q5：评审和测试是什么关系？**
A：互补且侧重不同。测试验证"代码在已知输入下行为正确"；评审发现"需求理解偏差、未知输入路径、设计耦合"这类测试盲区。覆盖率门禁（如本仓库 jacoco 行 ≥40%）能保底执行路径，但覆盖不到"这个分支根本不该存在"的问题——那正是人评的领域。

**Q6：小团队/单人项目还要评审吗？**
A：单人项目至少做**提交前自评**：`git diff --staged` 逐行过一遍，用同一套四维清单问自己；多人后引入 1 人主评 + 1 工作日 SLA 的轻量流程。关键是把评审从"仪式"变成"拦截器"——门禁（CI 必须过）比人数更重要。

**Q7：遇到"评审意见不同意"怎么办？**
A：先判断是否事实分歧——用基准测试/文档/规范佐证，而不是立场之争；确实是权衡取舍的（性能 vs 可读性），在 PR 里写下决策与理由（这就是文档），按 owner 原则：作者有最终决定权，评审者有升级权（拉第三方仲裁），不允许"默许合入、私下不满"。

**Q8：怎么评一段自己看不懂的代码？**
A：坦白标注 `[question]` 请作者解释设计——"看不懂"本身就是可读性维度的一手证据；如果解释清楚后仍觉得复杂，建议拆分或补注释。评审者不必假装全懂，诚实标注比含糊放行更有价值。

**Q9：评审发现设计层面的问题（不是实现细节）怎么办？**
A：区分"本 PR 修不了的"与"本 PR 引入的"。设计债若非本 PR 引入，记 issue + 在评论里链接，不阻塞合入；若本 PR 把设计推向更糟（如复制粘贴出第三处同样逻辑），必须 `[blocking]`，并给出去重/抽象的具体路径。原则：评审守住"不变更糟"，设计改进靠专门的立项（对应 [05](./05-需求拆解与估时.md) 的 Epic 排期）。

## 十、动手练习

1. 用 §二~五 的四维清单**自评**你最近一次提交：`git show HEAD --stat` 先看体量，再对每条清单逐项打勾/排除，写下一份 10 分钟自评记录。
2. 精读 `tools/lib/common.ps1` 的 `Get-JdkHome`（第 70-95 行）：按 §六案例 1 的问句式模板，给它写一条真实评审意见（提示：候选目录硬编码了 `D:\DevTools\jdk` 等机器路径，是否应该配置化？）。
3. 对照 `specs/005-after-sales-agent/tasks.md` 的阶段 2（T003-T016），把"T008 实现 AfterSaleService"拆成一个假想的 PR：写出 PR 标题（Conventional Commits 格式）、描述里放哪些"独立测试"证据、预计 diff 行数是否 <400。
4. 把 §六案例 2 的安全意见转化为 [08-质量门禁与自动化](./08-质量门禁与自动化.md) 的机器检查方案（提示：pre-commit 阶段的密钥正则扫描，或复用仓库已有的泄露密钥扫描脚本），体验"评审意见→门禁规则"的沉淀路径。
