## 一、结论先行：拆解的全流程

```
需求（一段话）
  → Epic（可交付的业务主题，对应一个 spec 目录）
      → 用户故事（US，用户可感知的最小价值单元，INVEST 校验）
          → 验收标准（Given-When-Then，写完就能变成测试）
              → 任务（T001…，2~8 人时可完成，标注 [P] 可并行与所属 US）
```

**拆解质量的三条判据**：
1. 每条用户故事能**独立交付并演示**（竖切，见 §六）；
2. 每条验收标准**机器可验证**（能翻译成测试用例，见 §三）；
3. 每个任务小到"估时不确定"的会自动暴露（§五的三点估算逼你拆）。

## 二、INVEST 原则：给用户故事做体检

| 字母 | 含义 | 反例（不合格） | 本仓库做法对照 |
|---|---|---|---|
| **I**ndependent 独立 | 不依赖其他故事即可交付 | "先做登录才能测购物车" | `specs/001` 的 US1 购物车管理可脱离优惠/支付独立测试 |
| **N**egotiable 可协商 | 是意图而非合同 | "按钮必须离左边 37px" | spec 写"实时更新小计金额"，实现方式留白 |
| **V**aluable 有价值 | 对用户可感知 | "给订单表加一列" | "系统实时更新小计金额和合计金额"——用户看得到 |
| **E**stimable 可估算 | 足够清楚，能估出大小 | "优化一下性能" | 每条 US 配了独立测试说明，范围封闭 |
| **S**mall 足够小 | 一个迭代内完成 | "实现整个结算流程" | 拆成 US1/US2/US3 三条，各带 P1/P2/P3 优先级 |
| **T**estable 可测试 | 有明确完成判据 | "体验要好" | 验收场景逐条写"假设…当…则" |

**用法**：拆完每个故事用 6 个字母打分，任一不过关就继续拆或重写。最常见的病根是 I（互相依赖）——治法就是竖切。

## 三、用户故事与验收标准（Given-When-Then）

### 3.1 格式

```
作为 <角色>，我希望 <能力/动作>，以便 <业务价值>。

验收标准（每条 = 一个测试用例）：
Given（假设）<前置状态> When（当）<触发动作> Then（则）<可观察的结果>
```

GWT 的价值不在语法，而在**逼你把"实现"翻译成"状态迁移"**——每一条"则"都必须是可观察的外部行为，且可以直接变成测试断言（自动化形态见 BDD 链接文档）。

### 3.2 本仓库真实样本（`specs/001-cart-checkout/spec.md`，摘录）

> ### 用户故事 1 - 购物车商品管理（优先级：P1）
> 用户进入购物车页面，查看已添加的商品列表，可以修改商品数量、删除不需要的商品，系统实时更新小计金额和合计金额。
> **此优先级的原因**：购物车管理是结算流程的入口，用户必须先确认商品和数量才能进入后续结算环节。
> **独立测试**：可以通过添加商品到购物车、修改数量、删除商品、验证金额计算来完整测试……
> **验收场景**：
> 1. **假设** 用户购物车中有 3 件商品，**当** 用户将某商品数量从 1 修改为 3，**则** 该商品小计更新为单价×3，购物车合计金额同步更新
> 2. **假设** 用户购物车中有 3 件商品，**当** 用户删除其中 1 件商品，**则** 该商品从列表消失，合计金额重新计算
> 4. **假设** 用户将某商品数量修改为 0 或负数，**当** 提交数量变更，**则** 系统提示数量无效，保持原数量不变

注意样本里的三个加分写法：**每条故事写明"为什么是这个优先级"**（防拍脑袋排序）、**写明"独立测试"**（INVEST 的 I 的显式证据）、**第 4 条验收场景是异常路径**（不只写 happy path）。对应地，`tasks.md` 里 T025 就有"修改数量超库存、修改数量为0/负数"的测试任务——验收标准与测试任务一一咬合。

### 3.3 另一个样本：写操作必须"确认 + 幂等"（`specs/005/spec.md`，US1 验收场景 2/3 摘录）

> 2. **假设** 用户确认换货申请，**当** Agent 收到确认，**则** 携带幂等键调用订单服务创建售后申请，成功后生成包含订单、商品、规则引用、推荐结果的摘要并持久化审计记录
> 3. **假设** 用户拒绝确认，**当** Agent 收到拒绝，**则** 流程进入 CANCELLED，不执行任何写操作，并解释放弃原因

对比 `specs/001`（纯查询/常规 CRUD），005 的验收标准里出现了**架构级约束**：写操作前强制确认、写操作必须带幂等键、拒绝路径零写操作、全程审计。这展示了验收标准的另一个功能——**把非功能性需求（幂等、审计）写进验收，而不是留到实现时"看心情"**。拆解时若发现某条故事需要这类约束，通常意味着它应该被显式拆出一条独立的验收场景（005 正是这么做的）。

阶段 1：初始化（T001-T005）        ← 模块骨架

### 4.4 咬合检验：验收标准 ↔ 测试任务（specs/005 实测）

拆解质量的终极检验是"每条验收标准都能指到至少一个测试任务"：

| `005/spec.md` US1 验收场景 | `005/tasks.md` 对应测试任务 |
|---|---|
| 场景 2：确认 → 幂等键创建 + 摘要 + 审计 | T003 中的"幂等键去重（重复提交返回首次结果）、创建成功返回申请单号" |
| 场景 3：拒绝 → CANCELLED、零写操作 | T003 中的"重复申请（存在 PENDING→拒绝）"（拒绝路径的状态断言） |
| US3：他人订单号 → 越权拒绝（US3 明文"验收：订单归属校验覆盖率 100%"） | T003 中的"归属校验（他人订单→拒绝）" |
| US1 场景 4：订单不满足换货条件 → 不创建申请并解释 | T003 中的"状态校验（非 PAID→不满足）" |

**审计方法**：把 spec 的验收场景编号列一列，把 tasks 的测试任务断言列一列，画连线——**连不上的两侧都是缺陷**：验收标准没有测试兜底（会被回归），测试任务没有验收来源（可能是在测实现细节而非需求）。这套连线只需要 10 分钟，却能在动工前暴露大部分拆解漏洞。

## 五、估时：故事点 vs 人时，与三点估算

### 5.1 故事点 vs 人时

| | 故事点 | 人时 |
|---|---|---|
| 度量 | 相对复杂度（斐波那契 1/2/3/5/8） | 绝对时长 |
| 优点 | 剥离"谁来做"的差异，聚焦工作量；跨迭代可校准速度（velocity） | 直观，好对外承诺 |
| 缺点 | 需要几个迭代才能建立基准 | 被当成"承诺"后必然掺水 |
| 适用 | 固定团队的迭代节奏 | 一次性外包报价、粗排期 |

**单人/自学项目（如本仓库）的务实做法**：跳过故事点，直接用"任务 ≤1 天"作为粒度约束——`specs/` 的任务没有估时列，但每个任务都小到一个文件/一类改动，超出这个粒度的（如"T008 实现资格校验、幂等创建、查询"）就是需要再拆或补估时的信号。

### 5.2 三点估算：把"不确定"变成数字

```
E = (O + 4M + P) / 6        标准差 σ = (P − O) / 6
O = 乐观值（一切顺利）  M = 最可能值  P = 悲观值（踩到坑）
```

例：实现"订单 30 分钟未支付自动取消"（本仓库真实功能，对应 `OrderTimeoutScheduler`）——
O=2h（RocketMQ 延迟消息一步到位）、M=5h（含补偿扫描兜底）、P=12h（延迟级别与本地时区/重试边界踩坑）。
→ E = (2 + 20 + 12)/6 ≈ **5.7h**，σ = (12−2)/6 ≈ **1.7h**。
对外报"6~8 小时"（E 到 E+σ）而非"5 小时"——**估时的诚实来自分布，而不是拍一个最乐观值**。

什么时候最该警惕：O 与 P 相差超过 5 倍——说明任务里藏了两个东西，回去继续拆（这就是三点估算的"逼拆"机制）。

### 5.3 估时的四个反模式

| 反模式 | 表现 | 解法 |
|---|---|---|
| 估时当承诺 | "估 3 小时"变成"必须 3 小时交付"，后续掺水抢量 | 报区间（E~E+σ）与置信条件，不报单点 |
| 平摊误差 | 10 个任务每个估 2h 就报 20h——误差相加不是相消 | 按任务独立估，汇总时用 σ 的平方和开根号（或至少认识到不确定性是累加的） |
| 忘记非编码时间 | 只估"写代码"，漏联调、写测试、数据准备、文档 | 本仓库 tasks.md 的教训样本：T010/T016"运行全部测试与覆盖率校验"是显式任务——这类"验证任务"必须单列 |
| 用估时掩盖拆解不足 | 一个"3 天"的任务 = 没拆 | O/P 相差超 5 倍即回去重拆（§5.2 的逼拆机制） |
| 只估一次 | 立项时估完再不回头，实施中的偏差无人记录 | 迭代校准：每轮把实际用时回填，修正下一轮的 M 值——估时是活文档 |

## 六、拆解技术：先竖切后横切

```
横切（按技术层）：        竖切（按用户价值）：
  阶段A：建所有表           故事1：改数量→算小计（实体+接口+页面+测试）
  阶段B：写所有 Service     故事2：优惠券→算应付（同上全栈走一遍）
  阶段C：写所有页面
```

| | 竖切 | 横切 |
|---|---|---|
| 首个可用版本 | 最早（故事 1 完即有产出） | 最晚（三层全做完才可见） |
| 风险暴露 | 早（每个故事都过全栈，集成问题立刻现形） | 晚（集成风险积压在最后） |
| 适用 | 产品功能开发（默认选择） | 确实无法竖切的平台/数据基建 |

**横切层的"硬边界"自查**：横切阶段只允许出现"改一行全局配置、建一张表、加一个枚举"这类**没有业务判断**的任务；如果横切层里出现了"实现 X 规则""校验 Y 逻辑"，那不是基建，是还没被竖切切开的故事——退回 §二 用 INVEST 重新切分。

**本仓库的真实印证——两者是配合而非二选一**：`specs/001/tasks.md` 的**阶段 2 基础层**是刻意的横切（建表/枚举/实体/Mapper 一次铺好，"阻塞性前置"），**阶段 3~5 按用户故事竖切**（每个故事内 测试→实现→检查点 独立闭环）。它的边界画得也对：横切只包含**无业务逻辑的纯基建**（建表与 DTO），一旦进入业务行为（校验、金额计算）就回到竖切。许多团队的失败恰恰是横切层过大——把 Service/Controller 都铺完了还没交付任何故事。

## 八、面试高频问答

**Q1：什么是好的需求拆解？**
A：三条判据——每个用户故事能独立交付演示（竖切）、每条验收标准机器可验证（GWT 能翻译成测试）、每个任务小到估时分歧会自动暴露。本仓库 `specs/001~005` 是完整样本：spec 承诺价值、plan 记录决策、tasks 排列执行，三件套互相咬合（验收场景 ↔ 测试任务）。

**Q2：INVEST 是什么？**
A：Independent/Negotiable/Valuable/Estimable/Small/Testable 六个故事质量的检查维度。实践中最常见的病根是 Independent 不达标——治法是竖切：按用户价值切而不是按技术层切。本仓库每条故事显式写"独立测试"一节，就是 I 的落地。

**Q3：故事点和人时怎么选？**
A：固定团队迭代节奏用故事点（相对复杂度，剥离个人差异，用 velocity 校准）；一次性报价、粗排期用人时。单人项目两者都可省——用"任务 ≤1 天"的粒度约束替代。关键是估时输出的是**区间**而非单点。

**Q4：三点估算是怎么做的？**
A：对每个任务估乐观/最可能/悲观三个值，期望 E=(O+4M+P)/6，标准差 σ=(P−O)/6，对外承诺报 E 到 E+σ 的区间。它的隐藏价值是"逼拆"：O 与 P 差距超过 5 倍说明任务里混了两件事，必须继续拆。

**Q5：先竖切还是先横切？**
A：默认竖切（每个故事全栈走通，风险早暴露、价值早交付）；横切只用于无业务逻辑的纯基建（建表、脚手架、DTO），且要给横切层画一条硬边界。本仓库 `specs/001/tasks.md` 的结构是标准示范：阶段 2 基础层横切（阻塞性前置），阶段 3 起按 US 竖切，每个故事测试先行、独立检查点。

**Q6：用户故事的验收标准怎么写才合格？**
A：每条用 Given-When-Then 表达成"状态→动作→可观察结果"，必须覆盖异常路径（数量为 0/负数、库存不足、越权），且逐条可翻译成测试断言。反例是"体验要好""性能要高"这类不可测描述。本仓库 `specs/001` 验收场景 4（数量为 0 或负数）与 `specs/005`（订单归属校验）都是合格样本。

**Q7：AI 能替代需求拆解吗？**
A：能替代"格式化产出"（按模板生成 spec/tasks 骨架，本仓库六件套即由 Spec Kit 工作流生成），不能替代三件事：价值排序的取舍、依赖关系的核实（[P] 并行标记是否属实）、不确定性的识别（三点估算的 P 值来自经验）。AI 产出的任务清单必须过一遍 INVEST 人工校验。

**Q8：估时总是不准，还要估吗？**
A：估时的首要价值不是"估准"，而是"暴露不确定性"：输出区间（E~E+σ）而非单点；O 与 P 差距过大就继续拆；实际用时回填校准 M 值。反过来，从不估时的团队要到排期日才发现任务根本拆不动。本仓库 `specs/*/tasks.md` 用"任务 ≤1 天"的粒度约束替代精细估时，是单人项目的务实形态（见 §5.1）。
