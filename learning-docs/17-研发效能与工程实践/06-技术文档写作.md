## 一、为什么写作也需要规范

技术文档是唯一"写给六个月后的自己和别人"的代码周边产物。没有规范的文档库会退化成三件事：**过期信息比没信息更糟**（读者信了错的）、**搜不到**（标题与结构混乱）、**没人敢删改**（不知道哪句还有效）。本仓库 `learning-docs` 经过 119 篇的迭代，沉淀了一套可以复用的骨架——本篇把它显式化，让"怎么写"不再依赖模仿。

**本模块的目标态一句话**：任何一篇笔记，陌生人（或半年后的你）只读文档本身，就能在不翻代码的情况下判断"这是什么、证据在哪、工程落地没有、我该练什么"。

## 二、文档骨架模板

### 2.1 单篇文档骨架（学习笔记/技术讲义通用）

```
# 标题                          ← 一眼说清主题，不加"浅谈/详解"
> 对应项目：`真实文件路径`（一句话说明它是什么）
> 相关：[其他文档](相对路径)（关系说明）      ← 引用块承载"证据锚点 + 关联阅读"

---

## 一、…（中文数字小节）
   第一节放结论 / 对比表 —— 读者可能只读这一节
## 二、… 原理与机制             ← 图（ASCII）优先于长段文字
## 三、… 项目现场               ← 引用本仓库真实代码，file:line 可核对
## 八、面试高频问答             ← **Q1：…** 换行 A：…（6~9 题，覆盖本篇主线）
## 九、动手练习                 ← 5 条左右，尽量绑定本项目可改造点

---

> 上一篇：[NN-x](./xx.md) ｜ 下一篇：[NN-x](./xx.md)
```

这个骨架的三个设计意图：**结论前置**（对比表当目录用）、**证据中置**（项目现场给 file:line）、**输出后置**（问答与练习把"读过"变成"会说、会做"）。

骨架不是八股：小节标题（"一、"之后的主题词）应随主题变化，固定的是**职能槽位**——结论槽/原理槽/现场槽/问答槽/练习槽，而不是字面标题。判断一篇是否"套模板套僵了"，就看它的"项目现场"一节有没有真证据：槽位在而证据缺，不如不设这个槽。

### 2.2 模块 README 骨架（以 `11-数据结构与算法/README.md` 为标杆）

```
# 模块名
> 定位一句话 + 前置阅读链接
## 一、为什么要单独学           ← 与已有模块的分工边界
## 二、知识地图                 ← ASCII 全景图
## 三、文档清单与学习路线       ← 分阶段表格：序号/文档/核心内容/难度(⭐)
## 四、本项目现场               ← 实践点 ↔ 仓库证据 ↔ 对应文档 三列表
## 五、速查表                   ← 学完之后回来的"入口"
## 六、学习方法建议
> 返回 [学习路线总览](../00-学习路线总览/README.md)
```

其中"**本项目现场**"表是本仓库 README 的招牌设计——`11-数据结构与算法/README.md` 第四节用 17 行表格把每个算法映射到真实源码路径与对应文档（如"LRU 缓存 ↔ `VectorCacheStore.java` ↔ 文档 09"），它是理论篇与代码库之间的**索引层**，也是面试前复习的总入口。

## 三、证据纪律：file:line 与"只认文件不认口说"

**规则：引用任何仓库文件/命令输出/依赖版本前，必须实际 Read/Grep/执行确认；文中给出真实片段或精确路径。**

四条实操细则：

1. **行号要可核对**：写 `根 pom.xml:343-365`（JaCoCo check 规则）而不是"父 POM 里配了覆盖率"。行号在代码移动后会过期，所以路径+行为描述要一起给（"verify 阶段的 check，行覆盖 ≥40%"），行号是加速器不是唯一依据。
2. **不确定就标注不确定**：远端仓库的分支保护、CI 的实际运行状态这类**本地无法验证的事实**，写"无法从本地确认，按 X 推断"——推断与事实分开表述。
3. **命令输出要真实**：统计类结论必须附产出它的命令（本篇 [03](./03-提交规范与变更日志.md) 的 type 分布表附了 `git log --pretty=format:"%s" | grep -oE ...`），读者能一键复跑。
4. **行号带分支与时点属性**：同一文件在不同分支的行号可能完全不同（本仓库 `feature/ai-chat-and-frontend` 领先 master 63 个提交），跨分支引用证据要重新核对；文档迭代时优先修漂移的行号——它是全文最脆弱的证据形态，这也是细则 1 要求"路径+行为描述一起给"的原因。

**反例与代价**：写了"项目已接入 SonarQube"而实际没接 → 读者按文档配 CI 时找不到任何依据，从此不再信任整个文档库。错误的确定性比承认无知伤害大得多。

## 四、诚实原则：工程未落地必须显式标注

**规则：文档描述"目标态/预研方案"时，必须在首次出现处用 `⚠️ 工程未落地` 显式标注，并与"现状"分开成节。**

本仓库已验证有效的三种标注形态（全部来自真实文档）：

| 形态 | 出处 | 示例 |
|---|---|---|
| 状态徽标 ✅/⚠️ | `00-学习路线总览/05-技术缺口分析与补全计划.md` 第三节 | "性能压测体系 ⚠️ 脚本已落、基线待跑"——比"未完成"精确得多 |
| A/B/C 三分类 | 同上 | A 类"工程已用、文档未写" / B 类"工程本身缺失" / C 类"**有意不引入**（记录决策，防反复横跳）" |
| 节级声明 | 本模块各篇 | [03](./03-提交规范与变更日志.md) §四/§五 标题直接写"⚠️ 工程未落地，本节为目标态" |

C 类是最高级的写法：**把"决定不做"也写成文档**（如"Testcontainers 暂缓（硬门槛 Docker），30 分钟接入清单已备"）——半年后没人会重提"要不要上 Testcontainers"，因为触发条件已写在案。

## 五、结构化表达：表格优先与速查表

**规则：能进表格的不写成段落，能画 ASCII 图的不堆文字。**

| 表达工具 | 适用 | 本仓库实例 |
|---|---|---|
| 对比表 | 多方案选型（列=维度，行=方案） | 本模块 [01](./01-Git工作流与分支模型.md) §一 的三模型对比 |
| 检查清单表 | 可执行的操作序列 | [04](./04-CodeReview实战.md) 四维评审清单 |
| 陷阱表 | "坑/后果/正确姿势"三列 | [02](./02-Git进阶与误操作恢复.md) stash 三大陷阱 |
| 现场表 | 理论点↔证据↔文档 | 11-模块 README 第四节 |
| ASCII 架构图 | 数据流/分层结构 | [07](./07-本地环境与脚本自动化.md) 脚本分层图 |
| 流程图（ASCII） | 有分叉/顺序的操作序列 | [04](./04-CodeReview实战.md) §8.4 一页纸评审流程 |

**速查表放在 README**（不是各篇里）——它是"学完之后回来的入口"，需求场景是"我记得学过，命令忘了"，此时读者要的是 10 秒内定位，而不是重读原理。

### 5.2 ASCII 图的三条画法约定

本库的架构图全部用 ASCII 字符（等宽字体下对齐、可 diff、可纯文本终端阅读），约定：

1. **一个图只讲一件事**：数据流、模块分层、状态迁移分开画，不画"全能图"；
2. **箭头带标注**：`──→` 上写清"什么在流动"（请求/事件/数据），无标注的箭头等于没画；
3. **宽度 ≤80 列**：并排小窗口阅读不折行。

```
好例子（本模块 07 篇的脚本分层图，每条箭头都带语义）：
start-all.ps1
   ├─ start-infra.ps1   ← 基础设施：Nacos → MQ → 配置发布
   └─ start-app.ps1     ← 应用：构建 → 后端服务 → 前端
        └─ lib/common.ps1   ← 只提供函数，不含流程
```

反例是直接截屏架构图：不可搜索、不可 diff、过期后没人更新——ASCII 图改一行就是一次可评审的 diff。

### 5.3 表格设计的三个细节

**细节一：每行是一个自足的事实。** 随机抽一行贴到聊天窗口里，别人不看上下文也能懂——表格会被单独截出来引用（评审意见、面试速记、周报），某列写"同上"或"见前文"的表格做不到这一点。

**细节二：读者检索用的列放最左，证据列居中。** "本项目现场"表的左列是"实践点"（如"幂等一键启动脚本"）而不是文件路径，因为读者的查询是"我要查幂等启动"，文件路径是查询结果而不是查询入口；把路径放最左的表只服务"已经知道文件名"的人，那不如直接给 grep。

**细节三：列数 ≤4，超了就拆两张表。** 五列以上的表在 80 列宽的终端或分屏里必然折行，折行后"行"这个单位就被破坏了。本库的现场表固定三列（实践点/证据/文档）、速查表固定两列（需求/命令），都是按最窄的阅读环境设计的。

## 六、链接与查重：内链维护

### 6.1 相对路径规则

```
同目录：   ./01-Git工作流与分支模型.md
跨模块：   ../08-测试/05-性能压测实战-k6与JMeter.md
模块入口： ../00-学习路线总览/README.md
```

三条维护纪律：
1. **引用不重复**：已有专篇的内容只链接、不重写（判据见 6.2）；链接处用括号注明"关系说明"（如"（GWT 的自动化形态）"），让读者知道为什么跳。
2. **链接必须成对出现读写方**：A 链接了 B，B 的"相关"块也应能回到 A——单向链接在文档搬家后最容易变成孤岛。
3. **机器校验兜底**：本仓库用 `scripts/docs/check-links.mjs` 做全库链接检查，新增文档后跑一遍，死链当场暴露（人眼校对 119 篇的链接是不可能的任务）。

### 6.2 查重后立项（写作前的 grep 纪律）

`05-技术缺口分析与补全计划.md` 第一节定义了标准流程："对疑似缺口先全目录 grep 确认'真的没写'再立项。例：NL2SQL（7 篇命中）确认已覆盖，不立项；提示词灰度（仅 1 篇提及）确认空白，立项。"

实操：动笔前 `grep -ril -E "关键词1|关键词2" learning-docs --include="*.md"`，三种结果三种动作——

| grep 结果 | 动作 |
|---|---|
| 多篇深度命中 | 不写，在新文档里链接到它们 |
| 少量提及、无专篇 | 立"专篇"项目，在提及相关处互链 |
| 零命中 | 全新篇目，正常按骨架写 |

### 6.3 模块的内链结构：向下扎根，向上挂接

一篇合格的新文档，链接关系应该长这样（以本模块 08 篇为例）：

```
                 [00-学习路线总览/README.md]        ← 向上：模块被总览收录
                          ↑
[08-测试/01,05] ←── 17/08-质量门禁与自动化 ──→ [07-运维部署/03-Jenkins]
   分工声明（不重复）      │    证据引用（现状走读）      分工声明
[01,03]（本模块内篇）←─────┘  概念依赖（分支保护/提交规范）
```

三个位置三种语义：**向上**（README 清单与总览收录）、**横向分工**（"这内容在 X 篇，本篇不重复"）、**概念依赖**（"不懂 Y 先读 Y"）。写完检查一遍：三种至少各有其一，否则这篇文档在库里是座孤岛。

本模块（17）的八篇都走了这个流程：如"质量门禁"确认 `07-运维部署/03-JenkinsCICD流水线.md` 只讲 Jenkins 怎么搭、不讲门禁设计，才立项 [08](./08-质量门禁与自动化.md) 并与其互链。

### 6.4 死链的三个常见来源

`check-links.mjs` 报出的死链，几乎都能归到三类：

| 来源 | 典型场景 | 预防动作 |
|---|---|---|
| 文件改名/搬家没跟上 | 重命名某篇文档后，README 清单与各篇"相关"块里的旧路径还在 | 改名是"删一处加多处"的操作，完成后必须复跑链接检查 |
| 相对路径层级抄错 | 从其他模块复制骨架，`../` 的层数没按新位置改 | 链接写完在编辑器里跳转一遍，或交给脚本兜底 |
| 链接"计划中"的文档 | 总览先收录了尚未落盘的模块入口 | 接受临时断链，但必须显式记录基线，落盘后归零 |

第三类在本仓库刚真实发生过：第六批（12~17）补全时，`00-学习路线总览/README.md` 先行收录了六个模块的入口，当时模块目录尚未创建，全库基线恰好 6 条断链；模块全部交付后复跑 `node scripts/docs/check-links.mjs` 归零。教训：**断链要有"基线"概念**——计划中的断链是待办，失控的断链才是事故；把"从基线归零"写进验收清单，断链就从感觉问题变成了数字问题。

## 七、写作流程 Checklist（可直接抄进 PR 模板）

**动笔前（立项）**：
- [ ] grep 全库查重，确定"链接已有篇目"还是"新立一篇"
- [ ] 确认引用的每个仓库证据已实际读/跑过，记录 file:line
- [ ] 区分本篇哪些内容是"工程已落地"、哪些是"目标态"（后者准备 ⚠️ 标注）

**写完后（自检）**：
- [ ] 第一节有结论/对比表（只读一节也能带走东西）
- [ ] 每个关键论断有 file:line 或命令可复核；目标态均已标 ⚠️
- [ ] 面试问答 6~9 题且覆盖主线；练习 5 条且绑定本项目
- [ ] 表格每行自足、可独立被引用（§5.3）；链接零断链，或死链基线已显式记录（§6.4）
- [ ] 上一篇/下一篇、模块 README 清单已更新；`check-links.mjs` 通过

**写作节奏**：骨架先行——先把标题层（第一节到练习）和小节首句写完，填证据，最后写面试问答。先写正文再"总结出问答"会拖慢一倍；先列 Q 清单再写正文，等于带着面试官的追问写作，正文自然不会跑偏。这也是 [05](./05-需求拆解与估时.md) "竖切"思想在写作上的同构：每完成一节就是一次可交付的完整闭环，而不是憋到最后一次成型。

## 八、面试高频问答

**Q1：技术文档和代码注释的边界是什么？**
A：注释解释"这段代码为什么这样写"（局部、随代码走）；文档解释"系统/主题为什么这样设计、怎么用、怎么验证"（全局、有独立目录结构）。判据：离开代码还有读者（新人、面试、评审）→ 写文档；只服务正在读这段代码的人 → 写注释。本仓库 `Idempotent.java` 的类注释就是合格示范——先讲语义分层与 fail-open 决策，而非复述代码。

**Q2：怎么保证文档不过期？**
A：三个机制：① 证据纪律——文档只写 file:line 可核对的事实，过期时读者能自行校验与修正；② 状态标注——✅/⚠️/A/B/C 分类让"未完成"是显式信息而非隐患；③ 机器检查——链接用脚本全库校验，事实用命令可复跑。完全防过期做不到，目标是**过期可被发现**。

**Q3：为什么强调"工程未落地要显式标注"？**
A：文档的价值在于可信任。把目标态写成现状，读者会基于错误前提做决策（按文档配 CI 却找不到配置）。显式标注（⚠️ + "本节为目标态"）让同一篇文档同时承载"现状描述"与"演进方案"而不混淆，也诚实记录了项目的真实边界。

**Q4：文档结构为什么结论前置？**
A：读者的注意力分布决定结构。多数读者是"带着问题来查"而非"从头读到尾"——第一节放结论/对比表，让 10 秒读者拿到答案、5 分钟读者按节跳转、深读的人再看原理与现场。这和代码"公共 API 放前面"是同一个组织原则。

**Q5：怎么给一个 119 篇的文档库做"缺口分析"？**
A：双清单比对：① 工程实证清单（逐模块读 pom/yml/package.json，只认文件）② 文档覆盖清单（逐模块梳理子主题）。交叉后把缺口分三类——工程已用文档没写（补文档）、工程本身缺失（补工程）、有意不引入（记录决策+触发条件）。每项动工前先 grep 确认真空白。本仓库 `05-技术缺口分析与补全计划.md` 是完整范例。

**Q6：怎么写出能"背下来面试用"的内容？**
A：把同一知识写两遍——正文讲原理与现场（理解），面试问答区用 Q/A 复述（输出）。问答不是正文的缩写，而是"面试官视角的追问链"：是什么→为什么这么选→代价与边界。动手练习则绑定项目真实改造点，保证"会做"而不只是"会说"。

**Q7：AI 时代还值得手写技术文档吗？**
A：更值得。AI 能生成"格式正确的文档"，但它不知道"这个仓库的真实状态"（哪些已落地、哪个文件第几行是什么）。人的价值收敛到三件事：证据的采集与核对（file:line）、未落地处的诚实标注、与既有文档的查重与互链——这些恰恰是本篇定义的纪律。让 AI 起草、人按证据纪律审校，是当前性价比最高的协作方式。

**Q8：怎么让团队真的按规范写，而不是规范落灰？**
A：降低遵循成本而非提高觉悟：① 把规范物化成模板（骨架直接复制就能填）；② 把检查自动化（check-links、自检 checklist 进 PR 模板）；③ 让规范"有出处"——每条规则能指到一个真实反例（如乱码提交、死链事故），新人心服口服；④ 规范自身按 §三 的证据纪律迭代，被推翻的规则要有记录地废弃，而不是悄悄不再提。

**Q9：文档写多长合适？**
A：长度由"读者完成一次任务所需的最小信息量"决定，而不是由"我懂了多少"决定。判据看结构不看字数：结论前置、每节可独立跳转、证据可核对。本库约束每篇 250~420 行，是按"一次深度学习会话"校准的经验区间——明显短于下限往往缺证据或缺练习，明显超上限就该按主题拆篇（拆分判据复用 §6.2 的查重：一个主题一篇）。

## 九、动手练习

1. 用 §七 的动笔前 checklist 给自己立一个新篇目：先 `grep -ril -E "docker compose|compose" learning-docs --include="*.md"`，根据命中情况决定"新写一篇 Docker Compose 深度笔记"还是"链接已有篇目"，把决策依据写成三行记录。
2. 抽查证据纪律：随机挑本模块某一篇里的 3 个 file:line 引用，逐一 Read/Grep 核对是否准确；发现漂移就修文档（这正是"行号是加速器不是唯一依据"的含义）。
3. 给 `learning-docs/常见业务相关/` 目录（本库中唯一没有 README 索引的目录）按 §2.2 骨架补一个 README：文件清单表 + 定位一句话，体会"索引层缺失"的检索成本。
4. 用 §四 的 A/B/C 三分类给本仓库**文档库本身**做一次盘点：A 类（工程已有、文档缺）举 2 例、B 类（工程缺）举 2 例、C 类（有意不写）定 2 条并各写触发条件，对照 `05-技术缺口分析与补全计划.md` 检查你的分类是否与它一致。
5. 把你最近写的一篇笔记按 §2.1 骨架重排：结论提前、补 file:line、加 3 道面试问答与 2 条绑定项目的练习，前后各花多少分钟对比——用数据回答"骨架是负担还是加速器"。
6. 给 `scripts/docs/check-links.mjs` 补一个"孤儿文档"检查：把全库所有 md 链接的目标路径收集成集合，与全部 md 文件求差集，找出没被任何文档链接到的篇目——体会 §6.3 说的"座孤岛"为什么靠人眼永远发现不了。
