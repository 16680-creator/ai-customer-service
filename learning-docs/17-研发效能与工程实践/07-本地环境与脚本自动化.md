## 一、脚本全景：分层设计

```
start-all.bat                    ← 双击入口：包装 powershell 调用 + pause
   └─ start-all.ps1              ← 编排层：只做参数透传，[1/2] infra → [2/2] app
       ├─ start-infra.ps1        ← 基础设施层：Nacos(8848) → RocketMQ NameServer(9876) → Broker(10911) → 发布 Nacos 配置
       └─ start-app.ps1          ← 应用层：Maven 构建 → 11 个后端服务 → Vite 前端 → Summary
            └─ lib/common.ps1    ← 公共库（dot-source 引入）：端口探测 / JDK8+JDK17+Maven 自动发现 / 服务注册表 / 进程与日志管理
```

**分层的价值**（真实文件注释里就写着）：`start-all.ps1` 头部注释明确" Prefer running the two scripts separately to skip parts that are already up"——分层让"只重启应用"、"只补基础设施"成为可能，而不是全量重来。三层的职责表：

| 层 | 文件 | 职责 | 不做什么 |
|---|---|---|---|
| 入口 | `start-all.bat` | 免改执行策略，双击可用 | 不含任何逻辑（`powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0start-all.ps1" %*`） |
| 编排 | `start-all.ps1` | 顺序调用 + 参数透传（`-SkipBuild`/`-NoFrontend`/`-Service`） | 不直接碰任何服务 |
| 功能 | `start-infra.ps1` / `start-app.ps1` | 各自领域的启动与等待 | 不重复实现探测/发现逻辑 |
| 公共库 | `lib/common.ps1` | 探测、发现、注册表、日志——**被 dot-source，不直接运行** | 无执行流程 |

## 二、幂等性：重复执行安全的设计

**幂等 = 脚本跑第 100 遍和第 1 遍结果一致；已就绪的组件被跳过，而不是报错或重复启动。** 本脚本的幂等性落在四处：

### 2.1 端口探测是唯一的"是否在跑"判据（`common.ps1:33-47`）

```powershell
function Test-PortListening([int]$port) {
    foreach ($addr in @([System.Net.IPAddress]::Loopback, [System.Net.IPAddress]::IPv6Loopback)) {
        $c = New-Object System.Net.Sockets.TcpClient($family)
        try {
            $t = $c.ConnectAsync($addr, $port)
            if ($t.Wait(1200) -and $c.Connected) { return $true }   # 1.2s 连接超时
        } catch { } finally { $c.Dispose() }
    }
    return $false
}
```

要点：异步连接 + 1.2 秒超时（不卡死在拒绝服务上）、IPv4 与 IPv6 回环都试（Windows 上 8848 可能监听在任一栈）。

### 2.2 每个组件启动前都先探测

```powershell
# start-infra.ps1（节选）——已启动就 [Skip]
if (Test-PortListening 8848) {
    Write-Host "  [Skip] Nacos already running on 8848"
} else { ... 启动并 Wait-Port 8848 120 "Nacos" ... }
```

`start-app.ps1` 的 `Start-BackendService`（`common.ps1:140-155`）同样：端口在监听 → `[Skip]` 返回。**效果**：脚本崩了重跑、服务起了一半重跑，都安全。

### 2.3 工具链与制品的按需解析

| 机制 | 位置 | 说明 |
|---|---|---|
| JDK 自动发现 | `Get-JdkHome`（`common.ps1:70-95`） | 候选链：`env.ps1` 配置 → 环境变量 → 常见安装目录（含版本校验 `Test-JdkMajor`）→ PATH。JDK8 给 Nacos、JDK17 给 RocketMQ 与全部 Spring Boot 服务——**一台机器双 JDK 共存**是这个设计的动机 |
| Fat jar 判定 | `Test-FatJar`（`common.ps1:116-127`） | 打开 jar 读 ZIP 条目查 `BOOT-INF/classes/*`：是 fat jar 就 `java -jar`，否则退回 `mvn spring-boot:run`——同一脚本兼容两种构建产物 |
| 前端依赖 | `start-app.ps1:55-60` | `node_modules` 缺失才 `npm install` |
| Nacos 配置发布 | `start-infra.ps1:40-53` | 逐个 yml 用 `curl --data-urlencode "content@file"` POST 到 `/nacos/v1/cs/configs`（tenant=aics），统计 ok/fail——**配置文件是事实源，每次启动都重新发布**，避免"控制台手改配置"漂移 |

### 2.4 幂等的边界：重复安全 ≠ 无副作用

幂等指的是"重复执行不会把系统搞坏"，**不等于"重复执行没有任何效果"**——本脚本有两处刻意的非幂等副作用：

| 行为 | 位置 | 为什么是刻意的 |
|---|---|---|
| 每次启动都重新发布 Nacos 配置 | `start-infra.ps1:40-53` | **覆盖语义是功能**：控制台上的手改会在下次启动被仓库版本冲掉，倒逼配置变更走代码（防配置漂移） |
| 每次 `-SkipBuild` 之外的启动都 `mvn clean install` | `start-app.ps1:26-33` | 构建失败立即 throw（`exit` 非零），宁可慢不可用旧 jar 起服务 |

设计幂等脚本时要显式区分：哪些重复执行应当跳过（起服务、起基础设施）、哪些应当**每次都做**（发布配置、构建）、哪些必须**每次都失败得响亮**（工具链缺失 throw，`common.ps1:162-164`）。

### 2.5 健康等待（`Wait-Port`，`common.ps1:49-60`）

```powershell
function Wait-Port([int]$port, [int]$timeoutSec, [string]$name) {
    $deadline = (Get-Date).AddSeconds($timeoutSec)
    while ((Get-Date) -lt $deadline) {
        if (Test-PortListening $port) { Write-Host "  [OK]   $name ready on $port"; return $true }
        Start-Sleep -Seconds 3                       # 3s 轮询
    }
    Write-Warning "  [WARN] $name not ready on $port after ${timeoutSec}s"
    return $false
}
```

**依赖顺序用等待表达**：Broker 必须等 NameServer 就绪（`start-infra.ps1:28-36`：9876 未监听时 Broker 直接 skip 并告警）；应用层等每个服务端口最多 180 秒。**已知短板**（评审视角）：`start-app.ps1:41,44` 用 `| Out-Null` 丢弃了返回值——超时只告警不失败，见 [04-CodeReview实战](./04-CodeReview实战.md) §六案例 1；且"TCP 通"≠"Spring 容器就绪"，更严格的做法是轮询 actuator `/actuator/health`。

## 三、环境变量管理：两层分离

```
tools/env.ps1          ← 入库：机器路径（JAVA8/JAVA17/MAVEN_HOME）、DB_PASSWORD
tools/env.local.ps1    ← 不入库（.gitignore）：LLM API 密钥等本机私密
加载顺序：common.ps1:26-30  先 . env.ps1，再 . env.local.ps1  → 后者覆盖前者
```

**这套设计的正确部分**：
- 密钥与机器路径分离，`env.local.ps1` 有模板且被 gitignore（`env.ps1` 头注释写明）；
- 密钥"非空才覆盖"（`common.ps1:170-172`：`if ($DEEPSEEK_API_KEY) { ... }`），避免脚本清掉机器级环境变量；
- 提供三重兜底：文件配置 / 环境变量 / 常见目录自动发现。

**这套设计的欠账（如实指出）**：`common.ps1:24` 仍写死了 `$DB_PASSWORD = "<明文密码>"`（该文件入库），数据库密码没走 `env.local.ps1` 通道——改进建议与评审意见见 [04](./04-CodeReview实战.md) §六案例 2。这正说明：**环境分离的机制建好了，不等于所有密钥都走了机制**。

**可复用的经验法则**：入库文件只放"结构"（有哪些变量、默认为什么），真实值走"被 gitignore 的本地文件或环境变量"；脚本对真实值 fail-fast（为空就提示），而不是塞一个能连上的默认值。

## 四、日志与进程管理

### 4.1 启动：重定向 + PID 落盘（`Start-Proc`，`common.ps1:129-138`）

```powershell
$p = Start-Process -FilePath $exe -ArgumentList $argList -WorkingDirectory $workdir `
        -RedirectStandardOutput $out -RedirectStandardError $err `
        -WindowStyle Hidden -PassThru
[IO.File]::WriteAllText("$logDir\$name.pid", "$($p.Id)")
```

每个组件三个产物：`tools/logs/<名>.out.log`（stdout）、`<名>.err.log`（stderr）、`<名>.pid`（进程号）。**价值**：服务隐藏窗口后台运行，但日志可 `tail`、进程可按 PID 精确停；排查顺序固定为"先 `tail <名>.err.log` 再看端口"。

### 4.2 停止：按端口反向清场（`stop-all.ps1`）

```powershell
$ports = @(8848, 9848, 9876, 10911, 8080..8090, 5173)   # 平台拥有的全部端口
Get-NetTCPConnection -State Listen | Where-Object { $ports -contains $_.LocalPort } |
    ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
# 之后再兜底：按命令行匹配残留的 java/node 进程
```

**"按端口找进程"比"按进程名找"可靠**——`java` 进程有十几个，但监听 8087 的只有一个；平台先声明"我拥有哪些端口"，停与启共用同一份事实。启动时统一 `-Dfile.encoding=UTF-8`（`common.ps1:150,153`），对应 `e6809c2 fix(tools): 统一后端进程UTF-8启动编码`——Windows 控制台 GBK 是真实踩过的坑（`git log` 里还有一条乱码提交，同根源）。

### 4.3 如实标注：已知欠账——日志无轮转

`Start-Proc` 的重定向是**追加覆盖式**的单文件（每次启动覆盖同名 `.out.log`），且 `tools/logs/` 下多服务多文件没有大小上限与轮转——长期高频重启的机器上日志目录会持续膨胀。改进方向：启动前把旧日志按时间戳归档（`Move-Item <名>.out.log <名>.out.$(Get-Date -Format yyyyMMdd-HHmm).log`），或接入已有的 Loki 聚合（见 [07-运维部署/07-Loki日志聚合](../07-运维部署/07-Loki日志聚合.md)）。列在这里而非"改进建议"，是因为它是**当前真实行为**——读日志时要知道"你看到的只是最近一次启动"。

### 4.4 结尾 Summary（`start-app.ps1:66-78`）

全部启动后打印一张 UP/DOWN 总表（11 个服务端口 + 前端 5173），并给出 Gateway/Frontend/Logs 三个入口地址。**一键脚本的收尾必须是可判定的事实**（每个端口 UP/DOWN），而不是"全部完成！"的口头承诺。

### 6.3 启动失败排查树（脚本 Summary 出现 DOWN 时按此走）

```
Summary 中某服务 DOWN
 ├─ 端口被别的进程占了？     netstat -ano | findstr :<端口>   → 非 java 进程则先清场
 ├─ tools/logs/<名>.err.log 有异常？                            → 启动期崩溃（Bean/端口/配置）
 ├─ Nacos UP 吗（8848）？    服务注册不上去多因配置中心没起       → 先跑 start-infra.ps1
 ├─ DB/Redis/ES 通吗？       docker-compose ps 看容器与端口      → 容器挂了先 docker-compose up -d
 └─ 都正常但起得慢？         Wait-Port 180s 可能不够首启        → 单独 start-app.ps1 -Service <名> 再看日志
```

排查树的价值在于**顺序**：从"最便宜、最常见"的检查开始（端口占用一条命令），而不是一上来就翻几十屏日志。把它写成团队文档后，"我起不来"这句话就有了标准的第一回应。

## 七、面试高频问答

**Q1：一键启动脚本最重要的设计原则是什么？**
A：幂等——重复执行安全。判据是"脚本跑第 100 遍和第 1 遍结果一致"：每个组件启动前先探测（本项目用 TCP 端口连通性），已就绪就跳过；健康等待有超时上限；收尾打印每个端口的 UP/DOWN 事实。没有幂等性的"一键启动"会在第二次执行时报端口冲突或重复拉起进程。

**Q2：怎么判断"服务已就绪"？TCP 连通够吗？**
A：分两档。TCP 端口可连通（本项目的 `Test-PortListening`）实现简单、足够用于"启动编排"场景；但它只能证明内核层监听，不等于 Spring 容器就绪（可能还在加载 Bean）。更严格的就绪探针是轮询 actuator `/actuator/health` 返回 UP。编排脚本用 TCP 起步、关键链路用 HTTP 健康检查，是成本与可靠性的常见折中。

**Q3：多环境/多机器的配置怎么管理？**
A：分层——入库文件只放结构与安全默认值；机器差异（JDK 路径）放入库但可覆盖的配置文件；私密值（密钥、密码）放入 gitignore 的本地文件或环境变量，脚本"非空才覆盖"以保护机器级变量。本项目 `env.ps1` + `env.local.ps1` 两层就是这个模型，同时要警惕"机制在、执行漏"（如某密码默认值仍写死在入库文件里）。

**Q4：启动脚本里如何处理多版本 JDK 共存？**
A：按组件声明所需版本（Nacos 要 JDK8，RocketMQ 与 Spring Boot 3 服务要 JDK17），启动时为每个组件显式解析对应 JAVA_HOME——自动发现链：显式配置 → 环境变量 → 常见安装目录带版本校验 → PATH。绝不依赖全局 `JAVA_HOME`，因为它只指向一个版本。

**Q5：服务的日志怎么管理才好排查？**
A：三个落点：① stdout/stderr 分文件重定向（err 才是启动失败的第一现场）；② 文件名与服务注册表同名，人和脚本都能从服务名推导日志路径；③ 进程 PID 单独落盘，停止与排查都不用重新找。本项目 `Start-Proc` 每个组件产出 `.out.log/.err.log/.pid` 三个文件。

**Q6：怎么停止一组本地服务最可靠？**
A：按端口反向定位进程再杀，而不是按进程名。先在脚本里声明"平台拥有哪些端口"（启动与停止共用这份清单），停止时 `Get-NetTCPConnection -State Listen` 过滤这些端口、按 `OwningProcess` 精确停止，最后按命令行匹配兜底残留进程。按名字杀 java 会误伤无关进程。

**Q7：为什么配置要"每次启动重新发布到配置中心"？**
A：把配置文件当事实源，防止"控制台手改"与仓库漂移——控制台里的修改会在下次启动被仓库版本覆盖，倒逼所有配置变更走代码评审。本项目 `start-infra.ps1` 每次启动把 `tools/nacos-config/*.yml` 逐个 POST 到 Nacos 并统计 ok/fail，就是这个原则。

**Q8：本地脚本和 CI 的关系？**
A：共享"事实源"分层——本地脚本负责"把我机器拉到可开发状态"，CI 负责"把提交拉到可发布状态"，两者应消费同一份声明（服务清单、端口、健康判据、覆盖率阈值）。若本地与 CI 各写一套，漂移只是时间问题；演进路径见 [08-质量门禁与自动化](./08-质量门禁与自动化.md)。

## 八、动手练习

1. **验证幂等**：跑 `tools/start-infra.ps1` 两次，第二次观察 Nacos/NameServer/Broker 的 `[Skip]` 输出；然后 `kill` 掉 Broker（按端口 10911 找 PID）单独重跑，确认只有 Broker 被补启。
2. **体验等待与超时**：把 `start-app.ps1` 里 `Wait-Port` 的超时参数从 180 改成 5，故意不改配置制造启动失败，观察 `[WARN]` 与 Summary 的 DOWN——再顺手实现"等待失败则以非零码退出"的小改造并自测。
3. **补齐就绪探针**：给 `Wait-Port` 之外加一个 `Wait-Health` 函数，轮询 `http://localhost:<port>/actuator/health` 直到返回 UP（超时 180s），在 `ai-cs-user` 上对比两者就绪判定的时间差。
