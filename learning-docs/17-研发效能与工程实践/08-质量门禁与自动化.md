## 一、什么是质量门禁：从"检查"到"卡位"

**检查（check）**是"跑一下看看结果"；**门禁（gate）**是"不达标就禁止进入下一环节"。两者差一个字，差在**失败时的处置权**：门禁的失败必须能阻断合入/发布，且**绕过门禁需要显式、留痕的特批**。

```
提交前（本地，秒级）        PR/推送（CI，分钟级）        合并前（主干保护）
┌──────────────────┐     ┌──────────────────────┐     ┌──────────────────┐
│ pre-commit hook   │     │ CI 流水线             │     │ 分支保护规则       │
│ 格式化 / 快速静态 │ ──→ │ 编译+单测+覆盖率门禁  │ ──→ │ status checks 必过 │
│ 密钥扫描/消息规范 │     │ 静态扫描/压测(可选)   │     │ 禁止 force push    │
└──────────────────┘     └──────────────────────┘     └──────────────────┘
   反馈最快、成本最低 ──────── 发现越早修复越便宜 ──────── 最后的机器防线
```

**设计原则**：越左越快（提交前只放秒级检查）、每层只做该层性价比最高的事、上层失败自动触发下家（CI 失败的 PR 不能合并）。分支保护的角色见 [01-Git工作流与分支模型](./01-Git工作流与分支模型.md) §五，提交消息卡点见 [03-提交规范与变更日志](./03-提交规范与变更日志.md) §四。

## 三、已落地的现状深读：JaCoCo 覆盖率门禁

根 `pom.xml`（`maven-compiler.parameters` 同文件）三段式配置，这是覆盖率从"报表"变"门禁"的关键：

```xml
<!-- pom.xml:328-367（节选） -->
<plugin>
  <groupId>org.jacoco</groupId>  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.11</version>      <!-- pom.xml:71 -->
  <executions>
    <execution><id>prepare-agent</id><goals><goal>prepare-agent</goal></goals></execution>
    <execution><id>report</id><phase>test</phase><goals><goal>report</goal></goals></execution>
    <execution><id>check</id><phase>verify</phase><goals><goal>check</goal></goals>
      <configuration><rules>
        <rule><element>BUNDLE</element><limits>
          <limit><counter>LINE</counter>  <value>COVEREDRATIO</value><minimum>0.40</minimum></limit>  <!-- :354 -->
          <limit><counter>BRANCH</counter><value>COVEREDRATIO</value><minimum>0.30</minimum></limit>  <!-- :359 -->
        </limits></rule>
      </rules></configuration>
    </execution>
  </executions>
</plugin>
```

| 设计点 | 说明 |
|---|---|
| `check` 绑定 `verify` 阶段 | `mvn verify` 即触发；**低于阈值直接 BUILD FAILURE**——这就是"门禁"而非"报表" |
| `BUNDLE` 级 LINE ≥40% / BRANCH ≥30% | 模块整体达标即可，行覆盖看执行路径、分支覆盖看条件组合（后者更难造假） |
| 规则放父 POM，子模块显式声明 | `ai-cs-message/pom.xml:121` 注释原文："JaCoCo 覆盖率门禁（行 ≥40%，分支 ≥30%，规则定义在父 POM pluginManagement）"——message/notify/order/product/pay 五个模块显式接入，其余模块靠继承 |
| 为什么是 40% 而不是 80% | 门禁的第一版阈值应该是**当前真实水平略高**（防倒退），而不是理想值（导致人人绕过）。验证：`mvn verify -pl ai-cs-message`，看日志里 jacoco check 是否通过 |

**防"刷覆盖率"的补充规则**（目标态）：`excludes` 排除生成的代码与 DTO；对 service 包单独设更高阈值（`element=CLASS` 规则二）；覆盖率只升不降（CI 里对比上一次 report，见 §七）。

### 3.1 父子 POM 的继承现状（实测）

```bash
grep -lc -i jacoco ai-cs-*/pom.xml   # 显式声明的只有 5 个
# ai-cs-message / ai-cs-notify / ai-cs-order / ai-cs-product / ai-cs-pay
```

| 接入方式 | 模块 | 说明 |
|---|---|---|
| 显式声明插件 | message、notify、order、product、pay | `ai-cs-message/pom.xml:121` 的注释写明了规则来源（父 POM pluginManagement）——这是好实践：**门禁在子模块可见**，而非藏在父 POM 里"默认生效" |
| 未显式声明 | chat、common、gateway、knowledge、mq、search、user | 行为依赖 Maven 继承；是否真的执行 check 应以 `mvn verify -pl <模块>` 实测为准，不能凭"应该继承了"下结论 |

这本身就是一个门禁设计的微教训：**门禁的可见性影响它的可信度**——开发者知道"这个模块有覆盖率卡点"才会写测试；"默认继承但没人提过"的卡点，等于不存在。

## 四、第一层：提交前门禁 pre-commit hook（⚠️ 工程未落地，本节为目标态）

> 现状：无 `.husky/`、无 `.pre-commit-config.yaml`、前端无 lint 脚本。提交消息卡点的两套方案已在本模块 [03](./03-提交规范与变更日志.md) §四 给过完整步骤，本节讲**消息之外**的提交前检查。

| 检查 | 工具 | 耗时目标 | 做法 |
|---|---|---|---|
| 格式化 | Spotless（Maven） | 秒级 | `pre-commit` 钩子跑 `mvn spotless:apply -pl <改动模块>`，把格式化结果自动 add 回暂存区 |
| 密钥扫描 | 正则/gitleaks | 秒级 | 复用本仓库已有的泄露密钥扫描脚本（`scripts/leaked-secrets-scanner.py`，`27e2bca chore(security)` 引入）的规则，hook 内只扫**本次暂存的 diff**，秒级完成 |
| 提交消息 | commitlint | 毫秒 | 见 [03](./03-提交规范与变更日志.md) §四方案 A/B |
| 前端构建冒烟 | `npm run build` | 十秒级 | 只在前端改动时触发（按文件路径判断），防止把编不过的代码提交上去 |

**一个零依赖的最小起点**（`.git/hooks/pre-commit`，先跑起来再演进）：

```bash
#!/bin/sh
# ⚠️ 目标态示例：提交前最后一道人工可感知的检查
# 1) 密钥正则：拦下最典型的明文密钥形态（完整规则见 scripts/leaked-secrets-scanner.py）
if git diff --cached -U0 | grep -inE '(sk-[a-z0-9]{20,}|AKIA[0-9A-Z]{16}|BEGIN (RSA|EC) PRIVATE KEY)'; then
  echo "✘ 暂存区疑似含密钥，提交被拦截（误报请调整正则并说明）"; exit 1
fi
# 2) 大文件：单文件 >1MB 拦下（配合 02 篇的 LFS 策略）
big=$(git diff --cached --name-only -z | xargs -0 -I{} du -k "{}" 2>/dev/null | awk '$1>1024{print $2}')
[ -n "$big" ] && { echo "✘ 超 1MB 的文件不应直接入库：$big"; exit 1; }
exit 0
```

两条规则都满足"秒级、零依赖、误报可控"——这是 hook 能存活下来的前提；分钟级检查一律推给 CI（§七）。

**取舍**：hook 只放**秒级**检查——分钟级的测试/覆盖率留给 CI（开发者会绕过慢的 hook，`--no-verify` 一挂就全盘失效）。Java 侧 hook 用 `.git/hooks/`（零依赖不入库）还是 husky（Node 依赖入库共享），按 [03](./03-提交规范与变更日志.md) §四的对比选择；单人起步先给 `commit-msg` + 密钥扫描两条，够用。

## 五、第二层：Java 静态检查工具链选型（⚠️ 工程未落地，本节为选型对比）

| 工具 | 检查什么 | 不检查什么 | 引入成本 | 建议 |
|---|---|---|---|---|
| **Spotless** | 格式（缩进/import 顺序/行尾），可执行 `apply` 自动修复 | 任何语义 | 极低 | ✅ 第一优先：先解决"格式争议"这类最廉价的评审噪音 |
| **Checkstyle** | 编码风格规则（命名/方法长度/魔数） | 缺陷 | 低，规则可全自定义 | 与 Spotless 二选一即可（职能重叠，Spotless 胜在自动修复） |
| **SpotBugs** | 字节码缺陷模式（NPE 风险/资源未关/equals 隐患） | 风格 | 中（有误报要治理） | ✅ 第二优先：抓真 bug，从 ERROR 级规则起步 |
| **PMD** | 源码层反模式（空 catch/未用变量/复杂度） | 与 SpotBugs 大量重叠 | 中 | 团队小就先不引入，避免两套工具互相打架 |
| **ArchUnit** | **架构约束**（分层依赖/包循环/命名约定） | 行为 | 低（就是单测） | ✅ 本项目高价值：11 个微服务的分层约束可写成测试 |

**推荐组合**（按边际收益排序）：Spotless（格式，自动修复）→ SpotBugs（缺陷）→ ArchUnit（架构）。

ArchUnit 的独特价值在本项目尤其明显——"网关不直接访问数据库、chat 不绕过 common 的 Result 包装"这类约束现在靠约定，可以变成一条会失败的测试：

```java
// ⚠️ 目标态示例：分层约束测试（放在 ai-cs-common 或独立 arch-test 模块）
@AnalyzeClasses(packages = "com.aics")
class ArchitectureTest {
    @ArchTest
    static final ArchRule servicesShouldNotAccessControllers =
        noClasses().that().resideInAPackage("..service..")
            .should().dependOnClassesThat().resideInAPackage("..controller..");
    @ArchTest
    static final ArchRule businessModulesShouldUseCommonResult =
        classes().that().areAnnotatedWith(RestController.class)
            .should().onlyHaveReturnTypesAssignableTo(Result.class);
}
```

它挂在 `mvn test` 里，随 JaCoCo 同一个阶段被执行与拦截，不需要新流水线。

## 六、第三层：SonarQube 与质量阈（⚠️ 工程未落地，本节为目标态）

**定位**：SonarQube 不是替代上面任何工具，而是**聚合器 + 趋势库**——聚合格式/缺陷/覆盖率/重复度，按项目与时间维度出"质量画像"，并对外提供"质量阈（Quality Gate）"供 CI 判定。

```
mvn verify ──(jacoco.exec + spotbugs.xml + sonar扫描)──→ SonarQube 服务
                                                           │ Quality Gate 评定
CI stage：sonar-quality-gate wait ──通过──→ 允许合并；失败──→ PR 标红
```

| 质量阈指标 | 建议初始值（对齐本仓库现状） | 理由 |
|---|---|---|
| 新代码覆盖率 | ≥ 40%（与 JaCoCo 现有 BUNDLE 阈值对齐，逐步上调） | 门禁盯"新代码"而非存量，老代码不被拦 |
| 新增 Bug / 安全热点 | 0 | 新问题不欠账 |
| 重复率（新代码） | ≤ 3% | |
| 可维护性评级 | 新代码 ≥ A | |

**最小落地路径**：docker 起 SonarQube → Jenkins 加 `sonarqube` stage（`mvn sonar:sonar`，服务端地址走凭据）→ Quality Gate 设上表 → `Jenkinsfile` 在测试阶段后加 "质量阈等待" stage。**没有 SonarQube 的过渡方案**：CI 里直接消费 `jacoco.exec`（现成产物）+ SpotBugs XML，用脚本判定阈值——先有卡点，后有平台。

## 七、CI 卡点设计：Jenkinsfile 现状与改造

### 7.1 现状走读（真实文件）

```groovy
// Jenkinsfile:17  —— 总闸没合：测试默认跳过
booleanParam(name: 'SKIP_TESTS', defaultValue: true, description: '跳过 Maven 测试')

// Jenkinsfile:50-67  —— 测试阶段存在，但被上面参数短路
stage('Maven 测试') {
    when { expression { return !params.SKIP_TESTS && params.DEPLOY_MODE != 'deploy-only' && ... } }
    steps { sh '''
        set -e
        docker run --rm -v "$PWD":/workspace -v "$HOME/.m2":/root/.m2 \
          -w /workspace maven:3.9-eclipse-temurin-17 mvn test -B
    ''' }
}
```

其余阶段：拉取代码 → 环境检查 → （Maven 测试）→ 写入 K8s Secret → 部署基础设施 → 构建推送/部署业务。流水线的**编排是完整的**，问题只有一个：测试阶段默认短路后，后面所有阶段照样往下走——**构建产物未经任何检查就进了部署链**，这是现状最大的门禁缺口。

### 7.2 改造清单（按优先级）

| 优先级 | 改造 | 具体做法 |
|---|---|---|
| P0 | **测试默认打开** | `SKIP_TESTS` 默认 `false`（`:17`），`build-only/deploy-only` 模式维持现有 when 跳过逻辑即可 |
| P0 | **测试失败必须终止** | 测试 stage 已有 `set -e`；确认 `mvn test` 后追加 `mvn verify`，让 §三 的 jacoco check 在 CI 里真正执行 |
| P1 | 覆盖率门禁入 CI | `mvn verify -B` 已含 check；把 `target/site/jacoco/` 归档为流水线产物，失败信息回写到构建页 |
| P1 | 静态检查 stage | `mvn spotless:check spotbugs:check -B`（§五组合，先 ERROR 级规则），独立 stage、失败标红 |
| P2 | 质量阈 stage | SonarQube 上线后加 `sonar-quality-gate`（§六） |
| P2 | 压测准入（发布前） | 发布阶段跑 `k6 smoke`（`scripts/loadtest/k6/gateway-rate-limit.js` 降 VU 版），阈值判读方法见 [08-测试/05](../08-测试/05-性能压测实战-k6与JMeter.md) |
| P3 | 与分支保护联动 | GitHub 仓库对 `master` 开启 required status checks，把 CI 结果变成合并前门禁（见 [01](./01-Git工作流与分支模型.md) §五） |

**设计口诀**：每层门禁 = 一个明确的**阈值** + 一个明确的**失败动作**（终止/标红/禁止合并）+ 一个**绕过的留痕**（特批谁批的、为什么）。三者缺一，就不叫门禁，只叫检查。

## 八、面试高频问答

**Q1：质量门禁和质量检查有什么区别？**
A：检查是"跑一下看结果"，门禁是"不达标就阻断进入下一环节且绕过需留痕"。区别在失败处置权：jacoco 的 `check` 目标低于阈值直接 BUILD FAILURE 是门禁；只生成 HTML 报表没人看是检查。门禁三要素：阈值、失败动作、绕过留痕。

**Q2：门禁分几层？各层放什么？**
A：三层——提交前（本地 hook，只放秒级检查：格式化、密钥扫描、提交消息规范）、CI（分钟级：编译、单测、覆盖率、静态扫描）、合并前（分支保护：required status checks、禁 force push）。原则是越左越快：慢检查放左层会被开发者用 `--no-verify` 绕过，失去意义。

**Q3：覆盖率阈值怎么定？**
A：从**当前真实水平略高**起步（防倒退），而不是拍理想值（80% 会让团队集体绕过门禁）。本项目现实是 BUNDLE 行覆盖 ≥40%、分支 ≥30%（根 pom verify 阶段），这是可执行的起点；后续盯"新代码覆盖率"逐步上调，存量用 excludes 隔离生成代码与 DTO。

**Q4：Spotless、Checkstyle、SpotBugs、ArchUnit 各解决什么问题？**
A：Spotless 管格式且能自动修复（消灭评审里最廉价的格式噪音）；Checkstyle 管风格规则（与 Spotless 职能重叠，二选一）；SpotBugs 从字节码抓缺陷模式（NPE 风险、资源泄漏）；ArchUnit 把架构约束写成会失败的测试（分层依赖、循环依赖）。小团队按"格式→缺陷→架构"的顺序引入。

**Q5：为什么说 ArchUnit 对微服务项目价值高？**
A：微服务的架构约束（网关不碰数据库、业务模块统一用 common 的 Result、service 不反向依赖 controller）传统上靠约定与评审人眼，衰减极快；ArchUnit 把它们变成 `mvn test` 里的断言，违规即红，架构文档从"嘴上说的"变成"机器验的"。

**Q6：没有 SonarQube 能做门禁吗？**
A：能。门禁的本质是阈值+失败动作，不依赖平台：JaCoCo check（已有）+ SpotBugs XML 阈值脚本 + k6 冒烟断言都能在 CI 里用命令行判定。SonarQube 的价值是聚合与趋势（多项目质量画像、按时间回归），属于"先有卡点、后有平台"的增强项。

**Q7：你们项目的 CI 门禁现状如何？**
A：如实说三层：已有的——JaCoCo 覆盖率门禁在父 POM verify 阶段落地（行 ≥40%/分支 ≥30%），Jenkins 流水线编排完整、含容器化 Maven 测试阶段，k6 压测脚本已备；缺的——CI 的 SKIP_TESTS 参数默认 true 导致测试默认不跑（P0 待修），静态检查/SonarQube/pre-commit hook 均未落地。演进顺序是"先合总闸、再补静态层、最后上平台"。

**Q8：开发者抱怨门禁拖慢速度怎么办？**
A：三招：① 分层减负——提交前只留秒级检查，分钟级的给 CI 异步跑；② 自动修复优先——格式类用 `spotless:apply` 直接改而不是报错让人改；③ 阈值随现实走——门禁拦的是"倒退"，不是"未达理想"，一个拦不住任何人的门禁和一个天天误伤的门禁一样失败。同时给紧急修复留"先合后补评 + 留痕"的逃生通道。

## 九、动手练习

1. **验证已有门禁**：跑 `mvn verify -pl ai-cs-message`，观察 jacoco check 输出与 `target/site/jacoco/index.html`；然后把某个模块的 `minimum` 临时调到 0.9 重跑，亲眼确认门禁失败的样子（跑完改回来）。
2. **合上总闸**：把 `Jenkinsfile:17` 的 `SKIP_TESTS` 默认值改为 false，本地用 `jenkins-cli` 或触发一次 build 验证测试阶段被执行；在 PR 描述里写明影响面（哪些 DEPLOY_MODE 不受影响）。
3. **接入 Spotless**：在根 pom 加 spotless-maven-plugin（google-java-format 或 palantir），先跑 `spotless:check` 看存量违规量，再决策"一次性 apply + 独立 PR"还是"只管新增"——写出你的选择理由。
4. **写一条 ArchUnit 规则**：验证"所有 `@RestController` 的方法返回类型必须是 `Result`"（本项目 `ai-cs-common` 已有 `com.aics.common.result` 包），先跑通，再故意在某个 controller 返回 Map 让它变红。
5. **设计本项目的完整门禁矩阵**：按 §一 三层 × §二 现状清单，产出一张"检查项 × 所在层 × 工具 × 阈值 × 失败动作"的五列表格，标注每项"已落地/目标态"，作为 17 模块的收官产物——它能直接当团队门禁建设的路线图。
