# 研发效能与工程实践

> 本专题是 `learning-docs` 的 **第十七个模块**（`17-研发效能与工程实践`），讲的是**脱离 AI 工具也成立的软件工程实践**：Git 工作流、提交规范、Code Review、需求拆解、文档写作、脚本自动化、质量门禁。
> **最大特色**：每个主题都用 `ai-customer-service` 仓库的真实状态当案例——真实的分支布局、真实的 205 条提交、真实的 `tools/` 启动脚本、真实的 `specs/001~005` 规格目录，好的坏的都是一手证据。
> 前置阅读：[00-学习路线总览](../00-学习路线总览/README.md)、[05-技术缺口分析与补全计划](../00-学习路线总览/05-技术缺口分析与补全计划.md)（本模块的"缺口盘点"方法来源）

## 一、为什么要单独学工程实践

`01`~`16` 教你"把系统写出来、跑起来"，本模块教你"**一群人怎么把系统持续写好**"。两者的分水岭在于：技术问题可以单打独斗，工程问题必须面对协作、变更与人。

| 场景 | 只懂技术 | 懂工程实践之后 |
|---|---|---|
| 团队协作 | 直接在 master 上改，互相覆盖 | 分支模型 + 合并策略 + 保护分支，变更可追溯可回滚 |
| 出了事故 | `reset --hard` 手一抖，半天工作没了 | reflog / bisect / stash 急救，五分钟找回 |
| 排查"上周哪次改动引入的 bug" | 靠记忆和翻聊天记录 | 提交规范 + `git bisect` 二分定位 |
| 新人接手 | 口口相传"怎么启动、怎么改代码" | README 索引 + 文档骨架 + file:line 证据纪律 |
| 本地环境 | "我机器上是好的" | 幂等启动脚本 + 健康等待 + 日志落盘 |
| 上线质量 | 全靠自觉 | 门禁分层（提交前 / CI / 合并前），机器卡人 |

一句话：**框架和语言决定"能不能做出来"，工程实践决定"能不能持续做出来"。** 面试中高级岗位的追问（"你们分支怎么管""评审怎么做的""怎么保证不把坏代码合进去"）全都落在这一模块。

## 五、速查表

### Git 日常

| 需求 | 命令 |
|---|---|
| 我刚提交错了，撤销但保留改动 | `git reset --soft HEAD~1` |
| 手滑 `reset --hard` 了 | `git reflog` 找到位置 → `git reset --hard HEAD@{n}` |
| 找哪次提交引入的 bug | `git bisect start` / `good <sha>` / `bad <sha>`（自动版：`git bisect run <脚本>`） |
| 同样的冲突反复解 | `git config --global rerere.enabled true`，Git 记住解法自动复用 |
| 把别的分支某次提交拿过来 | `git cherry-pick <sha>` |
| 临时存一下改动 | `git stash`（含新文件加 `-u`） |
| 强推但不覆盖别人 | `git push --force-with-lease` |
| 整理最近 3 条提交 | `git rebase -i HEAD~3` |
| 最近一条提交消息写错 | `git commit --amend`（已 push 过则需 `--force-with-lease`，见 [02](./02-Git进阶与误操作恢复.md)） |

### 提交消息与 semver

| 类型 | 什么时候用 | 对 semver |
|---|---|---|
| `feat` | 新功能 | minor +1 |
| `fix` | 缺陷修复 | patch +1 |
| `feat!:` / `BREAKING CHANGE:` | 破坏性变更 | major +1 |
| `docs` / `chore` / `refactor` / `test` / `style` | 文档 / 杂务 / 重构 / 测试 / 格式 | 不发版 |

### 本地环境

| 需求 | 命令 |
|---|---|
| 一键启动全部 | `powershell -ExecutionPolicy Bypass -File .\tools\start-all.ps1` |
| 只启动某个服务 | `... start-app.ps1 -Service ai-cs-user` |
| 停掉全部 | `powershell -ExecutionPolicy Bypass -File .\tools\stop-all.ps1` |
| 看谁占了端口 | `netstat -ano \| findstr :8081`（Windows） |
| 看服务日志 | `tail -f tools/logs/ai-cs-user.out.log` |
| 容器状态/日志 | `docker-compose ps` / `docker-compose logs -f mysql` |

### 质量门禁现状（本项目）

| 检查项 | 状态 | 证据 |
|---|---|---|
| 覆盖率门禁（jacoco） | ✅ 已落地 | 根 pom verify 阶段：行 ≥40% / 分支 ≥30% |
| 压测脚本（k6） | ✅ 已落地 | `scripts/loadtest/k6/` 两枚脚本（基线待测） |
| 格式化/静态检查（Spotless 等） | ⚠️ 未落地 | 全仓 pom grep 零命中 |
| SonarQube | ⚠️ 未落地 | 零命中 |
| 提交规范卡点（commitlint） | ⚠️ 未落地 | 无 .husky/ 与配置 |
| 静态检查进流水线 | ⚠️ 未落地 | Jenkinsfile 无 checkstyle/spotbugs/spotless stage |
| CI 跑测试 | ⚠️ 默认跳过 | `Jenkinsfile:17` SKIP_TESTS=true |

## 七、学习方法建议

1. **每篇先看"现状"，再看"目标态"**：本模块大量用本仓库真实状态当案例——先搞清楚"现在是什么样、为什么"，再学"应该是什么样"，比直接背最佳实践深刻得多。
2. **Git 命令全部在沙盒里练**：`02` 的每个急救场景都给了可复制验证的沙盒命令（`git init` 临时目录），**先在沙盒里弄坏、再修好**，练到手不抖。
3. **对照自己的提交历史**：学完 `03` 后跑一遍 `git log --oneline -40`，给自己仓库的提交打分，比读十篇规范文章有效。
4. **评审练习用真实代码**：`04` 给了从本仓库摘出的真实片段和写好的评审意见，学完拿自己最近的 PR 自评一遍。
5. **文档写作立即套用**：`06` 总结的骨架和纪律就是 `learning-docs` 本身的写法，学完写下一篇笔记时直接套，形成肌肉记忆。
6. **区分"已落地"与"目标态"**：所有 ⚠️ 标注的章节是预研/目标方案，不要误以为项目已经有——这也是 `06` 强调的诚实原则。
7. **以"给仓库留下改动"收尾**：每学完一篇，挑练习里最小的一条真的做掉（加一条 ArchUnit 规则、修一个 `SKIP_TESTS` 默认值、挂一个 pre-commit），学习成果落进仓库，比记十页笔记可靠。
