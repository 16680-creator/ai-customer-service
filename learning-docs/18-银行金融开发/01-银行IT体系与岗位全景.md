# 银行 IT 体系与岗位全景

> 本篇回答三个问题：一家银行的"IT"到底分散在哪些组织里、银行的系统版图长什么样、
> JD 里那句"熟悉银行柜面系统、结算现金管理、网络金融等相关业务系统研发运维工作，了解银行业信息安全管理规范"逐个词拆开对应到哪些系统、哪些活、哪些技能。
> 前置阅读：[00-学习路线总览](../00-学习路线总览/README.md)（本仓库的阅读编排方式）；本模块路线图见 [银行金融开发 README](./README.md)。

## 一、先认清对手：银行的 IT 不在一个地方

互联网公司的研发通常集中在"技术中台/业务研发部"一条线上，银行不是。同一家银行里，"写代码的人"分散在六七类组织中，**它们的编制、薪酬结构、招聘入口、成长路径完全不同**。看清楚这一点，投递和面试时才不会问错问题、选错 offer。

| 组织形态                                                   | 主要职责                                                                     | 招聘入口                                             | 成长路径与代价                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 总行部门（信息科技部/数字金融部等）                        | 科技规划、需求管理、预算与立项、供应商管理、架构与安全标准制定、投产决策     | 校招总行管培/社会招聘（少而精）                      | 走"管理者+架构治理"路线，离业务和决策近；代价是**自己很少写代码**，日常是文档、评审、协调                          |
| 软件开发中心（软开）                                       | 银行自研系统的主力交付方：需求分析、设计、编码、测试、版本投产               | 校招主力、社招大量 Java 岗（**你面的岗位多在这里**） | 从模块开发 → 交易/子系统负责人 → 架构师/项目经理；技术深度取决于所在组（核心组 vs 渠道组差别很大）                 |
| 数据中心 / 运营中心                                        | 生产环境运维：机房与网络、数据库与中间件运维、批处理值守、故障处置、投产执行 | 校招/社招，偏运维与运维开发                          | 7×24 值守与轮班是常态；离"真实故障"最近，成长为 DBA/SRE/投产负责人；不写业务代码                                   |
| 银行卡中心 / 信用卡中心                                    | 卡系统、支付、额度与风控、账单与催收等专项系统的建设与运营                   | 独立社招渠道                                         | 业务垂直度高，支付清算与风控经验值钱；技术栈常偏"专用系统 + 外采产品 + 自研补丁"                                   |
| 分行科技部                                                 | 落地总行系统：本地特色业务需求、报表取数、外围小系统、网点技术支持           | 分行社招/内部转岗                                    | 更靠近业务与经营指标；技术深度受限，大量精力在"取数、对账、协调总行改需求"                                         |
| 金融科技子公司（建信金科、工银科技、兴业数金、中银金科等） | 把行内科技能力公司化，对内承接开发、对外输出给中小金融机构                   | 独立公司招聘，节奏接近互联网                         | 薪酬与职级更市场化、技术栈更新；但**项目制交付压力真实存在**，且仍受银行客户的安全与流程约束                       |
| 外包厂商（乙方/驻场）                                      | 人力外包或整包交付，承担测试、外围模块、老系统维护、批量编码                 | 厂商招聘，门槛相对宽松                               | 接触不到核心设计与架构文档、账号权限受限、稳定性差；**可作为入行跳板但不宜久留**，谈薪时务必确认是行方自研还是外包 |

> **面试必问的一句话**：这个岗位是"总行/软开自研编制"还是"外包驻场"？两者的权限边界（能否登录生产、能否改核心代码）、文档完整度、技术积累差别巨大。这个问题不扣技术分，但直接决定你入职后的体验。

再补一个组织维度——**内控"三道防线"**（银行一切系统设计的底层逻辑）：业务部门与运维是第一道（自己出错自己发现）、风险与合规/内控部门是第二道（制定规则并检查）、内部审计是第三道（独立评价）。你在代码里看到的"经办提交后必须另一人复核""超阈值必须授权""每笔操作留痕且日志不可改"，全都是三道防线在系统里的物理化身——**这不是技术选型，是制度要求**（详见 [03-柜面系统与集中作业](./03-柜面系统与集中作业.md) 第五节）。

## 二、系统版图：五大类 + 前中后台

银行内部习惯按"这套系统是给谁用的、离钱有多近"来分层。记住这张分类表，任何新系统你都能在三秒内归位。

| 类别                 | 典型系统（行业通用叫法）                                                                             | 特点                                                     | 研发日常                                                                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 渠道类（最外层）     | 统一柜面、智能柜台 STM、手机银行、网上银行、电话银行、开放银行 API、银企直连、自助设备前置           | 变更最频繁、直接面对客户体验、安全合规要求密集           | 接口联调、页面/交易码改造、灰度与兼容性、性能与可用性                                                                                       |
| 产品与业务处理类     | 存款/贷款/信用卡/理财/贸易融资/国际结算、信贷管理、支付结算、现金与尾箱、凭证与账户管理              | 业务规则最密集、和产品参数/费率强绑定                    | 需求翻译、规则实现、大量参数配置、跨系统字段对齐                                                                                            |
| 核心账务类（最内层） | 核心银行系统（存款/贷款/账务/总账/客户信息）、会计引擎、产品工厂、日终批处理                         | **最不能出错**、并发一致性与热点账户问题、几乎不轻易改动 | 记账正确性、日终跑批、对账与差错、性能与稳定，改造周期长                                                                                    |
| 经营管理类           | 管理会计（FTP 与成本分摊）、财务、人力、OA、预算、采购、报表平台、数据仓库与数据服务                 | 数据量大但不直接影响客户资金；批处理与取数逻辑为主       | 取数口径、指标定义、宽表与调度、报表交付（可对照 [14-数据工程与OLAP/03-数仓分层与指标口径](../14-数据工程与OLAP/03-数仓分层与指标口径.md)） |
| 基础设施与风控类     | 反洗钱、欺诈检测、授信审批与决策引擎、限额管理、名单服务、密码与密钥管理、监控与日志、身份认证与权限 | 横切式存在于所有链路上；模型与规则驱动；数据密集且强合规 | 规则/名单落地、实时决策接口、埋点与审计日志、脱敏与加密改造                                                                                 |

**前中后台的划分**（银行语境里的"中台"和互联网的"中台"是两个意思，面试说混会露馅）：

| 划分              | 银行传统语义                                                                                  | 说明                                                |
| ----------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 前台              | 直接面对客户、带来收入的部分：网点、客户经理、渠道、产品营销                                  | 与互联网"前台=前端页面"含义相近但不等价             |
| 中台              | **风险管理、合规审查、集中作业、账务处理**等集中支撑环节                                      | 这是银行的经典用法，指"风险中台/作业中台"，由来已久 |
| 后台              | 总账财务、清算、人力科技、审计、监管报送                                                      | 强调"支撑与核算"，不直接对客户                      |
| 技术中台/业务中台 | 2015 年后从互联网引入的概念：统一客户视图、参数中心、支付网关、流程平台、消息与缓存等公共能力 | 说的时候要加限定语，避免和"风险中台"混淆            |

下面这张 ASCII 版图是本模块全部 11 篇的坐标系——从客户接触到监管报送，一次资金流动要穿过七层：

   │ 渠道层（客户可见，迭代最快，安全合规最密）                                  │
   │  统一柜面 │ 智能柜台STM │ 手机银行 │ 网上银行 │ 电话/视频银行 │ 微信/小程序    │
   │  自助设备ATM/CRS │ 收单POS │ 开放银行API │ 银企直连 │ 第三方代付入口         │

   ┌─────────────────────────────────────▼──────────────────────────────────────────▼──────────┐
   │ 核心银行系统（核心账务类，最内层，最不可动）                                                   │

读这张图的三个要点：

1. **越往下越稳**。渠道层的代码可能每周上线，核心账务层的一个字段可能要评审三个月。
2. **横切层不是可选项**。风控与合规在图右侧横切，意味着任何一笔交易的代码里都可能有"调名单、算限额、报反洗钱"的分支，这是银行代码量膨胀的主要来源之一。
3. **资金最终都要走出银行**。跨行必然落到人民银行或银联/网联清算，理解这一点才能理解"清算过渡科目"为什么存在（见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 第四节）。

## 三、把 JD 逐项拆开：四个词到底指什么

JD 原文：**"熟悉银行柜面系统、结算现金管理、网络金融等相关业务系统研发运维工作，了解银行业信息安全管理规范。"** 逐词翻译成系统 + 日常 + 技能：

| JD 词                | 指向的系统（版图位置）                                                                                                                                  | 研发日常做什么                                                                                         | 你需要会的东西                                                                           | 本模块哪篇讲                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **柜面系统**         | 渠道层最左一格：统一柜面/前端系统/柜员系统，外加成像采集、集中作业、授权平台                                                                            | 改交易码、加输入域与校验、对接核心的报文组装、打印与凭证模板、授权与复核流程、影像切片字段、无纸化改造 | 元数据驱动的表单/交易框架、报文拼装与解析、事务边界与冲正语义、字段影响面分析、权限模型  | [03](./03-柜面系统与集中作业.md)                                             |
| **结算现金管理**     | 两类：① 支付结算（行内账务清算、跨行走人行支付系统/银联网联）② 现金管理（网点钱箱尾箱、现金调拨、金库、自助设备清机加钞、全额清分与冠字号码、账户管理） | 清算对账与差错处理、报文收发（大小额/网结/银联）、账户与限额规则、现金实物账实核对、头寸与备付监控     | 对账与幂等、状态机与差错补偿、文件与批量处理、定时调度、DECIMAL 精度与借贷平衡           | [04](./04-支付清算体系与报文.md)、[05](./05-现金管理与资金头寸.md)           |
| **网络金融**         | 渠道层的电子渠道：手机银行、网上银行、直销银行、开放银行 API、场景分期与互联网贷款对接                                                                  | 接口与页面迭代、营销活动与流量承接、风控前置与实名/人脸核身、支付通道接入、可用性压测与降级            | 高并发与缓存、限流熔断、OAuth/签名验签与加解密、异步消息削峰、灰度发布、端到端埋点       | [06](./06-网络金融与电子渠道.md)                                             |
| **信息安全管理规范** | 横切所有层的制度与技术：数据分级分类、个人信息保护、密钥与加密机、脱敏、审计留痕、等级保护测评、渗透与代码审计                                          | 按规范改造：字段加密或脱敏、日志不落敏感信息、权限最小化与三员分立、上线前安全扫描与整改闭环           | 加解密与签名的工程用法（不是算法推导）、正则与脱敏实现、审计日志设计、合规条文的工程翻译 | [07](./07-银行业信息安全管理规范.md)、[08](./08-反洗钱账户管理与监管合规.md) |

一句话总结 JD 的画像：**这是一个"偏运营与渠道侧的 Java 后端岗"，主力战场在柜面 + 支付结算 + 现金/账户这条业务链上，而不是核心账务引擎的开发岗**。所以面试准备的重心应该是"业务术语 + 一致性与对账 + 合规意识"，而不是把时间全花在分布式事务理论上。

## 四、银行技术栈的现状与约束

### 4.1 双轨并存：大型机与分布式

| 轨道                                                           | 承载内容                                                              | 工程含义                                                                                     |
| -------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 大型机/传统集中式平台（IBM 主机、AS/400 小型机等，各行差异大） | 部分银行的老核心存款账务、清算、总账                                  | 语言与工具链陌生（COBOL/CICS、JCL、SMP/E）、改造周期长、文档与代码同源度低                   |
| 分布式与国产化平台                                             | 渠道、信贷、支付、管理、数据、新建核心或分布式核心                    | 技术栈和互联网接近（Spring Boot/Cloud、MySQL/国产库、Redis、MQ、容器），但版本被行内基线锁定 |
| 过渡形态                                                       | "双核心"或"核心下沉 + 外围上移"：老核心保留账务，新平台承接产品与流程 | **大量需求落在中间层**：同步/异步数据复制、双写一致性、灰度切流、结果比对                    |

### 4.2 单元化：把"高可用"变成一种架构约束

单元化（unit-based architecture，按客户/账号/机构等维度把流量与数据切片成多个可独立对外服务的"单元"，故障时只损失一个单元）在银行的价值是：单体故障半径可控、可水平扩展、天然满足灾备切换要求。代价也很实在：

- **路由规则要能讲清**：一笔跨单元转账（付款人在 A 单元、收款人在 B 单元）必须定义谁是主责单元、另一侧如何挂账过渡。
- **全局唯一 ID 变成硬需求**：单元内自增主键会撞号，必须用发号器或带单元位的复合 ID（对照 [03-数据库与ORM/04-分布式ID规范](../03-数据库与ORM/04-分布式ID规范.md)）。
- **全局汇总困难**：跨单元的实时合计（限额、头寸、报表）要么走集中层，要么走异步汇聚，不能靠一次跨单元 join。

### 4.3 信创 / 国产化替代：不是口号，是一堆具体适配工作

| 层次       | 常见替换方向（举例）                                      | 研发要做的具体事                                                                         |
| ---------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 芯片/整机  | ARM 系、x86 国产系等多种路线并存                          | 编译与依赖适配、性能基线重测、JDK 与 native 库版本对齐                                   |
| 操作系统   | 国产 Linux 发行版                                         | 路径与字符集差异、系统调用与内核参数、监控采集插件兼容                                   |
| 数据库     | 国产集中式/分布式数据库、MySQL 发行版；从 Oracle/DB2 迁移 | SQL 方言与函数改写、分页与序列语法、执行计划回归、事务隔离级别与锁行为差异、存储过程重写 |
| 中间件     | 国产消息、交易中间件、应用服务器、缓存                    | API 差异、集群与事务语义、连接池参数、替换后的可观测性补齐                               |
| 办公与工具 | 国产办公套件、浏览器内核约束                              | 打印/报表模板版式、旧浏览器的兼容代码                                                    |

**面试可以直接用的一句话**：信创项目的核心工作量往往不在"写新功能"，而在"把等价性验证做扎实"——SQL 方言改写、执行计划回归、双轨数据比对、结果一致性验收。这恰好是 Java + MySQL 背景能快速上手的地方（可对照 [03-数据库与ORM/01-MySQL核心知识](../03-数据库与ORM/01-MySQL核心知识.md) 与 [03-数据库与ORM/05-MySQL锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md) 里的锁与复制行为，迁移兼容性检查项都在这里）。

### 4.4 外采与自研的边界

| 通常外采                                                                                                                 | 通常自研                                                                             | 判断依据                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 核心账务产品、支付清算对接、影像与 ECM、信贷管理、反洗钱与名单、风控决策引擎、密码产品与加密机、监控与日志平台、流程平台 | 渠道与页面、场景与营销、中台公共服务、接口整合与适配层、数据服务与报表、内部效能工具 | 是否构成差异化竞争力、是否被监管指定接口、厂商锁定与 TCO、自主可控与信创要求、是否只有你有能力维护 |

外采系统的研发日常是"配置 + 二开 + 提工单 + 追版本"，而不是读源码改框架。**这也是为什么银行自研岗的价值集中在集成层和渠道层**：外采产品给了骨架，业务血肉全靠你写。

### 4.5 技术选型保守的真实原因

不要用"银行思维落后"解释，用这五个理由解释——面试这样答才加分：

1. **错误成本不对称**：一个 bug 在内容平台是"少曝光一条视频"，在银行是"客户资金算错 + 赔付 + 舆情 + 监管问询"。所以选择"被生产环境验证过多年的版本"。
2. **可回退优于可向前**：任何变更都要有回退方案，因此偏爱架构简单、问题可预测的组件。
3. **人才结构约束**：一个系统可能维护十年，人员轮转频繁，"任何一个骨干都能接手"比"用最新框架"更重要。
4. **审计与可追溯**：引入新组件要重建日志、权限、变更、密钥的审计链条，隐性成本极高。
5. **灾备指标是硬约束**：RPO/RTO（恢复点目标/恢复时间目标）要求组件必须具备成熟的跨中心切换能力，很多开源项目没有这个能力矩阵。

结论：**新技术先在外围试点，通常要经历数年才可能进入账务核心**。所以你会看到"手机银行用新前端框架、核心系统还在改老交易码"这种并存状态。

## 五、一家银行的"需求的一生"：组织协同视角

技术栈之外，你入职后最先不适应的是**流程**。下面这条链路是行业通用形态（各行叫法略有差异，具体以所在行制度为准），看懂它就看懂了"为什么银行做个小需求要两个月"：

```text
业务部门提需求（需求申请单 / 业务方案）
  ↓ ① 需求受理与初评（软开需求岗 + 系统负责人：有没有系统承载？属于哪班版本列车？）
  ↓ ② 可行性与架构评审（架构岗：能不能这么改？是否新增系统间接口？数据归属谁？）
  ↓ ③ 安全与合规前置评审（信息安全岗 / 反洗钱 / 运营与计财：涉及字段、科目、账户、外部机构都要过）
  ↓ ④ 立项与预算（涉及外采产品或新增资源的走采购，这一步可能独立耗时数月）
  ↓ ⑤ 需求规格说明 + 接口规格说明（写清到"交易码 / 字段 / 校验 / 异常码"级别）
  ↓ ⑥ 概设 / 详设评审（评审要留记录并签字，参与方包含被调系统的负责人）
  ↓ ⑦ 编码 + 单元自测 + 代码扫描（安全扫描与规范扫描不过线不能提测）
  ↓ ⑧ SIT 系统集成测试 → 性能测试 → 安全测试 → UAT 用户验收测试（业务部门签字确认）
  ↓ ⑨ 测试准出与缺陷收敛（遗留缺陷要分级并有人书面接受风险）
  ↓ ⑩ 投产方案评审（发布顺序、DDL 与数据脚本、参数下发、回退方案、验证清单，缺一不可）
  ↓ ⑪ 投产演练 / 预生产验证（用接近生产的规模与依赖跑一遍）
  ↓ ⑫ 投产窗口执行（数据中心执行、双人复核、逐步骤打勾；业务人员在窗口内做生产验证）
  ↓ ⑬ 观察期（盯差错、对账、批处理结果与关键交易成功率）
  ↓ ⑭ 需求关闭与文档归档（归档不是形式主义：审计与后续接手人都靠它）
```

| 阶段           | 主导方                 | 关键交付物                       | 新人最容易踩的坑                                     |
| -------------- | ---------------------- | -------------------------------- | ---------------------------------------------------- |
| 受理与初评     | 软开需求管理           | 需求受理结论、所属版本           | 以为"业务说要做"就能排上；实际版本席位是稀缺资源     |
| 架构与安全评审 | 架构岗、信息安全岗     | 评审意见与整改项                 | 跳过安全评审直接设计接口，投产前被打回               |
| 需求规格       | 业务 + 需求分析        | 需求说明书、接口规范             | 把"字段加一个"当成一句话需求，没人评估下游八层影响面 |
| 设计与评审     | 系统负责人             | 概设/详设、评审记录              | 只写正常流程，不写异常与冲正语义（银行最在意这个）   |
| 开发与自测     | 开发                   | 代码、单元测试、扫描通过报告     | 本地跑通用真实数据测，忽略了字段编码与敏感信息落日志 |
| 测试           | 测试团队 + 业务        | 测试案例、缺陷单、UAT 签字       | 需求变更只在口头同步，测试案例与文档不同步           |
| 投产           | 数据中心 + 开发 + 业务 | 投产方案、回退方案、生产验证清单 | 回退方案写"恢复备份"但没有数据回滚口径               |
| 观察期         | 运维 + 开发值守        | 差错登记、对账结果、值班记录     | 投完就走，第二天对账不平被叫回去查历史流水           |

这段流程里，**你的代码只是其中一步**。理解上下游的存在，才能写出"可回退、可核对、可审计"的代码——这是银行对工程师最真实的能力要求（流程细节与管控手段见 [10-银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)）。

## 六、银行 vs 互联网研发：真实差异与取舍理由

| 维度         | 互联网常见做法                      | 银行常见做法                                                                           | 银行为什么这么做（取舍理由）                                                                                                                                       |
| ------------ | ----------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 发布节奏     | 每天多次、持续交付、特性开关灰度    | 版本列车：按月/季集中投产，加紧急版本通道；投产在业务低峰窗口（通常周末夜间）          | 集中发布便于统一回归与整体回退；变更是最大故障源，减少变更次数就是减少故障机会                                                                                     |
| 变更管控     | Code Review + 流水线卡点            | 在流水线之外还有投产单、变更评审、回退点、双人复核执行、封版期（季末年末与监管报送期） | 生产环境的每一步都要"有人批准、有人执行、有人核对"，把个人权限压到最小                                                                                             |
| 测试重心     | 自动化 + 灰度 + 线上小流量          | 全量回归 + UAT（用户验收测试）+ 投产演练 + 生产验证清单                                | 银行不允许"用真实客户小流量试错"，账务错误不可灰度                                                                                                                 |
| 文档交付     | README + 接口注释，文档常滞后       | 需求说明书、概要/详细设计、接口规范、测试案例、投产与回退方案、变更记录，评审签字归档  | 审计要看、接管要用、追责要有依据。文档是交付物的一部分而不是附属品                                                                                                 |
| 稳定性优先   | 快速迭代 + 事后复盘，靠错误预算调节 | 事前评审极重，宁可推迟需求也不接受带风险上线                                           | 银行对"可用性"的度量还包括"资金正确性"，后者不能靠事后补偿（对照 [13-稳定性工程/04-高可用架构模式](../13-稳定性工程/04-高可用架构模式.md) 的通用手段，取舍点不同） |
| 技术决策驱动 | 团队自主 + 社区选型                 | 架构基线 + 安全规范 + 预算与采购流程 + 供应商支持能力                                  | 决策是"合规 + 商务 + 运维成本"的综合结果，纯技术优势不足以通过评审                                                                                                 |
| 数据与权限   | 内部工具可查较多数据                | 生产数据不可随意导出，敏感字段加密/脱敏，查询留痕，测试环境必须造数或用脱敏数据        | 个人信息保护与数据分级分类的硬要求（见 [07](./07-银行业信息安全管理规范.md)）                                                                                      |
| 加班结构     | 常态加班 + 大促/发布峰值            | 日常相对规律，**版本投产前集中冲刺 + 夜间/周末窗口执行**，数据中心有轮班值守           | 峰值由"窗口"决定而非"业务增长"决定，可预期，但窗口不由你选                                                                                                         |
| 薪酬结构     | 现金 + 股票，波动大                 | 基本工资 + 绩效 + 年终奖 + 各类补贴，结构稳定；子公司更市场化                          | 天花板明显但方差小；关注"总包 + 稳定性 + 公积金与福利基数"，别只看月薪                                                                                             |
| 晋升         | 技术职级为主，跳级靠项目与影响      | 岗位/职务序列 + 专业职级并行，重视年限、证书、内训与认证                               | 论资历的部分真实存在；破局方式往往是"成为某块业务唯一讲得清的人"                                                                                                   |

> 用错误预算的语言解释两者的差异最准确：互联网把可靠性预算当**决策依据**（预算花光就冻结功能），银行把可靠性当**准入门槛**（没有回退方案和评审结论就不许上线）。预算可以谈，门槛不能谈——这就是发布节奏差异的根因（错误预算机制见 [13-稳定性工程/01-SLI-SLO与错误预算](../13-稳定性工程/01-SLI-SLO与错误预算.md)）。

## 七、你已有的四项技能在银行怎么落位

你已经会的 Spring Boot / MySQL / Redis / RocketMQ **在银行都能直接用**，问题不在技术本身，而在"用法约束"。下表把每项拆成三层：能直接用、需要改造、必须新学。

| 你的技能                | 在银行的直接用途                                                     | 需要改造的习惯                                                                                                                                                 | 必须新学的认知                                                                        | 本仓库可对照的文档                                                                                                                                                                                                      |
| ----------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spring Boot / Cloud** | 渠道服务、中台公共服务、支付网关、对接层，与你现在的写法高度一致     | 版本被行内基线锁定（不能随意升级 starter）；很多行有自研统一框架与父 POM，配置来源是配置中心 + 参数中心而非本地 yml；日志格式与 traceId 要接行内规范           | "服务不能随意重启"、发布顺序依赖、优雅停机与在途交易处理                              | [13-稳定性工程/04-高可用架构模式](../13-稳定性工程/04-高可用架构模式.md)                                                                                                                                                |
| **MySQL**               | 外围与中台库、部分银行的分布式核心、报表与流水库；国产库迁移的主战场 | 金额一律 DECIMAL 且不能出现浮点；主键不能自增裸用（跨单元/分库要发号）；不允许在应用里跑长事务与全表扫描；DDL 要走变更审批                                     | 会计日期与自然日期分离、余额与流水分离、日终批量与归档策略                            | [03-数据库与ORM/01-MySQL核心知识](../03-数据库与ORM/01-MySQL核心知识.md)、[04-分布式ID规范](../03-数据库与ORM/04-分布式ID规范.md)、[05-锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md) |
| **Redis**               | 限额与频次计数、会话与令牌、分布式锁、热点参数缓存、幂等键存放       | **绝不能当账务事实源**：余额、发生额、凭证状态必须以数据库/核心为准；缓存与账面余额口径不一致时要有明确取数规则；生产 Redis 权限受控、大 key 与热 key 会被问责 | 缓存击穿在银行场景里等于"客户查询失败"，降级要给出"上次已知值 + 明显标注"而不是空数据 | [04-中间件/02-RocketMQ消息队列](../04-中间件/02-RocketMQ消息队列.md)（同层的中间件治理思路）                                                                                                                            |
| **RocketMQ**            | 记账事件异步化、渠道与核心的解耦、对账文件到达通知、批量任务削峰     | 消息不能替代对账：任何"发消息就认为成了"的设计在账务上都不成立；重试耗尽必须进死信并有人处理；消费幂等键要与交易流水号统一                                     | 事务消息 + 本地流水表 + 对账补偿的三件套；消息乱序对状态机的影响                      | [04-中间件/08-RocketMQ事务消息与死信队列](../04-中间件/08-RocketMQ事务消息与死信队列.md)、[02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)                                                  |

**面试表达模板**（把上面三层浓缩成一句可用的话）：
"我在原项目里用 Redis 做预占、用 RocketMQ 做异步解耦，思路迁移到银行是一样的——**只是银行多了一条硬约束：任何异步链路都必须有对账与补偿兜底，因为消息丢失在电商是体验问题，在账务是资金差错。**"

## 九、初学者常见误区

| 误区                                 | 真相                                                                                                                                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "银行开发 = 写核心系统"              | 核心账务团队人少、门槛高、改动极少。绝大多数银行 Java 岗在**渠道、支付结算、运营与中台集成层**，JD 里那四个词没有一个是核心账务开发                              |
| "银行都用最新技术"                   | 恰恰相反：技术栈被行内基线锁定，JDK/框架版本落后是常态。价值在于**把老技术用稳**，以及能做迁移和适配                                                             |
| "银行都是外包在干活"                 | 外包承担了大量测试、外围维护与批量编码，但需求分析、架构、投产决策、核心改造由行方自研团队掌控。**关键区别是有没有系统的所有权和设计权**                         |
| "银行开发就是 CRUD，没什么技术含量"  | 银行的技术难点不在业务复杂度低，而在**一致性、并发热点、日终批处理、灾备切换、可追溯**这些"看不见的需求"上。把 CRUD 做成可审计、可回退、可核对，是另一套工程能力 |
| "柜员看到的界面就是数据库字段"       | 柜面是元数据驱动的工作台，一个输入域可能来自参数中心、校验规则在中间层、落库字段在核心、展示口径还要加工（见 [03](./03-柜面系统与集中作业.md)）                  |
| "改个小字段影响很小"                 | 影响面要沿"渠道 → 报文 → 中间层 → 核心 → 凭证 → 影像 → 监管报送 → 对账文件"逐层评估，定长报文动一个字段会位移整条链路                                            |
| "银行的慢是效率问题"                 | 大部分"慢"是**用流程换确定性**：评审、回归、演练、回退点。你抱怨的地方，正是它不出大面积资金事故的原因                                                           |
| "先懂技术再学业务"                   | 银行岗的业务术语是入场券。听不懂"轧账""交易码""头寸""冲正"，技术方案再好也聊不下去                                                                               |
| "反洗钱、等保这些东西是合规部门的事" | 具体落到代码上：字段加密、脱敏、日志不落敏感数据、权限最小化、审计留痕，全是研发的活                                                                             |

## 十、面试高频问答

**Q1：银行的技术部门和业务部门是什么关系？**
A：业务部门（个金、公司、普惠、金融市场、运管、会计财务、风险管理等）提需求并拥有业务规则解释权；科技条线（总行科技部/软开/数据中心，或金科子公司）负责实现与运行。典型协作链路是"业务部门提需求 → 科技部评审架构与可行性 → 软开交付 → 数据中心投产运维"，涉及安全的过信息安全岗，涉及对外服务的过监管口径。你要能说出"需求方不是技术方，业务规则的最终解释权在业务部门"。

**Q2：为什么银行不轻易升级技术栈？**
A：四个原因：错误成本不对称（账务错误不可灰度试错）、可回退优先（偏爱被多年生产验证的版本）、人才与文档约束（系统生命周期十几年，人员轮转，接手成本高于性能收益）、灾备与审计硬要求（组件必须支持成熟的双活/切换能力和完整留痕）。所以技术引入遵循"外围试点 → 非关键系统 → 关键系统"的多年路径。

**Q3：银行说的"中台"和互联网的"中台"是一回事吗？**
A：不是。银行的"中台"传统上指**风险中台、作业中台**——把审批、授权、集中处理、合规检查从网点搬到总行集中做，是组织与流程概念。互联网语境的"业务中台/技术中台"指可复用的公共系统能力（统一客户、参数中心、支付网关、消息缓存）。面试时要说清是哪一种，说"我们建了个业务中台"而不加限定，在银行人耳朵里是含糊的。

**Q4：什么是信创？对研发具体提出什么要求？**
A：信创即信息技术应用创新，指从芯片、操作系统、数据库到中间件和办公软件的国产化替代。落到研发身上是四件事：SQL 方言与存储过程改写、执行计划与性能基线回归、依赖与编译适配、双轨数据一致性比对。它考验的是等价性验证能力，而不是从零写业务。

**Q5：单元化解决了什么问题，又带来什么麻烦？**
A：解决的是故障半径和水平扩展——按客户/账号/机构切片成多个能独立服务的单元，一个单元坏了不全盘失血，同时天然满足灾备切换。麻烦有三：跨单元交易要明确主责单元并用过渡科目挂账、全局唯一 ID 不能用自增主键、跨单元的实时汇总（限额、头寸、报表）必须走集中层或异步汇聚。

**Q6：JD 里的"结算"和"支付"有什么区别？**
A：口语里常混用，严格分层看：**支付**是付款意愿到资金指令的过程（交易发起、鉴权、报文）；**清算**是收付双方机构之间轧差与计算应收应付（谁该给谁多少钱）；**结算**是资金最终落定、账务完成记账（钱真的到了）。所以一笔跨行转账要穿过"支付指令 → 人行/银联网联清算 → 双方行内记账结算"。详细拆解见 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**Q7：柜面岗、支付岗、渠道岗，零金融经验的人选哪个切入最快？**
A：从**支付结算与对账**切入最快，因为它的问题结构和你已有的经验高度同构：异步链路、幂等、状态机、差错补偿、对账——都能在电商订单场景里找到对应物（对照 [02-Spring微服务/12-订单状态机治理](../02-Spring微服务/12-订单状态机治理.md)、[02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)、[14-数据工程与OLAP/08-数据质量与对账](../14-数据工程与OLAP/08-数据质量与对账.md)）。柜面岗需要补大量制度性知识（授权、复核、凭证、现金），上手慢但壁垒一旦建立就很难被替代。

**Q8：银行研发会不会被 AI 替代得更快，因为写的都是配置和胶水？**
A：被替代得最快的恰恰是"照模板改字段、写转换代码"这部分；替代不掉的是"知道这个字段能不能改、改了影响哪几层、出了问题谁负责"。银行系统里最难的是隐性知识——制度约束、历史包袱、跨系统契约，这些不在代码里。所以本模块的读法不是背术语，而是建立"看到一句话能推出影响面和风险点"的判断力。
