## 一、核心银行系统管什么、不管什么

核心银行系统（core banking system，全行客户、存款、贷款、账务与总账的权威记录系统，业内简称"核心"）的第一原则是：**它是账务事实源，不是业务前台**。

| 职责域               | 核心里做什么                                                           | 关键设计点                                                       |
| -------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 客户信息（CIF）      | 全行唯一客户号、证件、客户级状态与控制                                 | 一人多号的合并解并；客户级冻结优先于账户级                       |
| 存款                 | 活期/定期/通知/协定/保证金的开立、变动、到期处理                       | 账户状态机；控制账户与子账户；可动用余额与账面余额分离           |
| 贷款                 | 借据、放款、还款计划、逾期与展期、风险分类与减值                       | 应计与非应计切换；本金/利息/罚息/复利的科目归属拆分              |
| 支付结算             | 行内转账、汇出汇入、代收付、内部户资金流转                             | 借贷平衡的事务边界；清算过渡科目的挂账与轧平                     |
| 账务与总账           | 分录生成、登记分户账与总账、科目日结、损益结转                         | 复式记账强约束；总账与分户账账账核对                             |
| 产品参数（产品工厂） | 用参数定义产品：利率、期限、计费、账户结构、允许交易                   | 参数版本化与生效日期，绝不能用"当前值"算历史业务                 |
| 利率与计息           | 利率档次、计提与结息、积数维护                                         | 算头不算尾、360 天基准、复利规则                                 |
| 限额与日终           | 限额与累计控制、透支冻结；日终批处理（结转、对账、报送供数、日期推进） | 累计值天然是热点写（第八节）；批处理讲依赖顺序与可重跑（第七节） |

**不进核心的事**（面试常考边界感）：产品营销与页面流程（渠道）、授信审批与风控决策（信贷/风控）、财务核算与发票（财务系统）、监管报表口径加工（数据/报送平台）、跨行报文通信（支付前置）。核心只接收"已决定要发生的业务事件"，负责把它变成合规的分录。它在整张系统版图里位于"业务中台之下、总账之上"，完整分层见 [01-银行IT体系与岗位全景](./01-银行IT体系与岗位全景.md) 第二节。

## 二、会计基础从零：借贷记账法

### 2.1 唯一的恒等式与两个方向符号

```text
资产 = 负债 + 所有者权益                （静态：某一时点的家底）
利润 = 收入 − 费用                      （动态：一段时期的成果）
资产 + 费用 = 负债 + 所有者权益 + 收入    （扩展等式，借贷方向由此推出）
```

**人话版**：银行手里的每一分钱都有来源——要么是欠别人的（负债，含客户存款），要么是股东的和本年赚的（所有者权益）。两边永远相等，这是"有借必有贷，借贷必相等"的物理基础，不是玄学。而"借"（Debit）与"贷"（Credit）**只是 T 型账的左右两边，不含好坏、也不等于借钱**：借方不等于"增加"，贷方也不等于"贷款"。每笔分录至少一进一出、两边合计相等，绝不允许只记一边（单式记账）。

### 2.2 五类账户性质与余额方向（必须背下来）

| 账户性质     | 借方记             | 贷方记             | 正常余额方向                                         | 银行常见科目举例                                     |
| ------------ | ------------------ | ------------------ | ---------------------------------------------------- | ---------------------------------------------------- |
| 资产类       | 增加               | 减少               | 借方                                                 | 库存现金、存放中央银行款项、存放同业、贷款、应收利息 |
| 负债类       | 减少               | 增加               | 贷方                                                 | 吸收存款、同业存放、向中央银行借款、应付职工薪酬     |
| 共同类       | 视科目             | 视科目             | **由余额方向定性质**：借余表现为资产、贷余表现为负债 | 清算资金往来、货币兑换、衍生工具                     |
| 所有者权益类 | 减少               | 增加               | 贷方                                                 | 实收资本、资本公积、盈余公积、本年利润               |
| 损益类       | 费用增加、收入减少 | 收入增加、费用减少 | 期末结转后**无余额**                                 | 利息收入、手续费及佣金收入、利息支出、业务及管理费   |

**共同类为什么存在**：银行间清算往来在一天之内可能应收也可能应付，预先定成资产或负债都不合适，就用一个方向可正可负的过渡性质承载——最常见的是清算/联行往来类科目（见 §4.2）。

### 2.3 为什么客户存款是银行的负债

三个角度讲通一个即可。**偿还义务说**：客户存 100 元，银行有义务在客户要求时归还本金加利息——有现时义务、会导致经济利益流出，符合负债定义。**债权人视角说**：存款人是银行的债权人，"吸收存款"通常是银行资产负债表上占比最大的负债项。**资金流向说**：存款是资金**来源**（记贷方），贷款是资金**运用**（记借方），方向刚好相反——这解释了银行为什么赚"贷款利息收入 − 存款利息支出"这个息差。

> **面试加分句**：所以"给客户存款账户加钱"在系统里是**贷记**客户账。银行卡的"借记/贷记"命名根源就在这里：借记卡直接动用你在银行的债权（存款），贷记卡（信用卡）是银行给你一笔债权额度。

## 三、科目体系与"三账"

### 3.1 科目层级与三种"号"

```text
一级科目（总账科目）吸收存款 → 二级 活期/定期 → 三级明细（币种、期限档次）
   → 银行内部账户（分户账，记账的最小单位） → 客户账号（卡号/折号，对外展示标识）
```

| 概念                      | 是什么                                                 | 谁维护                     | 数量关系                                |
| ------------------------- | ------------------------------------------------------ | -------------------------- | --------------------------------------- |
| 会计科目                  | 全行统一的分类编号体系，新增停用需总行会计管理部门批准 | 总行会计/计财              | 一个科目下挂海量账户                    |
| 银行内部账户              | 系统里真实记账的对象，有余额、状态、归属机构           | 核心自动开户               | 绑定末级科目 + 币种 + 期限              |
| 客户账号                  | 客户看到的那个号（卡号、折号、单位结算账号）           | 卡系统/账户管理            | 与内部账户常为 1:1 或 1:N（一卡多账户） |
| 内部户（过渡/暂收暂付户） | 银行自己为业务过程开的账户                             | 运营与会计管理，开立要审批 | 挂账、差错、清算过渡都在此，审计重点    |

### 3.2 三账：总账、分户账、卡片账

| 账     | 记录粒度                  | 用途                                     | 一致性要求                                      |
| ------ | ------------------------- | ---------------------------------------- | ----------------------------------------------- |
| 总账   | 科目 × 机构 × 币种 × 期间 | 编报、平衡资产负债、监管口径             | 由分录汇总登记                                  |
| 分户账 | 单个账户                  | 客户对账、计息、余额查询、交易校验       | **Σ 该科目全部分户账 = 该科目总账**（账账相符） |
| 卡片账 | 单户"户口页"              | 账户资料、利率、期限、预留印鉴、余额快照 | 与分户账同源，改动留痕                          |

实务另有**科目日结单**（按科目汇总当日借贷发生额与凭证张数）与**余额表**（按科目列示账户余额清单）两个工具，目的都是让账账核对能机械化执行。

## 四、五个完整分录例子（含 T 型账）

> 金额均为示例；科目名用行业通用叫法，科目号各行不同。五笔的分录头均可自查"借方合计 = 贷方合计"。

### 4.1 例 1：客户现金存入 10,000.00 元（活期）

```text
借：库存现金                                10,000.00   （资产增加）
    贷：吸收存款——活期存款——××客户户         10,000.00   （负债增加）

    T 型账（左借右贷）
      库存现金（资产类）        借①10,000.00 │ 贷 ——        → 期末借余 10,000.00
      吸收存款·活期（负债类）    借 ——        │ 贷①10,000.00 → 期末贷余 10,000.00
```

工程侧要点：柜员收现金 → 钱箱实物增加 → 核心账面增加，**两个"增加"必须同时成立**。这就是轧账能查出长款短款的原理（见 [03-柜面系统与集中作业](./03-柜面系统与集中作业.md) 第四节）。

### 4.2 例 2：跨行转账 50,000.00 元（付款行视角，经人民银行支付系统清算）

难点在于：**扣客户账的时刻，钱还没真的划到对方行**。中间必须有共同类过渡科目承接这段差额。

```text
步骤①（受理，实时）扣客户账并挂账
借：吸收存款——活期存款——付款人A户            50,000.00
    贷：清算资金往来——汇出待清算款项          50,000.00
步骤②（清算完成，按回执或日终）资金从准备金划出
借：清算资金往来——汇出待清算款项              50,000.00
    贷：存放中央银行款项                      50,000.00

T 型账（左借右贷，A 户期初贷余 120,000）
  吸收存款·A户        借①50,000 │ 贷 120,000 → 期末贷余 70,000（负债减少记借方）
  清算资金往来（共同类）借②50,000 │ 贷①50,000 → 日终余额必须 = 0（轧平）
  存放中央银行款项      借  期初   │ 贷②50,000 → 期末借余 减少 50,000
收单行镜像（复式记账天然对称）：借 存放中央银行款项 50,000 / 贷 清算资金往来（汇入待入账）50,000
                        借 清算资金往来（汇入待入账）50,000 / 贷 吸收存款——B户 50,000
```

**过渡科目为什么是排障重点**：日终"清算资金往来"余额不为零，说明有笔数挂账未轧平——回执没回、重复记账、或清算文件与账务状态不一致。**所有跨行差错的排查都从这个科目开始**（机制见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md)）。

### 4.3 例 3：贷款放款 200,000.00 元到借款人本行账户

```text
借：贷款——个人贷款——本金——××借款人户        200,000.00   （资产增加：多一笔债权）
    贷：吸收存款——活期存款——××借款人户       200,000.00   （负债增加：客户账上多了钱）
```

**反直觉的点**：银行"凭空"创造了 20 万存款，资产与负债同时增加、等式仍平——这就是贷款创造存款的会计事实。同时还要登记借据台账、还款计划、担保与额度占用（这些是**登记簿，不产生分录**）；银行承兑汇票、保函等或有事项走**表外科目**登记，不进资产负债平衡。

### 4.4 例 4：贷款还款，本金 50,000.00 + 利息 1,200.00（本息拆分）

```text
情形 A：利息已按期计提并挂在应收利息（权责发生制下的常态）
借：吸收存款——活期存款——××借款人户          51,200.00
    贷：贷款——个人贷款——本金——××借款人户      50,000.00
    贷：应收利息                               1,200.00
情形 B：一部分利息未到计提节点，属本次还款当期新增收入
借：吸收存款——活期存款——××借款人户          51,200.00
    贷：贷款——本金——××借款人户                50,000.00
    贷：应收利息（已计提部分）                   1,050.00
    贷：利息收入（本期新增部分）                      150.00
```

**这就是"本息拆分"的代码语义**：一笔 51,200 拆成多条贷方分录，且金额来源不同（本金来自还款计划表、利息来自计息引擎）。拆错了会让贷款余额与利息收入同时错，而**总额仍然平衡、借贷校验查不出来**——只能靠业务恒等式兜底（思路同 [14-数据工程与OLAP/08-数据质量与对账](../14-数据工程与OLAP/08-数据质量与对账.md)）。含罚息与复利时还要拆逾期本金、罚息、复利，并处理逾期后利息由表内应收转表外登记的应计方式切换。

### 4.5 例 5：收取转账手续费 50.00 元（中间业务收入，含价税分离）

```text
借：吸收存款——活期存款——付款人户                 50.00
    贷：手续费及佣金收入——结算业务手续费          47.17
    贷：应交税费——应交增值税（销项税额）           2.83
计算：50 ÷ (1 + 6%) = 47.17，税额 = 50 − 47.17 = 2.83
（金融业增值税常见按 6%，税率与免税范围以现行税法为准）
```

若行内按简化口径全额计收入（贷：手续费及佣金收入 50.00），则由财务系统在期末做税金调整——**两种做法都存在，接口设计必须先确认口径**，否则收入与税会重复计。

## 五、账务系统数据模型

### 5.1 五条设计铁律

| 铁律                         | 为什么                                            | 违反后的典型事故                              |
| ---------------------------- | ------------------------------------------------- | --------------------------------------------- |
| **余额与流水分离**           | 流水是不可变事实，余额是可复算的派生值            | 只存余额→无法追溯；只存流水→每次查询全量汇总  |
| **会计日期与物理时间分离**   | 日切窗口内一笔交易物理时间在 T+1、会计归属在 T    | 用 `create_time` 做账→日终核对永远不平        |
| **余额与发生额同事务更新**   | 余额、当日借/贷累计、积数须在同一条 UPDATE 内完成 | 分两次更新→中间态被日切读到，积数与余额不一致 |
| **金额一律 DECIMAL**         | 浮点累加产生分位差                                | 用 double→对账不平且无法解释                  |
| **冲正用新流水，不删旧流水** | 审计要求任何变动可回放                            | `DELETE` 流水→审计直接判不合规                |

### 5.2 建表 DDL 示例

```sql
-- ① 分户账主档：余额 + 当日发生额累计 + 计息积数（客户主档/科目表/内部户从略）
CREATE TABLE acct_info (
    acct_no        VARCHAR(34)   NOT NULL COMMENT '账号（内部账户/分户账号）',
    cust_no        VARCHAR(32)   NOT NULL COMMENT '客户号（全行唯一主数据，证件号须密文存储）',
    subject_code   VARCHAR(20)   NOT NULL COMMENT '归属末级科目（科目号各行自定）',
    currency       CHAR(3)       NOT NULL COMMENT '币种 ISO 4217，如 CNY',
    branch_no      VARCHAR(15)   NOT NULL COMMENT '开户机构号',
    balance        DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '账面余额，无符号，方向看 balance_dir',
    balance_dir    CHAR(1)       NOT NULL COMMENT 'D借 C贷，自科目冗余以省 join',
    prev_day_bal   DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '上日日终余额',
    cur_debit_amt  DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '本营业日借方累计发生额',
    cur_credit_amt DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '本营业日贷方累计发生额',
    accum_product  DECIMAL(22,2) NOT NULL DEFAULT 0.00 COMMENT '计息积数（每日余额累加）',
    avail_bal      DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '可动用余额（扣冻结/质押/在途）',
    last_post_date DATE          NOT NULL COMMENT '最后记账的会计日期',
    acct_status    VARCHAR(8)    NOT NULL DEFAULT 'NORMAL' COMMENT 'NORMAL/FROZEN/DORMANT/CLOSED',
    PRIMARY KEY (acct_no),
    KEY idx_cust (cust_no, subject_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分户账主档';

-- ② 账户交易流水：append-only，按月分区，只插入不修改
CREATE TABLE acct_txn (
    biz_date       DATE          NOT NULL COMMENT '会计日期（营业日期），非物理时间',
    txn_serial_no  VARCHAR(64)   NOT NULL COMMENT '全局流水号：日期+机构+序列',
    txn_time       DATETIME(3)   NOT NULL COMMENT '物理交易时间，毫秒',
    txn_code       VARCHAR(12)   NOT NULL COMMENT '交易码',
    channel_id     VARCHAR(8)    NOT NULL COMMENT '柜面/STM/手机银行/前置/批量',
    acct_no        VARCHAR(34)   NOT NULL,
    dc_flag        CHAR(1)       NOT NULL COMMENT 'D借 C贷',
    txn_amt        DECIMAL(18,2) NOT NULL,
    balance_after  DECIMAL(18,2) NOT NULL COMMENT '本笔记账后余额，可复算，核对依据',
    txn_status     VARCHAR(12)   NOT NULL COMMENT 'SUCCESS/REVERSED/UNKNOWN/PENDING',
    orig_txn_no    VARCHAR(64)       NULL COMMENT '冲正/撤销时指向被冲正的原流水',
    PRIMARY KEY (biz_date, txn_serial_no, acct_no),
    KEY idx_acct_date (acct_no, biz_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账户交易流水'
PARTITION BY RANGE COLUMNS(biz_date) (PARTITION p202601 VALUES LESS THAN ('2026-02-01'));

-- ③ 会计分录行：一笔交易多借多贷，行合计必须借贷相等（分录头含流水号/机构/币种/摘要，略）
CREATE TABLE gl_entry_line (
    line_id BIGINT NOT NULL COMMENT '发号器生成，不用自增', entry_id BIGINT NOT NULL,
    line_seq INT NOT NULL COMMENT '行序号，保证重放顺序一致', subject_code VARCHAR(20) NOT NULL,
    acct_no VARCHAR(34) NULL COMMENT '客户/内部账户；纯总账行为 NULL', currency CHAR(3) NOT NULL DEFAULT 'CNY',
    debit_amt DECIMAL(18,2) NOT NULL DEFAULT 0.00, credit_amt DECIMAL(18,2) NOT NULL DEFAULT 0.00,
    PRIMARY KEY (line_id), UNIQUE KEY uk_entry_seq (entry_id, line_seq),
    CONSTRAINT chk_one_side CHECK (debit_amt = 0.00 OR credit_amt = 0.00)
) COMMENT='会计分录行';
```

四个易忽略的细节：① 流水主键把 `biz_date` 放首位，让"按日核对"和"分区归档"都走主键；② `CHECK (debit_amt = 0 OR credit_amt = 0)` 把"单行借贷混记"从数据层堵死；③ 还需要一张**总账余额表** `gl_balance(biz_date, branch_no, subject_code, currency, open_bal, debit_amt, credit_amt, close_bal)`，主键为四元组、由分录行汇总登记，它是"总分核对"的另一边；④ 全局流水号规范见 [03-数据库与ORM/04-分布式ID规范](../03-数据库与ORM/04-分布式ID规范.md)（单元化下自增主键一定不够用），客户证件号必须密文存储、不得明文落库（见 [07-银行业信息安全管理规范](./07-银行业信息安全管理规范.md)）。

### 5.3 记账的核心：一条 UPDATE 解决余额与发生额

```sql
-- 禁止"先 SELECT 再 UPDATE"：并发下必然丢更新
UPDATE acct_info
   SET balance = balance + #{amt}, cur_debit_amt = cur_debit_amt + #{amt},  -- 发生额累计同语句完成
       last_post_date = #{bizDate}
 WHERE acct_no = #{acctNo} AND acct_status = 'NORMAL'
   AND avail_bal >= #{amt};                    -- 可用余额校验下推进行锁内
-- 影响行数 = 0 的三种可能：状态不符 / 余额不足 / 锁等待超时，必须分别处理，不能一律报"记账失败"
```

对照阅读 [03-数据库与ORM/05-MySQL锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md)：为什么"记账走主库、余额查询也不能随便走从库"在银行是刚性结论——主从延迟会让客户看到旧余额并重复发起交易。

## 六、利息计算

### 6.1 计息法、换算与口径

| 方法/口径          | 规则                                                                | 用于                     | 工程要求                                                               |
| ------------------ | ------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------- |
| **积数计息法**     | 利息 = 累计积数 × 日利率；累计积数 = Σ（每日余额 × 该余额存续天数） | 活期等余额频繁变动的账户 | 须每笔变动或每日维护 `accum_product`，不能日终重算全历史               |
| **逐笔计息法**     | 利息 = 本金 × 利率 × 期限（对年对月对日，零散天数按日）             | 定期存款、贷款借据       | 借据存"起息日、到期日、利率、计息基准"且不可变                         |
| **利率换算**       | 年利率 ÷ 12 = 月利率；月利率 ÷ 30 = 日利率；年利率 ÷ 360 = 日利率   | 人民币存贷款             | 换算用 360，**计息天数仍按真实日历天数**（不是每月当 30 天），最易搞混 |
| **算头不算尾**     | 计息天数含起息日（或每笔变动当日）、不含结束日                      | 全部业务                 | 3 月 10 日存、3 月 21 日取 → 计息 11 天而非 12 天                      |
| **币种与利率层次** | 部分外币按 365 天折算；挂牌利率/执行利率/罚息利率三层分开存         | 外币与贷款               | 计息基准（ACT/360、ACT/365）作产品与借据参数                           |
| **利息税**         | 自 2008 年 10 月起对储蓄存款利息所得暂免征收个人所得税              | 个人存款                 | 现行个人利息入账不再代扣该税（以现行税法为准）                         |

### 6.2 手算算例（面试可能要你现场算）

**算例 A（积数法·活期）**：3 月 10 日存入 100,000.00，年利率 0.35%，3 月 15 日支取 40,000.00，结息日 3 月 20 日。

```text
3/10~3/14：100,000.00 × 5 天 = 积数 500,000.00 ；3/15~3/20：60,000.00 × 6 天 = 积数 360,000.00 → 合计 860,000.00
日利率 = 0.35% ÷ 360；利息 = 860,000.00 × 0.0035 ÷ 360 = 8.36 元
入账：借 利息支出 8.36 / 贷 吸收存款——活期存款——该户 8.36
```

**算例 B（逐笔法·定期）**：本金 200,000.00、存期 1 年、年利率 1.45% → 利息 = 200,000 × 1.45% = 2,900.00。提前支取部分通常按支取日挂牌活期利率计息（以合同与现行规定为准）；到期自动续存时本金与利息合并进入下一存期——这就是定期上的"复利"体现。

**算例 C（逾期罚息）**：贷款本金 100,000.00、合同年利率 6%、逾期 20 天、罚息按合同利率上浮 50% → 罚息利率 = 6% × 1.5 = 9%，罚息 = 100,000 × 9% ÷ 360 × 20 = **500.00 元**。逾期罚息按合同利率上浮一定幅度计收、挪用贷款幅度更高，幅度区间与复利规则以监管规定与借款合同约定为准；对未按期支付的利息一般按罚息利率计收复利，罚息本身是否再计息各机构口径不同，须按合同确认。

### 6.3 计提 vs 结息：两个动作别混淆

- **计提（accrual）**：每日/每期按权责发生制预提。存款侧 `借 利息支出 / 贷 应付利息`，贷款侧 `借 应收利息 / 贷 利息收入`。目的是让损益落在正确的会计期间。
- **结息（capitalization）**：按周期把利息真正入账给客户，`借 应付利息 / 贷 吸收存款——客户户`。个人活期通常按季结息，结息日常见为季度末月 20 日、21 日入账（以现行规定为准）。两动作分离，正是"利息算对了但没入账给客户"这类投诉的技术根源，也是日终最容易出错的环节之一。

## 七、日终与日切

### 7.1 日切在做什么

日切（daily cut，把系统营业日期从 T 推进到 T+1 的动作）不是改一个日期字段，而是**一整套有严格依赖顺序的批处理跑完之后才允许推进日期**。日期推进那一刻，前一天的账才算关账。

```text
营业日 T（白天）│ 日终批处理窗口（夜间）                            │ 营业日 T+1
────────────┼──────────────────────────────────────────────────┼──────────
 正常交易    │ ① 渠道暂停/入口交易限制  ② 在途交易终态化（查询/冲正/清账）│ 余额已结转
            │ ③ 外部清算报文与对账文件收取核对                      │ 发生额归零
            │ ④ 明细记账收尾 → 分户账余额与发生额结转                │ 新交易开跑
            │ ⑤ 利息计提 → 到期结息 → 积数结转                     │
            │ ⑥ 贷款到期逾期、风险分类、减值计提  ⑦ 外币汇兑损益重估   │
            │ ⑧ 分录汇总登记总账（科目日结单 → gl_balance）          │
            │ ⑨ 账账核对：总账 vs Σ分户账、余额与发生额勾对  ← 不平即差错│
            │ ⑩ 余额快照  ⑪ 报送与数仓抽取  ⑫ 归档/分区  ⑬ 日期 +1    │
```

铁律：**上游不完成，下游不能跑；⑨ 不平，⑬ 不许执行**。调度、重跑与水位线的通用做法见 [14-数据工程与OLAP/05-批处理与调度编排](../14-数据工程与OLAP/05-批处理与调度编排.md)。

### 7.2 日切窗口对交易的影响

| 场景                                                | 风险                           | 设计要求                                                                                                           |
| --------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 交易跨窗口边界（23:59:58 受理、次日 00:00:05 记账） | 会计归属日不明，两边少记或多记 | 以**受理时前置取到的营业日期**为准写入流水并全链传递，禁止各环节自取本地时间                                       |
| 客户端超时重发                                      | 重复记账                       | 幂等键 = 全局流水号，重发不换号（见 [02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)） |
| 日切中查询余额                                      | 读到中间态                     | 用 `last_post_date` 与结转状态位判断，必要时返回"日终处理中"而非错值                                               |
| 跑批失败重跑                                        | 重复计提/重复结转              | 每个任务按（营业日期、批次、机构）幂等，支持断点续跑                                                               |

### 7.3 账账核对、差额诊断与"不平怎么办"

| 核对项     | 口径                                                               | 频率      |
| ---------- | ------------------------------------------------------------------ | --------- |
| 总分核对   | 末级科目 `gl_balance.close_bal` vs `Σ acct_info.balance`           | 每日日终  |
| 余额勾对   | 期末余额 = 期初余额 ± 本期发生额（按余额方向定正负）               | 每日日终  |
| 发生额平衡 | 全行当日 Σ借方发生额 = Σ贷方发生额；资产 = 负债 + 所有者权益自平衡 | 每日/每月 |
| 内外核对   | 与人行/银联/网联对账文件逐笔核对；客户对账单                       | 每日      |
| 表外核对   | 表外科目余额 vs 登记簿与凭证库存                                   | 每日      |

差额诊断速查（背下来能省几小时）：

| 现象                  | 大概率原因                     | 定位方法                                           |
| --------------------- | ------------------------------ | -------------------------------------------------- |
| 差额恰等于某笔金额    | 该笔漏记或多记                 | 拿差额当金额条件反查 `acct_txn` 与 `gl_entry_line` |
| 差额等于某笔的 2 倍   | 借贷方向记反                   | 查该笔 `dc_flag` 与科目 `balance_dir` 是否矛盾     |
| 差额能被 9 整除       | 数字移位（12→21）或错位        | 找金额中相邻两位互换的记录                         |
| 差额只有分位（≤0.05） | 舍入口径或 DECIMAL 标度不一致  | 查 ROUND 位置（逐笔舍入 vs 汇总舍入）              |
| Σ分户 > 总账          | 账户串科目、重复记账           | 按 `subject_code` 分组统计定位异常账户             |
| 差异大且分散          | 日切时点不一致，交易归到另一天 | 比对 `last_post_date` 与流水最大 `biz_date`        |

不平的处理原则（制度性强于技术性）：① **当日查找、当日报告**，影响客户资金的优先恢复业务；② **禁止手工 `UPDATE balance` 抹平**，任何调整必须以合规分录（红字冲销或蓝字补记）入账、注明原由、双人复核；③ 查明不了的挂"待处理款项/应收应付差异"类内部科目并登记差错，跟踪到销案；④ 现金差错（长款/短款）与账务差错分开处理，长款不得归己、短款不得挪用（以所在行出纳制度为准）；⑤ 登记、查找过程、调整分录、审批人、销案结论全程留痕——审计看的就是这条链。

## 八、热点账户：核心系统最难的问题之一

### 8.1 问题本质

热点账户（hot account，同名账户被大量并发交易同时更新）难，是因为**它不是算法问题，是数据库行锁的物理限制**：一个账户一行，同一行的 `UPDATE` 必须串行，所有并发请求排队等 X 锁。判断一个账户会不会热，看的是"**有多少笔不同交易要写同一行**"，不是"这个账户余额多大"。

```text
代发工资入账 / 商户待结算 / 归集下拨 / 限额累计 / 清算汇总账户 → 高并发写同一户
   │      │      │      │      └──┘ 全部收敛到 acct_info 的一行记录
   ▼
 单行 X 锁串行：并发上限 ≈ 1 / 单事务持锁时间
 后果链：行锁排队 → 事务等待 → 连接池耗尽 → 上游超时 → 冲正与重试 → 压力更大（雪崩）
```

### 8.2 行业解法与代价

| 方案                | 做法                                                              | 收益                           | 代价（不讲代价等于只答了一半）                                                                                                                                              |
| ------------------- | ----------------------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 串行排队            | 按账号哈希把请求路由到固定队列/线程，队列内顺序处理               | 无死锁、行为可预测、实现最简单 | 单账户吞吐被单线程锁死；积压须可观测可回放；跨账户交易须按固定顺序取锁避免死锁                                                                                              |
| 余额缓冲 / 汇总入账 | 流水实时登记，余额变动先写缓冲，定时把 N 笔合并成 1 次 UPDATE     | 行锁冲突降 N 倍，能扛峰值      | **账面余额短期不准**，查询要返回"已入账 + 未汇总"两个口径；透支校验弱化（需前置预占）；日终必须验证缓冲已全部汇总                                                           |
| 子账户拆分          | 拆成 N 个内部影子子账户，按哈希落子账户，母户余额 = Σ 子账户      | 并发度 ×N 且仍是实时强一致     | 所有读逻辑要 SUM；日终母子一致性核对；哈希不均残留热点；对外展示与积数归属要在子户层重定义                                                                                  |
| 异步记账 + 最终平账 | 先受理记流水（PENDING），发消息异步生成分录，靠重试与对账最终一致 | 主链路 RT 短、削峰明显         | 一致性窗口内余额不可信；必须有死信与人工差错闭环（见 [04-中间件/08-RocketMQ事务消息与死信队列](../04-中间件/08-RocketMQ事务消息与死信队列.md)）；"最终"到何时要能向监管解释 |
| 前置额度预占        | Redis 原子扣减做可动用校验，DB 只做最终落账                       | 把"读+判断"摘出行锁            | 双写不一致要回滚与超时释放；Redis 绝不能成为账务事实源；预占值本身要可对账                                                                                                  |

```java
// 串行排队最小实现：同一账户恒定落同一队列，队列内天然有序；跨账户交易按 acctNo 字典序取锁防死锁
int queueIdx = Math.abs(acctNo.hashCode()) % QUEUE_NUM;
producer.sendToQueue(queueIdx, new PostingMsg(txnSerialNo, acctNo, amt));
```

务实路径：**先量化再选型**。绝大多数账户一生都不会热，需要处理的是少数内部户。顺序是"监控识别（按账户写 QPS）→ 缓冲汇总（改造成本最低）→ 子账户拆分（成本最高，只给真热点上）"。本仓库有同构练习场：库存/额度的高并发扣减（对照 [02-Spring微服务/12-订单状态机治理](../02-Spring微服务/12-订单状态机治理.md)），迁移到银行的关键差异只有两条——**金额一笔不能丢，每一步要能核对**。

## 九、产品工厂与会计引擎：把分录变成配置

痛点很直白：每上一个新产品都要开发手写"这业务记哪些科目"，核心会变成规则泥潭。会计引擎（accounting engine，把业务事件按规则自动翻译成会计分录的组件）的思路是**把"业务事实"与"记账口径"解耦**。

```text
业务事件（事件码 + 金额/币种/机构/客户类型/费率）
  ▼ 规则匹配（事件码 + 币种 + 机构 + 会计日期 + 条件表达式 → 命中一组规则）
  ▼ 分录模板实例化（每条规则 = 方向 + 科目 + 金额来源 + 摘要码 + 行序）
  ▼ 借贷平衡校验 → 登记分户账 / 分录 / 总账
```

| 引擎要素       | 说明                                         | 举例                                 |
| -------------- | -------------------------------------------- | ------------------------------------ |
| 业务事件码     | 业务侧原子动作，稳定、不含科目信息           | `INTX-TRANSFER-OUT`                  |
| 金额来源       | 从事件上下文取哪个字段作记账金额，可带表达式 | `本金`、`利息`、`手续费净额`、`税额` |
| 方向 + 科目    | 借或贷 + 末级科目                            | 贷：手续费及佣金收入                 |
| 条件表达式     | 同一事件按客户类型/金额区间/渠道走不同科目   | 对公优惠客户不产生手续费收入         |
| 生效与失效日期 | 规则版本化，保证历史业务可按当时规则重算     | 税率调整日切换                       |
| 内部户配置     | 收入、税、过渡科目的记账账号按机构维度取     | 各分行手续费收入户                   |

```java
public List<EntryLine> build(BizEvent ev) {
    // 关键：按会计日期取规则版本，否则改税率后历史交易无法复算
    List<PostingRule> rules = ruleRepo.match(ev.getEventCode(), ev.getCurrency(), ev.getBranchNo(), ev.getBizDate());
    List<EntryLine> lines = new ArrayList<>();
    for (PostingRule r : rules) {
        BigDecimal amt = amountResolver.resolve(r.getAmtSource(), ev);
        if (amt.signum() != 0) { lines.add(EntryLine.of(r.getSubjectCode(), r.getDcFlag(), amt, r.getSeqNo())); }
    }
    BigDecimal d = sum(lines, EntryLine::getDebitAmt), c = sum(lines, EntryLine::getCreditAmt);
    if (d.compareTo(c) != 0) { throw new UnbalancedJournalException(ev.getTxnSerialNo(), d, c); } // 判等一律 compareTo：equals 比 scale，10.0 与 10.00 不等会造出"假不平"
    return lines;
}
```

## 十、初学者常见误区

| 误区                                   | 真相                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| "借 = 增加，贷 = 减少"                 | 借贷只是 T 型账的左右两边，增减含义取决于账户性质：资产借增贷减，负债借减贷增                          |
| "存款是银行的资产，因为银行拿钱去投资" | 对客户的存款账户而言它是银行的负债；银行放贷形成的"贷款"才是资产。同一笔钱在表上是一负债一资产         |
| "系统里有余额字段，所以余额一定可信"   | 余额是派生值，必须能用"期初 + 借方发生额 − 贷方发生额"复算；不能复算的余额就是不可信的                 |
| "借贷平衡了，账就一定对"               | 本息拆分错、科目串户、金额来源取错，都可能借贷仍平衡。必须补业务恒等式校验                             |
| "利息就是本金 × 利率 × 时间"           | 活期用积数法、日利率按 360 折算但天数按实际日历、算头不算尾、计提与结息分离，任何一处错就产生客户投诉  |
| "日切就是把日期字段 +1"                | 日切是一整套有依赖顺序、能重跑、必须核对平的批处理链，核对不平就不许推进日期                           |
| "并发问题加个分布式锁就行"             | 热点账户争用的是数据库行锁与事务持锁时间，应用层锁只是把等待换个地方；要靠汇总入账或拆子账户降低写放大 |
| "会计引擎就是把 if-else 放进数据库"    | 差别在版本化（按会计日期取规则）、可审计（规则到科目的映射有据）、可重算（历史业务能复现）             |

## 十一、面试高频问答

**Q1：客户来存 1 万块，会计上发生了什么？为什么是贷方？** A：借：库存现金 10,000，贷：吸收存款——活期存款 10,000。库存现金是资产、增加记借方；吸收存款是银行对客户的负债、增加记贷方。根因是"资产 = 负债 + 所有者权益"必须始终平衡。

**Q2：跨行转账的分录怎么写？中间那一步是干什么的？** A：付款行先"借：吸收存款——付款人户 / 贷：清算资金往来（待汇出）"，清算完成后"借：清算资金往来 / 贷：存放中央银行款项"。中间的共同类过渡科目承接"客户账已扣、资金未划走"的时间差，日终余额必须轧平；不平时就是挂账，是排查跨行差错的起点。

**Q3：积数计息和逐笔计息的区别？日利率怎么来？** A：积数法"每日余额累计成积数，利息 = 积数 × 日利率"，适合活期；逐笔法"本金 × 利率 × 期限"，适合定期与借据。日利率 = 年利率 ÷ 12 ÷ 30 = 年利率 ÷ 360（年 360 天、月 30 天的折算惯例），但计息天数按实际日历并遵循算头不算尾。

**Q4：总分核对不平你怎么查？查不出来怎么办？** A：先看差额形状——等于某笔金额是漏记或多记、2 倍是方向记反、能被 9 整除是数字移位、只剩分位是舍入口径、分散且金额大是日切时点问题；再用差额反查流水与分录行。查不出来不许手工抹平，挂待处理款项类科目、登记差错、当日报告，事后以红字冲销或蓝字补记的调整分录销案，全程双人复核留痕。

**Q5：热点账户为什么难？你会怎么设计？** A：难在它是行锁的物理限制——同一账户一行、UPDATE 串行，排队会耗尽连接池并把超时放大成重试风暴。解法各有代价：串行排队（吞吐锁死但可预测）、缓冲汇总入账（余额短期不准、要改查询口径与透支校验）、子账户拆分（并发度换 N 倍但要做母子一致）、异步记账最终平账（要死信与对账兜底）。顺序是先监控识别真热点，优先上缓冲汇总，只有量级最大的几个才做子账户拆分。

**Q6：一笔还款借贷是平的，但业务错了，怎么发现？** A：这是最危险的一类，它绕过了平衡校验。要补业务恒等式的每日监控：已还本金累计 = 借据已销本金、贷款余额 + 已还本金 = 放款本金、利息收入合计 = 计息引擎重算值、应收利息下降幅度与回款利息一致；手段是每日重算 + 差异登记 + 阈值告警，与对账体系同构（见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md)）。
