# 柜面系统与集中作业

> 本篇回答：JD 里第一个点名的"银行柜面系统"到底是什么——一笔柜台交易从柜员敲下交易码到核心记账、打印凭证、日终轧账的全过程，以及集中作业、授权复核、冲正撤销、单位开户这些岗位日常。
> 读完你要能在面试里说出一句有细节的话："柜面是交易发起与凭证受理层，账务事实源在核心，改柜面不等于不改核心，因为报文里多一个字段就要核心加一列。"
> 前置阅读：[01-银行IT体系与岗位全景](./01-银行IT体系与岗位全景.md)（柜面在系统版图里的位置）、[02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)（柜面发起的交易最终在核心变成什么）。
> 说明：本篇为**行业通用形态**描述，本仓库不是银行系统、没有柜面与集中作业模块，文中的交易码、表名、阈值均为示意。

## 一、柜面系统是什么：位置与边界

柜面系统（counter system，业内也叫"综合业务系统前端"、"营业系统"、"柜员工作台"）本质是一台**表单驱动的交易发起器 + 报文组装器 + 凭证打印机**。它自己不记账、不存余额，全行唯一的账务事实源在核心（core banking）。这个边界一旦记住，很多银行特有的工程现象就能解释：柜面字段为什么和数据库字段对不上、为什么改一个界面要发四个系统的版本、为什么柜面代码量看着不大但变更审批极慢。

```text
客户 ──> 柜员（人） ──> 柜面系统（交易码/表单/校验/授权/凭证）
                              │  报文（定长或 XML/JSON）
                              ▼
                     前置 / ESB / 业务中台（路由、转换、幂等、限流）
                              ▼
                     核心系统（记账、账户、利息） ──> 总账 ──> 报送
        旁路：影像平台、集中作业平台、凭证管理、统一身份、审计日志
```

| 系统         | 职责                                           | 数据归属         | 改它的实际影响面                             |
| ------------ | ---------------------------------------------- | ---------------- | -------------------------------------------- |
| 柜面系统     | 交易受理、输入校验、授权、打印与凭证、流水登记 | 自己的交易流水表 | 界面 + 报文 + 校验规则，通常要联调核心       |
| 前置 / ESB   | 报文转换、路由、渠道鉴权、流水号下发、幂等     | 通信与流水登记   | 新增字段常"看起来不用改"，但映射与白名单要改 |
| 核心系统     | 账户、余额、记账、计息、日终                   | 账务事实源       | 最慢最重：需求评审、会计口径确认、全链路测试 |
| 影像平台     | 凭证与资料的扫描、切片、留存调阅               | 影像件与元数据   | 存储与保留期限、隐私分级                     |
| 集中作业平台 | 后台审核、录入、差错退回                       | 任务与审核结论   | 与柜面解耦，改字段要同步切片模板             |
| 凭证管理系统 | 重要空白凭证的领用、调拨、销号                 | 凭证号段库存     | 号段与交易码强绑定，容易漏测                 |

一句话记法：**柜面决定"业务被怎样发起"，核心决定"账变成什么样"**。前者是操作与凭证，后者是会计事实，两者的负责人、审批链、投产窗口常常都不一样（流程见 [10-银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)）。

## 二、一笔柜面交易的完整调用链（必背）

以"客户到柜台存现 10,000.00 元"为例。面试时能把这条链讲下来、并说清每步归谁负责，就已经超过大多数零金融经验的候选人。

```text
柜员           柜面前端        交易框架/校验      授权服务      前置/ESB       核心          凭证/打印     流水登记
 │ 登录+签到       │                │              │            │             │              │            │
 ├──────────────►│ 输交易码 21001  │              │            │             │              │            │
 │               ├───────────────►│ 输入域校验    │            │             │              │            │
 │               │                ├─────────────►│ 是否需授权  │             │              │            │
 │  按提示刷柜员卡/按指纹 ─────────►│              │            │             │              │            │
 │◄─────授权通过（授权流水与被授权流水关联）────────┤             │             │              │            │
 │               │                ├─ 组装报文 ──►│─ 加流水号 ─►│ 记账+落账 ─►│              │            │
 │               │                │              │            │◄─ 返回码 ────┤              │            │
 │◄─ 结果翻译（返回码→人话）────────┤◄─────────────┤◄───────────┤  打印/电子签名 ────────────►│            │
 │               │                │              │            │             ├─ 回写状态 ──────────────►│
 │  收钱、点钞、验钞（实物动作）      │              │            │             │  钱箱 +10,000 │            │
 ▼               ▼                ▼              ▼            ▼             ▼              ▼            ▼
（实物增加与账面增加必须同时成立，否则轧账出长款/短款——见第四节）
```

| 步骤 | 动作                         | 谁负责                      | 失败会怎样（这是面试的区分点）                           |
| ---- | ---------------------------- | --------------------------- | -------------------------------------------------------- |
| ①    | 柜员登录、签到、领钱箱与凭证 | 柜面 + 统一身份             | 未签到不能受理任何交易；柜员号与机构号被写入所有后续流水 |
| ②    | 输入交易码调起交易画面       | 柜面（交易码配置）          | 交易码未开放给该机构/该柜员级别则直接拒绝                |
| ③    | 输入域校验                   | 柜面（字段规则 + 数据字典） | 本地拦下，不发报文；这是最省成本的一道关口               |
| ④    | 业务规则校验                 | 柜面 + 核心 + 风控          | 账户状态、冻结、限额、证件有效期、名单命中               |
| ⑤    | 授权判断                     | 授权服务                    | 金额/交易类型/客户类型触发；无授权则交易挂起不允许发送   |
| ⑥    | 报文组装                     | 交易框架                    | 字段映射错→核心返回"格式错"或更糟的"静默落错科目"        |
| ⑦    | 发送前置 / ESB               | 前置                        | 流水号在此下发并全局唯一，是后续一切核对的锚             |
| ⑧    | 核心记账并返回               | 核心                        | 明确失败可安全重发；**超时无应答最危险，禁止直接重发**   |
| ⑨    | 返回码翻译                   | 柜面                        | 核心码到客户可读语言的映射表，需与核心同步维护           |
| ⑩    | 凭证打印 / 电子签名          | 凭证 + 影像                 | 打印失败但已记账：必须能补打且不得重复记账               |
| ⑪    | 流水登记与状态终态化         | 柜面 + 核心                 | 双边流水都要能对上，日终勾对才成立                       |

**要点**：①～⑥ 属于"可以不花钱就挡住错误"的阶段，⑦ 之后每一层出问题都要靠冲正或对账兜底。所以柜面代码里真正的体量不在业务逻辑，而在**校验、字段映射、状态机、返回码表、授权与留痕**——这就是"低估制度性约束的代码量"这个误区的由来（第十一节）。

## 三、交易码体系：为什么需求文档按交易码写

交易码（transaction code，柜面为每个可发起交易分配的编号，如"21001 现金存入"）是柜面世界的最小完整单位：**一个交易码 = 一组输入字段 + 一套校验 + 一条报文 + 一个摘要码 + 一个授权级别 + 一份流水记录**。需求评审说"改 21001 的一个字段"，开发、测试、运营、审计听的是同一件事；说"改一下存款逻辑"则没有任何可执行含义。这就是银行需求文档按交易码组织的根本原因。

### 3.1 交易码的构成要素

| 要素             | 含义                                    | 工程落点                | 漏改的后果                     |
| ---------------- | --------------------------------------- | ----------------------- | ------------------------------ |
| 交易码 / 名称    | 唯一标识与人话名称                      | 交易定义表、画面注册    | 无法调起、培训口径混乱         |
| 输入域与数据字典 | 字段、类型、长度、必填、值域、默认值    | 画面定义 + 校验规则     | 前后端校验不一致，脏数据进核心 |
| 币种与金额       | 允许币种、金额上限、精度、单位（元/分） | 报文字段与 DECIMAL 标度 | 精度丢失或单位错 → 千倍差错    |
| 账户与科目映射   | 用什么账号结构、记哪个科目方向          | 报文 + 会计引擎规则     | 借贷方向或科目串户，账平但错   |
| 凭证类型         | 是否消耗重要空白凭证、打印几联          | 凭证管理与号段          | 凭证账实不符，检查必出问题     |
| 摘要码           | 存折/对账单上打印的一句话               | 摘要码表                | 客户对账单看不懂、投诉与调账   |
| 授权级别         | 本地授权 / 远程集中授权 / 免授权        | 授权服务参数表          | 越权交易、审计红线             |
| 开放渠道与机构   | 哪些渠道、哪些机构、哪些柜员级别可办    | 权限与渠道参数          | 权限扩张，等于隐性放权         |
| 手续费与费率码   | 是否收费、计费方式、收入科目            | 计费引擎 + 分录规则     | 少收或多收，涉及价税分离口径   |
| 冲正/撤销规则    | 是否允许冲正、允许时间窗                | 反向交易码配置          | 出现"改不了也退不了"的死账     |

### 3.2 改一个字段的完整影响评估（背下这张表）

```text
需求：现金存入 21001 增加"资金来源"必填下拉框
  ①  柜面画面定义 / 校验规则           → 新增字段与值域
  ②  报文字段（定长位置 or XML/JSON 节点） → 长度变了要重排；老报文兼容？
  ③  前置映射与白名单                  → 未登记字段会被丢弃（最坑）
  ④  核心接收字段与账户/流水表列         → 要落库就是 DDL 变更 + 历史数据默认值
  ⑤  反洗钱与报送                     → 该字段是否进入大额/可疑报送要素
  ⑥  凭证打印与摘要                    → 是否影响打印版式与联次
  ⑦  影像切片与集中作业审核项            → 后台要不要审这个字段
  ⑧  测试用例 + 授权参数 + 培训话术 + 投产说明
```

| 改动类型             | 影响面               | 判断方法                       |
| -------------------- | -------------------- | ------------------------------ |
| 界面提示文案         | 仅柜面               | 不动报文即可自测               |
| 字段由非必填改必填   | 校验 + 培训 + 投诉   | 看存量客户是否有值可填         |
| 新增字段但核心不落库 | 柜面 + 前置          | 确认前置是否透传还是丢弃       |
| 新增字段且核心落库   | 全链路 + DDL + 报送  | 需求阶段就要拉账务与合规评审   |
| 改金额单位或精度     | 账务正确性最高级     | 必须做全链路金额比对与对账验证 |
| 改摘要码或科目       | 账务 + 对账单 + 报表 | 会计口径变更，通常需总行批准   |

估时方法与本仓库通用做法一致，可对照 [17-研发效能与工程实践/05-需求拆解与估时](../17-研发效能与工程实践/05-需求拆解与估时.md)；差别在于银行的"影响面"里多了制度项，且每一项都对应一个必须签的评审节点。

### 3.3 输入域与数据字典：怎么读一份柜面需求

柜面需求的正文核心不是一段描述，而是一张**字段表**。看懂它比看懂背景重要。

| 列名（常见写法）    | 含义                                           | 开发要立刻反应出的事                               |
| ------------------- | ---------------------------------------------- | -------------------------------------------------- |
| 字段号 / 域代号     | 报文或画面中的字段标识，定长报文里还含起止位置 | 位置变了 = 报文版本变了，老渠道要兼容              |
| 中文名 / 英文名     | 业务口径与技术口径可能不一致                   | 沟通时报字段号，不要只报中文名                     |
| 类型与长度          | `PIC 9(8)V99`、`CHAR(60)`、DECIMAL 精度        | 按字节还是按字符？GBK 下 60 字节只放得下 30 个汉字 |
| 必填 / 条件必填     | `M` 必输、`C` 条件必输、`O` 选输               | 条件表达式写在哪儿、谁能改                         |
| 值域 / 数据字典引用 | 引用代码表（币种、证件类型、账户类别）         | 新增枚举值是否要发布代码表版本                     |
| 默认值与带出规则    | 由客户号、机构、产品参数带出                   | 带出来源系统是否可用，失败时是否允许手输           |
| 校验位置            | 前端拦、交易框架拦、核心拦                     | 只有核心拦的校验才防得住非柜面渠道                 |
| 打印与回显          | 是否上存折、是否进回单                         | 涉及客户可见口径，改动要合规确认                   |

读需求时最值钱的三个追问：**这个字段谁产生、谁消费、错了谁负责**。银行系统的多数返工都源于第一版没问这三句。

### 3.4 柜面常见需求类型速查

| 需求类型            | 典型改动                           | 主要坑                                             |
| ------------------- | ---------------------------------- | -------------------------------------------------- |
| 字段新增 / 必输化   | 画面 + 字典 + 报文 + 核心落库      | 前置映射丢弃未登记字段；存量数据无值               |
| 新增交易码          | 全流程配置，权限与授权要单独申请   | 只加了码没加渠道开放参数，测试通过生产不可用       |
| 报错文案优化        | 返回码翻译表                       | 翻译表与核心码不同步，改一处漏三处                 |
| 授权阈值调整        | 授权规则参数                       | 参数按机构/币种/客户类型分维度，只调总行维度不生效 |
| 凭证版式改版        | 打印模板、联次、摘要               | 补打与作废逻辑没同步，凭证号段错乱                 |
| 影像件增减          | 采集清单 + 作业切片模板 + 审核要素 | 作业标准与切片不一致导致批量退回                   |
| 费率 / 计息口径变化 | 计费引擎 + 会计引擎规则            | 未按会计日期版本化，历史交易无法复算               |
| 批量代收付          | 文件规范、明细状态、退盘           | 部分成功如何记账与通知，最容易设计漏               |
| 名单与风控接入      | 校验点前移、阻断口径               | 名单服务超时的放行/阻断策略未定义                  |
| 信创与编码迁移      | 数据库方言、GBK→UTF-8              | 按字节截断与排序规则差异，需双轨结果比对           |

## 四、柜员、机构、现金与凭证：柜台的四本账

| 概念               | 是什么                                                 | 为什么系统要有它                                 |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------ |
| 机构号             | 网点在行内树中的唯一编号，决定权限、科目归属、利润归属 | 所有账务都按机构维度汇总；分行与总账核对以它为轴 |
| 柜员号             | 具体操作人的工号，绑定级别、权限、指纹/柜员卡          | 审计要能回答"这笔是谁办的"，不可共用不可借用     |
| 级别与权限         | 综合柜员、主管授权、支行行长等；按交易码与金额授权     | 权限按岗位设计，不按人临时开恩                   |
| 钱箱 / 尾箱        | 柜员当日持有的现金箱，有起止金额                       | 现金实物与账面发生额的载体                       |
| 重要空白凭证       | 空白存单、存折、本票、汇票、卡等，有号段               | 它们代表未来可能兑付的权利，必须按"准现金"管     |
| 现金流水与凭证流水 | 每笔交易记录钱箱增减与凭证销号                         | 轧账时把"系统应有多少钱/多少张"算出来            |

**三个必考动作：**

- **轧账**：柜员日终把"系统应然"与"实物实然"对上——账面现金 = 期初 + 当日收入 − 当日支出，与实点现金比较。不平即**长款**（实物多）或**短款**（实物少）。
- **碰库**：实物清点核对，通常是每日营业终了双人清点并与账面对；**查库**则是主管或检查人员不定期抽查，重点看是否超限额、是否有白条抵库。
- **日终签退**：柜员完成流水勾对、凭证销号、现金缴库后才允许签退。签退后当日流水原则上不再变动——这是"营业日期"这个概念在柜台侧的落点（账务侧见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 第七节）。

| 差错表现            | 第一排查方向                       | 处理原则                                           |
| ------------------- | ---------------------------------- | -------------------------------------------------- |
| 长款（实物 > 账面） | 收款未记账、金额记少、凭证重复销号 | 不得归己，登记差错、当日报告、查明后以合规分录调整 |
| 短款（实物 < 账面） | 付出未记账、金额记多、误找零       | 不得挪用或垫付掩盖，按所在行出纳制度处理并留痕     |
| 现金平但流水不平    | 交易状态未终态化、冲正未关联原流水 | 查在途交易，日终必须终态化（见 §五与 §七）         |
| 凭证份数不符        | 打印失败重复出票、作废未登记       | 凭证作废必须剪角/盖作废章并登记号段                |

手工账与系统账并行的这几年，很多差错不是算法错，而是**"实物动作"与"账面动作"没有严格成对发生**。这也是银行对"界面点了但报文没发"这类中间态特别敏感的原因（同构问题见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md) 第五节）。

## 五、三份流水与勾对：柜面流水、核心账务流水、凭证与现金台账

同一笔柜台交易至少留下**三份互相独立的记录**。新手把它们当"一份数据"，是各种对不上账的起点。

| 记录           | 谁写            | 内容                                                          | 用来回答                         |
| -------------- | --------------- | ------------------------------------------------------------- | -------------------------------- |
| 柜面交易流水   | 柜面            | 交易码、柜员、机构、终端、时间、客户/账号、结果码、授权流水号 | "这笔是谁在哪个工位办的、成没成" |
| 核心账务流水   | 核心            | 全局流水号、账号、借贷方向、金额、记账后余额、会计日期        | "账有没有变、变成了多少"         |
| 凭证与现金台账 | 柜面 + 凭证系统 | 凭证号段销号、钱箱现金增减、打印联次                          | "实物少了什么、多的是什么"       |

```text
柜面流水  ──┐
            ├─ 按全局流水号 1:1 对齐（缺哪边就是单边账）
核心流水  ──┤
            └─ 按柜员+营业日期汇总金额，与凭证/现金台账轧账结果对齐
```

三方勾对是柜面日终与差错排查的主战场：柜面有、核心无 → 报文未达或核心拒绝但本地误记成功；核心有、柜面无 → 回包丢失，须补登状态；两边都有但金额或方向不符 → 报文映射错，属最高优先级事故。

```sql
-- 日终单边账排查（表名为示意，实际以行内命名为准）
SELECT c.txn_serial_no, c.teller_no, c.biz_date, c.txn_amt AS counter_amt, k.txn_amt AS core_amt
  FROM counter_txn c
  LEFT JOIN acct_txn k ON k.txn_serial_no = c.txn_serial_no AND k.biz_date = c.biz_date
 WHERE c.biz_date = #{bizDate}
   AND c.txn_status = 'S'          -- 柜面认为成功
   AND k.txn_serial_no IS NULL;    -- 核心无对应账务流水 → 必须逐笔核实并终态化
```

注意 `biz_date` 要参与关联：日切窗口内两侧记录的会计日期可能不同，只按流水号关联会把正常交易误判成单边账（营业日期机制见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 第七节）。

## 六、授权与复核：制度性约束，不是技术选型

| 维度     | 本地授权                         | 远程集中授权                               |
| -------- | -------------------------------- | ------------------------------------------ |
| 谁授权   | 同网点主管现场刷卡/输密码        | 后台授权中心审核员，跨机构                 |
| 触发场景 | 小额超级权限、密码重置、部分冲正 | 大额、挂失解挂、提前支取、开户关键要素     |
| 传输内容 | 授权流水号 + 柜员身份            | 影像 + 关键要素 + 话术录音（各行不同）     |
| 优点     | 快                               | 标准统一、人情人面分离、防止网点内部"通融" |
| 代价     | 主管权限集中、易被绕过           | 需要排队，影响客户体验；网络与影像依赖     |

银行坚持**经办—复核—授权三分离**（同一个人不能同时完成受理、复核与授权），不是因为它好实现，而是因为它是内控制度要求：任何单人可完成的资金操作都被视为缺陷。落到设计上有四条硬约束。

| 设计要求         | 具体做法                                         | 别踩的坑                             |
| ---------------- | ------------------------------------------------ | ------------------------------------ |
| 双人不可合并     | 经办柜员号与授权柜员号两列分开存，同人不允许     | 用"管理员角色"绕过，审计直接判不合规 |
| 授权与被授权关联 | 授权流水通过 `orig_txn_no` 指回被授权交易        | 只记"已授权"标志，事后无法回答谁授的 |
| 触发点不可下移   | 金额阈值、风险规则在服务端判定，不信任前端       | 前端隐藏按钮 = 无授权                |
| 留痕完整         | 时间、机构、柜员、终端 IP/工位、指纹或柜员卡介质 | 日志缺介质类型，无法证明"本人操作"   |

金额阈值属于行内参数（不同行、不同时期口径不同），描述时统一写"通常为……量级，以本行现行参数与制度为准"，面试里不要报死数字。授权与权限模型的通用实现可对照 [09-安全与设计模式/03-SpringSecurity微服务两层安全模型](../09-安全与设计模式/03-SpringSecurity微服务两层安全模型.md)，但银行的岗位分离要求比 RBAC 默认语义更严。

## 七、冲正、反交易、撤销：三个词三种实现

| 术语                        | 语义                                             | 账务效果                                   | 常见约束                                             |
| --------------------------- | ------------------------------------------------ | ------------------------------------------ | ---------------------------------------------------- |
| 冲正                        | 系统或柜员对**已记账但需作废**的交易做反向处理   | 生成一笔方向相反的分录，原流水标记为已冲正 | 通常限当日、原金额全额、必须关联原流水号；跨日走调整 |
| 反交易                      | 柜面提供的与原交易业务含义相反的**另一个交易码** | 独立业务的正常记账（如退货、支取补存）     | 有自己的输入域与授权级别，不是简单取负               |
| 撤销                        | 记账前或清算前取消，客户或柜员主动放弃           | 未记账则只回滚状态；已记账等同冲正         | 一旦资金已清算，不能撤销，只能退款或再走一笔         |
| 调整（红字冲销 / 蓝字补记） | 事后纠错的合规分录手段                           | 以新的合规分录修正，绝不改历史             | 必须双人复核、注明原由、留痕到销案                   |

核心区别在**"有没有发生过账务事实"**：撤销针对"还没成立的业务"，冲正针对"已成立但要作废的账务"，反交易是"又发生了一笔新业务"。把三者混成一个"cancel"接口，是外部开发者进银行最容易犯的设计错误。

```text
超时 / 无应答处理（柜面侧铁律）
  发报文 ─┬─ 明确失败码  → 可安全重发（不换流水号）或让柜员改要素重做
          ├─ 明确成功码  → 正常走完打印与登记
          └─ 超时/无应答 → ① 禁止直接重发  ② 先查业务状态（按全局流水号）
                          ③ 查明成功：补登本地状态与凭证，不得重复记账
                          ④ 查明失败：允许重做或登记冲正
                          ⑤ 查不明：保持"未知"态，进日终在途清单，由对账/清算结果终态化
```

为什么"未知态"必须存在：柜面与核心之间是网络上的两次单向不确定（请求可能已到、应答可能丢），任何"看起来简单"的自动重试都可能造成重复记账。状态机设计、幂等键选择与对账兜底的完整做法见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md) 第三、五节；报文与清算侧的对应机制见 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

## 八、集中作业平台：把"审核"从柜台搬走

集中作业（centralized operation，把原本分散在各网点后台的审核、录入、复核类工作集中到区域作业中心处理的生产模式）与柜面解耦的四个原因：**人员专业化**（一个业务只需一批熟手）、**标准统一**（同一规则全行一致执行）、**风险隔离**（受理与审核不同人、不同机构、甚至不同城市）、**柜面专注**（柜台只做受理与影像采集，缩短客户等候）。

```text
柜面受理 → 影像采集（身份证/凭证/单据扫描）→ 影像切片（按审核要素拆成小图）
     │                                                      │
     │                                            任务池（按技能/负载分派）
     │                                                      ├─ 抢单/派单
     ▼                                                      ▼
 交易挂起，等待作业结论  <──  结论回写  <──  审核员逐片录入与判断 → 通过 / 差错退回
     │                                                      └─ 退回带原因码，柜面补扫或补录
     ▼
 放行后续账务（部分作业前置、部分后置，按交易码配置）
```

| 环节     | 关键设计                         | 容易忽略的工程点                                   |
| -------- | -------------------------------- | -------------------------------------------------- |
| 影像采集 | 一次业务多张件，按件类型分类     | 与交易流水的关联键必须唯一且可回溯；重复上传要去重 |
| 切片     | 把整页凭证切成审核员需要看的区域 | 切片模板变更要与作业标准同步，否则审核要素缺失     |
| 任务池   | 按技能组、机构、负载分派         | 抢单要用可超时的占锁，超时自动释放回池             |
| 审核录入 | 要素比对（影像 vs 报文）         | 关键字段不一致必须退回，不允许"看着像就过"         |
| 差错退回 | 原因码化、可统计、可考核         | 退回次数与整改要形成报表，是作业质量指标的来源     |
| 结论回写 | 通知柜面放行或终止               | 回写丢失要有主动查询与对账，不能只靠消息推送       |
| 时限管理 | 每类作业有时效要求               | 时效与工作量统计驱动排班，直接影响网点等候时长     |

对新人最实用的一条：**集中作业是"异步 + 人在环"的流程系统**，它的失败模式不是崩溃而是卡单。所以设计上要有超时、重派、人工干预入口和全链路可观测。这与消息驱动编排的思路一致，可对照 [04-中间件/08-RocketMQ事务消息与死信队列](../04-中间件/08-RocketMQ事务消息与死信队列.md) 与 [02-Spring微服务/12-订单状态机治理](../02-Spring微服务/12-订单状态机治理.md)。

## 九、单位银行结算账户开户：一个走完全部约束的例子

对公开户是柜面最容易做错、系统链路最长的交易，因为它一次动作要落到五六个地方：核心客户与账户、账户管理系统报备、反洗钱身份识别与名单筛查、影像与集中作业、印章与支付密码、后续非柜面渠道签约。

| 环节           | 内容                                                                                           | 制度要点（以现行有效版本为准）                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 资料受理       | 营业执照等主体资格证明、法定代表人/负责人身份证件、经办人授权书、印鉴、受益所有人信息          | "了解你的客户"要求原件与复印件留存，印鉴按规范预留                                               |
| 尽职调查       | 核实开户真实意愿、经营与办公场所、经营范围与开户理由合理性                                     | 许多机构要求双人上门核实或远程核实留痕，防止账户被用于电诈与洗钱                                 |
| 唯一性校验     | **一个企业只能开立一个基本存款账户**                                                           | 系统必须向账户管理系统查询已有基本户信息后才能确认开立                                           |
| 核准 vs 备案   | 人民银行已取消企业银行账户许可：企业银行结算账户开立由**核准制改为备案制**，不再核发开户许可证 | 部分主体（机关、事业单位等）仍属核准范围；具体适用主体以现行制度为准                             |
| 报备与账号管理 | 通过账户管理系统完成备案/核准，账号与备案信息一致                                              | 变更与撤销同样要报备；存量账户需按监管要求清理与复核                                             |
| 生效时点       | 旧规则为"正式开立之日起 3 个工作日后方可付款"；取消许可后企业账户自开立之日即可收付            | 为账户风险管理与反电诈需要，多数机构对新开单位账户的非柜面出金设审慎期与限额，以本行现行制度为准 |
| 后续动作       | 支付密码/网银/回单柜/代发协议、账户分类与限额、对账关系                                        | 与 [08-反洗钱账户管理与监管合规](./08-反洗钱账户管理与监管合规.md) 的账户管理章节对照阅读        |

柜面系统在这笔交易里做什么：把上述全部约束落成**字段、必校验、影像件清单、作业任务、授权级别和报备报文**。所以"开户交易改一个字段"经常牵动合规口径，这类需求的评审链最长，也最能体现银行研发与互联网研发的差别。

## 十、柜面技术形态与演进

| 阶段 / 形态               | 技术特征                                       | 现状与坑                                                                                                          |
| ------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 字符界面（绿屏）          | 主机终端仿真、字段位置式输入、快捷键流程       | 仍在部分行使用；业务规则"藏在屏幕第 7 屏第 3 字段"，文档缺失                                                      |
| C/S 胖客户端              | Windows 客户端、本地控件、直连前置             | 升级困难、终端管控重；打印控件与外设驱动是长期维护点                                                              |
| B/S + 自研交易框架        | 画面/字段/校验由配置元数据驱动，交易码统一入口 | 元数据结构晦涩；框架强绑定行内规范，外部经验不能直接搬                                                            |
| 大量存储过程              | 业务规则写在 DB 过程里，应用层只做转发         | 版本管理、可测试性、信创替换时的方言兼容都难（见 [01-银行IT体系与岗位全景](./01-银行IT体系与岗位全景.md) 第四节） |
| GBK / 定长报文            | 老系统按字节编码，定长字段按位置截取           | 汉字按字节截断成半个；姓名长度、备注超长、emoji 与全角都会炸                                                      |
| 统一平台 / 微服务化       | 服务拆分、统一身份、参数中心、编排层           | 拆分的价值在"复用与灰度"，代价是链路可观测与一致性要求提高                                                        |
| 无纸化与电子签名          | 取消纸质凭证，改用电子签名与电子凭证影像       | 签名存证、防篡改、与凭证效力相关的合规要求必须满足                                                                |
| 智能柜台（STM）/ 大堂分流 | 客户自助办理开卡、挂失、密码重置，远程坐席审核 | 本质是"另一类柜面"：同样交易码、同样授权、同样流水                                                                |
| 生物识别                  | 指纹、人脸用于身份确认与授权                   | 涉及个人金融信息分级保护（见 [07-银行业信息安全管理规范](./07-银行业信息安全管理规范.md)）                        |

编码这一项值得单独提醒：老柜面与主机侧普遍是 GBK 定长，新渠道是 UTF-8。链路里任何一次按字节截取、按字符算长度、把中文当 ASCII 校验的写法都会在跨层时出问题，机制对照 [15-计算机基础/07-字符编码与时区](../15-计算机基础/07-字符编码与时区.md)；日终与"营业时间边界"的日期处理陷阱见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 第七节。

**为什么柜面现代化改造大多落在"中间层"**：核心的记账与账务模型改动风险极高、周期极长，而客户体验、渠道整合、影像化、授权集中、流程编排都在中间层完成。于是行内出现大量"不动核心、只改前置与中台"的项目——这类项目正好需要既懂 Spring 技术栈、又能读懂柜面报文和交易码配置的人，是零金融经验 Java 开发最容易切入的位置。

## 十一、初学者常见误区

| 误区                                           | 真相                                                                                     |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| "柜面系统就是核心系统的前端页面，改了不影响账" | 柜面决定报文要素与业务事实；多一个字段可能就要核心加列、会计引擎加规则、报送加要素       |
| "界面字段 = 数据库字段"                        | 中间隔着交易框架元数据、报文映射、前置转换、核心内部账户结构，四层字段名和类型都可能不同 |
| "交易码就是一个编号"                           | 一个交易码承载权限、校验、报文、摘要、凭证、授权、冲正规则，是需求与投产的最小单位       |
| "冲正 = 撤销 = 删除记录，DELETE 掉就行"        | 三者语义不同且都必须以新流水留痕；账务事实永远不删（见第七节）                           |
| "授权就是管理员权限，用 RBAC 就够了"           | 银行是岗位三分离 + 金额阈值 + 介质留痕，同一个人既经办又授权属于制度缺陷                 |
| "集中作业 = 找人帮忙录单"                      | 它是异步人在环流程系统，卡单、退回、时效、切片一致性都要设计                             |
| "影像就是给交易加个附件上传"                   | 影像与流水的关联键、保留期限、隐私分级、切片模板都是制度要求，还要能调阅复现             |
| "智能柜台上线后柜面就没多少开发了"             | STM 复用同一套交易码、授权与流水体系，只是换了受理终端与分流策略                         |
| "老柜面技术旧，不值得做"                       | 它是全行业务入口与风险第一道闸，改造需求长期存在，也是新人最容易建立业务全局观的位置     |
| "柜面代码简单，主要是 CRUD"                    | 复杂在校验矩阵、状态机、字段映射、授权参数和跨系统一致性，纯增删改反而最少               |

## 十二、面试高频问答

**Q1：柜面系统和核心系统的边界在哪？** A：柜面是交易发起与凭证受理层——输入校验、授权、报文组装、凭证打印、流水登记；核心是账务事实源——账户、余额、记账、计息、日终。柜面不存余额，最多存展示用的返回结果。判断改动影响时问自己一句：这个字段会不会进入核心报文？会不会改变记账科目或摘要？会不会成为报送要素？只要有一个"是"，就不是柜面单方面的改动。

**Q2：一笔柜面交易从点击到完成，中间可能出哪些事？** A：按链路分层看——校验阶段被本地或核心业务规则拒绝；授权阶段挂起等待；报文阶段格式或映射错；发送后最危险的是超时无应答，禁止直接重发，要先按全局流水号查业务状态，查明成功就补登状态、查明失败才允许重做、查不明就保持在途态由日终对账终态化；记账成功后还可能打印失败，需要补打且不能重复记账。

**Q3：什么是交易码？为什么银行需求按交易码写？** A：交易码是柜面可发起交易的最小单位，一个交易码对应一组输入域、一套校验、一条报文、一个摘要码、一个授权级别和一份流水。需求按交易码写，是因为它天然定义了影响面和验收边界：开发看报文、测试看用例、运营看权限、审计看流水，四方读的是同一个标识。

**Q4：柜员日终为什么要轧账？长款短款怎么处理？** A：因为柜台同时存在账面与实物两套事实，必须每天核对——账面现金 = 期初 + 当日收入 − 当日支出，与实点现金比较。不平即长款或短款，原则是当日查找、当日报告，长款不得归己、短款不得挪用或垫付掩盖，查明后以合规分录调整，双人复核并留痕到销账，绝不允许手工改余额抹平。

**Q5：本地授权和远程集中授权怎么选？** A：按风险等级和标准化需求划分。现场小额、需要即时反馈的走本地主管授权；大额、挂失解挂、密码重置、开户关键要素这类高道德风险操作走远程集中授权，好处是受理与审核人、机构分离，标准全行统一，代价是要处理排队时长与影像依赖。技术上统一做成可配置的授权规则：输入是交易码、金额、客户类型、账户状态，输出是授权方式与级别，且触发判定必须在服务端。

**Q6：集中作业平台挂了会怎样？你怎么设计这个环节？** A：交易会被挂起在"待作业"状态，不会丢账但会卡单，所以要做四件事：任务抢占用可超时的锁并在超时后自动回池；结论回写走"消息通知 + 主动查询 + 日终对账"三重保障；退回必须原因码化以便统计与考核；柜面侧要能看到卡在哪个环节、谁在做、预计多久。它本质是异步人在环流程，可观测与可干预优先于吞吐。

## 十三、动手练习

1. **写一份"交易码变更说明书"**：为 §3.2 的"现金存入增加资金来源必填字段"补齐八个环节的受影响系统、负责人角色、验证方法（每条一句话），并给出你会设计的最小回退方案。对照 [17-研发效能与工程实践/06-技术文档写作](../17-研发效能与工程实践/06-技术文档写作.md) 检查是否可执行。
2. **画一遍调用链**：不看本文，凭记忆画出"跨行汇款 50,000.00 元"在柜面侧的时序（含授权触发点、流水号下发点、报文出口、未知态分支），再与 [04-支付清算体系与报文](./04-支付清算体系与报文.md) 的清算侧链路与 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) §4.2 的分录对齐，确认你能说出"哪一步之后不能再撤销、只能冲正或退款"。
3. **设计在途状态机**：用 Java 写出柜面交易的五态（INIT / SENT / UNKNOWN / SUCCESS / REVERSED）与允许的迁移，明确每个状态的超时处理动作；再用 SQL 写一条日终检查："当日营业日期下状态为 UNKNOWN 且无对应核心记账流水"的清单。幂等与状态机写法对照 [02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)。
4. **权限矩阵题**：给定 10 个交易码、3 个柜员级别、2 个金额阈值，画出"谁可经办 / 谁可本地授权 / 谁必须远程授权"的矩阵，并用一条 SQL 建出对应的授权参数表与判定查询。回答：为什么不能把远程授权实现成"主管在同一个页面点一下确认"？
5. **编码与字段长度排查**：构造一个 20 个汉字的户名 + 全角括号 + emoji 的备注，说明它在 GBK 定长字段、按字符算长度的校验、UTF-8 报文三层里分别会在哪一处出错，怎么用最少的日志复现它。
6. **开户链路自查**：列出对公开户在你的方案里要写到的所有系统与表（核心客户/账户、账户管理系统报备、反洗钱筛查、影像与作业、凭证与印章、非柜面签约），指出哪一步失败必须能整体回退，哪一步失败只能人工补录，并说明你据此设计了哪些补偿入口。
