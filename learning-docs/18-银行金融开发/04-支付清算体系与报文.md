## 一、先彻底分清三个词：支付 / 清算 / 结算

初学者最大的坑是把这三个词当成同一件事的三种说法。它们是**一条链上的三个不同阶段**，责任方不同、时点不同、出错的处理方式也完全不同。

| 环节 | 英文 | 谁在做 | 做什么 | 钱动了吗 |
|---|---|---|---|---|
| **支付** | payment | 客户 + 付款行 | 发出"请把这笔钱转给别人"的指令，付款行先从客户账上把钱扣走 | 客户账动了，银行间没动 |
| **清算** | clearing | 清算机构（央行系统/银联/网联） | 收集、分类、传递支付指令，算出"哪家银行该付哪家银行多少钱"（轧差） | **没动**，只是算账 |
| **结算** | settlement | 央行（最终结算方） | 按清算结果变更各家银行开在央行的账户余额，完成最终性 | **真动了** |

**轧差（netting，把多方应收应付互相抵扣后只结算差额）**：工行当天应付建行 100 亿、建行应付工行 80 亿，轧差后只需要实际转移 20 亿。轧差省的是流动性，代价是要等到轧差时点才能结，且承担"等待期内对手方违约"的风险。

**最终性（settlement finality，结算结果不可撤销、不可被追索）**：银行间业务只认央行结算的最终性。这是"清算完成 ≠ 客户到账"这个误区的根因（见 §8）。

### 1.1 一笔跨行转账的完整时间线

场景：客户 A（工行卡）向客户 B（建行卡）转 1000 元，走人民银行大额实时支付系统。

```
T0 10:00:00.000  A 在手机银行点"确认转账"，输密码/验指纹
                 └─ 工行渠道系统 → 工行核心系统
T0 10:00:00.400  【支付】工行核心扣 A 的存款 1000 元
                 分录：借 A 的活期存款 1000 ／ 贷 工行"汇入汇款-待转"内部户 1000
                 A 的 App 显示"转账处理中"——此时钱已在工行账上消失，但建行毫不知情
T0 10:00:00.900  工行支付前置系统组支付指令报文 → 发往人行大额系统
T0 10:00:01.500  【清算】大额系统收到指令：逐笔、全额（不轧差），先做合规与格式校验
T0 10:00:01.600  大额系统检查工行在央行的清算账户余额是否 ≥ 1000
                 ├─ 够  → 继续
                 └─ 不够 → 指令进排队队列（见 §3），等头寸或等排队释放
T0 10:00:02.000  【结算】央行借记工行清算账户 1000、贷记建行清算账户 1000
                 ★ 这一刻才是"钱真的在两行之间动了"，且不可撤销（最终性）
T0 10:00:02.100  大额系统把贷记通知发给建行
T0 10:00:03.000  建行收到通知 → 建行核心贷记 B 的存款 1000
                 分录：借 建行"汇入汇款"内部户 ／ 贷 B 的活期存款 1000
T0 10:00:04.000  B 收到到账短信。A 的 App 变"转账成功"
```

三个关键观察：

1. **"扣款"和"到账"之间必然有间隔**，这个间隔就是在等清算与结算。快的时候几秒（大额/网银互联），慢的时候几小时甚至次日（小额批量按场次、节假日非运行窗口）。
2. **中间任何一步失败，回滚方式完全不同**：扣款前失败只是交易未成立；扣款后、结算前失败必须走"冲正/退汇"；结算后失败只能靠"反向汇款"，央行结算本身不会被撤回。
3. **客户看到的"到账"是收款行自己的记账行为**，不是央行结算的时点。有些银行"先入账后冲正"，有些"先核对后入账"，所以会有"显示到账了又掉了"的客诉。

## 二、中国支付清算体系版图

**CNAPS（China National Advanced Payment System，中国现代化支付系统）** 是人民银行建设运行的支付清算系统总称，境内银行间资金转移的最终通道几乎都在它和它的兄弟系统里。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ 客户与渠道层   手机银行 │ 个人网银 │ 企业网银/银企直联 │ 柜面 │ ATM │ 支付机构 App │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │  行内交易/记账（渠道 → 核心）
┌───────────────────────────────▼──────────────────────────────────────────────┐
│ 银行内部        支付前置系统（组包/验签/流水登记/排队管理） + 核心账务系统      │
│                 直接参与者 = 法人银行自己在央行有清算账户                      │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │  人行支付系统报文
┌───────────────────────────────▼──────────────────────────────────────────────┐
│  人民银行运营（最终结算层）                                                    │
│  ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │
│  │ HVPS 大额实时   │ │ BEPS 小额批量   │ │ IBPS 网银互联   │ │ 境内外币支付系统│ │
│  │ 逐笔全额 实时   │ │ 批量 定时轧差   │ │ 7×24 逐笔实时   │ │ 外币 代理行模式 │ │
│  └────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘ │
│            结算发生在：各参与者开在人民银行的「清算账户」余额变更               │
└───────────────┬───────────────────────────────┬──────────────────────────────┘
                │ 银行卡跨行                      │ 支付机构 ↔ 银行
┌───────────────▼──────────────┐ ┌───────────────▼──────────────┐ ┌────────────┐
│ 中国银联（银行卡转接清算）     │ │ 网联清算（第三方支付收单直连） │ │ 城银清算   │
│ + 特许清算组织，算净额→发起结算│ │ "断直连"后的统一转接入口      │ │ 中小银行   │
└──────────────────────────────┘ └──────────────────────────────┘ └────────────┘

跨境：CIPS 人民币跨境支付系统（报文 + 人民币清算，与境内央行支付系统相连）
信息：SWIFT 报文网络（只传指令与对账信息，不搬运资金）  ←→  与 CIPS 互通
```

### 2.1 央行系五大系统速查表

| 系统 | 定位 | 清结算方式 | 时序特征 | 典型业务 | 可用性窗口 |
|---|---|---|---|---|---|
| **HVPS** 大额实时支付系统 | 银行间大额资金的高速路 | 逐笔、**全额**、实时（RTGS） | 秒级到达，无排队则即时结算 | 同业往来、大额企业汇款、金融市场交割 | 以工作日日间为主，设有日切与排队/清算窗口安排；节假日运行时段以人民银行最新业务通知为准 |
| **BEPS** 小额批量支付系统 | 小额、大批量的"绿皮车" | **批量打包、定时轧差净额** | 按场次（批次）跑，小时/天级 | 代发工资、水电煤、保险理赔批量入账 | 受理与清算场次分离，非实时到账 |
| **IBPS** 网上支付跨行清算系统（网银互联） | 网上支付小额跨行专用 | 逐笔实时，最终按净额与央行结算 | 面向互联网体验，快 | 网银/手机银行跨行小额、支付机构快捷支付的银行侧 | 7×24 连续运行，单笔金额设有上限（以现行制度为准） |
| **境内外币支付系统** | 境内美元/港币等外币清算 | 逐笔 + 代理行（结算银行）模式 | 分币种窗口 | 境内外币企业汇款 | 各币种窗口不同，受境外清算系统时区影响 |
| **CIPS** 人民币跨境支付系统 | 人民币跨境清算的主渠道 | 报文 + 结算一体，支持逐笔与批量混合 | 覆盖全球时区 | 跨境贸易结算、离岸人民币 | 多时区连续运行；直参在 CIPS 开结算账户，可与境内央行系统调拨流动性 |

**记忆抓手**：金额大又急 → HVPS；量小又批量 → BEPS；网上支付体验 → IBPS；跨境人民币 → CIPS。

### 2.2 SWIFT 到底是什么角色

SWIFT（Society for Worldwide Interbank Financial Telecommunication，环球银行金融电信协会）**是一个报文电传网络，不是清算通道**。它做的是"把你的付款指令安全、标准化地送到对方银行"，钱仍然要在两家银行各自的账户关系、代理行账户（nostro/vostro，我方在对方开的账户/对方在我方开的账户）或央行账户里变动。

| 误解 | 实际 |
|---|---|
| "通过 SWIFT 把钱汇出去" | SWIFT 只发报文；资金移动靠代理行账户余额调整或央行结算 |
| "CIPS 是用来替代 SWIFT 的" | CIPS 自带报文能力，也提供清算结算，与 SWIFT 是报文层/清算层不同定位，实践中并存并互通 |
| "SWIFT 挂了钱就丢了" | SWIFT 挂的是"寄信通道"，未送达的指令可重发或改电传；已结算的不动 |

跨境汇款"到账慢"的真实原因通常是：中间行多、需要反洗钱人工审核、时区错开、外汇报价与账号信息有误，而不是"SWIFT 传输慢"。

### 2.3 参与者与账户体系

| 概念 | 人话解释 | 开发为什么要关心 |
|---|---|---|
| **直接参与者** | 法人机构自己接入支付系统、自己在央行有清算账户 | 报文里的参与者代码（行号/机构代码）是路由键，唯一且不能改 |
| **间接参与者** | 没有央行清算账户，通过直接参与者代理接入（常见于小银行、村镇银行） | 一笔业务的"发起机构"和"资金实际结算机构"可能不是同一家，对账要区分两层 |
| **清算账户** | 银行开在人民银行、专门用于支付清算资金结算的账户 | 余额 = 可动用头寸，余额不足直接导致排队/失败（见 §3） |
| **备付金**（银行语境） | 商业银行为保证支付清算而存放在央行的钱（法定 + 超额存款准备金中的可动用部分） | 与"支付机构客户备付金"是**两个不同概念**，见 §4.2 |
| **头寸** | 某个时点某账户上可立即动用的钱 | "头寸不足"是支付失败的高频原因，不是程序 bug |
| **日间透支** | 央行允许参与者在日间临时透支清算账户以维持支付流转（有条件、有成本） | 透支额度会决定你的重试策略是否合理 |

## 三、净额 vs 全额：RTGS 与 DNS 的取舍

| 维度 | RTGS（Real-Time Gross Settlement，实时全额） | DNS（Deferred Net Settlement，延时净额） |
|---|---|---|
| 结算颗粒 | 每笔单独结算，不抵扣 | 攒一段时间，轧差后只结差额 |
| 流动性需求 | **高**：每笔都要有全额资金 | **低**：只需差额（常降到全额的百分之几） |
| 信用/对手风险 | 极低：结完就最终了 | 有：等待期内若某参与者违约，整个净额结果要重算 |
| 时延 | 秒级 | 场次/日终 |
| 适合 | 大额、紧急、金融交割 | 小额、海量、时间不敏感 |

**为什么大额走全额、小额走批量**：这是同一笔取舍的两端。让 1000 元的水电费逐笔全额结算，全国银行要准备的流动性会大到无法承受；让 50 亿元的同业划款等轧差场次，一家银行违约会把当天所有对手方拖进风险敞口。所以体系设计成"贵而快的通道走大钱，便宜而慢的通道走小钱"。

DNS 的信用风险靠三件套压住：**结算保证金/违约基金**（参与者共同出资兜底第一家违约者）、**净额上限**（限制单家最大应付净额）、**违约处理规则**（把违约者的交易从净额里剔除重算）。

**RTGS 也想要省流动性**，于是有排队与撮合机制：

- **排队（queueing）**：头寸不够时指令不失败，而是进队列等待。
- **优先级/紧急通道**：可标记个别支付优先释放（如央行公开市场操作、到期兑付）。
- **定时撮合释放（liquidity saving，算法化地在队头做小额互相抵扣）**：在不破坏逐笔最终性的前提下减少无效等待。
- **排队超时**：超过窗口仍未清算的指令会被退回（nack）发起行，由发起行决定次日重发或撤销。

对开发的直接含义：**排队不是失败，返回码不是错误码**。把"已排队"当成失败并自动重发，会造成重复汇款。

## 四、第三方支付链路

### 4.1 断直连前后

"直连"指第三方支付机构绕过清算组织，直接与各家银行一对一签订协议、拉专线对接接口。问题是：清算组织看不见这笔资金流，央行无法穿透统计与监管，支付机构在两家银行之间扮演了"影子清算行"。

```
断直连前（支付机构自己做转接清算）：
   用户 ── 支付机构 App ──┬── 专线 ──> 工行
                          ├── 专线 ──> 建行        支付机构 = N 家银行的"隐秘清算中枢"
                          └── 专线 ──> 招行        监管看不见全量资金流

断直连后（统一走特许清算组织）：
   用户 ── 支付机构 App ──> 网联 / 银联 ──> 各银行
                            │
                     转接 + 清算 + 可监管数据留痕
```

现在持牌支付机构与银行之间的网络支付业务必须通过**网联清算**或**中国银联**转接清算。

### 4.2 角色与备付金

| 角色 | 干什么 | 边界 |
|---|---|---|
| **收单机构** | 为商户受理支付：签约、布码/布 POS、清分打款 | 银行和持牌支付机构都能做收单 |
| **支付机构** | 拥有用户账户与支付业务许可证，代用户发起支付 | 不得无证从事支付清算业务 |
| **清算组织** | 网联/银联：转接、清算、规则 | 不直接面对终端用户 |
| **商户** | 收款方 | 拿到的钱来自收单机构结算 |

**客户备付金（支付机构语境）**：用户放在支付账户里、以及交易中代收但尚未结算给商户的钱，**所有权属于客户，不是支付机构的收入**。早期支付机构靠巨额沉淀资金吃利息、甚至挪用，监管的处置是：**客户备付金集中交存人民银行管理（现行已实现 100% 集中交存，支付机构不得挪用、不得计付利息，以现行有效规定为准）**。

### 4.3 "二清"为什么违规

"二清"（二次清算）指**没有支付业务许可证的主体**，先以自己名义（或作为其他机构的"商户"）统一收妥资金，再由自己向下游真实商户分账结算。

```
合规：  消费者 → 持牌支付机构/银行 → 清算组织 → 真实商户收款账户
二清：  消费者 → 【无牌平台自己的账户】→ 平台再自行"结算"给入驻商户
                     ↑ 资金在这里形成平台控制的沉淀池
```

违规原因不是"多了一道手续"，而是三个实质问题：

1. **无牌经营支付业务**：分账就是清算，清算需要牌照。
2. **沉淀资金挪用与跑路风险**：钱在平台账户里，平台卷款即发生系统性风险。
3. **监管穿透断裂**：反洗钱、消费者资金保障、备付金存管全部失效。

所以"聚合支付服务商"（第四方，只做受理入口与技术服务）的红线是**不碰资金**——只传交易信息，资金由持牌方直接结算给商户。一旦聚合服务商"统一收款再分账"，就落入二清。

### 4.4 条码支付分类

| 模式 | 术语 | 谁出示码 | 风险与限额特点 |
|---|---|---|---|
| 用户扫商户 | **主扫** | 商户展示收款码 | 若是**静态张贴码**，最易被覆盖替换，风险等级最低、单笔限额显著低于其他模式（以监管原文为准） |
| 商户扫用户 | **被扫** | 用户 App 出示付款码 | 付款码一次一换、有效期短；扫码枪/POS 可信，限额可放宽 |

开发要记住：**主扫与被扫走的是不同交易码、不同风控规则、不同限额档位**，接口字段（如"支付场景/终端类型"）不能混填，混填会被清算组织退单。

## 五、报文标准

### 5.1 ISO 8583 —— 银行卡联机交易

用于 ATM/POS/银联等银行卡联机交易，是**定长 + 位图驱动**的二进制/字符混合协议，不是 JSON。

```
┌────────┬──────────────┬───────────────────────────┬────────────────┐
│ MTI    │ Bitmap       │ 数据域（按位图标记存在）   │ 尾部扩展域     │
│ 4 位   │ 64/128/192 位 │ DE2 卡号 DE3 处理代码      │ DE64/128 MAC   │
│ 报文类型│ 标记哪些域有 │ DE4 金额 DE11 跟踪号 ...   │                │
└────────┴──────────────┴───────────────────────────┴────────────────┘
```

- **MTI（Message Type Indicator）**：4 位，标识版本、报文类型（请求/应答/指示/否定应答）、功能（如 0100 授权请求、0110 授权应答、0200 金融请求、0400 冲正、0800 网络管理）。
- **位图（bitmap）**：每一位对应一个域是否存在；第一位本身是"扩展位图标志"，所以有主/副/第三扩展位图。
- **常用域**：DE2 主账号、DE3 处理代码、DE4 交易金额、DE11 系统跟踪审计号（**幂等核心**）、DE12/13 交易时间/日期、DE25 服务码、DE32 受理机构代码、DE37 收单方参考号、DE38 授权号、DE39 响应码、DE41 终端号、DE42 商户号、DE43 商户名称地址、DE49/51 币种码、DE52 PIN 块、DE53 安全控制信息、DE55/62/63 附加数据、DE64/128 MAC。

各转接网络在 ISO 8583 之上都有**私有子集与自定义域**（DE55 常见 EMV 标签集，DE62/63 常放网络保留字段），所以"看过一次 8583 不等于会接任何一个网络"。

### 5.2 ISO 20022 与 MX

**ISO 20022 是一套"业务建模方法 + 报文语法无关的模型"**，先定义业务语义（UML 模型），再序列化成具体语法（实践中主要是 XML，即所谓 **MX 报文**）。常见报文：

| 报文 | 用途 |
|---|---|
| `pain.001` | 客户发起付款指令（企业→银行） |
| `pacs.008` | 客户跨行转账（银行间） |
| `pacs.009` | 银行间头寸转账 |
| `pacs.002` | 支付状态报告/退回通知 |
| `camt.053` / `camt.054` | 客户对账单 / 当日电子账单通知 |
| `mt940` → `camt.053` | SWIFT 侧同类替代关系（对账单） |

**SWIFT MT → MX 迁移**：SWIFT 的跨境支付报文正在从 MT（类电传定长格式）迁移到基于 ISO 20022 的 MX，规则由行业组织 CBPR+ 统一。停用时间表业内已多次调整，**以 SWIFT 官方发布时间表为准**。对开发的实际影响是：同一笔业务可能"一头 MT、一头 MX"，中间靠翻译（translation）维持，翻译存在**信息丢失（lossy translation）**风险——MT 装不下的结构化字段（如完整地址、多级法人信息）会被截断或塞进非结构化备注。

| 标准 | 语法 | 主要场景 | 特点 |
|---|---|---|---|
| ISO 8583 | 二进制/位图 | 银行卡联机 | 极紧凑、快、字段有限、可读性差 |
| ISO 20022 (MX) | XML | 行内外汇款、跨境、对账 | 结构化强、可读、体量大、需 schema 校验 |
| SWIFT MT | 类电传定长块 | 跨境报文 | 字符集受限、字段短、正在被 MX 替代 |
| 人行支付系统报文 | 专用报文格式（向 ISO 20022 体系演进） | 境内跨行清算 | 以参与者行号路由、含清算日期与业务编号，规范版本以人民银行发布为准 |

### 5.3 开发真正会踩的报文细节

| 细节 | 坑 | 正确做法 |
|---|---|---|
| **必输项** | 只按文档顺序拼字段，漏了条件必输项 | 三态 M（必输）/O（可选）/C（条件必输）；C 项要有"当 X 时必须填 Y"的规则代码与用例 |
| **金额单位** | 8583 金额域是**整数最小单位**（人民币=分），20022 是带小数的 decimal | 内部统一用"分"整型或 `BigDecimal`；转换只在报文边界做；**绝不用 `double`** |
| **小数位数** | 假设所有币种 2 位小数 | JPY/KRW/VND 是 0 位，BHD/KWD 是 3 位；币种-小数位表必须是数据不是硬编码 |
| **日期时间** | 服务器时区不同导致跨日 | 报文带时区偏移；明确区分交易日期/记账日期/清算日期/起息日 |
| **字符集** | 中文商户名进定长域被截断 | 定长域按**字节**算长度；GBK↔UTF-8 差异要显式转换，超长按规则截断或转拼音 |
| **编码歧义** | 位图 BCD 打包 vs ASCII，各家不同 | 接入前用样例报文逐字节比对（hex dump），不要靠"文档说一样" |
| **安全域** | PIN 块明文、MAC 校验漏做 | PIN 块只能在 HSM（加密机）内处理；MAC 校验失败必须拒付 |

## 六、开发视角必答题

### 6.1 流水号与业务参考号：终态唯一性

必须区分两类号：

| 号 | 生命周期 | 用途 |
|---|---|---|
| **交易流水号 / 系统跟踪号** | 每次**调用**一个（重试会变） | 链路追踪、报文对报文 |
| **业务编号 / 商户订单号 / 参考号** | 每笔**业务**一个（重试不变） | 幂等、查询、对账 |
| **渠道/清算侧返回号**（如 `trade_no`、清算流水号） | 由对方产生 | 对账时的权威匹配键 |

**终态唯一性**：一笔业务在同一时刻只能有一个终态，且终态不可逆（`SUCCESS` 不能回到 `PENDING`）。实现上就是"状态机 + 唯一键"：状态变更走条件更新（`WHERE status = 'PENDING'`），返回受影响行数为 0 即判定为"已被处理"。本仓库 `ai-cs-pay/src/main/java/com/aics/pay/service/impl/PayTransactionServiceImpl.java:53-56` 就是这个语义：已 `SUCCESS` 或记录不存在时 `markSuccess` 直接返回 `false`，重复通知不会重复生效。

幂等键的选取原则：**用业务编号，不用流水号**；用 Redis 抢占只是加速挡，权威一定在 DB 唯一约束 + 状态检查（参见 [02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)）。

### 6.2 联机交易超时：未知态与原交易查询

超时（读超时、连接超时、对端 502）**不等于失败**。对方可能已经记账成功，只是应答没回来。这就是"未知态"。

```
                    ┌──── 明确成功 ───> SUCCESS（终态，可推进后续）
 发起联机请求 ──应答─┼──── 明确失败 ───> FAILED（终态，可安全重做/重发）
                    └──── 超时/断连/解析失败 ───> UNKNOWN（非终态）
                                                    │
                                       ① 先查（原交易查询/单笔查单）
                                       ② 查不到再等，定时重查
                                       ③ 超过最大时限才转人工/差错挂账
                                                    │
                                          严禁：UNKNOWN 直接当失败重试
                                          后果：重复扣款 / 重复汇款
```

**原交易查询**（有的系统叫"查复""单笔对账""querySingle"）必须携带原交易的业务参考号与**原交易日期**；跨日切时还要处理"查哪一天的库"。这套语义与本模块 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md) 一脉相承，代码形态可对照 `ai-cs-pay/src/main/java/com/aics/pay/service/impl/PayCompensationServiceImpl.java:39`（PENDING 流水主动查单兜底回调丢失）。

### 6.3 报文加验签与重放防护

- **待签串构造必须唯一确定**：排除签名字段本身、按字典序排序、跳过空值、指定编码。稍有不一致就是"本地算出来对不上"。可对照 `ai-cs-pay/src/main/java/com/aics/pay/channel/UnionpaySignature.java:37`（排除 `sign`/`signMethod`、非空值、键升序、SHA256withRSA + Base64）。
- **验签用原始报文，不用解析后的对象**：一旦经过 JSON/Form 反序列化再重排，字段顺序和转义就可能变，验签会假失败/真漏判。
- **重放防护三件套**：时间戳（窗口化，如 ±5 分钟）+ 随机串 nonce（窗口内去重）+ 业务流水唯一约束。只靠时间戳是不够的。
- **证书与密钥**：签名证书与加密证书分开（密钥分离）；证书序列号/`keyId` 要随报文上传，便于对方选公钥；轮换要双版本并行，避免"换新证书当天全网失败"。传输层 TLS 与报文层签名是**两回事**，都要做（见 [15-计算机基础/05-HTTP与TLS](../15-计算机基础/05-HTTP与TLS.md)）。
- **验签失败 = 拒绝 + 不写业务 + 记安全事件**，返回码不能泄露"差在哪一位"，防探测。

### 6.4 清算文件对账

典型是 **T+1 对账文件**：清算机构/渠道在次日凌晨生成上一清算日的明细文件（也可能有日间多次清算文件、结算款到账通知）。

对账匹配关系（三单匹配）：

```
我方业务订单号 ──┐
                 ├──►  我方支付流水（trade_no / 渠道流水号）  ◄──┐
对账文件明细 ────┘        清算日期 + 币种 + 金额 + 手续费        │
                                                                  └ 渠道侧权威记录
```

差错三分类：

| 差错 | 含义 | 常见根因 | 处理 |
|---|---|---|---|
| **长款** | 对方/账上钱多，我方无对应记录（钱多出来） | 回调丢失、我方未落库、跨日切归属不同清算日 | 查渠道流水补单，或原路退款；不能自行"当收益" |
| **短款** | 我方有记录，对方无款或款少（钱少了） | 我方误判成功、渠道撤销未通知、金额/币种错 | 发起查询、必要时主动退款或差错追偿 |
| **不一致** | 两边都有但金额/手续费/状态不同 | 优惠/退部分款、手续费规则版本不同 | 以协议与清算文件为准，差异入账并告警 |

对账作业的实现要点：文件分片与断点续跑、编码/BOM/换行符差异、同订单多笔（部分退款、冲正后再收）、汇总（笔数+金额）与明细双层校验。方法论见 [14-数据工程与OLAP/08-数据质量与对账](../14-数据工程与OLAP/08-数据质量与对账.md)，跑批编排见 [14-数据工程与OLAP/05-批处理与调度编排](../14-数据工程与OLAP/05-批处理与调度编排.md)。

### 6.5 退款 vs 撤销 vs 冲正

| | 撤销/取消（void/cancel） | 退款（refund） | 冲正（reversal） |
|---|---|---|---|
| 触发时点 | 交易**未清算**前（通常当日） | 已清算后 | 联机异常时的自动反向报文 |
| 金额 | 一般只能全额 | 可部分、可多次 | 与原交易一一对应，全额 |
| 是否产生资金流 | 否（让交易"不发生"） | 是（反向打款） | 清算上通常被轧平 |
| 关键字段 | 原授权号 | **原交易参考号 + 原交易日期** | 原报文跟踪号 |
| 限制 | 过日切就撤不了 | 有可退期限、可退余额、手续费是否退 | 发起方必须处理"冲正应答" |

初学者最常见 bug：**把退款当撤销实现**，用一个新订单号发起，结果对账匹配不上原交易。退款必须携带原交易标识并可追溯到原流水（对照 `ai-cs-pay/src/main/java/com/aics/pay/entity/PayTransaction.java:15` 的流水建模，状态里 `REFUNDING/REFUNDED` 是独立状态而非新流水的初始态）。

### 6.6 日切窗口期间的交易

日切（切日）是核心系统从会计日 T 切到 T+1 的跑批窗口。难点：各系统切日时点不同步，会出现"渠道侧已是新会计日、核心侧还是旧日"。可行策略：

| 策略 | 做法 | 代价 |
|---|---|---|
| 停止受理 | 日切窗口关闭部分交易 | 违背 7×24 体验，只在必须时用 |
| 前置缓冲 | 渠道/前置接收请求，落队列，日切完成后重放 | 需幂等与队列积压监控 |
| 允许跨日记账 | 记账到下一会计日，起息日保持原日 | 计息与报表口径要配套 |
| 双账期查询 | 查询接口带"账务日期"参数，跨日切自动查两库 | 报文与调用方需支持日期入参 |

原则：**清算日与交易日不一致是设计常态**，不是 bug。别把业务日期当成分库分表键的唯一依据（对照 [07-运维部署/06-优雅停机与零丢失滚动更新](../07-运维部署/06-优雅停机与零丢失滚动更新.md) 中"在途请求怎么办"的同一类问题）。

### 6.7 限额与头寸不足的重试策略

先给错误码分族，再谈重试：

| 错误族 | 例子 | 可自动重试？ | 策略 |
|---|---|---|---|
| 业务规则拒绝 | 超单笔限额、账户状态异常、余额不足、户名不符 | **否** | 直接失败并引导用户改要素；重试只会在监管面前制造无效流量 |
| 系统繁忙/超时 | 网络抖动、对端 5xx、连接重置 | 是（进 UNKNOWN） | 指数退避 + 上限次数 + 幂等键不变；先查询再决定是否重发 |
| 头寸不足/排队 | 清算账户余额不足、进入排队 | 不由应用重试 | 走排队/流动性管理，或用备用通道；应用侧只做状态跟踪与用户告知 |
| 重复提交 | 已处理、唯一键冲突 | 否 | 视为幂等成功返回原结果，不当报错 |
| 报文校验失败 | 域缺失、验签失败、MAC 错 | 否 | 是代码/配置问题，修复后人工重发；同时告警 |

配置形态可参考本仓库：`ai-cs-chat/src/main/resources/application.yml:108-124` 的 Resilience4j 熔断（计数窗口 10、失败率阈值 50%、半开 3 次），但**银行的联机交易更强调"先查后重发"**，熔断只解决"对端已经不行了，别再压"的问题，解决不了"这一笔到底成没成"的问题——后者只能靠查询与对账。相关方法论见 [02-Spring微服务/08-Feign熔断与降级语义](../02-Spring微服务/08-Feign熔断与降级语义.md) 与 [04-中间件/06-Sentinel限流与熔断降级](../04-中间件/06-Sentinel限流与熔断降级.md)。

## 八、初学者常见误区

| 误区 | 真相 |
|---|---|
| 跨行转账就是钱在两行之间直接飞 | 钱只在各方与央行（或清算组织）的账户间变动；客户看到的是各家银行自己的记账 |
| 银联和网联是一回事 | 银联主责**银行卡跨行**转接清算；网联主责**第三方支付机构与银行之间**的网络支付转接，是断直连产物 |
| SWIFT 是转钱的通道 | SWIFT 传报文；资金变动靠代理行账户与央行结算 |
| 清算完成 = 客户已到账 | 清算完成后还要央行结算 + 收款行入账 + 风控放行，收款行可能延后入账甚至退汇 |
| 超时就是失败，赶紧重发 | 超时是未知态，先查后重发；盲目重发制造重复扣款 |
| 大额和小额只是金额大小不同 | 本质差别是全额实时（RTGS）与批量净额（DNS），流动性成本与信用风险的取舍不同 |
| 退款和撤销语义差不多 | 撤销发生在清算前、不留资金流；退款在清算后、有原交易参考号且有可退期限 |
| 支付机构沉淀的客户钱是它的利润 | 那是客户备付金，须集中交存监管，挪用是重大违规 |
| ISO 8583 金额就是"元" | 多数域是整数最小货币单位（分），币种另有域，小数位随币种变化 |
| 把"排队"当系统故障报警 | 排队是流动性管理常态机制，应用侧要区分"排队中"与"失败" |
| 银行内部有清算系统，我们项目里也有 | ⚠️ 本仓库是电商客服系统，只有支付渠道对接与流水对账，不是清算系统 |
