## 一、电子渠道全景与分层

**电子渠道**＝不通过柜员、由客户或企业系统自己发起交易的入口。JD 里的"网络金融"部门通常就是这些渠道系统的建设方，外加互联网存款/贷款、场景金融、开放银行等线上业务。

| 渠道 | 服务对象 | 典型交易 | 现状趋势 |
|---|---|---|---|
| 个人网银 | 个人 | 大额转账（U 盾）、缴费、理财 | 客户向 App 迁移，功能收缩 |
| 企业网银 | 对公 | 付款、代发、审批流、回单、银企直联配属 | **不易被替代**（审批 + 证书 + 财务系统耦合） |
| 手机银行 | 个人 | 几乎所有零售交易、生活场景 | 主战场，版本迭代最快 |
| 微信银行 / 小程序 | 个人 | 轻查询、通知、预约、小额场景 | 受公众号能力与合规约束，不做高风险交易 |
| 电话银行（IVR/坐席） | 个人为主 | 查询、挂失、部分转账（受强认证约束） | 转向坐席服务与老年客群兜底 |
| 短信银行 | 个人 | 下行通知、少量上行指令 | 主要剩"通知 + 验证码"，且验证码正被替代 |
| 开放银行 API | 企业/平台 | 账户、支付、验证、融资类服务输出 | 增量方向，安全与合规要求最高 |
| 自助设备 / 智能柜台 | 个人 | ATM 存取、开卡、挂失、打印回单 | 智能柜台替代大量柜面交易（见 [03-柜面系统与集中作业](./03-柜面系统与集中作业.md)） |

### 1.1 分层：为什么渠道要做成"薄"

```
┌───────────────────────────────────────────────────────────────────────────┐
│ 渠道接入层  App / H5 / 网银 / 小程序 / IVR / 开放 API / 前置机              │
│   职责：协议适配、会话与令牌、设备与版本、灰度开关、报文加解密与验签、限流   │
├───────────────────────────────────────────────────────────────────────────┤
│ 渠道管理层  菜单与权限、渠道限额、交易路由、双录/弹窗告知、埋点与体验监控    │
├───────────────────────────────────────────────────────────────────────────┤
│ 业务中台 / 产品服务层  转账、账户服务、理财申赎、贷款申请、支付、代发、对账   │
│   职责：业务规则、产品参数、状态机、风控调用、额度检查、幂等                │
├───────────────────────────────────────────────────────────────────────────┤
│ 支撑域      风控决策、反洗钱、实名核验、影像、消息、计息、限额中心、客户信息  │
├───────────────────────────────────────────────────────────────────────────┤
│ 核心系统（账务权威） + 支付前置（对外清算通道）                              │
└───────────────────────────────────────────────────────────────────────────┘
```

"渠道薄"的理由不是审美，而是四个硬约束：

1. **规则必须唯一**。转账限额若在手机银行和企业网银各写一份，改一次要改两处，漏改就是合规事故。规则要落在限额中心/业务中台，渠道只"问结果"。
2. **发布节奏不同**。App 一周两版，核心一年两次大版本。逻辑放渠道才能快，放核心就永远等窗口。
3. **风险半径**。渠道离公网最近，被攻破的概率最高；把账务与规则放在核心侧，渠道被拿下也拿不到"改规则"的能力。
4. **一致性体验与审计**。同一产品在不同渠道必须报同一个价、同一个限额，监管检查也按"产品规则归口"来看。

**薄渠道的边界**：渠道只做"认证 + 采集 + 呈现 + 前置校验（少金额、格式、必填）"，不做资金规则判定。看起来渠道"只是转发请求"其实是**目标态**，不是偷懒。

## 二、银行账户分类管理（最常问的硬知识）

个人银行结算账户按开立核验强度与功能分三类：

| | **Ⅰ 类户** | **Ⅱ 类户** | **Ⅲ 类户** |
|---|---|---|---|
| 定位 | 全功能"金库" | 理财与日常消费"钱包" | 小额高频"零钱包" |
| 开立方式 | **必须面对面核验**（柜面，或自助机具经银行工作人员现场核验身份） | 可远程开立（绑定 Ⅰ 类户 + 强核验 + 影像/视频） | 远程开立，核验强度最低档 |
| 存取现金 | 可以 | 视核验强度；未现场核验的受限 | **不得存取现金** |
| 转账/消费 | 功能全开，限额由客户与约定决定 | 面向非绑定账户的收支设有日累计与年累计限额 | 限额与账户余额上限均显著低于 Ⅱ 类 |
| 实体介质 | 通常对应借记卡（实体/虚拟） | 可配发实体卡，也可仅有电子账户 | 无实体介质（纯电子账户） |
| 典型场景 | 工资、大额、房贷、社保 | 绑定支付机构、理财、日常消费 | 扫码、公交地铁、小额免密 |
| 升降级 | — | 经现场核验或补强核验后可升级为 Ⅰ 类 | 可升级为 Ⅱ/Ⅰ 类，需重新核验身份 |

必须记住的四条规则：

1. **同一客户在同一法人银行只能开立一个 Ⅰ 类户**；已有 Ⅰ 类户再开，只能开 Ⅱ/Ⅲ 类。这是"一人多卡"治理的制度基础。
2. **绑定账户关系**是 Ⅱ/Ⅲ 类户的身份锚点：远程开立时通过绑定本行或他行 Ⅰ 类户（或信用卡账户）完成要素核验；资金往来的宽松程度也围绕绑定账户设计（绑户之间限制更松，非绑户限制更严）。
3. **非面对面开户的核验强度决定功能上限**。核验越弱，能做的事越少——不是一句口号，它直接实现为账户类别 + 交易权限矩阵。
4. **具体限额数字不要背**。现行制度给出限额口径，各银行还会在此基础上设置更严的自有档位：**数字以人民银行现行制度原文与开户行公告为准**。业内常引用的 Ⅱ 类户非绑定账户资金收付"日累计 1 万元、年累计 20 万元"以及 Ⅲ 类户余额上限（千元量级）等，只能当作"知道有这类限制"的示例，不要当结论说死。

### 2.1 高危陷阱：两套"Ⅰ/Ⅱ/Ⅲ 类"不是一回事

| 体系 | 谁的账户 | 依据哪套规则 | 关键点 |
|---|---|---|---|
| **个人银行结算账户** Ⅰ/Ⅱ/Ⅲ 类 | 商业银行 | 人民银行个人银行账户分类管理制度 | 涉及现金、账户实名强度、央行账户体系 |
| **支付账户** Ⅰ/Ⅱ/Ⅲ 类 | 第三方支付机构 | 非银行支付机构网络支付相关规章 | 是支付机构内部的虚拟记账余额，**不是银行结算账户**，限额与用途规则另成一套 |

面试被问"Ⅱ 类户限额是多少"时，先反问一句"您指的是个人银行结算账户Ⅱ类户，还是支付机构的Ⅱ类支付账户？"——这一句比报数字更能证明你懂。

## 三、网络支付：渠道侧的主要形态

### 3.1 快捷支付（绑定银行卡代扣）

**快捷支付**＝把银行卡"签约"到支付机构或银行自己的线上支付产品，之后支付不再跳转网银，由收款方后台发起验证与扣款。

```
签约阶段（一次性）                       支付阶段（每次）
用户输入 卡号+姓名+证件号+预留手机号      用户在商户端选"某某银行快捷支付"
   │  四要素核验（银行侧比对）              │  输入支付密码 / 短信验证码 / 指纹
   ▼                                       ▼
银行返回签约验证通过 ── 生成协议号 ─────► 支付机构/银行凭协议号发起扣款指令
   │  （协议号、限额、有效期落库）           （走 网联/银联 → 发卡行，见 04 篇 §4.1）
   ▼                                       ▼
签约短信/回跳确认                         扣款结果异步通知商户 + 页面回跳
```

- **四要素**：姓名、证件类型与号码、银行卡号、银行预留手机号。少一个就退单。
- **代扣协议**：有协议号、限额、有效期、签约渠道；**解约必须能自助完成**（监管明确要求，实现上是"协议状态 + 通知停止扣款"）。
- 免密/小额自动扣款（如订阅、停车缴费）本质也是代扣协议，必须明示与可撤销。

### 3.2 其他形态速查

| 形态 | 谁发起 | 特点 | 坑 |
|---|---|---|---|
| 网关支付 | 用户跳到银行/支付页面完成 | 依赖跳转与回跳，体验差但核验强 | 回跳参数可伪造，**必须以服务端查询/异步通知为准**（对照 [02-Spring微服务/13-支付渠道集成与回调一致性](../02-Spring微服务/13-支付渠道集成与回调一致性.md)） |
| 代收 | 收款单位批量发起扣款 | 需客户授权协议，走小额批量 | 协议缺失 = 投诉与处罚 |
| 代付 | 付款方批量出款（工资、理赔、报销） | 走小额批量/IBPS 场次 | 明细校验、失败重发、部分成功处理 |
| 主扫 | 用户扫商户码 | 静态码风险最高、限额最低 | 码被替换/覆盖（"换码偷钱"） |
| 被扫 | 商户扫用户付款码 | 一次一码、有效期短 | 付款码泄露、截屏外发 |
| 云闪付 / 手机 Pay | 银联网络与令牌化 | 银行卡令牌化（token）、NFC/二维码 | 令牌生命周期与卡挂失联动 |

### 3.3 支付要素与三方对账关系

一笔线上支付至少四个号，职责不同、**不能互相替代**：

| 要素 | 产生方 | 作用 |
|---|---|---|
| 商户号 `merId` | 收单机构/银行分配 | 身份与结算归属，费率协议的挂载点 |
| 终端号 `termId` | 收单机构分配 | 区分门店/接口/POS，风控维度 |
| 商户订单号 `orderId` | 商户自己 | 商户侧幂等键（**重试不变**） |
| 支付/渠道流水号 `tradeNo` | 银行或支付机构 | 对方侧权威凭证，**对账匹配键** |
| 清算日期 | 清算组织 | 归属哪一天结算（≠ 交易日期，见 04 篇 §6.6） |

对账关系：商户订单 ↔ 渠道流水（1:1 或 1:N，部分退款时会 1:N）↔ 银行记账 ↔ 清算文件 ↔ 结算入账金额（扣手续费后）。链条越长，"单边账"越容易出现——处理方法论见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md)。

## 四、安全与风控：渠道最有技术含量的部分

### 4.1 认证介质矩阵

| 介质 | 是什么 | 强度 | 弱点 |
|---|---|---|---|
| 交易密码 | 取款/柜面/支付时输入的静态密码 | 低（单因素） | 撞库、偷窥、社工 |
| 支付密码 / 手势 / 指纹 | 设备侧校验 | 中 | 换设备即失效；生物特征不可撤销 |
| 短信验证码（OTP） | 一次性口令下发到预留手机号 | 中 | 嗅探、补卡劫持、代收码诈骗；体验和到达率差 |
| U 盾 / USB Key | 硬件内私钥 + 证书，本地签名带屏幕按键确认 | 高（不可导出的私钥 + 交易可见性） | 成本高、驱动兼容、易用性差 |
| 蓝牙 UKey / 移动证书 | 手机侧安全载体证书 | 中高 | 依赖发证与设备绑定管理 |
| 动态口令器 / 口令卡 | 时间或事件同步的一次性口令 | 中 | 无交易内容绑定（"你不知道自己在签什么"） |
| 号码认证（一键取号） | 运营商网关侧校验本机号码 | 中（便利性极高） | 只证明"是这个号码"，不证明"是这个人" |
| 人脸/声纹 | 生物特征比对 + 活体检测 | 中（作为一次核验手段） | 深度伪造、面具攻击；须单独授权（敏感个人信息） |

**关键判断**：所有介质都要回答同一个问题——**它是否绑定了交易内容**。U 盾强在于"签名的是这笔具体交易、且用户能在屏幕上看到金额与收款方"；短信验证码弱在于"口令与交易无关，诱骗用户把码给别人就能用"。这是"为什么大额必须证书类介质"的技术答案，也是渠道交易分档的底层逻辑。

### 4.2 限额体系

限额不是一列数字，而是一张多维矩阵：

```
最终限额 = min(
   产品/账户类别限额（Ⅰ/Ⅱ/Ⅲ 类、支付账户）,
   认证介质档位限额（口令 / 短信 / U盾 / 人脸+设备）,
   渠道限额（手机银行 vs 网银 vs 开放 API）,
   客户风险等级限额（新户、老年、投诉命中、模型高分）,
   单笔 / 当日累计 / 短期（7 日/30 日）累计 / 年累计,
   收款方维度限额（新收款人首次、跨行、境外）,
   临时管控（风险事件后运营一键下调）
)
```

实现要点：**限额中心统一算，渠道只展示"还可用额度"**；取现/转账类还要"当日累计"随账务日期滚动（日切时点决定哪笔算哪天，见 04 篇 §6.6）；临时调限要能按客户/渠道/产品维度**分钟级生效并回滚**——这是运营最常用的止血开关（对照 [13-稳定性工程/05-降级预案与开关治理](../13-稳定性工程/05-降级预案与开关治理.md)）。

### 4.3 反欺诈与设备指纹

- **设备指纹**：采集设备与浏览器特征生成稳定 ID，用于识别模拟器、Root/越狱、群控、多账号共用一台设备。**边界**：只作风险信号，不做唯一身份凭证；采集范围受个人信息保护规则约束。
- **名单**：黑名单（设备/IP/收款账号/涉诈账户）、灰名单（观察）、白名单（企业客户常用 IP/设备）。
- **规则引擎 + 模型**：规则负责"可解释、可立即上线"（如改手机号 30 分钟内大额转出 → 拦截），模型负责"泛化、抓团伙"（关系图谱、序列模型）。两者结果汇成决策。
- **决策链路四态**：`通过` / `加验（step-up：追加人脸或短信或客服外呼）` / `转人工审核` / `拒绝`。**关键设计**：加验要能续跑原交易（不能让客户重新填一遍），转人工要有时效 SLA 与超时兜底策略（超时是放行还是拒绝，按金额与场景定）。
- **三段时间论**：

| 阶段 | 手段 | 说明 |
|---|---|---|
| 事前拦截 | 名单、限额、开户准入、设备绑定、首次收款人冷静期 | 唯一能真正阻止资金流失的窗口 |
| 事中监控 | 实时决策 + 准实时批量扫描（分钟级）、异常聚集检测、串行事件拼接 | 交易已完成但钱还在通道里 → **延迟出款**是最有效止损 |
| 事后核查 | 案件复盘、规则回检、投诉与公安涉案数据回流、断卡名单核处 | 反哺规则与模型，否则同一手法反复得手 |

为什么必须三段：单一时点拦截率有限（黑产会拆小额、分散账号、养号），事中延迟出款给"拦截 + 追截"争取时间窗，事后核查才能识别新手法。

## 五、开放银行与银企直联

```
企业 ERP / 财务系统 / 资金系统
   │  （1）银行侧签发企业证书  （2）签名请求 + 敏感字段加密
   ▼
企业侧前置机（部署在客户机房的转换与缓冲节点：证书、签名、协议转换、文件落地、断点续传）
   │  专线 / VPN（不允许直连行内生产网）
   ▼
银行开放平台 API 网关（认证、授权、限流、配额、审计、灰度、错误码归一）
   ▼
业务中台（账户服务 / 支付 / 代发 / 回单 / 现金管理落地）  → 核心 + 支付前置
```

| 主题 | 要点 |
|---|---|
| 认证与授权 | 机器对机器用 `client_id/secret` + 证书；第三方应用代表客户操作用 **OAuth2 授权码模式** + 最小 scope + 短时效 access token + refresh 轮换。**授权对象是"某个客户允许某应用读某类数据/发起某类交易"**，不是"应用能读所有数据" |
| 签名与验签 | 请求体规范化（排序、去空值、指定编码）→ 私钥签 → 对方公钥验；带 `keyId`/证书序列号支持密钥轮换；国内业务常用 SM2/SM3/SM4（国密）或 RSA/SHA256，**算法要可配置不能写死** |
| 报文加密 | 敏感字段（卡号、身份证号、手机号、密码）用**数字信封**：随机对称密钥加密数据，再用对方公钥加密对称密钥；整体走 TLS。两层各防各的（链路窃听 vs 落盘/日志泄露） |
| 前置机 | 存在理由是"客户与银行生产网之间必须有一层隔离 + 网络不可靠时要缓冲与文件落地"。运维难点：证书更新、版本升级、时钟偏移、断网重连、日志回传 |
| 幂等 | 幂等键 = 企业侧业务流水号；重复提交返回**原结果**而不是报错。语义细节见 [02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md) |
| 限流与配额 | 按应用/接口/客户三级配额；令牌桶容忍批量场景突发。参数形态可对照 `ai-cs-gateway/src/main/resources/application.yml:48-49`（`replenish-rate: 5`、`burst-capacity: 10`） |
| 错误码规范 | 三层：`S0xx` 系统级（可重试）、`B0xx` 业务级（不可重试，需改要素）、`C0xx` 渠道级（对方返回，需映射）。**不要把渠道原始错误码和报文透传给企业客户**（信息泄露 + 客户被绑死在渠道语义上）；对外错误码要有稳定文案、是否可重试、建议动作 |
| 接口文档 | 变更要向前兼容、给版本、给灰度期；上线前联调环境要有"全错误码可构造"能力，否则客户侧永远只测通主路径 |

**与现金管理的关系**：企业"跨行资金视图 + 统一付款"最常见的落地形态就是银企直联——客户财务系统通过多家银行 API 各自取数与出款。参见 [05-现金管理与资金头寸](./05-现金管理与资金头寸.md) §2.6。

## 六、线上开户与实名认证

```
用户发起 → 证件影像采集（OCR + 质量校验） → 联网核查（姓名/身份证号/照片一致性）
        → 人脸活体检测 + 与权威照片比对     → 预留手机号 + 验证码 / 绑卡要素核验
        → 地址/职业/税收居民等尽调信息采集   → 开户意愿确认（视频或双录，按产品要求）
        → 风控决策（通过 / 加验 / 人工）     → 登记开户结果 + 影像留存 + 账户类别分派
```

| 环节 | 人话解释 | 技术要点 |
|---|---|---|
| **联网核查** | 通过银行与公安部门的公民身份信息核验接口，核对姓名、身份证号、照片是否一致 | 接口不可用要有降级预案与拒绝策略（**不能"核查失败就默认通过"**）；返回码语义要区分"查无此人"与"系统故障" |
| **人脸比对** | 现场活体动作 + 与权威照片比对 | 活体类型（动作/静默/光线）、比对分与阈值分场景、留存比对流水与图片证据 |
| **绑卡验证** | 用已有 Ⅰ 类户四要素 + 小额/验证码证明"是你" | 验证次数限频，防"撞库枚举卡号" |
| **影像留存** | 证件、人脸、协议、告知书签核过程可回溯 | "可回溯"是硬要求：查任一笔开户能还原当时看到什么、点了什么（对照双录） |
| **反电诈尽调** | 询问开户用途、职业、居住地，识别异常（异地、无合理用途、被他人遥控） | 系统内建风险分级与"审慎开户/拒绝开户"路径，拒绝要有依据与留痕 |
| **一人多卡治理** | 同一人同一行 Ⅰ 类户唯一；存量超量、长期不动户、异常账户要清理与管控 | 实现为账户数量校验 + 久悬/异常状态机 + 非柜面渠道限额下调 |

安全规范与个人信息保护的体系化内容见 [07-银行业信息安全管理规范](./07-银行业信息安全管理规范.md)，反洗钱与客户尽调见 [08-反洗钱账户管理与监管合规](./08-反洗钱账户管理与监管合规.md)。

## 七、互联网贷款与场景金融

**互联网贷款**＝全流程（获客、申请、审批、放款、贷后）主要在线上完成的个人消费贷与小额经营贷。**场景金融**＝把支付、开户、贷款嵌入到消费或经营场景中（电商分期、物流司机加油、农资赊销）。

```
流量平台/场景方                     银行（资金与风控主体）
  导流 · 数据 · 初筛 · 贷后提醒  ──►  准入 · 授信决策 · 定价 · 放款 · 资产管理
                                          │
                       增信/担保机构 ◄────┤ 风险分担（须持牌、不得阻碍客户直接联系银行）
                                          ▼
                                  支付通道：受托支付直达交易对手
```

| 概念 | 说明 | 合规边界（描述式，以现行有效规定为准） |
|---|---|---|
| **助贷** | 平台导流并提供数据，银行自主风控、独立审批并全额出资 | 银行不得把**核心风控环节**外包；平台不得变相兜底而不具备资质 |
| **联合贷** | 银行与持牌合作方按约定比例共同出资、共担风险 | 监管对合作方出资比例设下限、对单笔额度与跨地域经营设限制（**具体比例数字以办法原文为准**） |
| **受托支付** | 贷款资金由银行直接支付给借款人的交易对手，不经过借款人账户 | 大额或场景明确时优先受托支付，防止资金挪用与回流套现 |
| **自主支付** | 放款到借款人账户由其自行支付 | 需设金额上限与用途监控，配合资金流向排查 |
| **年化利率明示** | 以内部收益率（IRR）口径展示年化资金成本，把利息、服务费、担保费合并折算 | 人民银行已就明示贷款年化利率发布公告；只报"日息万几""月费率"不合规 |
| **数据与征信合规** | 个人信用信息的采集与用于授信须经授权并通过持牌征信渠道流转 | "断直连"要求平台与银行之间的信用信息交互走持牌机构；不得以"数据服务"名义规避 |
| **贷后与催收** | 提醒、协商、司法处置分段管理 | 外访与催收行为受规范约束；投诉数据回流风控 |

渠道系统在这里通常扮演"申请入口 + 影像/协议/双录 + 状态查询 + 还款通道"，真正的授信与额度管理在信贷系统（审批链、决策引擎、额度中心、放款与贷后）。

## 八、网络金融系统的运维特性（JD 明说"研发运维"）

| 特性 | 表现 | 工程要求 |
|---|---|---|
| **7×24 不可停机** | 渠道没有"业务低谷可停机"概念，凌晨仍有人转账 | 零停机发布、优雅停机（对照 `ai-cs-gateway/src/main/resources/application.yml:2` 的 `shutdown: graceful` 与 `:7` 的 30s 超时；做法见 [07-运维部署/06-优雅停机与零丢失滚动更新](../07-运维部署/06-优雅停机与零丢失滚动更新.md)） |
| **可预期高峰** | 除夕/春节转账与红包、双十一、纪念币（钞）预约开放瞬间、每月 1—10 日代发工资、缴税截止日、月末季末结息、社保集中缴费期 | 高峰前压测与扩容预案、限流开关预置、"高峰窗口禁变更"（见 [13-稳定性工程/02-容量规划与性能预算](../13-稳定性工程/02-容量规划与性能预算.md)） |
| **发布窗口受限** | 日间原则上禁生产变更；夜间窗口 + 灰度（按客户尾号/机构/渠道）+ 明确回退点 | 变更评审、双轨开关、可回退数据库脚本（见 [10-银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)） |
| **外部依赖多且不可控** | 支付机构、银联/网联、征信、公安联网核查、短信通道、人脸供应商、证书服务、财政/社保对接 | **超时预算**（总超时 = 各级之和留余量）、熔断降级、多供应商互备、失败队列与人工兜底 |
| **联机交易监控** | 按交易码/渠道/错误码维度的成功率、平均与长尾耗时、三方健康度 | 分钟级指标 + 阈值与环比双条件告警；避免"总成功率掩盖单渠道崩了"（见 [06-Sentinel限流与熔断降级](../04-中间件/06-Sentinel限流与熔断降级.md)） |
| **日终与渠道对账** | 与银联/网联/支付机构/代收付单位逐日对账；对账未完成不能切日 | 文件到达监控、批次依赖编排、延迟告警（见 [14-数据工程与OLAP/05-批处理与调度编排](../14-数据工程与OLAP/05-批处理与调度编排.md)） |
| **应急与监管报送** | 一键限流/暂停渠道、暂停某类交易；事件按分级与时限报送；对外口径统一 | 预案要演练、演练要留痕；应急期间日志与流水必须完整可取证 |

**降级在银行渠道里的特殊含义**：互联网产品的降级通常是"少给点功能"，银行渠道的降级必须**先保证资金安全**。例：人脸服务超时 → 只能降级为"加验 + 转人工"，**不能降级为"跳过核验"**；短信通道挂 → 换备用通道或改为 App 推送确认，而不是免掉第二因素。

熔断的配置形态（本仓库 `ai-cs-chat/src/main/resources/application.yml:108-124`，计数窗口 10、失败率阈值 50%、半开 3 次试探、打开 30s）在银行同样用，但要额外满足两点：**熔断期间要有兜底路径与人工入口**，以及**已发出的交易不能因熔断开路而丢状态**（TimeLimiter 只是"别把线程吊死"，见 `:74-77` 的 60s 超时；对未知态仍须走查询与对账，见 04 篇 §6.2）。

⚠️ **诚实前提**：本仓库 `ai-customer-service` 是一个**电商 AI 客服系统**，不是网络金融系统。它没有账户体系、没有支付牌照业务、没有风控决策、没有监管报送。下表的"对照"指**工程能力形态相似**，可以当作"我在类似位置做过类似机制"的面试素材，不能夸大成"我做过银行渠道"。

| 银行网络金融关注点 | 本仓库已有的同形态能力 | 缺口（⚠️） |
|---|---|---|
| 第三方回调入口与验签后处理 | `ai-cs-pay/src/main/java/com/aics/pay/controller/PayCallbackController.java`（`POST /pay/callback/{paymentMethod}`，统一入口 + 渠道分发，异常返回 FAIL 让渠道重试） | 无幂等落库回执、无回调重试策略分级、无原始报文留存取证 |

## 十一、初学者常见误区

| 误区 | 真相 |
|---|---|
| 渠道系统只是把请求转发给核心 | 渠道承担认证、设备与风险信号采集、限额前置校验、报文安全、灰度与体验监控；只是"规则不放渠道" |
| Ⅰ/Ⅱ/Ⅲ 类账户的限额是死的数字 | 制度给口径，各家银行还会设更严档位；回答要先分清"银行结算账户"还是"支付账户" |
| Ⅲ 类户就是"额度小一点的 Ⅱ 类户" | Ⅲ 类户不得存取现金、无实体介质，功能与风险定位都不同，不是同一维度的缩放 |
| 支付账户里的钱就是银行里的钱 | 支付账户是支付机构的记账余额，不是银行结算账户；两者监管规则不同 |
| 风控是风控团队的事，渠道只要"把交易做完" | 渠道是风控信号的主要采集方（设备、环境、行为、位置），也是执行"加验/拒绝"的唯一触点 |
| 有验证码就等于安全 | 不绑定交易内容的短信验证码可被诱骗交出；强度要看"用户签的是不是这笔具体交易" |
| 人脸识别最可靠 | 它是便利性与强度折中手段，需活体检测 + 单独授权 + 证据留存，不能单独作为大额交易的唯一凭据 |
| 线上系统可以像内部系统那样停机发版 | 渠道 7×24，发版要零停机 + 灰度 + 回退点；变更窗口与监管报备都是硬约束 |
| 有熔断降级就够了 | 熔断解决"别再压垮对端"，不解决"这笔到底成没成"；后者只能靠查询与对账 |
| 外部依赖挂了就报错给用户 | 要分级：可等待（排队/异步补偿）、可替代（备用供应商）、必须拒绝（核验类不可跳过） |
| 开放 API 越像 REST 就越安全 | REST 只解决形式；安全靠证书 + 签名 + 字段加密 + 授权范围 + 幂等 + 配额的组合 |
| 互联网贷款是平台在放贷 | 放贷主体必须是持牌金融机构，核心风控不得外包；平台角色是导流与数据服务 |
| 年化利率就是"利息/本金" | 分期手续费、担保费都要计入，用 IRR 口径折算成年化才可比 |
| 我们项目有支付回调，所以懂网络金融 | ⚠️ 本仓库是电商客服系统，缺账户分类、限额、风控、对账文件与监管报送，只能做能力形态对照 |
