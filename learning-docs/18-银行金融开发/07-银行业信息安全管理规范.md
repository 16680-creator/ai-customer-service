# 银行业信息安全管理规范

> 本篇回答什么问题：银行 JD 里那句"**了解银行业信息安全管理规范**"到底在考什么？规范的四个层级分别约束谁、

## 一、规范体系：先建立四层地图

很多零金融经验的候选人把"银行安全规范"当成一坨，面试官一追问"哪些是你必须遵守的"就答不上来。
正确的记法是**四层**：越往上越稳定、越少改；越往下越具体、越是你天天撞的那一层。

```
┌───────────────────────────────────────────────────────────────┐
│  L1 法律层（全国适用，违反 = 违法）                            │
│   网络安全法 · 数据安全法 · 个人信息保护法 · 密码法             │
│   （另有：反洗钱法 · 反电信网络诈骗法，见 08 篇）              │
├───────────────────────────────────────────────────────────────┤
│  L2 监管规章与指引层（金融监管机构发布，违反 = 被处罚/被整改） │
│   银行业信息科技风险管理类要求 · 外包风险管理要求              │
│   商业银行业务连续性管理要求 · 数据治理与管理要求              │
│   个人金融信息保护相关要求 · 移动支付与渠道业务规范            │
├───────────────────────────────────────────────────────────────┤
│  L3 行业标准层（技术怎么做到，测评机构照此打分）               │
│   金融行业标准 JR/T 系列（人民银行发布，含个人信息保护技术规范）│
│   密码行业标准 GM/T 系列（密码行业，含算法与格式规范）         │
│   网络安全等级保护 GB/T 22239（"等保 2.0"，银行重要系统通常    │
│     定级为三级，具体级别以本行定级备案结果为准）               │
│   商用密码应用安全性评估（"密评"）                             │
├───────────────────────────────────────────────────────────────┤
│  L4 行内制度层（本行自己写的，违反 = 内部问责/停权限）         │
│   信息科技管理办法 · 开发安全规范 · 代码提交与评审规约         │
│   投产变更规程 · 测试数据管理办法 · 账号与权限管理办法         │
│   日志与留痕规范 · 保密协议与员工行为守则                      │
└───────────────────────────────────────────────────────────────┘
        约束强度：L1 最刚性 ←── 但天天碰到你的是 L4
```

| 层级 | 谁发布 | 约束对象 | 开发怎么"感知"它 | 违反的后果 |
|---|---|---|---|---|
| L1 法律 | 全国人大及其常委会 | 所有组织 | 内训必考、入职签保密协议 | 行政处罚直至刑事责任 |
| L2 监管规章 | 国家金融监督管理总局、人民银行等 | 银行机构 | 需求文档里"依据监管 XX 要求"的出处 | 机构被罚、业务叫停、评级下调 |
| L3 行业标准 | 人民银行、国家密码管理部门、国家标准体系 | 技术与产品 | 架构评审 checklist、等保/密评整改单 | 通不过测评，系统不能上线 |
| L4 行内制度 | 本行 | **你自己** | 提测门禁、代码扫描、堡垒机审批、变更窗口 | 通报、扣绩效、回收权限、追责 |

**一句话记忆**：L1~L3 决定"银行为什么要这么做"，L4 决定"你今天提交这段代码会不会被打回"。
面试时先讲这个分层，再说"实际约束日常开发的是行内制度，而行内制度是 L1~L3 的落地翻译"，这个认知就超过多数候选人。

> 注意：JR/T、GM/T 的**具体标准编号**各版本变动较多，本篇一律用描述式表述。
> 你要背住的结构事实只有三个：`GB/T 22239` 是等级保护基本标准（俗称等保 2.0）、
> SM2/SM3/SM4 是国产商用密码算法、"密评"是商用密码应用安全性评估。其余说"以本行现行制度与现行有效版本为准"。

## 二、网络与区域隔离：物理上不允许你犯很多错

银行不是"靠自觉"做安全的，第一道防线是**网络分区**——很多违规操作在网络上根本不通。

```
        互联网 / 合作机构
                │
        ┌───────▼────────┐   边界防护：防火墙 + WAF + IPS
        │ 外联区 / DMZ   │   ← 渠道前置机、对公对私外联前置、API 网关入口
        └───────┬────────┘   ← 只开放白名单端口与白名单源地址
                │  （单向受控，禁止从 DMZ 主动访问生产内网）
        ┌───────▼────────┐
        │   生产网       │   ← 核心/账务/支付/渠道后端，DB 与应用同区
        │  （最严）      │   ← 运维只经堡垒机进入；禁止直连办公网
        └───────┬────────┘
                │ 跨网数据交换：走审批 + 专用交换区/光闸/摆渡
        ┌───────▼────────┐        ┌────────────────┐
        │  开发测试网    │◀──────▶│  办公网        │
        │ 测试库/脱敏数据│ 禁止互 │ 邮件/上网/内部 │
        └────────────────┘  接    └────────────────┘
```

| 区域 | 允许放什么 | 典型边界管控 | 开发最容易踩的坑 |
|---|---|---|---|
| 生产网 | 真实业务系统与真实客户数据 | 只能经堡垒机运维；应用账号最小权限；出站全禁 | 想"临时"从本地直连生产库看数据 → 违规 |
| 外联区 / DMZ | 前置机、渠道接入、报文转换 | 与生产网之间只开必要端口；报文经清洗与验签 | 把外部回调直接打到生产服务上 |
| 开发测试网 | 代码、CI、测试库 | 与生产网**逻辑或物理隔离**；出网需审批 | 用从生产导出的真实客户数据建测试库 |
| 办公网 | 开发机、办公终端、内部系统 | 终端管控、DLP、禁用外设、上网行为审计 | 用办公邮箱/网盘传代码或数据 |

三个必背概念（人话版）：

- **前置机**：放在 DMZ 里、专门替内网跟外部机构"接头"的机器。外部只允许看到它，它再把请求按白名单转发进内网。
  银行接第三方支付、银联、代收付时几乎都是"专线 + 前置机"模式，所以你会看到大量报文转换、加验签的代码住在这一层。
- **跨网数据交换审批**：任何"把数据从一个网搬到另一个网"的动作（导文件、同步表、上传补丁）都要走流程：
  申请 → 说明数据范围与用途 → 审批 → 通过指定交换通道传输 → 留痕。**口头同意不算数**。
- **开发环境的数据库来源**：合法来源只有三种——① 手工构造的仿真数据；② 由生产数据经**脱敏加工**后下发；
  ③ 已有合规测试库。直接从生产 `mysqldump` 拖一份到本地，是最典型的红线事故。
  详见 [10-银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)。

**面试加分答法**：被问"你怎么理解银行的安全"时，别说"要加密要防注入"这种通用话，
说"银行安全的第一层是**结构性隔离**——网络分区、账号最小权限、变更走审批，制度设计上不信任任何单点个人，包括开发本人"。

## 三、身份与权限：三员分立是必考点

### 3.1 最小权限与特权账号

- **最小权限**（need-to-know / least privilege）：只给你完成当前工作所必需的最小权限，且**按需申请、按期回收**。
  默认拒绝，不是默认可用。
- **特权账号**：DBA 的库管理员账号、root、应用运维账号等"能绕过常规控制"的账号。管理要点：
  集中托管（不落地在个人手里）→ 使用前申请、用后归还 → 全程录屏/命令留痕 → 定期改密与轮换 → 名单可盘点。
- **双因素登录**（2FA）：密码之外再加一件东西（动态口令、USB Key、生物特征）。远程运维、生产访问普遍强制。

### 3.2 三员分立（高频面试点）

**人话**：把"一个超级管理员能干所有事"拆成三个人互相牵制。

| 角色 | 负责 | 明确不能做 |
|---|---|---|
| **系统管理员** | 装系统、配参数、建账号、发版操作 | 不能改安全策略、不能看审计日志 |
| **安全管理员** | 配权限策略、定安全规则、审批授权 | 不能执行业务/运维操作、不能删审计记录 |
| **审计管理员** | 查日志、出审计报告、追操作责任 | 不能配权限、不能做运维 |

**为什么必须分离**：如果同一个人既能改配置、又能改策略、还能清日志，那他做的任何违规操作都可以**自我抹除痕迹**，
整个控制体系形同虚设。三员分立的目的就是把"做事 / 授权 / 留证"三个环节交给不同人，形成互相制约，
让"谁能证明我没干过这件事"有一个不依赖本人的答案。这是内部控制（Internal Control）思想在 IT 上的直接体现。

⚠️ 本项目**没有实现三员分立**：所有配置与权限判断集中在开发者一人手里。这是学习项目的固有形态，不是缺陷，
但面试时千万别说"我项目里做了权限分离"——你说的是 Spring Security 的**业务角色**（普通用户/管理员），
那是应用层鉴权，与运维侧"三员分立"是两件完全不同的事（见 [../09-安全与设计模式/03-SpringSecurity微服务两层安全模型.md](../09-安全与设计模式/03-SpringSecurity微服务两层安全模型.md)）。

### 3.3 堡垒机、双人复核与账号生命周期

- **堡垒机**（运维安全审计系统 / 跳板机）：所有生产操作必须先登录堡垒机，再由它代理到目标机器。
  作用有三：统一认证 + 细粒度授权 + **全程命令留痕（含录屏）**。没有堡垒机权限就碰不到生产。
- **生产操作双人复核**：高危动作（改数据、跑批重跑、参数下发、账号授权）要求"一人操作、一人复核"，
  两人都留痕。落到系统上往往就是"提交人 ≠ 审批人"的字段校验——写这类校验时不要图省事允许自审自批。
- **账号生命周期（入转调离）**：入职开通、转正复核、转岗调整、离职当日回收。银行对**离职回收**尤其敏感，
  因为离职人员账号能访问生产是重大隐患。系统侧通常要做"人员状态变更 → 自动触发权限回收"的联动，
  这往往是一个跨系统数据同步需求（对应 [01-银行IT体系与岗位全景](./01-银行IT体系与岗位全景.md) 里的"管理支撑类系统"）。

## 四、个人金融信息保护（重点：能对应到写代码）

### 4.1 什么是"个人金融信息"，怎么分级

**人话**：客户在金融机构办理业务过程中产生的、能识别到具体个人并反映其金融状况的信息。
监管按**泄露后的危害程度**把它分成三档（表述以现行有效版本为准）：

| 档次 | 常见表述 | 典型内容 | 泄露后果 | 工程上的默认要求 |
|---|---|---|---|---|
| **最高敏感级** | 一般称"信息中涉及账户密码与银行卡认证信息的那一档" | 银行卡磁道/芯片信息、验证码、CVV2、卡片有效期、密码、动态口令、私钥 | 可直接盗刷、资金损失 | **禁止明文存储、禁止展示、禁止日志输出、禁止在测试环境出现** |
| **中级** | 可直接识别主体 + 金融状况 | 身份证号、手机号、账号、存款/贷款金额、交易流水、征信信息 | 精准诈骗、身份冒用 | 展示脱敏、按需授权、传输加密、访问留痕 |
| **最低级** | 单独无法识别、需组合使用 | 内部机构号、产品编号、脱敏后的统计标识 | 影响较小 | 仍不得批量外发 |

**判断口诀**：能不能"直接盗走钱"→ 最高；能不能"直接找到这个人并知道他有多少钱"→ 中；否则→ 低。

### 4.2 展示脱敏 ≠ 存储脱敏（必考辨析）

| 维度 | 展示脱敏（掩码） | 存储脱敏 / 加密 |
|---|---|---|
| 目的 | 让**人眼**看不到完整值，防肩窥、防截图、防页面源码 | 让**拿到文件/备份/磁盘的人**也读不到明文 |
| 手段 | 正则替换：`138****5678`、`622202********1234` | 对称加密（如 SM4）落库，密钥托管在 KMS/加密机 |
| 数据本身 | 数据库里仍是**完整明文**，只在渲染层遮蔽 | 数据库里存的是密文/摘要 |
| 能否还原 | 后端逻辑仍可拿到明文 | 需要密钥才能解密 |
| 防的是谁 | 前台使用者、运维看数据 | 拖库、备份介质丢失、内部人员直接查库 |

**误区核心**：只在 VO 层做了 `138****5678` 就宣称"满足个人金融信息保护"，是面试与入职都会被当场戳穿的错误。
DBA 直连库、导一份备份、开一次慢 SQL 日志，明文照样全裸。真正的合规是"**展示掩码 + 存储加密 + 访问留痕 + 权限最小化**"的组合。

### 4.3 落到代码上的七条硬要求

| # | 要求 | 写代码时具体做什么 | 违反的典型样子 |
|---|---|---|---|
| 1 | 采集最小必要 | 只问业务真的需要的字段；接口 DTO 不留"顺手传过来"的冗余字段 | 表单加了一堆"反正以后可能用到"的信息 |
| 2 | 展示脱敏 | 出参统一走脱敏组件（切面/序列化器），不要每个接口手写 | 前端掩码、后端接口仍返回全量明文 |
| 3 | 传输加密 | 全链路 HTTPS/TLS；跨机构走专线 + 报文加密 | 内网图省事用明文 HTTP 传卡号 |
| 4 | 存储加密 | 敏感字段密文落库，密钥进 KMS/加密机，与数据分离 | `varchar` 明文存身份证 |
| 5 | 日志禁打明文 | 打日志前统一过脱敏；`toString()` 不含敏感字段；接日志采集再兜一层 | `log.info("请求参数：" + req)` 一把梭 |
| 6 | 测试数据不用生产真数据 | 必须脱敏或仿真；导出脚本内置脱敏步骤 | dump 生产库回灌测试环境 |
| 7 | 数据导出审批 + 可追溯 | 导出走审批流、限量、加水印/编号，导出行为留痕 | 随手 `SELECT *` 导出 xlsx 拷走 |

最后还有**数据销毁**：介质报废要消磁/物理破坏，逻辑删除的数据在保留期后要有真正的清理任务，
"永久留在归档表里"同样不合规。

### 4.4 本项目对照：PiiMasker 做到了哪一层

`ai-cs-chat/src/main/java/com/aics/chat/util/PiiMasker.java:22` 是 PII（Personally Identifiable
Information，个人可识别信息）**掩码组件**，覆盖能力如下：

| 能力 | 实现位置 | 规则 | 说明 |
|---|---|---|---|
| 手机号掩码 | `PiiMasker.java:33` 正则 + `:89` 替换 | 保留前 3 后 4，`138****5678` | 中间 4 位遮蔽 |
| 身份证掩码 | `:45` + `:87` | 保留前 6（区划码）后 4，中间 8 位出生日期遮蔽 | 最先执行（18 位最长） |
| 银行卡掩码 | `:56` + `:98` `maskBankCards` | 13~19 位，**且必须通过 Luhn 校验**才遮蔽 | 前 6 为 BIN 发卡行标识 |
| 邮箱掩码 | `:63` + `:90` | 本地部分整体替换为 `***`，域名保留 | |
| 地址门牌掩码 | `:70` + `:91` | "X号/号楼/院/栋"前数字遮蔽 | 针对"望京街道***号院" |
| 误伤防护 | `:33`/`:45`/`:56` 的 `(?<!\d)…(?!\d)` | 定长数字正则前后加零宽数字边界 | 20 位订单号不再被切成"身份证+手机号" |
| Luhn 校验 | `:115` `luhnValid` | 从右往左隔位乘 2、>9 减 9，和 % 10 == 0 | 用校验位区分"真卡号"与"普通长数字" |

**真实调用点（这是最容易说错的地方，我 grep 过）**：`AgentTraceRecorder.java:85-86`（智能体执行轨迹的
输入/输出摘要**落库前**掩码）、`SecurityAuditRecorder.java:71`（安全审计事件摘要落库前掩码 + 截断）、
`VisionChatServiceImpl.java:160`（视觉模型生成的描述返回前掩码）。也就是说它对应第六节清单的第 5 条
"**日志与审计留痕里不得出现明文敏感字段**"，而**不是**"全链路输出掩码"。

注意它的定位：**这是落库/输出前的展示层掩码**，不是"存储加密"。
算法与正则的工程原理见 [../11-数据结构与算法/07-字符串匹配-Trie与PII脱敏.md](../11-数据结构与算法/07-字符串匹配-Trie与PII脱敏.md)。

⚠️ **本项目在个人信息保护上的真实缺口**（面试时主动说，比被问出来强得多）：

1. 数据库字段仍是**明文存储**，无字段级加密、无 SM4、无 KMS/加密机；
2. 无**密评**（商用密码应用安全性评估）相关能力，密钥以配置项/环境变量形式存在；
3. 无**三员分立**与审计管理员角色，运维与开发是同一人；
4. 掩码只覆盖"审计/轨迹摘要落库前"与视觉输出这几处，**不是全链路**：接口出参没有统一脱敏序列化器，
   业务日志（如 `log.info("创建支付流水: orderNo=..., amount=...")`）也没有统一过掩码组件；
5. 无测试数据脱敏流水线，测试数据由人手工构造；
6. 无数据保留期与销毁任务。

形态对照结论：**我能讲清"展示脱敏与存储脱敏的区别，并且知道自己项目只做到了前者"**——
这是一句诚实且有信息量的回答，比"我的项目做了脱敏所以懂合规"可信得多。

## 五、密码应用与国密改造

### 5.1 三种国密算法各解决什么

**国密 = 国家商用密码算法**，由中国自主设计，金融行业的存量系统正在按要求逐步替换国际算法。

| 算法 | 类型 | 解决什么问题 | 对应替换的国际算法 | 银行里的典型用法 |
|---|---|---|---|---|
| **SM2** | 非对称（椭圆曲线） | 加密小数据 + **数字签名/验签** + 密钥协商 | RSA / ECDSA | 报文签名、证书体系、登录挑战应答 |
| **SM3** | 摘要（哈希） | 数据完整性校验，"改了就能发现" | SHA-256 | 签名前的摘要、文件完整性、口令存储的加盐迭代（口令本身还应加慢哈希） |
| **SM4** | 对称分组 | 大数据量**加密**（快） | AES | 字段落库加密、报文正文加密、传输通道加密、文件加密 |

记忆法：**签名用 SM2，摘要用 SM3，加密用 SM4**——"2 签名、3 摘要、4 加密"。

### 5.2 密钥分层与加密机

```
          ┌──────────────────────────────┐
          │  主密钥 MK / 根密钥 (LMK)   │  ← 永不出加密机（HSM），人工分片保管
          └──────────────┬───────────────┘
                         │ 派生/加密保护
          ┌──────────────▼───────────────┐
          │  工作密钥 (KEK / 交易密钥)   │  ← 定期轮换，由主密钥保护
          └──────────────┬───────────────┘
                         │ 会话期临时派发
          ┌──────────────▼───────────────┐
          │  会话密钥 (Session Key)      │  ← 一次一密，用完即废
          └──────────────────────────────┘
```

- **HSM（加密机，Hardware Security Module）**：专门做密码运算和密钥保管的硬件，密钥**只进不出**，
  应用只能调它的接口让它"帮我加密/帮我签名"，永远拿不到密钥本身。银行的核心、ATM、支付系统都依赖它。
  开发视角：你要调 HSM 的 SDK/网络接口，而不是在 Java 里 `new SecretKeySpec(bytes)`。
- **为什么分层**：主密钥泄露影响太大 → 所以它不出机器；工作密钥要轮换 → 所以它被主密钥保护；
  会话密钥量最大、生命周期最短 → 所以用完即弃，即使泄露影响面也只有一笔会话。

### 5.3 报文 MAC、签名与证书

- **MAC（消息认证码）**：对称密钥 + 摘要算法算出的一段"校验值"，接收方用同一把密钥能验证
  "报文没被改过、且确实是对端发的"。银行老式报文（如 8583 系列金融报文）大量使用 MAC。
- **签名**：非对称版本，私钥签、公钥验，额外提供**抗抵赖**（签了就不能说不是我）。
- **数字证书**：把"公钥属于谁"这件事由 CA（证书认证机构）背书，形成 PKI 体系。银行与外部机构互联
  几乎都靠证书互信，证书有有效期、序列号、可被吊销——所以你会看到"证书到期"这类生产风险项。

### 5.4 国密落地在哪些位置

| 位置 | 落地形式 | 开发要做的改动 |
|---|---|---|
| 渠道接入（网银/手机银行/开放 API） | 国密 TLS 双向认证、报文 SM2 签名 + SM4 加密 | 换 SDK、加验签分支、算法协商兼容期 |
| 行内系统间调用 | 报文签名 + 敏感字段 SM4 加密 | 公共加解密组件、密钥统一走 HSM |
| 数据库存储 | 敏感列密文；密钥与数据分离 | MyBatis TypeHandler / 加解密拦截器 |
| 文件与报送 | 传输前加密 + 签名，防篡改防冒充 | 生成任务与校验任务成对开发 |

**改造的现实难点**（面试聊到这里会很加分）：国密替换不是"换个算法常量"，而是要处理**对端还没换**的兼容期，
所以真实项目里常见"算法可配置 + 双栈并行 + 灰度切换 + 对账验证"四件套，工程量和纯技术难度无关，全是协同成本。

### 5.5 本项目对照

`ai-cs-pay/src/main/java/com/aics/pay/channel/UnionpaySignature.java` 是可参考的**签名/验签骨架**：

| 环节 | 位置 | 实际做法 |
|---|---|---|
| 组装待签名串 | `UnionpaySignature.java:37` `buildContent` | 排除 `sign`/`signMethod`，非空字段按**键名升序**拼 `k=v&k=v` |
| 签名 | `:47` `sign` | `Signature.getInstance("SHA256withRSA")` + Base64 |
| 验签 | `:60` `verify` | 同规则重组原文后用对端公钥验证；异常一律返回 `false`（宁可拒绝） |
| 证书装载 | `:77` `loadSignCert` / `:91` `loadVerifyPublicKey` | PKCS12 取私钥与证书，X.509 `.cer` 取验签公钥 |
| certId | `:130` `SignCert.certId()` | 证书序列号十进制串，随报文上送供对端定位证书 |

⚠️ 关键诚实点：本项目用的是 **SHA256withRSA（国际算法）**，**不是 SM2/SM3/SM4**；私钥直接从本地 PKCS12 文件读，
**没有加密机、没有密钥托管、没有轮换机制**。所以准确表述是"我实现过非对称签名验签的通用流程，理解把它换成国密
时需要改算法标识、并把密钥取用改成 HSM 调用"，而**不是**"我做过国密改造"。

## 六、应用安全开发：写代码的人要背的清单

这一节是你入职后真正常被安全评审打回的原因清单。每条都对应"评审单上会怎么写"。

| # | 控制项 | 具体要求（可执行） | 评审常见打回理由 |

| 1 | 身份认证与会话 | 统一认证入口；会话有绝对超时 + 空闲超时；登出即失效；凭证不落 URL | Token 永不过期、可无限续期 |

| 4 | 注入防护 | 一律参数化查询；MyBatis 用 `#{}`，`${}` 必须白名单校验；动态排序/表名单独枚举 | 拼接 SQL 处理排序字段 |

| 6 | 文件上传 | 校验真实类型（看魔数不看扩展名）、重命名、存非 web 目录、大小上限、下载走鉴权 | 用原始文件名落盘 |
| 7 | 错误信息 | 对外返回错误码 + 可读文案；**不返回堆栈、SQL、内部 IP、组件版本** | 500 页面带堆栈 |
| 8 | 防暴力 | 登录/短信/支付密码等做次数限制、锁定、验证码；失败也要限频 | 验证码可跳过、限制只在前端 |
| 9 | 传输安全 | 明确最低 TLS 版本、禁用弱套件、客户端校验证书（不"信任所有"）、必要时双向证书 | `X509TrustManager` 全放行 |
| 10 | 依赖治理 | 组件准入清单 + 漏洞扫描 + SCA 门禁；已知高危版本不允许进生产 | pom 随手加一个"小工具"库 |
| 11 | 代码审计与安全测试 | 静态扫描（SAST）+ 动态扫描（DAST）+ 渗透测试；高危问题**上线门禁** | 安全测试没做完先发版 |
| 12 | 敏感数据在内存与日志 | 不在 `toString()`、异常消息、日志里带明文敏感字段 | 排错时把整段报文打进日志 |

## 七、日志、审计与追溯

**操作日志五要素**（缺一即"不可追溯"）：

| 要素 | 内容 | 落库字段示例 |
|---|---|---|
| 谁 | 操作主体（工号/账号，不是 IP） | `operator_id`、`operator_name` |
| 何时 | 精确到毫秒、统一时区 | `operate_time` |
| 何地 | 哪个渠道、哪台终端、哪个节点 | `channel`、`client_ip`、`device_id`、`app_node` |
| 做了什么 | 业务动作 + 关键入参（脱敏后） | `action_code`、`biz_no`、`before_value` / `after_value` |
| 结果 | 成功/失败 + 错误码 + 流水号 | `result_code`、`trace_id` |

三个硬性要求：

1. **审计日志独立存储、与业务日志分离**。业务开发不能有任何删除/修改审计记录的权限——否则审计管理员这个角色就没意义了。
   常见做法：只追加（append-only）、异地/异库保存、定期归档并对归档件做完整性签名。
2. **留存期限**：不同法规与监管对日志、交易记录的留存年限要求不一致（多数以"年"为单位）。
   **具体年限以现行有效规定与本行制度为准**，本篇不给数字。
3. **异常行为审计**：大批量查询、非工作时间访问、越权尝试、频繁导出、离柜不锁屏等都会进审计规则，触发人工核查。
   开发侧的含义：你的系统要**预留可审计字段**（谁查了谁的什么），事后补埋点成本极高。

监管检查时的一句话逻辑："**这条数据在 X 时间被 Y 账号通过 Z 渠道改成了现在这样，审批人是 W**"——
如果你的系统能出这条证据链（业务流水 + 审计日志 + 审批记录 + `trace_id` 串联的调用日志），检查就过得去。
本项目已有 `trace_id` 全链路贯穿（见 [13-稳定性工程/08-oncall手册与故障响应.md](../13-稳定性工程/08-oncall手册与故障响应.md) 的同类思路），
这是可以迁移的"可追溯性"经验。

## 八、数据与生产安全红线（入职第一天要记住）

| 红线 | 为什么是红线 | 常见"我以为没事"的说法 |
|---|---|---|
| 生产数据**不落地**到个人设备 | 一旦离开受控网络就无法追回 | "我只导 100 条看看问题" |
| 不得私拷数据（U 盘/网盘/邮箱/IM/相册） | 外传即视为泄露事件 | "发给自己手机，回头再看" |
| 生产变更必须走审批与变更窗口 | 未审批变更是银行生产事故主因 | "只是一行配置，我直接改了" |
| 不得从办公网/开发网直连生产 | 结构性隔离，绕过即违规 | "网络策略临时开一下，马上关" |
| 不得在外部工具/公开渠道粘贴代码或数据 | 无法撤回，且进入第三方模型训练语料风险 | "问一下 AI 又没人知道" |
| 外部网络传输受限，代码只在受控仓库 | 源码本身即商业秘密 | "自己搭个私有仓库方便点" |
| 保密协议与竞业/离职承诺持续有效 | 离职后仍承担保密义务 | "都离职了还不能说吗" |
| 客户信息泄露可能触及刑事责任 | 侵犯公民个人信息是刑事罪名范畴 | "我又没卖，就是发给朋友看看" |

最后一行请当真：**客户信息泄露的后果不是"扣绩效"级别，可能是法律级别**。
这也是银行安全培训反复讲、看起来啰嗦的原因——它讲的不是技术，是你的个人风险。

## 九、初学者常见误区

| 误区 | 真相 |
|---|---|
| "安全是安全部门的事，我写好业务就行" | 安全部门定标准、做测评；**漏洞长在你的代码里**。SQL 注入、越权、明文打日志都是开发责任，评审打回也是打回你 |
| "上了 HTTPS 传输就安全了" | TLS 只保护**链路**。内网东西向流量常常仍是明文；端到端的敏感字段仍需应用层加密与签名；证书校验被写成"信任所有"等于白干 |
| "加了字段脱敏就满足个人金融信息保护了" | 展示掩码不防拖库。合规要求是分级 + 最小采集 + 存储加密 + 传输加密 + 日志管控 + 测试数据脱敏 + 导出审批 + 到期销毁的**组合** |
| "开源组件随便用，能跑就行" | 组件带漏洞、带协议风险、带供应链风险。银行要求准入清单 + SCA 扫描 + 高危版本门禁，一个 `fastjson` 就足够上重大安全事件榜 |
| "内网环境，密码存明文没关系" | 等保与密评都按"最坏假设"评估：假定边界已被突破。数据库、备份、日志是三个最常失守的地方 |
| "三员分立 / 双人复核是走形式，效率低" | 它的价值恰恰在**不信任任何单点个人**。事故追责与监管检查时，它保护的是你本人——留痕能证明"不是我改的" |
| "等保就是买几个安全设备" | 等保是"技术 + 管理"双体系，含定级、备案、建设整改、测评的完整流程，且要持续复评。设备只是其中一小块 |
| "国密改造 = 把算法名换成 SM4" | 难点在**密钥体系**（HSM 托管、分层、轮换）、对端兼容期、灰度与回退、改造后的对账验证 |

## 十、本篇速查表（面试前 3 分钟看这一张）

| 问题 | 一句话答案 |
|---|---|
| 规范体系分几层 | 法律 → 监管规章与指引 → 行业标准（JR/T、GM/T、等保 GB/T 22239、密评）→ 行内制度；天天约束我的是行内制度 |
| 网络怎么隔离 | 生产网 / 外联区 DMZ / 开发测试网 / 办公网四区，跨网交换必须审批走专用通道，办公网不得直连生产 |
| 三员分立是哪三员 | 系统管理员做事、安全管理员授权、审计管理员留证，三者不得兼任，目的是让人无法自证清白式地抹痕迹 |
| 个人金融信息分几档 | 按泄露危害分三档；账户密码与银行卡认证信息是最高档，禁止明文存储/展示/入日志 |
| 展示脱敏 vs 存储脱敏 | 前者防人眼，后者防拖库；只做掩码时数据库仍是明文 |
| 国密三件套 | SM2 签名与密钥协商、SM3 摘要、SM4 加密；对应替换 RSA / SHA / AES |
| 加密机干什么 | 保管密钥并代做密码运算，密钥只进不出，应用永远拿不到密钥本体 |
| 应用安全十条里最常被问的三条 | 越权校验（水平/垂直）、防重放（时间戳+随机数+签名）、参数化查询 |
| 操作日志五要素 | 谁、何时、何地、做了什么、结果 |
| 入职第一天最不能碰的三条线 | 生产数据不落地、不私拷数据、不未审批变更生产 |

## 十一、动手练习

1. **把脱敏做全**：在 `ai-cs-pay` 里挑一个会打业务日志的方法（例如支付流水创建处），
   把它的日志参数改造成"经过 `PiiMasker.mask(...)` 后输出"，并解释为什么这一步应该放在**日志框架的 Layout/Converter 层**
   而不是每个调用点手写（提示：漏一个调用点就是一次泄露）。
2. **补一个越权用例**：给订单查询接口写一个测试：用 A 用户的凭证查 B 用户的订单，断言返回 403/业务错误而不是数据。
   然后 grep 全仓，看哪些"按 ID 查询"的接口没做归属校验，列成清单（这就是安全评审要出的那张表）。
3. **把 RSA 换成国密的推演**：读 `UnionpaySignature.java:47`，写出"若对端要求 SM2+SM3"时的最小改动点清单
   （算法标识、证书类型/密钥算法、待签名串规则、依赖库、双栈兼容与灰度开关），并指出哪些改动**不需要**动业务代码。
4. **给本行制度写一条 checklist**：假设你是某银行的安全接口人，把第六节 12 条改造成"提测单必填 12 项"，
   每项写清"证据材料是什么"（截图 / 扫描报告 / 评审记录 / 渗透测试结论）。这个练习能直接用于面试"你会怎么落地"。
5. **画出你自己环境的分区图**：把本仓库的 MySQL / Redis / RocketMQ / Nacos / MinIO / 各服务端口
   对应到"生产网 / DMZ / 开发测试网"三区，标出银行环境下哪些连接会被边界策略直接拒绝（提示：办公网 → 生产 DB、DMZ → 生产 DB 直连）。
   对照 [06-网络金融与电子渠道](./06-网络金融与电子渠道.md) 理解为什么渠道侧只能到前置机。
