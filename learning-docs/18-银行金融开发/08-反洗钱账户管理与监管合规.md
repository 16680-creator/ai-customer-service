## 一、监管全景：谁在管什么

```
      法律层（全国人大）
   反洗钱法 · 反电信网络诈骗法 · 个人信息保护法 · 数据安全法 …
                       │ 授权与要求
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  金融监管机构     人民银行        外汇/证监等其他条线
  （行为监管、    （货币政策、支付清算、  （跨境、证券相关）
   机构监管）      反洗钱牵头、征信业管理）
        │              │
        └──────┬───────┘
               ▼
        银行机构：把监管要求翻译成「制度 + 系统功能 + 岗位流程 + 报送」
               │
               ▼
        科技部门：字段 / 校验 / 名单库 / 规则引擎 / 跑批 / 报表 / 留痕 ← 你的活
```

| 合规主题 | 主管条线（人话） | 对系统的直接影响 | 详见 |
|---|---|---|---|
| 反洗钱（AML） | 人民银行牵头，行内设反洗钱牵头部门 | 客户身份与交易数据全量归集、名单筛查、规则引擎、案例管理、报送 | 本篇 §2 §3 |
| 结算账户管理 | 人民银行账户管理条线 | 开户资料、核准/备案、账户状态机、久悬、管控冻结 | 本篇 §4 |
| 支付结算纪律 | 人民银行支付条线 + 清算组织 | 票据、退回、清算对账、不得垫付 | 本篇 §5、[04](./04-支付清算体系与报文.md) |
| 征信 | 人民银行征信管理条线 | 授权查询、报文报送、异议处理 | 本篇 §6 |
| 监管报送与数据治理 | 多口径并行（财务/统计/检查分析等） | 数仓 + 指标口径 + 血缘 + 补录修正流程 | 本篇 §7 |
| 消费者权益保护 | 金融监管条线消保要求 | 适当性、双录、年化利率展示、投诉工单与时限 | 本篇 §8 |
| 业务连续性 | 监管对重要信息系统要求 + 等保密评 | 灾备、切换演练、RTO/RPO、事件报告 | 本篇 §9、[07](./07-银行业信息安全管理规范.md) |

**核心认知**：银行里"合规需求"不是可选项，而是**优先级最高的必做项**，且通常带硬性截止日期。
它的产品负责人往往是合规/运管部门，需求描述方式是"依据监管要求，系统需支持 XXX"，
你需要具备的能力是**把这句话拆成字段、任务、报表和留痕**。

## 二、反洗钱：四项法定义务 + 名单筛查

### 2.1 框架（人话版）

**反洗钱（AML, Anti-Money Laundering）**：防止犯罪分子把非法所得"洗"成看似合法资金的一整套制度。
手段不是"抓人"，而是**让非法资金在金融体系里留下可分析的数据痕迹**，并把可疑线索报给国家监测分析机构。
因此银行的角色本质是**数据采集器 + 初步分析器**——这也解释了为什么它对数据质量要求极高。

机构的四项基础义务（开发必须能一口报出）：

| 义务 | 内容 | 开发落点 |
|---|---|---|
| ① 客户身份识别（KYC） | 开户与业务办理时确认"你是谁"，含**受益所有人**识别；高风险情形强化尽职调查 | 客户信息模型的必填校验、证件联网核查、影像资料、持续识别（信息过期提醒） |
| ② 客户风险等级划分与再审核 | 按客户身份、地域、业务、交易特征划分风险等级，并**定期复评** | 打分模型/规则表、等级字段、到期复评跑批、等级变化触发管控 |
| ③ 身份资料与交易记录保存 | 业务关系存续期间的身份资料与交易记录须完整保存，年限以现行规定为准（常说不少于 5 年量级） | 归档策略、不可篡改存储、按客户/账号可检索的索引 |
| ④ 大额交易与可疑交易报告 | 达到门槛的交易按时报送；可疑的由系统识别 + 人工分析后报送 | 采集→清洗→规则/模型→案例→报文，全套见 §3 |

### 2.2 客户身份识别（KYC）里开发会被问到的细节

- **KYC**（Know Your Customer，了解你的客户）：不只是"有身份证复印件"，而是"识别并持续验证"。
- **受益所有人**（Ultimate Beneficial Owner, UBO）：最终实际控制或受益的**自然人**。
  企业客户必须穿透股权结构找到自然人，防止用空壳公司藏身份。开发侧的坑：股权链路可能多层、
  需保存"穿透过程数据"（当时算出的结论 + 依据），事后要能重算。
- **代理办理**要同时登记代理人与被代理人身份；**一次性金融服务**（不特定客户来办一笔业务）也要识别。
- **持续识别**：证件到期、客户信息变更、法人被更换 → 都要触发再识别任务。这是一个典型的"跑批 + 提醒 + 管控"三件套需求。

### 2.3 大额交易与可疑交易（门槛只给量级）

**大额交易**：客观、可程序化判定，"够数就报"，无需主观分析。常见判定维度（**具体数值以现行有效的
《金融机构大额交易和可疑交易报告管理办法》为准，下面只是帮你建立量级感，别当条文背**）：

| 交易类型 | 门槛量级（人民币） | 判定要点 | 开发实现要点 |
|---|---|---|---|
| 现金收支（存/取/结售汇/现钞兑换/现金汇款等） | **万元级**（常说 5 万元及以上；外币等值万美元级） | 同一客户、**当日累计** | 必须按"客户 + 交易日"聚合，而不是按单笔判断 |
| 非自然人（单位）账户款项划转 | **百万元级**（常说 200 万元及以上） | 当日单笔或累计 | 同一客户多账户、多渠道的累计口径要打通 |
| 自然人账户**境内**款项划转 | **十万元级**（常说 50 万元及以上） | 当日单笔或累计 | 需含转账、汇款等各类渠道 |
| 自然人账户**跨境**款项划转 | **十万元级以下一档**（常说 20 万元及以上，外币等值更低） | 跨境维度单独判定 | 跨境标志、币种折算（折算汇率来源与生效日必须统一） |

三条工程陷阱（面试讲得出来就是加分项）：

1. **"当日累计"是合规口径的日切**，它的零点可能与业务日切、自然日不一致（见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 的日切概念）。
   跨日、冲正、退款、当日撤销是否计入累计，必须在需求阶段就要书面口径，不能自己猜。
2. **多系统、多入口**：柜面、手机银行、网银、代收付、ATM 都产生交易，累计只能在**归集之后**做，
   所以任何一条链路漏采集 = 漏报，这是最典型的"数据质量问题演变成合规问题"。
3. **币种与折算**：门槛是"人民币或等值外币"，汇率来源、取哪一天的中间价、精度与舍入方向，全部要固化成一个可追溯的折算函数。

**可疑交易**：没有金额门槛，看**特征**。既然大额可以漏报，可疑则可以"小额分散"绕过，
所以反洗钱**绝不只针对大额**（这是最普遍的误区）。典型特征类别：

| 类别 | 特征示例（描述性，不是条文） | 为什么可疑 |
|---|---|---|
| 结构异常 | 短期内分散转入集中转出 / 集中转入分散转出；快进快出、当日进出 | 典型过账、拆分规避门槛 |
| 身份不符 | 交易金额、频率与客户身份、经营规模、行业明显不匹配 | 账户被挪用或出借 |
| 规避行为 | 临近门槛金额的整数化拆分、频繁跨行转账、频繁现金存取 | 结构化交易（structuring）试探阈值 |
| 休眠异常 | 长期无交易账户突然大量进出 | 账户买卖或涉案 |
| 敏感方向 | 与高风险国家/地区、制裁名单、涉诈账户的往来 | 外部风险传导 |
| 现金密集 | 大量现金存取且无合理商业理由 | 切断电子链路 |

**报送流程与时限（量级）**：系统命中 → 生成可疑交易任务 → 分析岗人工研判（排除/上报）→ 确认可疑后**及时**报送，
常说时限在"工作日级"（如确认后 10 个工作日内）；大额常说"交易发生之日起 5 个工作日内"。
**确切天数以现行有效版本与本行制度为准。** 开发要知道的关键点：**报送是有时限的工作流**，
所以系统必须支持任务分派、超时提醒、退回补充、证据附件与审批链，而不是一个"报表导出"功能。

### 2.4 名单筛查

| 名单类型 | 来源 | 匹配方式 | 命中后怎么办 |
|---|---|---|---|
| 制裁名单 | 联合国安理会决议、国家有权机关发布的制裁/反恐名单 | 姓名/名称/证件号/别名/音译 + **模糊匹配**（拼音、缩写、异体字） | 冻结/止付 + 立即报告，通常**不得继续交易** |
| 监管要求关注名单 | 有权机关要求协查、涉诈、涉案名单 | 精确 + 模糊 | 按名单类型执行管控措施 |
| 内部黑灰名单 | 本行自建的欺诈、套现、违规代办、频繁误报排除名单 | 精确（证件号/账号/设备/手机号） | 加强审核或拦截 |
| PEPE/政要名单 | 外国政要及其关系人 | 姓名 + 关系人链路 | 强化尽职调查、高层审批 |

**工程难点全在"模糊匹配"上**：姓名"张三"与"張三 / zhang san / ZhangSan / ZHANG-SAN"要能命中，
同时不能把"张三丰"误命中成"张三"。所以真实系统会做：规范化（去空格、统一大小写与全半角、繁简转换）
→ 多语言转写 → 拼音/编辑距离/音似匹配打分 → 阈值分档（高分自动拦截、中分进人工、低分记录留痕）。
误报率控制是个调参活，需要**排除名单**（人研判过说不是的，下次不再重复告警）——这本身就是你的"规则命中结果缓存"设计题。
匹配算法基础可参考 [../11-数据结构与算法/07-字符串匹配-Trie与PII脱敏.md](../11-数据结构与算法/07-字符串匹配-Trie与PII脱敏.md)
里的 Trie / 编辑距离思路（**本项目未实现名单筛查，形态对照**）。

## 三、AML 系统怎么建（纯工程视角）

```
 业务系统（核心/柜面/网银/手机银行/ATM/代收付/信用卡）
        │ ① 数据采集：实时流水 + 日终批量 + 客户主数据
        ▼
 ┌────────────────┐
 │  贴源/明细层   │  ← 全量、可重跑、带来源系统与原始流水号
 └───────┬────────┘
         ▼ ② 清洗与标准化
 ┌────────────────┐  字段映射、码值统一、币种折算、客户号归一、
 │  数据质量闸门  │  去重、缺失与异常值拦截（不达标进差错池）
 └───────┬────────┘
         ▼ ③ 规则/模型计算
 ┌────────────────┐  大额：当日累计判定     名单：筛查命中
 │  规则引擎/模型 │  可疑：特征规则 + 评分卡  客户风险等级打分
 └───────┬────────┘
         ▼ ④ 案例管理（人工分析）
 ┌────────────────┐  告警分派 → 分析 → 排除/上报 → 审批 → 时限监控
 │  工作流 + 证据 │  全程留痕（谁看的、谁判的、依据什么）
 └───────┬────────┘
         ▼ ⑤ 报送与回执
   监管报文生成 → 发送 → 回执/退回 → 重报 → 归档
         │
         └──────────▶ ⑥ 后续处置：补报、回溯筛查（改规则后重跑历史）
```

| 环节 | 开发工作量类型 | 最容易低估的地方 |
|---|---|---|
| 采集 | 接口/文件/CDC 对接，幂等与重跑 | 各业务系统字段口径不一致；"同一笔交易在两套系统里各有一条"的去重 |
| 清洗 | ETL/数仓任务、码值映射表 | 客户号归一（一人多证件、企业多账户）；汇率与折算基准日 |
| 规则 | 规则引擎、可配置阈值、版本化 | 规则要能**改完只对以后生效**，且历史结果可追溯到当时用的规则版本 |
| 案例 | 工作流、权限、超时提醒 | 分析岗要求"一屏看完客户全貌"→ 关联查询很多，性能是真问题 |
| 报送 | 报文格式生成、加签、回执解析 | 重报/补报/撤销的场景状态机；报送失败必须可重试且不重复 |
| 回溯 | 历史数据重跑 | 算力和增量标记：改一次规则可能要重算数年数据 |

**AML 系统要向业务系统"要"的字段清单**（这就是为什么开户与交易接口不能少字段）：

| 类别 | 字段 | 为什么合规需要它 |
|---|---|---|
| 主体 | 客户号、证件号码/类型、客户名称、统一社会信用代码、风险等级 | 一切累计与穿透的主键 |
| 对手方 | 交易对手名称、账号、开户行（行外大额支付行号）、对手方客户号（若本行客户） | 判断"集中转入分散转出"等结构特征 |
| 交易本质 | 金额、币种、方向、**用途/附言**、业务类型码、交易方式码 | "用途"是判断合理性的关键文本，也最难拿全 |
| 渠道 | 渠道标识（柜面/ATM/网银/手机/代收付/开放 API）、终端号、设备指纹 | 同一客户跨渠道累计；识别异常设备聚集 |
| 网络 | IP、地理位置、基站/Wi-Fi 信息、登录设备变更事件 | 跨境识别、代理登录与账户买卖线索 |
| 经办 | 经办柜员号、授权人号、代理人证件、双人复核记录 | 内控追责；内部人员参与是重要风险信号 |
| 时间 | 渠道时间、核心记账时间、日切归属日 | 累计口径与"当日"的判定基础 |

**结论句（面试可直接说）**：*反洗钱合规能力 = 数据质量 × 规则有效性。*
系统规则做得再漂亮，只要某个新渠道上线时忘了上报交易明细，就会直接造成漏报——
这就是为什么银行要求"任何新增渠道/新增交易类型上线，反洗钱与报送系统必须同步评估"。
数据质量的具体治理手段见 [../14-数据工程与OLAP/08-数据质量与对账.md](../14-数据工程与OLAP/08-数据质量与对账.md)。

## 四、银行结算账户管理

### 4.1 单位（对公）银行结算账户：四类

| 账户类型 | 用途 | 数量规则 | 常见业务约束 |
|---|---|---|---|
| **基本存款账户** | 主办账户：日常转账结算 + **现金收付**、工资奖金支取 | **唯一**：一个单位只能开立一个基本户 | 未开立基本户不得开立其他账户；是核准/备案的重点对象 |
| **一般存款账户** | 借款转存、借款归还等结算 | 可多个，**不得与基本户在同一营业机构** | **不能支取现金**（这是最常被追问的点） |
| **专用存款账户** | 有特定用途需专项管理的资金（如专项资金、保证金） | 按用途开立 | 按规定的用途使用，通常有限支/审批要求 |
| **临时存款账户** | 临时机构、临时经营活动、注册验资等 | 有**有效期** | 到期须撤销或延期 |

**"基本户唯一性"的工程含义**：开户校验不能只看本机构，必须**全行范围**（甚至跨机构、跨渠道）判重；
若同时受理两条开户申请，唯一性就靠数据库唯一约束 + 锁来保证，这是一个典型的
"业务规则最终落到唯一索引 + 并发控制"的场景（参考
[../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md)）。

### 4.2 核准制 / 备案制 与开户流程变化

- **核准制**：账户需经人民银行核准（核发开户许可/核准件）后方可正式使用。
- **备案制**：银行自行办理后向监管系统报备即可。
- 演变方向：**企业银行账户开户许可已取消、改为备案管理**（属"放管服"改革），
  落地细节与例外情形（哪些账户仍属核准类）以现行有效规定与本行制度为准。
- **对开发的真实影响**（面试若被问"政策变了系统要改什么"，答这五条）：
  1. 开户流程少了"等核准件"环节 → 状态机要新增/合并状态，且**存量在途申请**要处理；
  2. 账号可用时点前移 → 上下游（代发、代收、贷款放款）校验逻辑要跟着放宽或加二次校验；
  3. 报送口径变化：从"核准结果回执"改为"开户信息报备"，接口与报文要改；
  4. 合规责任从"监管事前把关"转为"银行事中事后自查" → 需要新增**核查与抽检功能**；
  5. 影像与资料留存要求提高（因为没有核准件兜底了），要能随时应对检查。

### 4.3 个人账户与反电诈

- **个人银行结算账户 I / II / III 类**：按**开立方式与实名强度**分档，功能与限额逐级收窄——
  I 类为全功能账户（须面对面核验），II/III 类可线上开立但限用途限额度。
  **具体限额数值以现行规定与本行制度为准。** 详细对比与渠道侧实现见 [06-网络金融与电子渠道](./06-网络金融与电子渠道.md)，本篇不重复展开。
- **账户实名与联网核查**：开户时通过权威数据源核验身份证件真实性（姓名 + 号码一致性），
  核查结果、返回码、核查时间必须留痕；核查不通过不能继续开立。开发要点：**联网核查是外部依赖，必须设计超时、
  失败重试、降级与人工复核路径**，不能让它成为开户链路的单点。
- **账户变更与撤销**：名称/证件信息变更、法定代表人变更、销户；撤销前要校验余额为零、无未了结业务
  （未归还凭证、在途代收付、签约关系未解约）。这类校验是典型的"跨系统一致性"问题，
  常见做法是"逐条前置检查 + 检查项清单落库 + 允许登记例外并审批"。
- **久悬账户**（长期不动户）：符合"长期未发生收付活动且无欠银行债务"等条件的单位账户，
  银行应通知客户办理销户；逾期未办的按制度转入**久悬未取专户**管理，继续计息/不计息与提取流程按行内规定执行。
  开发侧含义：需要**定期识别 → 通知 → 状态迁移 → 单独台账 → 提取时加强审核**的完整闭环，通常是一个日终跑批任务。

### 4.4 反电信网络诈骗（《反电信网络诈骗法》）下的账户管控

**反电诈**：电信网络诈骗里，银行账户与支付账户是"资金转移"的关键通道，因此法律把大量义务压到了银行和支付机构身上。
开发会遇到：

| 义务 | 系统落地 |
|---|---|
| 开户审核与风险分级 | 开户前问询与用途登记、异常开户识别（同一人多次开户、异地集中开户）、拒绝开户并留痕 |
| 涉诈名单防控 | 涉案/涉诈账户与人员名单实时筛查，命中即拦截 |
| **紧急止付** | 接有权机关指令后**分钟级**冻结账户或止付资金；系统须支持高优先级指令实时下发与回执上报 |
| 账户管控与限制 | 非柜面交易限额下调、暂停非柜面业务、只收不付/不收不付等状态位组合 |
| 异常交易监测 | 与设备/IP/收款方聚集度结合的风控模型；对公账户"快进快出" |
| 受害者劝阻 | 可疑转账前弹窗、延时到账、人工外呼工单 |
| 惩戒与申诉 | 被惩戒人员的开户限制名单，及"解除惩戒"的工单流程 |

技术要点：**"管控状态"是一个多状态位的组合模型**（不冻结 / 只收不付 / 不收不付 / 限额 / 暂停某渠道），
并且要在核心、渠道、支付三条链路**同步生效**——这就是一个"状态一致性 + 实时下发"的经典题目
（可参考 [../04-中间件/08-RocketMQ事务消息与死信队列.md](../04-中间件/08-RocketMQ事务消息与死信队列.md) 的思路）。
**切记**：止付类接口幂等性必须极强（重复指令、乱序指令、部分成功），否则会造成资金误冻结，属重大生产事件。

## 五、支付结算纪律

《支付结算办法》体系的三条基本原则（**这三句是行内培训的原话，可以背**）：

1. **恪守信用，履约付款**；
2. **谁的钱进谁的账，由谁支配**；
3. **银行不垫款**。

| 票据 | 出票人 | 付款人（谁给钱） | 常见使用场景 |
|---|---|---|---|
| **银行汇票** | 银行（申请人交存后由银行签发） | 银行 | 异地购货、先款后货，见票即付 |
| **商业汇票**（分银行承兑 / 商业承兑） | 企业 | 承兑人（银行或企业） | 供应链账期，可背书转让、贴现 |
| **银行本票** | 银行 | 银行 | 同城结算，信用度高 |
| **支票** | 企业/个人（在银行有存款账户） | 出票人的开户银行 | 最常用的对公付款工具 |

**空头支票**（签发金额超过付款时在银行实际可用的存款额）：属禁止行为，
银行会**予以退票**，监管机构可**罚款**并记入不良信用记录，持票人还可要求赔偿
（**罚款比例、赔偿比例与金额下限以现行规定为准，本篇不给具体数字**）。
开发侧含义：签发校验、退票处理、违规客户台账、征信报送联动。

其他会被问到的纪律：

- **不得违规垫付**：银行不能用自己的钱替客户垫付款项。工程上意味着"账户余额不足时应失败退票，
  而不是记账成负余额"——这对应你在 §11 手写题里写的"扣减不能为负"。透支只在有明确授信产品时才允许。
- **结算时限**：各类支付工具都有法定的提示付款期限、银行处理时限与资金入账时点，
  系统里的到期提醒、退回、逾时报错都要按对应业务办法配置（具体天数以现行规定为准）。
- **银行不得挪用、滞留客户资金**："谁的钱进谁的账，由谁支配"意味着**支付机构备付金**
  （客户预付但尚未完成结算的资金）必须专户集中存管、不得挪用。
  这也是"二清"被禁止的原因，详见 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

## 六、征信

| 要点 | 内容 | 开发落点 |
|---|---|---|
| 采集与使用必须**授权** | 查询个人信用报告需取得信息主体本人书面/电子授权，且**用途限定**（贷款审批、信用卡审批、担保审查、贷后管理、异议核查等法定用途） | 查询接口必须携带授权凭证与查询原因；每次查询记录人、时间、原因、报告编号，并可被审计 |
| 报送准确及时 | 信贷业务数据按周期向征信系统报送（含借据、账户状态、逾期表现） | 数据抽取 + 报文生成 + 校验 + 反馈文件解析 + **错报更正重发**流程；这是一个典型批处理链路 |
| **异议处理** | 客户可对错误信息提出异议，机构须在规定时限内核查、更正并答复 | 工单流、留痕、与核心/信贷的数据回溯能力（要能证明当时报送的值从哪来） |
| 不良信息保存期限 | 自不良行为或事件**终止之日**起保存一定年限后删除（常说 5 年量级，**以现行有效规定为准**） | 到期清理任务 + 清理前可追溯归档；"终止之日"的口径要与业务确认（结清日？销户日？） |
| **"断直连"** | 非银行支付机构原先**直连**多家银行分别对账，被要求改为通过依法设立的**清算组织**（如银联、网联）统一转接，使资金链路透明可查 | 银行侧接口对手方与报文格式变化、对账文件来源从"机构一对多"变为"清算组织一对内多"；详见 [04](./04-支付清算体系与报文.md) |
| 大数据风控 vs 征信的边界 | "信用评分"若涉及采集、整理、保存、加工个人信用信息并对外提供，可能落入征信业务监管范围，需持牌或通过持牌机构开展 | 需求评审时要把"我们到底在做风控还是在征信"问清楚；涉及个人信用信息对外输出的一律拉合规评审 |

**"查询必须授权"是最容易被实习生和新人违反的一条**：为了方便排查问题去查了一个不该查的客户征信，
在没有授权记录的前提下就构成违规查询，且**每次查询都留痕、可被检查倒查**。记住：能查 ≠ 该查。

## 七、监管报送与数据治理：为什么银行有做不完的报表

新人常困惑"为什么这里每天在改字段、加校验、对数字"。因为报送是**多条并行、各有口径、都带考核**的硬任务：

| 报送方向（类别描述，不涉及具体系统代号） | 用途 | 数据特征 | 开发工作长什么样 |
|---|---|---|---|
| 财务与监管指标类 | 反映机构资本充足、流动性、资产质量等监管指标的计算基础 | 科目级汇总、时点值与期间值混合 | 取数逻辑改造、指标口径变更跟随、逐月/逐季跑批 |
| 检查分析类 | 供监管机构做非现场风险分析与穿透检查 | 明细级、字段极多、要求可勾稽 | 明细抽取 + 勾稽校验规则 + 疑点整改回传 |
| 金融基础数据统计类 | 存贷款、客户、账户等基础统计 | 全量 + 增量、按报文段组织 | 数据模型映射、变更检测、补录 |
| 反洗钱类 | 大额与可疑交易报告（见 §2 §3） | 交易流水 + 客户身份 + 研判结论 | 报送通道与回执处理 |
| 征信类 | 信贷信息报送与查询合规 | 借据与表现期数据 | 批量报文 + 反馈更正 |
| 行内管理报表 | 条线经营、绩效考核、内部风险 | 口径五花八门 | 需求变更最频繁的一类 |

三条铁律（做过报送的人会深表认同）：

1. **口径必须唯一**。同一个"贷款余额"在财务口径、监管口径、绩效考核口径下可能不同；
   一旦各处各算，就永远对不平。工程做法：指标定义进**指标字典**，取数逻辑集中在一处（数仓层/指标服务），
   报表只引用不重算。参考 [../14-数据工程与OLAP/03-数仓分层与指标口径.md](../14-数据工程与OLAP/03-数仓分层与指标口径.md)（若与本模块冲突，以行内口径为准）。
2. **数据血缘必须能追**。监管问"这个数字从哪来"，你要能从报表单元格一直追到某张表的某几条记录，
   再追到业务系统的一笔交易。这要求任务有**运行批次号、抽取时间、来源系统、记录主键**四件套。
3. **补录与修正必须有流程**。报送错了不能改数据库了事，要走"发现 → 登记差错 → 分析原因 → 修正 → 重报 → 留痕"。
   所以报送系统天然需要一个"差错池 + 修正工作流"，且**修正前后值都要保存**（不能原地覆盖）。

**数据治理四件套**（行内制度层面，入职后一定会遇到）：

| 治理项 | 通俗解释 | 开发感知 |
|---|---|---|
| 数据标准 | 字段叫什么、什么类型、取值范围、口径含义 | 建表要评审，命名与码值有字典；加字段要走标准比对 |
| 数据质量 | 完整性、唯一性、及时性、准确性、一致性的检查与整改 | 落 QC 规则、跑批出质量报告、异常挂账不能静默丢弃 |
| 元数据 | "数据的数据"：这张表是什么、谁负责、从哪来到哪去 | 表注释、字段注释、任务依赖登记，很多行要求强制填写 |
| 数据责任部门 | 每个数据域要有**归属部门**（数据 Owner），科技只是保管者 | 需求阶段要找 Owner 部门签字；口径变更由业务提，不能由开发拍板 |

关键认知：**科技部门不是数据的主人**。开发永远不能自己决定"这个字段填什么算对"，
必须回到业务归口部门拿到书面口径。这一条能帮你避开大量返工。

## 八、消费者权益保护与适当性

| 要求 | 人话 | 系统落地 |
|---|---|---|
| **适当性**（把合适的产品卖给合适的人） | 卖理财/基金/保险前，必须做客户风险承受能力评估，且客户风险等级 ≥ 产品风险等级才能买 | 风测问卷 + 等级计算 + 购买时强校验 + 客户主动购买超风险等级时的**双录与书面确认**流程 |
| **双录**（录音录像） | 面销关键产品时同步录音录像，证明"已充分告知风险" | 双录任务与业务订单绑定、质检状态、未通过质检不得成交 |
| **年化利率明示** | 贷款/分期必须展示年化利率（不是只展示日息、月费率），避免误导 | 计息与展示分离：展示口径由统一计算器提供，文案版本化留痕 |
| 收费公示 | 服务价格要公开、按公示标准收取 | 费率表版本化 + 生效时间 + 计价走配置不走硬编码 |
| 投诉处理与时限 | 投诉要受理、告知、在规定时限内办结并回访；重大投诉需上报 | 工单系统 + SLA 计时 + 超时升级 + 全过程留痕（**这是最像"互联网工单系统"的一块，上手最快**） |
| 营销与个人信息 | 未经同意不得发送营销信息；须提供退订 | 同意状态存储（**授权留痕**）+ 频控 + 退订实时生效 |
| 适老化与无障碍 | 老年客户、残障客户的可及性服务 | 大字版、人工入口保留、上门服务流程 |

**消保是近年投诉与处罚高发区**，需求往往来自"监管通报 + 内部整改"，特点是**时间紧、面广、跨系统**。
如果你在简历里写过"配置驱动的费率/文案版本化"或"工单 SLA 与超时升级"，这就是能直接复用的经验。

## 九、业务连续性与重要信息系统的特殊要求

JD 里的"**运维**工作"一半落在这里。业务连续性（BCM）= 出事了系统还能不能干活、多快能恢复。

| 概念 | 全称与人话 | 举例 |
|---|---|---|
| **RTO** | Recovery Time Objective：**允许停多久**。从故障到业务恢复的最长可接受时间 | 核心渠道 RTO 常以"分钟级"要求；管理报表可能容忍小时级 |
| **RPO** | Recovery Point Objective：**允许丢多少数据**。以数据丢失的时间跨度衡量 | RPO=0 意味着不能丢任何一笔已确认交易（需要同步复制或强一致方案） |
| 高可用架构 | 同城双活、**两地三中心**（生产中心 + 同城灾备 + 异地灾备）、单元化 | 见 [../13-稳定性工程/04-高可用架构模式.md](../13-稳定性工程/04-高可用架构模式.md) |
| 灾备切换演练 | 定期真切或桌面推演，证明"预案可用" | 演练要出报告、留指标（实际 RTO/RPO）、发现预案缺陷要整改闭环 |
| 重要时期保障 | 重大节假日、"开门红"、重要会议与活动期间的加强值守与变更冻结 | 变更窗口收紧、封网、值班表升级、预案前置准备 |
| 突发事件分级 | 按影响范围与时长分级，级别决定响应层级 | **达到一定级别有向监管机构报告的义务**，报告有时限 |

开发必须记住的三件事：

1. **重要信息系统的灾备能力等级、切换时限、演练频次都有硬性要求**（具体数值按监管规定与本行制度，本篇不给）。
   你写的组件如果无法在灾备环境部署（比如依赖了同城某个不可复制的本地文件），演练时会直接暴露。
2. **"能恢复"要证明，不是声称**。灾备环境必须常备可用、版本不能落后、数据同步链路延迟要监控。
3. **故障要报告**。生产事件在银行里不只是内部复盘，可能触发对外报告，所以事件时间线、影响笔数、
   恢复时点必须准确——这就是为什么日志与监控留痕是**合规要求**而不只是运维便利（见 [07 篇第七节](./07-银行业信息安全管理规范.md)）。

## 十、核心交付：监管要求 → 系统落地 → 开发工作量（速查表）

| # | 监管要求 | 落到系统里的东西（字段/校验/任务/报表/留痕） | 开发工作量类型 |
|---|---|---|---|
| 1 | 客户身份识别（KYC） | 客户信息必填字段与格式校验；联网核查调用与结果留痕；证件到期日 + 提醒跑批；影像资料归档 | 接口对接（外部依赖容错）+ 状态字段 + 定时任务 |
| 2 | 受益所有人识别 | 股权链路模型、UBO 计算结果与依据快照、变更触发的重算任务 | 数据建模 + 可重算的算法服务 + 历史版本保存 |
| 3 | 客户风险等级划分 | 风险因子表、评分规则版本、等级字段、复评周期到期任务、等级变化触发管控 | 规则引擎 + 版本化配置 + 批量重评作业 |
| 4 | 大额交易报告 | 交易明细全渠道归集；按客户 + 日 + 币种累计；当日撤销/冲正的计入口径；报文与回执 | 数据归集链路 + 聚合计算 + 报文生成 + 幂等重报 |
| 5 | 可疑交易报告 | 特征规则集、命中告警、案例工作流、人工研判结论、排除名单、时限监控 | 工作流引擎 + 规则可配置 + 关联查询性能优化 |
| 6 | 名单筛查 | 名单库版本化管理、模糊匹配打分、命中处置、实时拦截接口 | 匹配算法 + 缓存/索引 + 实时性优化 + 调参 |
| 7 | 资料与记录保存 | 不可篡改归档、按客户/账号检索索引、保留期策略与到期销毁任务 | 归档分层 + 检索设计 + 生命周期作业 |
| 8 | 账户四类与基本户唯一性 | 账户类型字典、唯一性约束（全行范围）、类型间迁移规则 | 唯一索引 + 并发控制 + 数据迁移校验 |
| 9 | 账户核准/备案政策变化 | 状态机调整、在途单据处理、报备报文、核查抽检功能 | 存量数据迁移 + 兼容期双逻辑 + 回归测试 |
| 10 | 反电诈管控 | 管控状态位组合、止付/解除指令接口、限额下调、指令回执 | 状态一致性下发 + **强幂等** + 高优先级通道 |
| 11 | 支付结算纪律（不垫付） | 余额校验不可为负、退票处理、逾期与退回流程 | 并发扣减正确性 + 差错处理链路 |
| 12 | 征信查询授权 | 授权凭证与查询原因必传；每次查询留痕；越权查询告警 | 通用切面（授权校验 + 审计埋点） |
| 13 | 征信报送与异议 | 借据/表现期数据抽取、报文与反馈解析、更正重发、异议工单 | 批处理 + 错误恢复 + 工单流 |
| 14 | 监管报送与数据治理 | 指标字典、统一取数层、数据血缘字段（批次号/来源/抽取时间）、差错池与修正流程 | 数仓建模 + 口径集中 + 可追溯性设计 |
| 15 | 消保适当性 | 风测问卷与等级、购买校验、超风险确认与双录绑定、年化利率展示计算器 | 规则校验 + 文案/费率版本化 + 跨系统状态关联 |
| 16 | 投诉与时限 | 工单、SLA 计时、超时升级、回访记录、监管转办件台账 | 最接近通用工单系统的一块，可快速上手 |
| 17 | 业务连续性 | 灾备可部署性、切换脚本、同步链路延迟监控、事件时间线记录 | 非功能性建设 + 演练整改 |
| 18 | 个人信息保护 | 分级标签、脱敏组件、字段加密、导出审批、日志管控 | 与 [07 篇](./07-银行业信息安全管理规范.md) 完全共用一套基建 |

## 十一、初学者常见误区

| 误区 | 真相 |
|---|---|
| "合规是法务/合规部门的事，开发只管写代码" | 合规部门出**要求**，系统里的字段、校验、跑批、留痕**全是开发实现**。漏一个渠道不上报、少一个字段没落库，就是真实的合规事件 |
| "反洗钱只针对大额交易" | 大额只是客观报送的一半；**可疑交易无金额门槛**，且洗钱恰恰会刻意拆成小额规避阈值。风险等级、名单筛查、账户行为特征同样核心 |
| "AML 就是一个 SQL 统计" | 关键是"按客户 + 日 + 币种"跨渠道**归集**能力、规则版本可追溯、人工研判工作流与报送时限管理。统计只是其中一小环 |
| "监管报送是手工填表" | 银行报送量巨大且频次固定，几乎全是系统跑批 + 报文 + 回执。手工填表的部分（如个别统计底表）也要求可追溯到取数逻辑 |
| "口径差一点没关系，最后能对上就行" | 报送口径不一致会导致**同一指标两处不同值**，被检查追问时无法自证。口径必须唯一且有定义出处 |
| "账户政策改动很小，系统跟着小改一下" | 账户类改动牵动**存量数据 + 在途流程 + 上下游校验 + 报送接口**，属于"改一点要全行回归"的高风险变更 |
| "基本户和一般户差不多，都能取现金" | 一般存款账户**不得支取现金**；基本户是唯一的主办账户且一个单位只能开一个 |
| "查一下客户征信不算什么，又没外传" | 无授权查询即违规，且**每次查询都留痕、可倒查**。这是最容易毁掉职业生涯的低级错误 |
| "灾备建好了就是安全的" | 能力要**演练证明**：版本一致、数据同步延迟达标、脚本可执行、人员会操作。未演练的预案等于没有 |
| "客户信息泄露最多是内部处罚" | 可能触及法律责任，包括刑事责任。参见 [07 篇第八节](./07-银行业信息安全管理规范.md) |

## 十二、动手练习

1. **做一个最小 AML 规则**：给本项目的 `pay_transaction` 表写一个"同一 `order_no` 对应客户当日成功支付累计 ≥ 某阈值"
   的聚合查询，并明确写出你的**日口径**（用 `pay_time` 还是 `create_time`？跨 0 点怎么算？退款是否抵扣累计？）。
   然后回答：如果退款不计入，会漏报什么？如果计入，会误报什么？
2. **给"当日累计"设计幂等重跑**：跑批任务在 03:00 执行，02:10 有一条交易补录进来。
   写出你的重跑方案（按 `业务日 + 客户号` 全量重算并覆盖结果 vs 增量累加），并说明为什么前者更安全、代价是什么。
   参考 [../14-数据工程与OLAP/05-批处理与调度编排.md](../14-数据工程与OLAP/05-批处理与调度编排.md) 的重跑与幂等章节。
3. **实现账户管控状态位模型**：设计一个只收不付 / 不收不付 / 限额 / 暂停某渠道的组合状态（枚举或位标志），
   给出"入账"与"出账"两个方法在该状态下的判断表，并写单元测试覆盖 4 种组合。
   思考：为什么用**位标志**比用单个枚举更合适？多个系统如何保证状态一致地下发？
4. **写一条数据血缘**：挑 `../14-数据工程与OLAP/08-数据质量与对账.md` 里的一个对账场景，
   画出"报表单元格 → 汇总表 → 明细表 → 业务库表字段 → 产生该记录的业务动作"的完整链路，
   并指出链路上你需要哪四个字段才能证明"这个数是怎么来的"。
5. **合规需求翻译演练**：找一句真实感的需求描述（自己编一句即可，例如"系统需支持对高风险客户交易进行实时拦截并留存研判记录"），
   在 5 分钟内把它拆成：涉及系统 / 新增字段 / 新增校验 / 新增任务 / 报表 / 留痕 / 权限，
   再对照本篇 §10 的表检查自己漏了什么。这就是银行需求评审的日常。
