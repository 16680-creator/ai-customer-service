# 金融级一致性与对账实战

> 本篇回答一个问题：**钱进了系统，怎么保证它一分不多、一分不少、随时能查清在哪**。它把银行资金系统最硬的三块能力——复式记账、幂等与状态机、对账与差错处理——逐条绑到 `ai-customer-service` 的真实支付代码上，并明确标出本仓库**没有**的部分。
> 前置阅读：[02-Spring微服务/14-分布式幂等设计](../02-Spring微服务/14-分布式幂等设计.md)（已给出通用工程结论，本篇只做银行视角深化与反例剖析，不重复其结论）、[02-Spring微服务/13-支付渠道集成与回调一致性](../02-Spring微服务/13-支付渠道集成与回调一致性.md)、[02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)。
> 一句话立场：**账不平就是 bug**，不管它是网络抖动、MQ 重投，还是有人手工改了库。

## 一、先立不变式：账不平就是 bug

互联网系统的一致性目标是"最终能看到同一个值"；资金系统更苛刻，可拆成**四个"不"**，每个都有明确机制去扛：

| 目标 | 人话 | 失效现场 | 靠什么机制扛 | 本仓库落点 |
|------|------|----------|--------------|------------|
| **不丢** | 客户付了钱，系统必须知道 | 回调丢失、进程在落库前崩溃 | 主动查单兜底 + 事务消息回查 + T+1 文件对账 | ✅ `PayCompensationServiceImpl:39`、`PaySuccessTransactionListener:56` |
| **不重** | 同一笔业务执行 N 次只入账一次 | 用户双击、渠道重投、MQ 至少一次 | 业务唯一键 + 状态前置校验（**DB 唯一约束终审**） | ✅ `pay_transaction.uk_order_no`（`PaySchemaInitializer:37`）+ `markSuccess:55` |
| **不错** | 金额、账户、方向、汇率折算都对 | 回调金额被改、元/分搞混、精度截断 | 金额校验 + 借贷平衡 + 总分核对 | ⚠️ 金额校验只在订单侧（`OrderServiceImpl:248`），账务核对 ❌ 不存在 |
| **不失** | 灾难后钱不会凭空蒸发或变多 | 机房故障、误删数据、被改库 | 复式记账可重算 + 不可变流水 + 灾备演练 | ❌ 本仓库无账务层 |

**"最终一致"在资金系统不等于"随便等等就好"**：它的完整表述是"在有限时间内收敛到**可验证的正确值**"。少了"可验证"，最终一致就退化成听天由命。银行的做法是给每条异步链路配一个**核对任务**，把"我相信它一致"变成"我每天都证明了它一致"——这也是 JD 里"研发运维工作"最容易被忽略的部分：**做完功能只是开始，长期可核对才算交付**。口诀：**不丢靠查单与对账，不重靠唯一键与状态机，不错靠借贷平衡与金额校验，不失靠可重算的流水。**

## 二、复式记账：账务层的三张表

### 2.1 三层结构与铁律

只有**分录层**是事实（source of truth），余额层是它的物化缓存——任何时刻 `余额 = 期初 + Σ发生额` 必须成立，不成立就是 bug：

```text
   业务流水层（业务视角："我付了 100 元买会员"）
   └── biz_transaction   一次业务动作一条，幂等键 = 业务唯一键
            │ 1 : N（一笔业务 → 一组会计分录）
   会计分录层（会计视角："谁的钱从哪到哪"，append-only 不可改）
   └── acct_journal      一笔业务的借贷分录必须成组出现且金额相等
            │ N : 1（多笔分录 → 汇总进账户余额）
   余额层（查询视角："这个账户现在有多少钱"，派生数据）
   └── acct_balance      期初余额 + 本期发生额 = 期末余额（每天可校验）
```

### 2.2 为什么余额不能只存在业务表的一个字段里

`orders` 表有 `pay_amount`、`status`，那是"业务状态"不是"账务余额"。把余额写成某个表的一个字段（"读出 → 内存算 → 写回"），会同时踩四个坑：

| 坑 | 说明 | 银行怎么避 |
|---|---|---|
| **无轨迹** | 字段只保留最后一次写入结果，出错时无法回答"什么时候错的、错在哪一笔" | 分录表 append-only，只插不改不删 |
| **丢更新** | 并发下后写覆盖前写；即便写成 `balance = balance - ?` 靠行锁保序，也扛不住跨表口径不一致 | 同一事务内"插入分录 + 带前置条件的余额增量更新" |
| **不可重算** | 一旦发现余额错，没有依据恢复 | 从期初余额 + 分录重放即可重建余额 |
| **无法汇总核对** | 一个字段表达不了"这笔钱去了哪个对手科目"，日终总分核对无从下手 | 每笔分录带 `direction`（D 借 / C 贷）与对手科目 |

### 2.3 可跑 DDL（本仓库不存在，是练习要建的）

```sql
-- ① 会计分录表：一次记账的多条分录共享 entry_no；金额恒正，方向用 D/C 表达
CREATE TABLE IF NOT EXISTS acct_journal (
    entry_no      VARCHAR(32)   NOT NULL COMMENT '分录号：一次记账的多条分录共用',
    biz_date      DATE          NOT NULL COMMENT '营业日期（记账日，非自然日）',
    account_no    VARCHAR(32)   NOT NULL COMMENT '账号/内部账号',
    subject_code  VARCHAR(20)   NOT NULL COMMENT '科目号，如 201001 活期存款',
    direction     CHAR(1)       NOT NULL COMMENT 'D 借 / C 贷',
    amount        DECIMAL(18,2) NOT NULL COMMENT '恒正金额',
    currency      CHAR(3)       NOT NULL DEFAULT 'CNY',
    source_type   VARCHAR(20)   NOT NULL COMMENT 'PAY/REFUND/FEE/ADJUST',
    source_no     VARCHAR(64)   NOT NULL COMMENT '关联业务流水号（追溯用）',
    seq           BIGINT        NOT NULL COMMENT '账户内分录顺序号',
    balance_after DECIMAL(18,2) NOT NULL COMMENT '本笔后余额快照（逐笔定位靠它）',
    PRIMARY KEY (entry_no, account_no, direction),
    UNIQUE KEY uk_src_acct_dir (source_type, source_no, account_no, direction), -- 幂等终审
    KEY idx_acct_date (account_no, biz_date, seq)
) ENGINE=InnoDB COMMENT='会计分录表（append-only，只插不改不删）';

-- ② 余额表：派生数据，任何时刻可由"期初 + 分录发生额"重算
CREATE TABLE IF NOT EXISTS acct_balance (account_no VARCHAR(32) NOT NULL, biz_date DATE NOT NULL,
    opening_balance DECIMAL(18,2) NOT NULL, debit_amount DECIMAL(18,2) NOT NULL DEFAULT 0,
    credit_amount   DECIMAL(18,2) NOT NULL DEFAULT 0, closing_balance DECIMAL(18,2) NOT NULL,
    PRIMARY KEY (account_no, biz_date)) ENGINE=InnoDB COMMENT='账户余额表（日）';
```

> 注意精度选型：上面用 `DECIMAL(18,2)`，而本仓库 `pay_transaction` 用的是 `DECIMAL(10,2)`（`PaySchemaInitializer:29`）——整数位只有 8 位，上限 9999 万元。"字段定义也是资金风险"，这就是最具体的一个例子。

### 2.4 三条必背核对 SQL

```sql
-- 核对 1：借贷平衡（每组分录内部必须平）——挂在记账提交前，不平直接回滚
SELECT entry_no FROM acct_journal WHERE biz_date = CURDATE()
GROUP BY entry_no HAVING SUM(CASE direction WHEN 'D' THEN amount ELSE -amount END) <> 0;

-- 核对 2：余额 = 期初 + 发生额（账户级总分核对）
SELECT account_no, closing_balance - (opening_balance + credit_amount - debit_amount) AS diff
FROM acct_balance WHERE biz_date = CURDATE()
  AND closing_balance <> opening_balance + credit_amount - debit_amount;

-- 核对 3：逐笔定位第一次出错的那一笔（MySQL 8 窗口函数，比较余额快照链）
WITH s AS (SELECT seq, direction, amount, balance_after,
    LAG(balance_after, 1, b.opening_balance) OVER (PARTITION BY j.account_no ORDER BY j.seq) AS prev
    FROM acct_journal j JOIN acct_balance b ON b.account_no = j.account_no AND b.biz_date = j.biz_date
    WHERE j.biz_date = CURDATE())
SELECT * FROM s WHERE balance_after <> prev + CASE direction WHEN 'D' THEN -amount ELSE amount END;
```

**"账不平怎么定位到具体一笔"**：思路是**检查点 + 二分**。`balance_after`（或每 N 笔存一次的余额快照表）本质是检查点数组，从后往前找第一个不满足 `本笔余额 = 上笔余额 ± 本笔金额` 的位置即最早出错的那一笔；没有检查点就只能从期初重放（replay）——慢，但一定对。

### 2.5 借贷方向（很多人第一次会记反）

站在**银行**的会计视角：客户的存款是银行**欠客户的债**，所以"客户存入 100 元"= 贷记客户活期存款（负债↑记贷）、借记库存现金/存放央行款项（资产↑记借）；"客户对外付款 100 元"反过来，借记客户存款（负债↓）、贷记清算资金（资产↓）；"收手续费 5 元"= 借记客户存款、贷记手续费收入。**资产/费用增加记借，负债/权益/收入增加记贷**——记住这一句，其余全能推。

## 三、幂等：银行侧的核心是"业务唯一键 + 状态机推进"

[14 篇](../02-Spring微服务/14-分布式幂等设计.md)已给出"正确性归 DB，性能归 Redis"的通用结论，这里不重复，而是**把本仓库 Redis 方案的边界条件讲透**——银行评审追问的正是这些边界。

### 3.1 走读 `IdempotentAspect`：注释里自己承认的陷阱

`ai-cs-common/src/main/java/com/aics/common/idempotent/IdempotentAspect.java`（103 行）：

```java
21   * 幂等切面：@Idempotent 注解的执行器，以 Redis SET NX EX 实现分布式"首次占位"。
26   * <p>注意：方法内若自带 {@code @Transactional}，占位发生在事务提交前——
27   * 这正是想要的行为：同 key 并发请求在占位期间直接拒绝，而不是等到锁在行上排队。
```

`:49-68` 是执行体（占位 + 拒绝 + fail-open）：

```java

51          if (TransactionSynchronizationManager.isActualTransactionActive()) {
52              // 占位在事务内不会随回滚自动释放：失败路径显式删除（见下方 catch），此处仅提示
53              log.debug("幂等方法存在活跃事务，失败时将主动释放 key: {}", idempotent.key());
54          }

62          } catch (RuntimeException e) {

64              return joinPoint.proceed();

```

`:69-74` 是"业务异常才释放 key"（`catch (Throwable t) { tryRelease(redisKey); throw t; }`），`:78-84` 是 `tryRelease` 本身——释放失败就退化成等 TTL 自然到期。

### 3.2 三个陷阱与银行的处置

| 陷阱 | 现场后果 | 银行侧处置 |
|------|----------|------------|
| **占位早于事务提交**（`:26`、`:52`） | 业务事务回滚了，Redis 的 key 却留到 `tryRelease` 才消失。若进程在 `:70` 与 `:72` 之间被 kill，key 会一直留着，后续合法重试在 TTL 内被误拒 409 | 幂等键**落到数据库唯一约束**，占位记录与业务数据**同库同事务**写入：事务回滚，占位一起消失，天然一致 |
| **业务异常才释放 key**（`:71-73`、`:78`） | "看起来成功但实际未入账"与"业务正常但返回慢被判重复"都会误判 | 渠道返回"处理中/未知"时**不允许释放幂等键**，必须转入未知态流程（第五节），查到终态才允许重发 |
| **Redis 故障 fail-open**（`:62-65`） | 降级方向是**对的**（去重层挂了不能阻断业务），但前提是后两层真的存在 | 写成硬性评审项：**用了 Redis 幂等，必须当场指出唯一约束在哪一列、状态前置判断在哪一行**，指不出来就是资损隐患 |

`:26`/`:52` 那句"这正是想要的行为"是本仓库的取舍（回调场景宁可快拒也不让并发请求在 DB 行锁上排队）；在银行，同一取舍要**按业务分级**：查询类可以快拒，入账类必须排队或转人工——**绝不能把"被拒绝"当成"没发生"**。同时必须诚实说明现状：`@Idempotent` 目前**没有应用到任何业务方法上**（全仓 `src/main` 除注解定义与切面示例外无使用点），真实防线只有一层半：状态检查 + `uk_order_no`。讲简历时要说"组件已落地并有单测，接入验证是下一步"，不能说"我做了支付幂等"。

## 四、状态机与终态：哪些可重入、哪些不可逆

```java
// ai-cs-pay/.../service/impl/PayTransactionServiceImpl.java:53-57
53  public boolean markSuccess(String orderNo, String tradeNo, BigDecimal amount) {
54      PayTransaction tx = getByOrderNo(orderNo);
55      if (tx == null || STATUS_SUCCESS.equals(tx.getStatus())) {
56          return false; // 幂等：已成功或不存在
57      }
```

返回 `false` 的含义是"**这次通知没有推进状态**"，不是"处理失败"——调用方（`PaySuccessTransactionListener:44` 注释：PENDING → SUCCESS，幂等，重复通知不重复处理）据此决定要不要触发下游记账。这是"重复通知安全"的最小实现。

| 状态 | 可由哪些态进入 | 是否终态 | 重复调用是否安全 | 可逆性 |
|------|----------------|----------|------------------|--------|
| `PENDING` | 建单（`createOrUpdatePending:31`） | 否 | ✅ 同单重复发起走**更新**而非新建（`:43-47`） | 可关单 |
| `SUCCESS` | PENDING（`:55` 判重） | 半终态 | ✅ `markSuccess` 重复返回 false | 只能通过退款/冲正反向 |
| `CLOSED` | 仅 PENDING（`markClosed:76`） | 终态 | ✅ 非 PENDING 返回 false | 不可逆 |
| `REFUNDING` | SUCCESS 或 PENDING（`markRefunding:88`） | 否 | ✅ 其他态返回 false | 中间态 |
| `REFUNDED` | **任意非空**（`markRefunded:98-107`） | 终态 | ❌ 无前置态校验、无判重，恒返回 true | 不可逆 |

⚠️ **本仓库三处真实的口子**（这三条是"你读过代码"的最好证明）：

1. `PayTransactionService.java:39` 注释写"标记已退款（幂等）"，但实现 `PayTransactionServiceImpl:98-107` 只判了 `tx == null`——既不校验来源态也不判重，`SUCCESS → REFUNDED` 反复执行会反复刷 `refund_time` 并恒返回 true。银行里这叫"退款终态可重复推进"，必须修：**终态迁移带 CAS 条件**（`WHERE status = 'REFUNDING'`）并看受影响行数。
2. `markSuccess` 的更新是 `payTransactionMapper.updateById(tx)`（`:67`），WHERE 只有主键，**没把 `status = 'PENDING'` 带进更新条件**。两个并发通知同时通过 `:55` 检查时，`notify_count`（`:65`）与 `pay_time`（`:66`）会被后写覆盖。它今天没造成资金错误，只因为下游靠"首次返回 true 才处理"——**这是运气不是设计**。
3. `MockPayController.java:79-84` 先调渠道 `refund(...)`、后调 `markRefunding(...)`，且**丢弃了渠道退款返回值**。真实银行顺序相反：先落"退款受理中"的退款流水（拿到退款账号），再发渠道请求，最后用渠道回执推进终态——否则渠道超时时你连"我到底发没发过退款"都答不出。

对照本仓库订单状态机，"状态收敛"有现成正例：


`OrderStateTransitionService.java:21-35` 的做法值得在面试里点名：每次调用先 `resetStateMachine(current)` 把内存态强制对齐 DB 态（`:25-27`），再 `sendEvent`（`:28`），不被接受就抛业务异常（`:29-32`）。配置类注释（`OrderStateMachineConfig.java:12-13`）明写"不使用内存 persister，多实例下内存状态不可靠"，**DB status 是唯一事实来源**。银行核心同理：状态推进的权威一定在数据库，任何"进程内状态"都不能作为推进依据，否则重启或扩容就丢状态。

**未知输入怎么分层**：`OrderServiceImpl.confirmPay`（`:227-253`）——订单不存在 `return`（`:230-233`）、已支付 `return`（`:236-239`）、状态机不允许迁移则忽略（`:242-245`）、**只有金额不一致才抛异常**（`:248-253`）。这条划分就是资金系统的风险分级：**金额不一致 = 可能资损 = 必须炸出来；状态不匹配 = 可能重放 = 可以静默**。

## 五、超时未知态：联机交易最难的一类问题

**请求超时 ≠ 失败。** 超时有三种真相，调用方在超时那一刻完全无法区分：

```text
 发请求 ─┬─ 网络断在去路          → 实际失败（可安全重试）
         ├─ 对方处理成功，回包丢了 → 实际成功（重试 = 重复付款！）
         └─ 对方收到了但还在处理   → 未知（既不能判成功也不能判失败）
```

**三步收敛（银行联机交易的通用形态，各行叫法略有差异）**：

| 步骤 | 做什么 | 判定 | 本仓库对应 |
|------|--------|------|------------|
| ① 原交易查询 | 拿**原流水号**去对方系统查这笔的真实结果 | 明确成功 → 入账；明确失败 → 置失败；仍处理中 → 下一步 | ✅ `PayChannel.queryPayment`（接口 `:52`）+ `PayNotifyService.syncByQuery:46-54` |
| ② 冲正 | 结果不可知且已过超时阈值 → 发"冲正"把两边拉回交易前状态 | 冲正成功 → 置失败；冲正也超时 → 下一步 | ❌ 本仓库不存在 |
| ③ 差错挂账 | 仍无法判定 → 登记差错，钱**不动**，转人工/日终对账 | 挂账后有明确核销流程 | ⚠️ 只有内存 List（`PayCompensationServiceImpl:60-65`），无台账 |

**为什么宁可挂账也不能盲目重试**：重试的代价是"万一是成功，我就多付了一笔"，多付的钱要追回 = 资损 + 客诉 + 监管报送 + 事故定级；挂账的代价只是"这笔晚一点处理，有人跟进"。**资金系统里"慢"几乎总是比"错"便宜**——这句话可以原样说给面试官。落到工程上是三件事：① 每笔联机交易有全局唯一流水号且**重试期间不变**（否则查不到原交易，见 [03-数据库与ORM/04-分布式ID规范](../03-数据库与ORM/04-分布式ID规范.md)）；② 超时阈值与对方处理时长分布匹配并留出查询时间；③ 未知态在库里是**一个真实存在的状态值**，而不是靠"没有记录"隐式表达。

## 六、冲正、撤销、退款：三个词三种实现

| 维度 | 冲正（reversal） | 撤销（void/cancel） | 退款（refund） |
|------|------------------|---------------------|----------------|
| 语义（触发方） | 系统异常导致结果未知，把一笔交易**恢复到发生前**（系统自动） | 作废一笔**已确认成功**的交易（人工或前端） | 正常业务下的资金反向流动（业务流程驱动） |
| 时间约束 | 通常限**当日、清算前** | 当日当批 | 可跨日，受原交易可退余额限制 |
| 金额 | 全额（部分冲正严格受限） | 全额 | **支持部分**，需累计校验 |
| 是否授权 | 系统发起，无需授权 | 视渠道 | 隔日/超额需**主管授权**（行业通用做法） |

**关联字段设计**（冲正流水必须能反查原流水，原流水必须知道自己被冲过）：

```sql
ALTER TABLE pay_transaction
    ADD COLUMN orig_seq_no VARCHAR(32) DEFAULT NULL COMMENT '被冲正/被退款的原交易流水号',
    ADD COLUMN txn_type VARCHAR(10) NOT NULL DEFAULT 'PAY' COMMENT 'PAY/REVERSAL/VOID/REFUND',
    ADD COLUMN reversed_flag CHAR(1) NOT NULL DEFAULT 'N' COMMENT '原交易是否已被冲正 Y/N',
    ADD COLUMN auth_teller VARCHAR(20) DEFAULT NULL COMMENT '授权柜员号（隔日/超额退款必填）',
    ADD UNIQUE KEY uk_biz_idem (txn_type, orig_seq_no, order_no);
```

- 三者记账上都生成**反向分录**（退款另有独立退款流水），而关联字段少了 `reversed_flag`，一笔交易就可能被冲正**两次**——这是直接资损。
- **隔日冲正/隔日退款需要授权**：跨了日切，原分录已进入已轧平的账，反向记账会影响已报送的报表，必须留下授权人与原因（具体以行内制度为准）。
- ❌ 本仓库现状：只有退款（`PayChannel:68`）与关单（`:63`），**没有冲正、没有撤销、没有上述任何关联字段**。

## 七、对账：JD 里最常被问的能力

### 7.1 三层对账

| 层次 | 比什么 | 对手方 | 频率 | 抓什么 |
|------|--------|--------|------|--------|
| ① **渠道对账** | 我方流水 vs 外部机构对账文件（T+1） | 外部（有争议方） | 日切后 | 渠道说成功而我方没记、金额不一致、手续费 |
| ② **行内交易对账** | 跨系统流水互核（支付流水 vs 订单状态） | 内部（无争议，纯 bug） | 分钟~小时 | 单边账、丢消息、状态推进失败 |
| ③ **账账核对** | 总分核对：明细余额之和 vs 总账科目；余额 vs 期初+发生额 | 账务内部恒等式 | 日切时 | 记账逻辑错、漏记、重复记 |

> **方法论**（数据质量六维、增量对账的 EXTRA 盲区、对账任务自监控、差异登记表）见 [14-数据工程与OLAP/08-数据质量与对账](../14-数据工程与OLAP/08-数据质量与对账.md)，本篇不重复，只补两条银行侧差异：**其一**，银行对账是"双边都有原始凭证"的比对，OLAP 对账是"源端 vs 派生端"，差别在于发现差异后**不能默认以我方为准**——渠道文件可能就是对的、我方就是错的，所以差错必须先分类再定责；**其二**，对账文件本身要防篡改与防漏：文件名带日期与机构号、带文件级控制总数（control total，笔数与金额合计）与签名，**文件未到要告警不能静默跳过**，控制总数对不上时逐条比对毫无意义，先解决文件完整性。

### 7.2 差错三种与处理链

| 差错类型 | 定义 | 谁的账有问题 | 典型处理 |
|----------|------|--------------|----------|
| **长款** | 我方账上有钱、对方账上没钱（本方多出的差额） | 客户少付了或我方多记 | 挂"待处理款项"，查明后退汇或补记收入 |
| **短款** | 我方账上没钱、对方账上有钱（本方少了） | 我方漏记或客户多付 | 挂账 → 向客户追收 / 向渠道索赔；最敏感，直接对应资损 |
| **金额不一致** | 双方都有这笔但金额不同 | 多为精度、手续费、汇率折算差异 | 容差内自动核销并留痕；超容差转人工 |

处理流程是一条固定链：**挂账（进差错台账）→ 核销（自动规则或人工判断）→ 退汇 / 补账（真实资金动作）→ 留痕（谁、依据什么、做了什么）**。自动核销只允许在无歧义规则下做（如"差 ≤ 1 分且手续费科目一致"），任何需要"猜"的都必须人工，且双人复核。

## 八、消息与账务通知：为什么用事务消息

`ai-cs-pay/src/main/java/com/aics/pay/mq/PaySuccessTransactionListener.java`（69 行）：

```java
40  public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
43      try {
44          // 本地事务：支付流水 PENDING → SUCCESS（幂等，重复通知不重复处理）
45          payTransactionService.markSuccess(payload.getOrderNo(), payload.getTradeNo(), payload.getAmount());
47          return RocketMQLocalTransactionState.COMMIT;      // 消息对消费者可见
48      } catch (Exception e) {
51          return RocketMQLocalTransactionState.ROLLBACK;    // 半消息删除
56  public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {   // Broker 回查
58      PayTransaction tx = payTransactionService.getByOrderNo(payload.getOrderNo());
59      if (tx == null) { return RocketMQLocalTransactionState.ROLLBACK; }
63      return switch (tx.getStatus()) {
64          case "SUCCESS" -> RocketMQLocalTransactionState.COMMIT;
65          case "PENDING" -> RocketMQLocalTransactionState.UNKNOWN; // 流水未决，等待下次回查

```

**为什么"支付成功后通知记账"适合事务消息**：两个子动作（改流水状态、通知下游）分处**同一个 DB** 和 **Broker**，无法用一个本地事务包住；业务上又要求"流水成功了，通知就一定发生"。事务消息（半消息 = 先持久化到 Broker 但对消费者不可见）把顺序倒过来：**先落"我要通知"的意图 → 再执行本地事务 → 用二阶段确认让意图对消费者可见**。

| 方案 | 致命窗口 | 结果 |
|------|----------|------|
| 先更 DB，再发消息 | DB 成功后、发送前进程崩溃 | 消息永丢，下游永远不知道 —— 单边账 |
| 先发消息，再更 DB | 消息已发但本地事务回滚 | 下游收到"成功"其实没成功 —— 更糟 |
| 本地消息表（同库表 + 扫表） | 无（同库同事务） | 可靠，但要维护扫描任务与消息状态 |
| **事务消息**（本项目） | 无 | 意图持久化在 Broker，回查以 DB 真实状态为准；代价是要实现回查器 |

**回查表设计**：本仓库直接复用业务表 `pay_transaction`（`PayTransaction.java:15`）的 `status` 做判定，**不额外建消息表**——因为流水状态本身就是权威。只有当业务状态不足以判定（例如一次业务改多张表）时，才建专用回查表 `msg_transaction(state, biz_key, create_time)`，字段要求：业务唯一键 + 状态（LOCAL_COMMIT / LOCAL_ROLLBACK / UNKNOWN）+ **与业务写库同事务**。而 `:65` 的 `UNKNOWN` 是三个分支里最值得学的：**它不猜**——PENDING 意味着"本地事务可能还在跑"，返回 UNKNOWN 让 Broker 稍后再问一次；换成"查不到成功就 ROLLBACK"会在应用变慢时把成功交易的记账通知直接抹掉。机制细节见 [04-中间件/08-RocketMQ事务消息与死信队列](../04-中间件/08-RocketMQ事务消息与死信队列.md)。但反过来也要清楚：事务消息**保证"必达"、不保证"只达一次"**——`PaySuccessListener.java:30` 配了 `maxReconsumeTimes = 8`，8 次里每次都可能重投，安全性完全靠消费端 `confirmPay` 判重（该文件 `:18` 注释自己写明了）。

## 九、分布式事务：银行核心为什么不用强一致

强一致分布式事务把"可用性"和"资金确定性"都赌在协调者的存活上；而银行核心的跨系统链路（核心 ↔ 支付清算 ↔ 总账）里，参与方可能是外部机构，根本不可能被一个 TC 回滚。所以通用形态是：**每步本地事务 + 全局幂等 + 异步推进 + 对账兜底**。

**Seata AT 的边界**（机制见 [02-Spring微服务/06-Seata分布式事务AT模式](../02-Spring微服务/06-Seata分布式事务AT模式.md)）：适合"同企业内、可控的几个 MySQL 库 + 短事务 + 数据可反向补偿（undo_log）"；不适合"跨机构/外部渠道（对方没有你的 TC）""长事务（全局锁会拖死热点行，见第十一节）""带外部副作用的动作（发消息、调支付、扣实物库存）"。

本仓库正例：`OrderServiceImpl.java:78` `@GlobalTransactional(rollbackFor = Exception.class, name = "order-create")` 加在 `doCreateOrder`（`:92`）上，入口 `createOrder`（`:73`）先拿分布式锁再进事务（`OrderCreateLockService.java:44-53`，`waitTime=0` 快拒）——**锁在事务外层**在银行同样是硬要求：锁在内层会造成"事务回滚时锁已释放"或"锁被长事务占住"。⚠️ 但 `:103-104` 的注释承认"MQ 不是 Seata 资源，全局回滚时下方延迟消息已发出"，靠消费侧 `cancelExpiredOrder` 查不到订单天然幂等兜住——这在"关单"这种无资金语义场景可以，在"付款"场景不行：**有资金副作用的动作绝不能放在可回滚的全局事务里裸发**，要么走事务消息（第八节），要么放到事务提交之后（`OrderPaidEventListener` 的 `AFTER_COMMIT` 就是这个思路）。XID 传播见 [02-Spring微服务/07-服务调用统一与SeataXID传播](../02-Spring微服务/07-服务调用统一与SeataXID传播.md)。

## 十、日切：一天的结束不是一个时间点

```text
 ────────────────────────────────────────────────────────────────▶
     │ ① 停/限联机  │ ② 跑批（清算/计息/汇总/对账）│ ③ 开新营业日 │
     │ 切日窗口     │ 顺序：先明细账后总账       │              │
 ────┴──────────────┴─────────────────────────────┴──────────────┴───
 受理日 = 客户点下"确认"的那一天     记账日 = 这笔分录真正落账的 biz_date
 跨日交易：23:59:50 受理、00:00:20 记账 → 归属规则必须写死并与渠道文件口径一致
```

**四件套**：① **营业日期表** `busi_date(biz_date, status, prev_biz_date)`，全行唯一一行状态（`OPEN`/`CUTTING`/`CLOSED`），所有交易取号与所有记账写 `biz_date` 都读它——**不允许各处自己 `LocalDate.now()`**；② **切日窗口内拒绝哪些交易**：通常是影响当日汇总与清算的（大额转账、跨行、还款计息、开户结息），查询与不动账的保留，具体以行内制度为准；③ **跨日归属**：受理日与记账日两个字段都要落库；④ **跑批失败可重跑且不重复入账**——这是日切最实际的工程问题，规则是"批次号 + 日期唯一、任务级状态表记录已完成批次、按日期分片支持从指定日重跑"。方法论（幂等重跑、水位线、回填）见 [14-数据工程与OLAP/05-批处理与调度编排](../14-数据工程与OLAP/05-批处理与调度编排.md)，本篇只补银行侧的一条硬约束：**幂等必须落在"记账"这一层**（同一 `biz_date` + 同一 `entry_no` 只允许一份分录），而不是只落在"任务不重复执行"这一层——因为任务可能重跑一半时账已经记进去了。❌ 本仓库现状：无营业日期表、无切日窗口、无日终批处理，全用 `LocalDateTime.now()`（如 `PayTransactionServiceImpl:66`，实体自动填充见 `PayTransaction.java:41-45`）。

## 十一、热点账户：为什么"给同一账户加行锁"会压垮 TPS

**热点账户** = 大量交易同时更新同一个账户（商户结算户、备付金汇总户、还款归集户、手续费收入户）。`UPDATE acct_balance SET balance = balance + ? WHERE account_no='HOT'` 会把所有请求排在同一行锁上，**TPS 上限 ≈ 1 / 单事务持锁时长**——几十毫秒的事务就能把 TPS 压到个位数，还伴随锁等待超时雪崩（锁机制原理见 [03-数据库与ORM/05-MySQL锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md)）。

| 方案 | 做法 | 一致性代价 | 复杂度代价 |
|------|------|------------|------------|
| ① 串行排队 | 应用层队列/单线程消费该账户，DB 无竞争 | 无（本来就串行） | 最低，但吞吐天花板明确，只适合低频账户 |
| ② 余额缓冲 / 汇总入账 | 交易只写"发生额明细"（无锁），异步按批（每 N 笔或每 200ms）把净额合并成**一条**余额更新 | 余额可见性延迟数十~数百毫秒；查余额要"缓冲余额 + 未汇总明细"，否则客户看到少钱 | 中 |
| ③ 子账户拆分 | 一个逻辑账户拆 N 个物理子账户随机路由，余额 = Σ 子账户 | 汇总瞬间可能读不到刚写入的子账户；扣款要跨子账户聚合，会出现"某子账户余额不足"的重分配问题 | 高；透支控制、冻结、计息都按逻辑账户聚合，最容易做错 |
| ④ 异步记账 + 最终平账 | 联机只做校验与流水登记，分录异步落，靠平账任务收敛 | 明确窗口内账不平（可控）；**必须有日终兜底核对** | 高；对账不做就是纯粹埋雷 |

> 记账引擎的整体设计见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)。❌ 本仓库没有热点账户场景（用户之间订单互不相关），这块只能靠讲原理过关。最小练手：给 `product.stock` 扣减加一层"发生额缓冲 + 汇总入账"，量一下 TPS 与库存可见性延迟。

## 十二、金额与精度：最便宜也最常犯的错

```java
// ai-cs-pay/.../channel/WechatNativeChannel.java:222-227（银联同款 UnionpayChannel.java:259-264）
222  /** 元转分：BigDecimal 避免浮点误差，如 1.23 元 = 123 分 */
223  public static int yuanToFen(BigDecimal yuan) {
224      if (yuan == null) {
225          return 0;
226      }
227      return yuan.movePointRight(2).setScale(0, RoundingMode.HALF_UP).intValueExact();
```

这一段是金额规范的正例三件套：**BigDecimal 入参 → `movePointRight` 移位（不乘 100，避免精度污染）→ `setScale(0, HALF_UP)` → `intValueExact()` 溢出即抛**。`AlipayChannel.java:89` 用 `toPlainString()` 传金额（不用 `toString()`，防科学计数法）、`:156` 用字符串构造 `new BigDecimal(...)`，也都合规。

⚠️ 但用 `int` 装"分"上限是 2,147,483,647 分，折合 **21,474,836.47 元（约 2147 万元）**——大额转账第一天就溢出（好在 `intValueExact()` 是抛异常而不是静默回绕，属于"能炸出来"的错）。银行做法：内部一律 `long`/`BIGINT` 存最小货币单位（人民币 = 分）或用 `DECIMAL(18,2)`；**跨币种还要带"小数位数量"**（有的币种 0 位或 3 位小数，不能硬编码 ×100）。

| 规则 | 正确 | 错误 | 后果 |
|------|------|------|------|
| 类型 | `BigDecimal` / `long`（分） | `double` / `float` | 0.1+0.2≠0.3，账永远不平 |
| 构造 | `new BigDecimal("1.23")` | `new BigDecimal(1.23d)` | 把二进制误差搬进十进制 |
| 比较 | `a.compareTo(b) == 0` | `a.equals(b)` | `1.0` 与 `1.00` 判不等 |
| 除法 | `a.divide(b, 2, RoundingMode.HALF_UP)` | `a.divide(b)` | 除不尽抛 `ArithmeticException`（正例 `ModelUsageRecorder.java:131-136` 显式给了 scale 与舍入） |
| 落库 | `DECIMAL(18,2)` 或 `BIGINT` 分 | `DOUBLE` / `DECIMAL(10,2)` | 精度丢失 / 额度溢出 |

**舍入差异带来的分差**：逐笔舍入 vs 汇总后舍入、HALF_UP vs HALF_EVEN 都会产生 1 分钱差。银行做法是**先定规则再写代码**（全行统一舍入模式、统一舍入发生的位置），剩余分差在对账时按容差自动核销并留痕——**分差不是 bug，说不清来源的分差才是 bug**。**多币种折算**还要把折算所用汇率随交易一起落库，否则事后无法复算，监管检查与差错追溯都做不了。

## 十三、资损防控：为什么"资损"是最高优先级事故

- **事前**：限额（单笔 / 日累计 / 月累计 / 账户级 / 渠道级）、黑白名单、客户风险等级、重复交易识别。
- **事中**：校验（金额三要素、借贷平衡、账户状态、权限与授权）、开关与熔断、单笔超时**不重试**。
- **事后**：准实时核对（分钟级单边账）、日终对账、账务重算抽核、差错台账。
- **应急**：预案（发现 → 止血 → 定损 → 追损 → 复盘）、可一键关闭的资损开关、7×24 联系链（流程见 [10 篇](./10-银行研发运维流程与投产管控.md)）。

> 银行把资损排最高优先级，不是因为"钱多"，而是因为**资损不可逆且不可辩解**：性能问题可以道歉，账错了要么客户有钱还、要么银行自己掏，还牵涉监管报送。所以被问"你怎么防止重复付款"，标准答法按四层给：**幂等唯一键 → 状态 CAS → 未知态不重试 → 对账兜底**，一条都不能少。

## 十六、初学者常见误区

| 误区 | 真相 |
|------|------|
| "加了 Redis 幂等就安全了" | Redis 是加速挡不是权威：会丢、会 fail-open 放行、占位还早于事务提交（`IdempotentAspect:26`）。用了它就要能当场指出唯一约束在哪一列、状态判断在哪一行 |
| "'更新余额'就是一句 UPDATE" | 背后要有：同事务的分录登记、CAS 条件、余额快照、借贷平衡校验、失败可重算。少任一项，出错时你连"从哪开始错"都答不出 |
| "对账 = 查一下有没有不一致" | 对账是闭环：取数 → 匹配（含容差）→ 差错分类 → 挂账 → 核销 → 资金动作 → 留痕 → 下轮确认不再出现。只查不修等于把 bug 攒成一笔笔待爆的账 |
| "用了事务消息就不会重复记账" | 事务消息保证必达、不保证只达一次；"至少一次投递 + 幂等消费"才是安全组合（`PaySuccessListener:18` 注释已写明） |
| "超时了重试一下就好" | 超时可能是"对方已成功"，盲目重试 = 重复付款。正确动作是原交易查询 → 冲正 → 挂账，**慢永远比错便宜** |
| "金额差 1 分钱无所谓" | 1 分说明某处舍入规则不一致，而这条规则影响百万笔交易。分差也要留痕核销，不允许"抹平" |
| "状态字段随便加一个就行" | 取值集合、可重入性、终态定义要写成设计并由代码 + DB 双重约束。`markRefunded` 无前置态校验就是"状态只用来记录、不用来守卫"的典型 |
| "分布式事务能解决跨系统一致性" | Seata 只能回滚它管得住的 DB 分支，管不了 MQ 与外部渠道（`OrderServiceImpl:103-104` 注释自己承认）。跨系统的正确答案是最终一致 + 对账 |
