## 一、为什么 JD 里"研发"和"运维"写在同一句话

互联网的常态是开发写完丢给 SRE，出事叫 SRE。银行的常态是**研发运维一体化**——软件研发中心（软开中心）对自己开发的应用的生产运行负最终责任。这不是加班文化，是三条硬约束逼出来的：

1. **生产权限收得很紧**。开发账号进不了生产库、点不了生产发布按钮。你不能操作，但你必须解释——出问题时第一个被叫去查日志、判影响、定方案的还是开发。
2. **变更必须有人出方案**。生产变更单里有一栏"实施方案编写人"，通常就是应用负责人（开发），运维只做"复核 + 按单操作"。运维不会替你设计回退路径。
3. **监管问责追到系统**。发生资损或中断，检查对象是"这个系统的研发和运维管理是否到位"，不区分甲方乙方。

职责边界要背下来（面试高频："上线当晚你干什么"）：

| 角色（通用叫法）   | 负责什么                          | 不负责什么            | 开发要配合的动作                  |
| ------------------ | --------------------------------- | --------------------- | --------------------------------- |
| 应用运维           | 应用启停、发布执行、日终盯屏      | 不改代码、不判业务影响 | 出启停顺序表、出验证案例          |
| 系统运维           | 主机、OS、容器平台                | 不管应用逻辑          | 提资源需求（CPU/内存/磁盘）       |
| DBA                | 生产库账号、DDL/DML 执行、备份    | 不写业务 SQL          | 出 SQL + 影响行数预估 + 回退      |
| 网络               | 防火墙策略、专线、负载均衡        | 不懂端口的业务含义    | 提开通申请（源/目的/端口三元组）  |
| 安全               | 漏扫、渗透、账号审计              | 不修漏洞              | 按整改单限期修复并复测            |
| 科技风险 / 内控    | 变更审批、制度符合性检查          | 不碰技术实现          | 提供证据材料（评审记录、签字）    |

记法：**运维有手，开发有脑；生产上的每个动作，开发出方案、运维执行、双方签字。**

## 二、从需求到投产：一条完整流水线

下面是行业通用形态的泳道图（各行阶段名可能不同，但顺序和"必须有产出物"一致）。

```text
【业务/需求方】  业务需求书 ──┐
                              ▼
【可研/立项】   需求分析 ─→ 可研报告 ─→ 立项批复 + 预算 + 版本火车排期
                              │
                              ▼
【开发(软开中心)】 概要设计 ─→ 详细设计 ─→ 编码 ─→ 代码评审 ─→ 合入版本分支
                              │                                   │
                              ▼                                   ▼
【测试】        开发自测案例 ─→ SIT 集成测试 ─→ 缺陷回归 ─→ SIT 准出
                              │                                   │
                              ├──────────→ UAT 业务验收(签字) ←───┘
                              │                       │
                              └──→ 性能测试/安全渗透 ─┴→ 全部准出报告
                                                      │
                                                      ▼
【变更管控】  投产申请 ─→ 变更评审(CAB) ─→ 批准变更窗口 ─→ 双人复核授权
                                                      │
                                                      ▼
【投产实施】  投产前检查 ─→ 进窗口 ─→ 实施 ─→ 冒烟 ─→ PVT 验证案例
                              │                        │
                        失败 ─┴→ 回退方案执行 ─→ 恢复   ├ 成功: 版本封存/留档
                                                      ▼
【运维移交】  监控告警接入 ─→ 应急预案更新 ─→ 值班表 ─→ 投产总结(T+1/T+7)
```

三个细节：① **准出是关卡不是进度**——SIT/UAT/性能/安全任一没签，变更单提交不上去（"测试报告没盖章，生产见不到这个版本"）；② **UAT 必须业务签字**，开发自认符合需求不算，谁签字谁担责；③ **投产后有 T+1 / T+7 两次观察**，第一天看日终跑批能不能过（很多 bug 只在批里暴露），第七天看慢累积问题（内存泄漏、连接池、数据量上来后的慢 SQL）。

### 2.1 交付物速查表（每个字都要能写出来）

| 交付物           | 谁写               | 核心内容                                                     | 银行为什么必须有                     |
| ---------------- | ------------------ | ------------------------------------------------------------ | ------------------------------------ |
| 需求规格说明书   | 业务 + 需求分析    | 功能点、字段级规则、异常分支、报表口径                       | 开发的唯一输入依据，也是 UAT 案例来源 |
| 可研报告         | 项目经理           | 技术可行性、投入产出、替代方案、风险                         | 立项批文的支撑材料                   |
| 概要设计         | 系统设计人员       | 系统边界、接口清单、数据流向、非功能指标（TPS/响应时间）     | 评审对象，跨团队约定的起点           |
| 详细设计         | 模块开发           | 表结构、状态机、算法、异常与差错处理、幂等点                 | 代码评审对照物；离职交接的救命物     |
| 接口文档         | 服务提供方         | 字段、类型、必输、错误码、样例报文、幂等约定                 | 联调依据；出问题时判定"谁违约"       |
| 测试案例         | 开发自测 + 测试    | 正常/边界/异常/并发/回退，含预期结果                         | 案例即证据，覆盖度是审计要看的       |
| 变更/投产方案    | 应用开发负责人     | 步骤化操作序列 + 执行人 + 验证点 + 时间点                    | 生产操作的唯一授权依据               |
| 回退方案         | 同上               | 触发条件、决策人、退到哪、**数据怎么办**、回退后验证         | 没有它，变更不予批准                 |
| 投产总结         | 项目经理           | 是否按计划、异常与处置、遗留项、下次改进                     | 闭环证据，监管检查会翻的材料         |

### 2.2 为什么银行文档量比互联网大

三件事逼出来的，不是折腾人。**审计与追溯要求"决策过程可见"**：互联网问"这段代码谁写的"，银行问"当时为什么允许这么做、谁批准的、评估过风险吗"，文档就是当时的证据。**外包协作占比高**：核心系统常见"行内出设计和评审、外包出编码"，没有可执行的详细设计外包无法工作，没有接口文档就无解扯皮。**人员流动与系统长寿并存**：一个账务系统跑 15-20 年，写它的人 5 年内可能全走光，代码注释会腐化，结构化文档是低成本的组织记忆。

别因为"文档很虚"就少写——在银行，你写的详细设计就是你自己的免责证据。

## 三、环境体系与配置管控

### 3.1 环境矩阵（速查表）

| 环境       | 常见称呼      | 数据来源                     | 访问控制                    | 典型用途                     |
| ---------- | ------------- | ---------------------------- | --------------------------- | ---------------------------- |
| 开发       | DEV           | 造的假数据                   | 项目组内                    | 编码、单元自测               |
| 集成       | INT / 联调    | 造的假数据                   | 项目组 + 联调方             | 跨系统接口打通               |
| SIT        | 系统测试      | 造假数据 + 基准数据集        | 测试团队主导                | 功能测试、缺陷回归           |
| UAT        | 用户验收      | **脱敏后的准生产数据**       | 业务人员                    | 业务签字验收                 |
| 性能测试   | PERF          | 造数（数据量贴近生产）       | 测试 + DBA                  | 压测、容量评估、SQL 验证     |
| 准生产     | PRE / 类生产  | 脱敏 + 生产同版本配置        | 严格审批、操作留痕          | 投产演练、回退演练           |
| 灾备       | DR            | 复制生产                     | 平时不可写                  | 切换演练                     |
| 生产       | PROD          | 真实                         | 三权分立 + 堡垒机 + 录屏审计 | 真实交易                     |

准生产不是"多一套测试机"，它的作用是让**投产步骤被真跑过一遍**，包括投产脚本、参数变更和回退。投产窗口通常只有 2-4 小时，不是拿真生产练手的地方。

### 3.2 测试数据的红线

UAT 想看真实数据、压测想要大数据量，最省事的做法是从生产导一份——**这在银行明确违规**。生产数据含客户身份信息、账号、交易明细，属敏感个人信息，未脱敏不得离开生产。脱敏也不是简单 `REPLACE`：账号要保持格式（长度/校验位不变才能过校验）、金额做同比例扰动、姓名证件号整体替换，且脱敏规则本身要评审留痕。详见 [银行业信息安全管理规范](./07-银行业信息安全管理规范.md)。

本仓库这条线上是干净的，可作正例：`deploy/testdata/` 下三个文件全是手工构造的合成数据，`redbox-test-data.sql:2` 标明"可选 MySQL 测试数据"，`:4-6` 还提示了"直插库不会触发向量化"这个坑（写脚本的人知道副作用并留在文档里，是好习惯）。

### 3.3 配置管控与"密钥不落代码库"

目标态：任何口令、密钥、证书私钥不进代码库、不进镜像、不进构建参数，统一由 KMS（密钥管理系统）或密码机在运行时注入，配置里只存引用。

本仓库**做得比预期好**，绝大部分配置走的是占位符注入：

- `ai-cs-gateway/src/main/resources/application.yml:15-16` 用 `${REDIS_HOST:127.0.0.1}` / `${REDIS_PORT:6379}`，本地有默认值、生产由外部注入。
- `ai-cs-user/src/main/resources/sharding-user.yaml:33`、`:42`、`:51` 数据源口令写 `$${DB_PASSWORD}`（ShardingSphere 的转义占位），`:14` 的注释还诚实标注了自己的覆盖范围："当前仅 username/password 走环境变量（DB_USER / DB_PASSWORD），host/port 直接写死"。
- `tools/nacos-config/aics-shared.yml:9-10` 两行注释解释"不要写 `password: ""`（空串），Redisson 会拿空串发 AUTH 被拒"——这里根本没有落口令。
- `deploy/k8s/middleware-secrets.example.yaml:3` 直接写"此文件只作为字段结构模板，禁止提交真实密码"，值处填 `replace-with-strong-password`。
- `deploy/docker-compose/docker-compose-all.yml:16`、`:66`、`:153` 中间件口令均为 `${VAR:default}` 形态。

⚠️ **仍有真实缺口**（只列路径，不列值）：

| 位置                                        | 问题形态                                                       | 目标态改造                       |
| ------------------------------------------- | -------------------------------------------------------------- | -------------------------------- |
| `tools/nacos-config/ai-cs-order.yml:9`、`:10` | 数据源 URL 直写公网 IP、账号写死 `root`（口令本身已达标：`:6` 留空、`:11` 走 `${}` 占位）——**泄露的是连接入口与高权限账号名** | 主机/端口一并外部注入，改用低权限专用账号 |
| `deploy/scripts/verify-deploy.sh:45`、`:60` | 数据库账号与口令以命令行参数内联在 `mysqladmin ping` 里（明文入仓 + 进程列表可见） | 用登录认证文件或环境注入         |
| `Jenkinsfile:22` → `:79-84`                 | API Key 以**构建参数**传入再写进 Secret，会留在构建参数历史与日志 | 改由外部 Secret / 凭据插件注入   |

> ❌ 本仓库不存在：KMS 集成、配置加密（如 Jasypt）、密钥轮换、密钥访问审计。

## 四、代码与制品管控

### 4.1 分支模型：版本火车驱动

银行常见形态不是 Git Flow，而是**按投产版本切分支**：主干/开发分支随时可丢弃；**版本分支（release）一个投产版本一条**，从立项起建，只接受该版本范围内的需求，投产后打 tag 封存；**补丁分支**用于生产紧急修复，修完要"双合"（既回主线又合入当前版本）。这就是为什么**需求搭车**（没排进这班车、中途硬塞进当前版本）是高风险动作——它破坏分支内容的可追溯性，评审要重走一遍。细节见 [Git 工作流与分支模型](../17-研发效能与工程实践/01-Git工作流与分支模型.md)。

### 4.2 入库检查：有规则不等于有门禁

银行通常要求"入库即扫描"：编码规范（Checkstyle/PMD）、静态缺陷（SonarQube/SpotBugs）、开源组件与已知漏洞（SCA）、许可证审查（禁 GPL 传染性协议）。本仓库现状是**只有覆盖率，没有静态扫描**：

- ✅ `pom.xml:343-345` 把 JaCoCo 的 `check` 目标绑到 `verify` 阶段，`:354` LINE ≥ `0.40`、`:359` BRANCH ≥ `0.30`；`ai-cs-pay/pom.xml:119-122` 只声明插件、不复写配置，因此继承了这套门限。
- ⚠️ **但门禁在流水线里根本不触发**：`Jenkinsfile:64` 跑的是 `mvn test -B`，`test` 阶段停在 `verify` 之前；`Jenkinsfile:17` 的 `SKIP_TESTS` 默认值就是 `true`，连 `test` 都跳过（`:51-55` 的 `when` 表达式）。两道"跳过"叠加 = 覆盖率门禁形同虚设。
- ❌ 不存在：Checkstyle / PMD / SpotBugs / SonarQube / SCA / 许可证检查（全仓 `find` 零命中）。

面试可以直接讲这个：**有规则不等于有门禁，要看它在哪个阶段、被谁触发。**

### 4.3 依赖白名单

银行不允许随便引第三方 JAR，原因有三：许可证风险（商业闭源/传染性协议）；漏洞响应——出 0day 时必须能在分钟内回答"哪些系统用了这个组件的哪个版本"，只有私有仓库 + 白名单做得到；国产化/信创约束。落地形态是"行内私服 + 引入申请 + 安全评估 + 登记台账"，新依赖要走一次小型评审。

### 4.4 制品与镜像可追溯

目标态：一个制品对应**不可变版本号 + 来源提交 + 构建时间 + 依赖清单**，任何一次生产部署都能回答"这个进程跑的是哪次构建的哪个产物"。本仓库正例反例并存：

- ✅ `Jenkinsfile:28` `IMAGE_VERSION = "${params.VERSION ?: env.BUILD_NUMBER}"` 用构建号做版本，`:35` 打印 `git rev-parse --short HEAD`，日志里能反查提交。
- ⚠️ `deploy/scripts/k8s-build-push.sh:28`、`:34`、`:39` 把同一镜像同时打成 `:${VERSION}` 和 `:latest` 并**连 `latest` 一起推**。`latest` 是可覆盖标签，生产一旦用 `latest` 拉起就无法确定实际内容。银行做法是禁用 `latest`。
- ⚠️ `ai-cs-gateway/Dockerfile:17` `FROM eclipse-temurin:17-jre-jammy` 用可变 tag 而非 digest 锁定，运行阶段没有 `USER` 指令（默认 root 跑进程）；`:14` 在镜像构建里再次 `-DskipTests`——即使流水线不跳测试，容器构建阶段也跳。
- ❌ `deploy/scripts/` 与 `deploy/k8s/` 全目录找不到任何镜像漏洞扫描步骤。做法见 [镜像构建优化与安全扫描](../16-云原生与GitOps/06-镜像构建优化与安全扫描.md)；评审实操见 [CodeReview 实战](../17-研发效能与工程实践/04-CodeReview实战.md)。

### 4.5 本仓库的硬缺口：pay 服务没有投产路径

银行评审最怕"范围不清"，这张表就是典型问题：

| 检查项                          | gateway/user/… | ai-cs-order | **ai-cs-pay** |
| ------------------------------- | -------------- | ----------- | ------------- |
| `Dockerfile` 存在               | ✅             | ✅          | ❌ 无         |
| `k8s-build-push.sh:6` 白名单    | ✅             | ❌ 不在     | ❌ 不在       |
| `deploy/k8s/services/*.yaml`    | ✅（8 个）     | ❌ 无       | ❌ 无         |
| `docker-compose-all.yml`        | ✅             | ❌          | ❌            |
| `deploy.sh:35` 单机部署清单     | ✅             | ❌          | ❌            |

**资金服务恰恰是唯一一个完全无法通过本仓库脚本部署上线的模块**，这在银行属于投产申请直接驳回（投产范围与制品清单不一致）。而且 `deploy.sh:41` 对缺失镜像只打 `WARN` 然后跳过——**会静默少部署整个服务**。动手练习 2 会要求补齐。

## 五、投产与变更管控（银行特色，重点）

### 5.1 变更窗口：由业务决定，不由技术决定

```text
 00:00 ─ 06:00   联机低峰：可做非中断类变更（参数、扩容）
 09:00 ─ 17:00   营业时段：禁止核心/账务类变更          ← 与互联网最大差别
 17:00 ─ 20:00   日终批量窗口：跑批进行中，禁止发布被批处理依赖的版本
 20:30 ─ 23:00   ★ 常用投产窗口：批起之前或次日开门之前，且必须预留回退时间
 23:00 ─ 24:00   冻结缓冲：只允许观察与回退，不允许任何新动作
```

（行业通用形态，**具体窗口以行内制度与现行有效版本为准**。）窗口取决于三件事：**日终跑批的时刻、开门营业的时刻、以及"最晚必须开始回退"的时刻**。最后一个最易被忽略——窗口 4 小时而回退要 1.5 小时，实际只有 2.5 小时做实施；超时就自动进入回退，不是"再试半小时"。

### 5.2 变更等级与审批（速查表）

| 等级 | 典型场景                                   | 审批层级             | 复核要求                   | 窗口           |
| ---- | ------------------------------------------ | -------------------- | -------------------------- | -------------- |
| 重大 | 核心账务、支付清算、总账；结构性变更       | 部门 + 分管行领导    | 双人 + 准生产演练过        | 专门批准窗口   |
| 一般 | 电子渠道、报表、非资金功能                 | 处室/团队负责人      | 双人复核                   | 常规窗口       |
| 低   | 前端文案、参数（不改逻辑）                 | 团队内               | 单人 + 事后确认            | 灵活，避开高峰 |
| 紧急 | 生产故障处置、资损止血                     | 事后补审批，先做后报 | **电话授权 + 录音/留痕**   | 立即           |

紧急变更是新手最容易踩的坑：**可以绕过流程，不能绕过留痕**。事后必须补齐变更单、影响说明和 RCA，否则"未经审批变更生产"本身就是审计发现项。

### 5.3 投产方案：必须是一份可执行的检查清单

银行格式的投产方案不是段落文章，是**逐条可打勾的操作序列**，每条含序号 / 操作 / 执行人 / 验证方式 / 预期结果 / 实际结果 / 时间。以本仓库 pay 服务上线为例：

```text
□ T-3  准生产完成全流程演练，演练记录归档（执行人：开发）
□ T-3  DBA 复核 DDL：pay_transaction 建表/变更语句已在准生产验证（执行人：DBA）
□ T-2  制品清单核对：镜像 tag = aics/pay-service:<BUILD_NUMBER>，digest 已登记
□ T-2  配置变更单：Nacos dataId ai-cs-pay.yml 差异 diff 已评审（禁则：无明文口令）
□ T-1  依赖服务确认：order / 渠道 Mock 可用；接口文档双方版本一致
□ T-1  回退方案单独成文并被批准（含数据回退，见 5.4）
□ T-0  窗口进入确认：日终批未启动 / 联机已降级公告（执行人：应用运维）
□ 00   滚动发布（顺序写清先下游还是先上游）
□ 01   数据库变更执行（先 DDL 后 DML，逐条记影响行数）
□ 02   健康检查：/actuator/health = UP，且启动日志无 ERROR
□ 03   冒烟：下单 → 支付 → 回调 → 订单转 PAID，一笔真实流水
□ 04   PVT 业务案例集（含金额一致性核对 SQL，见 09 篇 §2.4）
□ 05   观察期：联机成功率、响应时间 P99、异常日志关键字
□ 06   决策点：GO / NO-GO（签字人 + 时间戳）
□ 07   退出窗口：恢复公告、值班表更新、T+1 日终盯批安排
```

**决策点是这份清单的灵魂**：没有预设决策点的投产方案，等于把临场判断留给凌晨两点的疲惫人员。

### 5.4 回退方案：回滚镜像 ≠ 回退

新手以为回退就是 `kubectl rollout undo`。银行问的是**数据怎么办**：

| 变更类型           | 制品回退             | 数据回退                                  | 风险                     |
| ------------------ | -------------------- | ----------------------------------------- | ------------------------ |
| 纯代码（无表变更） | 回旧镜像，滚动重启   | 无需                                      | 旧代码能否处理新流量字段 |
| 加字段/加索引      | 回退代码，**保留新对象** | 通常不回退（向前兼容）                  | 新索引影响旧版本写入性能 |
| 改语义/迁移数据    | 回退代码             | 必须靠**备份表 + 反向脚本**，且提前演练   | 迁移中途失败留半态       |
| 涉及在途资金       | 不能简单回退         | 先止血（关渠道/限流）+ 差错挂账 + 事后逐笔处理 | 回退可能造成重复记账 |

本仓库有一个**正例值得抄**：`deploy/mysql/user-sharding-migrate.sql`。`:10-13` 先写执行前提，其中 `:12` 明确要求"ai-cs-user 服务已停止写入"——这就是变更窗口意识；`:15-16` 用 `RENAME TABLE` 把原表改名备份而不是 `DROP`，`:15` 注释直说"不删数据，可回滚"；`:30-39` 用一段 `UNION ALL` 的 `COUNT(*)` 比对源表与 8 张分片表行数——这正是对账里的**控制总数**（control total，用汇总数快速判定有没有丢行/重行）。一个脚本同时具备窗口、可回滚、可校验三要素。

缺口同样明显：⚠️ 该脚本的路由口径靠 `:8` 的注释"与 `UserIdLast4ModShardingAlgorithm` 保持一致"约束 Java 侧，**两处规则没有单一事实来源**，属典型口径漂移风险。❌ `deploy/scripts/` 与 `deploy/k8s/` 全目录 `grep` "rollout undo / rollback" 零命中，**不存在任何应用回退脚本**；`Jenkinsfile` 也没有 `input` 人工审批步骤和回退 stage，它是纯自动直通（`:32 → :39 → :50 → :69 → :89 → :104 → :119 → :134`）。

### 5.5 双人复核、灰度与投产后验证

**双人复核（four-eyes）**：生产上每个不可逆动作，一人操作、一人核对并留痕（实操常是"复核者在工单里回一句'已核对，与方案第 X 条一致'"）。**灰度与分批**：多实例先起一台、多网点先切一个分行、多渠道先放 1% 流量——但注意**账务类变更往往不能灰度**，同一笔钱的记账规则不能一半新一半旧，只能靠窗口 + 回退兜底。**PVT（投产后验证）**至少三层：进程活（health）、接口通（真实调用）、业务对（案例 + 数据核对）。

本仓库**⚠️ 验证严重不足，只到第一层**：

| 位置                                     | 现状                                          | 差距                       |
| ---------------------------------------- | --------------------------------------------- | -------------------------- |
| `Jenkinsfile:134-146` "部署验证" stage   | 只有 `kubectl get nodes/pods/svc`             | 连 health 都没查           |
| `Jenkinsfile:20` `VERIFY_DEPLOY` 描述    | "查看 Pod、Service 和 rollout 状态"           | 目标就定在"进程活着"       |
| `deploy/scripts/verify-deploy.sh:52-53`  | 最深处是 `actuator/health` 返回 200           | 无业务案例、无数据核对     |
| `deploy/scripts/verify-deploy.sh:22-33`  | `check()` 把失败吞成 `FAIL++` 计数            | 见下一行                   |
| `deploy/scripts/verify-deploy.sh:99-106` | 结尾只打印"有 N 项检查失败"，**不 `exit 1`**  | 退出码恒 0，无法阻断流水线 |
| `Jenkinsfile:19` `INIT_DATABASE` 描述    | 自认"重复执行会覆盖部分初始化逻辑"            | 无幂等保障，也无回退       |

`Jenkinsfile:151-169` 的 `post` 块在 failure 时打印 4 条排查提示，是好雏形，但它只是文字，**不触发任何处置动作**。窗口内的失败处置必须有预案：冒烟失败立即判"影响范围 + 能否隔离"且**决策时限提前写死**（如 30 分钟）；不可隔离或原因未知就回退，不做"再改一版试试"；回退也失败就升级（值班经理 → 科技负责人 → 业务启动应急/公告）。铁律是**窗口关闭前必须让生产回到已知状态**——要么新版本要么旧版本，最坏的是中间态。

## 六、发布技术手段

### 6.1 优雅停机与零丢失

银行的停机窗口由业务定（§5.1），但**窗口之内仍要求不丢在途交易**，靠两侧配合：应用侧先摘流量、处理完在途请求再退出；编排侧给足终止宽限期、不要 SIGKILL。这块本仓库做得**相当到位**，可直接当简历证据——全部 11 个服务（gateway/user/knowledge/chat/search/message/notify/order/pay/product/mq）的 `src/main/resources/application.yml` 都在 `:2` 写 `shutdown: graceful`、`:7` 写 `timeout-per-shutdown-phase: 30s`。以支付服务为例（`ai-cs-pay/src/main/resources/application.yml:1-7`）：

```yaml
server:
  shutdown: graceful
  port: 8089

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

`:2` 让 Spring Boot 收到终止信号后停止接收新请求、等已有请求处理完；`:7` 是最长等待时间——**30 秒就是"零丢失"与"必须让路"之间的取舍点**。银行里要注意：联机交易超时通常配在 20-30 秒，30 秒宽限刚好覆盖最坏情况；若系统里有长事务或批量接口，30 秒就不够，必须单独评估。

编排侧的缺口在 `deploy/scripts/k8s-deploy-services.sh:39-41`：

```bash
  echo "Deploying ${deployment} with image ${full_image}"
  kubectl set image "deployment/${deployment}" "${container}=${full_image}"
  kubectl rollout status "deployment/${deployment}" -n "${NAMESPACE}" --timeout=300s
```

`:41` 会等新 ReplicaSet 就绪再进下一轮循环（`:42`），所以**单个服务内部仍是 K8s 滚动更新，不会一次全停**。但有三个问题：① 串行发 7 个服务，任一失败则 `set -euo pipefail`（`:2`）直接退出，**前面已发布的不回退 → 半新半旧**；② 无分批灰度、无 `kubectl rollout pause`；③ 无 `rollout undo`。原理与更完整做法见 [优雅停机与零丢失滚动更新](../07-运维部署/06-优雅停机与零丢失滚动更新.md)。

### 6.2 日终跑批与发布顺序的冲突

银行独有的坑：联机（OLTP）可以滚动发布，**批量不行**。日终跑批跨多个应用——清算批在 A、记账批在 B；若 A 已升 B 未升，新 A 产出的中间文件旧 B 读不懂，跑批失败就得在第二天开门前处理完。结论：**被批处理依赖的版本必须整体停联机再整体升，不能滚动**，这就是 §5.1 窗口那么窄的根因。联机与批量并行时（有些行允许日终期间部分联机继续），批量会持大量表锁/行锁，联机交易被阻塞甚至超时；同一张表上批写与联机写并发时，幂等点和唯一键是最后一道防线（见 [金融级一致性与对账实战](./09-金融级一致性与对账实战.md)）。

本仓库的"批"很轻，但有一个真实的双轨问题值得讲：

| 位置                                              | 机制                                       | 多实例行为             |
| ------------------------------------------------- | ------------------------------------------ | ---------------------- |
| `ai-cs-order/.../task/OrderTimeoutScheduler.java:29` | `@Scheduled(fixedDelay = 300000, initialDelay = 60000)` | **每个实例都会跑** |
| `ai-cs-order/.../task/OrderTimeoutScanJob.java:27-32` | `@XxlJob("orderTimeoutScanJob")` 集中调度 | 由调度中心路由到单台   |

`OrderTimeoutScanJob.java:24-25` 的注释还给了运维建议："路由策略建议 `FIRST`，阻塞处理策略建议`丢弃后续调度`"——前者控制落到哪台机器，后者防止上一轮没跑完又开一轮（**跑批重叠是银行经典事故源**）。而 `@Scheduled` 那条在滚动发布期间会出现"新旧版本同时跑同一个扫描"，只能靠业务幂等兜住。这个对比很适合当"发布期间批怎么办"的面试案例。

> ⚠️ XXL-Job 只在 order 模块接入（`ai-cs-order/pom.xml`、其 `application.yml`、`deploy/mysql/xxl-job-init.sql`）；pay 模块既无 `@Scheduled` 也无 `@XxlJob`，其补偿任务只能靠人工调 `PayController:126-129` 的 `POST /pay/compensate` 触发（见 09 篇 §7）。

## 七、运维体系：ITIL、监控、值班与故障

### 7.1 ITIL 五个核心流程（速查表）

| 流程     | 人话解释                                                    | 银行里的日常体现                     |
| -------- | ----------------------------------------------------------- | ------------------------------------ |
| 事件     | Event：任何"不该发生"的情况，先恢复再说原因                 | 告警、电话、网点报障，目标是快速止血 |
| 问题     | Problem：反复发生或原因不明的事件，找根因                   | 事件单升级为问题单，做 RCA           |
| 变更     | Change：任何对生产的改动，需审批与回退方案                  | 见 §5，最严格的流程                 |
| 发布     | Release：一组变更打包成一次可部署的版本                     | 版本火车、制品封存                   |
| CMDB     | 配置管理数据库：系统/主机/中间件及关系的台账                | 故障影响面分析、变更影响评估都查它   |

CMDB 常被新人轻视，但它是银行运维的中枢：**告警打到哪台机器 → 这台机器属于哪个应用 → 这个应用支撑哪个业务产品 → 影响多少客户**。这条链断了，故障分级和对外公告都做不出来。

### 7.2 监控与告警：银行盯的四类指标

1. **联机交易**：按交易码/接口维度的成功率、响应时间（看 P99 与最大，不只看均值）、交易量。核心系统成功率下降是最高优先级。
2. **批作业**：**日终是否在承诺时间前完成**——银行有"批完成时限"考核，因为第二天开门的事都排在这之后。看的是"起没起、跑完没、几点跑完、比昨天慢多少"。
3. **账务与差错**：借贷不平笔数、单边账/挂账笔数、对账差异金额。**这类指标不看趋势看绝对值，非 0 即告警**。
4. **资源与中间件**：连接池、线程池、GC、MQ 堆积、主从延迟、锁等待。

本仓库现状：`deploy/observability/` 下有 `prometheus.yml`、`grafana/`、`tempo.yaml`、`otel-collector.yaml`，采集与看板链路齐全——但 `prometheus.yml` 只有 `:3` `scrape_interval: 15s` 和 `:8` 一个抓取 job，**全文件没有 `rule_files` 也没有 `alerting` 段，仓库内找不到一条告警规则**。即：**有指标、无告警**，从"能看"到"出事能叫人"这一步没走。链路侧 `ai-cs-pay/src/main/resources/application.yml:30` 是 `probability: ${TRACING_SAMPLING:1.0}`（同行注释"生产可调低采样率，本地全采样"）——注意银行生产通常要求**全量或按交易号强制采样**，因为排障需要"这一笔的完整链路"，1% 采样在低峰故障时等于什么都没采到。

告警收敛分级见 [告警治理](../13-稳定性工程/07-告警治理.md)；值班与升级见 [oncall 手册与故障响应](../13-稳定性工程/08-oncall手册与故障响应.md)；复盘见 [RCA 根因分析与复盘](../13-稳定性工程/06-RCA根因分析与复盘.md)。

### 7.3 故障分级与重大保障时期

分级维度通常是影响客户数、影响时长、资金损失金额、是否涉及重要信息系统、是否可能被媒体或监管关注。**银行特有且最要命的一条**是"对外公告 + 监管报送"——达到某一级必须向监管报告，这使分级判定格外严肃，也让"降级上报"成为一种足以毁掉一个人的行为。

重大保障时期需提前进入值守状态：**年初/春节前**（返乡转账、红包、结工资，交易量峰值）、**"开门红"**（年初营销季，理财存款活动集中、渠道流量激增）、节假日与重大会议、行级营销活动、大版本后的首个日终。保障期通常要求：**变更封板**（冻结非必要变更）、骨干现场值守、预案预演、演练提前完成。新手最容易忽略：**封板意味着你的版本必须赶上前一班车**，错过一班车不是延后一周，是延后一个版本周期。

## 八、数据与 SQL 管控

银行生产库的铁律：**开发不碰生产库**。所有生产数据操作走 DBA，所有 SQL 走审核。

| 管控项      | 规则要点                                                                       |
| ----------- | ------------------------------------------------------------------------------ |
| SQL 审核    | 走审核平台/工单；DBA 评估后执行，开发不直连生产库                              |
| 禁止写法    | 无 `WHERE` 的 UPDATE/DELETE；无界全表扫描；未走索引的大结果集；跨库大事务；隐式类型转换导致索引失效 |
| 事务要求    | 单事务影响行数上限；持锁时长评估；禁止事务里做远程调用（见 09 篇事务边界）     |
| 索引变更    | 附执行计划前后对比（`EXPLAIN`）、锁表评估、耗时评估，必要时低峰执行            |
| 慢 SQL      | 平台自动抓取 + 通报 + 限期整改，**纳入考核**                                   |
| 数据订正    | 双人审批 + 留痕 + 备份 + 可验证（见下）                                        |
| 取数        | 说明用途与字段范围，敏感字段脱敏，禁止随手 `SELECT *` 导出                     |

**数据订正**（改生产上的错账数据）是银行最严肃的日常流程之一：① 先定性质——是数据错还是逻辑错？逻辑错改数据只是止血，必须同时提缺陷走版本修复；② 出方案——订正原因、精确 SQL、**影响行数预估**、备份方式（先建 `_bak_YYYYMMDD` 表或保留反向 UPDATE）、验证 SQL、执行时长；③ 逐级审批（开发 → 应用负责人 → 业务确认金额 → DBA 评估 → 变更审批）；④ 窗口内执行：备份 → 订正 → 验证 → 对账复核 → 归档全套证据；⑤ 涉及金额的必须同步财务/总账口径，事后必须对得上。

对应到本仓库：`deploy/mysql/` 下有 `all-init.sql`、`order-init.sql`、`seata-undo-log.sql`、`xxl-job-init.sql`、`master.cnf`/`slave.cnf`/`slave2.cnf`，属于"初始化脚本"，不是"订正流程"。⚠️ **DDL 由应用启动时代码发起**：`ai-cs-pay/.../config/PaySchemaInitializer.java:11` 注释写"启动时幂等初始化支付流水表（生产可改用 Flyway/Liquibase）"，`:20-47` 用 `CREATE TABLE IF NOT EXISTS` 建表——银行视角这是**明确违规**，生产表结构不能由应用进程持有 DDL 权限来创建；这条注释说明作者知道目标态，只差没做。❌ 不存在：Flyway/Liquibase、SQL 审核规则文件、订正模板、生产库账号权限分级。

实操见 [SQL 调优与执行计划](../12-性能工程/05-SQL调优与执行计划.md)；锁与读写分离见 [MySQL 锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md)。

## 九、灾备与业务连续性

| 概念           | 人话解释                                                                 | 关键点                                   |
| -------------- | ------------------------------------------------------------------------ | ---------------------------------------- |
| 同城灾备       | 同一城市另一机房，延迟低，可近实时同步                                   | 覆盖机房级故障                           |
| 异地灾备       | 另一城市，距离足够躲开区域性灾难                                         | 网络延迟大，通常异步复制，切换有数据损失 |
| **两地三中心** | 生产中心 + 同城灾备中心 + 异地灾备中心                                   | 银行主流形态                             |
| 单元化         | 按客户/账户维度切成自包含单元，一个单元故障只影响该单元客户              | 控制"爆炸半径"，也解单库容量瓶颈         |
| RTO            | 恢复时间目标：从中断到业务恢复**允许多久**                               | 业务决定，不是技术决定                   |
| RPO            | 恢复点目标：切换后**允许丢多久的数据**                                   | RPO=0 要求同步复制或强一致，代价很高     |

**为什么灾备必须"演"不能只"有"**：灾备环境的配置长期无人改动、无人访问，真出事才发现密码过期、网络策略没开、版本落后三年、DNS 没同步。银行对重要信息系统的灾备有切换频率与报告要求（**具体指标以行内制度与现行有效版本为准**）。演练通常要求：真实切、计时、业务验证、总结问题清单并闭环。

**高可用不等于多部署一套**：主从复制有延迟（切过去可能丢数据）、连接串要能漂（VIP/DNS）、状态要能恢复（会话、幂等记录、消息消费位点）、有状态组件切换最难。账务系统切换还必须搭配对账与差错处理，因为切换瞬间一定产生在途交易（见 [金融级一致性与对账实战](./09-金融级一致性与对账实战.md)）。

本仓库现状：`deploy/mysql/` 提供 `master.cnf` + `slave.cnf` + `slave2.cnf`（一主两从**配置模板**），`docker-compose-master-slave.yml` 可拉起主从。❌ 不存在：跨机房/跨地域拓扑、自动切换、演练脚本、RTO/RPO 定义、单元化路由。K8s 多节点（`deploy/scripts/deploy-host1/2/3.sh`）属同集群高可用，不等于灾备。架构模式见 [高可用架构模式](../13-稳定性工程/04-高可用架构模式.md)；声明式部署带来的"配置不漂移、切换可重放"见 [GitOps 与 ArgoCD](../16-云原生与GitOps/03-GitOps与ArgoCD.md)。

## 十四、初学者常见误区

| 误区                                 | 真相                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 投产 = 部署脚本跑完                  | 投产是一次**受管控的生产变更**：申请、评审、批准窗口、双人复核、PVT、总结归档，脚本只是其中一步   |
| 回退就是回滚镜像                     | 代码可以回滚，**数据不能凭空回滚**。难的是备份表、反向脚本、在途资金处置，这些必须提前写进方案并演练 |
| 文档是形式主义                       | 文档是**你的免责证据**和跨团队协作的接口约定。银行里"没记录 = 没发生"，审计只认证据               |
| 运维只是"看监控的"                   | 运维有生产操作权但不做业务判断。开发出方案、运维执行、双方签字——方案质量决定当晚能不能回家       |
| 测试数据从生产导一份最真实           | 生产数据未脱敏不得离开生产，这是安全红线（见 07 篇）。要么造，要么走脱敏流程                       |
| 流水线跑绿就是质量达标               | 门禁要看它在哪个阶段被谁触发。`Jenkinsfile:17` 默认跳测试 + `:64` 只跑到 `test`，覆盖率门限形同虚设 |
| 灾备建好了就不用管                   | 不演的灾备等于没有。配置漂移、版本落后、策略未开，只有真实切换时才暴露                             |
| 紧急变更可以先做就不用补             | 可以先做，但**必须留痕并事后补审批 + RCA**。"未经审批变更生产"本身就是审计发现项                   |
