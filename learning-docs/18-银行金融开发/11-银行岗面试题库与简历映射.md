# 银行岗面试题库与简历映射

> 本篇回答什么问题：银行（含软开中心、科技子公司、外包厂商）**到底会怎么面你**，
> 零金融经验的 Java 后端该怎么把"AI 客服 + 支付"这个项目翻译成银行岗语言，以及手写题怎么写不被追问倒。
> 前置阅读：本模块其余 10 篇（本篇是出口）、[../11-数据结构与算法/11-高频面试题清单.md](../11-数据结构与算法/11-高频面试题清单.md)（算法与数据结构题在那里，本篇不重复）。
> 用法：A 组看自己能不能把要点顺出来；B 组**必须能讲完整链路**；C 组提前把答案改成自己的真事；D 组直接抄进简历。

## 一、先搞清形式：你面的可能是四种不同的面试

| 面试主体 | 典型轮次 | 笔试/测评 | 侧重 | 你要准备什么 |
|---|---|---|---|---|
| **总行软件研发中心（软开）** | 技术面 → 综合面 →（部分有主管面）→ HR 面 | **常有行测 + 性格测试**，部分岗位有技术笔试 | 基础是否扎实、稳定性、可培养性、合规意识 | A 组 + C 组 + 行测刷题 |
| **集团科技子公司**（银行控股） | 技术面 → 综合/HR | 可能有 | 更接近互联网风格，但项目是银行交付 | A 组 + 项目深挖 |
| **外包/厂商驻场**（做银行项目的公司） | 一到两轮技术面，快 | 一般无 | **能不能立刻干活**：技术栈对口、能接受驻场与流程 | 上手速度 + 流程意识 + 稳定性 |
| **业务部门/数据中心面试** | 主管面为主 | 无 | 沟通、责任心、抗压、能否长期做这块 | C 组为主 |

三个必须知道的形式特点：

1. **行测与性格测试是真实筛人环节**，不是走过场。银行行测 ≈ 公务员行测（言语理解、数量关系、判断推理、资料分析）；性格测试看"稳定性 + 合规倾向 + 协作性"，**别装完美**——前后矛盾会被判"掩饰性高"，这恰好是银行最反感的特质。
2. **技术面问得深但不追求新**。技术栈以 Java/Spring/MySQL-Oracle/Redis/MQ/分布式为主，面试官在意"你有没有真正想清楚"。**八股背得溜但讲不清链路，是最高频的失败原因。**
3. **"稳定"是显性偏好**。培养一个懂核心系统的开发要几年，频繁跳槽（3 年 3 跳及以上）会被重点追问，且很难靠话术翻盘——诚实 + 合理动机，比掩饰有效。

## 二、A 组：技术面高频题（含"银行为什么特别看重"）

### 2.1 Java 基础与并发

| # | 题目 | 考察点 | 答题要点（含银行侧重） |
|---|---|---|---|
| A1 | 金额该用什么类型？为什么不能用 `double`？ | 精度意识 | ① `double` 是二进制浮点，`0.1+0.2≠0.3`，钱不能"约等于"；② 用 `BigDecimal`，且**必须用字符串构造**（`new BigDecimal("0.1")`，`new BigDecimal(0.1)` 一开始就错了）；③ 比较用 `compareTo` 不用 `equals`（`1.0` 与 `1.00` 的 `equals` 为 false，因为 scale 不同）；④ DB 侧对应 `DECIMAL(p,s)`，不是 `float`。银行里精度错一分钱就是账务差错 |
| A2 | `BigDecimal` 的舍入模式怎么选？ | 舍入是业务规则 | ① `RoundingMode` 常用 `HALF_UP`（四舍五入）与 `HALF_EVEN`（银行家舍入，长期统计更公平）；② **舍入模式与精度位数必须由业务书面规定**，不能开发自己定；③ 除法必须显式给 `scale` + 舍入，否则无限小数直接抛 `ArithmeticException`；④ 尽量只在最后一步舍入，中间多保留几位，避免误差累积 |
| A3 | `HashMap` 线程不安全体现在哪？并发用什么？ | 并发容器 | ① JDK7 头插法并发下可成环（死循环），JDK8 改成尾插但仍会丢数据/覆盖；② 用 `ConcurrentHashMap`（JDK8 起 CAS + `synchronized` 桶头）；③ `Collections.synchronizedMap` 是整表锁，吞吐差；④ 追问"`computeIfAbsent` 里能再调 `computeIfAbsent` 吗"→ 不能（同 key 递归会死锁/异常） |
| A4 | `volatile` 能保证原子性吗？ | 可见性 vs 原子性 | ① 只保证可见性与禁止重排序，不保证原子；② `i++` 是读-改-写三步，volatile 下仍会丢更新；③ 原子性用 `Atomic*`（CAS）或锁；④ 经典用途是状态开关与 DCL 单例的字段 |
| A5 | `synchronized` 和 `ReentrantLock` 怎么选？ | 锁的能力边界 | ① `synchronized` 自动释放、JVM 优化好、代码简洁；② `ReentrantLock` 提供 `tryLock(timeout)`、可中断、公平锁、多 `Condition`；③ **需要"拿不到锁就快速失败并返回业务提示"时必须用 `tryLock`**——银行渠道防重复提交就是这个诉求；④ `lock()` 必须在 `finally` 里 `unlock()` |
| A6 | 线程池七个参数，拒绝策略怎么选？ | 背压与降级 | ① `corePoolSize/maximumPoolSize/keepAlive/workQueue/threadFactory/handler`；② 执行顺序：核心线程 → 队列 → 非核心 → 拒绝；③ 四种策略：`Abort`（抛异常，默认）/`CallerRuns`（调用方执行，天然降速）/`Discard`/`DiscardOldest`；④ 银行侧重：**绝不能静默丢任务**（丢一个记账请求 = 一笔差错），`Discard` 类策略几乎不可接受，要么 `CallerRuns` 要么快速失败进重试表；⑤ 线程必须命名（`ThreadFactory`），否则故障时看不出是谁在跑 |
| A7 | 如何停止一个线程？为什么不用 `stop()`？ | 中断协作 | ① `stop()` 已废弃——会在任意点终止并释放所有锁，导致对象处于半更新状态；② 用 `interrupt()` + 检查中断标志或响应 `InterruptedException`；③ 阻塞方法被中断会抛异常，**必须恢复中断位** `Thread.currentThread().interrupt()`；④ 生产上更常用"超时 + 优雅关闭 `shutdown()` → `awaitTermination()` → `shutdownNow()`" |
| A8 | `ThreadLocal` 为什么会内存泄漏？ | 生命周期 | ① key 是弱引用、value 强引用，线程池里线程不死 → value 一直被引用；② 用完必须 `remove()`；③ 银行场景常见用途：链路上下文（`traceId`）、操作人信息、数据源路由；④ 追问"异步/线程池切换会丢 `ThreadLocal` 吗"→ 会，需要显式传递（装饰 `Runnable` 或用可继承/Transmittable 方案） |

### 2.2 JVM

| # | 题目 | 考察点 | 答题要点 |
|---|---|---|---|
| A9 | 堆内存怎么分？对象一定在堆上吗？ | 内存模型 | ① 新生代（Eden + 2 Survivor）+ 老年代；② 标量替换/逃逸分析后可能栈上分配，不绝对；③ 栈、方法区/元空间各自存什么要说清 |
| A10 | 什么对象会进老年代？ | 晋升规则 | ① 年龄达阈值；② 大对象直接分配；③  Survivor 放不下走担保机制；④ 银行批量作业一次读几十万条 = 典型大对象/ premature promotion 场景 |
| A11 | G1 和 CMS/ZGC 的区别？生产怎么选？ | GC 选型 | ① G1 分区（Region）+ 可预测停顿模型（`MaxGCPauseMillis`），是当前主流；② CMS 并发标记清除，碎片与重新标记问题，已移除；③ ZGC 停顿亚毫秒级、适合大堆低延迟；④ **银行更看重"停顿稳定可预期"而非"最快"**，交易类系统偏好 G1，账务类批处理可接受较长停顿 |
| A12 | 一次 Full GC 频繁，你怎么排查？ | 现场能力 | ① 先看 GC 日志（`Full GC` 前后老年代占用是否回收的下去）；② `jmap`/MAT 看支配树找大对象与泄漏引用；③ 检查是否有显式 `System.gc()`、堆外内存、元空间不足；④ 讲清"**先定位现象 → 再看证据 → 最后改代码**"的次序，比说对一个答案更重要 |
| A13 | `OOM` 有哪些类型？怎么让线上问题可查？ | 事前准备 | ① 堆 OOM、元空间、`unable to create native thread`、直接内存；② 生产必配 `-XX:+HeapDumpOnOutOfMemoryError` 与 dump 路径；③ 讲出"我配了自动 dump，事后用 MAT 分析"这类实操会加分 |

### 2.3 MySQL

| # | 题目 | 考察点 | 答题要点（银行侧重） |
|---|---|---|---|
| A14 | 事务四个特性，隔离级别分别解决什么？ | 基础 | ① ACID；② 读未提交→脏读；读已提交→不可重复读；可重复读→幻读（InnoDB 靠 MVCC + 间隙锁在很大程度上抑制）；串行化→性能差；③ **银行账务类默认取最保守的一致性策略**，很多老系统直接靠锁；追问"你们项目哪级"要说得出实情 |
| A15 | InnoDB 怎么实现可重复读？MVCC 是什么？ | 原理 | ① 每行隐藏事务 ID + undo 版本链；② ReadView 决定可见版本；③ RC 每次查询生成新 ReadView，RR 事务首次快照复用；④ 长事务的危害：undo 膨胀、版本链变长、锁持有时间长——银行跑批里最常见的性能杀手 |
| A16 | 有哪些锁？什么时候锁表？ | 锁粒度 | ① 全局/表/行；行锁有记录锁、间隙锁、Next-Key；② **`WHERE` 未走索引 → 锁扫描到的全部行（近似锁表）**；③ `UPDATE` 命中唯一索引等值 → 只锁一行；④ 死锁排查看 `SHOW ENGINE INNODB STATUS`，靠固定加锁顺序与缩小事务范围解决。详见 [../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md) |
| A17 | 一条 SQL 突然变慢，怎么定位？ | 调优方法论 | ① `EXPLAIN` 看类型/键/行数/Extra；② 确认索引是否真被使用（最左前缀、函数包裹、隐式类型转换、`LIKE '%x'`、`OR`）；③ 回表 vs 覆盖索引；④ 统计信息过期导致走错索引 → `ANALYZE TABLE`；⑤ 数据量增长需分库分表或归档。银行面试极爱问"你怎么做优化"，**要答流程不要只答技巧** |
| A18 | 主从复制延迟会导致什么业务问题？怎么处理？ | 一致性与运维 | ① 写完立刻读从库 → 读不到自己刚写的数据（"读己之写"问题）；② 处理：关键读强制走主、会话内粘性路由、或等待位点；③ 银行大量报表查询走从库，交易走主库，**读写分离的路由规则必须能人工干预**（故障时一键全回主库） |
| A19 | 大表变更（加字段/加索引）怎么做？ | 生产风险意识 | ① 直接 `ALTER` 会长时间锁/元数据锁等待，业务可能被卡死；② 用在线变更工具（pt-osc / gh-ost 思路）或"影子表 + 双写 + 切换"；③ **必须在变更窗口、有回退方案、有主备延迟评估**——这一条最能体现"银行研发运维"意识 |
| A20 | 分库分表后哪些能力会丢？ | 分布式代价 | ① 跨分片 JOIN、全局排序、分页深翻、分布式事务都变贵；② 分片键选错 → 全路由扫描；③ 项目实例：按用户 ID 后几位分片，扩容量迁移比例高（一致性哈希可改善）；④ 银行倾向"能不分就不分，先归档先分区表" |

### 2.4 Redis

| # | 题目 | 考察点 | 答题要点 |
|---|---|---|---|
| A21 | 缓存穿透/击穿/雪崩分别怎么治？ | 高频基础 | ① 穿透（查不存在的 key）→ 空值缓存 + 布隆过滤器；② 击穿（热点 key 过期瞬间打穿）→ 互斥重建 or 逻辑不过期；③ 雪崩（大批 key 同时过期）→ 过期时间加随机抖动 + 多级缓存 + 熔断兜底；④ 银行补充：**缓存不可用时必须能降级到 DB 且 DB 有限流保护**，不能"缓存一挂全站挂" |
| A22 | 缓存与数据库怎么保证一致？ | 一致性方案 | ① 推荐 Cache-Aside：更新 DB 后**删除**缓存，不是更新缓存；② 先删缓存再更新 DB 有并发窗口；③ 延迟双删 or 订阅 binlog 失效（Canal）；④ 必须承认"只能收敛到最终一致，做不到强一致"——这句话在银行面试里是**成熟度信号** |
| A23 | 分布式锁怎么写才算对？ | 正确性细节 | ① `SET key randomValue NX EX ttl`；② 解锁必须校验 value 是自己的（Lua 原子比较后删），否则会误删别人的锁；③ TTL 太短业务没跑完 → 看门狗续期；④ 主从切换可能丢锁（Redlock 争议），**强一致场景要靠 DB 唯一约束或状态机兜底**。项目实现见 `ai-cs-order/src/main/java/com/aics/order/lock/OrderCreateLockService.java:44` |
| A24 | Redis 为什么快？持久化怎么选？ | 原理 | ① 纯内存 + 单线程避免锁竞争 + IO 多路复用 + 高效数据结构；② RDB 快照恢复快但会丢最后一次快照后的数据，AOF 更完整但体积大；③ 混合持久化；④ 银行语境：**Redis 不作为账务存储**，只做缓存/锁/限流计数，资金数据一律落库 |
| A25 | 生产 Redis 慢，怎么查？ | 运维 | ① `slowlog`；② 大 key（`--bigkeys`/scan 统计）与热 key；③ 持久化 fork 阻塞、AOF rewrite；④ 网络与 `KEYS *` 之类的误用；⑤ 有 `latency monitor` 使用经验会加分 |

### 2.5 MQ 与分布式

| # | 题目 | 考察点 | 答题要点 |
|---|---|---|---|
| A26 | 为什么用 MQ？用消息有什么代价？ | 权衡 | ① 解耦、异步、削峰；② 代价：一致性变弱、链路变长、要处理重复/乱序/丢失/积压、可观测性下降；③ **能讲清代价的人才敢让他碰生产**。银行补充：核心记账链路很多仍走同步，异步用在通知、积分、报表等旁路 |
| A27 | 如何保证消息不丢？ | 端到端 | ① 生产端：确认机制（同步发送 + 失败重试 + 本地失败表）；② Broker：持久化 + 多副本；③ 消费端：**处理成功后再 ACK**；④ 兜底：对账/补偿任务。项目实现：`ai-cs-pay/src/main/java/com/aics/pay/mq/PaySuccessTransactionListener.java:40` |
| A28 | 如何保证幂等？ | 银行必考 | ① 消费方用业务唯一号（流水号）做**唯一索引**，重复插入直接冲突；② 或状态机判断（已是终态就不再处理）；③ Redis 占位是"加速挡"，**权威必须在 DB**；④ 项目证据：`ai-cs-common/src/main/java/com/aics/common/idempotent/IdempotentAspect.java:61`（SET NX 占位）+ `:78`（业务异常释放 key 允许重试）；`PayTransactionServiceImpl.java:53` 已是 SUCCESS 直接返回 false。原理见 [../02-Spring微服务/14-分布式幂等设计.md](../02-Spring微服务/14-分布式幂等设计.md) |
| A29 | 消息积压怎么办？ | 生产事件处理 | ① 先看是消费变慢还是生产暴增；② 扩容消费者实例与队列数（**消费者数不能超过队列数**，否则空跑）；③ 临时旁路：转储到临时 topic 慢慢消化；④ 关键判断：**这条消息有没有时效性/是否会引发资损**，决定是"追平"还是"降级丢弃 + 事后补偿"；⑤ 死信与重试策略要预先设计，见 [../04-中间件/08-RocketMQ事务消息与死信队列.md](../04-中间件/08-RocketMQ事务消息与死信队列.md) |
| A30 | 分布式事务方案对比，你们为什么选它？ | 选型论证 | ① 2PC/TCC/Seata AT/事务消息/Saga/本地消息表 + 对账补偿；② AT 对业务无侵入但有全局锁开销，适合中低频写；③ 事务消息适合"本地事务成功 → 通知下游"；④ **钱的链路首选"最终一致 + 对账兜底"**，因为可用性优先级高于"绝不重复"；⑤ 项目双证据：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:78`（`@GlobalTransactional`）+ `PaySuccessTransactionListener.java:56`（回查以落库状态为唯一权威） |
| A31 | 超时和重试怎么配才不会出事？ | 稳定性细节 | ① **写操作重试必须幂等**，否则一次超时重试 = 两笔扣款；② 调用方超时必须 **大于** 被调方内部超时，否则上游已放弃、下游还在干活 → 产生单边账；③ 指数退避 + 抖动，避免重试风暴；④ 熔断/降级要配"探活恢复"。项目：`ai-cs-chat/src/main/resources/application.yml:74-77`（TimeLimiter 60s）、`:108-124`（熔断窗口 10 / 失败率 50%） |
| A32 | 什么是"热点账户"？怎么设计？ | 银行特色题 | ① 同一账户行被高频更新（如商户收款户、头寸户），行锁串行化导致 TPS 上不去、锁等待雪崩；② 方案：余额拆分（多子账户轮询记账 + 定期归并）、请求排队/削峰、缓冲记账（先记流水后异步汇总）、按账户做本地聚合；③ 代价：余额变成"最终一致"，查询要合并、对账要严格；④ 详见 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md) 与 [04-支付清算体系与报文](./04-支付清算体系与报文.md) |

### 2.6 Spring / 微服务

**B1 什么是日切？**
- 日切 = 系统从一个营业日切换到下一个营业日的过程：停止/限制部分交易、跑日终批量、完成账务结转、切换系统营业日期。
- 关键点：**业务日 ≠ 自然日**。日切后发生的交易，归属日期可能是前一个营业日，"当日累计""日余额"都以业务日为准。
- 开发影响：所有"当日""T 日"的统计都要用业务日字段，不能用 `now()` 的日期；跨日切时点的交易要能正确归属；批量重跑要按业务日重算。
- 详见本模块 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)。

**B2 借贷记账法是什么？**
- 有借必有贷、借贷必相等；每笔交易至少两条记录，方向相反、金额相等，全局汇总后借贷平衡。
- 关键差异：会计意义上的"借/贷"是账户方向，**不是"增加/减少"**——资产类与负债类的借贷方向相反，站客户视角与银行视角还会再翻一次。
- 开发影响：记账接口必须成对写入、余额只能通过记账变动、任何手工修数都要有对应红字/蓝字凭证；日终"总分核对"（明细账合计 = 总账）是硬校验。
- 详见本模块 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)。

**B3 一笔跨行转账的完整流程？**
- 客户发起 → 本行校验（身份/余额/限额/风控/反洗钱）→ 本行记账（扣付款人）→ 走清算通道（大额实时/小额批量/网银跨行互联等）→ 对手行入账（记收款人）→ 通知双方。
- 关键：钱不是"直接飞过去"，中间经过**清算机构与双方在央行/清算组织的账户**变动，所以会有"我方已扣款、对方尚未入账"的中间态。
- 失败点：通道超时、报文格式不符、对方账号户名不符退回、清算窗口关闭、日切。处理原则：状态未知时**先查单再决策**，绝不重复扣款。
- 详见本模块 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**B4 支付、清算、结算的区别？**
- 支付：客户发起的资金转移请求与授权（信息流为主）。
- 清算：算清"谁该给谁多少钱"——把大量交易轧差/汇总，算出应收应付结果（对账、净额计算、指令生成）。
- 结算：按清算结果**实际完成资金划拨**，钱真正动了，交易进入最终性。
- 记法：支付是"下单"，清算是"算账"，结算是"给钱"。开发时三者数据表与状态机是分开的，混在一起迟早对不平。
- 详见本模块 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**B5 什么是"二清"？**
- 一清 = 资金由持牌支付机构/银行直接清算给**实际收款人**。
- 二清 = 无牌照的平台先归集商户资金到自己账户，再由自己"二次清算"给商户。平台账户里沉淀了大量他人资金，存在挪用、跑路与资金链断裂风险。
- 为什么禁：无证经营支付业务 + 客户资金不在监管视野内。合规做法是资金走持牌机构通道分账，平台只做信息撮合。
- 开发含义：平台不能建"资金池"，分账能力必须依赖持牌方的分账/合规通道。详见 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**B6 备付金是什么？**
- 支付机构收到的、已属于客户但尚未完成结算的待处理资金（充值未消费余额、在途货款等）。
- 现行要求是集中存放交存，不得挪用、不得靠它赚利息，且要按规则计算交存金额。
- 系统含义：备付金账户要与自营账户严格分离、可逐笔追溯到业务订单、余额与在途明细必须能对平。
- 与"谁的钱进谁的账由谁支配"的支付结算原则直接呼应。详见 [05-现金管理与资金头寸](./05-现金管理与资金头寸.md) 与 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**B7 I / II / III 类个人账户有什么区别？**
- 分档依据是**开立方式与实名强度**：I 类须面对面核验（或经自助设备由银行工作人员现场核实），II/III 类可线上开立。
- 功能逐级收窄：I 类全功能（存款、理财、消费缴费、转账、存取现、大额支付，基本无限制）；II 类可理财 + 限额消费缴费与向非绑定账户转出；III 类仅小额消费缴费、余额上限很低。
- 关键约束：同一人在同一银行只能有一个 I 类户；II/III 类有绑定账户与限额约束。
- 渠道侧的产品实现与落地细节详见 [06-网络金融与电子渠道](./06-网络金融与电子渠道.md)，本篇不重复展开。

**B8 什么是热点账户？怎么处理？**
- 现象：极少数账户（商户收款户、内部头寸户、代发总户）承担绝大部分交易量，同一行被高频更新，行锁排队 → TPS 卡死、超时雪崩。
- 处理思路：① 余额拆分为多个子账户轮询记账、定期归并；② 请求侧排队/合并（同一账户的变更在内存里批量合并再落库）；③ 流水先落地、余额异步汇总更新；④ 缩短事务、减少索引维护。
- 代价：余额变成最终一致，实时余额查询要合并子账户，对账逻辑变复杂。
- 详见本模块 [02-核心系统与会计账务引擎](./02-核心系统与会计账务引擎.md)。

**B9 单边账怎么产生、怎么处理？**
- 定义：一笔交易只有一侧成功。常见三种：我方扣款成功、渠道/对手方未入账；我方未扣款、渠道记为已支付；双方都记但金额或状态不一致。
- 产生原因：网络超时（最常见，请求发出但结果未知）、进程宕机在两步之间、消息重复或丢失、两边日切时点不同、对账文件口径不一致。
- 处理原则：**先查单确定事实，再决定补单或冲退**；状态未知期间不能重复发起扣款；处理结果要留痕并回写。
- 项目证据：`PayCompensationServiceImpl.java:53` 就是"流水成功但订单未支付"的单边检测。详见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md)。

**B10 冲正和退款的区别？**
- 冲正：把一笔**未最终完成/当场失败**的交易恢复到交易前状态，通常由系统在原交易链路内自动触发，金额与原交易一致，当日、当日链路、同一渠道。
- 退款：对**已成功完成**的交易做反向资金转移，需要授权、可能部分退、可跨日、走独立审批与限额校验，账务上是新的一笔交易。
- 关键差异：冲正是"这笔没发生"，退款是"这笔发生了但我要反向补一笔"。账务与报表口径完全不同。
- 开发含义：冲正要求幂等且只能对原流水做一次；退款要能查原单、支持多次部分退并防超退（累计退款额 ≤ 原交易额）。

**B11 柜面为什么要有授权/复核？**
- 本质是**内控**：把"发起—执行—审核"分开，防止单人完成一笔可获利或可掩盖的交易。典型：大额取现、挂失解挂、账户信息修改、冲正、强制扣划。
- 授权（主管级）解决"这个操作能不能做"；复核（另一人重复录入/比对）解决"录入的内容对不对"。
- 开发含义：必须有"提交人 ≠ 审批人"的字段校验，禁止自审自批；授权记录（谁授权、依据什么）落库可查；高敏操作双人 + 留痕。
- 详见本模块 [03-柜面系统与集中作业](./03-柜面系统与集中作业.md)。

**B12 什么是"断直连"？**
- 背景：早期第三方支付机构**直接**与各家银行逐一对接、自行传输与归集资金与信息，资金链路对监管不透明。
- 要求：网络支付业务必须通过依法设立的**清算组织**（银联、网联）统一转接，"直连"模式被切断。
- 结果：交易信息与资金清算都经持牌清算机构，机构侧报送、对账、反洗钱可观测性提升。
- 开发影响：接口对手方从"N 家银行"变成"1 家清算组织"，报文规范、对账文件来源与格式全部改变。详见 [04-支付清算体系与报文](./04-支付清算体系与报文.md)。

**B13 反洗钱的四项基础义务是什么？**
- 客户身份识别（KYC，含受益所有人识别与持续识别）；客户风险等级划分并定期复评；客户身份资料与交易记录保存；大额交易与可疑交易报告。
- 常加第五项：名单筛查（制裁/涉诈/内部黑灰名单）与内部培训、检查。
- 一句话工程理解：银行是"数据上报器"，**任何渠道漏采集都会直接造成漏报**，所以数据质量决定合规能力。
- 详见本模块 [08-反洗钱账户管理与监管合规](./08-反洗钱账户管理与监管合规.md)。

**B14 个人金融信息怎么分级？工程上分别要做什么？**
- 按泄露后的危害程度分三档：最高档是账户密码与银行卡认证信息（密码、验证码、CVV2、有效期、磁道/芯片信息）；中档是可识别个人 + 反映金融状况的（身份证号、手机号、账号、余额、流水）；最低档是单独无法识别的信息。
- 最高档：禁止明文存储、禁止展示、禁止入日志、禁止出现在测试环境。中档：展示脱敏 + 按需授权 + 传输加密 + 访问留痕。
- 必答辨析：**展示脱敏（掩码）只防人眼，不防拖库**；存储脱敏/加密才是防拿到文件的人。只做了前者不等于满足个人金融信息保护。
- 详见 [07-银行业信息安全管理规范](./07-银行业信息安全管理规范.md) 第四节。

**B15 说说国密算法。**
- SM2 非对称：签名/验签、密钥协商，替换 RSA/ECDSA；SM3 摘要：完整性校验，替换 SHA-256；SM4 对称分组：批量数据加密，替换 AES。
- 记法："2 签名、3 摘要、4 加密"。
- 配套概念：加密机 HSM（密钥只进不出，应用只能调用不能读取）、密钥分层（主密钥 / 工作密钥 / 会话密钥）、密评（商用密码应用安全性评估）。
- 诚实表态模板："我实现过 SHA256withRSA 的签名验签流程（可指项目代码），换成国密主要改算法标识与把密钥取用换成 HSM 调用，具体标准编号我需要回来看现行文本确认。"详见 [07 篇第五节](./07-银行业信息安全管理规范.md)。

**B16 灾备等级、两地三中心、RTO/RPO 讲一下。**
- RTO = 允许停多久（恢复时间目标）；RPO = 允许丢多少数据（恢复点目标，以时间跨度衡量，RPO=0 表示不能丢已确认交易）。
- 两地三中心 = 同城生产中心 + 同城灾备中心 + 异地灾备中心：同城解决机房级故障（低 RTO/RPO），异地解决城市级灾难（RPO 通常不为 0）。
- 能力等级不只看机房，还看数据复制方式、系统冗余、网络可达、运维与预案成熟度，并**通过切换演练证明**。
- 开发含义：组件必须能在灾备环境部署（不能依赖不可复制的本地文件/单机中间件），切换脚本与回退方案要随版本一起交付。详见 [../13-稳定性工程/04-高可用架构模式.md](../13-稳定性工程/04-高可用架构模式.md)。

**B17 什么是单元化？**
- 把业务按某个路由维度（如用户 ID 尾号）切成多个自包含"单元"，每个单元内有完整的应用 + 数据 + 缓存，请求在单元内闭环，跨单元调用尽量少。
- 收益：① 水平扩展突破单机房容量；② **故障爆炸半径受限**（一个单元坏只影响部分客户）；③ 异地多活可行。
- 代价：分片键一旦定下极难改；跨单元交易（同一账户两边动）要特殊路由；全局唯一性（如同一客户只开一个户）需要额外方案。
- 与我熟悉的东西的映射：本质是"按 key 哈希分片 + 就近闭环"，和分库分表、一致性哈希同源；本项目的按用户维度分片是它的微缩版。

**B18 银行的研发流程和变更（投产）流程？**
- 典型链路：需求（业务部门提，带依据）→ 方案设计评审（含安全、数据、架构）→ 开发（在开发网，代码入库）→ 单元测试与代码扫描 → 提测（含安全测试）→ SIT/UAT → 投产评审（**要带影响分析、回退方案、验证清单**）→ 变更窗口投产 → 投产后验证与值守 → 归档。
- 特点：环境严格隔离、每步有产出物、变更窗口固定、封网期不变更、投产要"多人配合 + 双人复核"。
- 开发感受：**等待与文档的时间不比写代码少**；一次生产变更失败会被要求写事件分析。
- 详见 [10-银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)。

**B19 你理解的银行研发和互联网研发的差别？**
- 目标函数不同：互联网优先"快 + 体验"，银行优先"不出错 + 可追溯 + 合规"，速度是第二目标。
- 约束不同：数据不能出网、变更有窗口、技术栈受准入清单限制、新功能常由监管截止日驱动。
- 质量标准不同：不是"P99 变慢一点"，而是"一分钱都不能错，错了要能解释并追责"，所以留痕、对账、幂等、双人复核是标配。
- 收尾一句（很重要）："我不是说哪种更好，我是说我的工程习惯——幂等、状态机、补偿对账、优雅停机——本来就朝这个目标函数练的，只是需要把领域词补齐。"

**B20 什么是头寸？为什么开发要关心？**
- 头寸 = 银行在某处**可动用的钱**（本外币资金、在央行与代理行的存款），流动性管理就是保证"该付的时候付得出、且不闲置"。
- 系统提供的是：实时可用余额、已占用/在途资金、未来现金流预测、大额资金流动预约。
- 开发关心是因为：清算窗口有截止时间，**头寸不足会导致支付排队失败**，所以"资金占用与释放的准确性"是硬要求；报表口径错一天，可能一次大额支付排队。
- 详见 [05-现金管理与资金头寸](./05-现金管理与资金头寸.md)。

## 四、C 组：综合面 / 压力面（诚实且不自我贬低的答法）

> 通用心法：**承认缺口 + 给出可验证的迁移能力 + 给出具体补齐动作**。不要说"我学得快"（空），要说"我两周能读完 XX 并交付 XX"。

**C1 你没有金融经验，为什么觉得自己适合银行岗？**
> "确实没有做过银行系统，这是事实。我能提供的是三点：一是**资金链路的工程直觉**——我自己实现过支付渠道对接、回调一致性、幂等、状态机和对账补偿，单边账为什么会发生、状态未知时该先做什么，这些我是踩过写过的；二是**合规相关的基础**——我系统整理过信息安全管理、个人金融信息分级、反洗钱四项义务与账户管理（可指本模块笔记），知道哪些是红线；三是**补齐路径**——入职第一个月我打算读透本行开发规范与安全制度，跟一次完整投产，把核心账务的科目与状态机摸熟。JD 说"优先"而非"必须"，我想我属于第二句能靠时间换掉的那一半。"

**C2 能接受驻场、加班、出差吗？**
> 能接受，但要说清"我接受的是**有原因的强度**"：投产窗口、重要时期保障（节假日/封网/演练）、突发故障，这些是银行业本质，我预期之内，也愿意承担 oncall。同时坦白一句"我更希望把强度花在前置质量上，比如充分的验证清单和可回退方案，减少事后救火"——这句话既表态又显专业。

**C3 生产事故你会怎么处理？**
> 顺序固定：**先止血（按预案：降级、切流、重启、关开关，恢复优先于查明原因）→ 通报（按级别与时效上报，绝不瞒）→ 保留现场（日志、线程栈、dump、当时的变更记录）→ 定位与修复 → 复盘改进 + 验证监控是否覆盖**。
> 补两句关键：**"第一时间查最近变更"**（多数事故来自变更）；**"我不确定能不能修，但我确定不会自己动手改生产数据"**——生产数据修正必须走审批与双人复核。

**C4 和运维/测试/业务意见冲突怎么办？**
> 拉回三个共同基准：一是**影响与风险**（这处改动会影响哪些交易、有没有回退）；二是**证据**（日志、监控、评审记录，不是"我觉得"）；三是**决策人**（业务口径归业务归口部门，投产窗口归运维，我提供技术可行性判断）。争执不下时我会主动写一份一页方案对比（含风险与工时）让决策变成选择题而不是辩论题。

**C5 为什么不去互联网，来银行是不是想躺平？**
> "不是图轻松，银行对'不出错'的要求其实比大多数互联网业务更严苛。我选银行有两个具体原因：一是我的工程兴趣本来在**一致性、幂等、可追溯**这类问题上，这在资金系统里是核心命题而不是加分项；二是我希望做**长寿命的系统**，而不是每周改一版就没人维护的东西。我也清楚代价：流程多、迭代慢、技术选型受限——这些我了解并愿意接受。"

**C6 你的职业规划？（考稳定性）**
> 三年目标要具体且与岗位绑定：第一年能独立接需求、过一次完整投产、不触发生产事件；第二年能在一个业务域（比如支付清算或账户）成为组内可依赖的人；第三年能承担方案设计与跨系统协调。收尾一句：**"我不想每两年换一个领域重新从零开始，银行这类系统的价值就在于长期沉淀，这也是我看中它的原因。"**

**C7 能接受薪资结构（基本工资 + 绩效 + 各类补贴，总包波动）吗？**
> 接受，我理解绩效与考核、与机构效益挂钩，也接受奖金递延这类安排。我只希望明确两点：**考核规则透明**、**成长路径清晰**。如有具体数字（如绩效占比）可以礼貌反问，这在银行面试里不会减分。

**C8 你最大的短板是什么？**
> 用真短板 + 有动作：**"金融领域词汇与业务全景我是零的，看需求文档里'冲正、备付金、日切、头寸'需要翻译。"** 动作：已在系统整理模块笔记、每次读需求把术语入库并做对照表。避免说"我太追求完美"这类假短板，也避免说"我不擅长沟通"这种致命真短板。

**C9 如果你的代码引发了生产事件，你怎么办？**
> 三步：① 配合止血与定位，不隐瞒不甩锅（**银行对"隐瞒"的容忍度远低于对"犯错"的容忍度**）；② 如实提供时间线、变更记录与验证情况，复盘聚焦"为什么流程没拦住我"而不是"我真心的道歉"；③ 提出可落地的防线（补校验、补监控、补单测、补发布验证清单）。

**C10 你有什么想问我们的？（一定要问，且问对）**
> 好问题清单：① "这个组负责的域是哪个，新人一般从什么类型的需求开始接？"② "从需求到投产的链路大概有几环，新人有没有 mentor 带着走一次完整投产？"③ "技术栈与准入清单里，我现在需要额外学哪一块？"④ "生产变更窗口和 oncall 是怎么排的？"
> 别问：能不能远程、几点下班、"我们用什么最新技术吗"。

### E1 按"算头不算尾"算活期利息

```java
import java.math.BigDecimal;
import java.math.RoundingMode;
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;

/** 活期利息计算：算头不算尾（起息日计息、支取日不计息）。 */
public final class DemandDepositInterest {

    /** 人民币业务常用日利率折算口径：年利率 / 360（实际以本行计息办法为准） */
    private static final BigDecimal DAYS_OF_YEAR = new BigDecimal("360");

    private DemandDepositInterest() {
    }

    /** @param annualRate 年利率小数值，如 0.0035 表示 0.35%；返回两位小数（以分为最小单位） */
    public static BigDecimal interestOf(BigDecimal principal, BigDecimal annualRate,
                                       LocalDate startDate, LocalDate endDate) {
        if (principal == null || annualRate == null || startDate == null || endDate == null) {
            throw new IllegalArgumentException("本金/利率/起止日期不得为空");
        }
        if (principal.signum() < 0 || annualRate.signum() < 0) {
            throw new IllegalArgumentException("本金与年利率不得为负: " + principal.toPlainString());
        }
        // 算头不算尾：between(起, 止) 恰好等于「含起不含止」的天数
        long days = ChronoUnit.DAYS.between(startDate, endDate);
        if (days < 0) {
            throw new IllegalArgumentException("到期日不得早于起息日");
        }
        // 中间精度多留几位（scale=8），只在最后一步舍入，避免误差累积
        BigDecimal dailyRate = annualRate.divide(DAYS_OF_YEAR, 8, RoundingMode.HALF_UP);
        return principal.multiply(dailyRate)
                .multiply(BigDecimal.valueOf(days))
                .setScale(2, RoundingMode.HALF_UP);
    }
}
```

真实系统用**积数计息法**：`利息 = Σ(每日余额 × 该余额存续天数) × 日利率`（即"计息积数 × 日利率"），
因为活期账户余额每天都在变，且**遇利率调整要分段计息**。上面的单段版本是它的最小内核。

**银行面试会追问**：① 为什么用 `String` 构造 `BigDecimal`？② 除数 360 还是 365，谁规定的（→ 以本行计息办法为准，
不要自己拍）？③ 舍入模式谁定（→ 业务书面规定，`HALF_UP` vs `HALF_EVEN`）？④ 为什么不在中间步骤 `setScale`？
⑤ `interest.compareTo(BigDecimal.ZERO) == 0` 为什么不能写 `equals`？⑥ 利率调整日在计息区间中间怎么办（分段）？
⑦ 期间有存入有支取怎么算（积数）？⑧ 起息日与到期日同一天（0 天）应该返 0 还是报错？——**要主动把边界说出来**，
面试官在等你说这句。

### E2 扣减账户余额且不能为负（乐观锁 CAS + 重试）

```java
import java.math.BigDecimal;

/**
 * 余额扣减（乐观锁 CAS + 有限重试）。依赖的 Mapper 方法用 @Update 声明（全部 #{} 参数化，杜绝拼接）：
 * UPDATE t_account SET balance = balance - #{amount}, version = version + 1, update_time = NOW()
 *  WHERE id = #{id} AND version = #{version} AND balance >= #{amount}
 * 即 int deductIfEnough(@Param("id") Long id, @Param("amount") BigDecimal amount, @Param("version") Long version)
 */
public final class BalanceDeductService {

    private final AccountMapper mapper;

    public BalanceDeductService(AccountMapper mapper) { this.mapper = mapper; }

    /** @return true 扣减成功；false 余额不足（业务失败，不重试）。账户不存在或重试耗尽抛异常（系统失败，交上层降级/登记差错） */
    public boolean deduct(Long accountId, BigDecimal amount, int maxRetry) {
        if (accountId == null || amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("账户号必填、扣减金额必须为正");
        }
        for (int attempt = 1; attempt <= maxRetry; attempt++) {
            Account acc = mapper.selectById(accountId);
            if (acc == null) {
                throw new IllegalStateException("账户不存在: " + accountId);
            }
            if (acc.getBalance().compareTo(amount) < 0) {
                return false;                         // 余额不足：直接业务失败
            }
            // CAS：version 不变 且 余额够 才更新；两个条件同时成立才生效
            int affected = mapper.deductIfEnough(accountId, amount, acc.getVersion());
            if (affected == 1) {
                return true;
            }
            backoff(attempt);                         // affected==0 → 版本被他人抢先，退避后重试
        }
        throw new IllegalStateException("余额扣减重试耗尽: accountId=" + accountId);
    }

    /** 指数退避：避免高并发下所有失败线程同时重试造成重试风暴 */
    private void backoff(int attempt) {
        long sleepMs = Math.min(100L, (1L << Math.min(attempt, 6)));
        try {
            Thread.sleep(sleepMs);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("扣减重试被中断", e);
        }
    }
}
```

**银行面试会追问**：① SQL 里为什么还要写 `balance >= amount`（**读到的余额可能已过期**，DB 条件才是最终裁判；
应用侧判断只为了提前返回业务失败）？② 重试耗尽为什么抛异常而不是返回 `false`？
→ **必须区分"余额不足（业务失败）"与"没抢到/超时（系统未知）"**，把后者当失败返回，上层可能重复扣款。
③ 结果未知怎么办？→ 靠这笔扣减的**幂等号 + 查询/对账**判定，不能盲重试。
④ 悲观锁 `SELECT ... FOR UPDATE` 与 CAS 怎么选？→ 冲突率高时 CAS 反复重试更亏，悲观锁更稳；
冲突率低时 CAS 不长期持锁。⑤ 热点账户 5000 TPS 怎么办？→ 回到 **B8 热点账户**：拆子账户/合并记账。
⑥ 怎么防"扣了钱但记账流水没写"？→ 同一事务 + 事务消息 + 对账兜底。⑦ `version` 用 `int` 会不会溢出？

### E3 写一个对账 diff（找长款 / 短款 / 金额不一致）

```java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** 双边流水对账：以业务号对齐，输出四类差异。 */
public final class Reconciler {

    public record Flow(String bizNo, BigDecimal amount, String status) { }

    /** ONLY_IN_BANK：我方无、渠道有 → 可能长款（该收未到/该记未记）；ONLY_IN_OURS：反之 → 可能短款 */
    public enum DiffType { ONLY_IN_BANK, ONLY_IN_OURS, AMOUNT_MISMATCH, STATUS_MISMATCH }

    public record Diff(DiffType type, String bizNo, BigDecimal bankAmount, BigDecimal ourAmount) { }

    public static List<Diff> reconcile(List<Flow> bankFlows, List<Flow> ourFlows) {
        Map<String, Flow> bank = index(bankFlows, "bank");
        Map<String, Flow> ours = index(ourFlows, "ours");
        List<Diff> diffs = new ArrayList<>();
        for (Map.Entry<String, Flow> e : bank.entrySet()) {
            Flow b = e.getValue();
            Flow o = ours.get(e.getKey());
            if (o == null) {
                diffs.add(new Diff(DiffType.ONLY_IN_BANK, b.bizNo(), b.amount(), null));
                continue;
            }
            // 金额比较一律 compareTo：BigDecimal("1.0").equals("1.00") 为 false
            if (b.amount().compareTo(o.amount()) != 0) {
                diffs.add(new Diff(DiffType.AMOUNT_MISMATCH, b.bizNo(), b.amount(), o.amount()));
            }
            // 金额相同但状态不同（渠道成功、我方仍 PENDING）同样是差错，不能漏
            if (!b.status().equals(o.status())) {
                diffs.add(new Diff(DiffType.STATUS_MISMATCH, b.bizNo(), b.amount(), o.amount()));
            }
        }
        for (Map.Entry<String, Flow> e : ours.entrySet()) {
            if (!bank.containsKey(e.getKey())) {
                diffs.add(new Diff(DiffType.ONLY_IN_OURS, e.getKey(), null, e.getValue().amount()));
            }
        }
        return diffs;
    }

    /** 业务号必须唯一；重复出现说明数据质量问题，绝不能静默取其一 */
    private static Map<String, Flow> index(List<Flow> flows, String side) {
        Map<String, Flow> map = new HashMap<>(Math.max(16, flows.size() * 2));
        for (Flow f : flows) {
            if (f.bizNo() == null || f.amount() == null || f.status() == null) {
                throw new IllegalArgumentException(side + " 侧存在关键字段为空的流水");
            }
            Flow prev = map.putIfAbsent(f.bizNo(), f);
            if (prev != null) {
                throw new IllegalStateException(side + " 侧业务号重复: " + f.bizNo());
            }
        }
        return map;
    }
}
```

**银行面试会追问**：① 内存对账放不下怎么办？→ 两侧按业务号**排序后归并比对**（外排 + 双游标，O(n) 内存 O(1)），
或者落库后 `FULL OUTER JOIN`/`LEFT JOIN ... IS NULL` 比对；② "长款/短款"到底是哪个是哪个？
→ 站在我方视角：**长款 = 实际多了钱/多记（渠道有我方无，需查明是否该入账）；短款 = 实际少了钱（我方有渠道无，
最危险，可能已扣款未付出）**。方向口径必须先说清是谁对谁，别背反；③ 金额一致但状态不一致为什么要报？
→ 这是"我方仍 PENDING、渠道已 SUCCESS"的典型漏单，不报就是资损；④ 时区与日切导致的"两边不在同一天"怎么处理
（B1 日切）；⑤ 部分退款/多笔合并对账怎么对齐（1:N）；⑥ 差错找到之后呢？→ 检测 ≠ 处理，
必须有**差错台账 + 人工确认 + 冲正/补单 + 留痕**，参考 `PayCompensationServiceImpl.java:53` 的"输出差异清单而非自动修数"。
详见 [09-金融级一致性与对账实战](./09-金融级一致性与对账实战.md)。

## 七、F 组：诚实提醒（这一节比上面所有题都重要）

1. **绝对不要把自己包装成有银行经验。** 银行背调与核验通常包含学历学位、**社保/公积金缴纳单位连续性**、
   前雇主离职证明与实际任职期间，部分岗位还查个人征信与犯罪记录（均需你授权）。伪造经历一旦被查出，
   后果不只是 offer 撤回，可能进入该机构或同业黑名单。
2. **替换策略：把"我有经验"改成"我用工程能力换业务入门速度"。** 三种合规且更有力量的表述：
   - "我没有银行项目经验，但我把 JD 里的'信息安全管理规范'按**法规 → 监管 → 标准 → 行内制度**四层整理过，可以给您看笔记目录。"
   - "支付渠道对接、幂等、状态机、对账补偿这些我是亲手写过的，**代码在这里，我可以逐行讲**。"
   - "领域词我需要时间补，但我不需要人教我怎么保证一笔钱不被扣两次。"
3. **不要贬低非银行经历。** 说"之前做的都是 CRUD、没技术含量"，等于说"我做过的事没价值"，
   面试官会照单全收。正确姿势是**重述价值**：同一件事换个说法（"多服务交易链路的一致性设计"）。
4. **不知道编号就说不知道。** 面试里被追问"XX 标准的编号是什么"，正确回答是
   "编号我不敢凭记忆说，我确认的是它的结构与要求，具体版本我入职后以行内制度文本为准"。
   这句话在银行环境里不是失分项，是**合规人格**的证明。
5. **写进简历的每一行都要能撑住三层追问**：怎么实现的 → 为什么这样做 → 还有什么没做。
   第三问答不上来，前两问说的都会被怀疑。**红线自查**：简历与面试中**绝不**提及任何密钥、连接串、真实账号数据
   （哪怕是学习项目），也不要说"我把生产数据拉到本地测试过"——后者在银行是致命信号。
6. **别把银行当"轻松稳定"的代名词**。它有 oncall、投产熬夜、驻场、封闭开发、文档量与流程摩擦。
   预期落差是试用期离职的主因，面试前就想清楚比入职后抱怨便宜得多。

## 八、常见误区

| 误区 | 真相 |
|---|---|
| 把题背熟就行 | 面试官一句话就能戳穿："那这笔扣款超时了你怎么办？" **链路理解 > 答案背诵**，B 组 20 题必须能画出来 |
