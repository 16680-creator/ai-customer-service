## 一、先把概念钉住：信创不是一句口号，是三层不同的事

**信创 = 信息技术应用创新**，指把 IT 栈从芯片到应用换成国内厂商提供、可持续演进的版本。但"国产化替代"在银行内部其实是三层要求，混在一起谈就会被面试官问穿：

| 层次           | 换的是什么     | 判断标准                                         | 谁负责               |
| -------------- | -------------- | ------------------------------------------------ | -------------------- |
| 产品替代       | 品牌与供货来源 | 采购合同里的标的、生产实际运行的制品             | 采购、科技部门       |
| 技术体系替代   | 架构与技术栈   | 是否摆脱了对原厂商垂直整合栈的依赖，能否横向扩展 | 架构、研发           |
| 供应连续性替代 | 断供风险       | 关键部件与软件断供后能否持续获得版本、补丁与备件 | 科技管理层、风险条线 |

只做到第一层的替换，业内有个不太客气的说法叫"换皮"——硬件是国产的，架构、闭源中间件、运维方式全都照旧。这也是第五节"真替真用"要拆的东西。

### 1.1 "2+8+N"：业内通用说法，不是政策原文

"2+8+N"是**业内流传的推进范围概括说法**（该提法未见公开的权威政策原文，口径来自行业报道与厂商材料，面试引用时请说明是俗称），大意是：

- **"2"**：党政机关先行；
- **"8"**：八个重点行业，通常列举为金融、电力、电信、石油、交通、教育、医疗、航空航天；
- **"N"**：其余行业逐步跟进。

银行被普遍认为在"8"里落地最早、投入最大的一档，原因是：客户资金与结算连续性不能赌、外部供应受制于人时风险无法用商务手段对冲、以及科技投入本来就在全行业前列。**注意：这是一句经验判断，不是制度条文，各行的实际进度差异极大。**

### 1.2 去 IOE 为什么成为起点

**去 IOE** 指去掉三样东西：I = IBM 的大型机/小型机（承载核心与关键数据库）、O = Oracle 数据库、E = EMC 存储。它比"信创"这个词更早出现在国内技术圈的讨论里，起点是**成本与扩展性**，后来才叠加了供应连续性。

| 部件              | 在银行原来的用途                 | 非换不可的真实动因                                                                            | 换完之后的常见形态                                   |
| ----------------- | -------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| IBM 大型机/小型机 | 核心账务、关键业务库的运行平台   | 纵向扩展（加 CPU 加内存）单价陡增、容量到顶、变更高度依赖原厂；新机型停产后备件与维修窗口收紧 | x86/ARM 多节点横向扩展 + 应用层做分片与高可用        |
| Oracle 数据库     | 核心与重要业务的集中式库         | License 与维保按处理器授权计价、随容量线性上涨；特性绑定深（RAC、存储过程、闪回）             | 集中式国产库或分布式库；老应用先跑兼容模式再逐步改写 |
| EMC 存储          | 集中式磁盘阵列，承载数据库与文件 | 高端阵列单位容量成本高、扩容受单一厂商节奏约束                                                | 分布式存储/国产中端阵列 + 对象存储分层               |

**关键因果**：去掉小型机意味着"一台机器变多台机器"，一台机器变多台就必须处理数据分片、一致性、故障转移——这些是应用架构问题，不是采购问题。**所以去 IOE 从第一天起就是架构改造，而不是换个牌子**。这条因果链解释了第三节里"信创改造"和"核心下移/分布式改造"为什么经常被合并成一个项目。

### 1.3 采购门槛怎么起作用：机制链条

银行研发一般不参与招投标，但你写的代码能用什么软件，是被下面这条链决定的（只描述机制，不写任何期号与文件编号）：

```text
 信创在银行里的真实决策链

  ① 国家级测评机构定期公布"安全可靠测评结果"
        │   产品与版本两级都要过，才有资格进入银行视野
        ▼
  ② 行方据此建立并持续更新"全行产品入围目录"
        │   采购与架构管理把关；目录外产品 = 例外审批，或者直接被拒
        ▼
  ③ 项目可选产品收敛为目录内的少数几个
        │   架构师无法自由选型，比较维度变成"案例规模 + 支持矩阵 + 服务能力"
        ▼
  ④ POC 与兼容性互认证验证
        │   交付物里附兼容性证明；没有证明就得自己在测试环境跑一遍
        ▼
  ⑤ 试点 → 分批投产 → 全行推广
        │   按重大变更管控：更强回退要求、更长观察期、配置基线落档
        ▼
  ⑥ 运维交接 + 审计与监管检查
        └── 要能拿证据：谁批的、比过什么、性能余量多少、老系统何时下线
```

| 环节       | 谁把关                                         | 对你的直接后果                                                                                                 |
| ---------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 测评与入围 | 总行采购与架构管理                             | 你写需求申请"某开源库的某版本"，不在目录就得走例外审批，或者直接被拒                                           |
| 版本入围   | 行内技术基线（不只是产品入围，具体版本也入围） | 不能用最新版：JDK、框架、驱动都被基线锁定（见 [01 篇 4.5 节](./01-银行IT体系与岗位全景.md)）                   |
| 互认证     | 厂商之间 + 行方测试部门                        | 交付物里要附"兼容性证明/互认证书"，没有就得自己在 POC 环境验一遍                                               |
| 投产管控   | 投产委员会、数据中心                           | 信创改造被当成**重大变更**：更强的回退要求、更长观察期（见 [10 篇第五节](./10-银行研发运维流程与投产管控.md)） |

一句人话总结：**目录决定你能不能用，POC 决定你敢不敢用，运维工具链决定你用不用得起来。**

## 二、产业链分层全景：五层，每层的成熟度差异极大

先看结构，再看玩家。下面这张图的读法是：**越往下越难、越往下厂商越少、越往下事故代价越大**。

```text
 ┌────────────────────────────────────────────────────────────────────────────────┐
 层5 云与运维    私有云/超融合 │ 备份与容灾 │ 监控与日志 │ 自动化运维 │ 制品库    │  ← 决定"敢不敢签字"
 ├────────────────────────────────────────────────────────────────────────────────┤
 层4 信息安全    边界与终端防护 │ 数据库审计与脱敏 │ 密码产品与加密机 │ 身份管理  │  ← 合规强驱动
 ├────────────────────────────────────────────────────────────────────────────────┤
 层3 应用软件    ERP/财务 │ OA 与办公套件 │ 邮箱 │ 行业应用（含银行核心/信贷）    │  ← 最成熟，替换阻力最小
 ├────────────────────────────────────────────────────────────────────────────────┤
 层2 基础软件    操作系统 │ 数据库 │ 中间件（应用服务器/消息/交易） │ 虚拟化      │  ← 改造工作量主要在这层
 ├────────────────────────────────────────────────────────────────────────────────┤
 层1 基础硬件    CPU（多条技术路线）│ 整机 │ 存储 │ 网络（含交换芯片）│ 部件      │  ← 采购金额最大、周期最长
 └────────────────────────────────────────────────────────────────────────────────┘
     ▲ 采购归口通常是三条线：硬件集采 / 基础软件集采 / 安全与运维专项
```

### 2.1 分层速查表

| -------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |

| 基础软件 | 数据库                  | OceanBase（蚂蚁）、TiDB（PingCAP）、TDSQL（腾讯云）、GaussDB 与开源 openGauss（华为）、GoldenDB（中兴通讯）、达梦、人大金仓 KingbaseES、GBase（南大通用） | 事务型已跨过"能不能用"，比拼的是生态、工具链与迁移成本        | 见 [15 篇](./15-国产数据库选型与迁移.md)                      |

| 应用软件 | 通用应用                | 办公套件（金山办公 WPS）、OFD 版式（数科、福昕等）、OA（泛微、致远、蓝凌）、ERP（用友、金蝶）                                                             | 最成熟，替换成本最低                                          | 通常是全行第一波，也是模板与打印兼容的坑区                    |
| 应用软件 | 金融行业应用            | 长亮科技、神州信息、宇信科技、高伟达、天阳科技、中电金信等（核心/信贷/渠道/风控外包产品，各行差异大）                                                     | 与银行制度深度耦合，选型=选厂商的多年服务能力                 | 外采与自研边界见 [01 篇 4.4 节](./01-银行IT体系与岗位全景.md) |
| 信息安全 | 与密码                  | 奇安信、深信服、启明星辰、天融信、绿盟科技、安恒信息；金融密码产品与加密机厂商多家并存                                                                    | 成熟（合规驱动，需求稳定）                                    | 国密改造见 [07 篇第五节](./07-银行业信息安全管理规范.md)      |
| 云与运维 | 私有云/超融合/备份/监控 | 华为、新华三、浪潮、曙光、阿里与腾讯的专有云形态；超融合与备份、监控类厂商众多                                                                            | 较成熟但**工具链碎片化**：国产 OS + 国产库的采集插件常滞后    | 运维适配是"真替真用"最现实的卡点（第五节）                    |

读表三要点：

1. **成熟度不是产品好坏，是生态厚度**。同一个库在 POC 里跑分漂亮，不代表监控采得到、备份做得回、原厂半夜接电话。
2. **层的组合数量决定扯皮面**。五层全换 = 五家原厂 + 若干集成商，故障定位时的第一问题是"谁先查"（第六节第 8 类工作）。
3. **越往上越看业务耦合，越往下越看工具链**。上层换的是功能，下层换的是"可运维性"。

## 三、银行替换次序模型（本篇核心）

### 3.1 行业通行的推进次序

各行做法不完全一致，但普遍遵循的次序是：**办公系统 → 一般业务与管理类 → 渠道与外围 → 重要业务 → 核心账务与清算**。

```text
  越往上越危险（风险与事故后果 ↑）
  ┌───────────────────────────────────────────────────┐
  │     5  核心账务与清算：核心·总账·清算·日终批处理  │  一致性最高 · 事故=资损与监管事件
  ├───────────────────────────────────────────────────┤
  │     4  重要业务：支付结算前置·信贷审批·反洗钱·限额│  需双轨逐笔比对 · 外部机构联调
  ├───────────────────────────────────────────────────┤
  │     3  渠道与外围：手机银行·网银·客服·开放 API    │  可用性事故 + 舆情，账务不受损
  ├───────────────────────────────────────────────────┤
  │     2  一般业务与管理类：报表·审计·后管·运维管理  │  允许延迟与重算，失败可重跑批
  ├───────────────────────────────────────────────────┤
  │     1  办公系统：OA·邮箱·文档·ERP                 │  故障只影响内部效率
  └───────────────────────────────────────────────────┘
  ─────────────────────────────────────────────────────────────────────────────▶ 推进时间轴
  第 1 批（练工具链、建基线、写回退模板）→ 第 2 批 → 第 3 批 → 第 4/5 批（步长以年度计，不是季度）
```

| 次序 | 系统类型                                                       | 为什么排在这                                     | 典型改造动作                                               | 事故后果量级            |
| ---- | -------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------- | ----------------------- |
| 1    | 办公与通用应用（OA、邮箱、门户、文档、HR、ERP）                | 没有 7×24 硬要求，数据可重录，故障只影响内部效率 | 客户端与浏览器内核兼容、版式与打印模板重做、外设驱动       | 内部投诉                |
| 2    | 一般业务与管理类（报表、审计、后管、运维管理、知识管理）       | 允许延迟与重算，失败可重跑批                     | 取数 SQL 方言改写、批量作业调度迁移、大数据组件替换        | 数据延迟、口径争议      |
| 3    | 渠道与外围（手机银行、网银、客服、开放 API、非资金类）         | 客户可感知但没有资金账务错乱风险，可降级排队     | 前端兼容、SDK 与探针换架构版本、容器与镜像多架构、压测重做 | 可用性事故 + 舆情       |
| 4    | 重要业务（支付结算前置、信贷审批、反洗钱、限额、渠道账务前置） | 有外部机构与监管通道依赖，涉及资金但仍有对账兜底 | 报文与文件处理回归、与外部联调排期、双轨结果比对           | 资金差错 + 对外报送延误 |
| 5    | 核心账务与清算（核心银行、总账、清算、日终批处理）             | 一致性要求最高、变更窗口最窄、错了要赔付并被问责 | 先做等价性验证再做架构改造；长期双轨；逐笔记分比对         | 资损事件 + 监管问责     |

### 3.2 排次序用的五个判据

别背上面的表，背这五个判据——遇到任何一个新系统，你自己就能推出它该排第几。这也是面试里"你怎么判断替换优先级"的标准答案骨架。

| 判据         | 你要问的问题                                                      | 低次序位置的答案        | 高次序位置的答案                                                                           |
| ------------ | ----------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------ |
| 可用性要求   | 允许停多久？RTO（能容忍多久恢复）与 RPO（能容忍丢多少数据）是多少 | 小时级、RPO 可放宽      | 分钟级以内、RPO 必须为 0 或接近 0                                                          |
| 数据可恢复性 | 出错了能不能重录、重算、回灌                                      | 能重录（OA 流程、报表） | 不能重录（客户账、总账），只能冲正与差错处理                                               |
| 外部依赖数量 | 链路上有几个外部机构（人行、银联/网联、监管报送、合作机构）       | 0～1 个，联调自主可控   | 多个，外部排期决定你的投产窗口                                                             |
| 变更窗口     | 有没有日终、清算场次、报送节点卡死操作时间                        | 白天也能改              | 只有日终后几小时、季末年末封版期禁改（[10 篇 5.1 节](./10-银行研发运维流程与投产管控.md)） |
| 事故后果     | 最坏情况赔多少钱、报不报告监管、上不上新闻                        | 内部效率与口碑          | 客户资金受损、监管事件、舆情                                                               |

**一句话记住**：可用性越高、数据越不可再生、外部依赖越多、窗口越窄、后果越重，就越往后放。

### 3.3 为什么"核心下移/分布式改造"常和"信创替代"合并成一个项目

三条现实原因：

1. **一次预算**。核心改造与硬件替换都花大钱，合并立项好审批；换硬件不换架构等于把同一笔手术做两次。
2. **必须一起做**。老核心绑在小型机 + 集中式库上，不换架构就没有国产硬件的可放置形态（见 1.2 节因果链）。
3. **人员与知识窗口**。懂老核心业务规则的骨干就那几个，第二次动员的成本更高（这类系统文档与代码同源度低，见 [01 篇 4.1 节](./01-银行IT体系与岗位全景.md)）。

代价是**风险叠加**：架构变了、数据库换了、CPU 与 OS 也换了，一旦结果不一致，你无法判断差异来自哪一层。行业通行的处置手段是这六条：

| 手段                | 做法                                                                                                                          | 防的是什么                 |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 一次只动一个变量    | 明确"先迁后改"或"先改后迁"，并在选型报告里写清理由                                                                            | 归因不可能                 |
| 双轨并行 + 逐笔比对 | 老系统继续记账，新系统影子跑批，按日全量比对余额、发生额、分录（对照 [09 篇第七节](./09-金融级一致性与对账实战.md) 对账三层） | 结果不等价                 |
| 不变式独立校验      | 不只比对"两边一样"，还要各自校验借贷平衡、总分核对（[09 篇第一节](./09-金融级一致性与对账实战.md)）                           | 两边一起错                 |
| 分批切流            | 按机构/客户/交易类型灰度，从最低风险的交易类型开始（[10 篇 5.5 节](./10-银行研发运维流程与投产管控.md)）                      | 全量爆炸                   |
| 真做回退演练        | 至少完成两次以上真实回退演练并留时间戳记录                                                                                    | 回退方案是纸面文章         |
| 给双轨定"结束日期"  | 观察期结束即启动老系统下线计划，逾期要重新审批延期理由                                                                        | 双轨长期化（第五节形态 2） |

### 3.4 替换优先级打分卡（可以直接拿去用）

把 3.2 的五个判据量化，你就有了一张可以自己打分的卡。**分数越低越先做**——先做低风险的，把方法论与工具链练熟，再往高层推。

| 判据         | 1 分（最轻）     | 3 分（中）        | 5 分（最重）                         | 你的系统 |
| ------------ | ---------------- | ----------------- | ------------------------------------ | -------- |
| 可用性要求   | 允许工作时间停机 | 7×24 但可短暂降级 | 7×24 且不可降级，RPO/RTO 以秒/分钟计 |          |
| 数据可恢复性 | 可重录、可重算   | 可从上游回灌      | 不可再生，只能冲正与差错处理         |          |
| 外部依赖数量 | 0~1 个内部依赖   | 若干行内系统      | 含清算机构、监管报送、合作机构       |          |
| 变更窗口     | 随时可发         | 有固定发布日      | 只有日终/清算后窗口，封版期禁改      |          |
| 事故后果     | 内部效率受损     | 客户体验受损      | 客户资金受损 + 需对外报告            |          |

- **5~9 分**：第一批（办公与管理类，练工具链、建基线、写回退模板）。
- **10~16 分**：第二批（渠道与外围，重点是压测与灰度切流）。
- **17~25 分**：第三批（重要业务与核心账务，必须双轨 + 逐笔比对 + 真回退演练，见 3.3）。

> 这张卡的分数区间只是经验切法，各行的分级名称与阈值不同；面试时说"我会用这五个维度排序，具体阈值按行内变更分级制度对齐"比报一个数字更稳。

## 四、选型决策框架：18 个必须先回答的问题

这 18 问的用法是：**写在选型报告里，答不上来的就是项目风险**，不是走过场的附录。按五类看更清楚——迁移与生态（1、2、11、12）、能力与余量（3、4）、商务与授权（7、8、9）、支持与生命周期（5、6、13、14）、运维与退出（10、15、16、17、18）。

| #   | 问题                                                                                      | 为什么在银行必须问                                                                                                                                  | 什么证据才算答过                                                                                                                                        |
| --- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 生态与迁移成本：现有代码用了多少原产品的特性，改写得动吗？                                | 迁移成本由"你依赖了多深"决定，不由它的功能列表决定                                                                                                  | 现有代码特性清单（方言函数、存储过程、驱动 API、事务写法）逐项对照表与人天估算                                                                          |
| 2   | 兼容性证据是谁给的、覆盖到哪个版本？                                                      | "厂商说兼容"和"我们环境验过兼容"是两件事                                                                                                            | 互认证书 + 本行 POC 报告（两者都要，且版本一致）                                                                                                        |
| 3   | 性能余量在**你的**峰值模型下还剩多少？                                                    | POC 通常验平均态，生产要的是峰值态 + 故障态余量                                                                                                     | 固定并发阶梯的 p99 曲线；数据量放大 3~10 倍后的扩展性曲线（验证是否线性）                                                                               |
| 4   | 高可用形态与一致性语义能不能满足 RPO/RTO？                                                | 业务连续性有硬要求；隔离级别、锁粒度、主从延迟语义差异会直接造成账务差错                                                                            | 切换演练记录含实测耗时；一致性用例集（脏读/幻读/丢失更新/重复提交）在新栈上的实测结果（对照 [13-稳定性工程/04](../13-稳定性工程/04-高可用架构模式.md)） |
| 5   | 支持主体是原厂还是集成商？                                                                | 出事故时接电话的是谁，直接决定恢复时长与责任归属                                                                                                    | 合同支持条款 + 工单系统里真实响应记录抽样                                                                                                               |
| 6   | 版本与生命周期：这个版本何时停止维护？                                                    | 银行系统生命周期以十几年计，"上线即末版"是常见事故伏笔                                                                                              | 生命周期公告 + 与本行技术基线的版本对齐表                                                                                                               |
| 7   | License 按 CPU 颗数、按核数，还是按实例/节点计价？                                        | 国产 CPU 常常**颗数少而核数多**：按核计价时成本随核数线性膨胀，按颗计价则相反。同一产品换计价口径，报价能差数倍；还要问清灾备节点、测试环境是否计费 | 计价公式 + 你选定机型的核数与颗数 + 三个环境（生产/灾备/测试）的分别报价                                                                                |
| 8   | 源码与知识产权授权到什么程度？                                                            | "可用"与"可改"是两种合同；二开成果归属不清会在后续项目里被卡死                                                                                      | 授权条款原文（修改权、使用主体范围、是否允许分包、成果归属）                                                                                            |
| 9   | 断供与备份风险怎么兜？                                                                    | 出口管制与厂商经营风险都真实发生过，商务手段对冲不了                                                                                                | 可替代厂商清单 + 代码与数据取回条款 + 离线制品留存方案                                                                                                  |
| 10  | 运维工具链是否适配？                                                                      | 这是"真替真用"的分水岭：采不到指标就没人敢签字                                                                                                      | 监控指标清单、一次真实恢复备份的成功演练记录                                                                                                            |
| 11  | 团队技能与培训成本多少？要驻场多久？                                                      | 交接不干净就是永久依赖                                                                                                                              | 培训计划 + 约定"六个月后本行人员能独立处置的故障类别清单"                                                                                               |
| 12  | 已有同业案例的规模有多大？                                                                | 案例的**量级**比案例的**数量**重要：只跑在办公系统上的案例，和跑在全行最高并发的账务链路上的案例，是两种成熟度                                      | 可回访的同业案例（行业、系统层级、数据量、上线年限），最好拿到对方的踩坑清单                                                                            |
| 13  | 故障响应 SLA（Service Level Agreement，服务水平协议，约定响应与恢复时限）怎么算、怎么罚？ | 纸面时限没有违约条款等于没有                                                                                                                        | 条款里的分级时限 + 违约金/服务积分机制                                                                                                                  |
| 14  | 升级与补丁通道怎么走？能不能自主选择打或不打？                                            | 被迫自动升级在生产环境是大风险；不能升级则是安全欠账                                                                                                | 补丁发布节奏、灰度方式、单个补丁的回退可行性                                                                                                            |
| 15  | 与现有监控/备份/审计/堡垒机怎么对接？留痕够不够审计？                                     | 审计要能回答"谁在什么时候做了什么"（[07 篇第七节](./07-银行业信息安全管理规范.md)）                                                                 | 对接方案 + 一条完整可回放的审计取证链样例                                                                                                               |
| 16  | 供应商锁定与退出成本多大？                                                                | 选型报告里没有退出方案，等于把议价权交出去                                                                                                          | 数据与代码的可导出性**实测**（真导一次，不是文档承诺）                                                                                                  |
| 17  | 迁移窗口、双轨时长与回退方案是什么？                                                      | 决定排期是否现实；回退点未定义会让投产无法审批（[10 篇 5.4 节](./10-银行研发运维流程与投产管控.md)）                                                | 迁移时序图 + 回退点与反向数据同步方案                                                                                                                   |
| 18  | 验收与考核口径谁定、怎么算通过？                                                          | 口径不定就会上线即扯皮："已投产"不等于"已承接业务"                                                                                                  | 验收用例清单（业务方签字）+ 上线后 3~6 个月的量化考核指标（见 5.2 节）                                                                                  |

> **面试可用的一句话**：银行选型不是选"最强的产品"，是选"最能在本行环境里被验证、被运维、被审计、被退出的一整套东西"。所以我答选型问题习惯从第 7、12、13、15、18 问开始——它们最容易在事后变成事故或扯皮。

## 五、真替真用 vs 为替而替

### 5.1 八种走样形态

| 形态                   | 现场怎么认                                           | 根因                             | 代价                                         |
| ---------------------- | ---------------------------------------------------- | -------------------------------- | -------------------------------------------- |
| 只换硬件不换架构       | 单机仍跑集中式库、仍靠纵向加配、仍用原厂闭源 HA 组件 | 把采购任务当技术任务             | 架构债留在原地，下一次还得做两遍             |
| 双轨长期并行不下线     | 老系统跑了一年还在"备份"，两边都要人守               | 没人愿意签"下线"这个字           | 成本翻倍、责任模糊、真故障时两边都不敢动     |
| 用兼容模式不敢改 SQL   | 方言兼容开关一开到底，应用代码一行没动               | 改造工作量算不进工期             | 特性受限、性能不可预测、新库的运维能力用不上 |
| 性能余量不足不敢上生产 | POC 达标但生产容量红线卡死，长期只跑非关键流量       | 压测用平均态模型、没算故障态余量 | 项目名义完成、实际不承载业务                 |
| POC 数据与生产差异     | 测试数据是均匀造出来的，生产有倾斜、大字段、历史包袱 | 造数省事                         | 结论不可迁移，投产后集中暴雷                 |
| 只换外围，关键路径未换 | 目录外例外审批单越来越多                             | 风险规避理性但缺路线图           | "替完"的报告与实际不符，检查时说不清         |
| 工具链没跟上           | 监控看板缺指标、备份只能冷备、诊断要等厂商远程       | 采购范围只写了主产品             | 值班不敢签字，事故时靠打电话                 |
| 用模拟/兼容层跑原系统  | 在国产 OS 上虚拟出原环境跑旧软件                     | 迁移成本压力                     | 本质上没替换，还要维护两套技术栈             |

### 5.2 怎么判断"替换是真做了"：可验证指标

不要问"替了吗"，要看下面这些能取到数的东西。

| 指标                 | 怎么取数                                                                                 | 为什么骗不过去                                                       |
| -------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 老系统下线数         | 合同终止记录、机房退租与设备下架单、CMDB 实例状态变更                                    | 下线是有财务与资产痕迹的动作，嘴上说"下线了"没有记录就是没下         |
| 生产流量占比         | 生产网关/负载均衡的真实交易笔数按系统栈拆分，按月看趋势                                  | 镜像回放、影子流量不进生产链路统计                                   |
| 生产制品实际形态     | 生产节点上的 CPU 型号、内核版本、运行镜像的 digest（不是 tag）                           | 从生产实机采集，不接受截图                                           |
| 事故归属与闭环       | 新栈上发生过几起故障、根因定位在哪家、RCA（Root Cause Analysis，根因分析报告）有没有落地 | 从没在生产出过故障的系统谈不上"能用"；出了故障能定位并闭环才算真在用 |
| 原厂支持是否真在用   | 工单数量与响应时间记录、驻场人员签到、版本升级由谁发布                                   | 工单为零通常不是产品没问题，而是没人敢报                             |
| 双轨比对差异清零时间 | 每日比对差异条数曲线，看是否收敛到 0 并保持                                              | 长期不收敛说明还有未识别的行为差异                                   |

> **诚实声明**：本仓库不是银行系统，第九节的对照只比"工程手法"，不比业务。上面这些指标在任何做过替换的工程组织里都可取数——这是你可以现在就练的能力。

## 七、银行采购与投产视角：信创特有部分

与 [10 篇](./10-银行研发运维流程与投产管控.md) 的通用研发流程呼应，这里只写信创改造**多出来**的那些环节。

### 7.1 推进节奏

| 阶段      | 行内在做什么                         | 研发要交出的东西                         | 常见卡点                               |
| --------- | ------------------------------------ | ---------------------------------------- | -------------------------------------- |
| 入围      | 建立/更新产品与版本目录              | 候选清单与技术约束说明                   | 目录里的版本比你想要的旧               |
| POC       | 样机 + 行内环境做技术验证            | 测试方案、用例集、测试报告（含原始数据） | 用厂商脚本、没有本行真实负载模型       |
| 集采/框架 | 总行集中谈判，签框架价，分行按需下单 | 需求数量与配置基线（部件到型号）         | 配置基线漏写内存插法、网卡队列等细节   |
| 试点      | 选 1~2 个低风险系统或分支机构先跑    | 试点方案、回退方案、观察期指标           | 试点成功被当成全行可复制，忽略规模差异 |
| 全行推广  | 分批投产、标准镜像与配置基线下发     | 迁移批次表、双轨比对报告、运维交接文档   | 老系统下线无人签、双轨长期化           |

### 7.2 为什么要"互认证/兼容性证明"

**互认证**（也叫兼容性互认证）指两家厂商互相在自己的产品上完成对方产品的安装、功能与稳定性验证，出具书面证明。它在银行有用是因为：投标与投产评审需要一个"不是我们拍脑袋"的第三方证据；它的局限也必须说清：**互认证只证明"在厂商自己的环境与版本组合下装得上、跑得通"，不证明"在你行的数据量、负载模型与配置下跑得好"**。所以有互认证仍要做本行 POC——评审时能把这层区分讲清楚，比背一堆产品名更值钱。

### 7.3 一个信创改造项目的典型里程碑与交付物

1. 立项：选型报告（含第四节 18 问逐条回答）、替代范围与批次计划、风险登记。
2. POC：测试方案与用例、异构性能基线（含 p99 与 GC 数据）、兼容性改造清单。
3. 详细设计：架构方案（含高可用与灾备）、数据迁移方案、双轨比对方案、回退点定义。
4. 改造与验证：SQL 与依赖改造记录、SIT/UAT 报告、监控与备份接入验证（[10 篇 3.1 节](./10-银行研发运维流程与投产管控.md) 的环境矩阵）。
5. 试点投产：投产方案、回退方案、投产后验证与观察期日报。
6. 推广与收尾：配置基线、运维手册与告警规则、故障责任矩阵、**老系统下线计划与实际下线证据**。

### 7.4 评审会上一定会被追问的六句话

信创项目的评审（架构评审、投产评审、后评价）问法高度固定。提前把答案准备好，比临场组织语言安全得多。

| 追问                               | 谁在问             | 合格答案的形态                                                          |
| ---------------------------------- | ------------------ | ----------------------------------------------------------------------- |
| "这个产品入围了吗？哪个版本入围？" | 架构管理、采购     | 报出目录内厂商 + **版本号一致**；不一致要说明例外审批单号与有效期       |
| "性能余量是多少？峰值挂了怎么办？" | 性能与容量负责人   | 给 p99 与余量百分比，并说明故障态（少一个节点）下的余量，不是只给平均值 |
| "回退要多久？数据怎么回来？"       | 投产评审、数据中心 | 说清回退点、反向同步方案、回退后数据一致性怎么验；"回滚镜像"不算答案    |
| "老系统什么时候下线？谁签？"       | 项目管理、财务     | 有明确日期与前置条件（比对差异清零 + 流量占比达标），否则就是双轨长期化 |
| "出了问题谁先查？"                 | 运维、值班经理     | 一张跨厂商责任矩阵 + 各自的取证清单，而不是一句"原厂支持"               |
| "这套东西五年后还能拿到补丁吗？"   | 风险管理、审计     | 生命周期公告 + 版本演进计划 + 备选替代路径                              |

## 十、动手练习

1. **信创适配差距盘点**：照第九节的表格式，把本项目按 [13](./13-国产芯片与服务器选型.md)~[16](./16-国产中间件与Java运行时适配.md) 篇的口径重做一遍（芯片/镜像/OS/JDK/数据库/中间件/监控七栏），每栏写"证据 + 判定 + 改造动作"。产出物就是你的"选型报告草案"，面试可直接当作品讲。
2. **18 问实战**：用第四节 18 问，为"把 `ai-cs-pay` 的 MySQL 换成某国产分布式数据库"写一份选型评估要点。至少覆盖：自增 ID 语义（`PaySchemaInitializer.java:24` 用了 `AUTO_INCREMENT`）、启动期建表在生产是否允许、`ON DUPLICATE KEY UPDATE` 与幂等实现（对照 [09 篇第三节](./09-金融级一致性与对账实战.md)）的等价性、Seata AT 与新库的隔离级别/可见性交互、分片键与支付流水查询模式是否匹配、计价方式（按核 vs 按实例）在本项目的成本差异、回退方案与反向数据同步、验收口径。写成表格，不许出现"厂商说支持"。
3. **"真替真用"自查表**：给本项目做一次 5.2 节六个指标的自查——挑一个组件（如 Elasticsearch 或 MinIO），列出"如果明天要换成国产替代，我用什么数据证明换成功了"。要求每条指标都能落到一条命令或一次实机采集，不接受文档描述。
4. **优先级排序**：把本仓库 9 个 Java 服务（gateway/user/knowledge/chat/search/message/notify/order/product）按第 3.2 节五个判据打分排序，写出"如果只能先替两个，你选哪两个、为什么"。注意：本仓库里没有账务系统，请按"资金影响 + 客户可感知"两维近似，并显式声明这个近似。
5. **跨厂商扯皮演练**：假设"国产 OS + 国产数据库 + 自研 Java 服务"出现 p99 抖动，写出你的取证清单（JVM、OS、内核参数、库侧慢日志各自要留什么），并定义一张责任矩阵（谁先查、查到什么程度转交）。话术准备见 [11 篇](./11-银行岗面试题库与简历映射.md)。

## 十一、初学者常见误区

| 误区                              | 真相                                                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "信创 = 换个国产牌子"             | 品牌换掉只完成第一层（1.1 节）。不换架构，你只是把同一笔技术债换了个债主；去 IOE 起于成本，成于分布式改造                                                       |
| "Java 跨平台，所以零成本迁移"     | 字节码跨平台，**依赖不跨平台**：native 库、驱动、探针、容器镜像、JDK 发行版都要重验；性能与 GC 行为也得重测（详见 [13 篇第三节](./13-国产芯片与服务器选型.md)） |
| "国产库性能一定差"                | 差异主要来自你是否按它的设计模型改了表结构与 SQL（分片键、索引、事务粒度）。拿未调优的结论对比调优过的原厂栈，比较本身无效                                      |
| "替完就没事了"                    | 真正的长期成本在生命周期：补丁、版本演进、备件、原厂支持年限。第 12、13、14 问才是决定五十年后谁替你背锅的地方                                                  |
| "POC 结论可以直接当生产结论"      | POC 用的是均匀造数、平均负载、无故障态。生产的差异来自数据倾斜、峰值余量、故障时性能塌陷（5.1 节形态 5）                                                        |
| "有互认证就安全了"                | 互认证只证明"装得上"，不证明"在你行跑得值"。7.2 节那三层区分要能讲出来                                                                                          |
| "信创是运维/采购的事，和开发无关" | 开发决定 80% 的适配成本：SQL 写法、依赖形态、镜像构建、可观测性埋点。你写的每一处专有语法都是未来的人天                                                         |
| "替换越彻底越好，应该全栈一起换"  | 全栈同换 = 归因不可能。行业通行做法是分批、可回退、一次只动一个变量（3.3 节）                                                                                   |
| "双轨并行说明我们做得稳"          | 双轨是**过渡态**，长期双轨就是为替而替。判断标准是差异条数有没有收敛到零、老系统有没有下线日期（5.1 节形态 2）                                                  |
| "面试只要背一堆厂商名就行"        | 背名字最容易被打断。真正加分的是次序模型（第三节）与 18 问（第四节）——它们证明你知道**为什么**这么选                                                            |
