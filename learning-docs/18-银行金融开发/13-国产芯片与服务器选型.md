## 一、四条技术路线全景

先给一句结论：**国产服务器 CPU 不是一种东西，而是四条谱系完全不同的路线**（ARM 系两家、x86 授权系两家、龙芯自主指令集、申威）。它们的差异不在"谁更快"，而在**你现有的二进制能不能直接跑**、**出了问题有几家厂商能互相背锅**、**五年后还有没有新版本**。

**排序记法**：迁移成本 海光/兆芯（x86）最低 → 鲲鹏/飞腾（aarch64）中等 → 龙芯高 → 申威最高。**但这不等于"选 x86 授权路线就赢了"**：架构兼容只省了移植人天，省不掉性能回归、可运维性验证和授权成本，也省不掉"下一代还能不能供货"这个问题。

> 趋势判断（业内普遍看法，不是结论）：RISC-V 路线在嵌入式与部分处理器上已有国内厂商布局，OpenJDK 上游也在跟进其移植，但通用服务器与银行生产环境短期内仍以 ARM 与 x86 授权两条路线为主。面试被问"未来怎么看"，答"看上游工具链与整机厂供货能力，不看发布会"比猜时间更稳。

### 1.3 逐条拆解：每条路线各自要盯什么

**ARM 系（鲲鹏、飞腾）**。指令集来自 ARM 的架构授权，两家各自做微架构，用户态 ABI 同为 aarch64（`linux/arm64`）。好处是**一份镜像两家能跑**，工具链跟着上游 OpenJDK 与主流 Linux 发行版走，Java 层适配问题最少；难点有三：① 内核与驱动侧（网卡、RAID、存储多路径）在国产发行版上的版本组合要逐个确认；② 大量开源组件的官方容器镜像是否提供 arm64 变体必须自己 `manifest inspect` 查，不能猜；③ 换厂（鲲鹏 ↔ 飞腾）**必须重跑性能基线**，因为微架构、缓存层次、NUMA 形状都不同。面试提"ARM 路线"时最好说清是 aarch64 ABI 一致、性能特征不一致，这一句就能把背名字的人区分开。

**海光（x86 兼容路线）**。通过公开报道的 AMD 技术授权路径获得 x86 内核设计后自主演进，用户态与整个 x86 生态兼容，**迁移人天最少、软件可获得性最好**，在银行里常被用于"先把业务搬上国产硬件"这一阶段。要盯的是：指令扩展集合与最新 x86 不完全相同（依赖特定 SIMD 指令的库可能回退或行为不同）、机型与整机厂分布、以及供货连续性话题。适配难度低不等于免测：性能、稳定性、授权计价三项一样都不能省。

**兆芯（x86 兼容路线）**。走威盛（VIA）系技术授权路径，同样 x86_64 用户态。服务器领域可选机型与同业案例相对少，更多出现在桌面与行业终端。**选型时的动作不是争论路线好坏，而是要求厂商给出可回访的同行业投产案例**（[12 篇第四节第 12 问](./12-信创全景与银行替换路线.md)），拿不到就把风险写进选型报告。

**龙芯（LoongArch 自主指令集）**。早期产品基于 MIPS 指令集授权，2021 年前后转向自研 LoongArch，与 MIPS 不再二进制兼容，另有二进制翻译层跑其他架构的软件。对 Java 工程而言这是**成本最高的一档**：JDK 必须有 loongarch64 构建（上游支持较新，实践中多用厂商定制发行版），依赖里的 native 库、监控探针、加解密 SDK 都可能没有对应包，需要现场重编或找厂商要。翻译层能跑起来，但性能与兼容性都要实测，**不能拿"能启动"当"能上生产"**。

**申威（DEC Alpha 分支，口径来自公开报道）**。主要出现在高性能计算与专用领域（曾用于国家级超算的众核处理器），通用商业发行版与中间件覆盖有限，一般不进银行通用业务系统的选型池。出现在面试里时，能说清"它属于另一条谱系、生态决定了适用面"就够了，不必强行评价性能。

## 二、选型维度：主频之外还有十二项

评审会上只报"几核几 G、主频多少"，一定会被架构与运维问穿。下表按"要确认什么 + 对 Java 服务的实际影响 + 踩坑信号"三栏给全十二项，可以直接抄进选型材料。

| 维度                | 要确认什么                                                                                                      | 对 Java 服务的实际影响                                                                   | 踩坑信号                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 单核性能            | 同频 IPC 高低、依赖链长度、同步调用链耗时                                                                       | 银行交易型应用是**同步链路 + 序列化 + 校验**为主，p99 由单核速度决定                     | 只比核数不比单核；上线后 p99 达标但 p999 爆表         |
| 核数                | 总核数、每节点可分配核数                                                                                        | 决定吞吐上限与可并行的批处理分片数                                                       | 把"核多"直接当作"算力强"（第十节误区 1）              |
| 内存通道与容量      | 通道数、每通道插几条、是否插满且对称                                                                            | 内存带宽直接影响 GC、序列化与大批量查询；插法不对可能让带宽腰斩                          | 采购只报容量不报插法；同型号不同批次插法不一致        |
| NUMA 拓扑           | NUMA（Non-Uniform Memory Access，多颗 CPU 各自挂本地内存、跨颗访问更慢的内存拓扑）节点数、距离矩阵、每节点核数  | 堆与线程绑到跨节点内存上会稳定拉高时延抖动                                               | 从不记录 `numactl --hardware` 输出；容器里没人管 NUMA |
| PCIe 与网卡         | PCIe 通道数与代次、网卡是否多队列、驱动在该 OS 内核版本上是否可用                                               | 单队列收包会把软中断压在一个核上，吞吐上不去                                             | 换机型后网络时延上升，查半天发现队列数没配            |
| RAID/HBA 与存储兼容 | 卡型号与固件、缓存写策略与掉电保护、多路径软件与国产存储的兼容列表                                              | 缓存电池失效会自动降级成透写，写延迟成倍上升                                             | 只用厂商"理论支持"清单，没有同配置同业案例            |
| SSD/NVMe            | 企业级型号、掉电保护、耐久等级、队列与 NUMA 亲和                                                                | 日志与数据库写密集场景最先暴露                                                           | 拿消费级盘跑生产日志                                  |
| 功耗与机柜          | 单机典型/峰值功耗、电源冗余、机柜已有功率余量、送风方式                                                         | 换 ARM 常见动因是省电与降 PUE（Power Usage Effectiveness，机房总用电与 IT 设备用电之比） | **只算电费不算改造**：配电、PDU、布线、风道可能都要动 |
| 可运维性            | BMC（Baseboard Management Controller，主板上的带外管理芯片）能力、Redfish/IPMI 接口、SEL 日志能否被现有监控采到 | 带外采不到就没法做硬件故障预警；部分机型用自研管理芯片（如华为 iBMC），采集脚本要两套    | 运维平台只写过一套 IPMI 解析，新机型字段变了          |
| GPU/AI 可选性       | 同机型是否支持所需加速卡、驱动与国产 OS 内核版本适配                                                            | AI 推理/检索类服务未来可能需要                                                           | 先买机器后发现不支持要插的卡                          |
| 供货与价格          | 是否单一来源、交付周期、备件池、保修年限                                                                        | 影响推广批次的可行性                                                                     | 试点用赠送样机、推广时供货周期排不进计划              |
| 软件授权            | 数据库/中间件/虚拟化**按颗还是按核**计价；该机型核数是否让授权费膨胀                                            | 这是最常见的成本反转：**核数多的 CPU 在按核计价下更贵**，可能把"国产硬件便宜"的账抵掉    | 只算硬件报价，不算配套软件授权与后续扩容重计价        |

### 2.1 "单核 vs 核数"对 Java 谁重要

| 你的应用形态                                                       | 更看重                   | 为什么                                                                      |
| ------------------------------------------------------------------ | ------------------------ | --------------------------------------------------------------------------- |
| 联机交易（柜面/渠道/支付前置）：链路同步、响应时间敏感、p99 有 SLA | **单核性能**             | 一笔交易在一个线程上串行穿过校验、序列化、DB 往返；核再多也不能把这一串变短 |
| 批量与跑批（日终、对账、报表、文件解析）                           | **核数 + 内存带宽**      | 天然可并行，吞吐优先；但要确认批处理窗口够不够                              |
| 检索/聚合类（全文、向量、报表 OLAP）                               | 内存带宽、容量、IO       | 常见瓶颈在数据搬运而不是指令执行                                            |
| 高并发接入（网关、消息消费）                                       | 网络栈与核数、软中断分布 | 绑核与网卡多队列的收益常大于换 CPU                                          |

一句话：**银行核心与渠道侧的联机交易对单核更敏感，日终跑批对核数更敏感。同一台机器要同时承载两者时，容量规划要按两笔账分别算**（容量口径见 [02-容量规划与性能预算](../13-稳定性工程/02-容量规划与性能预算.md)）。

### 2.2 三笔最容易算错的账

选型报告里只写硬件报价的，通常在评审第二轮被打回。三笔账要分开算：

| 账     | 怎么算                                                                                                                    | 常见漏项                                                                                                                                                       |
| ------ | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 硬件账 | 机型 + 部件（内存按通道配齐、盘按容量与耐久选、网卡按队列与速率）+ 延保与备件池                                           | 为了压价把内存只配到少数通道、把网卡降成单口——省的钱在性能账上双倍吐回去                                                                                       |
| 授权账 | 按计价单位 × 实际部署规模：数据库/中间件**按核**还是**按颗**，虚拟化按 Socket 还是按宿主机，监控/备份按节点还是按被管对象 | **国产 CPU 常常一颗里塞很多核**：按颗计价时省、按核计价时暴涨；灾备节点与测试环境是否计费经常漏写（对应 [12 篇第四节第 7 问](./12-信创全景与银行替换路线.md)） |
| 机房账 | 功耗与散热（单机典型/峰值）、机柜功率余量与 PDU、配电改造、风道与承重、带外管理网络改造                                   | 只算"电费省了多少"，没算"机柜要重新布线、要换 PDU、要腾功率余量"；一个换型项目最后卡在电力改造上很常见                                                         |

**判断句**：如果一份国产化方案的收益只写了"硬件单价下降"，那这笔账基本没算完。**真正稳定的收益来源是授权与维保模式的变化，以及横向扩展带来的容量弹性**，硬件单价往往只是三者里最小的那一项。

## 三、x86 → ARM 迁移对 Java 工程的真实影响（本篇最硬核）

### 3.1 "字节码跨平台"这句话的准确边界

真的部分：`.class` 文件与 `--release 17` 产物是平台无关的，只要目标机器上有**对应架构的 JVM**，Java 源码不需要重编译。

容易被夸大的部分：**你的应用从来不是只有字节码**。

```text
 可移植性 ─────────────────────────────────────────────────────────────────────────────▶ 越来越不可移植
 ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
 │ Java 源码  │ → │ 字节码     │ → │ JDK 发行版 │ → │ 依赖 jar   │ → │ .so 原生库 │ → │ OS/内核    │
 │ 与 Maven   │ → │ (跨平台)   │ → │ (分架构)   │ → │ 内含资源与 │ → │ 强绑定     │ → │ glibc 与   │
 │ 构建       │ → │            │ → │ 按 ABI 出  │ → │ native 包  │ → │ 架构+ABI   │ → │ 系统调用   │
 └────────────┘   └────────────┘   └────────────┘   └────────────┘   └────────────┘   └────────────┘
   免测             免测             必须换           逐个清点         必须重出         重验参数
```

所以"Java 跨平台 = 零成本迁移"是**第十节误区 2**。正确的说法：**移植成本发生在依赖链和运行环境上，不在源码上**。

### 3.2 八类必须重验的东西

| #   | 项                       | 为什么要重验                                                                                                                                                                                                                                                                                                    | 失败时的现场表现                                                                                  | 怎么验（命令/动作）                                                                                                                                                                              |
| --- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | JNI / native 库          | 压缩（zstd/lz4/snappy）、加解密与加密机 SDK、图像与 PDF、编解码类库都以 `.so` 形式按架构发布                                                                                                                                                                                                                    | `UnsatisfiedLinkError: no xxx in java.library.path`；或 `Can't load library`                      | `jar tf` 扫依赖里的 `*.so`/`*.dll` 与 `META-INF/native`；对每个 native 依赖确认是否有 `linux-aarch64` 版本；找不到就找厂商要或换纯 Java 实现                                                     |
| 2   | Netty 的 epoll 传输层    | `netty-transport-native-epoll` 是按架构发布的（classifier 形如 `linux-x86_64`、`linux-aarch64`），缺 arm 包时会静默回退 NIO                                                                                                                                                                                     | 不报错，但吞吐/连接数下降、GC 分配上升——**最难发现的一类**                                        | 启动日志/`NativeTransport.isEpollAvailable()`；对比两边的连接建立耗时与 CPU/请求                                                                                                                 |
| 3   | glibc 与系统调用差异     | 用户态 ABI 依赖 C 库；musl（Alpine 系）与 glibc 行为不完全一致。同一 OS 在不同架构上的**系统调用号也不同**，依赖 seccomp/审计白名单的基线要按架构各出一份                                                                                                                                                       | 偶发 DNS 解析、时区、`iconv`、线程栈大小相关怪异行为；安全基线误杀                                | `ldd --version`、`cat /etc/os-release`；在生产与测试环境用同一 libc；本项目 `ai-cs-product/Dockerfile:1` 用的是 alpine（musl），与其他服务的 jammy（glibc）不同                                  |
| 4   | 字节序与对齐             | **现代主流服务器 CPU 基本都是小端（little-endian）**，x86_64 与常见 aarch64 配置都是；所以"搬去 ARM 要改字节序"多半是**吓自己**。真正要防的是把二进制表示当持久格式：定长报文与 ISO 8583 字段用网络序（大端）需要显式转换；`ByteBuffer`/`Unsafe` 按平台序读写；把 Java 序列化/Kryo 二进制落库后再在异构机器上读 | 跨架构读旧数据字段错位、金额位移（银行最不能出的错）                                              | 全局搜 `ByteBuffer`、`Unsafe`、`DataOutput`、序列化落库；持久格式一律改显式编码（长度前缀 + 大端）或文本/标准格式（对照 [04-支付清算体系与报文](./04-支付清算体系与报文.md) 的报文六问）         |
| 5   | 内存序与 `volatile`/屏障 | x86 是强内存模型，ARM 是弱内存模型：同一份 Java 代码在 ARM 上屏障更贵，而**没写同步却"碰巧能跑"的代码**会在 ARM 上暴露成真实的可见性问题（原理见 [08-CPU缓存与内存序](../15-计算机基础/08-CPU缓存与内存序.md) 第五、六节）                                                                                      | 偶发读到旧值、双重检查锁半初始化对象、无锁计数丢更新，**极难复现且只在压测里出现**                | 静态审查：所有跨线程共享可变字段是否有 `volatile`/锁/final 正确发布；自旋与 CAS 结构做长时间压力回归；用 `-XX:+UnlockDiagnosticVMOptions` 类诊断前先与架构组确认                                 |
| 6   | JIT 与内联缓存           | C2 的指令选择、寄存器分配、内联与 OSR 决策分架构；不同 JDK 发行版在 aarch64 上的成熟度也不同                                                                                                                                                                                                                    | 冷启动阶段 p99 明显更差、预热曲线变长；同一接口两边稳态一致但首分钟差异大                         | 固定预热流量后再测量；比较两边的编译日志与热点方法；必要时用 CDS/AOT 类手段前先做 A/B（工具口径见 [03-火焰图与性能剖析](../12-性能工程/03-火焰图与性能剖析.md)）                                 |
| 7   | GC 行为与停顿            | 写屏障、根扫描、卡片表处理、内存带宽都随架构变；堆大小与线程数照抄 x86 配置常导致停顿分布右移                                                                                                                                                                                                                   | 平均吞吐看着差不多，但最大停顿与抖动变大，触发 p99 告警                                           | 打开 GC 日志重跑基线，比对停顿分布而不是比对平均值（方法见 [02-GC日志与停顿分析](../12-性能工程/02-GC日志与停顿分析.md)、参数选型见 [01-JVM参数与GC选型](../12-性能工程/01-JVM参数与GC选型.md)） |
| 8   | 容器镜像与第三方二进制   | 镜像 tag 相同不代表架构相同；多架构镜像靠 manifest list 聚合。APM 探针、日志采集 agent、License 组件、内核模块类工具都要逐个确认有 ARM 版                                                                                                                                                                       | 在混合节点集群上出现"某些 Pod 起不来（`exec format error`）"或"同一 tag 在不同节点跑的是不同东西" | `docker manifest inspect <image>` / `buildx imagetools inspect`；生产环境记录**digest 而不是 tag**；本项目现状见第八节                                                                           |

### 3.3 迁移验证矩阵（贴到改造清单上）

| 验证层       | 通过标准                                                        | 谁签        |
| ------------ | --------------------------------------------------------------- | ----------- |
| 编译产物     | 目标架构 JDK 上编译并跑通全部单测                               | 开发        |
| 依赖清点     | 每个 native 依赖标注"有 arm 版/纯 Java/需替换/未知"，无一项未知 | 开发 + 架构 |
| 功能等价     | 同一用例集在两边跑，结果逐字段一致（金额、日期、编码、排序）    | 测试        |
| 性能基线     | 按第四节方法做同负载对比，p99 与 CPU/请求均达标且有余量         | 性能负责人  |
| 稳定性       | 长时间浸泡测试（含 GC 与内存增长趋势）无泄漏、无抖动            | 运维        |
| 可观测与备份 | 监控指标可采、日志可解析、备份可恢复演练成功                    | 运维        |
| 回退         | 真实演练过"退回 x86 栈"，含数据回同步                           | 投产负责人  |

### 3.4 x86 → ARM 改造清单（可直接贴进 PR 模板）

1. 目标架构与基础镜像确定：运行阶段基础镜像明确写 `linux/arm64` 变体，构建阶段用 `--platform=$BUILDPLATFORM` 避免交叉架构下慢到不可用。
2. 依赖清点表产出：每个含 native 的依赖标注"有 arm 版 / 纯 Java / 需替换 / 未知"，**未知项为 0 才允许提测**。
3. Netty/epoll 与线程模型确认：检查是否仍在用原生传输，回退到 NIO 要在报告里显式记录。
4. 序列化与持久格式审查：全局搜 `ByteBuffer`、`Unsafe`、Java 原生序列化、跨语言二进制格式；凡落库/落文件的二进制表示改为显式字节序。
5. 并发代码审查：跨线程共享可变字段的发布与可见性（`volatile`/final/锁），重点看自旋、双重检查、无锁计数（对照 [08-CPU缓存与内存序](../15-计算机基础/08-CPU缓存与内存序.md)）。
6. JVM 参数重算：堆大小、`ActiveProcessorCount`、`ParallelGCThreads`、`ConcGCThreads`、GC 算法选择全部按新平台重出，不允许照抄（第五节）。
7. 镜像可追溯：部署清单写 **digest**，禁用 `latest`；构建产物推多架构 manifest list 并保留一份"本次构建包含哪些架构"的记录。
8. 第三方 Agent 逐个确认：APM 探针、日志采集、加解密 SDK、License 组件是否有 ARM 版；没有的必须给出替代方案（外置采集/换库/找厂商）。
9. 观测面补齐：指标里加节点架构标签（否则两边的数据在同一个看板上混在一起，事故时无法归因）。
10. 基线测试：按第四节八条规则做同代码异构对比，报告含 p99、CPU/请求、GC 停顿分布，三轮以上。
11. 浸泡测试：长时间运行看内存增长与停顿趋势，异构上的泄漏与退化常比 x86 更晚暴露。
12. 回退可执行：明确"退回 x86 栈"的操作路径与数据回同步方式（投产口径见 [10 篇 5.4 节](./10-银行研发运维流程与投产管控.md)）。

## 四、性能基线方法论：为什么"ARM 慢三成"多半是没调优

**不要拿"我们试过 ARM，慢 30%"当结论。**这句话在行业讨论里非常常见，而绝大多数情况下的真实原因是下面这些前提没做，不是 CPU 本身：

| 常见假因                    | 说明                                                                    |
| --------------------------- | ----------------------------------------------------------------------- |
| 照抄 x86 的 JVM 参数        | 核数、GC 线程数、堆大小、 region 大小都按原机型的比例配的，换平台没重算 |
| 没绑核、没管 NUMA           | 线程在 NUMA 节点间漂移，跨颗访存把时延抖动作常态化                      |
| 内存没插满通道 / 网卡单队列 | 硬件本身就残，跟 CPU 无关                                               |
| BIOS 用出厂默认             | 出厂常偏节能，负载上来后频率与延迟都在动                                |
| native 依赖静默回退         | 如 3.2 表第 2 行，epoll 退成 NIO，报表看不出来                          |
| 没预热就采样                | JIT 未收敛，前几分钟的数据被当成结论                                    |
| 负载模型不可比              | 两边数据量、并发、缓存命中率、SQL 分布都不一样                          |

### 4.1 可信对比的八条规则

1. **同代码**：同一 commit、同一构建产物（记录 digest），只换运行环境。
2. **同数据量与分布**：含倾斜、大字段、冷热比；造数方式两边完全一致。
3. **固定并发阶梯**：如 1 → 2 → 4 → 8 → 16 → 32 → 64 并逐级加压，取每一级的稳态值；不要只跑一把固定并发。
4. **看分布不看均值**：p50/p95/p99/p999 与最大停顿；均值在银行场景几乎没有决策价值。
5. **显式记录环境**：CPU 型号与核数、`numactl --hardware`、内核版本、glibc 版本、BIOS 关键项、内存插法、网卡队列数、**完整 JVM 参数**。
6. **隔离 NUMA 做两组**：一组默认调度、一组绑核绑内存，差异本身就是要报告的内容。
7. **跑三轮以上取分布**：单轮数据不采信；同时报告轮间波动幅度。
8. **单变量归因**：每次只改一个参数重跑，否则"慢"无法归因到 CPU/参数/依赖中的哪一个。

### 4.2 必采指标清单

| 指标                | 为什么必须采                                                          | 采集口径                                                                                |
| ------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 吞吐（QPS/TPS）     | 基础可比项                                                            | 阶梯每一级的稳态值，剔除预热与收尾                                                      |
| p95 / p99 / p999    | 银行看的是长尾，不是平均                                              | 按接口分别统计，不合并全站                                                              |
| **CPU 时间 / 请求** | 异构比较时比"CPU 占用率"更可比：占用率受核数影响，每请求 CPU 时间不受 | 总 CPU 时间 ÷ 请求数                                                                    |
| 单位功耗吞吐        | 换 ARM 常以省电为动因，不量功耗就证不了收益                           | 机柜电表或 BMC 功耗读数 ÷ 吞吐（无计量条件就明确写"未采"）                              |
| GC 次数与停顿分布   | 停顿直接决定 p99 达标与否                                             | GC 日志（→ [12-性能工程/02](../12-性能工程/02-GC日志与停顿分析.md)），不要只看监控面板  |
| 分配速率与晋升量    | 判断"是不是堆太小在硬扛"                                              | 同上                                                                                    |
| 上下文切换          | 绑核与线程池配置是否合理的信号                                        | `pidstat -w` / `vmstat`（→ [01-进程线程与调度](../15-计算机基础/01-进程线程与调度.md)） |
| 内存带宽 / LLC      | 带宽是否成为上限（有条件才采）                                        | `perf` 相关事件，采不到就在报告里写"未采"                                               |
| 线程数与池等待      | 线程池/连接池排队是隐性时延                                           | 应用指标（→ [07-线程池调优与背压](../12-性能工程/07-线程池调优与背压.md)）              |
| 错误率与超时率      | 高压下先崩的是尾部                                                    | 按错误类型分开，别只报总数                                                              |

压测工具与脚本口径见 [05-性能压测实战-k6与JMeter](../08-测试/05-性能压测实战-k6与JMeter.md)。

```text
异构基线的正确姿势：一次只换 CPU，其余全部锁死

  同一构建产物（digest 相同，禁止为不同架构分别编译）
          │
          ├──────────────────────────────┐
          ▼                              ▼
  x86 节点（基线组）               ARM 节点（对比组）
  环境记录表 A                     环境记录表 B
  机型 / 主频 / 内核 / JDK 版本     机型 / 主频 / 内核 / JDK 版本
          │                              │
          └──────────────┬───────────────┘
                         ▼
  同一份造数 + 同一并发阶梯 + 同一预热规则 + 同一时长 + 至少三轮
                         │
                         ▼
  指标集：p50 / p95 / p99 / p999、CPU 时间每请求、GC 停顿分布、
          上下文切换次数、内存带宽与 LLC 未命中
                         │
                         ▼
  结论：差值必须能归因到"换了 CPU"这一个变量，否则结论无效
```

### 4.3 手上没有 ARM 实机怎么办（三档替代与其边界）

学习阶段不必买服务器，但必须诚实标注每档手段能证明什么——把模拟结果写进性能结论，是最典型的"POC 结论当生产结论"（[12 篇 5.1 节形态 5](./12-信创全景与银行替换路线.md)）。

| 手段                            | 能证明                                                                      | 不能证明                                                          | 备注                                                   |
| ------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------ |
| 公有云 ARM 实例（按量开几小时） | 功能等价性、启动与依赖可用性、粗略性能量级、GC 行为趋势                     | 行内机型的具体表现（微架构、内存插法、网卡与存储组合）            | 性价比最高的一档；记得按 4.1 节第 5 条把环境记录表填全 |
| `binfmt` + QEMU 跑 arm64 容器   | 镜像能否构建与解析、`exec format error` 类问题、纯 Java 代码能否运行        | **任何性能结论**（模拟有数量级开销）；native 库的真实行为可能失真 | 适合放进 CI 做"能不能起"的冒烟，不适合做基线           |
| 厂商借用样机 / 联合实验室       | 目标机型的真实性能、可运维性（BMC/带外/固件）、与国产 OS 和数据库的组合表现 | 你行的真实数据量与负载模型                                        | 借用期短，提前把测试用例与脚本全部备好，进场只做执行   |

> 一句可以写进报告的话：**功能结论可来自模拟环境，性能与容量结论必须来自目标机型的实机测量。**

## 五、操作系统与 JVM 调优在国产平台上的差异

核数变多、NUMA 变复杂之后，原来"参数照抄就行"的前提没了。下面每一项都是**换平台必须重看**的。

| 项                  | 为什么在国产多核平台上要重看                                                                                                                                                                        | 怎么落                                                                                                                                                                                                                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 大页与 THP          | 大页降低 TLB miss，对堆大、内存访问密集的服务有利；**透明大页 THP 对数据库和延迟敏感服务常是抖动源**                                                                                                | THP 在数据库节点上通常设为 `never` 或 `madvise`（具体取值与厂商建议一致，改前做 A/B）；显式大页要宿主预留内存，容器内不能自己变出来                                                                                                                              |
| CPU 亲和与绑核      | 线程跨核漂移带来缓存失效与 NUMA 远端访问；核数一多，漂移概率反而更高                                                                                                                                | 容器里用整核申请 + CPU Manager 静态策略（→ [02-K8s资源治理与弹性伸缩](../16-云原生与GitOps/02-K8s资源治理与弹性伸缩.md)）；裸机用 `taskset`；网卡中断另行绑到不跑业务的核                                                                                        |
| `numactl`           | 让 JVM 的内存落在它运行的那个 NUMA 节点上                                                                                                                                                           | `numactl --cpunodebind=N --membind=N java ...`；多节点大堆也可考虑 `--interleave=all`，但要实测，两种都可能更好                                                                                                                                                  |
| 容器内可见 CPU 数   | JVM 靠 cgroup 配额推算可用核数，决定 GC 线程、编译器线程、fork-join 池大小；配额形态不同（`cpus` 小数配额 vs 整核）会让 JVM 得到很不一样的核数                                                      | 用 `-XX:ActiveProcessorCount=N` 显式钉住并在环境记录表里写清；cgroup 版本与 JDK 版本的组合要实测（原理见 [06-容器隔离原理](../15-计算机基础/06-容器隔离原理-namespace与cgroup.md) 第五节）；本项目已具备注入条件：`ai-cs-chat/Dockerfile:21` 的 `${JAVA_OPTS:-}` |
| GC 线程数与核数放大 | **核多不等于并发 GC 线程越多越好**：并行阶段需要所有线程到齐，线程越多"等最慢那个"的概率越高；还会加剧内存带宽竞争与伪共享（→ [08-CPU缓存与内存序](../15-计算机基础/08-CPU缓存与内存序.md) 第四节） | 显式设置 `-XX:ParallelGCThreads` / `-XX:ConcGCThreads` 做 A/B，不要默认随核数线性放大；停顿目标看 `-XX:MaxGCPauseMillis` 与实测分布是否一致                                                                                                                      |
| 堆大小与内存预算    | 单机从 8 核变 64 核，一个 Pod 的堆上限若照抄，节点上进程数与堆总量关系全变                                                                                                                          | 按节点重算内存预算（→ [01-JVM参数与GC选型](../12-性能工程/01-JVM参数与GC选型.md) 第五节的容器内存算法），堆外、元空间、线程栈都要留                                                                                                                              |
| 内核参数            | 文件描述符、`pid_max`、`swappiness`、conntrack、网络缓冲等在核数与并发放大后不再是同一个量级                                                                                                        | 变更要留档、并纳入配置基线（配置管控口径见 [10 篇第三节](./10-银行研发运维流程与投产管控.md)）；别在单台机器上手改后忘了记                                                                                                                                       |
| 时间一致性          | 异构与虚拟化程度更高时，时钟漂移与跳变风险上升；证书校验、分布式 ID、日志排序、超时判断都依赖时间                                                                                                   | 统一 `chrony` 源与时区策略；`TZ` 与容器时区一致性检查（见 [07-字符编码与时区](../15-计算机基础/07-字符编码与时区.md) 第六节只讲时间的那部分）                                                                                                                    |

| --------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 机型与入围状态  | 机型 + 部件配置（CPU/内存/盘/网卡型号）都在目录内；同一"型号名"下的可选部件差异                             | 只锁到机型名，到货后部件换了批次，问题不复现                                 |

| BIOS/UEFI 设置  | 性能模式（关节能）、C/P-state 策略、超线程/SMT 开关、硬件预取、NUMA 与内存交错模式、虚拟化支持、Secure Boot | 用出厂默认；后来发现"慢"其实一直没开性能模式                                 |

| 磁盘与 RAID     | RAID 级别、卡缓存写策略与掉电保护（电池/超级电容）**当前健康状态**、分区对齐、盘调度器                      | 缓存电池失效自动转透写，写延迟成倍上升却无人报警                             |

| 支持矩阵（HCL） | Hardware Compatibility List（硬件兼容列表）：OS/数据库/中间件厂商是否明确支持该机型与部件组合               | 把"厂商说支持"写进方案，出事后没人认                                         |

### 6.1 到货与投产前的实测命令清单（输出全部归档）

验收不看外观和数量，看这十几条命令的输出。把它们存进 4.1 节第 5 条要求的"环境记录表"，异构对比才有共同前提。

```bash
# CPU 与 NUMA 拓扑：核数、Socket、NUMA 节点数与距离
lscpu; numactl --hardware; lstopo --of txt > topo.txt 2>/dev/null   # lstopo 缺失就退回 lscpu -e

# 每核归属与在线状态（绑核策略的输入）
lscpu -e=CPU,CORE,SOCKET,NODE

# 内存通道是否插满（条数与容量分布；具体通道归属要看厂商文档）
dmidecode -t memory | grep -E "Size|Locator|Speed" | grep -v "No Module"

# RAID/HBA：卡缓存写策略与掉电保护状态（工具名随厂商不同，示意用 storcli）
storcli64 /call show; storcli64 /call/cv show all        # cv = cachevault，电池/电容状态

# 盘与调度器：确认 NVMe 使用的调度器与队列数
lsblk -d -o NAME,ROTA,SIZE,MODEL; cat /sys/block/nvme0n1/queue/scheduler

# 网卡：多队列是否开启、队列数、当前 IRQ 分布
ethtool -l eth0; ethtool -i eth0; grep eth0 /proc/interrupts

# 大页与 THP（数据库节点常要求 never/madvise，以厂商建议为准）
cat /sys/kernel/mm/transparent_hugepage/enabled; grep -i huge /proc/meminfo

# 时钟同步：源、偏移与是否在线
chronyc tracking; chronyc sources -v; timedatectl status

# 带外管理与固件基线（Redfish 示例，凭据从密钥管理系统取，不写进脚本）
curl -sk -u "$BMC_USER:$BMC_PASS" "https://$BMC_IP/redfish/v1/UpdateService/FirmwareInventory"

# JVM 视角的可用处理器数（与容器配额是否一致）
java -XshowSettings:vm -version 2>&1 | grep -i processor
nproc; cat /sys/fs/cgroup/cpu.max 2>/dev/null || cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us
```

> 表里出现的具体工具名（`storcli`、`lstopo`）随厂商与发行版不同，**以现场实际可安装的工具为准**；采不到的项在记录表里写"未采"，不要留空——留空在评审时会被当作"没验"。

## 九、动手练习

1. **写一段采集脚本**（`deploy/scripts/collect-node-profile.sh`）：在同一台机器上输出 `uname -m`、`lscpu`（型号/核数/Socket/NUMA 节点数）、`numactl --hardware`、`nproc` 与容器内 `-XX:+PrintFlagsFinal` 里的 `ActiveProcessorCount`、`ldd --version`、`cat /proc/meminfo | grep -i huge`、THP 开关、`java -XshowSettings:properties -version 17`。要求：把输出重定向成 `<host>-<arch>.txt` 归档，作为第 4.1 节的"环境记录表"。**这一步做完，你才有资格说两台机器跑的数据可以比较。**
2. **给本项目补多架构构建**：改 `ai-cs-chat/Dockerfile` 与 `deploy/scripts/k8s-build-push.sh`——(a) 在 Dockerfile 用 `FROM --platform=$BUILDPLATFORM maven:3.9-eclipse-temurin-17 AS builder`（构建阶段跑在本地架构上，避免交叉架构下 Maven 慢），运行阶段仍按目标架构取基础镜像；(b) 构建脚本改用 `docker buildx build --platform linux/amd64,linux/arm64 -t ... --push`，产出 manifest list；(c) 把 `:latest` 推送去掉、改为**部署清单里写 digest**；(d) 用 `docker manifest inspect` 验证。完成后把 `ai-cs-product` 的 alpine 镜像统一到 `17-jre-jammy`（理由写进提交说明）。镜像构建优化口径见 [06-镜像构建优化与安全扫描](../16-云原生与GitOps/06-镜像构建优化与安全扫描.md)。
3. **设计一份"同代码异构机器"压测方案**：以 `ai-cs-chat` 的一个接口为对象，按第 4.1 节八条规则写完整方案（负载模型、阶梯、数据量、预热、指标清单、三轮安排、报告模板），并在报告模板里强制包含"CPU 时间/请求"和"p99"两栏。工具用本仓库现有的 k6 脚本改造（→ [05-性能压测实战-k6与JMeter](../08-测试/05-性能压测实战-k6与JMeter.md)）。没有 ARM 实机怎么办？用 `qemu` + 容器模拟做**功能等价性**验证，并在方案里明确写"性能结论必须实机取得，模拟不采信"——这句话本身就是评审加分项。
4. **做一次 native 依赖清点**：执行 `mvn -q dependency:list` 输出全量依赖，用脚本扫本地仓库里各 jar 中的 `.so`/`.dll`/`META-INF/native`，产出一张"依赖 → 是否含 native → 是否有 aarch64 变体 → 处置方案"的表。重点确认 Netty 与 Redisson 相关包的 classifier。这张表就是第 3.2 节表第 1、2 行的答案。
5. **做一次弱内存序实验**：拿 [08-CPU缓存与内存序](../15-计算机基础/08-CPU缓存与内存序.md) 第八节走读过的并发结构，故意去掉一个 `volatile`，在 x86 机器上跑 10 分钟不报错，再在 ARM 环境（可用云上的 arm64 实例）跑同样用例观察差异。**做完这个实验，你就再也不会说"Java 跨平台所以不用重测"。**

## 十、初学者常见误区

| 误区                               | 真相                                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| "核多就是算力强"                   | 联机交易的 p99 由**单核性能 + 内存延迟 + NUMA 归属**决定；核数只决定并行上限。64 核不绑核、跨节点访存的服务，常常输给 16 核调优过的服务（第二、五节）              |
| "Java 跨平台，所以换架构不用重测"  | 免测的只有源码到字节码那一段。native 库、libc、JIT/GC 行为、镜像架构、探针可用性全部要重验（第 3.1 节那张横向图）                                                  |
| "换 ARM 之后要处理大端小端问题"    | 现代主流服务器 CPU 基本是小端，x86_64 与常见 aarch64 都是。真正要防的是**把平台序的二进制当持久格式**：定长报文、序列化数据落库后跨架构读才会出错（3.2 表第 4 行） |
| "镜像 tag 一样，内容就一样"        | 同一个 tag 可以在不同架构上解析成不同 manifest。异构环境的取证单位是 **digest**，`latest` 更是不可追溯（本项目 `docker-compose.yml:149` 就是这个反例）             |
| "厂商标称跑分能当业务性能"         | 跑分是固定负载的稳态值，不反映你的依赖链、GC、网络与数据倾斜。可信度来自第四节的同代码异构对比，不来自 datasheet                                                   |
| "按 CPU 颗数计价最划算"            | 先确认软件到底按什么计价。按核计价的软件 + 核数多的 CPU，会把硬件省下的钱在授权上吐回去（2 节最后一行、[12 篇第四节第 7 问](./12-信创全景与银行替换路线.md)）      |
| "换国产服务器主要是省电费"         | 省的是单位算力能耗，代价可能在配电、风道、机柜功率余量、带外采集适配上。**先做机房勘察再谈节能**（第二节的"功耗与机柜"行）                                         |
| "x86 授权路线完全兼容所以零风险"   | 用户态二进制能跑 ≠ 指令扩展、性能特征、供货连续性都一致。海光/兆芯路线仍需完整的性能与稳定性回归，只是不需要重出镜像                                               |
| "先把机器换完，性能问题投产前再调" | 平台相关的问题（NUMA、绑核、native 回退、GC 停顿）越晚发现改造成本越高，因为**业务代码已经按错误基线扩了容量**。基线要在选型阶段就出（第四节）                     |
| "JVM 参数照抄 x86 那套"            | 参数里凡是与核数、内存、GC 并发度相关的默认值都会随平台变。第五节那张表逐项重看，并把最终值写进配置基线                                                            |
