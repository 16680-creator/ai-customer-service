# 国产操作系统与虚拟化容器适配

> 本篇回答一个问题：**假设你的 Java 应用要换到国产 OS + 国产虚拟化/容器平台上跑，作为后端开发，哪些事情必须你亲自验证、坑到底在哪一层、验证动作具体敲哪条命令**。
> 信创（信息技术应用创新，即芯片/OS/数据库/中间件的国产化替代）不是"运维换个系统重装一遍"，它会把"你以为和 OS 无关的东西"——JVM 参数、native 库、字符集、时钟、镜像架构——全部推到台面上。
> 前置阅读：[银行 IT 体系与岗位全景](./01-银行IT体系与岗位全景.md) §4.3（信创在银行技术栈里的位置）、[银行业信息安全管理规范](./07-银行业信息安全管理规范.md)（OS 层基线的制度来源）、[银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)（打补丁与变更窗口怎么走）。芯片与整机侧的内容见 [国产芯片与服务器选型](./13-国产芯片与服务器选型.md)，OS 之上的中间件与运行时见 [国产中间件与 Java 运行时适配](./16-国产中间件与Java运行时适配.md)。

## 一、先看清版图：谁是发行版，谁是根社区，谁在自研

银行机房里能看到的"国产操作系统"，绝大多数**仍然是 Linux**：内核主线由国际社区维护，国内厂商做的是"发行版"这一层——打补丁、集成驱动、加固安全模块、给支持和认证。理解这一点，就知道踩坑时该改配置还是该找原厂。

| 产品/社区                  | 厂商与归属（公开资料）                                                               | 技术源流与定位                                                                                         | 踩坑时找谁                |
| -------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ | ------------------------- |
| 银河麒麟高级服务器操作系统 | 麒麟软件有限公司（由中标软件与天津麒麟合并组建，公开资料显示控股方在中国电子体系内） | 面向党政与关键行业的商业化服务器发行版；与 openEuler 生态存在承接关系（以具体版本 release notes 为准） | 发行版原厂工单            |
| 统信服务器操作系统 UOS     | 统信软件技术有限公司                                                                 | 与社区版 deepin 同源的商业化 lineage，桌面侧存量最大，服务器侧扩张中                                   | 发行版原厂工单            |
| openEuler（欧拉）          | 华为发起并开源，现由开放原子开源基金会托管                                           | **根社区**：多家厂商基于它发布商业发行版，也承担"上游"角色                                             | 社区 + 你的商业发行版厂商 |
| 龙蜥 Anolis OS             | 龙蜥社区（阿里发起并投入为主，多家厂商参与）                                         | 定位为 CentOS 迁移的承接者之一，内核有自研分支                                                         | 社区 / 提供商业支持的厂商 |
| CentOS（历史包袱）         | 红帽（IBM 系）                                                                       | 曾是 RHEL 的"下游免费二进制兼容版"，后改为 Stream（上游滚动预览版）                                    | 没人——这正是问题的根源    |
| 其他                       | 普华、中科方德、麒麟信安等                                                           | 各有行业侧重；**具体以行内采购目录与入围证明为准**                                                     | 采购目录里的原厂          |

**三类角色的现实差别**（决定了你排查问题的路径）：

```text
   内核主线（Linux kernel，国际社区）
        │  厂商打补丁、加安全模块、认证驱动
        ▼
   根社区 ── openEuler / 龙蜥 Anolis ──►  提供"上游"：包、内核分支、CVE 响应
        │  商业集成、认证硬件、SLA、驻场
        ▼
   商业化发行版 ── 麒麟 / 统信 / 各厂商衍生版 ──►  你在生产上真正跑的那一层
        │
        ▼
   你的应用（JDK / jar / 容器镜像）
```

| 你要做的事          | 商业化发行版                             | 根社区版                   |
| ------------------- | ---------------------------------------- | -------------------------- |
| 拿安全补丁          | 走原厂通道，有 SLA，包带签名             | 自己跟社区，自己验证与分发 |
| 硬件驱动认证矩阵    | 找厂商兼容性列表（不在列表=不受理）      | 自己验证                   |
| 出重大故障定责      | 提工单，厂商给结论与回退方案             | 没有对手方，全靠自己定位   |
| 排查通用 Linux 问题 | 完全一样：文档、命令、内核参数都是通用的 | 一样                       |

**为什么 CentOS 停更是这轮替代的直接导火索**：过去十年银行的应用服务器大量是 CentOS（免费、和 RHEL 二进制兼容、运维熟）。CentOS 8 从"稳定复刻版"改成"滚动预览版"、CentOS 7 也越过维护终点之后，行内出现一个真空：**要安全更新，就得付钱买 RHEL；不想付钱又要支持，就得找一个有原厂的替代品**。这个"替代品"恰好和信创采购目录重合，于是"换 OS"从技术决策变成了既成事实。这也是银行口径里"不能把生产系统建在一个没有人负责更新的上游"的具体来历（行业通行做法）。

## 二、对 Java 应用的适配影响：逐条给可验证动作

以下每一条都给"人话解释 + 怎么确认"。**不要背结论，要背验证动作**——面试官追问时，能说出命令的人才是真踩过坑的人。

### 2.1 glibc 版本：`GLIBC_2.xx not found` 是怎么来的

glibc（GNU C Library，Linux 上最常见的 C 运行时库）是**所有 native 代码的地基**：JDK 本身、JNI 库、APM Agent（应用性能监控探针）里的 `.so`、数据库本地客户端、压缩/加解密库，都链接它。glibc 用"符号版本化"（symbol versioning，同一个函数名在库里按版本共存，符号名带 `@@GLIBC_2.xx` 后缀）做到**向后兼容、不向前兼容**：在老 glibc 上编的二进制能在新 glibc 上跑，反之会报：

```text
/lib64/libc.so.6: version `GLIBC_2.34' not found (required by /app/lib/libxxx.so)
```

成因只有一个：**构建环境的 glibc 比运行环境新**。排查动作：

```bash
getconf GNU_LIBC_VERSION            # 本机 glibc 版本（构建机与生产机各查一次）
ldd --version | head -1
readelf -V /app/lib/libxxx.so | grep -o 'GLIBC_[0-9.]*' | sort -u   # 这个 so 要求哪些版本
objdump -T /usr/lib64/libc.so.6 | grep -c GLIBC_                    # 运行时 libc 提供哪些版本
```

处置原则（按优先级）：① **构建基线与运行基线同源**——用和生产同一发行版同一镜像版本的构建容器，别用"最新开发机上顺手 build"；② 若必须前向兼容，在**更低 glibc 的环境里编译**（"取最低公共基线"是行业通行做法）；③ 不要试图靠拷贝 `libc.so.6` 或 `LD_LIBRARY_PATH` 指到新 glibc 解决——glibc 和动态链接器 `ld-linux` 必须成对，硬换会把整台机器弄挂。

### 2.2 OpenSSL 大版本：native 库与 Agent 的第二块地基

OpenSSL 是 TLS 与加解密实现，大版本之间**共享库 soname 不同**（`libssl.so.1.1` 与 `libssl.so.3` 是两个不同的库；更老的发行版还有 `libssl.so.10`）。影响面：

| 受影响的东西                     | 典型现象                                                     | 确认方式                                                     |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 链接 OpenSSL 的 native 库/JNI    | 启动即 `error while loading shared libraries: libssl.so.1.1` | `ldd /app/lib/*.so`；`ls -l /usr/lib64/libssl*`              |
| Netty 的 tcnative / APR 类加速库 | 优雅降级为 JDK 自带实现（性能变化）或加载失败                | 启动日志里搜 `OpenSSL` / `tcnative`                          |
| APM/安全 Agent（带本地加密组件） | Agent 注入失败，应用"能跑但没监控数据"                       | 比对 Agent 厂商的支持矩阵                                    |
| TLS 握手                         | 新 OpenSSL 默认安全级别更严，老算法/老证书被拒               | `openssl version`；`openssl s_client -connect <host>:<port>` |

银行场景特别注意：**国密（SM2/SM3/SM4）算法栈往往依赖厂商提供的 OpenSSL 分支或密码中间件**，替换 OS 等于替换了这套加密底座，涉及对接加密机与渠道证书链路，必须和 [07 篇第五节](./07-银行业信息安全管理规范.md) 的国密改造一起评估，不能当成"系统自带库升级"。

### 2.3 libc 家族：glibc 与 musl 不是一回事

musl 是另一个 C 运行时库（Alpine 系镜像默认用它）。它体积更小，但**ABI 与 glibc 不兼容**：按 glibc 编译的 `.so` 在 musl 上直接加载失败；DNS 解析、`nsswitch.conf`、locale 与 iconv 支持、线程栈默认大小也都与 glibc 有差异。本仓库就有一个现成的反例：

```dockerfile
# ai-cs-product/Dockerfile:1 —— 全项目唯一一个 alpine（musl）运行镜像
FROM eclipse-temurin:21-jre-alpine
```

其余 8 个服务的运行阶段都是 `eclipse-temurin:17-jre-jammy`（见 `ai-cs-chat/Dockerfile:17`），glibc 家族。**同一套代码在两种 libc 上不是同一个测试范围**：product 服务如果哪天接了带 JNI 的加解密 SDK 或本地压缩库，它的失败模式和其他 8 个服务完全不同。确认 libc 家族：

```bash
ls /lib/ld-musl-*.so.1 2>/dev/null && echo musl || echo glibc   # 容器内快速判型
ldd /bin/ls                                                     # glibc 显示 linux-vdso...libc.so.6；musl 显示 ld-musl
```

结论性要求：**同一集群内的基础镜像 libc 家族必须统一**，并在基线文档里写明；换 libc 家族视同换 OS，走完整回归。

### 2.4 systemd 单元与默认运行级别

systemd 是现代发行版的 1 号进程与服务管理器（`systemctl`、`journalctl` 都由它提供）。换 OS 后要确认的不是"有没有 systemd"（都有），而是**默认值不一样**：

```bash
systemctl get-default                       # 默认运行级别：multi-user.target（相当于旧 runlevel 3）/ graphical.target（5）
systemctl is-active chronyd ntpd firewalld  # 谁在提供时间同步、谁在管防火墙（各行基线要求不同）
systemctl show <svc> -p LimitNOFILE         # 服务级文件描述符上限（不看这个，只看 ulimit 会误判）
journalctl --disk-usage                     # 本地日志占盘策略，银行基线会限制并要求外发
```

生产上还要注意：应用不该依赖 `rc.local`、`xinetd`、SysV 脚本这类旧机制；开机自启、依赖顺序（`After=network-online.target`）、失败重启策略都要落到 unit 文件里，并且**这些改动属于配置变更，要走 [10 篇第五节](./10-银行研发运维流程与投产管控.md) 的变更流程**。

### 2.5 内核参数：默认值随发行版变，不改就会在生产现形

内核参数是"宿主机级别"的，容器里的 Java 进程读的也是宿主机的值。**换 OS = 换了一批默认值**，这张表是要逐台核对的（行业通行做法是把它们写进行内 OS 基线并纳入配置核查）：

| 参数/项             | 看什么                                                                                | 谁会受影响                                           | 不处理的后果                            |
| ------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------- |
| `vm.swappiness`     | `sysctl vm.swappiness`；是否设为 0/10/60                                              | JVM 堆、页缓存、本地缓存类中间件                     | 堆被换出 → 停顿突然放大、监控看不出原因 |
| THP 透明大页        | `cat /sys/kernel/mm/transparent_hugepage/enabled`                                     | Redis、MongoDB、部分内存型中间件（官方部署建议关闭） | 内存碎片整理触发长停顿、延迟毛刺        |
| 文件描述符上限      | `ulimit -n`、`/etc/security/limits.conf`、`DefaultLimitNOFILE`、unit 的 `LimitNOFILE` | 所有高并发服务（连接数 = fd 数）                     | `Too many open files`，且只在压测后出现 |
| `nf_conntrack`      | `sysctl net.netfilter.nf_conntrack_max`；`dmesg` 搜 `table full`                      | 有 NAT/iptables 的容器节点（K8s 节点高发）           | 静默丢包，表现为"偶发连接超时"          |
| 网络队列与 backlog  | `net.core.somaxconn`、`tcp_max_syn_backlog`、`ip_local_port_range`、`tcp_fin_timeout` | 网关、负载均衡前置、大量短连接的外部对接             | 高并发下 SYN 队列溢出、端口耗尽         |
| 内存回收与 OOM 行为 | `vm.overcommit_memory`、`dmesg` 里的 oom-kill 记录                                    | 容器化 Java（堆 + 元空间 + 线程栈 + 直接内存）       | 进程被内核杀掉，日志里没有 Java 异常    |

排查动作：把 `sysctl -a > baseline.txt` 在旧环境与新环境各采一份做 diff，**diff 出来的每一项要么写进行内基线，要么显式说明"不需要改"**——"不确定就不改"在银行会被认定为未完成验证。

### 2.6 时钟同步：银行对时间一致性是刚性要求

新发行版的默认 NTP 实现普遍是 **chrony**（`ntpd` 在不少发行版已不再是默认甚至不再提供）。chrony 和 ntpd 不是"换个名字"：chrony 用 step/slew 策略更积极，配置项、状态查询命令都不同。

```bash
chronyc tracking          # 当前偏移、上次同步时间、选的源
chronyc sources -v        # 候选源列表与健康度（^ 表示当前同步源）
timedatectl               # NTP 是否生效、时区、本地时间
```

为什么银行把这件事提到很高优先级（这条链要能一口气讲完）：

```text
时钟偏移 / 跳变
  ├─ 日志时间戳错位 → 跨系统排障时对不上同一次请求（见 ../13-稳定性工程/08-oncall手册与故障响应.md）
  ├─ 会计日期归属错 → 日切边界交易归错营业日，账账核对不平（见 ./02-核心系统与会计账务引擎.md §7）
  ├─ 对账文件找不到 → 按日期匹配的渠道对账文件落到相邻目录，表现为"文件未到"（见 ./09-金融级一致性与对账实战.md §7）
  ├─ 雪花 ID 冲突 → 发号器依赖时钟单调，回拨会等待甚至生成重复 ID（见 ../03-数据库与ORM/04-分布式ID规范.md）
  ├─ 证书/TLS 校验失败、令牌过期判断错 → 对接渠道报"签名无效/已过期"，实为时钟问题
  └─ 审计合法性 → 留痕时间不可信，检查时属于证据链缺陷
```

要求（行业通行做法）：全行统一时钟源与层级、生产机禁止手工 `date -s`（会破坏审计链，且触发告警）、偏移量进监控并有告警阈值、时间同步服务本身纳入变更管控。开发侧要做的配合是：**业务时间一律取"受理时前置生成的营业日期与时间戳"并随报文全链传递，任何环节不得自取本地时间**——这条与 [02 篇 §7.2](./02-核心系统与会计账务引擎.md) 是同一个结论在 OS 层的展开。

### 2.7 字符集与 locale：GBK/UTF-8 的历史包袱

locale（区域设置，决定语言、字符集、排序与数字格式）在生产上常常是"最小化安装 + 没人配"，于是 `LANG` 为空。这里有一个**只对 JDK 17 成立的坑**：JDK 18 起默认字符集统一为 UTF-8，而本项目用的是 JDK 17（`pom.xml:30`），它的 `file.encoding` 与 `sun.jnu.encoding`（文件名编码）**仍然跟随环境**。C/POSIX locale 下可能落到 US-ASCII，表现为中文常量、SQL 注释、文件名、日志全部乱码，而同一镜像在开发机上完全正常。

```bash
locale                                  # LANG/LC_ALL 是否被显式设置
cat /etc/locale.conf
java -XshowSettings:properties -version 2>&1 | grep -E 'file.encoding|sun.jnu.encoding'
jcmd <pid> VM.system_properties | grep encoding    # 线上进程实际生效值（比看文档可靠）
```

银行历史包袱的三种具体形态：老系统/老终端用 GBK 或 GB18030；渠道报文与固定长度字段按字节计数；报表导出给老版 Excel 时按 GBK 编码打开。**换 OS 不会把 GBK 变成 UTF-8，只会让"谁在隐式转换"暴露出来**。字符与时区的地基在 [字符编码与时区](../15-计算机基础/07-字符编码与时区.md)，本篇只补一条信创视角：新发行版默认 UTF-8，凡是依赖平台默认编码的代码都必须显式指定，禁止 `new String(bytes)` 这类无charset写法。

### 2.8 cgroup v1 / v2：JVM 能不能"看见"容器给的资源

cgroup（control group，内核做资源限制与统计的机制）有两个互不兼容的版本布局。K8s 节点切到 cgroup v2 后，**限制读取路径变了**（v1 是 `memory.limit_in_bytes`，v2 是 `memory.max`），JDK 15 及以后原生支持 cgroup v2，老 JDK 补丁版本只认 v1——本项目 JDK 17 在支持范围内，但行内如果有 JDK 8 存量服务必须逐个确认。

```bash
stat -fc %T /sys/fs/cgroup/       # cgroup2fs = v2；tmpfs = v1
cat /sys/fs/cgroup/memory.max     # v2；v1 路径为 memory/memory.limit_in_bytes
```

后果是三件事叠在一起：① `-XX:MaxRAMPercentage` 算出的堆大小变了；② `Runtime.getRuntime().availableProcessors()` 变了，连带 GC 线程数、ForkJoinPool、Netty 默认线程数、连接池初始化都变；③ 依赖 cgroup 文件的监控探针/APM Agent 若版本过老，采到空值或按宿主机总量上报。本仓库运行镜像的堆是靠环境变量注入的（`ai-cs-chat/Dockerfile:21` 的 `java ${JAVA_OPTS:-} -jar app.jar`），而 K8s 清单里把堆写成固定值且和容器 limit 关系紧（`deploy/k8s/services/user-service.yaml:69-77`，堆与内存 limits 同时给出）——这类配置在换 cgroup 版本时必须重新核对，做法与参数选择见 [JVM 参数与 GC 选型](../12-性能工程/01-JVM参数与GC选型.md)，隔离机制本身见 [容器隔离原理](../15-计算机基础/06-容器隔离原理-namespace与cgroup.md)。

## 三、容器与镜像在信创环境的现实约束

### 3.1 镜像必须按目标架构构建

CPU 架构决定镜像架构：x86_64 节点跑 `linux/amd64`，ARM 系国产 CPU 节点跑 `linux/arm64`（`uname -m` 显示 `aarch64`）。拿错架构的镜像，报错非常直白：

```text
exec format error
no matching manifest for linux/arm64/v8 in the manifest list entries
```

确认动作：`docker manifest inspect <image>` 看它支持哪些平台；节点侧 `kubectl get nodes -o wide` 看 ARCHITECTURE 列。本仓库的构建脚本目前是单架构 `docker build`（`deploy/scripts/k8s-build-push.sh:31-35`），推上去的镜像只有构建机那一种架构——**假设要进异构机房，这里必须先改**。

### 3.2 多架构 manifest 是必需品，不是优化项

同一个 tag 要能在 x86 与 ARM 节点上都拉到自己该跑的那份，靠的是 manifest list（多架构清单，一个"索引"指向每架构一份镜像）。构建用 `docker buildx`：

```bash
docker buildx create --name aics-multiarch --driver docker-container --use
docker buildx inspect --bootstrap            # 看 PLATFORMS 是否含 linux/arm64
docker buildx build --platform linux/amd64,linux/arm64 \
  -t <registry>/aics/user-service:1.4.0 --push .
```

两个现实提醒：① 跨架构构建在缺原生 builder 时用 QEMU 指令模拟（QEMU 是一种用软件翻译另一种 CPU 架构指令的模拟器，能跑但慢），Maven 编译阶段尤其明显——行内常见做法是 x86 与 ARM **各留一台原生构建节点**，模拟只做兜底；② 多架构一次构建不能同时用 `--load` 导回本地 docker，只能 `--push` 到仓库，所以**必须有一个支持 OCI 索引（多架构清单的标准格式）的制品仓库**。

### 3.3 基础镜像从哪来：外网不可达时的制品流程

信创生产环境通常访问不了公网镜像仓库。此时"基础镜像"是一条正式流程，不是一次 `docker pull`：

```text
需求提出（含架构、libc、JDK 版本、SBOM 依赖清单——SBOM 即 Software Bill of Materials，软件物料清单，列出镜像里所有组件与版本）
  → 外网可信源获取 / 向发行版原厂索取授权介质 → 内网导入区（隔离网闸）
  → 病毒与漏洞扫描 + 签名校验 → 入内网私有仓库（禁止匿名推送、禁止覆盖同名 tag）
  → 进入"行内基础镜像白名单"，写明版本、digest、适用架构、支持责任人
```

对应到工程要求：镜像引用**必须带 digest**（`image@sha256:...`）或带不可变版本号。本仓库现状是反例样本：`deploy/k8s/services/user-service.yaml:46` 拉的是 `:latest`，`k8s-build-push.sh:28`、`:34`、`:39` 把同一镜像同时打 `latest` 并推送，`docker-compose.yml:149` 的 minio 也是 `latest`。在生产口径里，用 `latest` 意味着"无法回答这个进程跑的是哪次构建"——投产申请直接驳回项（对照 [10 篇 §4.4](./10-银行研发运维流程与投产管控.md)）。

## 四、虚拟化与私有云：银行是"虚拟化 + 容器"双栈长期并存

### 4.1 常见形态（只列公开可确认的，最终以行内采购目录为准）

| 层次                         | 常见形态                                                        | 银行里的典型用途                               |
| ---------------------------- | --------------------------------------------------------------- | ---------------------------------------------- |
| 服务器虚拟化                 | 华为 FusionCompute、新华三 CAS、深信服 aSV、浪潮 InCloud Sphere | 承载传统集中式应用、老版本中间件、非容器化系统 |
| 超融合（计算+存储+网络一体） | 深信服 aCloud、SmartX、云轴 ZStack 等                           | 分支机构、开发测试、外围业务系统               |
| 私有云 / 云上 OS             | 基于 OpenStack 二次开发的行内私有云、华为云 Stack 等            | 统一资源交付、计量、多租户隔离                 |
| 容器平台                     | 华为 CCE 及各厂商容器云、开源自建 K8s                           | 微服务、渠道类、CI/CD 交付的运行时             |

**双栈并存是常态，不是过渡态**：虚拟化负责"存量和不敢动的东西"，容器负责"新交付的东西"。开发要知道的差别是**故障域和容量弹性完全不同**——一台虚拟化宿主机故障会同时带走几十个 VM，一个节点故障带走该节点上的 Pod 组。

### 4.2 超配策略：VM 与容器不是一套逻辑

| 维度     | 虚拟机                                      | 容器                                                                                      |
| -------- | ------------------------------------------- | ----------------------------------------------------------------------------------------- |
| CPU      | vCPU 可超配，靠调度时间片；性能抖动要看争用 | request/limit + shares；可超配但要看节点水位                                              |
| 内存     | 可轻度过量分配（有 ballooning/swap 兜底）   | **不可超配**：写满就被 OOM Kill，没有"慢一点"这个中间态                                   |
| 磁盘 IO  | 虚拟化层有队列与限速，路径固定              | 看存储类型（本地盘 vs 网络盘），尾延迟更难预测                                            |
| 时钟     | 虚拟化客户机需专门的时间同步/时钟源配置     | 共享宿主机时钟，容器内无需也不该再跑独立 NTP                                              |
| 许可计价 | 虚拟化聚合 vs 按物理核，规则复杂            | 按核计价产品在容器化后可能反而多算——见 [15 篇](./15-国产数据库选型与迁移.md) License 一节 |

对照本仓库：`deploy/k8s/services/user-service.yaml:72-77` CPU 是 `requests 100m / limits 500m`（5 倍超配，可接受），内存是 `requests 256Mi / limits 512Mi` 而堆固定 `-Xms256m -Xmx256m`——**堆等于 request、远小于 limit 的写法看似安全，但元空间、线程栈、直接内存、GC 开销全部要从剩下的 256Mi 里出**。异构机房 + cgroup 版本变化时，这类"看着没事"的配置最容易先出事。容量口径见 [容量规划与性能预算](../13-稳定性工程/02-容量规划与性能预算.md)。

### 4.3 为什么数据库和关键中间件常放裸金属

裸金属（bare metal，不装虚拟化层、直接在物理服务器上跑 OS）在银行不是复古，是工程取舍：

1. **IO 路径与尾延迟**：虚拟化多一层队列与中断开销，数据库对 P99（第 99 百分位响应时间，即最慢那 1% 请求的耗时）与 fsync 延迟敏感。
2. **NUMA 与大页**：NUMA（多颗 CPU 各自"靠近"一块本地内存、跨颗访问更慢的内存拓扑）决定了数据库要靠绑核、绑内存节点、大页来稳定性能，虚拟化客户机看到的 NUMA 拓扑由宿主决定，可控性差。
3. **故障域收敛**：一台宿主机挂掉 = 几十个实例同时不可用，违背"数据库实例分散到不同物理机"的基本容灾要求。
4. **时钟与稳定性**：虚拟化客户机时钟在高负载下漂移，直接影响前面 §2.6 的所有后果。
5. **支持边界**：原厂经常要求"裸金属或专有云形态"才受理故障工单；性能类问题在虚拟化上无法举证。

代价是资源交付慢、弹性差、运维人力重。所以行内常见结论是：**账务/核心类库用裸金属或独占节点，外围与无状态应用上容器**，而这个划分要写在投产方案里，不能口头默认。

## 五、运维与安全基线在 OS 层怎么落地

这一节和 [07 篇](./07-银行业信息安全管理规范.md) 是同一套要求的两种视角：那篇讲制度，这篇讲"在机器上敲什么"。

| 基线项             | OS 层落地动作                                                         | 怎么验证                                                                                          | 谁核查          |
| ------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | --------------- |
| 口令策略           | PAM 复杂度模块、有效期与历史重复、连续失败锁定                        | 尝试设一个弱口令，应被拒绝；查 PAM 配置                                                           | 安全 + 审计     |
| 特权账号与 sudo    | 禁止 root 直登、SSH 密钥登录、sudoers 白名单到命令、所有操作过堡垒机  | 用应用账号执行 `sudo -l`，看是否最小授权                                                          | 系统管理 + 三员 |
| 命令审计与日志外发 | `auditd` 规则 + rsyslog 远程到日志平台，本地保留受限                  | 生产机上执行一条命令，去日志平台查得到且有时间戳                                                  | 审计管理        |
| 时间同步           | chrony 指向行内统一源，偏移进监控                                     | `chronyc tracking`，看偏移与同步源                                                                | 运维 + 开发     |
| 网络与端口         | 只开必要端口、出站策略默认拒绝                                        | 从其他网段 `telnet`/`nc` 试探，未授权端口应不通                                                   | 网络 + 安全     |
| 内核补丁与 CVE     | 停自动更新，补丁走"评估→测试环境验证→变更窗口灰度→投产"，可回退旧内核 | 查 CMDB（配置管理数据库，登记每台机器的软硬件版本与归属）里的内核版本 + GRUB 默认项是否保留旧内核 | 变更管理        |
| 主机加固           | 加固脚本改权限、限 ptrace、启安全模块                                 | 在加固后的机器上试 `jstack`/arthas，看是否被禁                                                    | 系统管理        |

三个开发必须知道的连锁影响：

- **加固与杀软会改变 Java 的可观测性与启动速度**。实时扫描会在启动时逐个 stat/read 大量文件，fat jar（把全部依赖打进一个可执行 jar 的 Spring Boot 打包方式）解包与类加载明显变慢；限制 `ptrace`（一个进程附加到另一个进程做调试/取栈的内核能力）会让 `jstack`、arthas 这类工具直接不可用（表现为"线上想抓栈抓不到"）；inotify watch 上限被占满会让热更新/文件监听类组件静默失效。做法是把 jar 目录、日志目录、诊断工具加入白名单，并在变更前后各测一次启动耗时（优雅停机与启动顺序见 [优雅停机与零丢失滚动更新](../07-运维部署/06-优雅停机与零丢失滚动更新.md)）。
- **自动化在国产化环境要现场验证，不能假设可用**。Ansible 之类工具依赖目标机上的 Python 版本与 OpenSSH：老发行版可能 Python 版本不齐、新 OpenSSH 默认禁用了老算法导致原有密钥连不上、`gather_facts` 识别不到国产发行版使 playbook 的条件分支失效。结论：**自动化脚本必须在每一类 OS/架构组合上跑一次幂等性验证**（重复执行两次，结果应一致），并把结果作为投产材料。
- **补丁与内核升级是"有回退的变更"**。内核回退意味着旧内核仍在引导项里、且新内核期间产生的数据/新特性不被旧版本依赖；数据库类组件的内核参数变更（THP、大页）要与回退方案一起写，否则回退后性能回退与故障现象混在一起，无法定位。灾备与演练要求见 [高可用架构模式](../13-稳定性工程/04-高可用架构模式.md)。

## 六、升级与生命周期风险：这一节最容易出大事

| 风险形态                            | 具体表现                                                                                                    | 防线                                                                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 发行版停维（CentOS 已经演示过一次） | 无安全更新 → 等保测评与安全基线核查直接不通过，被迫仓促整体迁移                                             | 采购阶段就问清 ELS（延长支持）政策、上游血缘、社区活跃度；把"退出条件"写进合同                                                  |
| 内核小版本引发驱动/存储问题         | 升级后网卡/HBA（主机总线适配器，服务器上连存储或网络的板卡）/多路径不识别、`initramfs` 缺驱动导致机器起不来 | 严格按厂商硬件兼容列表升级；升级前重建并验证回退内核；小范围灰度                                                                |
| "同一版本、不同内核"                | 版本号一样，实际 build/补丁集不同 → 故障不可复现、原厂与集成商互相推诿                                      | 记录到内核 build 级别（CMDB 精确到 `uname -r`）；只允许从统一基线派生                                                           |
| 原厂补丁通道与 SLA 不明             | 出现高危 CVE 后等不到补丁，或补丁要排队                                                                     | 合同里写清响应时限与升级路径；自建应急缓解方案（临时封端口/降功能开关）                                                         |
| 组件版本互相牵制                    | JDK 小版本、APM Agent、native 库、发行版补丁必须同时验证，任一方单独升级都可能崩                            | 维护"已验证组合矩阵"，升级以组合为单位，不做单点升级                                                                            |
| 容器平台与 K8s 版本收敛             | 集群版本不齐 → CNI/CSI 行为差异、字段废弃导致清单失效                                                       | 版本收敛窗口 + 清单兼容性检查（先在测试集群跑通，见 [K8s 网络模型与 Service](../16-云原生与GitOps/04-K8s网络模型与Service.md)） |

**版本收敛策略**是全行统一动作，通常落成三件事：① **统一镜像基线**（一个镜像工厂定期产出 OS 基线镜像，含版本、digest、加固脚本、探针、适用架构，应用团队不许自带 OS 版本）；② **版本白名单 + 退役时间表**（每个 OS 版本有引入日和退出日，退出前强制迁移）；③ **组合矩阵公示**（OS × JDK × Agent × 中间件的已验证组合，未列出的组合需要专项评估）。开发要参与的是第二、三件——你的 JDK 与 Agent 版本必须落在矩阵里，否则投产评审要解释"为什么用了未验证组合"。

## 七、动手练习（全部可在本地完成，不依赖真实国产环境）

### 练习 1：写一份"环境体检脚本"，在 x86 与 ARM 节点各跑一次

目标：用一份脚本产出可对比的环境指纹，理解"同一镜像 ≠ 同一运行环境"。

```bash
#!/usr/bin/env bash
# env-fingerprint.sh —— 环境指纹采集；输出为单行 key=value，便于 diff
set -euo pipefail
arch=$(uname -m)                                  # x86_64 / aarch64
os=$(. /etc/os-release && echo "${PRETTY_NAME:-unknown}")
kern=$(uname -r)
libc_family=$([ -e /lib/ld-musl-"$(uname -m)"-linux-gnu.so.1 ] 2>/dev/null && echo musl || echo glibc)
glibc=$(getconf GNU_LIBC_VERSION 2>/dev/null | awk '{print $2}' || echo n/a)
openssl=$(openssl version 2>/dev/null | awk '{print $2}' || echo n/a)
cgroup=$(stat -fc %T /sys/fs/cgroup/ 2>/dev/null || echo n/a)   # cgroup2fs=v2, tmpfs=v1
swappiness=$(sysctl -n vm.swappiness 2>/dev/null || echo n/a)
thp=$(cat /sys/kernel/mm/transparent_hugepage/enabled 2>/dev/null || echo n/a)
nofile=$(ulimit -n)
clock=$({ chronyc tracking 2>/dev/null | head -3; } || echo "chrony unavailable")
echo "arch=${arch} os=${os} kernel=${kern} libc=${libc_family}/${glibc} openssl=${openssl} cgroup=${cgroup}"
echo "vm.swappiness=${swappiness} thp=${thp} nofile=${nofile} lang=${LANG:-unset}"
echo "clock=$(echo "${clock}" | tr '\n' '|')"
# JVM 视角：容器里看到的核数与堆上限（关键：是否感知 cgroup 配额）
jshell -q -s - <<'EOF' 2>/dev/null || echo "jshell n/a"
System.out.printf("availProc=%d maxHeapMB=%d%n",
  Runtime.getRuntime().availableProcessors(), Runtime.getRuntime().maxMemory()/1048576);
/exit
EOF
```

验收：本地用 `docker run --rm --platform linux/arm64 <base> sh /env-fingerprint.sh`（QEMU 模拟即可）与 amd64 各跑一次，输出 diff。**重点看三处差异**：`arch`、JVM `availProc`（同一 limit 下不同架构/内核是否给出同样的核数）、`lang`（最小镜像里 locale 是否为空）。写一份 5 行结论：哪些差异会改变应用行为，哪些不会。

### 练习 2：统一 9 个 Java 服务的运行镜像与 JDK 版本，并做多架构构建

范围：`ai-cs-{chat,gateway,knowledge,message,notify,order,product,search,user}/Dockerfile`。当前状态是"8 个 `17-jre-jammy` + 1 个 `21-jre-alpine`"，且 `ai-cs-order/Dockerfile:21` 与 product 一样没有 `JAVA_OPTS` 注入口。要求：

1. 运行阶段统一到**同一个基础镜像 + 同一个 digest**（`FROM <internal-registry>/aics/eclipse-temurin:17-jre@sha256:<digest>`），与 `pom.xml:30` 的 `java.version=17` 对齐；libc 家族统一为 glibc。
2. 统一 `ENTRYPOINT` 为可注入 JVM 参数的形式（对齐 `ai-cs-chat/Dockerfile:21` 的写法），并在清单里显式给出堆策略（`-XX:MaxRAMPercentage` 或固定堆二选一，不要两边都写）。
3. 基础镜像只能来自内网私有仓库白名单，禁止 `latest`。
4. 改造 `deploy/scripts/k8s-build-push.sh`，用 buildx 产出双架构并把 digest 回写到 K8s 清单。

```bash
#!/usr/bin/env bash
# build-multiarch.sh —— 双架构构建并推送，输出 digest 供清单回写
set -euo pipefail
REGISTRY="${REGISTRY:?内网私有仓库地址，例如 registry.aics.internal:5000}"
VERSION="${VERSION:?不可变版本号，禁止 latest}"
PLATFORMS="${PLATFORMS:-linux/amd64,linux/arm64}"
for module in ai-cs-gateway ai-cs-user ai-cs-knowledge ai-cs-chat ai-cs-search \
              ai-cs-message ai-cs-notify ai-cs-order ai-cs-product; do
  docker buildx build --builder aics-multiarch --platform "${PLATFORMS}" \
    -f "${module}/Dockerfile" -t "${REGISTRY}/aics/${module}:${VERSION}" --push . \
  | tee /tmp/build.log
  # 取 manifest list digest，写进部署清单（image: ...@sha256:...）作为唯一可信引用
  digest=$(docker buildx imagetools inspect --raw "${REGISTRY}/aics/${module}:${VERSION}" \
           | sha256sum | awk '{print "sha256:"$1}')
  printf '%s\t%s\t%s\n' "${module}" "${VERSION}" "${digest}"
done
```

制品仓库要求（写进方案，不能只写脚本）：支持 OCI manifest list / 索引查询；支持按 digest 拉取；**同名 tag 不可覆盖**（不可变）；有导入审批与扫描钩子；有跨架构 blob 去重与配额；对外只提供白名单命名空间。构建侧优化与扫描做法见 [镜像构建优化与安全扫描](../16-云原生与GitOps/06-镜像构建优化与安全扫描.md)。

### 练习 3：为本项目写一份 K8s 异构节点池调度约束清单

`deploy/k8s/` 目前没有任何调度约束（全目录 grep `nodeSelector` / `kubernetes.io/arch` / `affinity` / `tolerations` 均无结果）。请为 `deploy/k8s/services/*.yaml` 补齐下面这份模板，并写清"哪些服务只能落在 ARM 池、哪些需要独占节点、哪些可混跑"：

```yaml
spec:
  template:
    spec:
      nodeSelector:
        kubernetes.io/arch: arm64            # 架构选择：arm64 / amd64（kubelet 自动打标签）
        aics.internal/os-baseline: kylin-v10  # 自定义标签：只调度到指定 OS 基线节点
      tolerations:                            # 专用池必须打 taint，Pod 显式 toleration 才能进入
        - key: "aics.internal/dedicated"
          operator: "Equal"
          value: "middleware"
          effect: "NoSchedule"
      affinity:
        podAntiAffinity:                      # 同一服务的副本分散到不同节点/不同机架（故障域收敛）
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels:
                    app: user-service
```

交付物三件：① 一张"服务 × 架构 × OS 基线 × 是否需要独占节点"的矩阵；② 节点池标签与 taint 的命名规范（含"谁有权打标签"）；③ 一条检查规则：清单里出现 `:latest` 或没有 `kubernetes.io/arch` 约束的 Deployment 不予通过投产评审。K8s 基础见 [Kubernetes 入门](../07-运维部署/02-Kubernetes入门.md)，资源与弹性见 [K8s 资源治理与弹性伸缩](../16-云原生与GitOps/02-K8s资源治理与弹性伸缩.md)。

## 八、初学者常见误区

| 误区                                   | 真相                                                                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| "都是 Linux，行为肯定一样"             | 命令、目录、工具链一样；**默认值不一样**（内核参数、locale、cgroup 版本、OpenSSL/glibc 版本），差异全在默认值和补丁集里 |
| "换 OS 是运维的事，跟开发没关系"       | JDK 与 native 依赖、字符集、时钟、镜像架构、JVM 容器感知这些都要开发改代码或改构建，运维改不了你的 Dockerfile           |
| "我的应用是纯 Java，不涉及 C 库"       | JDK 本身、APM Agent、JNI 加解密、压缩库、数据库本地客户端全是 native；glibc/OpenSSL 一变就加载失败                      |
| "在信创环境继续用 `latest` 镜像，方便" | `latest` 可被覆盖，等于放弃了"这个进程跑的是哪次构建"的可追溯性——投产评审的驳回项                                       |
| "基础镜像换个架构重跑一遍就行"         | 要同时确认 libc 家族、glibc/OpenSSL 版本、是否有架构专属的 `.so`、探针与 CNI/CSI 是否提供该架构构建                     |
| "探针能装上就说明兼容"                 | 装上 ≠ 采得对：cgroup v2 下老探针会采空或按宿主机总量上报；必须在目标环境实测指标数值可信                               |
| "把内核版本当 OS 版本管理"             | 同一发行版版本号可能对应多个内核 build；基线与 CMDB 必须记到 `uname -r`，否则故障无法复现、无法定责                     |
| "时钟同步有 NTP 就够了，飘一点无所谓"  | 飘几十毫秒就足以让日切归属、对账文件匹配、雪花 ID、证书有效期判断出错，而且现场看不出来                                 |
| "OS 升级 = 换镜像，应用不用回归"       | libc/编码/cgroup 任一变化都会改变 JVM 行为；至少要重跑性能基线与字符集用例，并留对比数据                                |

## 九、本篇速查：一条命令体检清单

| 要看什么      | 命令                                                                      | 期望/异常信号                              |
| ------------- | ------------------------------------------------------------------------- | ------------------------------------------ |
| 发行版与版本  | `cat /etc/os-release`                                                     | 是否在行内白名单内                         |
| 内核          | `uname -r`、`rpm -qa kernel`                                              | 是否等于基线记录的 build（不是只看版本号） |
| 架构          | `uname -m`、`lscpu`                                                       | aarch64 / x86_64，决定镜像平台             |
| glibc         | `getconf GNU_LIBC_VERSION`、`readelf -V <so>`                             | 依赖版本不得高于运行时                     |
| OpenSSL       | `openssl version`、`ls /usr/lib64/libssl*`                                | 大版本与 native 依赖 soname 是否匹配       |
| libc 家族     | `ldd /bin/ls`                                                             | 出现 `ld-musl` 说明是 musl 环境            |
| cgroup 版本   | `stat -fc %T /sys/fs/cgroup/`                                             | `cgroup2fs`=v2、`tmpfs`=v1                 |
| fd 上限       | `ulimit -n`、`systemctl show <svc> -p LimitNOFILE`                        | 只看 `ulimit` 会漏掉服务级设置             |
| 内核参数      | `sysctl vm.swappiness net.core.somaxconn`、THP 文件                       | 与基线 diff 后逐项有结论                   |
| 时钟          | `chronyc tracking`、`timedatectl`                                         | 偏移在阈值内、源唯一且合法                 |
| locale / 编码 | `locale`、`java -XshowSettings:properties -version 2>&1 \| grep encoding` | JDK 17 下 `file.encoding` 不得落到 ASCII   |
| JVM 容器感知  | `jcmd <pid> VM.flags`、`VM.system_properties`                             | 堆与可用核数是否符合 limits                |
