## 一、先建立坐标系：三条血统、四类形态

选型讨论之所以经常鸡同鸭讲，是因为大家把"国产数据库"当成一个品类。它至少是四类完全不同的东西，**风险、改造量、面试问法都不一样**。

| 类别                                                                          | 代表产品（名称可核实）                                                                                                                                                             | 血统与性质（公开资料）                                                                                               | 典型定位                                                       |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 集中式 / Oracle 语法替代路线                                                  | 达梦 DM8；人大金仓 KingbaseES；瀚高 HighGo DB                                                                                                                                      | 达梦为武汉达梦（公开资料显示其控股股东在中国电子体系内），自研路线；金仓、瀚高均为 PostgreSQL 系商业化发行           | 替换单体 Oracle/DB2 库；主备或共享集群；改造量集中在方言与函数 |
| openGauss 血统                                                                | GaussDB（华为商业版）/ openGauss（华为发起、现由开放原子开源基金会托管的开源版）；商用发行如 Vastbase（海量数据）、MogDB（恩墨）、GBase 8c（南大通用，公开资料显示基于 openGauss） | openGauss 官方说明其内核在 PostgreSQL 社区版基础上开发，并叠加 Oracle 兼容能力；商业发行版在其上做集成与支持         | 集中式为主，部分形态支持分布式；信创目录里出现频率高           |
| 原生分布式（Share-Nothing：每个节点有独立的存储与计算，靠网络协同做水平扩展） | OceanBase（蚂蚁集团自研，MySQL 兼容模式 + Oracle 兼容模式）；TiDB（PingCAP，MySQL 兼容，开源）；TDSQL（腾讯，含 MySQL 语法与 PostgreSQL 语法两条产品线）；GoldenDB（中兴通讯）     | 内核自研为主，对外做 MySQL/PostgreSQL 生态兼容（TDSQL 的 MySQL 形态以 MySQL 内核配合分布式调度组件，以厂商资料为准） | 大容量高并发联机交易、需要在线水平扩展与多副本容灾的系统       |
| 分析型 / 专用负载                                                             | GBase 8a（南大通用，列式 OLAP 路线，OLAP 即 Online Analytical Processing，面向大范围扫描与聚合的分析型负载）等                                                                     | 与交易型产品不是同一条技术路线                                                                                       | 报表、经营分析、监管报送数据落地；**不承载联机交易写入**       |

```text
                    语法与行为"向谁看齐"
   Oracle / DB2 ◄───────────────┐        PostgreSQL 社区版 ◄──── MySQL 社区版
                                │              │                    │
      自研路线                  │              │                    │
   ┌──────────────┐             │      ┌───────┴────────┐    ┌──────┴───────────┐
   │ 达梦 DM8     │─────────────┤      │ KingbaseES     │    │ TiDB             │
   │（对标 Oracle）│             │      │ HighGo         │    │ OceanBase-MySQL  │
   └──────────────┘             │      │ openGauss ─────┼──► │ GoldenDB         │
                                │      └────────────────┘    │ TDSQL            │
        ┌───────────────────────┴───────────────┐            └──────────────────┘
        │  兼容模式：语法 + 函数包 + 类型 + 行为开关 │                   ▲
        └───────────────────────────────────────┘                   │
              ▲                                                     │
     GaussDB / openGauss 商用发行（Vastbase、MogDB、GBase 8c）───────┘
              （同一份开源内核，多家厂商各自集成、加固、给支持——差异在支持与认证，不在 SQL 语义）
```

两个容易被忽略的结论：

1. **"开源版"与"商业版"的差别不是"功能阉割"这么粗**。以 openGauss / GaussDB 为例：一个可自取源码（木兰宽松许可证）但没有 SLA、没有硬件认证矩阵、没有原厂兜底；另一个绑定云与专有云形态、有支持合同，但有退出成本。银行采购走的是后者，**开发者要清楚自己测试环境用的可能是前者，两者行为不完全一致**。
2. **一个厂商往往同时有多条产品线**（集中式 + 分布式 + 分析型）。所以选型结论必须写成"**产品 + 形态 + 版本 + 兼容模式参数**"四要素，只写"我们用某厂的库"在评审里等于没写。

## 二、"兼容模式"是什么，为什么"号称兼容 Oracle"和"你的 SQL 真能跑"是两件事

**兼容模式（compatibility mode）就是一组数据库参数/开关**：打开后，解析器额外接受某些写法（`(+)`、`DUAL`、`MERGE`）、补上一批函数与系统包（`NVL`、`DECODE`、`DBMS_OUTPUT`）、调整类型映射与长度语义、并切换若干行为（大小写折叠、空串是否等于 NULL、默认排序规则）。它通常在建库/建实例时指定，**建完之后改不动**，这本身就是选型阶段必须锁定的决策。

关键在于它只覆盖到三层里的第一层：

| 层次               | 兼容模式能给你什么                     | 它给不了你什么                                     | 怎么验                                |
| ------------------ | -------------------------------------- | -------------------------------------------------- | ------------------------------------- |
| ① 语法层           | 老写法能解析、能执行、不报错           | 执行结果对不对、边界条件一致不一致                 | 自动评估工具跑 SQL 语料               |
| ② 语义层（行为层） | 部分开关对齐（长度语义、大小写、NULL） | 隔离级别、锁范围、快照粒度、错误码这些内核行为     | 并发用例 + 边界值用例，逐条断言       |
| ③ 计划层（性能层） | 无                                     | 优化器不同 → 同一个 SQL 走不同索引、不同 join 顺序 | 生产真实 SQL 指纹回放 + 执行计划 diff |

所以"号称兼容 Oracle 99%"（这类百分比**不可作为决策依据**，各家统计口径不同）真正该翻译成：**我能少改多少条 SQL**。而成本大头永远在第 ② ③ 层——就是下面这张表。

### 兼容 ≠ 等价的 15 个具体差异（迁移事故高发区）

| 项                            | Oracle 常见行为                         | MySQL 常见行为                   | PostgreSQL / openGauss 系常见行为             | 迁移后果（银行视角）                                                                 |
| ----------------------------- | --------------------------------------- | -------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------ |
| 空字符串                      | `''` 即 `NULL`                          | `''` 与 `NULL` 不同              | `''` 与 `NULL` 不同                           | `col IS NULL` 判断、`NOT NULL` 约束、`NVL` 兜底全变；摘要字段"看起来为空但不为 NULL" |
| 标识符大小写                  | 未加引号折叠为大写                      | 表名按平台、列名不敏感           | 未加引号折叠为小写                            | 迁移后报"表/列不存在"，最常见的一类首日故障                                          |
| `NULL` 在排序中的位置         | 升序默认在最后                          | 升序默认在最前                   | 升序默认在最前（`NULLS FIRST/LAST` 可显式）   | 分页第一页内容变了；按"最新时间"取记录时漏/多一条                                    |
| `DATE` 是否含时间             | 含时分秒                                | `DATE` 不含，`DATETIME` 含       | `date` 不含，`timestamp` 含                   | 日切边界比较错、时间戳被截断到日                                                     |
| `VARCHAR(n)` 的 n             | 可按字节或按字符（受长度语义参数控制）  | 按字符                           | 按字符                                        | 中文字段在新库"能存但宽度含义变了"，或老库超限数据迁移失败                           |
| 默认隔离级别                  | 读已提交（语句级一致性读）              | 可重复读（事务级快照，含间隙锁） | 读已提交（快照，一般无间隙锁）                | **最容易造成"迁移后偶发重复/汇总对不上"的一项**，见 §六                              |
| 分页写法                      | `ROWNUM` / `FETCH FIRST`                | `LIMIT n OFFSET m`               | `LIMIT m OFFSET n` / `FETCH FIRST`            | ORM 与手写 SQL 全要重生成；见 §5.10                                                  |
| 唯一索引与 `NULL`             | 全 NULL 行不受唯一约束限制              | 唯一索引允许多行 `NULL`          | 默认也允许多行 `NULL`                         | **幂等表的防重唯一键可能失效**（09 篇"DB 权威"这条腿会漏）                           |
| 隐式类型转换                  | 依赖上下文，规则细                      | 宽松（字符串与数字互转）         | 严格（多数需要显式 `::`/`CAST`）              | 迁移到严格一方出现"操作符不存在/类型不匹配"批量报错                                  |
| 错误码与 `SQLState`           | `ORA-xxxxx`                             | MySQL 数字错误码                 | SQLState 为主，厂商另有自有码                 | 应用里"按错误码分支"的代码（重复键、锁等待、连接断）全部要重映射                     |
| 序列取值语义                  | `seq.NEXTVAL` / `CURRVAL`（会话内）     | 无原生序列（自增列替代）         | `nextval()` / `currval()` / `SELECT seq`      | 主键生成、批次号生成、`trigger` 组合都要重写                                         |
| 触发器行引用                  | `:NEW` / `:OLD`                         | `NEW` / `OLD`                    | `NEW` / `OLD`（PL/pgSQL 变量语义不同）        | 触发器与审计字段填充逻辑逐个改写、逐个测                                             |
| `ON UPDATE CURRENT_TIMESTAMP` | 无（靠 trigger）                        | 列级自动更新                     | 无（靠 trigger 或默认值）                     | "更新时间"静默不再变化——最难被发现的一类语义丢失                                     |
| hint / 优化器依赖             | `/*+ */` 系列 + 计划基线                | `STRAIGHT_JOIN` 等               | 各有扩展（如 GUC/计划绑定能力，支持度需实测） | 靠 hint 保命的高频 SQL 在新库上计划漂移，压测过、生产炸                              |
| 统计信息策略                  | `DBMS_STATS` / `ANALYZE` + 自动收集作业 | `ANALYZE TABLE` + 直方图         | `ANALYZE` / 自动清理与采样，参数体系不同      | 迁移首日统计信息缺失 → 全库计划劣化，必须"先收集再放量"                              |

> 用法建议：这张表不是拿来背的，是**拿你手上的 SQL 逐行去套**。每套中一项，就在迁移评估报告里记一条"依赖项 + 出现位置 + 改造动作 + 责任人"。这份报告就是评审与举证的取证材料。

| 团队技能               | 谁运维？DBA 会不会、开发会不会看新执行计划？原厂培训与驻场？                                                                                          | 全行只有厂商工程师会用                          | 培训计划 + 内部手册（能自己完成一次扩容/切换）                            |
| License 计价方式       | 按核、按颗 CPU、按实例还是按容量？ARM 多核怎么算？虚拟化环境怎么算？                                                                                  | 报价按 x86 8 核历史价，未换算到目标机型核数     | 计价口径书面确认 + 目标机型的实际计费演示                                 |
| 维保与原厂支持         | 故障分级响应时限、补丁通道、驻场可得性、夜间窗口能否到人                                                                                              | 只有销售热线，无支持 SLA 条文                   | 合同支持条款 + 一次真实工单的闭环记录                                     |
| 退出成本与数据可迁出性 | 能不能把数据和结构无损导回通用格式？私有类型/函数用了多少？                                                                                           | 用了大量厂商专属能力，换不回                    | 迁出演练（导出 + 在第三方库重建 + 校验）                                  |

## 四、Oracle 依赖清单：迁移工作量真正的来源

**改造量的大头从来不是"表结构"，是"库里的资产"和"代码里的写法"**。先按下面这张表清点，再谈工期。定位手段两类：静态（代码 grep + 视图/存储过程 DDL 导出）与动态（生产游标缓存/SQL 审计采指纹，按"执行次数 × 单次耗时"排序）。

| 依赖项                                     | 目标库对应能力                                                 | 改造方式                                                                                                                           | 风险                                                   |
| ------------------------------------------ | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `ROWNUM`（取前 N 行、分页）                | 多数目标库有 `LIMIT`/`FETCH FIRST`，部分提供 ROWNUM 兼容       | 统一改写为标准分页或交给 ORM 方言生成                                                                                              | "先取号再排序"的语义差异 → 分页漏行/重复行             |
| `(+)` 外连接写法                           | ANSI `LEFT JOIN` 通用支持                                      | 全量替换为 ANSI 写法                                                                                                               | 与 `OR` 组合时优先级不同，静默改变结果集               |
| `CONNECT BY` 层次查询                      | 标准 `WITH RECURSIVE`；部分库保留 `CONNECT BY`                 | 改写递归 CTE，或应用层展开                                                                                                         | 机构树/科目树/现金池层级这类查询性能与终止条件都要重测 |
| `MERGE INTO`                               | 多数支持（语法细节不同，如是否需 `USING`/`WHEN MATCHED` 变体） | 逐个核对子句；必要时拆成 `UPDATE` + 不存在再 `INSERT`                                                                              | 拆分后不再是原子操作，需要事务或唯一键兜底             |
| `DUAL` 虚拟表                              | 多数支持或可省略                                               | 保留即可；部分库要求去掉                                                                                                           | 影响小，但 ORM 拼接语句会踩                            |
| 序列 + `trigger` 生成主键                  | 序列能力存在（语法不同），或有身份列/应用发号                  | 优先改应用侧发号（与 [分布式 ID 规范](../03-数据库与ORM/04-分布式ID规范.md) 一致），退掉 trigger                                   | 主键值域、空洞、批量取号的 `cache` 大小差异            |
| `NVL` / `DECODE` / `TO_CHAR` / `TO_DATE`   | 通常有同名或等价函数（`IFNULL`/`COALESCE`/`CASE`）             | 用兼容模式或函数映射；格式化模型逐个核                                                                                             | 日期格式模型、数字千分位、时区行为细节不一致           |
| `DBMS_` 系列包（输出/锁/作业/统计）        | 部分有兼容包；作业能力通常不完整                               | `DBMS_JOB` 上收到调度平台（如 XXL-Job，见 [XXL-Job 分布式调度](../07-运维部署/05-XXL-Job分布式调度.md)）；`DBMS_LOCK` 改应用层方案 | 库内作业与行内调度"两张皮"，日终顺序失控是重大隐患     |
| `ANALYZE` / 统计信息策略                   | 各有 `ANALYZE`/自动收集，参数体系不同                          | 迁移后立即收集；把收集窗口写进日终流程                                                                                             | 首日无统计 → 全量计划劣化（典型"上线当晚崩"）          |
| 表空间、数据文件与自动扩展                 | 表空间概念存在但实现不同；扩展与配额机制各异                   | 重新做容量规划与落盘策略；不要在目标库硬套原文件布局                                                                               | 自动扩展打满磁盘、日志把数据盘写满                     |
| `ROWID` / 依赖物理定位的写法               | 语义不等价                                                     | 一律改为业务主键定位                                                                                                               | 老代码里"用 ROWID 加速"的更新直接不可用                |
| hint 与计划固化                            | 支持度与写法各异                                               | 建"hint 清单"，逐条给等价替代或删除                                                                                                | 无 hint 后走错索引，靠人肉回滚                         |
| PL/SQL 存储过程与自治事务                  | 各家有过程语言，但自治事务/包/异常体系差异大                   | 能上收到应用的上收；留下的逐个重写 + 单测                                                                                          | 业务规则藏在库里，改错一处影响全行——**必须双人复核**   |
| 分区表与索引组织表（IOT）                  | 分区普遍支持；IOT 类结构需找等价物（如索引组织表/聚簇表）      | 分区键与粒度重做设计，不照搬                                                                                                       | 分区键选错 → 热点与倾斜（见 §九）                      |
| 字符集与 `VARCHAR` 字节/字符语义、排序规则 | 目标库字符集与 collation 体系不同                              | 建库时锁定字符集/排序规则；中文排序需求专项验证                                                                                    | 迁移后"同名客户排到别处"、模糊查询命中集变化           |

## 五、MySQL → 原生分布式库的真实差异（用本仓库做对照基准）

本仓库的现有技术栈就是"评估基准"：MySQL 8.0（`docker-compose.yml:9`）、MyBatis-Plus 3.5.6（`pom.xml:45`）、ShardingSphere-JDBC 5.5.0（`pom.xml:46`、坐标 `pom.xml:130-132`）、`mysql-connector-j` 8.0.33（`pom.xml:155-157`）、Seata 1.7.1 AT 模式（`ai-cs-order/src/main/resources/application.yml:48-49`）。**假设要把它换成原生分布式库**，逐条看职责怎么重划。

### 5.1 自增主键与全局唯一 ID

分布式库里的 `AUTO_INCREMENT` 通常是"全局递增但不连续、不保证逐行递增、且按批次预分配"（每个节点/会话预取一段，故障重启会跳号）。本仓库订单侧实体用的是最朴素的库内自增：

```java
// ai-cs-order/src/main/java/com/aics/order/entity/Order.java:16
@TableId(type = IdType.AUTO)
```

清点结果：`deploy/mysql/*.sql` 里 `AUTO_INCREMENT` 出现 56 处、建表语句 110 处（脚本级 grep 计数，多个初始化脚本对同一张表有重复定义，所以这两个数字是"写法出现次数"，不是唯一表数量——正式摸底要用 §十 的 `information_schema` 查询在真实库上跑）。要问的三个问题：① **有没有代码依赖"自增值连续/单调/按插入顺序"**（分页游标 `WHERE id > ?`、对账按 id 区间切片、日志排序）；② `IdType.AUTO` 意味着"插入后回读 DB 生成的主键"，目标库驱动的 `getGeneratedKeys` 行为与批量插入（`rewriteBatchedStatements`）是否支持；③ 业务号与主键是否分离（银行铁律：**主键可以是技术键，业务流水号必须自己可控**）。规范结论已在 [分布式 ID 规范](../03-数据库与ORM/04-分布式ID规范.md)：新表一律 `ASSIGN_ID`，换库时这条规范的价值才真正显出来——应用侧发号不受目标库实现牵制。

### 5.2 分片层与事务层的职责重划

```text
换库前（本仓库现状）                     换库后（假设迁到原生分布式库）
────────────────────────────            ─────────────────────────────
应用 SQL                                应用 SQL
  └─ ShardingSphere-JDBC 5.5.0            └─ （分片路由能力被库内核接管 → 中间件要不要留？）
       2 库 × 4 表 路由（user）                保留价值：数据源路由/灰度切流/影子库/脱敏/读写分离
       └─ HikariCP + mysql-connector            撤销价值：多一层 SQL 改写就多一层方言与语义风险
            └─ MySQL（单机语义）              └─ 驱动换成目标库 JDBC（连接池仍可留 Hikari）
Seata AT（跨服务事务，前后镜像 undo_log）      Seata AT 或上收到库内核分布式事务
       └─ 每个分支库要有 undo_log 表            └─ undo 解析器/方言支持需按版本实测；镜像字段类型要映射
```

评估要点（这就是练习 2 要写的报告骨架）：**不要两层分布式语义叠着上生产**。库内核已经保证"一条 SQL 覆盖多分片时原子"，那 ShardingSphere 的分片路由就可以撤；而"跨服务、跨库、含外部调用"的事务仍需业务层协调（Seata，或 TCC——Try-Confirm-Cancel，把业务操作拆成预占、确认、取消三步的补偿型事务——或消息最终一致；账务场景的取舍见 [09 篇第九节](./09-金融级一致性与对账实战.md)）。中间件与库内核的取舍必须写成"哪层负责什么"的一张表，投产评审要问的就是这张表。

顺带一个真实迁移阻塞点：`undo_log` 的 `rollback_info` 是 `LONGBLOB`（`deploy/mysql/seata-undo-log.sql:14-20`），大字段在目标库的类型映射、分片限制与网络传输都要实测——**这类"框架自带的表"最容易在评估里漏掉**，因为它不在业务 DDL 清单里。

### 5.3 跨分片 JOIN、`ORDER BY` 与深翻页

分片/分布式后，"一条 SQL 里 join 两张大表"要拆成"广播小表、按分片键对齐、或在应用层组装"。深翻页（`LIMIT 100000, 20`）在多分片上是"每个分片各取 100020 行再归并"，代价指数级放大。迁移后必须重做的三件事：把 `ORDER BY` 的非确定列补齐（否则翻页出现重复/漏行——这与 §二 的 NULL 排序位置差异叠加）、给列表页改成游标分页、把报表类大查询从交易库剥离。SQL 层的通用调优与执行计划读法见 [SQL 调优与执行计划](../12-性能工程/05-SQL调优与执行计划.md)。

### 5.4 全局一致性读与"读己之写"

多数派 + 多副本带来一个新问题：**你从副本读，可能读到旧数据**。原生分布式库通常提供"全局一致性读"（靠全局时间戳服务 TSO/GTS 或事务快照决定"读到哪一刻"），代价是每次取时间戳要走一次网络往返，跨地域时尤其明显。另一个必须单独确认的是"读己之写"（read-your-writes：自己刚提交的数据，随后一定能读到，哪怕这次读落在副本上——客户"充值完立刻查余额还是旧值"就是它没做好）。落到银行结论上（对应 [09 篇](./09-金融级一致性与对账实战.md) 的"余额不能读从库"）：

| 读场景            | 要求                                         | 换库后要确认的能力                                    |
| ----------------- | -------------------------------------------- | ----------------------------------------------------- |
| 余额/可用额度校验 | 必须读到已提交的最新值                       | 强一致读（leader 读或全局快照读），且要有超时降级策略 |
| 客户查询流水列表  | 容忍毫秒级滞后，但**自己刚做的操作要能看到** | "读己之写"（session consistency）开关是否提供         |
| 日终汇总/报表     | 与联机写隔离                                 | 是否支持只读副本/读独立节点，是否会拖慢主链路         |
| 对账取数          | 取数时点必须明确可复现                       | 快照/一致性视图能力，或按全局时间戳固定取数区间       |

### 5.5 `SELECT ... FOR UPDATE` 与行锁语义

这是最容易被"兼容模式"糊过去的一类差异，因为它**功能上都能跑，行为上不同**：锁范围（是否有间隙锁防幻读）、锁等待与超时参数、`NOWAIT` / `SKIP LOCKED` 是否支持（跑批"抢任务"模式依赖它）、锁是否在跨节点事务里放大持锁时间、死锁检测与报错码。对照 [02 篇 §8](./02-核心系统与会计账务引擎.md) 的热点账户结论：**单行 X 锁串行是物理限制，换成分布式库不会让它消失，反而可能把持锁时间拉长（多了一跳网络与一次共识）**。所以"热点账户四解法"在新库上要重新压测，不是照搬收益数字。锁机制基础见 [MySQL 锁机制与主从复制读写分离](../03-数据库与ORM/05-MySQL锁机制与主从复制读写分离.md)。

### 5.6 DDL 与在线变更

分布式库的 DDL 需要跨节点做 schema 版本协商，"加一列"背后可能是全表数据重分布。评估要问三件事：**是否在线、是否阻塞写、能否暂停与续跑**，并且要用**生产等量数据**演练一次（不是 DDL 语法能过就算）。变更窗口与回退方案要按 [10 篇 §5](./10-银行研发运维流程与投产管控.md) 的投产口径写。

### 5.7 binlog 依赖：Canal 链路在目标库上换成什么

本仓库的商品索引同步依赖 MySQL binlog + Canal（权限见 `deploy/mysql/canal-init.sql:2-3` 的 `REPLICATION SLAVE`），消费侧幂等与对账设计见 [Canal CDC 商品索引同步](../04-中间件/11-CanalCDC商品索引同步.md)。换库后"日志订阅"这件事要重新回答：目标库提供什么（各家的 CDC/同步工具、逻辑解码、或厂商自带的数据同步产品），**下游语义是否等价**（是否给全镜像前后值、DDL 事件怎么表达、事务边界是否完整、顺序是否有保证、断点续传位点存哪）。链路通用原理见 [CDC 与实时同步链路](../14-数据工程与OLAP/04-CDC与实时同步链路.md)。底线结论：**同步链路换向 = 对账必须重做一轮**（源端和目标端同时变了，历史校验规则不再可比）。

### 5.8 字符集、JSON、全文索引与"隐式列行为"

同一份建表脚本里的三处 MySQL 专属写法，就是三类典型迁移障碍：

| 写法                                                           | 位置                        | 迁移障碍                                                     | 处置                                                                                                                  |
| -------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `utf8mb4` + `utf8mb4_unicode_ci` 排序规则                      | `deploy/mysql/init.sql:7`   | 目标库字符集/collation 体系不同，中文排序与等值判断会变      | 建库时锁定；对"按名称排序/模糊匹配"做结果比对                                                                         |
| `metadata JSON` 列与 JSON 函数                                 | `deploy/mysql/init.sql:312` | JSON 类型与函数（`JSON_EXTRACT` vs `->>`、jsonb 算子）差异大 | 抽成少数几个查询方法统一改写，别散落                                                                                  |
| `FULLTEXT ... WITH PARSER ngram`                               | `deploy/mysql/init.sql:258` | ngram 分词器与全文索引语法基本不可移植                       | 全文检索下沉到搜索引擎（见 [Elasticsearch 搜索引擎](../04-中间件/03-Elasticsearch搜索引擎.md)），交易库不承担模糊检索 |
| `ON UPDATE CURRENT_TIMESTAMP`（`deploy/mysql/*.sql` 共 56 处） | 多数表                      | 目标库无此列属性 → `update_time` 静默不再更新                | 收敛到 ORM 自动填充（本仓库已有先例：`KnowledgeDocument.java:57`、`:61` 的 `FieldFill`）                              |

### 5.9 驱动与连接池

`mysql-connector-j` 是 Maven 中央仓库公开依赖（`pom.xml:155-157`），而**国产库的 JDBC 驱动常常不在中央仓库**，要走内网私服 + 依赖白名单（对照 [10 篇 §4.3](./10-银行研发运维流程与投产管控.md)）。要实测的清单：驱动与 JDK 17 的模块化兼容、与 HikariCP 的配合（`sharding-user.yaml:29` 用的就是 `HikariDataSource`）、连接有效性检测语句（不同库的"探活 SQL"支持不同，配错会导致连接池整体失效）、超时参数名与语义、批量执行与 `getGeneratedKeys`、字符集与时区参数、驱动版本与库版本的配套关系（**必须写进制品基线，随库升级一起升**）。提醒一句：驱动是 native 依赖较重的组件之一，"驱动 + JDK + 基础镜像 + OS 基线"要作为**一组**在目标环境上验证，不能只在开发机上验过——组合矩阵的方法见 [国产操作系统与虚拟化容器适配](./14-国产操作系统与虚拟化容器适配.md) §六。

### 5.10 ORM 与分页方言：本仓库已经埋好的雷

```java
// ai-cs-order/src/main/java/com/aics/order/config/OrderConfig.java:27
interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
```

四个服务都把分页方言**硬编码成 `DbType.MYSQL`**（另外三处：`ai-cs-knowledge/.../MybatisPlusConfig.java:38`、`ai-cs-message/.../MybatisPlusConfig.java:34`、`ai-cs-product/.../MybatisPlusConfig.java:22`）。MyBatis-Plus 的分页插件是**按方言改写 SQL 字符串**的，目标库不是 MySQL 时不改这里就等价于"分页语句按 MySQL 语法发给一个不懂 MySQL 语法的库"。迁移改造要点：方言从配置注入（一个环境变量切换）、主键策略随方言一起评估（`AUTO` → `ASSIGN_ID`/序列）、以及若继续用 ShardingSphere，需要确认它对目标库的方言实现是否可用。ORM 侧基础见 [MyBatisPlus 实战](../03-数据库与ORM/02-MyBatisPlus实战.md)，分片现状见 [ShardingSphere 用户表分库分表实战](../03-数据库与ORM/03-ShardingSphere用户表分库分表实战.md)。

## 六、换库之后，09 篇的结论还成立吗

这是本篇真正的"深化"部分：**09 篇讲的机制不是随库走的常量，其中一半的成立前提就是 InnoDB 的行为**。

| 09 篇的结论                                           | 换库后是否仍成立                                             | 必须重做的验证                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| 幂等以"业务唯一键 + DB 唯一索引"为最终防线            | **成立且更要紧**，但要确认唯一索引对 `NULL` 的行为           | 构造"幂等键某列为 NULL"的重复请求，确认是否被挡住                    |
| "Redis 加速挡 + DB 权威"分层                          | 成立（Redis 不参与换库）                                     | Redis 挡掉的那部分与 DB 兜底那部分的比例要重新观测（新库耗时变了）   |
| 余额与发生额必须在同一条 `UPDATE` 内完成（02 篇铁律） | **更严格**：跨节点拆成两条语句就可能被并发插入读到中间态     | 用并发脚本压同账户，核对 `Σ发生额 = 期末-期初`                       |
| 记账走主库、余额查询不走从库                          | 语义变成"读哪个副本 + 什么一致性等级"（§5.4）                | 打开副本读，验证"刚写完立刻读"是否能看到自己的写                     |
| 对账以流水为准、差异分类后定责                        | 成立；但**流水时间戳来源**要重看                             | 全局时间戳（库给）与物理时间（应用给）二选一，混用会让按时间切片失败 |
| 超时是未知态，不是失败                                | 成立；新增一种可能：跨节点提交阶段超时，状态在多数派上"半途" | 注入提交阶段网络抖动，确认恢复后是否有唯一终态                       |
| 用 `SELECT ... FOR UPDATE` 做"取任务"式并发控制       | 支持度与语义都要重新确认（§5.5）                             | 多实例抢同一批任务，确认不重不漏、且 `SKIP LOCKED` 不可用时另有替代  |

**最值得记住的一条**：从 MySQL 默认的 REPEATABLE READ（事务级快照 + 间隙锁）迁到 RC（语句级快照、一般无间隙锁）后，"同一事务里两次读到的数据一致"这一**默认行为消失了**。老代码里凡是依赖"先查再改，反正事务里不会再变"的地方，都会变成偶发的资损或重复记账风险；反过来，间隙锁消失会**减少**死锁但**增加**幻读型重复插入。这不是理论差异，是两类可写成用例的断言。

## 七、迁移方法论：八阶段与每阶段交付物

| #   | 阶段               | 做什么                                                                            | 交付物                                                                         | 银行场景特有的要求                                                     |
| --- | ------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 1   | 摸底与资产盘点     | 对象清点（表/视图/索引/约束/序列/过程/触发器/作业）、**SQL 指纹采集**与调用量排序 | 资产清单 + Top SQL 榜 + 工作量估算表                                           | 估算要有依据可查（评审会看"你怎么算出来的"）；采集脚本只读取、留痕     |
| 2   | 兼容性评估         | 自动评估工具跑全量 SQL 与 DDL + 人工兜底复核不兼容项                              | 评估报告（逐条：不兼容项/位置/改造动作/责任人/是否阻塞）                       | **报告就是取证材料**，须双方签字留痕；不能只交"兼容性百分比"           |
| 3   | 结构与数据类型映射 | 类型映射表、精度与标度、字符集/排序规则、分区与索引重设计                         | 映射表 + 新 DDL + 与源库的 diff 说明                                           | DDL 必须走 SQL 审核 + DBA 代操作；精度类改动直接影响金额，双人复核     |

| 5   | SQL 与应用改造     | 方言、函数、分页、事务、ORM 配置、错误码映射、hint 清理                           | 改造清单 + 代码评审记录 + 回归用例通过率                                       | 改造与功能需求分开提版本，禁止"顺手改"；每处行为变化写进变更说明       |
| 6   | 性能测试           | **用生产真实 SQL 指纹回放**（含并发比例、数据量、参数分布），做执行计划 diff      | 压测报告（TPS、P99＝第 99 百分位响应时间、资源水位、劣化清单）+ 计划 diff 记录 | 数据量用等量或按比例放大到等量；结论要能被复现（脚本与数据版本留存）   |
| 7   | 双轨并行与灰度     | 先读新库（影子读）→ 部分写 → 按流量/机构/客户维度逐步切                           | 切流方案 + 双轨对账日报 + 放量决策记录                                         | 读写比例与放量节奏需审批；**每日对账不平即停止放量**（见 §八）         |
| 8   | 回退方案与切换决策 | 定义回退触发条件、回退窗口、数据回流路径与回流校验                                | 回退方案（可执行清单 + 决策树 + 演练记录）                                     | 回退必须**真演过**；回退也要留痕并出复盘报告                           |

## 八、数据一致性校验：把对账手法用在迁移上

迁移校验不是"跑一次 count 看一样不一样"，而是一条可重跑的校验流水线。方法论与差错台账的通用形态见 [数据质量与对账](../14-数据工程与OLAP/08-数据质量与对账.md)，本篇只补"跨异构库校验"的四层做法：

| 层次         | 比什么                                                       | 时机与频率          | 能抓什么 / 抓不到什么                         |
| ------------ | ------------------------------------------------------------ | ------------------- | --------------------------------------------- |
| ① 行数对总账 | 每表 `COUNT(*)`（按同一过滤口径，如按时间片或主键段）        | 全量后 + 每轮增量后 | 抓漏搬/多搬；抓不到"值错了"                   |
| ② 聚合值     | `SUM(金额)`、`COUNT(DISTINCT 状态)`、`MAX(更新时间)`、空值率 | 与 ① 同批           | 抓金额/状态漂移；抓不到行内字段错位           |
| ③ 分片校验和 | 按主键区间分片，每片算校验和（分段哈希）                     | 每轮增量收敛后      | 把差异定位到某个主键段，成本远低于逐行        |
| ④ 抽样深比对 | 抽中的行逐列比（含精度、时区、大小写、空格、LOB/JSON）       | 每日 + 关键字段全量 | 抓类型映射与语义丢失；覆盖有限，靠 ③ 指哪打哪 |

三条必备设计：

1. **可重跑与幂等**：校验任务按（表、主键段、水位线——标记"同步/校验做到哪儿了"的位点，通常是时间戳或日志位点）分片记录进度，重跑只补差异段，不整表重来——否则窗口不够，校验就成了摆设。
2. **增量期间的收敛策略**：边写边搬的表永远对不平。做法是"按水位线切片停止增量写入 → 追平 → 校验该段 → 下一段"，或用"业务时间 + 状态终态"作为可比条件；**没进终态的行不参与比对，但要单独统计数量**（这个数字异常增长就是链路积压的信号）。
3. **差异定位到主键 + 差错台账**：差异不是日志里一行 `diff`，而是台账表里一行记录（表名、主键、差异列、源值、目标值、发现批次、处理人、处理方式、复核人、销案时间）。台账缺失就等于"发现了问题但没有管理"，评审时这会被直接指出。

```sql
-- 分片校验和（两侧库各自执行，比较结果表；<PK_COL> 换成实际主键列）
-- 目的：把差异范围收敛到某个主键段，而不是整表重比
SELECT MOD(<PK_COL>, 64)                                   AS bucket,
       COUNT(*)                                            AS rows_cnt,
       SUM(total_amount)                                   AS amt_sum,        -- 金额类必带
       SUM(CRC32(CONCAT_WS('|', id, status, total_amount,
                           DATE_FORMAT(update_time, '%Y-%m-%d %H:%i:%s')))) AS chk_sum
FROM   orders
WHERE  create_time >= '2026-01-01' AND create_time <  '2026-02-01'
GROUP BY MOD(<PK_COL>, 64)
ORDER BY bucket;
-- 注意：CONCAT_WS 对 NULL 的处理、CRC32 的可用性、DECIMAL 转字符串的标度表现
-- 在两库可能不同 → 校验和不等不代表数据不等，代表"这一段要进入 ④ 逐列比"
```

> 校验本身要防"假绿"：两侧都用同一套转换脚本生成比对 SQL，会屏蔽掉真实差异；比对基准必须以**源库导出文件（不可变）+ 目标库直查**双路径做，并且校验任务自己要有监控（跑没跑、跑多久、差异趋势）。

## 九、金融特色约束：为什么账务类数据最晚迁

### 9.1 迁移顺序不是技术问题，是风险控制问题

行业通行做法是**先迁查询/报表/日志类，最后迁账务类**，理由四条：① 账务数据不可"重放"——错了要出会计分录调整，还会触发客户资金差错与监管报告义务；② 账务链路是唯一一处"任何非零差异都不允许"的，而查询类可以接受读侧灰度与结果比对；③ 前几轮的迁移经验、工具链、原厂磨合、回退演练都要在外围系统上先跑完；④ 外围先迁可以把"方言与工具坑"在低风险环境里暴露干净。落位到模块内的对照：**账务模型见 [02 篇](./02-核心系统与会计账务引擎.md) §5，一致性不变式见 [09 篇](./09-金融级一致性与对账实战.md) §1**。

### 9.2 热点分区与账户倾斜

分布式库的分片键决定"哪些请求会撞在同一台机器上"。金融数据的倾斜比互联网更极端：**代发工资、商户待结算、汇总清算账户、限额累计账户会在同一时刻集中写少量账户**（同 [02 篇 §8](./02-核心系统与会计账务引擎.md) 热点账户的四种解法）。换库时的三个新问题是：① 按客户号哈希分片，但热点账户是"一个账户"不是"一个客户"，哈希救不了它；② 按日期/机构范围分区会把当日集中写入打到同一分区；③ 全局二级索引（跨分片才能查的索引）会引入写放大的新瓶颈。所以**分片键设计必须在含真实倾斜的数据集上压测**，不能只测均匀分布。

### 9.3 日切窗口与跑批在国产库上的重排

日终批处理在换库后是"必须整体重做一遍"的对象：`DELETE + INSERT` 型重算的锁影响、并行度参数、批量提交大小、统计信息收集时点、作业依赖顺序，全都跟老库不同；更常见的是"过程语言细节差异导致跑批结果对不上"。要求：跑批后必须自动执行账账核对（借贷平衡、总分核对、余额勾对，口径见 [02 篇 §7.3](./02-核心系统与会计账务引擎.md)），**核对不平则日切不得推进**——这条规则与库无关，但实现要重做。调度与水位线机制见 [批处理与调度编排](../14-数据工程与OLAP/05-批处理与调度编排.md)。

### 9.4 单元化 / 多活与数据库拓扑

单元化（把客户按维度切成可独立运行、可整体搬迁的"单元"，每单元含完整应用 + 数据栈）会**反向决定数据库形态**：单元内数据要能自成闭环、跨单元访问要走显式路由、切换要能整单元搬迁。所以选型时要问的不是"支不支持分布式"，而是"能不能按单元切、切换时数据归属怎么保证、跨单元一致性怎么收敛"。架构模式见 [高可用架构模式](../13-稳定性工程/04-高可用架构模式.md)，灾备切换流程见 [10 篇 §9](./10-银行研发运维流程与投产管控.md)。

## 十、动手练习（都可在本地 MySQL 上完成，输出物可直接进简历/评审材料）

### 练习 1：给本项目写一份"MySQL → 国产分布式库"兼容性摸底清单

要求用 `information_schema` 产出**对象清点 + 高风险写法统计**，可重复执行、结果可存档：

```sql
-- ① 对象清点：把"库内资产"变成数字（换库工作量的第一份依据）
SELECT TABLE_SCHEMA, TABLE_NAME, ENGINE, TABLE_COLLATION,
       TABLE_ROWS, AVG_ROW_LENGTH
FROM   information_schema.TABLES
WHERE  TABLE_SCHEMA NOT IN ('information_schema','mysql','performance_schema','sys')
ORDER BY TABLE_SCHEMA, TABLE_NAME;

-- ② 库内可编程对象与约束：本项目预期为 0（无过程/触发器/外键），
--    这本身就是一条重要评估结论：工作量集中在应用侧 SQL 与 ORM 方言
SELECT SPECIFIC_SCHEMA, ROUTINE_TYPE, COUNT(*) AS cnt
FROM   information_schema.ROUTINES
WHERE  ROUTINE_SCHEMA NOT IN ('information_schema','mysql','sys') GROUP BY 1,2;
SELECT TRIGGER_SCHEMA, EVENT_OBJECT_TABLE, ACTION_TIMING, EVENT_MANIPULATION
FROM   information_schema.TRIGGERS;
SELECT TABLE_SCHEMA, TABLE_NAME, CONSTRAINT_NAME, REFERENCED_TABLE_NAME
FROM   information_schema.KEY_COLUMN_USAGE WHERE REFERENCED_TABLE_NAME IS NOT NULL;

-- ③ 主键与自增：哪些表换库后要重新设计发号（对照 §5.1）
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME, EXTRA, DATA_TYPE
FROM   information_schema.COLUMNS
WHERE  EXTRA LIKE '%auto_increment%' ORDER BY TABLE_SCHEMA, TABLE_NAME;

-- ④ 类型与字符集风险：JSON/TEXT/BLOB/ENUM、非 utf8mb4、精度可疑的浮点
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME, DATA_TYPE, CHARACTER_SET_NAME, COLLATION_NAME
FROM   information_schema.COLUMNS
WHERE  TABLE_SCHEMA NOT IN ('information_schema','mysql','performance_schema','sys')
  AND  (DATA_TYPE IN ('json','tinytext','text','mediumtext','longtext','blob',
                      'mediumblob','longblob','enum','set','float','double')
        OR (CHARACTER_SET_NAME IS NOT NULL AND CHARACTER_SET_NAME <> 'utf8mb4'));

-- ⑤ 列属性依赖：ON UPDATE CURRENT_TIMESTAMP（目标库多半没有这个语法）
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME, EXTRA
FROM   information_schema.COLUMNS WHERE EXTRA LIKE '%on update%';
```

交付：一张矩阵（表 × 风险项 × 命中条数 × 处置方式 × 责任人）。**本项目已知的四个高分项**是：56 处自增、56 处 `ON UPDATE CURRENT_TIMESTAMP`、JSON 列（`deploy/mysql/init.sql:312`）、ngram 全文索引（`deploy/mysql/init.sql:258`），以及硬编码的 `DbType.MYSQL` 分页方言（§5.10）。

### 练习 2：`ai-cs-user` 换库后还需要 ShardingSphere 吗——评估报告要点

现状：`ai-cs-user/src/main/resources/sharding-user.yaml` 配的是 2 库 × 4 表、按用户 ID 后四位取模路由（`actualDataNodes` 在 `:67`），分片算法是自定义类（`:76-88`），非分片表收敛到 `user_db`（`- !SINGLE` 段 `:58-61`），连接池为 Hikari（`:29`）。报告要求写出：

1. 目标库若原生水平扩展，**分片路由这层是否可以撤**（撤的收益：少一层 SQL 改写；撤的代价：失去影子库/灰度双写/统一数据源治理这些手段）；
2. 保留哪些能力：`!SINGLE` 的多数据源归属、迁移期的双写与切流、读写分离；
3. 与 Seata AT 的关系：库内核事务 + 中间件 + 全局事务三层叠加时，超时与回滚怎么算（给一张"哪层保证什么"的表）；
4. 结论必须给"分阶段"：**迁移期保留 → 稳态收敛 → 明确退役条件**，而不是一句"可以删了"；
5. 附一条风险提示：配置文件头注释里的 ShardingSphere 版本与实际依赖版本不一致（注释写 5.4.1，`pom.xml:46` 是 5.5.0），这类"文档与制品不一致"在银行评审里就是缺陷项。

### 练习 3：写一个两侧库的表级校验脚本

要求：行数 + 关键列校验和 + **差异定位到主键** + 可重跑 + 输出台账表。给一个最小可跑版本（源侧基准文件与目标侧直查两条路径）：

```bash
#!/usr/bin/env bash
# verify-table.sh <db> <table> <pk> <cols> <buckets>
set -euo pipefail
DB="$1" TBL="$2" PK="$3" COLS="$4" BUCKETS="${5:-64}"
MYSQL="mysql -h<host> -P3306 -u<user> -p'<PWD>' -N -B ${DB}"

# 第一层：分片校验和（两侧同一 SQL 文本执行，避免两套拼接逻辑屏蔽真实差异）
sql=$(cat <<EOF
SELECT MOD(${PK},${BUCKETS}) b, COUNT(*) c,
       SUM(CRC32(CONCAT_WS('|',${COLS}))) s
FROM ${TBL} GROUP BY 1 ORDER BY 1
EOF
)
${MYSQL} -e "${sql}" > src.chk
# 目标库侧同理（换成目标库客户端），然后比对
comm -3 <(sort src.chk) <(sort dst.chk) > diff.bucket

# 第二层：只对差异桶取主键集合做差（定位到主键，而不是整表比）
while read -r bucket _; do
  ${MYSQL} -e "SELECT ${PK} FROM ${TBL} WHERE MOD(${PK},${BUCKETS})=${bucket} ORDER BY 1"
done < diff.bucket > src.pk
# 目标侧同样导出后：comm -23 src.pk dst.pk > only_in_src；comm -13 > only_in_dst

# 第三层：把差异写进台账（可重跑：先按 batch_id 删除本次记录再插入）
cat <<'SQL'
INSERT INTO migrate_diff_ledger
  (batch_id, table_name, pk_value, diff_type, src_val, dst_val, status, create_time)
SELECT 'B20260908-01','orders', o.pk, 'ONLY_IN_SRC', o.val, NULL, 'OPEN', NOW()
FROM tmp_only_in_src o
ON DUPLICATE KEY UPDATE dst_val = VALUES(dst_val), status = 'OPEN';   -- 幂等：以 (batch_id,table,pk) 为唯一键
SQL
```

交付时补三条设计说明：**为什么校验和不等不代表数据不等**（跨库 `CRC32`/`CONCAT_WS` 对 NULL 与标度的表现不同，桶级只作定位）、**增量期怎么取可比区间**（水位线切片 + 未进终态的行单独计数）、**差异台账怎么闭环**（挂账 → 修复 → 复核 → 销案，处理链与 [09 篇 §7.2](./09-金融级一致性与对账实战.md) 的差错处理同构）。

## 十一、本篇术语速查

| 术语                | 一句话人话解释                                                                      | 见哪节 |
| ------------------- | ----------------------------------------------------------------------------------- | ------ |
| Share-Nothing       | 每个节点有独立的存储与计算，靠网络协同做水平扩展的架构                              | §1     |
| 兼容模式            | 一组建库时锁定的开关，让数据库额外接受某种方言写法与函数，不保证语义等价            | §2     |
| SQL 指纹            | 把 SQL 里的字面量归一化后得到的"同一类查询"标识，用来统计调用量与耗时分布           | §4     |
| 快照粒度            | 一致性读"拍照"的时机：按事务拍一次（RR）还是每条语句拍一次（RC）                    | §6     |
| 间隙锁              | 行锁之外把"索引区间"也锁住，用来防幻读；范围越大越容易死锁                          | §5.5   |
| 多数派（quorum）    | 写入过半数副本才算成功，用于选主与容灾判定                                          | §3     |
| TSO / GTS           | 全局时间戳服务：中心节点给事务发单调递增时间戳，用来做全局一致性读与快照            | §5.4   |
| 全局一致性读        | 跨分片读到同一个时间点的完整视图，而不是"每个分片各自的此刻"                        | §5.4   |
| 读己之写            | 自己刚提交的数据，随后一定能读到（哪怕从副本读）——客户"充值完查余额还是旧值"就是它  | §5.4   |
| GSI（全局二级索引） | 不按分片键建也能查的索引，代价是写入要同步维护多份，形成写放大                      | §9.2   |
| 在线 DDL            | 不长时间阻塞读写地完成表结构变更；关键问点是"是否拷贝数据、能否暂停续跑"            | §5.6   |
| PITR                | 恢复到任意时间点（Point-In-Time Recovery），靠基础备份 + 归档日志回放实现           | §3     |
| CDC                 | 变更数据捕获：订阅数据库的变更日志，把数据变化推给下游（本仓库用 Canal 做商品索引） | §5.7   |
| 双轨并行            | 新旧两套库同时跑，先影子读、再灰度写、最后切流，全程做数据比对                      | §7     |
| 水位线              | 增量同步"做到哪儿了"的标记（时间戳/日志位点），校验与重跑都以它为切片边界           | §8     |
| 差错台账            | 把每一条差异登记成可跟踪的记录（发现、定责、处理、复核、销案），而不是打一行日志    | §8     |
| 单元化              | 按客户/机构把系统切成可独立运行、可整体搬迁的单元，数据库拓扑要跟着它设计           | §9.4   |

## 十二、初学者常见误区

| 误区                                 | 真相                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| "有兼容模式就不用改代码"             | 兼容模式只覆盖语法层；隔离级别、锁范围、NULL 语义、排序规则、错误码这些**行为层**差异它管不了        |
| "只做功能验证就够了，测试全绿就能上" | 功能用例覆盖不到计划层。必须用生产真实 SQL 指纹回放，并对执行计划做 diff，否则上线当晚才现原形       |
| "把兼容率百分比当结论"               | 百分比是厂商口径。可交付的只有"不兼容条目清单 + 每条的改造动作与责任人"                              |
| "分布式库天然比单机快"               | 单行点查多半更慢（多了一跳共识）；它买的是**容量、可用性和在线扩展**，不是单请求延迟                 |
| "分页和 ORM 不用管，框架会自动适配"  | 方言是硬编码的（本仓库 4 处 `DbType.MYSQL`）。换库不改这里等于把 MySQL 语法发给另一个库              |
| "自增主键哪个库都有，差不多"         | 分布式库的自增会跳号、不保证顺序，`getGeneratedKeys` 与批量插入行为也要实测；正解是应用侧发号        |
| "驱动装上能连就行"                   | 驱动与 JDK、连接池、探活语句、超时语义是一组组合；不在内网私服白名单里连投产都过不了                 |
| "先迁核心账务，证明能力"             | 恰恰相反。账务最晚迁，外围与查询类先趟坑（§9.1）；拿核心做第一次练手是标准的高危决策                 |
| "数据校验跑个 count 一致就算迁完"    | count 一致只能证明行数对。金额/状态/时间/精度/大小写这些"值错"只能靠聚合值 + 分片校验和 + 抽样深比对 |
| "回退方案就是写一句'恢复备份'"       | 要有可执行清单、触发条件、数据回流路径、以及**真演过的记录**。没有真回退方案就不该被允许上生产       |
| "库换了，幂等/对账那套不用重做"      | 快照粒度与锁语义一变，幂等防线与"读己之写"都要重测；见 §六 那张表                                    |
