## 一、本篇在信创专题里的位置：一条异构交付链路

信创改造最容易讲散，是因为它横跨硬件、OS、数据库、中间件、运行时、制品六层，每层都有人在讲。把它拉成一条链路就清楚了：**你的代码要在一台指令集可能不同的机器上跑起来，中间每一步都要"复制一份正确性的证据"**。

```text
      【开发机 / CI 构建机：绝大多数是 x86_64 + Linux(glibc)】
                        │
   pom.xml:30 java.version=17 ──┐
   依赖树里的 native 组件        │  ① 编译期：字节码跨平台，native 库不跨平台
 (netty epoll / zstd / rocksdb) ┘
                        │
                        ▼
        docker build（现状：单架构，只产宿主架构镜像）
                        │
     ② 目标态：buildx 多平台构建，一次产出 amd64 + arm64 + …
                        │
                        ▼
   制品仓库（registry）
   ├─ tag: aics/user-service:<版本>-<流水线号>       ← 可覆盖，不是证据
   └─ digest: sha256:...（镜像内容摘要，同一 tag 指向不同内容时它是唯一可靠标识）← 这才是证据
                        │
     ③ 准入：架构校验 + 漏洞扫描 + 签名，缺一不进生产
                        │
                        ▼
   K8s 集群（异构节点池：同一集群里混着不同指令集的机器）
   ├─ 节点标签 kubernetes.io/arch=amd64 / arm64 / …
   ├─ Pod 需要 nodeSelector / affinity（亲和调度）声明落在哪类节点
   └─ 现状：deploy/k8s/ 全目录零命中 → ❌ 没有任何架构约束
                        │
                        ▼
   运行时：国产 JDK 发行版 + 国产 OS + 国产中间件（TongWeb / BES / MQ / 注册中心）
                        │
                        ▼
   故障与取证：hs_err + core dump + GC 日志 + 内核日志 → 多方（服务器/OS/中间件/DB）定责
```

分工要背清楚，面试时能一句话说清"你负责哪一段"：

| ------------------ | ------------------------------------------ | ------------------------------------------ |
| 为什么换、怎么评   | 采购目录、测评与适配证明、路线与节奏       | [12 信创全景与银行替换路线](./12-信创全景与银行替换路线.md) |

| OS 与虚拟化容器    | 内核/glibc、虚拟化与容器运行时             | [14 国产操作系统与虚拟化容器适配](./14-国产操作系统与虚拟化容器适配.md) |

## 二、国产中间件版图：名称、性质，以及"能跑"和"跑得对"的差距

### 2.1 应用服务器 / Java EE 容器

| 产品                        | 提供方（公司）                                  | 性质       | 常见对标替换物           |
| --------------------------- | ----------------------------------------------- | ---------- | ------------------------ |
| TongWeb                     | 东方通（北京东方通科技）                        | 商业       | Tomcat / WebLogic / JBoss |
| BES 应用服务器              | 宝兰德（北京宝兰德软件）                        | 商业       | WebLogic / Tomcat        |
| Apusic 应用服务器           | 金蝶天燕（金蝶集团旗下）                        | 商业       | WebLogic / JBoss         |
| InforSuite 应用支撑平台     | 中创中间件（济南）                              | 商业       | WebLogic / JBoss         |
| Tomcat / Jetty / Undertow   | Apache / Eclipse 等社区                         | 开源       | ——（被替换方）           |

银行为什么大量在用，三个现实原因：**采购目录里有**（合规先于技术）、**有原厂可追责**（出问题能找到人，商业合同里写着响应时限与驻场支持）、**历史包袱本来就在商用容器上**（核心与渠道系统早年多数跑 WebLogic，替换候选只能是同类商业件，不是 Tomcat）。

"应用起来没报错"和"行为一致"是两件事。逐条对照（这张表是面试区分度所在）：

| 差异维度               | Spring Boot fat jar（内嵌 Tomcat）                                     | 外置商用容器（TongWeb/BES/Apusic/InforSuite）                     | 应用侧必须验证的点                                     |
| ---------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| Servlet/JSP/EL 规范实现 | 由 `spring-boot-starter-web` 带入固定版本的内嵌实现，随应用版本走       | 由容器厂商实现，版本随容器走，应用不可挑                            | 表达式解析、错误页、静态资源与 MIME 行为是否变化       |
| 线程与连接数           | 应用配置文件里自己管                                                   | 容器统一管理，改的是容器控制台/配置，应用改不动                     | 高峰并发下连接排队、拒绝策略、超时值由谁给             |
| 会话管理               | 应用内存或 Spring Session                                              | 容器自带 session 复制/亲和与过期策略                                | 登录态在灰度多版本并存时会不会丢                       |
| 类加载隔离             | 单一 fat jar 类加载器，父子关系简单                                    | 容器级 + 应用级 + 共享级多层 classloader，共享库优先               | 同名类被容器版本"抢走"（`LinkageError`/`ClassCastException`） |
| 数据源与 JNDI          | 应用自建连接池（HikariCP 等），口令走应用配置                          | 数据源常由容器以 JNDI 提供，账号口令归容器管                        | 连接池参数（超时/泄漏检测）你还能不能调，DB 口令轮换归谁 |
| 日志框架               | Logback + `log4j-to-slf4j` 桥接（实测在 `ai-cs-common` 依赖树中）      | 容器自带日志实现与落地目录                                         | 日志是否仍写到行内采集路径，级别由谁控制               |
| 健康检查与优雅停机     | Actuator + `server.shutdown: graceful`（本仓库全部服务已配，见 [投产管控](./10-银行研发运维流程与投产管控.md)） | 容器自己的管理控制台与生命周期，未必认 Actuator 语义               | 摘流量是否真做到"不丢在途请求"                         |

> ⚠️ **本仓库与这条路线的结构性差距**：12 个 Maven Java 模块（11 个服务 + `ai-cs-common` 公共模块）`<packaging>` **全部是 `jar`**（例：`ai-cs-common/pom.xml:14`），依赖树里是 `spring-boot-starter-web` → 内嵌 Tomcat。要走"外置到国产商用容器"这条路，通常得改成 `war` + 排除内嵌容器 + 逐个适配容器的类加载与 JNDI 配置——这是**架构级改动，不是换个镜像**。银行里更常见的折中是"容器能力由行方 PaaS 承接，应用仍以自包含形态交付"，所以先问清"我们要不要外置"，再谈改造量。

### 2.2 消息中间件

| 类别         | 代表                                    | 性质     | 在银行里的典型位置                     |
| ------------ | --------------------------------------- | -------- | -------------------------------------- |
| 国产商用 MQ  | TongLINK/Q（东方通）                    | 商业     | 传统交易类异步通道、跨系统报文传递     |
| 国产商用 MQ  | 宝兰德消息中间件产品线（**名称以行内选型目录为准**） | 商业     | 与 BES 应用平台配套采购                |
| 开源 MQ      | Apache RocketMQ、Kafka、RabbitMQ        | 开源     | 互联网化渠道、日志与数据管道、新项目   |
| 行方自研     | 自研消息/总线平台                       | 自研     | 统一接入、统一审计、统一运维的收敛结果 |

金融场景对 MQ 的额外要求（比互联网多出来的部分）：**同一笔业务的报文必须有序**（先扣款后记账不能颠倒）、**可靠投递 + 不重复**（至少一次 + 消费幂等）、**与本地事务一致**（两阶段/事务消息）、**报文级加密与签名**（通道加密不够，报文本身要能验签）、**全量留痕可审计**（谁发的、谁消费的、什么时候、原文或摘要留存多久）、**与前置机对接**（前置机 = 银行与外部机构之间做报文收发与格式转换的那台专用机器；对外渠道往往经它收发，MQ 只是中间一段，边界要说清）。

换成另一家的 MQ 时，RocketMQ 的这些能力**不会自动等价存在**，必须逐项验证（这张表就是"功能映射差"）：

| 能力               | RocketMQ 侧能力与本仓库实测现状                                   | 替换时要问对方的一句话                                   | 拿不到等价能力时的兜底                        |
| ------------------ | ------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------- |
| 顺序消息           | 支持按业务 key 选队列；⚠️ **本仓库未启用顺序发送**（无相关调用） | 是否支持分区级严格顺序，扩容/故障切换后顺序是否被打破   | 业务侧带序号，消费端做重排序/版本比对         |
| 事务消息（半消息 + 回查） | ✅ 在用：支付成功消息走 `sendMessageInTransaction`（`ai-cs-pay/.../mq/PaySuccessMessageProducer.java:52`），本地事务由 TransactionListener 执行 | 是否有等价的"预提交 + 回查"机制，还是要应用自己补偿 | 落地"本地消息表 + 补偿任务"，见 [金融级一致性与对账实战](./09-金融级一致性与对账实战.md) |
| 延迟/定时消息      | ✅ 在用：订单超时取消用延迟档位投递（`ai-cs-order/.../OrderServiceImpl.java:158`） | 任意时刻定时还是固定档位，档位是否可配、能不能对齐业务时限 | 自建扫描任务 + 数据库到期时间字段              |
| 死信与重试         | ✅ 在用：消费重试上限显式配置（`ai-cs-order/.../listener/PaySuccessListener.java:30` 的 `maxReconsumeTimes = 8`），死信由消费者落表（`ai-cs-mq/.../consumer/WorkOrderDlqListener.java:23-24`） | 死信怎么命名、能否转投人工差错池、重试次数与间隔谁定    | 消费端记录失败流水入差错池，绝不静默丢弃       |
| 消费幂等约定       | 至少一次投递 → 幂等靠业务唯一键与前置状态条件                       | 是否真"至少一次"，有没有"至多一次"模式被误用             | 幂等表 / 状态机前置条件，见 [金融级一致性与对账实战](./09-金融级一致性与对账实战.md) |
| Rebalance 模型     | 消费者组内队列分配，扩缩容触发重平衡                                | 重平衡期间会不会重复消费、会不会短暂停顿                  | 消费端可重入 + 抖动窗口告警                    |
| 广播 vs 集群      | 两种消费模式语义明确                                                | 是否都支持，切换要不要改配置/走申请                       | 用集群模式 + 每实例本地缓存刷新替代广播        |
| 优先级队列         | 需按版本与部署确认                                                  | 是否支持消息优先级，还是只能拆 topic                      | 拆 topic + 消费端线程池配额                    |
| 堆积与回溯         | 按时间/位点重置消费                                                 | 能否按业务时间回溯，消息保留多久                          | 关键流水落 DB，MQ 只当管道                     |

> 术语就地解释：**rebalance（消费组内队列的重新分配）**——消费者实例增减时，谁消费哪几个队列要重算，重算窗口内容易出现短暂停顿或重复消费；**死信队列（DLQ）**——重试仍失败的消息的去处，没人管的死信等于业务数据消失。MQ 基础概念见 [RocketMQ 消息队列](../04-中间件/02-RocketMQ消息队列.md)，半消息/回查与死信的代码落点见 [RocketMQ 事务消息与死信队列](../04-中间件/08-RocketMQ事务消息与死信队列.md)。

### 2.3 注册中心 / 配置中心 / 服务治理

| 组件                                  | 性质 | 本仓库锚点                                             | 信创环境里的现实处境                                   |
| ------------------------------------- | ---- | ------------------------------------------------------ | ------------------------------------------------------ |
| Nacos（注册 + 配置中心）              | 开源 | `pom.xml:41` spring-cloud-alibaba `2023.0.1.0`、`docker-compose.yml:54` `nacos/nacos-server:v2.3.2`、`deploy/k8s/nacos.yaml:51` | 多数继续沿用开源，但**没有商业原厂支持**：制品要先进内网私服，故障要自己定位 |
| Sentinel（限流熔断）                  | 开源 | `docker-compose.yml:257`、`deploy/k8s/sentinel-dashboard.yaml:43` | 常被"行方统一流控/网关平台"取代，控制台可能不让你开    |
| XXL-Job（分布式调度）                 | 开源 | `docker-compose.yml:233`、`deploy/k8s/xxl-job.yaml:43` | 银行更常用统一批调度平台（跑批要进日终调度视图）       |

"没有商业支持时团队要自己承担什么"，四件事，一件都跑不掉：**版本收敛**（全行 N 个系统各用不同版本 = 每个 CVE 都要查 N 遍，所以行内一定定一个基线版本并禁止散引）、**故障自研定位**（原厂不会替你抓堆栈，源码和 arthas 都得自己上）、**补丁与安全响应**（0day 出来时你要在几分钟内答出"哪些系统用了哪个版本"，靠的是依赖清单台账不是记忆）、**变更自证**（升级 Nacos 客户端等于改全行应用的启动依赖，要单独走变更评审）。这也是很多行最终把注册配置中心**收敛成自研平台或统一中间件平台**的原因——把"支持责任"从项目组搬回平台团队。

组件本身的用法与配置口径不在本篇展开：注册与配置中心见 [Nacos 注册与配置中心](../02-Spring微服务/03-Nacos注册与配置中心.md)，网关侧见 [SpringCloudGateway 网关](../02-Spring微服务/04-SpringCloudGateway网关.md)。**信创改造后这些文章的配置项不一定还认**——容器/平台接管了哪一项，先去问行方平台，再回来改配置文件。

### 2.4 缓存 / NoSQL / 检索

| 类别      | 本仓库现状（实测）                                                            | 信创目录里的常见处置（描述性，不编产品名）                                   |
| --------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 缓存 KV   | `docker-compose.yml:35` `redis:7`；`deploy/k8s/redis.yaml:112` `redis:7`     | 通常继续沿用 Redis 协议栈，由行内统一缓存平台承接部署与支持；是否引入其他兼容实现**以行内选型目录为准** |
| 文档库    | `docker-compose.yml:172` `mongo:7.0`；`ai-cs-chat/pom.xml:213` mongo starter | 多数走"许可证 + 支持"双评审；无国产替代时按开源件管理，或以关系库/自研归档替代 |
| 搜索引擎  | `docker-compose.yml:84` `elasticsearch:8.12.0`；`ai-cs-search/pom.xml:58`    | 许可证口径变化会让引入评审更谨慎；常见结论是"行内既有检索平台承接"，不自建    |
| 对象存储  | `docker-compose.yml:149` `quay.io/minio/minio:latest`（无 digest）；`deploy/k8s/minio.yaml:50` 同为 `latest` | 常与行内统一存储/备份平台合并评估；S3 兼容接口是应用侧的隔离层                |
| 向量/图库 | `docker-compose.yml:192` chroma、`:209` `neo4j:5-community`                   | AI 类组件通常单独走新技术引入流程，不进通用信创目录，**以行内选型目录为准**   |

一句话原则：**不要假设"每个开源件都有一个国产替代品"**。没有替代是常态，此时合规动作是"按开源软件治理"（版本基线 + 私服 + 台账 + 安全响应），而不是硬凑一个名字出来。各组件的用法与部署细节在 [Redis 缓存实战](../04-中间件/01-Redis缓存实战.md)、[Elasticsearch 搜索引擎](../04-中间件/03-Elasticsearch搜索引擎.md)、[MinIO 对象存储](../04-中间件/04-MinIO对象存储.md) 三篇，向量库/图库这类"新技术件"为什么也进 K8s 清单见 [AI 与治理中间件部署](../04-中间件/09-AI与治理中间件部署.md)。本篇只管"上信创环境时它会被怎么处置"。

### 2.5 外围组件：只记类别，品牌以行内目录为准

| 类别             | 干什么                          | 国产化常见处置                       | 应用侧的接口差异点                                   |
| ---------------- | ------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| 批量文件传输     | 日终与外部机构互传文件          | 采购国产传输平台或行内自研           | 断点续传/校验码/目录权限由平台管，应用只申请通道     |
| 加解密与签名     | 报文加签验签、字段级加密        | 密码机 / 服务端密码服务（**品牌从略**） | 本地 SDK 调用 vs 远程密码服务调用：延迟、连接池、批量接口 |
| 电子印章/签章    | 回单、协议盖章                  | 采购第三方签章服务                   | 图片/PDF 合成在对方完成，超时与重试要按外部服务配    |
| 短信/消息网关    | 验证码、动账通知                | 行内统一网关                         | 应用不直连运营商，模板与频次受网关策略约束           |
| 前置机/渠道接入  | 与人行、银联、第三方渠道对接    | 多为存量专用系统                     | MQ/HTTP 边界之外还有报文格式与签名层，见 [支付清算体系与报文](./04-支付清算体系与报文.md) |

这一层的共同特点：**它们不是"换实现"而是"换责任边界"**。算法是否合规、密钥归谁管、日志留多久，都由安全条线定，不由项目组定——相关口径见 [银行业信息安全管理规范](./07-银行业信息安全管理规范.md)。柜面与电子渠道两类系统对上述组件的依赖方式不同，分别在 [柜面系统与集中作业](./03-柜面系统与集中作业.md) 与 [网络金融与电子渠道](./06-网络金融与电子渠道.md) 两篇里更完整地讲。

## 三、Java 运行时（JDK）：选型的看点不是排名

### 3.1 OpenJDK 与各发行版的关系（人话版）

**OpenJDK 是上游源码项目**；各厂商从它构建出可安装的 JDK，加上自己的补丁节奏、长期支持、诊断工具和商业条款——这就是**发行版**。银行说的"国产 JDK"多数指国内厂商/社区发布的 OpenJDK 下游构建；对应用而言**API 同源，差异在支持责任、更新通道、架构覆盖、工具链和许可证**。

| 发行版               | 出处              | 性质           | 选型时值得留意的点（不排名）                        |
| -------------------- | ----------------- | -------------- | --------------------------------------------------- |
| Alibaba Dragonwell   | 阿里巴巴          | 开源（另有支持服务口径） | 面向大规模在线应用做过增强，需按其官方发布说明确认  |
| Tencent Kona         | 腾讯              | 开源           | 关注其对目标架构的正式发布情况                      |
| BiSheng JDK（毕昇）  | 华为              | 开源           | 与 ARM 服务器场景结合紧密；诊断/性能特性看官方说明  |
| 龙芯平台 JDK         | 龙芯生态（社区/厂商） | 视具体来源 | 目标指令集是否已发布、是完整 JDK 还是受限构建，必须逐版本确认 |
| Amazon Corretto      | AWS               | 开源，含免费更新 | 长期支持与安全更新通道清晰，海外厂商                |
| Eclipse Temurin      | Adoptium 社区     | 开源           | 覆盖面广，本仓库现状用的就是它（见 §3.4）           |

### 3.2 选型检查清单（这张表比"哪个更快"有用得多）

| 维度                   | 要问的问题                                                       | 通不过会怎样                             |
| ---------------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| 目标架构是否已发布     | 你要跑的那个指令集 + OS 组合，有没有正式 JDK 包（不是"能编译出来"） | 整条国产化路线卡死                       |
| 更新与 CVE 响应通道    | 出高危漏洞多久有包、有没有订阅通知、谁负责跟                     | 只能自己打补丁，审计问"你何时修的"答不上 |
| 长期支持周期           | 这个版本还在不在维护窗口内                                       | 生产跑无更新 JDK = 明确检查发现项        |
| GC 能力                | G1/ZGC 等在该版本该架构上是否可用、参数是否被支持                | 调优手册失效，性能问题定责扯不清         |
| 诊断工具               | 是否带连接池/内存/性能剖析等增强诊断，能否与行内 APM（应用性能监控，以 Java Agent 形式挂在 JVM 上采指标与链路）探针共存 | 排障只能靠 jstack + 日志，效率减半       |
| 许可证与商用约束       | 商用是否需要订阅、是否允许再分发（redistribution）到行内镜像仓库   | 投产评审阶段被法务驳回                   |
| 与探针/Agent 的兼容性  | APM、Java Agent、字节码增强框架能否在该 JDK + 该架构上正常加载并共存 | 启动期 `LinkageError`，或监控静默无数据  |
| 行内是否已统一基线     | 全行有没有一个"必须用这个 JDK 版本"的基线                        | 你的版本进不了生产镜像仓库               |

### 3.3 libc 与"同一镜像名不同底子"

`ai-cs-product/Dockerfile:1` 用的是 `eclipse-temurin:21-jre-alpine`。Alpine 系镜像用 **musl libc**，而其他 8 个服务用的 Ubuntu（jammy）系是 **glibc**。差别不在 Java 代码，在**任何触碰操作系统的角落**：DNS 解析行为、locale 与字符集、`tzdata` 位置、以及**为 glibc 编译的 native 库直接加载失败**。这是本仓库里一个不需要信创环境就能理解异构风险的活样本。

### 3.4 本仓库 JDK/镜像基线现状（实测）

| 事实                                                                 | 位置                                             | 影响                                       |
| -------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------ |
| 声明编译版本 Java 17（`<java.version>17</java.version>`，并配 source/target 17） | `pom.xml:30`、`:31`、`:32`                       | 全仓唯一权威版本口径                       |
| 8 个服务运行阶段 `FROM eclipse-temurin:17-jre-jammy`                 | `ai-cs-chat/Dockerfile:17` 等 8 个文件           | 版本一致，但 tag 可变、未锁 digest         |
| 1 个服务 `FROM eclipse-temurin:21-jre-alpine`                        | `ai-cs-product/Dockerfile:1`                     | ⚠️ 与声明版本不一致（编译 17 / 运行 21）+ musl |
| 8 个服务构建阶段 `FROM maven:3.9-eclipse-temurin-17 AS builder`      | `ai-cs-chat/Dockerfile:3` 等                     | 构建 JDK 与 `pom.xml:30` 一致（这点是对的）|
| `ai-cs-product` 是单阶段：镜像只 `COPY target/*.jar`                 | `ai-cs-product/Dockerfile:7`                     | ⚠️ 构建发生在容器外，制品无法由镜像链自证 |
| 7 个服务 `ENTRYPOINT` 里注入 `${JAVA_OPTS}`                          | `ai-cs-chat/Dockerfile:21` 等                    | GC/内存参数可由编排层下发（好实践）        |
| `ai-cs-order/Dockerfile:21`、`ai-cs-product/Dockerfile:11` 是裸 `java -jar` | 同左                                       | ❌ 改 JVM 参数只能重新构建镜像，等于改一次代码 |

编译 17 运行 21 在字节码层面是允许的（高版本运行时跑低版本字节码），但**行为差异不来自字节码**：默认 GC 与默认参数、被移除的内部 API、反射与 `Unsafe` 相关行为、以及 JVM 参数兼容性都会变。银行基线口径对此的态度通常是一句话——**"运行版本高于声明版本"也要评审**，因为你的调优手册是在 17 上验的。

## 四、交付链路的异构改造：本篇最能落地的部分

### 4.1 多架构镜像怎么产

```bash
# 一次性：为 buildx 准备构建器与跨架构执行能力
docker buildx create --name aics-multiarch --use --bootstrap
docker run --privileged --rm tonistiigi/binfmt --install all

# 一次构建产出两个架构，并按 manifest list（多架构镜像索引）聚合推送
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --tag "${REGISTRY}/aics/user-service:${VERSION}" \
  --tag "${REGISTRY}/aics/user-service:${VERSION}-amd64" \
  --tag "${REGISTRY}/aics/user-service:${VERSION}-arm64" \
  --attest type=sbom,generator=default --attest type=provenance,mode=min \
  --provenance-repository "${REGISTRY}/aics/sbom-store" \
  --push .

# 关键一步：把 digest 写进投产方案（同一 tag 内容变了 digest 必变）
docker buildx imagetools inspect "${REGISTRY}/aics/user-service:${VERSION}" --format '{{json .Manifest}}' | jq -r .digest
```

要点四条：
1. **manifest list（多架构索引）不是镜像，是一张寻址表**：节点按自己的架构去拉对应那一份。你登记投产证据时登记的是**索引的 digest 还是单架构镜像的 digest**，必须写死一种，否则回退时会找错包。
2. `--attest` 挂的是两类元数据：**SBOM（软件物料清单，这份镜像里到底有哪些组件）**与 **provenance（构建来源证明，谁在什么提交上把它造出来的）**。银行审计问"这个包里有什么、从哪来"，靠的就是这两样，不是你的记忆。
3. **构建机与目标机架构不同 → 走模拟执行（emulation）**，代价是构建显著变慢、native 编译与偶发测试不稳定、任何"在构建期跑的基准测试"结果不可信。正确做法是**同架构原生 builder 节点组成 builder 池**，模拟只当兜底。
4. **CI 同时产出 amd64/arm64 的工程要求**：builder 池两类架构都有、Dockerfile 里不能有 `RUN ./某二进制`（构建期执行宿主架构程序）、缓存要按平台分片、registry 必须支持 manifest list 与 OCI attestation；制品仓库还要求内网私有 registry、按架构分 tag 或分目录、保留期覆盖审计要求、禁 `latest`（见 10 篇 §4.4）。

### 4.2 依赖治理：native 组件要一个个问"有没有目标架构版本"

字节码跨平台，**native 库不跨平台**。带 native 的常见类别：压缩编解码、加解密、netty 的 epoll/kqueue 传输层、监控 Agent、内嵌 KV 引擎。用 Maven 把清单拉出来：

```bash
# 全模块依赖树落盘，便于登记台账
mvn -o dependency:tree > /tmp/deptree.txt
# 只看可能的架构相关件（按 classifier 或已知 groupId 命中）
mvn -o dependency:tree | grep -Ei "native|linux-|aarch|loongarch|riscv|snappy|lz4|zstd|rocksdb|tcnative|bouncycastle"
# 验证某个 jar 里到底打了哪些 .so（这是"有没有目标架构版本"的唯一硬证据）
unzip -l ~/.m2/repository/org/xerial/snappy/snappy-java/<版本>/snappy-java-<版本>.jar | grep '\.so$'
```

本仓库实测结果（命令与结论都可复现，架构覆盖按"包里打了哪些 `.so`"判断，`.so` = Linux 动态库）：

| 组件（groupId:artifactId）        | 谁带进来的（实测）        | 打包的 native 覆盖（实测目录名）                       | 缺口与后果                                                       |
| --------------------------------- | ------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------- |
| `io.netty:netty-transport-native-epoll` | gateway 侧 reactor-netty；RocketMQ 客户端侧 `netty-all` | classifier 有 `linux-x86_64`、`linux-aarch_64`、`linux-riscv64` | ❌ **无龙芯 classifier** → 该架构上回退 NIO 传输层；性能与线程模型变化，但功能可用（要重新压测） |
| `com.github.luben:zstd-jni`       | RocketMQ 客户端（压缩）   | `linux/amd64`、`linux/aarch64`、`linux/loongarch64` 等 | ❌ 无 riscv64；且这些是 glibc 构建 → **alpine/musl 镜像上加载失败风险** |
| `org.xerial.snappy:snappy-java`   | MinIO SDK（`ai-cs-common` 依赖树实测） | `x86_64`、`aarch64`、`riscv64`、`ppc64le`、`s390x` 等 | ❌ 无 `loongarch64` 目录                                          |
| `io.github.aliyunmq:rocketmq-rocksdb` | RocketMQ 客户端       | 仅 `linux32`、`linux64` 及二者 `-musl` 变体           | ❌ **无 ARM/龙芯构建**。native 缺失只在真正走到该代码路径时抛 `UnsatisfiedLinkError`，所以必须确认"我们的用法会不会触发这条路径"，不能靠"启动没报错"就下结论 |
| `org.bouncycastle:bcprov-jdk18on` | MinIO SDK（实测，含 `org/bouncycastle/crypto/gm/` 国密实现） | 纯 Java，`.so` 计数为 0 | ✅ 架构无关；但见 §5.1 的版本共存问题                           |
| `com.mysql:mysql-connector-j`     | `pom.xml:47`              | 纯 Java                                                | ✅ 架构无关；数据库侧差异见 15 篇                                |

> 由此得出一条**通用工程结论**：一个依赖树里同时存在"覆盖龙芯""覆盖 ARM 但缺龙芯""只有 x86_64"三种情况。所以异构改造的排期不该按"应用数量"估，要按**"native 依赖清单 × 目标架构矩阵"**估——这就是 12 篇里评估阶段真正该交付的东西。

**锁版本清单**（本仓库现状已有的可用抓手）：`pom.xml` 的 `<properties>` 已把版本集中（`:40` spring-cloud、`:41` spring-cloud-alibaba、`:45` mybatis-plus、`:46` shardingsphere、`:47` mysql-connector、`:54` rocketmq-spring）；⚠️ 但**没有 `dependencyManagement` 之外的 BOM/约束检查**，也没有"禁止新增未登记依赖"的门禁（10 篇 §4.2、§4.3）。异构改造要求：目标架构上不存在的 native 组件必须**显式排除或替换并记录原因**，不能靠运行时降级。

机制层面的基础：多模块版本集中与 `dependencyManagement` 的优先级见 [Maven 多模块管理](../01-Java基础/02-Maven多模块管理.md)；epoll/kqueue 这类原生传输层相对 JDK NIO 是什么关系（**它是可选加速路径，不是功能必需**）见 [IO 模型与 Netty 基础](../01-Java基础/07-IO模型与Netty基础.md)——这个区别正是"降级后功能可用但要重新压测"的依据。

### 4.3 本仓库改造清单（按投入产出排序）

| #  | 现状（实测事实）                                                            | 风险（异构视角）                                         | 改法（⚠️ 目标态）                                              | 验收方法（❌ 目前做不到）                          |
| -- | --------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| 1  | `deploy/k8s/` 全目录 `nodeSelector`/`kubernetes.io/arch`/`affinity`/`tolerations` 零命中 | Pod 可能漂到异构节点，或该去的节点去不了；故障无法归因   | 为每个 Deployment 显式声明架构亲和 + 节点池标签，写进行内模板   | `kubectl get pod -o jsonpath='{.spec.nodeName}'` 反查节点 arch |
| 2  | 基础镜像用可变 tag：`ai-cs-chat/Dockerfile:17` 等 8 处                      | 同 tag 内容漂移，"生产跑的是哪个包"答不出                 | 锁 digest + 行内基线镜像；做法见 [镜像构建优化与安全扫描](../16-云原生与GitOps/06-镜像构建优化与安全扫描.md) | Dockerfile 里出现 `@sha256:`；`docker buildx imagetools inspect` 可核对 |

| 8  | `ai-cs-product/Dockerfile:7` 从 `target/` 取 jar（构建在镜像外）            | 镜像链自证不了"这个 jar 由这次源码构建而来"               | 改多阶段，构建进镜像，产物挂 provenance attestation             | 凭流水线号可反查源码提交与镜像 digest              |
| 9  | CI 验证只到 `kubectl get`：`Jenkinsfile:134-148`；`verify-deploy.sh:20` 计数、`:99-106` 汇总不 `exit 1` | 架构错了、起错节点都不算失败                              | 加"架构校验 + 镜像准入 + 健康 + 业务案例"四层，失败阻断         | 人为投一个错架构镜像，流水线必须变红               |
| 10 | 无内网制品源/JDK 基线登记                                                   | 出 CVE 时无法回答"谁受影响"                                | 私服 + 依赖台账 + 基线镜像清单（对齐 10 篇 §4.3）              | 任一分发件可在台账中被反查到调用它的服务列表       |

排序逻辑说清楚（评审时一定被问"为什么先做 1"）：**1~3 是"不做到生产就不受控"**——架构不可声明、制品不可追溯，后面所有验证都失去意义；**4~6 是"做到就能省掉一类变更"**——构建脚本与参数入口统一后，换架构、调 GC 不再需要动代码；**7~10 是"补齐链路与制度"**——交付范围一致、门禁生效、台账落地。任何一项在银行都要单独提变更，别指望一个版本全包。

门禁与自动化怎么落到流水线，见 [质量门禁与自动化](../17-研发效能与工程实践/08-质量门禁与自动化.md)；调度约束的 K8s 基础概念见 [Kubernetes 入门](../07-运维部署/02-Kubernetes入门.md)，Service 与流量入口在异构集群里的差异见 [K8s 网络模型与 Service](../16-云原生与GitOps/04-K8s网络模型与Service.md)。

### 4.4 投产视角：异构交付的证据链

| 环节           | 银行要求                                    | 你要产出的证据                                                    |
| -------------- | ------------------------------------------- | ----------------------------------------------------------------- |
| 制品可追溯     | 版本号 + 架构 + digest + 流水线号四元组      | 投产方案里一张"服务 → 镜像 → digest → 架构 → 流水线号"表           |
| 镜像准入       | 扫描通过、签名可信、基线镜像来源合规         | 扫描报告（阻断级为 0）+ 签名校验记录，做法见 [镜像构建优化与安全扫描](../16-云原生与GitOps/06-镜像构建优化与安全扫描.md) |
| 灰度批次       | 同一批次内架构一致，异构分批按节点池推进     | 批次计划 + 每批次落地节点清单（含 arch 标签）                     |
| 回退           | 能退到"确知内容"的旧制品                     | 旧版本 **digest**（不是 tag）提前登记，见 10 篇 §5.4              |
| 监管取证/审计  | 能证明"生产跑的就是这个包"                   | digest 比对记录 + 构建 provenance + 部署时间线，三者互相咬合      |

**同 tag 不同架构**是最阴的坑：`registry/aics/user-service:latest` 昨天在 x86 集群推了一次、今天在 ARM 集群又推了一次，后者把前者覆盖，x86 环境里已运行的 Pod 一重启就拉到 ARM 镜像 → `exec format error`，而 tag 看起来"完全没变"。**只有 digest 能区分**，这也是回退必须登记 digest 的原因。

## 五、银行特色约束：中间件层最难的不是技术

### 5.1 外采与自研混合：类冲突与"容器给你的 classloader"

银行系统里常见"三合一"：你写的代码 + 外采厂商 JAR + 容器/平台提供的库。三者共用一套类加载体系，就会出这类现象：

| 症状                                        | 根因                                             | 处置                                             |
| ------------------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| `NoClassDefFoundError` / `ClassNotFoundException` | 容器不提供你以为会有的包；或应用依赖被容器屏蔽 | 显式打进应用 + 声明优先加载顺序（容器的配置项） |
| `ClassCastException: X 无法转换为 X`        | 同名类被两个 classloader 各加载一份              | 把该库上收到唯一提供方；应用侧排除副本           |
| `LinkageError` / `loader constraint violation` | 共享层与私有层版本不同                          | 统一版本 + 记录到依赖台账                        |
| 日志不落预期文件 / 出现多绑定告警           | 应用带 Logback，容器带另一套实现                 | 只保留一套绑定，桥接件显式声明（本仓库实测为 Logback + `log4j-to-slf4j` 路线） |
| 数据库口令轮换后连不上                      | 数据源由容器 JNDI 提供，改配置改到了应用侧        | 变更单里写明"数据源归属容器"，双方各改各的       |

本仓库已经有一个**真实的双版本共存样本**：`ai-cs-pay` 的依赖树里同时出现 BouncyCastle 的两个变体（一个 `jdk18on`、一个由支付宝 SDK 带入的 `jdk15on`），两者 Java 包名相同、都含 `org/bouncycastle/crypto/gm/`。今天只是"谁先被加载"的运气问题；一旦上外置容器（共享层优先）或上异构 JDK，同一份代码的行为就可能变。**结论：外采 SDK 会把依赖版本钉在你无法控制的地方，异构改造前必须先把 `dependency:tree` 全量落盘做体检。**

> 硬约束提醒：**外采应用不能改代码，只能换容器/换运行时**。所以国产化项目里"最贵的应用"往往不是自研的，而是外采的——你只能通过容器配置、JDK 参数、类加载顺序、数据源归属去调，每一项都要厂商出适配承诺。

### 5.2 异构联调环境：全项目最稀缺的资源

异构测试集群（国产 CPU + 国产 OS + 国产中间件那一套）通常机器少、申请流程长、还得跟别的系统排队。新手常犯的错是"先写完再说"，结果最后两周抢不到环境，测试全部堆到投产窗口前。可行做法：

| 阶段       | 在没有异构环境时先做                                  | 拿到环境后要一次带走的东西                                   |
| ---------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| 编码期     | 依赖树体检（§4.2）、native 矩阵、架构无关单测         | 冒烟脚本（必须脚本化，人在场时不要手点）                     |
| 自测期     | ARM 公有云/开发板/docker 模拟做**功能**验证（性能结论不作数） | 全用例回归 + 日志/取证样例包（给厂商看的东西要当场采集）     |
| 联调期     | 报文与接口契约先用 Mock 打通                          | 与 MQ/DB/密码服务的**真实**端到端一笔流水 + 死信与回查验证  |
| 投产前     | 演练脚本与回退脚本在 x86 上演练到位                   | 在异构环境重演一次，并记录时间（窗口只有 2-4 小时，见 10 篇 §5.1） |

争取资源的正确姿势：把需求写成**可核对的清单**（几台、什么架构、什么中间件版本、要不要 DB、要多久、哪几天必须独占），而不是"我需要个环境"。项目排期里把"环境可用日期"当硬依赖登记，逾期即升级。

### 5.3 故障多方定位：先有取证，再谈定责

异构环境里出问题，最容易出现"服务器说是 OS，OS 说是中间件，中间件说是 JVM，JVM 说是应用"。破法只有一个：**问题现场的第一手证据在你手上，且各方约定好取证口径**。

| 取证项            | 采什么                                             | 为什么必须有                                  |
| ----------------- | -------------------------------------------------- | --------------------------------------------- |
| JVM 崩溃现场      | `hs_err_pid*.log` + core dump（需在容器里允许写）  | 判断是 JDK/原生库/JIT 还是应用逻辑            |
| GC 行为           | GC 日志（含时间戳、暂停、堆变化），见 [GC 日志与停顿分析](../12-性能工程/02-GC日志与停顿分析.md) | 区分"内存不够""参数不对""泄漏"三类定责方向   |
| 线程与栈          | `jstack`/`jcmd Thread.print` 连续多次快照         | 锁竞争、线程池打满、MQ 消费停顿的第一证据     |
| 内核侧            | `dmesg`、`journalctl -k`、OOM killer 记录          | 容器被杀 vs 进程自己死的分水岭——cgroup 内存限额打满时是内核动的手，见 [容器隔离原理：namespace 与 cgroup](../15-计算机基础/06-容器隔离原理-namespace与cgroup.md) |
| 网络与容器        | 连接数、TCP 重传、`kubectl describe pod` 事件      | 排除"中间件慢其实是网络/调度"                 |
| 复现步骤          | 最小可复现命令 + 环境指纹（arch/JDK 发行版/容器版本） | 没复现步骤，厂商可以合法地"无法定位"          |

**性能定责基线**要提前签：约定基线环境（同一台机、同一份配置）、基线场景与数据量、基线时刻（国产化改造前的同版本结果）、以及"变慢多少个百分点触发联合排查"。没有这套基线，"国产化后变慢了"这句话谁都可能说、谁都不认账。做法参见 [性能问题定位方法论](../12-性能工程/08-性能问题定位方法论.md)；复盘与 RCA 流程见 [RCA 根因分析与复盘](../13-稳定性工程/06-RCA根因分析与复盘.md)。

变更窗口与国产化演练另见 [银行研发运维流程与投产管控](./10-银行研发运维流程与投产管控.md)（§5.1 窗口、§9 灾备演练）；容器隔离与内核视角的原理见上表"内核侧"一行指向的那篇计算机基础文档。

| ---------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- | ------ |

## 七、术语速查：本篇黑话一次讲清

| 术语               | 人话解释                                                                       | 在本篇的位置       |
| ------------------ | ------------------------------------------------------------------------------ | ------------------ |
| digest             | 镜像内容摘要（形如 `sha256:...`），同一 tag 指向不同内容时它是唯一可靠标识     | §1、§4.1、§4.4     |
| tag（标签）        | 人读的镜像名字后缀，**可被覆盖**，所以不能当证据                               | §4.4 的坑          |
| manifest list      | 多架构镜像索引——一张"按架构去拉哪一份"的寻址表，它本身不是镜像层               | §4.1               |
| classifier         | Maven 坐标里区分构建变体的那一段（如 `linux-aarch_64`），native 依赖的关键     | §4.2               |
| native 库          | 非 Java 的机器码库（Linux 上多为 `.so`），**只在匹配的 CPU 架构上能加载**      | §4.2               |
| glibc / musl       | 两套 Linux C 标准库。Alpine 用 musl，为 glibc 编译的 native 库可能加载失败     | §3.3               |
| 类加载器隔离       | 容器把库分成共享层/应用层，先找到谁就用谁的副本，于是出现"同名不同份"          | §2.1、§5.1         |
| JNDI 数据源        | 由容器（而非应用）按名字提供的数据库连接池，账号口令归容器管                    | §2.1、§5.1         |
| 死信队列（DLQ）    | 重试仍失败的消息的去处；没人管它，等于业务数据静默消失                          | §2.2               |
| rebalance          | 消费组实例增减时重算"谁消费哪几个队列"，窗口内容易重复消费或停顿                | §2.2               |
| 异构节点池         | 同一集群里按 CPU 架构分组的机器集合，靠节点标签区分                             | §4.3               |
| 适配证明           | 厂商就该版本/该架构出具的兼容性材料，投产评审的常见准入件（口径见 12 篇）      | §六                |
| 取证包             | 故障现场一次性采集的证据集合（JVM/内核/容器/复现步骤），用来堵住多方推诿      | §5.3               |

## 八、动手练习（本地可执行，不需要信创环境）

1. **给本项目设计"一次构建产出双架构镜像"**。基于 `deploy/scripts/k8s-build-push.sh:25-40` 重写：`PLATFORMS`（默认 `linux/amd64,linux/arm64`）与 `VERSION` 由入参给；用 `docker buildx build --platform ... --push`；同时打 `<版本>-<架构>` 分架构 tag 与聚合 tag；构建后把 `docker buildx imagetools inspect` 得到的 digest 逐行写入 `artifacts/<流水线号>.txt`。自查：为什么这个文件比 `:latest` 值钱（写三句话）。
2. **把 9 个服务的 Dockerfile 收敛成统一基线**。定义：统一构建阶段 `maven:<...>-temurin-<基线>`、运行阶段单一 JRE 镜像（禁 `latest`）、统一 `JAVA_OPTS` 入口（消灭 §3.4 里 7 vs 2 的分歧）、`ai-cs-product` 从单阶段改多阶段。给出**迁移顺序**并说明理由——建议"先在参数入口一致的服务上验证基线镜像 → 再动 8 个同构服务 → 最后动 `product`（它同时改版本 + 换 libc）与 `order`"，每步都有回退点。
3. **用 `mvn -o dependency:tree` 做一次 native 体检**。产出一份 native 依赖台账（记在自己的笔记文件里即可，不必塞进仓库）：每条含 `groupId:artifactId`、谁带入、`unzip -l` 看到的 `.so` 目录名、目标架构缺口、降级后果、处置结论。至少覆盖 §4.2 表的六类。加分：给 `ai-cs-pay` 的 BouncyCastle 双变体写一条 `<exclusions>` 方案并说明为什么**不能只靠"看起来能跑"**。
4. **给 `deploy/k8s/` 补异构调度约束**。为每个业务 Deployment 加 `nodeSelector: {"kubernetes.io/arch": "amd64"}`（先按现状架构显式固定，把隐式行为变显式），并在每个清单文件顶部用 YAML 注释写清"为什么需要它"：不加这行会发生什么、加了之后想上 ARM 要改哪几处、以及它与"同一 tag 不同架构"事故（§4.4）的关系。改完自查：`grep -rn "kubernetes.io/arch" deploy/k8s/` 命中数 = Deployment 数。
5. **写一份"异构故障取证包"生成脚本**。一条命令导出：容器内 `java -version` 与 `uname -m`、`jcmd` 线程快照、GC 日志尾部、`dmesg` 片段、`kubectl describe pod` 事件、镜像 digest。这就是你在 §5.3 里跟厂商对话的底气。

## 九、初学者常见误区

| 误区                                                   | 真相                                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 国产化 = 把中间件换个牌子                              | 换的是**支持责任与行为基线**。Servlet 实现、类加载隔离、数据源归属、日志落点、MQ 语义全要重新验（§2.1/§2.2） |
| Java 字节码跨平台，所以行为一定一致                    | 字节码一致 ≠ 行为一致：libc（glibc/musl）、native 库架构覆盖、JDK 发行版默认参数与内部 API 差异都会改变行为 |
| 同一个 tag 在两个架构集群里都能用                      | 同 tag 会被后推的架构覆盖，回退时拉到错包报 `exec format error`。**只有 digest 能区分内容** |
| 异构镜像在 x86 构建机上模拟跑一下、结果差不多          | 模拟执行只可用于功能验证；任何性能数字、任何构建期执行的架构相关检查都不可信               |
| 外采应用也让我们改代码来适配                           | 外采件经常"只能换容器不能改代码"，适配手段只剩参数与类加载顺序，改造成本要按这个前提估     |
| 没有国产替代的开源件就一定不能用                       | 常态是"继续沿用开源 + 由行内平台/私服/台账承接支持"。要补的是支持责任，不是硬凑替代品      |
| 联调环境等开发完再申请                                 | 异构环境是全项目最稀缺资源。它必须是排期上的硬依赖，逾期就升级                             |
| 出了问题先拉各方开会扯责任                             | 没有第一手取证就没法定责。先凑齐 §5.3 那张表，再开会                                       |
| 制品没锁 digest 也能上生产（有版本号就够了）           | 版本号可被覆盖，且不含架构信息。投产登记必须含 digest（§4.4）                              |
| JDK 选型要看哪个性能最好                               | 先看"目标架构有没有正式发布 + 有没有更新通道 + 行内基线是什么"，性能只是最后一步           |
