# 02 - 简历与项目包装

> **目标**：把 12 个模块、3 万行代码，压缩成 HR 愿意看、面试官愿意问的一页纸。
> **前提**：先读完 [01 岗位地图与 JD 拆解](01-岗位地图与JD拆解.md)，知道自己投什么档位。
> **纪律**：**不编造数据、不把个人项目写成公司项目、写上去的每个词都要能讲三层。**

---

## 一、三条底层原则

1. **一页纸（最多一页半）**。HR 初筛平均 20 秒，第二页基本不看。
2. **项目占 60% 篇幅**。Java 后端岗的区分度在项目，不在技能列表。
3. **每个技术点准备三层**（做过 / 懂原理 / 有取舍），见 [01 第三节](01-岗位地图与JD拆解.md#三面试四轮地图与精力分配)。

> 判断标准：把简历上任意一行指给面试官，你能不能讲 3 分钟？不能就删掉。

## 二、简历结构（Java 后端）

```text
1. 基本信息        姓名 / 电话 / 邮箱 / GitHub / 城市         （3 行）
2. 求职意向        Java 后端开发 / 期望城市 / 到岗时间        （1 行）
3. 教育背景        学校 / 专业 / 学历 / 时间                  （1~2 行）
4. 专业技能        8~12 行，分「熟练 / 熟悉 / 了解」三档       （10 行）
5. 项目经历        2 个为佳：1 个主项目 + 1 个补充项目         （20~25 行）
6. 工作经历        有则写（公司/职位/时间/职责），无则删       （0~5 行）
7. 其他            证书 / 博客 / 开源 / 竞赛                  （2~3 行）
```

**版式建议**：单栏、10.5~11pt、不用花哨模板、PDF 导出、文件名 `姓名-Java后端-年限.pdf`。

## 三、两版简历模板

### 3.1 A 版：业务后端（投电商/交易/支付/SaaS）

```markdown
## 专业技能
- 熟练：Java 17、Spring Boot 3、Spring Cloud Alibaba、MyBatis-Plus
- 熟练：MySQL（索引/事务/MVCC/锁）、Redis（缓存/分布式锁）、RocketMQ
- 熟悉：分布式事务（Seata AT）、幂等设计、状态机、DDD 分层
- 熟悉：Docker / K8s / Jenkins、Prometheus 监控、JUnit5 + Mockito
- 了解：Spring AI、RAG 检索增强、Elasticsearch 混合检索

## 项目经历

### AI 智能客服平台（个人项目 / 12 模块微服务）        2026.07 - 至今
技术栈：Java 17 · Spring Boot 3.2 · Spring Cloud 2023 · MySQL · Redis · RocketMQ · ES · K8s

- **交易链路**：实现购物车 → 下单 → 支付 → 售后的完整闭环。下单用 Redisson 按用户加锁防重，
  锁外开启 Seata 全局事务；支付侧抽象支付宝/微信/银联/Mock 四渠道（策略 + 工厂），
  回调走 RocketMQ 事务消息保证「流水落库 ⇒ 订单状态必达」，并用「回调重试 + 主动查单 + 对账补偿」三层兜底。
- **一致性治理**：封装 `@Idempotent` 注解 + AOP + Redis SET NX 的去重组件；
  订单用 Spring StateMachine 收敛状态流转（待支付/已支付/已取消/售后中），非法迁移直接拒绝；
  支付成功事件用 `@TransactionalEventListener(AFTER_COMMIT)` 推送，事务回滚不误发通知。
- **网关治理**：按路由配置 Redis + Lua 分布式令牌桶（5 QPS/用户、突发 10），
  并实现最少连接负载均衡（按实例在途请求数分流），配合 Resilience4j 熔断与降级。
- **AI 能力**：基于 Spring AI 实现 RAG（查询改写 + 向量/BM25 混合召回 + RRF 融合 + Rerank + 引用溯源）；
  售后 Agent 用显式状态机编排工具，写操作需二次确认（Token + 摘要 + 超时），支持人工转接与全链路轨迹审计。

### （补充项目，可选）xxx
```

## 四、项目描述的四段式

每一段项目经历都按这个结构写，**不要写成功能清单**：

```text
背景（1 句）：为什么要做 / 解决什么问题
挑战（1~2 句）：难点是什么（一致性？性能？安全？）
方案（3~4 句）：你做了什么（技术 + 关键设计）
结果（1 句）：效果（有数据写数据，没数据写"验证了什么"）
```

**反例 vs 正例**：

| 反例 | 正例 |
|---|---|
| "使用 Redis 实现缓存，使用 RocketMQ 实现消息队列" | "支付回调与订单状态跨服务，用事务消息保证『流水落库 ⇒ 状态必达』，并用主动查单兜底回调丢失" |
| "使用 Spring Cloud 搭建微服务" | "按业务边界拆 12 个服务，服务间只经网关/Feign，common 不反向依赖业务模块" |
| "实现了 AI 对话功能" | "RAG 链路加 Rerank 与引用溯源，回答可定位到文档段落" |

## 五、本项目 STAR 拆解（4 个可直接用的故事）

> 每个故事都要能讲三层，第三层必须有「取舍或踩坑」。数字留空处等实测回填。

### 故事 1：网关限流与负载均衡

| 项 | 内容 |
|---|---|
| **S 背景** | 11 个服务共用一个网关，需要防止单用户打爆后端，也要避免请求集中到慢实例 |
| **T 任务** | 做「按用户维度」的分布式限流 + 更合理的负载均衡 |
| **A 行动** | Redis + Lua 令牌桶（5 QPS、突发 10），按 `X-User-Id`/IP 分桶；另实现最少连接 LB，按实例在途请求数分流；断路器按路由命名避免共享 |
| **R 结果** | 30 req/s 压测下理论放行 160/900、429 ≈ 82.2%（**待实测回填**） |
| **第三层** | 为什么不用固定窗口？窗口边界会双倍放行；为什么限流键选用户而不是全局？全局会让一个用户影响所有人 |

### 故事 2：交易一致性（最适合当主故事）

| 项 | 内容 |
|---|---|
| **S 背景** | 下单要同时扣库存、写订单、核销优惠券，跨 order/product 两个服务 |
| **T 任务** | 保证「要么全成功，要么全回滚」，且重复请求不能重复下单 |
| **A 行动** | Redisson 按用户加锁防重（锁在事务外）→ Seata AT 管跨服务事务 → 订单状态机收敛流转 → 支付成功用事务消息 → 回调丢失用主动查单 + 对账补偿 |
| **R 结果** | 重复下单被锁挡住、非法状态迁移被拒绝、回调丢失可自愈（**待补集成测试验证**） |
| **第三层** | 为什么锁在事务外？避免锁持有时间 = 事务时间，放大冲突；为什么不全链路 Seata？AT 对 MQ/第三方渠道无效，最终一致更现实 |

### 故事 3：Agent 编排（差异化）

| 项 | 内容 |
|---|---|
| **S 背景** | 售后场景要让模型「查订单、查规则、给建议、办业务」，但模型不能直接写库 |
| **T 任务** | 让 Agent 能办事，又不失控 |
| **A 行动** | 显式状态机限定每步可用工具；意图识别（LLM 结构化 + 规则兜底）；写操作二次确认（Token + 摘要 + 超时）；步数/超时上限；全链路轨迹审计；支持转人工 |
| **R 结果** | 未确认的写操作 100% 拒绝、每一步可回溯 |
| **第三层** | 为什么不用纯 ReAct？自由循环不可控、成本高、写操作无法审计；状态机的代价是灵活性，用「意图识别 + 工具注册表」补回来 |

### 故事 4：RAG 质量

| 项 | 内容 |
|---|---|
| **S 背景** | 纯向量召回对型号、错误码这类精确词不敏感 |
| **T 任务** | 提升召回与可解释性 |
| **A 行动** | 查询改写 + 向量/BM25 双路召回 + RRF 融合 + Rerank + 引用溯源；20 条 golden case 做评估 |
| **R 结果** | 回答带出处、可定位（**评测指标待跑**） |
| **第三层** | RRF 为什么比加权求和稳？它只用排名不用分数，避免两路分数量纲不一致 |

## 七、专业技能怎么写

### 7.1 三档的真实含义

| 用词 | 面试官的理解 | 你要能答到 |
|---|---|---|
| **熟练** | 用过 2 年以上、能独立排障 | 原理 + 踩坑 + 选型 |
| **熟悉** | 用过、知道原理 | 怎么用 + 为什么用 |
| **了解** | 看过、写过 demo | 概念 + 适用场景 |

### 7.2 写法规则

- **不超过 12 行**，每行一个技术域，不要一行堆 8 个名词；
- **同域只写最高频的 2~3 个**（如"MySQL 索引/事务/锁"），不要罗列所有中间件；
- **写版本号**（Spring Boot 3.2 / Java 17），能体现时效性；
- **不确定的不要写**——面试官专挑你不熟的问。

### 7.3 反面例子

```text
❌ 精通 Java、Python、Go、C++、JavaScript、Vue、React、Spring、Spring Cloud、
   MySQL、Oracle、Redis、MongoDB、Kafka、RocketMQ、RabbitMQ、ES、K8s、Docker...
```

问题：① 没人信；② 每个词都会被追问；③ 没有层次。

## 九、包装陷阱（踩了会翻车）

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 把个人项目写成"某公司项目" | 背调/社保/离职证明一问就穿，可能被拉黑 | 写"个人项目"，放在项目经历，不放在工作经历 |
| 写"主导/负责"但答不出细节 | 二面必挂 | 用"设计并实现""独立完成"，然后准备三层 |
| 数字造假（QPS/用户量） | 追问一句就崩 | 没有就不写，或写"验证了机制正确性" |
| 技能堆砌 20 个名词 | 面试官挑最弱的问 | 8~12 行，分三档 |
| 项目描述写成功能清单 | 看不出你的思考 | 按"背景-挑战-方案-结果"写 |
| 一份简历投所有岗位 | 匹配度低 | A/B 两版，按 JD 选 |

## 十、投递前自检清单

- [ ] 一页（最多一页半），PDF，命名规范
- [ ] 项目占 60% 篇幅，且是"背景-挑战-方案-结果"结构
- [ ] 每个技术名词都能讲 3 分钟（随机抽 5 个自测）
- [ ] 所有数字都有来源（模块数/代码量/测试数可写；QPS/用户量没实测就不写）
- [ ] 没有"精通"超过 3 个
- [ ] 没有把个人项目写成公司项目
- [ ] 联系方式、GitHub 链接可点开
- [ ] 让一个不懂技术的朋友读一遍，能说出"你做了什么"
