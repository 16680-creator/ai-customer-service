# 04 - 系统设计八题

> **目标**：设计题不是背答案，是背**框架**。面试官要听的是"你怎么想"，不是"你背过"。
> **前提**：先看 [01 岗位地图](01-岗位地图与JD拆解.md) 确认目标档位，[docs/00 架构图](../../docs/00-项目总览与架构图.md) 熟悉本项目全景。
> **纪律**：八题里 **订单 / 支付对账 / 限流** 是本项目真实落地、可以讲到代码的；**短链 / Feed / 排行榜** 本项目未落地，只讲方案并明确说"没做过"。

## 一、先背框架：五步答题法（25~35 分钟）

```text
第 1 步 澄清需求（3 分钟）    功能边界、规模、一致性要求、读写比例
第 2 步 容量估算（3 分钟）    QPS、存储、带宽、连接数（数量级对即可）
第 3 步 高层设计（8 分钟）    画组件图：接入层 → 应用层 → 存储层 → 异步层
第 4 步 深挖 1~2 个点（10 分钟） 存储选型 / 一致性 / 热点 / 故障
第 5 步 收尾（3 分钟）        瓶颈、监控、演进、取舍
```

### 1.1 第 1 步：澄清什么（不问清楚就开画 = 扣分）

| 维度 | 必问 | 为什么 |
|---|---|---|
| 规模 | DAU、峰值 QPS、读写比 | 决定要不要分片/缓存 |
| 一致性 | 强一致 / 最终一致 / 可容忍丢失 | 决定事务与消息方案 |
| 时延 | P99 目标 | 决定同步/异步 |
| 边界 | 要不要管理后台、要不要多端 | 防止画大了收不住 |
| 已有限制 | 团队技术栈、预算 | 决定选型 |

> 话术："我先确认几个前提，如果和您想的不一样随时打断我。"

### 1.2 第 3 步：万能分层图

```text
客户端 → CDN/静态 → 接入层（网关/LB/限流/鉴权）
        → 应用层（无状态服务，水平扩容）
        → 缓存层（Redis，抗热点）
        → 存储层（MySQL 分库分表 / ES / 对象存储）
        → 异步层（MQ，削峰/解耦/最终一致）
        → 可观测（日志/指标/追踪）
```

### 1.3 第 4 步：深挖点的选择

**只深挖 1~2 个**，选你最有把握、且与题目最相关的：

- 有库存/余额 → 一致性 + 幂等
- 有热点 → 缓存 + 分片
- 有长连接 → 连接管理 + 消息可靠性
- 有第三方 → 回调 + 对账 + 补偿

## 三、八道题

### 题 1：秒杀 / 抢购

**澄清**：库存量级？参与用户数？是否要求公平（先到先得）？能否接受"排队中"？

**30 秒骨架**：

```text
前端：按钮置灰 + 验证码 + 静态化
接入：网关限流（按用户/IP/活动）+ 黑名单
应用：Redis 预扣库存（Lua 原子）→ 扣减成功才发 MQ
异步：MQ 削峰 → 订单服务真正落库
兜底：超时未支付回补库存 + 对账 + 幂等
```

**关键设计**：

| 问题 | 解法 |
|---|---|
| 超卖 | Redis Lua 原子扣减 + DB 乐观锁/唯一约束兜底 |
| 重复下单 | 用户+活动维度幂等键，Redis SETNX |
| 热点 key | 库存分桶（100 份库存拆 10 个 key） |
| 刷子 | 风控 + 限流 + 验证码 |

**本项目锚点**：

- 网关按用户限流：`ai-cs-gateway/.../RouteConfig.java`（`RedisRateLimiter` 5/s、突发 10）
- 下单防重：`OrderCreateLockService`（Redisson，`waitTime=0` 快速失败）
- 库存扣减：`ProductClient.deductStock`（Feign + Seata XID）
- 超时回补：`order-timeout-topic` 延迟消息 → `cancelExpiredOrder` → `restoreStock`

**追问**：

- "Redis 扣减成功但 MQ 发失败怎么办？" → 本地消息表/事务消息，或 Redis 扣减与发消息用 Lua 合并（不推荐），最稳是"Redis 只做预筛，DB 扣减为准 + 对账"。
- "Redis 挂了？" → 降级到 DB 乐观锁（性能差但正确），或直接拒绝（保正确性）。

**陷阱**：只讲 Redis 扣减，不讲回补与对账——库存会"凭空消失"。

### 题 2：短链系统

**澄清**：QPS？存储几年？是否允许自定义短码？跳转 301 还是 302？

**30 秒骨架**：

```text
写：长链 → 发号器（雪花/号段）→ Base62 → 存 MySQL（短码唯一索引）→ 返回
读：短码 → 布隆过滤器挡不存在 → Redis 缓存 → 回源 MySQL → 302 跳转
统计：异步埋点（点击流）→ OLAP
```

**关键设计**：

| 点 | 方案 |
|---|---|
| 短码唯一 | 发号器保证全局唯一；DB 唯一索引兜底 |
| 防遍历 | 短码加随机盐/双射混淆；或布隆过滤 |
| 缓存 | 短码 → 长链，Redis String，TTL + 懒加载 |
| 301 vs 302 | 301 省流量但不可统计；302 可统计（推荐） |

**本项目锚点**：

- 分布式 ID：[03/04 分布式 ID 规范](../../learning-docs/03-数据库与ORM/04-分布式ID规范.md)（雪花/号段，时钟回拨兜底）
- Redis 缓存：[04/01 Redis 缓存实战](../../learning-docs/04-中间件/01-Redis缓存实战.md)（穿透/击穿/雪崩）
- ⚠️ 短链本身**本项目未实现**，只讲方案与组件复用

**追问**："发号器挂了怎么办？" → 号段模式本地缓存一批，宕机只影响未用完的号段。

**陷阱**：说"用 MD5 取前 6 位"——会有碰撞，且不可逆推。

### 题 3：IM / 客服会话

**澄清**：单聊/群聊？在线/离线？要不要已读、撤回、多端同步？消息量级？

**30 秒骨架**：

```text
连接层：WebSocket 网关（有状态），会话路由表（userId → 连接节点）
消息层：消息 ID 单调递增（雪花/会话内 seq）→ 存储 → 推送
离线：未读表 + 推送（APNs/厂商通道）
多端：每个端一个 session，按端同步
可靠性：ACK + 重发 + 去重（msgId 幂等）
```

**关键设计**：

| 问题 | 解法 |
|---|---|
| 不丢 | 先落库再推送；客户端 ACK 后删离线 |
| 不重 | 客户端按 msgId 去重；服务端幂等 |
| 不乱序 | 会话内 seq 单调；客户端按 seq 排序 |
| 水平扩展 | 连接网关 + 路由表（Redis 存 userId→node） |

**本项目锚点**：

- WebSocket 推送：[NotifyController](../../ai-cs-notify/src/main/java/com/aics/notify/controller/NotifyController.java)（`/send`、`/broadcast`、`/online`、`/handoff`）
- STOMP 用户目的地：[02/11 STOMP 实时通知](../../learning-docs/02-Spring微服务/11-STOMP实时通知与用户目的地.md)
- 会话/消息表：`ai-cs-message`；历史归档：MongoDB（`MongoChatHistoryArchiveService`）
- SSE 流式：`ChatController` 的 `stream/sse`（单向推送）
- ⚠️ 完整 IM（多端同步、已读、撤回）**未落地**，客服场景只做"推送 + 工单"

**追问**："百万连接怎么扛？" → 连接网关分片 + 每节点 5~10 万连接 + 心跳 + 路由表。

**陷阱**：把 WebSocket 说成"无状态"——连接是有状态的，扩容要考虑连接迁移。

### 题 4：Feed / 朋友圈

**澄清**：关注关系（单向/双向）？刷新实时性？大 V 粉丝量？

**30 秒骨架**：

```text
推模式（写扩散）：发帖 → 写入所有粉丝的收件箱 → 读时直接取
拉模式（读扩散）：发帖只写自己发件箱 → 读时聚合关注列表
推拉结合：普通用户推、大 V 拉（读时合并）
存储：Redis ZSet 存 timeline（score=时间戳），MySQL 存内容
```

**关键设计**：

| 场景 | 选择 |
|---|---|
| 粉丝少（< 1000） | 推，读快 |
| 大 V（> 10 万） | 拉，避免写放大 |
| 冷用户 | 拉，减少存储 |

**本项目锚点**：

- ⚠️ **未落地**。可类比的是"知识库列表 + ES 检索"（[04/03 ES](../../learning-docs/04-中间件/03-Elasticsearch搜索引擎.md)）和 Redis ZSet（[04/01](../../learning-docs/04-中间件/01-Redis缓存实战.md)）
- 面试时明说："这个场景我没做过，按推拉结合讲思路"

**追问**："取关/删帖怎么清理 timeline？" → 读时过滤 + 异步清理。

**陷阱**：上来就说"用 Redis ZSet 存所有粉丝 timeline"——大 V 一发帖就是百万次写。

### 题 5：排行榜

**澄清**：实时性（秒级/小时级）？维度（日/周/总榜）？用户量？要不要同分排序？

**30 秒骨架**：

```text
实时榜：Redis ZSet（member=用户, score=分数）→ ZREVRANGE 分页
同分：score 拼接时间戳（score * 1e10 + (MAX_TS - ts)）保证稳定排序
周期榜：按周期建 key（rank:2026-10-18），定时任务归档
海量：按业务分片（如按城市/品类），查询时合并
```

**关键设计**：

| 点 | 方案 |
|---|---|
| 分页 | `ZREVRANGE start stop`，深分页限制 |
| 分数更新 | `ZINCRBY` 原子 |
| 持久化 | 定时快照到 MySQL，Redis 挂了可恢复 |
| 防刷 | 分数变更走业务校验 + 限流 |

**本项目锚点**：

- Redis：[04/01](../../learning-docs/04-中间件/01-Redis缓存实战.md)
- 定时任务：XXL-Job（[07/05](../../learning-docs/07-运维部署/05-XXL-Job分布式调度.md)）
- ⚠️ 榜单**未落地**，商品热销榜可作为练手最小实现

**追问**："1 亿用户的总榜怎么存？" → 只存 Top N + 分片榜，全量榜离线算。

**陷阱**：忽略同分排序，导致分页重复/漏数据。

### 题 6：订单系统（本项目主战场，必须讲最深）

**澄清**：下单峰值？库存扣减方式？支付方式？要不要超时取消/售后？

**30 秒骨架**：

```text
下单：校验购物车 → 分布式锁防重 → 事务（扣库存/写订单/核销券）→ 发延迟消息
支付：创建支付单 → 渠道下单 → 回调验签 → 事务消息 → 订单状态机 → 通知
兜底：超时取消回补库存、回调丢失主动查单、对账补偿
```

**关键设计**（每条都能落到代码）：

| 设计点 | 为什么 | 本项目锚点 |
|---|---|---|
| 锁在事务外 | 锁持有时间 ≠ 事务时间，减少冲突 | `OrderServiceImpl.createOrder` → `OrderCreateLockService.withCreateLock` |
| 事务边界独立 Bean | 避免自调用绕过代理 | `OrderCreateTxService`（2026-10 拆出，见 [docs/28 C1](../../docs/28-故障案例库.md)） |
| 状态机唯一入口 | 防止非法状态迁移 | `OrderStateMachineConfig` / `OrderStateTransitionService` |
| 幂等确认 | 回调可能重复 | `confirmPay` 已支付直接返回 |
| 事件 AFTER_COMMIT | 事务回滚不能发通知 | `OrderPaidEventListener` |
| 超时取消 | 未支付订单占库存 | 延迟消息 level 16（约 30min）→ `cancelExpiredOrder` |
| 库存回补 | 取消/退款要还库存 | `productClient.restoreStock` |

**追问**：

- "重复下单怎么防？" → 用户维度 Redisson 锁 + 幂等键（客户端 token）。
- "支付成功但订单没改？" → 事务消息 + 消费重试 + `syncByQuery` 主动查单 + 对账。
- "超卖？" → DB 原子扣减（`stock >= n`）+ 失败回滚；Redis 预扣只做前置。
- "大促流量怎么办？" → 网关限流 + MQ 削峰 + 库存分桶 + 异步下单。

**陷阱**：只讲"用了 Seata"，讲不出"为什么锁在事务外""消息不是 Seata 资源怎么办"。

### 题 7：支付与对账

**澄清**：接几个渠道？T+1 还是实时？差错怎么处理？退款要不要？

**30 秒骨架**：

```text
支付：统一下单（渠道策略）→ 返回支付参数
回调：验签 → 幂等落库 → 事务消息通知订单
兜底三层：渠道重试 → 主动查单 → 对账补偿
对账：渠道账单 vs 本地流水，按 orderNo 比对，处理单边/金额不一致
```

**关键设计**：

| 问题 | 解法 | 锚点 |
|---|---|---|
| 多渠道 | 策略 + 工厂 | `PayChannelFactory`（支付宝/微信/银联/Mock） |
| 回调丢失 | 主动查单 | `PayNotifyService.syncByQuery` |
| 回调重复 | 幂等（流水状态 + 唯一键） | `PayTransactionService.markSuccess` |
| 消息必达 | 事务消息 | `PaySuccessMessageProducer` + `PaySuccessTransactionListener` |
| 差错 | 对账 + 补偿 | `PayCompensationServiceImpl.compensate()`（返回 `querySynced`、`diffs`） |
| 退款 | 两段迁移 | `refundConfirm`：PAID→REFUNDING→REFUNDED |

**追问**：

- "渠道回调验签怎么做？" → 渠道各自的签名算法，统一封装在 `PayChannel.parseNotify`。
- "对账发现'支付成功但订单未支付'怎么办？" → 以渠道为准补单 + 告警 + 人工复核。
- "退款重复请求？" → 退款单号幂等 + 状态机。

**陷阱**：把"对账"说成"定时跑个 SQL"——要讲差错分类（长款/短款/金额不一致）和处理动作。

### 题 8：分布式限流

**澄清**：限流维度（全局/用户/IP/接口）？集群还是单机？允不允许突发？

**30 秒骨架**：

```text
算法：计数器（临界问题）→ 滑动窗口（平滑）→ 令牌桶（允许突发）→ 漏桶（恒定速率）
单机：Guava/Sentinel 本地
集群：Redis + Lua（原子扣减令牌）或网关 RedisRateLimiter
分层：网关边缘限流 + 应用内限流 + 下游保护
```

**关键设计**：

| 点 | 方案 | 锚点 |
|---|---|---|
| 令牌桶参数 | 5 QPS、桶容量 10 | `ai-cs-gateway/application.yml:47-49` |
| 按用户分桶 | KeyResolver = `X-User-Id`/IP | `RouteConfig` |
| 多实例共享 | Redis + Lua | `RedisRateLimiter` |
| 兜底 | Redis 不可用切本地滑动窗口 | `RateLimitFilter`（`enabled=false` 可切回） |
| 应用内 | Sentinel 注解 | `ChatController` 的 `@SentinelResource` |

**追问**：

- "为什么用令牌桶不用固定窗口？" → 固定窗口在边界会双倍放行。
- "Redis 挂了限流失效怎么办？" → 本地限流兜底 + 快速失败；不能"限流失效=全放行"。
- "限流键怎么选？" → 用户维度防单用户刷；IP 维度防代理池；接口维度保护下游。

**陷阱**：只说"用了 Sentinel"，讲不出算法和参数怎么定。

## 五、容量估算速查

### 5.1 常用公式

```text
平均 QPS = DAU × 人均请求数 / 86400
峰值 QPS ≈ 平均 QPS × 2~5（按业务定）
存储 = 条数 × 单条大小 × 副本数 × 增长系数
带宽 = QPS × 平均响应大小
连接数 = 在线用户数 × 每用户连接数
```

### 5.2 算例（面试可直接说）

```text
假设：1000 万注册用户，DAU 100 万，人均 10 次请求/天
平均 QPS = 1,000,000 × 10 / 86400 ≈ 116
峰值 QPS ≈ 116 × 3 ≈ 350

订单：1 亿条 × 1KB ≈ 100GB（单副本），3 年增长 ×2 → 200GB
按用户分 16 库 × 每库 16 表，单表约 39 万行（完全可控）

消息：100 万日活 × 20 条/天 = 2000 万条/天 ≈ 231 条/秒（平均）
```

### 5.3 估算的三种错误

| 错误 | 正确做法 |
|---|---|
| 纠结精确值 | 数量级对即可，说明假设 |
| 只算平均不算峰值 | 一定乘峰值系数 |
| 忘了副本/索引 | 存储 × 2~3 |

| 容量估算 | 10% | 数量级 + 假设清晰 | 完全不算 |
| 数据模型 | 15% | 表结构 + 索引 + 分片键 | 只画框不画表 |
| 扩展性 | 15% | 无状态、水平扩容、分片 | 单机思维 |
| 一致性 | 20% | 事务/消息/幂等/对账成体系 | 一句"用事务"带过 |
| 可运维 | 15% | 监控、降级、灰度、回滚 | 从不提故障 |
| 表达与取舍 | 10% | 说清"为什么不用另一个" | 只报菜名 |

> 一句话：**设计题考的是"边界与取舍"，不是"组件清单"**。

---

## 七、常见扣分点（自查）

1. 不问需求，直接画架构图。
2. 组件堆砌："Kafka + Redis + ES + HBase"全上，说不出为什么。
3. 没有数据模型，只有框。
4. 不提失败场景（超时、重复、丢失、乱序）。
5. 不讲容量，导致方案明显不匹配规模。
6. 被追问就改口，前后矛盾。
7. 把"最终一致"说成"强一致"。

## 八、练习方法

### 8.1 白板 25 分钟法

```text
0-3 分钟：写澄清问题（至少 4 个）
3-6 分钟：写估算（QPS/存储）
6-14 分钟：画三层图 + 表结构
14-22 分钟：深挖一个点（挑最有把握的）
22-25 分钟：讲瓶颈、监控、演进
```

### 8.2 三遍法

| 遍数 | 目标 |
|---|---|
| 第 1 遍 | 不看答案，限时 25 分钟，录音 |
| 第 2 遍 | 对照本文的"关键设计"，补漏 |
| 第 3 遍 | 只讲 3 分钟版本，练"电梯陈述" |

拿 **订单** 和 **支付对账** 两题，对着 [docs/00 的时序图](../../docs/00-项目总览与架构图.md#五核心链路一下单--支付--回调--对账) 讲一遍，
要求每个箭头都能说出"为什么这么设计、不这样会怎样"。
