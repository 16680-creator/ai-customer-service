## 二、选型的五个判据

面试被问"为什么选 X"，按这五条答，比背参数强：

| 判据 | 要问的问题 | 反例 |
|---|---|---|
| **团队** | 团队会不会用、招不招得到人 | 选了个没人会的冷门框架 |
| **场景** | 数据量、并发、一致性要求匹配吗 | 单体项目上 Service Mesh |
| **运维** | 多一个组件就多一套监控/备份/升级 | 小团队自建 ES 集群 |
| **生态** | 社区活跃度、文档、周边工具 | 选已停止维护的库 |
| **成本** | 机器成本 + 人力成本 + 迁移成本 | 为了"技术先进"重写核心链路 |

> 面试话术："我们选 X 主要是三点：团队熟、场景匹配、运维成本可控。如果换成 Y，需要额外解决 A/B 两个问题。"

## 三、生产细节 12 条（"看起来一样，实际不一样"）

### 3.1 版本与兼容

1. **Spring Boot 3 = jakarta.***：从 `javax.servlet` 迁到 `jakarta.servlet`，老依赖（如旧版 Swagger、旧版 MyBatis 插件）可能不兼容。
2. **JDK 17 的强封装**：反射改 `private` 字段会被拒，`--add-opens` 才能放开；很多老框架在这里挂。
3. **MySQL 5.7 → 8.0**：默认字符集变 `utf8mb4`、`ONLY_FULL_GROUP_BY` 默认开启、驱动类名变 `com.mysql.cj.jdbc.Driver`。

### 3.2 配置与运行环境

4. **时区**：容器默认 UTC，MySQL 连接串要 `serverTimezone=Asia/Shanghai`，否则时间差 8 小时。
5. **字符集**：库/表/连接三处都要 `utf8mb4`，否则 emoji 存不进去。
6. **配置优先级**：命令行 > 环境变量 > Nacos > 本地 `application.yml`。排查"配置没生效"先看这条链。
7. **连接池 ≠ 数据库连接数**：每个服务 Hikari 10，10 个服务就是 100，超过 MySQL `max_connections` 会拒连。

### 3.3 中间件使用边界

8. **Redis Cluster 的 key 必须在同一 slot**：`MGET`、事务、Lua 多 key 操作会报 `CROSSSLOT`；用 hash tag `{user:1}:name` 强制同槽。
9. **RocketMQ 顺序消息**：按业务键选队列 + 单线程消费；消费并行度一开就失去顺序。
10. **ES 深分页**：`from + size` 默认上限 10000；深分页用 `search_after` 或滚动。
11. **Feign 默认不重试，Ribbon 会重试**：重试必须配幂等，否则重复下单；超时要小于上游超时。

### 3.4 部署与发布

12. **K8s 探针配错 = 无限重启**：`liveness` 太激进会杀掉正在启动的 JVM；启动慢的服务用 `startupProbe`。
13. **优雅停机**：`server.shutdown=graceful` + `preStop sleep` + 就绪探针摘流，三者缺一都会丢请求。

## 四、被高估的技术（生产里没那么多）

| 技术 | 真实情况 |
|---|---|
| **GraphQL** | BFF 场景有价值，但多数团队 REST 够用；缓存/限流/权限更复杂 |
| **Service Mesh** | 解决多语言治理，小团队引入 Istio 的运维成本 > 收益 |
| **Serverless** | 适合事件/定时/轻量 API；核心交易链路冷启动和可观测性仍是问题 |
| **微服务** | 团队 < 10 人时，模块化单体往往更划算 |
| **多语言混布** | 除非有明确性能/生态理由，否则维护成本翻倍 |
| **"中台"** | 组织能力问题，不是技术选型问题 |

> 面试时敢说"这个场景我们**不用** X"，比列一堆技术更能体现判断力。

## 五、上线前自检清单（15 项）

- [ ] 数据库：连接池、慢查询日志、索引、备份策略
- [ ] 缓存：TTL、穿透/击穿/雪崩防护、热 key 预案
- [ ] MQ：重试次数、死信队列、消费幂等、堆积告警
- [ ] 配置：生产密钥不进代码、配置中心有兜底
- [ ] 日志：级别、脱敏、采集、磁盘上限
- [ ] 监控：QPS/错误率/P99/线程池/连接池/GC
- [ ] 告警：阈值、通知渠道、值班人
- [ ] 限流：网关 + 应用两层，阈值有依据
- [ ] 熔断降级：下游挂了返回什么
- [ ] 发布：滚动更新、就绪探针、优雅停机、回滚方案
- [ ] 数据：初始化脚本、变更脚本、回滚脚本
- [ ] 安全：鉴权、越权、上传、注入
- [ ] 容量：压测基线、扩容预案
- [ ] 依赖：第三方超时/重试/证书有效期
- [ ] 文档：部署手册、排障手册、联系人

## 六、AI 时代怎么学这套东西

| 层级 | AI 能帮你什么 | 你必须自己有什么 |
|---|---|---|
| L1 选型 | 列候选、给对比表 | **判断哪个匹配你的场景** |
| L2 落地 | 生成配置/样板代码 | 能改、能调试、知道边界 |
| L3 生产 | 给"可能原因清单" | **看栈、看 GC、看锁、看网络的能力** |

**建议**：

1. 每学一个组件，问三个问题：它解决什么问题？它怎么坏？坏了看什么？
2. 每个组件准备一条"最小复现"命令（如 Redis `--bigkeys`、MySQL `EXPLAIN`）。
3. 别背参数，背**判据**（见第二节）。

## 七、面试怎么讲选型（模板）

```text
背景：我们的场景是 ___（QPS/数据量/一致性要求）。
候选：A、B、C。
排除：B 因为 ___（运维成本/团队不熟/社区不活跃）。
选择：A，因为它 ___（匹配场景 + 团队能维护）。
代价：选了 A 要接受 ___（比如最终一致/额外的运维组件）。
如果重来：数据量再大 10 倍，我会换 ___。
```

> 最后一句"如果重来"是加分项——说明你想过边界，不是照抄。
