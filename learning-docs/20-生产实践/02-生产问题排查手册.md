# 02 - 生产问题排查手册

> **目标**：线上出问题时，能在 5 分钟内找到"从哪查"，30 分钟内定位方向。
> **原则**：**先止损，再定位**（回滚 > 降级 > 限流 > 扩容 > 查根因）。
> **纪律**：所有命令都给出**判读标准**；同一现象按"发生概率"列根因，不要一上来就猜最罕见的。
> **警告**：生产操作前先确认影响面；`jmap`/`dump` 会 STW，高峰慎用。

---

## 〇、通用排查框架

### 0.1 三组黄金指标

| 维度 | 看什么 | 工具 |
|---|---|---|
| **RED**（服务） | Rate 请求量、Errors 错误率、Duration 延迟 | Prometheus / 网关日志 |
| **USE**（资源） | Utilization 使用率、Saturation 饱和度、Errors 错误 | top / iostat / vmstat / node_exporter |
| **四黄金信号**（Google SRE） | 延迟、流量、错误、饱和度 | 同上 |

### 0.2 排查顺序（不要跳步）

```text
1. 影响面：多少用户/哪些接口/是否资损 → 决定止损优先级
2. 止损：回滚最近变更 → 降级非核心 → 限流 → 扩容
3. 定位：指标（哪台/哪个接口）→ 日志（错误栈）→ 链路（traceId）→ 资源（CPU/内存/IO/网络）
4. 修复：改配置/发版/切流
5. 复盘：根因 + 改进项（见 13/06 RCA）
```

### 0.3 先问三个问题

1. **最近有没有变更？**（发版、配置、SQL、扩容）——80% 的故障与变更相关。
2. **是单点还是全局？**（单台 → 机器/实例问题；全局 → 依赖或流量）。
3. **是突然还是逐渐？**（突然 → 变更/依赖挂；逐渐 → 泄漏/容量）。

## 一、CPU 飙高

**现象**：监控 CPU 100%，接口变慢，告警。

**30 秒判断**：是用户态高还是内核态高？是单核满还是全核满？

```bash
top -Hp <pid>                 # 找最耗 CPU 的线程 TID
printf '%x\n' <tid>           # 转十六进制
jstack <pid> | grep -A 30 "nid=0x<hex>"   # 对应线程栈
# 或
arthas: thread -n 3           # 直接看最忙的 3 个线程
```

**常见根因（按概率）**：

| 根因 | 特征 | 处置 |
|---|---|---|
| 死循环 / 正则回溯 | 单线程 100%，栈固定在同一方法 | 修代码/限制正则 |
| GC 线程忙 | `jstat` 看 GC 时间占比高 | 查内存/调堆 |
| 线程数过多 | `jstack | grep -c 'java.lang.Thread.State'` 很大 | 查线程池/连接泄漏 |
| 加密/序列化/JSON 大对象 | 栈在 `ObjectMapper`/`Cipher` | 减少对象大小/换序列化 |
| 内核态高（sy） | `top` 的 sy 高 | 查系统调用/网络（`strace -c`） |

**预防**：接口耗时监控 + 线程池隔离 + 单机压测。

## 二、内存高 / OOM

**现象**：内存持续上涨、频繁 Full GC、`OutOfMemoryError`、容器 OOMKilled。

**30 秒判断**：堆内还是堆外？是泄漏还是不够用？

```bash
jcmd <pid> GC.heap_info                     # 堆使用情况
jstat -gcutil <pid> 1000 10                 # 各区使用率与 GC 次数
jmap -histo:live <pid> | head -30           # 存活对象 Top
jcmd <pid> GC.heap_dump /tmp/heap.hprof     # 堆转储（会 STW，慎用）
```

**常见根因**：

| 类型 | 特征 | 处置 |
|---|---|---|
| 集合无界增长 | `HashMap`/`List` 占大头 | 加容量上限/TTL |
| 缓存未设上限 | 本地缓存无限增长 | Caffeine `maximumSize` |
| ThreadLocal 泄漏 | 线程池线程持有大对象 | `finally remove()` |
| 连接/流未关闭 | `SocketInputStream` 多 | try-with-resources |
| 堆外（Netty/直接内存） | 堆正常但 RSS 高 | `-XX:MaxDirectMemorySize` + `NativeMemoryTracking` |
| 容器 limit < 堆 | OOMKilled（exit 137） | 堆 ≤ limit × 70% |

**堆外排查**：

```bash
java -XX:NativeMemoryTracking=summary ...
jcmd <pid> VM.native_memory summary
```

**预防**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`，并确保 dump 目录有空间。

## 三、GC 频繁 / 停顿

**现象**：接口 P99 毛刺、`Full GC` 频繁、`GC overhead limit exceeded`。

```bash
jstat -gcutil <pid> 1000
# JDK 9+ 开 GC 日志
-Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags:filecount=5,filesize=50m
```

**判读**：

- `YGC` 频繁但 `YGCT` 小 → 新生代偏小或对象晋升快。
- `FGC` 增长、`FGCT` 高 → 老年代压力大/内存泄漏/大对象。
- G1 出现 `Humongous` 分配 → 大对象（> region/2），考虑拆分。

**处置**：先定位是"泄漏"还是"不够"；泄漏修代码，不够调堆/换收集器（G1/ZGC）。

## 四、接口变慢（全链路）

**现象**：某个接口 P99 上升，或整体变慢。

**排查顺序**（从外到内）：

```text
1. 网关：是否限流/熔断触发？上游是否超时？
2. 应用：线程池是否满？连接池是否等待？GC 是否停顿？
3. DB：慢查询？锁等待？主从延迟？
4. 缓存：命中率下降？热 key？
5. 下游：Feign/HTTP 超时？第三方限流？
6. 网络：重传？DNS？TLS 握手？
```

**关键指标**：

| 指标 | 看什么 |
|---|---|
| `http_req_duration` P99 | 整体延迟 |
| 线程池 `activeCount` / `queueSize` | 是否排队 |
| Hikari `pending` / `active` | 连接等待 |
| Redis 命中率 | 是否回源 |
| DB `Slow_queries` | 慢 SQL |

**一条经验**：**先看"是不是我们变慢了"，再看"是不是下游变慢了"**。用 traceId 串起来最快。

## 五、线程池满 / 拒绝

**现象**：日志出现 `RejectedExecutionException`，接口超时但 CPU 不高。

```bash
jstack <pid> | grep -A 5 "pool-" | head -50
arthas: thread -n 3
```

**常见根因**：

| 根因 | 处置 |
|---|---|
| 下游慢导致线程堆积 | 加超时 + 熔断 + 隔离 |
| 队列无界 | 改有界队列 + 拒绝策略 |
| 核心线程太小 | 按 IO/CPU 类型调 |
| 任务里有阻塞（DB/HTTP） | 异步化或拆分线程池 |

**拒绝策略选择**：核心链路用 `CallerRunsPolicy`（背压）或自定义"降级返回"，不要用 `DiscardPolicy` 静默丢。

## 六、数据库连接池耗尽

**现象**：`Connection is not available, request timed out after 30000ms`。

```bash
# 应用侧
HikariPool metrics: hikaricp_connections_pending / active / idle
# 数据库侧
SHOW STATUS LIKE 'Threads_connected';
SHOW PROCESSLIST;
```

**根因**：

1. 慢 SQL 占住连接（最常见）→ 查慢查询。
2. 事务里做远程调用（Feign/HTTP）→ 事务拉长。
3. 连接泄漏（未关闭）→ 查代码 try-with-resources。
4. 池子太小 / DB `max_connections` 不够。

**处置**：先杀长事务/慢查询；再改代码；最后调池子（池子不是越大越好）。

## 七、数据库问题

### 7.1 慢查询

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
EXPLAIN SELECT ...;              -- 看 type/key/rows/Extra
SHOW PROCESSLIST;                -- 看正在执行的 SQL
```

**判读**：`type=ALL`（全表）、`Using filesort`、`Using temporary` 是重点；`rows` 估算大要加索引。

### 7.2 死锁

```sql
SHOW ENGINE INNODB STATUS;       -- LATEST DETECTED DEADLOCK
SELECT * FROM information_schema.innodb_trx;
```

**处置**：固定加锁顺序、缩小事务、补索引（减少间隙锁）、`innodb_lock_wait_timeout` 兜底。

### 7.3 主从延迟

```sql
SHOW SLAVE STATUS\G              -- Seconds_Behind_Master / Slave_SQL_Running
```

**根因**：大事务、无主键表、从库压力大、单线程回放（MySQL 8 可开并行复制）。

### 7.4 大事务

**特征**：`trx_rows_modified` 很大、undo 暴涨、主从延迟。

**处置**：拆批（每批 500~1000）、避免事务里调远程、`IN` 大列表拆分。

## 八、缓存问题

| 现象 | 根因 | 处置 |
|---|---|---|
| 大量请求打到 DB | **穿透**（查不存在的数据） | 布隆过滤器 / 空值缓存 |
| 某个 key 过期瞬间 DB 崩 | **击穿**（热点 key 失效） | 互斥锁 / 逻辑过期 |
| 大批 key 同时过期 | **雪崩** | TTL 加随机值 / 多级缓存 |
| 单 key QPS 极高 | **热 key** | 本地缓存 / key 拆分 / 读写分离 |
| 单 key 内存过大 | **大 key** | 拆分 / 压缩 / 换结构 |
| 数据不一致 | 更新顺序/并发 | 先更 DB 再删缓存 + 延迟双删 |

**命令**：

```bash
redis-cli --bigkeys                 # 大 key
redis-cli --hotkeys                 # 热 key（需 LFU 策略）
redis-cli MEMORY USAGE <key>
redis-cli INFO memory / stats
redis-cli SLOWLOG GET 10
redis-cli LATENCY DOCTOR
```

## 九、消息队列问题

### 9.1 堆积

```bash
# RocketMQ
mqadmin consumerProgress -g <group> -n <namesrv>
mqadmin topicStatus -t <topic> -n <namesrv>
# Kafka
kafka-consumer-groups.sh --describe --group <group> --bootstrap-server ...
```

**根因**：消费慢（DB/下游）、消费线程少、消息突增、死循环重试。

**处置**：扩消费者（注意顺序消息不能随便扩）、优化消费逻辑、临时跳过非核心消息。

### 9.2 重复消费

**处置**：消费幂等（唯一键/状态机/去重表）；不要依赖"消息只投一次"。

### 9.3 消息丢失

**排查链**：生产端（发送失败？事务消息回滚？）→ Broker（刷盘？）→ 消费端（异常吞了？）。

### 9.4 顺序错乱

**原因**：多队列/多线程消费。**处置**：按业务键选队列 + 单线程消费。

### 9.5 死信

`%DLQ%<consumerGroup>`；查死信原因（反序列化/业务异常/超时），修复后重投。

## 十、网络问题

| 现象 | 命令 | 根因 |
|---|---|---|
| 大量 TIME_WAIT | `ss -tan state time-wait \| wc -l` | 短连接多；开 `tcp_tw_reuse`、用长连接/连接池 |
| 大量 CLOSE_WAIT | `ss -tan state close-wait` | **应用没关连接**（代码问题） |
| 连接被拒 | `curl -v` / `telnet host port` | 服务没起/端口错/防火墙 |
| 偶发超时 | `mtr` / `tcpdump -i any port 8080 -w a.pcap` | 丢包/重传/DNS |
| TLS 握手失败 | `openssl s_client -connect host:443` | 证书过期/链不全/协议不匹配 |
| DNS 慢 | `dig` / `nslookup` | 解析超时；本地缓存 |

**排查原则**：先用 `curl -w` 拆解耗时（DNS/TCP/TLS/TTFB），再决定抓包还是查应用。

```bash
curl -o /dev/null -s -w "dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n" https://example.com
```

## 十一、发布与容器问题

| 现象 | 排查 | 常见原因 |
|---|---|---|
| Pod `CrashLoopBackOff` | `kubectl describe pod` / `kubectl logs --previous` | 启动异常、探针失败、OOMKilled |
| `OOMKilled`（exit 137） | `kubectl describe pod` 看 Last State | 堆 > limit、堆外内存 |
| 启动慢被 kill | 看 `startupProbe` | 探针超时太短 |
| 滚动更新卡住 | `kubectl rollout status` | 就绪探针不过、镜像拉取失败 |
| 发布后 502 | 网关/Ingress 日志 | 实例没就绪就被摘/加 |
| 配置没生效 | 看配置优先级 | 本地配置覆盖了 Nacos |
| 流量不均 | 看 LB 策略/会话保持 | 长连接、最少连接算法 |

**标准发布姿势**：`startupProbe` + `readinessProbe` + `preStop sleep 5~10s` + `server.shutdown=graceful`。

## 十二、第三方依赖问题

| 现象 | 排查 | 处置 |
|---|---|---|
| 调用超时 | 看下游 RT/错误率 | 超时 + 重试（幂等）+ 熔断 + 降级 |
| 被限流（429） | 看响应头/错误码 | 退避重试 + 配额 + 排队 |
| 证书过期 | `openssl s_client` | 续期 + 监控到期时间 |
| 返回格式变更 | 对比接口文档 | 加兼容层/版本化 |
| SDK 版本冲突 | `mvn dependency:tree` | 排除/统一版本 |

## 十三、数据不一致 / 资损

**排查顺序**：

1. **定位差异**：对账（渠道 vs 本地、订单 vs 支付）。
2. **判断方向**：多扣/少扣、重复、状态不对。
3. **止损**：先冻结相关操作，避免扩大。
4. **修复**：补单/退款/冲正（要有审批与留痕）。
5. **复盘**：是幂等缺失、消息丢失，还是并发写？

**预防**：幂等键、状态机、对账任务、资金操作双人复核。

## 十四、速查表（打印贴墙）

| 现象 | 第一条命令 | 先看什么 |
|---|---|---|
| CPU 高 | `top -Hp <pid>` | 哪个线程 |
| 内存高 | `jcmd <pid> GC.heap_info` | 堆还是堆外 |
| GC 频繁 | `jstat -gcutil <pid> 1000` | FGC 次数/耗时 |
| 接口慢 | 看监控 P99 + traceId | 应用还是下游 |
| 线程池满 | `jstack <pid>` | 卡在哪个调用 |
| 连接池满 | `SHOW PROCESSLIST` | 慢 SQL/长事务 |
| 慢 SQL | `EXPLAIN` | type/key/rows |
| 死锁 | `SHOW ENGINE INNODB STATUS` | 最后一段死锁 |
| 缓存异常 | `INFO stats` | 命中率/淘汰 |
| MQ 堆积 | `mqadmin consumerProgress` | 消费 TPS |
| 连接异常 | `ss -s` | TIME_WAIT/CLOSE_WAIT |
| 发布异常 | `kubectl describe pod` | 探针/退出码 |
