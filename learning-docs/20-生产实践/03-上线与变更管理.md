# 03 - 上线与变更管理

> **目标**：把"能跑"变成"敢发"。发布不是 `git push` + 重启，而是一套**可回滚、可观测、可止损**的流程。
> **核心事实**：业界经验里 **60%~80% 的线上故障与变更相关**（发版、配置、SQL、扩缩容）。
> **纪律**：没有回滚方案的发布，不叫发布，叫赌博。

---

## 一、先建立三个认知

1. **发布 ≠ 部署**：部署是把包放上去，发布是让流量切过去。两者要解耦（蓝绿/灰度）。
2. **回滚要快于定位**：出事第一动作是"回到上一个已知好状态"，不是"查根因"。
3. **数据库变更最难回滚**：代码可以回滚，数据不能。所以 DB 变更要"向前兼容"。

---

## 二、发布策略：四种，按场景选

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **停机发布** | 停旧 → 起新 | 简单 | 有中断 | 内部系统、非核心 |
| **滚动发布** | 逐批替换 Pod | 不停机、资源省 | 新旧版本共存，要兼容 | K8s 默认，多数服务 |
| **蓝绿发布** | 两套环境，切流量 | 回滚最快（切回去） | 资源翻倍 | 核心链路、大版本 |
| **灰度/金丝雀** | 按比例/用户/标签放量 | 风险最小 | 需要流量治理 | 核心功能、算法变更 |

**本项目的默认选择**：K8s 滚动更新 + 就绪探针 + 优雅停机；核心服务可加灰度（按 `X-User-Id` 白名单）。

---

## 三、零停机发布的四个必要条件

缺一个都会丢请求：

| 条件 | 本项目配置 | 作用 |
|---|---|---|
| **优雅停机** | `server.shutdown: graceful`、`spring.lifecycle.timeout-per-shutdown-phase: 30s` | 停止接收新请求，处理完在途请求 |
| **就绪探针** | K8s `readinessProbe` | 没就绪不接流量 |
| **启动探针** | `startupProbe`（JVM 启动慢时必需） | 防止 liveness 把启动中的实例杀掉 |
| **preStop 延迟** | `preStop: sleep 5~10s` | 等 Endpoint 摘除生效，避免"已摘流但仍有请求" |

**顺序**：新 Pod 就绪 → 加入 Endpoints → 旧 Pod preStop → 摘流 → 优雅停机 → 退出。

> 常见坑：只配了 `liveness` 没配 `readiness`，结果新版本一启动就被打流量，报错后又重启。

---

## 四、回滚：三种对象，三种难度

| 对象 | 手段 | 速度 | 注意 |
|---|---|---|---|
| **镜像/代码** | `kubectl rollout undo` / 重新部署上一版 | 分钟级 | 确认镜像 tag 唯一（别用 `latest`） |
| **配置** | Nacos 历史版本回滚 / ConfigMap 回滚 | 秒级 | 配置也要版本化、审计 |
| **数据库** | 回滚脚本 / 向前修复 | 小时级 | **能前进就不要后退** |

**回滚决策树**：

```text
出问题
 ├─ 能回滚？ → 立刻回滚（先止损）
 ├─ 回滚代价大？ → 降级/限流/开关关掉
 └─ 都不能？ → 热修复（风险最高，需双人复核）
```

---

## 五、数据库变更：最难的一块

### 5.1 三阶段（Expand → Migrate → Contract）

```text
阶段 1 扩展：加新字段（可空）/ 新表，旧代码不受影响
阶段 2 双写：新代码同时写新旧字段，后台回填历史数据
阶段 3 切换：读新字段，验证无误
阶段 4 收缩：删旧字段/旧表（至少隔一个发布周期）
```

> 口诀：**先加后改、先双写后切换、删留一个版本**。

### 5.2 大表 DDL 的三种做法

| 方式 | 说明 | 风险 |
|---|---|---|
| `ALGORITHM=INSTANT`（MySQL 8） | 加列瞬间完成（部分场景） | 只支持特定操作 |
| `pt-online-schema-change` | 建影子表 + 触发器同步 + 切换 | 需要额外空间、触发器开销 |
| `gh-ost` | 基于 binlog 同步，无触发器 | 需要主库权限、切换瞬间 |

**禁止**：业务高峰直接 `ALTER TABLE` 大表；`ADD INDEX` 不评估锁表。

### 5.3 数据迁移

- **幂等**：迁移脚本可重复执行（`INSERT ... ON DUPLICATE KEY` / 先删后插）。
- **可校验**：迁移后对账（条数、金额、抽样）。
- **可回滚**：保留旧表/旧字段，别急着删。
- **分批**：每批 500~1000，避免大事务与主从延迟。

---

## 六、配置变更：最容易出事的地方

| 规则 | 说明 |
|---|---|
| **禁止直改生产** | 配置走配置中心 + 审批 + 审计 |
| **版本化** | Nacos 有历史版本，回滚一条命令 |
| **灰度** | 先改一个实例/一个分组，观察 5 分钟 |
| **可回滚** | 改之前记下原值（或依赖配置中心历史） |
| **敏感配置加密** | 密钥不进 Git、不进日志 |
| **刷新范围** | `@RefreshScope` 只刷新 Bean，不是所有配置都能热更新 |

**本项目的配置分层**：Nacos（`aics-shared.yml`、`ai-cs-xxx.yml`）> 本地 `application.yml` 兜底；改完看 `/actuator/env` 确认生效。

---

## 七、灰度与开关

### 7.1 灰度的三个维度

| 维度 | 做法 | 适用 |
|---|---|---|
| 按用户 | 白名单 / 用户 ID 取模 | 功能灰度 |
| 按流量 | 网关权重 1% → 10% → 50% → 100% | 版本灰度 |
| 按标签 | K8s 节点/Pod 标签 | 环境隔离 |

### 7.2 Feature Flag

- 开关放配置中心，代码里 `if (flag) {...}`；
- **开关要能独立回滚**，不依赖发版；
- 开关要有**过期清理**，否则技术债越积越多。

> 面试话术："我们把'发布'和'上线'分开：代码先发但开关关着，验证没问题再开开关，出事直接关开关，不用回滚。"

---

## 八、发布检查清单

### 8.1 发布前

- [ ] 变更单/审批（谁改、改什么、影响面、回滚方案）
- [ ] 代码：CI 通过、镜像 tag 唯一、依赖无冲突
- [ ] 配置：新配置已发布、密钥就位、开关默认值正确
- [ ] DB：变更脚本已评审、备份完成、回滚脚本就绪
- [ ] 容量：资源够、连接池/线程池评估过
- [ ] 观测：监控面板、告警、日志采集正常
- [ ] 沟通：相关方知会、值班人到位

### 8.2 发布中

- [ ] 先发 1 个实例，观察 5~10 分钟
- [ ] 看黄金指标：错误率、P99、QPS、GC、连接池
- [ ] 看日志：异常、超时、重试
- [ ] 再全量滚动

### 8.3 发布后

- [ ] 核心链路回归（下单/支付/登录/搜索）
- [ ] 对比发布前后指标
- [ ] 观察 30 分钟无异常再收工
- [ ] 记录发布结果（成功/回滚/问题）

## 九、故障止损的优先级

```text
1. 回滚（最快恢复）
2. 关闭开关/降级（牺牲功能保核心）
3. 限流（保护后端）
4. 扩容（扛流量）
5. 热修复（最后手段）
```

**原则**：**先恢复，再定位**。不要一边救火一边查根因。

## 十、发布后验证（本项目可用）

```powershell
# 1. 健康检查
curl http://localhost:8080/actuator/health

# 2. 全链路自检（仓库自带）
powershell -ExecutionPolicy Bypass -File deploy/scripts/check-local.ps1

# 3. 关键接口
curl -s -o NUL -w "%{http_code} %{time_total}\n" http://localhost:8080/api/product/page
```

> `check-local.ps1` 会检查 11 个服务、中间件、Nacos 注册、网关、前端，输出 PASS/FAIL 报告，可作为发布验收证据。

## 十一、常见发布事故（都真实发生过）

| 事故 | 原因 | 预防 |
|---|---|---|
| 发布后 502 | 实例没就绪就被加流量 | readinessProbe + preStop |
| 滚动更新卡住 | 新版本启动失败/探针不过 | startupProbe + 看 events |
| 配置没生效 | 本地配置覆盖了 Nacos | 看配置优先级、`/actuator/env` |
| 镜像拉错 | 用了 `latest` tag | 每次构建唯一 tag（commit sha） |
| SQL 锁表 | 高峰直接 ALTER | 在线 DDL + 低峰执行 |
| 回滚后更糟 | 数据库已改，旧代码不兼容 | 向前兼容（expand-contract） |
| 灰度变全量 | 权重配置错 | 变更审计 + 双人复核 |

## 十二、小团队的变更管理（不搞形式主义）

```text
1. 所有变更走一个群/一个看板：发版、配置、SQL、扩缩容
2. 每次变更写三行：改什么、影响谁、怎么回滚
3. 生产操作双人复核（至少回滚方案有人确认）
4. 发布窗口避开高峰（除非紧急）
5. 每周复盘一次变更记录（有没有惊险的）
```

---

## 十三、面试怎么讲"零停机发布"

```text
四件事：
① 优雅停机：先摘流，再等在途请求处理完（30s）；
② 就绪探针：没就绪不接流量；
③ 启动探针：JVM 启动慢也不会被 liveness 杀掉；
④ preStop 延迟：等 Endpoint 摘除生效。
回滚：镜像回滚分钟级，配置回滚秒级，数据库尽量向前兼容。
```

**追问**："滚动更新时新旧版本共存，接口不兼容怎么办？" → 接口版本化/向后兼容（加字段不删字段），必要时蓝绿。
