# 04 - 真实案例复盘

> **目标**：把"踩过的坑"变成"可复述的资产"。
> **纪律**：
> - 本仓库的 4 个案例是**真实代码问题**（详见 [docs/28](../../docs/28-故障案例库.md)）；
> - 另外 4 个是**通用模式**（业界常见，非本仓库真实发生），用于练习"如果是我怎么查"。
> - 不编造故障时长、影响用户数、资损金额。

---

## 一、复盘方法论

### 1.1 时间线（Timeline）

```text
T0 变更/异常开始
T1 首次告警
T2 人工介入
T3 止损动作
T4 恢复
T5 根因定位
```

> 时间线能暴露两个关键指标：**MTTD**（发现时长）和 **MTTR**（恢复时长）。

### 1.2 5 Whys（连问五层）

```text
为什么订单没回滚？→ 因为事务没生效
为什么没生效？→ 因为同类自调用绕过代理
为什么没发现？→ 因为没有集成测试
为什么没有集成测试？→ 因为一直用单测覆盖，没人验证代理
为什么？→ 因为团队把"单测通过"当成"功能正确"
→ 改进：补集成测试 + Review 清单加一条
```

### 1.3 根因分类（避免"人为失误"这种废话根因）

| 类型 | 例子 | 改进方向 |
|---|---|---|
| 技术缺陷 | 自调用事务失效 | 代码/测试 |
| 配置错误 | 复制过滤漏库、死配置 | 配置校验/审计 |
| 流程缺失 | 无集成测试、无发布检查单 | 流程/门禁 |
| 容量不足 | 连接池太小、队列无界 | 容量评估 |
| 依赖故障 | 第三方超时、证书过期 | 熔断/监控 |
| 认知偏差 | "单测过了就行" | 培训/复盘 |


## 三、本仓库 4 个真实案例（精简版）

### C1 订单创建的事务注解失效（自调用）

| 项 | 内容 |
|---|---|
| **现象** | 设计意图是"锁内开事务"，但按 AOP 语义推演，`doCreateOrder` 的 `@Transactional/@GlobalTransactional` 可能不生效 |
| **定位** | 读代码发现 `createOrder` 通过 lambda 调 `this.doCreateOrder(...)`；单测用 `@InjectMocks` 裸对象，测不出代理 |
| **根因** | 同类自调用绕过 Spring 代理 |
| **修复** | 拆出独立 Bean `OrderCreateTxService`，`createOrder` 经注入的代理调用 |
| **验证** | 新增 `OrderCreateTxWiringTest`（最小 Spring 上下文 + H2）：**修复前 RED（Expecting true but was false），修复后 GREEN**；order 模块 85 个测试全绿 |
| **预防** | Review 清单加一条"本类方法调本类带注解方法"；补集成测试 |
| **话术** | 见 [docs/28 C1](../../docs/28-故障案例库.md) 的三层话术 |

### C2 从库复制过滤漏了订单库

| 项 | 内容 |
|---|---|
| **现象** | 从库只有用户/知识库/会话/Nacos 四个库 |
| **定位** | 看 `deploy/mysql/slave.cnf` 的 `replicate-do-db` 白名单 |
| **根因** | 白名单缺 `ai_customer_service`（订单）和 `product_db`（商品） |
| **影响** | 订单域读写分离失效、从库备份不完整、切主丢数据 |
| **修复** | 补白名单并重启复制；或去掉过滤做全量复制 |
| **预防** | 上线检查单加"复制过滤是否覆盖全部业务库" |
| **话术** | "冗余 ≠ 备份"——有从库不等于有备份 |

### C3 `pay.sandbox` 死配置

| 项 | 内容 |
|---|---|
| **现象** | Nacos 有 `pay.sandbox: true`，但改它没任何效果 |
| **定位** | 全仓 grep `pay.sandbox`，代码零命中 |
| **根因** | 配置加了但消费代码没跟上（或删代码没删配置） |
| **风险** | 误判环境（以为在沙箱，实际在真实渠道） |
| **修复** | 补 `@ConfigurationProperties` 消费，或删除该键 |
| **预防** | CI 做"配置键 vs 代码引用"差集检查 |
| **话术** | "死配置比缺配置更危险" |

### C4 K8s 清单缺 3 个服务

| 项 | 内容 |
|---|---|
| **现象** | K8s 只能部署 8 个服务，order/pay/mq 没有 manifest |
| **定位** | `deploy/k8s/services/` 只有 8 个 yaml，而系统有 11 个服务 |
| **根因** | 新增服务只补了 Dockerfile/compose，没同步 K8s 清单 |
| **风险** | CI 显示"部署成功"，但核心交易链路没上去 |
| **修复** | 补 3 份 manifest + Jenkins 服务列表 |
| **预防** | 门禁：模块数 vs manifest 数不一致则构建失败 |

## 四、4 个通用模式（练习用）

> 以下为业界常见模式，**非本仓库真实发生**，用于练习排查思路。

### G1 缓存与 DB 不一致（更新后删缓存失败）

```text
现象：用户改昵称后，刷新还是旧值（部分请求）
定位：看缓存命中率、更新日志；发现删缓存抛异常被吞
根因：先更新 DB 再删缓存，删失败没重试 → 脏缓存直到 TTL
修复：删缓存加重试 + 延迟双删 + 缩短 TTL
预防：缓存操作失败要告警；强一致场景不缓存
```

### G2 MQ 重复消费导致重复退款

```text
现象：对账发现同一订单退了两笔
定位：查退款流水，发现两条相同 msgId 的消费记录
根因：消费端无幂等，MQ 至少一次投递
修复：退款单号唯一索引 + 状态机（已退款直接返回）
预防：所有写操作消费必须幂等；对账兜底
```

### G3 滚动更新探针配置错误

```text
现象：发布后实例反复重启，流量 502
定位：kubectl describe pod 看到 liveness 失败；日志显示启动还没完成
根因：只配了 liveness，初始延迟太短，JVM 还在启动就被杀
修复：加 startupProbe / 调大 initialDelaySeconds；加 readinessProbe
预防：发布清单检查探针三项
```

### G4 慢查询拖垮连接池

```text
现象：接口大面积超时，报 "Connection is not available"
定位：SHOW PROCESSLIST 看到大量同一条 SQL；EXPLAIN 全表扫描
根因：新上线查询没走索引，连接被长时间占用
修复：补索引/改写 SQL；临时 kill 长查询
预防：SQL 上线前必须 EXPLAIN；慢查询告警；连接池监控
```

## 五、怎么把案例讲成面试故事

### 5.1 四段式（60~90 秒）

```text
背景（10s）：我在做什么功能
现象（15s）：出现了什么异常
定位（30s）：我怎么缩小范围（命令/对比/复现）
根因+修复+验证（30s）：根因、改了什么、怎么证明修好了
```

### 5.2 三个加分动作

| 动作 | 效果 |
|---|---|
| 说**排查路径**而不是直接给答案 | 证明会定位 |
| 说**为什么测试没发现** | 证明理解测试边界 |
| 说**怎么防止再发生** | 从修 bug 升级到改流程 |

### 5.3 不要做

- 把"通用模式"说成"我司真实故障"；
- 编造影响面（多少用户、多少钱）；
- 把别人的功劳说成自己的。

## 六、复盘会怎么开（不追责）

```text
1. 先还原时间线（只看事实，不评价）
2. 问"系统为什么允许这个错误发生"，而不是"谁干的"
3. 产出三类改进项：代码/测试、监控/告警、流程/门禁
4. 每项有 owner 和截止时间
5. 一周后回看改进项是否落地
```

> 好的复盘产出是"**系统变强了**"，不是"某人被罚了"。

---

## 七、案例库维护规则

1. 每个案例必须有**证据**（日志/命令输出/代码行号）；
2. 标注**状态**：已修复 / 待验证 / 通用模式；
3. 修复后补**回归方式**（测试/对账/监控）；
4. 每季度回看：有没有同类问题再次发生。
