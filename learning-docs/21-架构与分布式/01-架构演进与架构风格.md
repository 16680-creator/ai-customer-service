# 01 - 架构演进与架构风格

> **目标**：能判断"什么时候该拆、拆成什么样、拆完的代价是什么"。
> **前提**：[docs/00 架构图](../../docs/00-项目总览与架构图.md)、[02-Spring微服务/02](../02-Spring微服务/02-SpringCloud微服务架构.md)。
> **纪律**：架构没有"先进/落后"，只有"匹配/不匹配"。

---

## 一、演进四阶段

```text
单体 → 模块化单体 → 微服务 → 平台化/中台
```

| 阶段 | 特征 | 适合 | 主要问题 |
|---|---|---|---|
| **单体** | 一个进程、一个库 | 团队 < 10 人、业务未定型 | 发布耦合、技术栈锁定、扩容粗粒度 |
| **模块化单体** | 单进程 + 清晰模块边界 + 独立包 | 多数业务系统 | 边界靠自觉，容易退化成大泥球 |
| **微服务** | 独立部署、独立数据、网络调用 | 团队多、发布频繁、资源需隔离 | 分布式复杂度、运维成本、一致性 |
| **平台化** | 服务 + 能力复用 + 自服务 | 多业务线、规模化 | 组织与治理成本高 |

**判断"该不该拆"的四个触发条件**（满足 2 个以上再考虑）：

1. **团队规模**：超过 2 个 pizza team（约 10~15 人），沟通成本开始上升；
2. **发布冲突**：不同模块的发布频率差异大，互相阻塞；
3. **资源隔离**：某个模块需要独立扩缩容/独立技术栈；
4. **故障隔离**：某模块故障不能拖垮全局。

**三个不该拆**：

- 领域边界还没想清（拆了也是分布式单体）；
- 团队没有运维能力（监控/日志/发布/排障）；
- 只是为了"技术先进"或"简历好看"。

> 本项目 12 个服务是**学习目的**的刻意拆分，真实业务按规模可能先做 3~4 个服务。

## 二、分层架构：最常见的起点

```text
Controller（接口层） → Service（业务层） → DAO/Mapper（数据层）
```

**优点**：简单、团队熟悉、上手快。

**问题**：

1. **业务逻辑泄漏**：Controller 里写业务、Service 里拼 SQL；
2. **依赖方向单一**：Service 依赖 DAO，导致业务依赖数据库细节；
3. **领域模型贫血**：只有数据类 + 一堆 Service 方法；
4. **换存储困难**：业务代码里到处是 SQL/ORM 注解。

> 分层架构不是错，错在"只有分层，没有边界"。

---

## 三、六边形架构（端口与适配器）

```text
         ┌───────────── 应用核心（领域）─────────────┐
入站适配器 →  端口（接口）  →  用例/领域服务  →  端口（接口）  → 出站适配器
（HTTP/MQ）                                      （DB/MQ/外部API）
```

**核心思想**：领域核心不依赖任何框架/存储，通过**端口（接口）**与外界交互，**适配器**实现端口。

**好处**：

- 领域逻辑可单测（不启 Spring、不连 DB）；
- 换存储/换协议只换适配器；
- 依赖方向：**外 → 内**。

**本项目对照**：`OrderService` 接口 + `OrderServiceImpl` 是"端口+实现"的雏形，但仍依赖 MyBatis 注解（`@TableName`），不是纯六边形。

---

## 四、洋葱架构 / 整洁架构

```text
实体（Entities）→ 用例（Use Cases）→ 接口适配器 → 框架与驱动
```

规则（依赖倒置）：

1. 内层不知道外层；
2. 跨层通过接口；
3. 框架是细节，不是核心。

> 与六边形本质相同，只是画法不同。面试说清"依赖方向向内"即可。

## 五、微服务拆分的四种方法

| 方法 | 做法 | 适用 |
|---|---|---|
| **按业务能力** | 商品、订单、支付、用户 | 最常见，直观 |
| **按 DDD 限界上下文** | 先事件风暴划上下文，再映射服务 | 领域复杂时最准（见 02 篇） |
| **按团队（康威定律）** | 一个团队一个服务 | 组织驱动 |
| **按变更频率** | 高频变更与稳定部分分开 | 发布冲突严重时 |

**拆分后的三个必答题**：

1. 数据怎么分？（每服务独立库，禁止跨库 join）
2. 一致性怎么保？（事务消息/对账/补偿）
3. 调用链怎么排障？（traceId + 日志 + 指标）

## 六、分布式单体：最该避免的反模式

**特征**：

- 服务拆了，但共享一个数据库；
- 一次请求同步调用 5+ 个服务；
- 任何一个服务挂，全链路挂；
- 发布必须一起发。

**后果**：拿到了微服务的复杂度，没拿到自治性。

**解法**：要么合回去（模块化单体），要么把数据与调用链真正拆开。

## 七、架构决策记录（ADR）

每个重要决策写一页：

```markdown
# ADR-001：订单与支付拆成两个服务

## 背景
支付渠道多、回调逻辑复杂，与订单生命周期耦合。

## 决策
拆出 ai-cs-pay，独立库；通过事务消息通知订单。

## 备选
1. 合在订单服务（简单，但支付渠道变更影响订单发布）
2. 拆服务但共享库（不推荐，分布式单体）

## 后果
+ 支付可独立演进、独立扩容
- 多一个服务运维；需要处理消息重复/丢失
```

> 面试时能说出"我们当时比较了 A/B，选了 B，代价是 C"，就是架构能力。

## 九、面试题

| 题 | 答法骨架 |
|---|---|
| 单体 vs 微服务怎么选？ | 看团队/发布/隔离/故障四个触发条件；多数场景模块化单体更划算 |
| 微服务拆分依据？ | 业务能力 + DDD 限界上下文 + 团队边界；先划上下文再映射服务 |
| 拆分后数据一致性？ | 每服务独立库；事务消息/对账/补偿；不强求跨库事务 |
| 什么是分布式单体？ | 拆了服务但共享库/强耦合调用，复杂度上升但没自治 |
| 六边形架构解决什么？ | 领域核心与框架/存储解耦，依赖向内 |
| 你们项目有什么架构问题？ | 诚实说 12 服务偏多、无 ADR、K8s 清单缺口 |
