# 03 - 分布式一致性理论

> **目标**：讲清"为什么分布式这么难"，以及 CAP、一致性模型、共识协议之间的关系。
> **前提**：[15-计算机基础](../15-计算机基础/README.md) 的网络与 OS 部分。
> **纪律**：先定义再比较；不把"共识"和"分布式事务"混为一谈。

---

## 一、问题从哪来

单机时代，一次写操作要么成功要么失败。分布式之后，出现三个新变量：

| 变量 | 表现 | 后果 |
|---|---|---|
| **网络分区（P）** | 节点之间收不到消息 | 无法区分"对方挂了"还是"网络断了" |
| **延迟（L）** | 消息可能很慢 | 无法用超时确定"失败" |
| **节点故障** | 进程崩溃/重启 | 内存状态丢失，需持久化与恢复 |

> 核心难题：**在不可靠的网络上，多个节点如何对"同一个值"达成一致。**

---

## 二、CAP：不是"三选二"

### 2.1 精确定义

- **C 一致性**：每次读都能读到最新写入（线性一致）。
- **A 可用性**：每个请求都能在有限时间得到非错误响应。
- **P 分区容忍**：网络分区时系统仍能运行。

### 2.2 正确理解

```text
P 是客观存在的（网络一定会分区），所以真正的选择是：
分区发生时，选 C（拒绝服务/等待）还是选 A（返回可能旧的数据）。
```

| 选择 | 行为 | 例子 |
|---|---|---|
| **CP** | 分区时少数派不可用 | ZooKeeper、etcd、MySQL 主从（强一致模式） |
| **AP** | 分区时仍可读写，可能不一致 | Eureka、Cassandra、Redis 主从（异步复制） |

**常见误解**：

- ❌ "CAP 只能选两个"——P 必须选，实际是 C/A 取舍。
- ❌ "CA 系统存在"——单机才没有分区问题。
- ❌ "BASE 是 CAP 的替代"——BASE 是 AP 的实践延伸。

---

## 三、BASE

| 字母 | 含义 | 做法 |
|---|---|---|
| **BA** | Basically Available 基本可用 | 降级、限流、部分功能不可用 |
| **S** | Soft state 软状态 | 允许中间状态（支付中、退款中） |
| **E** | Eventually consistent 最终一致 | 对账、补偿、重试 |

> 互联网业务大多选 AP + 最终一致；金融核心账务往往选 CP。

---

## 四、一致性模型谱系

从强到弱：

```text
线性一致（强一致）
  > 顺序一致
    > 因果一致
      > 最终一致
```

| 模型 | 保证 | 例子 |
|---|---|---|
| **线性一致** | 所有操作像在单机上按实时顺序执行 | etcd、ZK（写） |
| **顺序一致** | 所有节点看到相同顺序，但不要求实时 | 部分内存模型 |
| **因果一致** | 有因果关系的操作有序 | 协同编辑 |
| **最终一致** | 停止写入后，副本最终相同 | DNS、Redis 主从、MQ |

**面试要点**：说"强一致"时要能落到"线性一致"；说"最终一致"时要能说出"窗口多大、怎么兜底"。

## 五、副本协议

### 5.1 主从复制（最常见）

```text
写 → 主 → 同步/异步 → 从
读 → 从（可能读到旧数据）
```

| 模式 | 一致性 | 可用性 | 代价 |
|---|---|---|---|
| 同步复制 | 强 | 低（从库挂则写失败） | 延迟高 |
| 异步复制 | 最终 | 高 | 可能丢数据 |
| 半同步 | 折中 | 中 | 至少一个从库确认 |

**读写分离的坑**：写后立即读从库可能读不到（主从延迟）→ 写后读主、或等位点。

### 5.2 多主复制

多节点可写，冲突需解决（LWW、版本向量、业务合并）。适合多地域，复杂度高。

### 5.3 无主复制与 Quorum

```text
N 个副本，写需 W 个确认，读需 R 个确认
只要 W + R > N，读写集合必有交集 → 能读到最新值
例：N=3, W=2, R=2
```

**注意**：Quorum 只保证"能读到最新"，不保证"读到的就是最新"（需要版本号/读修复）。

## 六、2PC / 3PC

### 6.1 2PC（两阶段提交）

```text
阶段一 准备：协调者问所有参与者"能提交吗？" → 参与者锁资源、写 undo/redo、回复 yes/no
阶段二 提交/回滚：全部 yes → commit；否则 rollback
```

**缺陷**：

1. **同步阻塞**：参与者锁资源直到阶段二；
2. **协调者单点**：协调者挂了，参与者一直等；
3. **数据不一致**：部分参与者收到 commit、部分没收到。

### 6.2 3PC

在 2PC 前加一个 `CanCommit`，并给参与者加超时，缓解阻塞，但**仍不能解决分区下的不一致**。

> 工程上更常用：**本地消息表 / 事务消息 / TCC / Saga**（见 [02/06 Seata AT](../02-Spring微服务/06-Seata分布式事务AT模式.md)）。

## 七、Paxos（了解即可）

### 7.1 角色

- **Proposer**：提提案（编号 + 值）；
- **Acceptor**：投票，接受提案；
- **Learner**：学习已确定的值。

### 7.2 两个阶段

```text
Prepare：Proposer 发编号 n → Acceptor 承诺不再接受 < n 的提案，返回已接受的最大编号值
Accept：Proposer 发 (n, value) → 多数派接受 → 值被选定
```

### 7.3 为什么需要多数派

任意两个多数派必有交集 → 保证"已选定的值不会被覆盖"。

### 7.4 活锁

两个 Proposer 互相抬价 → 永远无法完成。解法：随机退避 / 选主（Raft 的做法）。

## 八、Raft：为可理解性而生

Raft 把共识拆成三个子问题：

1. **选主**（Leader Election）
2. **日志复制**（Log Replication）
3. **安全性**（Safety）

> 详细流程与手写实现见 [04-Raft 协议与手写实现](04-Raft协议与手写实现.md)。

## 九、共识 ≠ 分布式事务

| | 共识（Consensus） | 分布式事务 |
|---|---|---|
| 目标 | 多副本对"一个值/日志顺序"达成一致 | 多个业务操作原子提交/回滚 |
| 典型 | Raft/Paxos/ZAB | 2PC/TCC/Saga/事务消息 |
| 解决 | 复制状态机的顺序 | 跨服务数据一致性 |
| 例子 | etcd 选主与日志 | Seata AT、支付+订单 |

> 面试常问"Raft 和 2PC 区别"——一个是**复制共识**，一个是**事务提交协议**，解决的不是同一个问题。

## 十、故障模型

| 模型 | 假设 | 算法 |
|---|---|---|
| **崩溃故障（Crash）** | 节点只会停，不会说谎 | Raft、Paxos、2PC |
| **拜占庭故障（Byzantine）** | 节点可能发错误消息 | PBFT、区块链共识 |

> 绝大多数后端系统假设崩溃故障；拜占庭容错在联盟链/高安全场景才用。

---

## 十一、时钟与顺序

| 机制 | 作用 | 局限 |
|---|---|---|
| 物理时钟（NTP） | 近似时间 | 会漂移、可能回拨 |
| **Lamport 逻辑时钟** | 偏序（因果） | 无法判断并发 |
| **向量时钟** | 检测并发/冲突 | 元数据大 |
| **混合逻辑时钟（HLC）** | 物理 + 逻辑 | 实现复杂 |

**实践**：分布式 ID 用"时间戳 + 机器位 + 序列"；事件排序用版本号/offset，不依赖物理时间。

---

## 十二、面试题

| 题 | 答法骨架 |
|---|---|
| CAP 怎么理解？ | P 必选，分区时在 C/A 取舍；不要背"三选二" |
| 最终一致怎么保证？ | 重试 + 幂等 + 对账 + 补偿；给出窗口与兜底 |
| 2PC 有什么问题？ | 阻塞、协调者单点、分区不一致；工程用消息/TCC/Saga |
| Paxos 为什么需要多数派？ | 任意多数派有交集，保证已选定值不被覆盖 |
| Raft 和 2PC 区别？ | 共识 vs 事务提交，目标不同 |
| 主从延迟怎么解决？ | 写后读主、等位点、半同步、业务容忍 |
| Quorum 怎么选 W/R？ | W+R>N 保证交集；读多写少可 R 小 W 大 |
| 什么是线性一致？ | 所有操作像单机实时顺序；etcd 写是典型 |
