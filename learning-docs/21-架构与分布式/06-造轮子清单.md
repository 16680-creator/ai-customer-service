# 06 - 造轮子清单

> **目标**：用"最小可运行实现"检验你是否真的理解中间件。造轮子不是重复发明，是**拆开看内部**。
> **纪律**：每个轮子只做**核心路径**（能跑通 + 能讲清），不追求生产级；代码放独立仓库或 `mini/` 目录。

---

## 一、为什么造轮子

| 收益 | 说明 |
|---|---|
| 面试差异化 | 别人说"用过 Dubbo"，你说"我写过 500 行 RPC，知道动态代理怎么做" |
| 真正理解 | 超时/重试/序列化/连接池，只有自己写才懂取舍 |
| 排障能力 | 知道框架内部，线上问题能定位到层 |
| 架构判断 | 知道成本，才不会乱选型 |

**推荐顺序**（由易到难）：

```text
IOC → 分布式锁 → 注册中心 → RPC → 简易 MQ → 网关
```

---

## 二、手写 IOC 容器（1~2 天）

**目标**：扫描包 → 实例化 → 依赖注入 → 生命周期。

```java
// 1. 扫描：反射找带 @Component 的类
Set<Class<?>> classes = scan("com.demo");

// 2. 实例化：无参构造
Map<Class<?>, Object> beans = new HashMap<>();
for (Class<?> c : classes) beans.put(c, c.getDeclaredConstructor().newInstance());

// 3. 注入：字段上有 @Autowired 就赋值
for (Object bean : beans.values()) {
    for (Field f : bean.getClass().getDeclaredFields()) {
        if (f.isAnnotationPresent(Autowired.class)) {
            f.setAccessible(true);
            f.set(bean, beans.get(f.getType()));
        }
    }
}
```

**进阶**：构造器注入、循环依赖（三级缓存）、`@PostConstruct`、单例/原型。

**验收**：能启动一个含 3 层依赖（Controller→Service→Dao）的 demo。

## 三、手写分布式锁（2~3 天）

**目标**：Redis `SET NX PX` + Lua 解锁 + 续期。

```java
public boolean tryLock(String key, String value, long ttlMs) {
    return Boolean.TRUE.equals(redis.opsForValue()
        .setIfAbsent(key, value, Duration.ofMillis(ttlMs)));
}

public void unlock(String key, String value) {
    String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                 "return redis.call('del', KEYS[1]) else return 0 end";
    redis.execute(new DefaultRedisScript<>(lua, Long.class), List.of(key), value);
}
```

**要讲清的点**：

1. 为什么 value 要唯一？→ 防止解别人的锁；
2. 为什么用 Lua？→ 判断 + 删除原子；
3. TTL 怎么定？→ 业务耗时上限 + 续期（看门狗）；
4. Redlock 争议？→ 时钟漂移/分区下不绝对安全；强一致场景用 ZK/etcd。

**验收**：两个线程并发抢锁，只有一个成功；锁过期后另一个能拿到。

## 四、手写注册中心（3~5 天）

**目标**：服务注册、心跳、健康检查、订阅推送。

```text
注册：POST /register {service, ip, port, ttl}
心跳：PUT /heartbeat {service, ip, port} （每 5s）
健康：超过 ttl 未心跳 → 摘除
发现：GET /instances?service=xxx
推送：长轮询 / WebSocket / 客户端定时拉
```

**存储**：`Map<service, List<Instance>>` + 过期时间。

**要讲清的点**：

- 推 vs 拉：Eureka 拉、Nacos 推+拉；
- AP vs CP：Eureka AP、ZK CP；
- 自我保护：网络抖动时不要大面积摘除。

**验收**：启动 3 个 provider，consumer 能拿到列表；kill 一个，5s 后列表更新。

## 五、手写 RPC（1~2 周）

**目标**：动态代理 + 序列化 + 网络 + 超时 + 负载均衡。

### 5.1 核心链路

```text
Consumer 调用接口
 → 动态代理拦截
 → 组装请求（类名/方法/参数）
 → 序列化（JSON/Protobuf）
 → 网络发送（Netty/Socket）
 → Provider 反序列化 → 反射调用 → 返回
```

### 5.2 动态代理

```java
public <T> T refer(Class<T> interfaceClass) {
    return (T) Proxy.newProxyInstance(
        interfaceClass.getClassLoader(),
        new Class[]{interfaceClass},
        (proxy, method, args) -> {
            RpcRequest req = new RpcRequest(interfaceClass.getName(), method.getName(),
                    method.getParameterTypes(), args);
            byte[] resp = client.send(encode(req));
            return decode(resp);
        });
}
```

### 5.3 必做四件事

| 能力 | 做法 |
|---|---|
| 超时 | `Future.get(timeout)` / Netty 定时任务 |
| 重试 | 失败重试 N 次 + 退避；**只对幂等方法重试** |
| 负载均衡 | 随机/轮询/最少连接 |
| 连接管理 | 长连接 + 心跳 + 连接池 |

**验收**：能给一个接口生成代理，跨进程调用成功；超时能抛异常；provider 挂掉能切到另一个。

## 六、手写简易 MQ（1~2 周）

**目标**：存储、消费位点、重试、顺序。

```text
Producer → append 到文件/DB（topic + offset）
Consumer → 按 offset 拉取 → 处理 → 提交位点
失败 → 重试队列 → 超过次数 → 死信
```

**要讲清的点**：

1. 为什么顺序写快？→ 磁盘顺序 IO；
2. 怎么保证不丢？→ 刷盘 + 副本 + 消费确认；
3. 怎么保证不重？→ 做不到，只能消费幂等；
4. 位点存哪？→ Broker（RocketMQ）vs 客户端（Kafka 旧版）。

**验收**：能发能收；消费者重启后从上次位点继续；处理失败进重试。

---

## 七、手写网关（1 周）

**目标**：路由 + 过滤器链 + 限流 + 鉴权。

```text
请求 → 路由匹配（path → upstream）
     → 过滤器链（鉴权 → 限流 → 日志 → 重写）
     → 转发（HttpClient/Netty）
     → 响应过滤
```

**要讲清的点**：

- 路由表怎么存、怎么热更新；
- 过滤器顺序与短路；
- 限流放网关还是应用（见 [20/02](../20-生产实践/02-生产问题排查手册.md)）；
- 超时/重试/熔断。

**验收**：两个后端服务，按 path 路由；加一个鉴权过滤器；加令牌桶限流。

---

## 八、验收标准总表

| 轮子 | 最小功能 | 能讲清的取舍 | 预计 |
|---|---|---|---|
| IOC | 扫描/注入/单例 | 循环依赖、生命周期 | 1~2 天 |
| 分布式锁 | 加锁/解锁/续期 | 原子性、续期、Redlock | 2~3 天 |
| 注册中心 | 注册/心跳/发现 | AP/CP、推拉、自我保护 | 3~5 天 |
| RPC | 代理/序列化/调用 | 超时、重试、LB | 1~2 周 |
| MQ | 发/收/位点 | 顺序写、不丢、幂等 | 1~2 周 |
| 网关 | 路由/过滤/限流 | 过滤器顺序、热更新 | 1 周 |

## 九、面试怎么讲

```text
"我写过一个小 RPC：动态代理把接口调用转成请求，JSON 序列化后走 Netty，
provider 反射调用返回。做的过程中最麻烦的是超时和重试——
超时要用 Future + 定时任务，重试只能对幂等方法做，否则会重复下单。
后来我把它和 Dubbo 的设计对照，理解了为什么 Dubbo 要搞泛化调用和连接池。"
```

> 重点不是"我写了"，而是"我因此理解了 XX 的取舍"。

---

## 十、常见误区

| 误区 | 纠正 |
|---|---|
| 追求生产级 | 造轮子是为了理解，不是替代中间件 |
| 只写不测 | 每个轮子至少 3 个测试（正常/超时/宕机） |
| 不看成熟实现 | 写完对照 Netty/Dubbo/Redis 源码，收获最大 |
| 全部一起写 | 按顺序，一个跑通再下一个 |
| 不记录 | 写设计笔记 + 踩坑，面试直接用 |
