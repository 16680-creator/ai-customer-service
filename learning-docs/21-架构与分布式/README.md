# 架构与分布式（21 模块）

> 本专题解决从"会用框架"到"能做设计"的跨越：
> **架构风格怎么选、领域边界怎么划、分布式共识怎么保证、轮子怎么造。**
>
> 前 20 个模块多数在讲"某个技术怎么用"，本模块讲"**为什么这样设计、不这样会怎样**"。

---

## 一、为什么单开这个模块

2026-10 盘点全库 248 篇文档，发现三个"设计层"空白：

| 主题 | 现状 | 影响 |
|---|---|---|
| **DDD（领域驱动设计）** | `领域驱动` 0 篇、`DDD` 仅 3 处提及 | 说不清"服务边界怎么划"，只能答"按业务" |
| **CQRS / 事件溯源** | 0 篇 | 读多写多场景只会加缓存 |
| **共识算法与造轮子** | Raft 9 处（在 ZK/etcd 篇）、Paxos 0 | 会用 Nacos/Seata，但讲不清"为什么需要多数派" |

> 结论：**广度已经够了，缺的是"设计判断"和"第一性原理"。**

---

## 二、三层能力模型

```text
第一层 架构风格   →  01 架构演进与架构风格
第二层 领域建模   →  02 DDD（战略 + 战术 + 订单域重构）
第三层 分布式     →  03 一致性理论 → 04 Raft 手写 → 05 CQRS/事件溯源
贯穿   动手验证   →  06 造轮子（RPC/注册中心/锁/MQ/网关）
```

**判断标准**：学完每一篇，你能不能回答"**这个设计解决了什么问题、代价是什么、什么场景不该用**"。

## 五、三条使用路径

### 路径 A：面试冲刺（1 周）

1. 01 的"演进判据 + 拆分方法"；
2. 02 的战略设计（限界上下文/上下文映射）+ 订单域示例；
3. 03 的 CAP/一致性模型/2PC；
4. 04 的选主与日志复制（能画图讲清即可）。

### 路径 B：做设计（1 个月）

1. 01 + 02 精读，用本项目订单域做一次重构方案；
2. 03 精读，能区分"共识"与"分布式事务"；
3. 04 手写 mini-raft（选主 + 日志复制跑通）；
4. 05 用事件表实现一个最小事件溯源。

### 路径 C：造轮子（2 个月）

按 06 的顺序：RPC → 注册中心 → 分布式锁 → 简易 MQ → 网关 → IOC，每个都有验收标准。

## 六、写作纪律

1. **先讲问题再讲方案**：每个模式都要说清"它解决什么痛点"。
2. **必须讲代价**：没有银弹，每个选择都有成本。
3. **能落到本项目**：用订单/支付/Agent 做正例或反例。
4. **代码给骨架不给全文**：能跑的最小实现，放独立仓库或 `mini/` 目录。
5. **不神化**：DDD/CQRS/微服务都不是默认答案，讲清"什么时候不用"。
