## 一、异常体系对照

```text
Java                              Python
─────────────────────────────────────────────────────
Throwable                         BaseException
 ├── Error（OutOfMemoryError…）     ├── SystemExit / KeyboardInterrupt / GeneratorExit
 └── Exception                     └── Exception
      ├── RuntimeException               ├── ArithmeticError
      ├── IOException (checked)          ├── LookupError
      ├── SQLException (checked)         │    ├── IndexError
      └── 自定义                          │    └── KeyError
                                         ├── ValueError
                                         ├── TypeError
                                         ├── OSError（含 IOError）
                                         └── 自定义
```

| 概念 | Java | Python |
|---|---|---|
| 根 | `Throwable` | `BaseException` |
| 业务异常基类 | `Exception` | `Exception` |
| **checked exception** | 有（`IOException` 等必须处理或声明） | **完全没有** |
| `throws` 声明 | 必须 | 不需要，也不支持 |
| `finally` | 有 | 有 |
| try-with-resources | 有 | `with`（更通用） |
| 多异常捕获 | `catch (A \| B e)` | `except (A, B) as e` |
| 重新抛出 | `throw e;` | `raise` |
| 异常链 | `new X(msg, cause)` | `raise X(...) from e` |

### 最大的区别：**没有 checked exception**

```java
// Java：编译器逼你处理
public String read(String path) throws IOException {
    return Files.readString(Path.of(path));   // 必须声明
}
```

```python
# ---- 本段讲：Python 没有 checked exception ----
# Java 要求方法在签名上 throws IOException，调用方必须 try 或继续 throws；
# Python 完全不需要声明，异常什么时候抛、抛什么类型，编译器一概不管。
# 后果：调用第三方库前要翻文档的 Raises 段；边界处（API/任务入口）必须自己兜底。
# Python：随便抛，没人管
def read(path):                       # 没有任何 throws 声明，函数签名不体现异常
    return open(path).read()      # 可能抛 FileNotFoundError，但编译器不知道   ← 文件不存在/无权限时在运行期才炸
```

**后果**：Python 的异常是**运行时契约**，README 和类型注解不会告诉你会抛什么。所以：

- 调第三方库前看一眼文档的 Raises 段
- 边界处（API 入口、任务入口、消息消费入口）必须兜底 `except Exception`
- 用 `raise ... from e` 保留原因，否则排查时看不到根因

## 二、try 的完整形态

```python
# ---- 本段讲：try 的完整形态（try / except / else / finally） ----
# 执行顺序：try 成功 → else → finally；try 抛异常 → 匹配的 except → finally。
# except 从上到下匹配，所以"具体异常"必须写在"宽泛异常"前面，否则永远轮不到具体分支。
# else 是 Java 没有的：它只捕获 try 块里的异常，把"后续业务逻辑"隔离出来，避免误捕。
# finally 与 Java 完全一致：无论是否异常、是否 return，都会执行（常用于释放资源）。
try:                                              # 可能出错的代码放这里
    result = risky()                              # 演示用：可能抛各种异常的函数
except ValueError as e:                           # 只接 ValueError；as e 拿到异常实例
    print(f"值错误：{e}")                         # f-string 打印异常信息
except (KeyError, IndexError) as e:               # 元组写法=一次捕获多种异常，等价 Java 的 catch (A | B e)
    print(f"查找失败：{e}")                       # KeyError=字典缺键，IndexError=列表越界
except Exception as e:                            # 兜底：接住其余所有普通异常（不含 KeyboardInterrupt 等 BaseException）
    print(f"未预期：{type(e).__name__}: {e}")     # __name__ 拿类名，等价 Java 的 e.getClass().getSimpleName()
    raise                       # 重新抛出（保留原栈）   ← 单个 raise 无参数 = 原样抛出当前异常，类似 Java 的 throw e;
else:                                             # 仅当 try 没有抛异常时执行
    print("没有异常才执行")       # Java 没有   ← 把"成功后的逻辑"放这里，语义更清晰
finally:                                          # 无论如何都执行（包括 try 里 return 之前）
    print("无论如何都执行")                       # 对应 Java 的 finally，用于清理资源
```

### `else` 子句的价值

```python
# ---- 本段讲：else 子句的价值（缩小 try 的管辖范围） ----
# 对比两个写法：左边把 process(data) 也放进 try，于是 process 内部抛的 OSError 也会被当成"加载失败"；
# 右边用 else 把"后续处理"移出 try，except 只负责 load 这一步，排错时归因准确。
# Java 里只能靠"把 try 块写小一点"来达到同样效果，没有 else 这种语法级隔离。
# ❌ 容易把"业务代码抛的异常"也 catch 掉
try:                                              # try 范围过大
    data = load()                                 # 第一步：加载
    process(data)           # 这行抛的异常也会被下面的 except 捕获，误判为 load 失败   ← 归因错误的根源
except OSError:                                   # 本意只想接 load 的 OSError
    print("加载失败")                             # 但 process 抛 OSError 时也会走到这

# ✅ 用 else 分离
try:
    data = load()                                 # try 里只有一步
except OSError:                                   # 只可能来自 load
    print("加载失败")
else:                                             # load 成功才执行
    process(data)           # 只处理 load 的异常   ← 这里的异常不再被上面的 except 捕获，会正常向上冒泡
```

### 异常链：`raise ... from`

```python
# ---- 本段讲：异常链 raise ... from e ----
# 作用等价 Java 的 new ConfigException(msg, cause)：把底层异常挂到新异常上，栈里能看到"根因"。
# from e 会设置 __cause__ 并让输出显示 "The above exception was the direct cause of ..."。
# 千万不要用 raise ConfigError(str(e))，那样只剩一句字符串，原始栈和类型全丢了。
def load_config(path):
    try:
        return json.loads(Path(path).read_text(encoding="utf-8"))   # 读文件 + 解析 JSON，两处都可能抛异常
    except (OSError, json.JSONDecodeError) as e:                    # OSError 覆盖文件类错误，JSONDecodeError 覆盖格式错误
        raise ConfigError(f"配置加载失败：{path}") from e   # 保留根因   ← 用 from 把 e 挂成 __cause__，等价 Java 的 cause 参数
```

输出会有两段栈：

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1
The above exception was the direct cause of the following exception:
ConfigError: 配置加载失败：app.json
```

> 相当于 Java 的 `new ConfigException(msg, cause)`。**永远用 `from e`，不要用 `raise X(str(e))`**——后者丢栈。

### `raise X from None`：故意切断链

```python
# ---- 本段讲：raise X from None（故意切断异常链） ----
# 场景：底层异常属于实现细节（比如参数格式错误），不想暴露给调用方/日志，
# 就用 from None 让 Python 不打印 "During handling of the above exception..." 那一段。
# 注意区别：from e 保留链；from None 隐藏链；什么都不写则会自动生成 __context__（也会显示链）。
try:
    int("abc")                                 # 这行必抛 ValueError
except ValueError:                             # 接住底层异常
    raise BusinessError("参数非法") from None    # 不显示底层 ValueError   ← 只保留业务异常，避免噪声
```

## 三、自定义异常：项目的正确做法

```python
# ---- 本段讲：自定义业务异常体系（三层结构） ----
# ① 一个业务异常基类 AppException：统一携带 code / message / detail，并定制 __str__；
# ② 若干具体异常：只负责传参，调用方按类型捕获；
# ③ 边界统一转换：把异常翻译成 {"code": ..., "message": ...} 返回体。
# 对照 Java：基类 ≈ BusinessException，具体类 ≈ 继承它的子类，③ ≈ @RestControllerAdvice。
# 1. 定义业务异常基类
class AppException(Exception):                    # 继承内置 Exception（相当于 Java extends RuntimeException）
    """所有业务异常的基类"""                       # 文档字符串，可用 AppException.__doc__ 读取
    def __init__(self, code: str, message: str, *, detail: dict | None = None):   # * 后面的参数只能用关键字传
        super().__init__(message)                 # 先调父类构造，让 e.args / str(e) 有内容（必须在设置字段之前或之后都行，习惯先调）
        self.code = code                          # 业务错误码，如 ORDER_NOT_FOUND
        self.message = message                    # 可读消息
        self.detail = detail or {}                # None 时退化成空字典，避免后面取值报错

    def __str__(self):
        return f"[{self.code}] {self.message}"    # 等价 Java 重写 getMessage()/toString()，日志里更好读


# 2. 具体异常
class OrderNotFound(AppException):                # 子类只需固定错误码与消息模板
    def __init__(self, order_no: str):
        super().__init__("ORDER_NOT_FOUND", f"订单不存在：{order_no}", detail={"order_no": order_no})   # 调基类构造并补 detail

class InsufficientStock(AppException):            # 另一个具体异常
    def __init__(self, sku: str, required: int, available: int):
        super().__init__(                              # 多行调用：参数分两段
            "INSUFFICIENT_STOCK",                      # 固定错误码
            f"库存不足：{sku} 需要 {required} 现有 {available}",   # 明细消息
            detail={"sku": sku, "required": required, "available": available},   # 结构化上下文，便于前端/日志使用
        )


# 3. 边界统一转换（FastAPI 里的异常处理器，见 11 篇）
try:
    do_business()                                 # 业务逻辑，可能抛任意 AppException 子类
except AppException as e:                         # 只接业务异常，其他异常继续冒泡（重要）
    return {"code": e.code, "message": e.message, "detail": e.detail}   # 转成统一响应体，对应 Java 的 Result.fail(...)
```

### 对照项目的 Java 做法

```java
// 项目的 GlobalExceptionHandler
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result handle(BusinessException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }
}
```

Python 的 FastAPI 等价物：

```python
# ---- 本段讲：FastAPI 版全局异常处理器 ----
# @app.exception_handler(X) 相当于 Spring 的 @ExceptionHandler(X.class)，统一兜住某类异常。
# 注意 status_code=200 是业务约定：HTTP 层算"请求成功"，真正的结果看 body 里的 code。
# async def 表示协程函数；FastAPI 会在有异常时自动调用它（详见 11 篇）。
from fastapi import FastAPI, Request               # FastAPI 应用类；Request 用于读取请求上下文
from fastapi.responses import JSONResponse         # 构造 JSON 响应

app = FastAPI()                                    # 创建应用实例（Java 里由 Spring Boot 自动创建容器）

@app.exception_handler(AppException)               # 注册：捕获 AppException 及其所有子类
async def handle_app_exception(request: Request, exc: AppException):   # 参数由框架注入，不用手动传
    return JSONResponse(                           # 返回 JSON 响应对象
        status_code=200,          # 业务异常用 200 + code 表达（与 Java 侧一致）
        content={"code": exc.code, "message": exc.message, "detail": exc.detail},   # 手工组装的响应体
    )
```

## 四、EAFP vs LBYL：两种编程哲学

| 缩写 | 全称 | 含义 | 对应 Java 习惯 |
|---|---|---|---|
| LBYL | Look Before You Leap | 先检查再操作 | `if (x != null)` |
| EAFP | Easier to Ask Forgiveness than Permission | 先做，出错再处理 | try-catch 兜底 |

**Python 社区推崇 EAFP**，因为检查和处理之间有竞态窗口：

```python
# ---- 本段讲：EAFP（先做，出错再处理） ----
# LBYL 是"先检查再操作"，Java 习惯；EAFP 是"直接做，异常兜底"，Python 习惯。
# 原因是"检查"和"操作"之间存在时间窗口（TOCTOU）：检查时存在，读取时可能已被删除。
# 例外场景：用户输入校验、代价极高的操作，仍应做显式检查（要给出明确错误信息）。
# LBYL：检查后文件可能被删（TOCTOU 竞态）
if Path(p).exists():                              # 先判断存在
    content = Path(p).read_text()      # ❌ 这一步仍可能 FileNotFoundError   ← 两步之间文件可能被别的进程删掉

# EAFP：直接做
try:
    content = Path(p).read_text(encoding="utf-8")   # 直接读，成功就走正常路径
except FileNotFoundError:                          # 只处理"不存在"这一种情况
    content = ""                                   # 兜底成空字符串
```

```python
# ---- 本段讲：EAFP 的另外两个典型场景（字典取值、字符串转数字） ----
# 字典：先用 in 判断再取值要哈希两次，用 .get() 一次搞定，还能顺便给默认值。
# 类型转换：Python 的 int() 失败必抛 ValueError，与其写一堆正则判断，不如直接转 + 兜底。
# Java 对照：d.get("key") 返回 null 需要判空；Integer.parseInt 抛的是 NumberFormatException。
# LBYL：字典检查
if "key" in d:                                    # 第一次哈希：判断键是否存在
    v = d["key"]         # 两次哈希查找   ← 第二次哈希：真正取值

# EAFP / Pythonic：一次
v = d.get("key")         # 或者 try: d["key"] except KeyError   ← get 不存在返回 None，可传第二参数给默认值

# 类型转换
# ❌ 检查字符串是不是数字很麻烦
# ✅ 直接转，失败就处理
try:
    n = int(s)                                    # 成功即得到整数（自动去掉首尾空白，允许正负号）
except ValueError:                                # "abc"、""、"1.5" 都会走到这里
    n = 0                                         # 兜底默认值
```

> **但在**以下场景仍应 LBYL：校验用户输入（要给明确错误信息）、幂等操作、代价高的异常。判断标准：**异常是否"预期内的常规分支"**。是 → EAFP；只是"非法输入" → 校验。

## 五、`with`：上下文管理器（Java 的 try-with-resources）

### 问题：不用 with 会怎样

```python
# ---- 本段讲：不用 with 的风险 vs 用 with 的保证 ----
# with 是 Python 的"上下文管理器"语法，等价 Java 的 try-with-resources。
# 但能力更强：Java 要求类实现 AutoCloseable；Python 只要实现 __enter__ / __exit__ 两个方法，连继承都不用。
# with 块结束（正常结束 / return / 抛异常）时都会调用 __exit__，所以文件一定能关。
# ❌ 如果 write 抛异常，f 不会关闭   ← 没有 try/finally 保护，句柄泄漏
f = open("a.txt", "w")                            # 打开文件（写模式会清空原内容）
f.write("x")                                      # 若这里抛异常（如磁盘满）
f.close()                                         # 这一行就被跳过，文件句柄一直占着

# ✅ with 保证关闭（即使抛异常）
with open("a.txt", "w", encoding="utf-8") as f:   # as f 接收 __enter__ 的返回值（这里就是文件对象）
    f.write("x")                                  # 块内随便抛异常都没关系
# 出了 with 块，f 自动 close()   ← 由 __exit__ 负责，等价 Java 的 try-with-resources 自动 close
```

`with` 能管的不只是文件——**任何实现了 `__enter__` / `__exit__` 的对象**都能用。这是 `try-with-resources` 的超集（Java 要求实现 `AutoCloseable`，Python 只要两个魔术方法，连继承都不需要）。

### 多资源

```python
# ---- 本段讲：同时管理多个资源 ----
# 两种写法都等价于 Java try-with-resources 里写多个资源（try (A a = ...; B b = ...)）。
# 关闭顺序与打开顺序相反（后开先关），由解释器保证。
# 第一种用反斜杠续行；3.10+ 推荐第二种括号写法，增删资源时不会漏改反斜杠。
# 注意：反斜杠必须是该行最后一个字符，后面不能再写注释，否则语法错误
with open("in.txt", encoding="utf-8") as src, \
     open("out.txt", "w", encoding="utf-8") as dst:    # 第二个资源；两个都会自动关闭
    for line in src:                                   # 逐行迭代文件对象，内存恒定（不整体读入）
        dst.write(line.upper())                        # 转大写后写出，等价 Java 的 line.toUpperCase()

# Python 3.10+ 可以用括号换行（更清晰）
with (
    open("in.txt", encoding="utf-8") as src,          # 资源 1
    open("out.txt", "w", encoding="utf-8") as dst,    # 资源 2（末尾逗号允许）
):
    ...                                                # 省略的处理逻辑
```

### 自己实现上下文管理器

```python
# ---- 本段讲：自己实现上下文管理器（__enter__ / __exit__） ----
# 执行流程：进入 with → 调 __enter__ 并把返回值交给 as 变量 → 执行块 → 调 __exit__（无论是否异常）。
# __exit__ 的三个参数是 (异常类型, 异常实例, 堆栈)；正常退出时三者都是 None。
# __exit__ 的返回值是"是否吞掉异常"：返回 True 会抑制异常继续上抛，返回 False/None 则正常抛出。
# Java 对照：等价 AutoCloseable.close()，但 Java 的 close 拿不到异常信息，也不能决定是否吞掉。
import time                                   # 标准库，提供高精度计时器

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()      # 记录起始时间（perf_counter 精度高，适合测耗时）
        return self                         # 返回值给 as 后面的变量   ← with Timer() as t: 时 t 就是 self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.cost = time.perf_counter() - self.start   # 计算耗时
        print(f"耗时 {self.cost*1000:.2f}ms")          # 乘 1000 转毫秒，:.2f 保留两位
        return False                        # False = 不吞异常；True = 吞掉   ← 这里让异常继续传播

with Timer():                                 # 没有 as，因为不需要用到 self
    sum(range(1_000_000))                     # 被测代码：对 0..999999 求和
# 耗时 18.34ms   ← 即使上面抛异常，这行打印依然会执行
```

`__exit__` 的三个参数：

```text
exc_type  异常类（正常退出时为 None）
exc_val   异常实例
exc_tb    堆栈
```

**返回值决定是否吞异常**——这是最容易踩的坑：

```python
# ---- 本段讲：__exit__ 返回 True 会静默吞异常（危险示例） ----
# Swallow 的 __exit__ 用 *args 接住全部三个参数并直接 return True，
# 于是 with 块里抛出的任何异常都被"消化"，后面的代码继续执行——调试时极难发现。
# 正确做法：只在明确需要"忽略特定异常"时返回 True，且最好只判断特定异常类型。
class Swallow:
    def __enter__(self): return self          # 进入时返回自身（一行写完，等价于 return self 换行）
    def __exit__(self, *args):                # *args 收下 exc_type/exc_val/exc_tb 三个参数
        return True          # ❌ 悄悄吞掉所有异常，调试时极其痛苦

with Swallow():                               # 进入上下文
    raise ValueError("你看不到我")            # 本应中断程序，但被 __exit__ 的 True 抑制了
print("继续执行")                              # 所以这行真的会打印
```

### 用 `@contextmanager` 写更省事（生成器版）

```python
# ---- 本段讲：@contextmanager（用生成器写上下文管理器） ----
# @contextmanager 把"一个生成器函数"变成上下文管理器：
#   yield 之前 = __enter__ 的逻辑；yield 的值 = as 收到的值；
#   yield 之后 = __exit__ 的逻辑（异常会在这行重新抛出，所以必须包 try/finally 才能保证清理）。
# 好处：不用写类，省掉 __enter__/__exit__ 样板；坏处：只能用一次（生成器一次性）。
from contextlib import contextmanager          # 标准库，把生成器转成上下文管理器

@contextmanager
def timer(label=""):                           # 生成器函数，yield 一次
    start = time.perf_counter()                # 进入 with 时执行（= __enter__）
    try:
        yield                        # yield 之前 = __enter__，之后 = __exit__   ← yield 本身把控制权交回 with 块
    finally:                                   # 无论正常结束还是异常，都走这里（关键）
        print(f"[{label}] {time.perf_counter() - start:.4f}s")   # 打印耗时，:4f 保留四位

with timer("计算"):                             # 调用得到的对象支持 with 语法
    sum(range(100_000))                        # 被测代码；即使抛异常，上面的 finally 也会打印
```

**关键**：`yield` 必须放在 `try/finally` 里，否则异常发生时清理代码不执行。

### 实用模板：数据库事务

```python
# ---- 本段讲：实用模板 · 数据库事务 ----
# 这是 @contextmanager 最经典的用法：把 commit/rollback 封装起来，业务代码只写 SQL。
# 三段逻辑：yield 前（无）→ yield conn（把连接交给 with 块）→ 正常则 commit，异常则 rollback 并 raise。
# Java 对照：@Transactional 注解自动做同样的事；没有框架时只能手写 try/catch + rollback。
@contextmanager
def transaction(conn):                        # conn 是已打开的数据库连接
    try:
        yield conn                            # 把连接交给 with ... as c；块内正常结束就走下面 commit
        conn.commit()                         # 只有块内没抛异常才会执行，提交事务
    except Exception:                         # 块内任何异常都会在这里被捕获
        conn.rollback()                       # 回滚，撤销本次事务的所有改动
        raise               # 必须重新抛，别吞   ← 单 raise 原样抛出，让上层知道失败了

with transaction(conn) as c:                  # c 就是 yield 出来的 conn
    c.execute("INSERT ...")                   # 块内可能抛异常 → 自动回滚
```

## 六、文件读写：`pathlib` 优先

### 老写法 vs 新写法

```python
# ---- 本段讲：老写法 os.path vs 新写法 pathlib ----
# os.path.join 返回普通字符串，用错分隔符、忘记 close、忘记指定编码都是常见坑。
# pathlib.Path 是对象化路径（对应 java.nio.file.Path），支持 / 运算符拼路径、read_text 一行读写。
# 关键点：Path / "子路径" 会按当前系统自动用 \ 或 /，所以同一份代码能跨 Windows/Linux。
import os                                     # 老式路径/文件 API

# ❌ 老写法（字符串拼接路径，Windows 下坑多）
path = os.path.join("data", "sub", "a.txt")   # 得到 "data\\sub\\a.txt"，仍是字符串
content = open(path).read()                   # 没指定 encoding → 用系统默认（Windows=GBK）；也没 close

# ✅ 新写法（pathlib，跨平台）
from pathlib import Path                      # 面向对象的路径类

path = Path("data") / "sub" / "a.txt"     # 用 / 拼路径，自动处理分隔符   ← 等价 Java 的 Path.of("data","sub","a.txt")
content = path.read_text(encoding="utf-8")    # 一步完成"打开-读-关闭"，且显式指定编码
```

### `Path` 常用 API（对照 `java.nio.file.Path` + `Files`）

```python
# ---- 本段讲：Path 常用 API 速查（重点是"属性不用加括号，方法要加括号"） ----
# 下面每一行都是"表达式 + 预期值"的速查表，可以逐行粘到 REPL 里验证。
# 属性类（name/stem/suffix/parent/parts）后面不加 ()；方法类（exists/mkdir/read_text）必须加 ()。
# 对照 Java：Path 提供路径结构，Files 提供读写/判断，Python 把两者合并到 Path 一个类上。

p = Path("D:/Projects/data/report.csv")       # Windows 下用 / 也能识别（pathlib 会归一化）

p.name              # 'report.csv'   ← 文件名（含扩展名），对应 Java 的 getFileName()
p.stem              # 'report'   ← 去掉最后一个后缀
p.suffix            # '.csv'   ← 扩展名（带点）
p.parent            # Path('D:/Projects/data')   ← 上级目录
p.parents[0]        # 同上   ← parents 是"所有祖先"的序列，下标 1 是再上一层
p.parts             # ('D:', 'Projects', 'data', 'report.csv')   ← 拆成不可变元组

# 存在性 / 类型
p.exists()          # 路径是否存在（文件或目录都算）
p.is_file()         # 是否是文件
p.is_dir()          # 是否是目录

# 创建 / 删除

p.unlink(missing_ok=True)                            # 删文件   ← missing_ok=True 表示不存在也不报错
Path("dir").rmdir()                                  # 删空目录   ← 非空会抛 OSError

# 读写（一行搞定）
p.read_text(encoding="utf-8")                        # 读全部文本；不传 encoding 就用系统默认（Windows 坑）
p.write_text("内容", encoding="utf-8")               # 覆盖写；同样要显式编码
p.read_bytes()                                       # 读二进制，返回 bytes
p.write_bytes(b"...")                                # 写二进制，参数必须是 bytes

# 遍历
for f in Path(".").iterdir():           # 直接子项   ← 只一层，不递归
    print(f)
for f in Path(".").rglob("*.py"):       # 递归匹配   ← rglob = recursive glob，等价 **/*.py
    print(f)
for f in Path(".").glob("**/*.log"):    # 同上   ← ** 表示任意层级目录
    print(f)

# 信息
p.stat().st_size          # 字节数   ← 对应 Java Files.size(p)
p.stat().st_mtime         # 修改时间戳   ← Unix 秒数（float）
from datetime import datetime
datetime.fromtimestamp(p.stat().st_mtime)    # 转成可读的本地时间字符串

# 绝对路径 / 相对
p.resolve()                                  # 转绝对路径，并解析 .. 与符号链接
p.relative_to(Path("D:/Projects"))           # 求相对路径；不在该目录下会抛 ValueError

# 改名 / 移动
p.rename(new_path)                           # 重命名/移动；目标已存在时行为随平台而变，跨盘移动建议用 shutil.move
```

### 大文件：必须逐行读

```python
# ---- 本段讲：大文件必须逐行读（内存恒定） ----
# read_text() 会把整个文件读进内存并构造完整字符串，1GB 文件就直接吃 1GB 以上内存。
# for line in f 是"流式迭代"：每次只取一行，内存占用与文件大小无关。
# Java 对照：Files.readAllLines 一次性载入；大文件要用 BufferedReader.readLine() 循环。
# ❌ 一次读进内存，1GB 文件直接爆
lines = Path("huge.log").read_text(encoding="utf-8").splitlines()   # 先整体读成 str，再切成 list，内存翻倍

# ✅ 逐行迭代，内存恒定
with open("huge.log", encoding="utf-8") as f:   # 文件对象本身可迭代，with 保证关闭
    for line in f:                              # 每次产出一行，行尾仍带 \n
        process(line.rstrip("\n"))              # rstrip 去掉行尾换行符（Windows 下还有 \r）
```

### 模式说明

| 模式 | 含义 | 文件不存在 |
|---|---|---|
| `"r"` | 读（默认） | `FileNotFoundError` |
| `"w"` | 写（**清空**） | 创建 |
| `"a"` | 追加 | 创建 |
| `"x"` | 独占创建 | `FileExistsError`（安全写法） |
| `"r+"` | 读写 | 报错 |
| `"rb"` / `"wb"` | 二进制 | — |

> **`"w"` 会静默清空文件**。想"存在就报错"用 `"x"`，想"追加"用 `"a"`。这是生产事故高发点。

## 七、编码：**Windows 上的第一号坑**

### 问题现象

```python
# ---- 本段讲：Windows 编码问题的现象 ----
# 根因只有一句：不显式指定 encoding 时，open() 用"系统默认编码"。
# Windows 中文系统默认是 GBK(cp936)，于是"写的时候按 GBK 编码、读的时候也按 GBK 解码"看似正常，
# 但只要有一方用了 UTF-8（比如文件是别人在 Linux 上生成的），就会抛 UnicodeDecodeError。
# 这里写 "中文" 用的是默认编码，随后读也用默认编码，看起来能跑；一旦换环境就炸。
# 在 Windows 上（系统默认编码 GBK）
Path("a.txt").write_text("中文")                # 未指定 encoding → 按 GBK 写入字节
# 然后读
Path("a.txt").read_text()                       # 未指定 encoding → 按 GBK 解；若文件其实是 UTF-8 就会出错
# UnicodeDecodeError: 'gbk' codec can't decode byte 0xad in position 3   ← 典型报错：字节序列不符合 GBK
```

或者在控制台 print 中文时报：

```text
UnicodeEncodeError: 'gbk' codec can't encode character '\u2014'
```

### 根因

```python
# ---- 本段讲：确认当前环境的默认编码 ----
# 写跨平台代码前，先用这两行看看本机的"默认"是什么，能快速定位编码问题。
# locale.getpreferredencoding() 是 open() 的默认编码来源；sys.stdout.encoding 是控制台输出的编码。
# 两者可能不同：文件读写走前者，print 走后者，所以"文件能写但控制台乱码"是可能的。
import locale, sys                            # 逗号分隔一次导入两个模块（Java 要写两个 import）
print(locale.getpreferredencoding())     # Windows 上通常是 'cp936'（GBK）   ← open() 的默认编码
print(sys.stdout.encoding)               # 也是 'cp936' / 'utf-8' 视终端而定   ← print 的编码，受终端/重定向影响
```

`open()` 不指定 `encoding` 时，用**系统默认编码**。Linux/macOS 是 UTF-8，Windows 是 GBK。所以同一份代码在 Linux 上跑得好好的，到 Windows 就炸。

**Java 的对照**：Java 的 `Files.readString(path)` 默认也是 UTF-8（JDK 18+），而 `FileReader` 早期版本用平台编码——同样的坑。但 Java 程序员被教育"永远指定 Charset"，Python 里这个教育不够普及。

### 正确做法（三条铁律）

```python
# ---- 本段讲：编码三条铁律 ----
# ① open() 永远显式写 encoding="utf-8"；② Path 的 read_text/write_text 也要写；
# ③ 读历史文件/不可信来源时加 errors 参数容错，避免一个坏字节让整个任务崩掉。
# errors 取值：'strict'（默认，遇错抛 UnicodeDecodeError）/ 'ignore'（直接丢）/ 'replace'（换成 �）/
#              'backslashreplace'（转成 \xNN 转义，便于排查）。
# ① 所有 open 都显式指定 encoding
with open("a.txt", encoding="utf-8") as f:     # 读也一样要指定，不能只在写的时候指定
    ...                                        # 省略的处理逻辑

# ② pathlib 的读写方法也指定
Path("a.txt").read_text(encoding="utf-8")      # 读
Path("a.txt").write_text("中文", encoding="utf-8")   # 写；两个方向都要一致

# ③ 处理不可信/历史文件时，用 errors 参数容错
Path("legacy.txt").read_text(encoding="utf-8", errors="replace")   # 坏字节变 �
# errors 可选值：'strict'(默认) 'ignore' 'replace' 'backslashreplace'
```

### 相关环境变量

```bash
# Windows 上开启 UTF-8 模式（3.7+）
set PYTHONUTF8=1

# 或者永久设置
setx PYTHONUTF8 1
```

更彻底的办法：Python 3.15 起 UTF-8 成为默认（PEP 686）。在那之前，**永远显式 `encoding="utf-8"`**。

### 其他编码坑

```python
# ---- 本段讲：另外三个高频编码坑 ----
# ① 子进程：text=True 时 Python 要用某个编码解码子进程输出，不指定就用系统默认 → Windows 上炸；
# ② json.dumps：默认 ensure_ascii=True，中文被转成 \uXXXX，日志里没法看；
# ③ CSV：Excel 靠 BOM 判断 UTF-8，所以要写 utf-8-sig（给程序读的仍用 utf-8）。
# ① 子进程输出用系统编码
import subprocess
r = subprocess.run(["cmd", "/c", "echo 中文"], capture_output=True, text=True,   # text=True 表示把 bytes 解码成 str
                   encoding="utf-8", errors="replace")   # 不指定会 UnicodeDecodeError   ← 显式指定解码方式 + 容错

# ② json.dumps 默认转义中文成 \uXXXX
import json
print(json.dumps({"名": "中文"}))                        # {"\u540d": "\u4e2d\u6587"}   ← 默认 ensure_ascii=True
print(json.dumps({"名": "中文"}, ensure_ascii=False))    # {"名": "中文"}  ✅   ← 关掉转义，便于阅读和排查

# ③ CSV 用 utf-8-sig（Excel 才认）
import csv
with open("a.csv", "w", encoding="utf-8-sig", newline="") as f:   # newline="" 防止 Windows 上多出空行
    csv.writer(f).writerows([["姓名", "金额"], ["张三", 100]])    # 一次写多行，每行是列表/元组
```

> `utf-8-sig` 会写 BOM。**给 Excel 看的文件用 `utf-8-sig`，给程序读的文件用 `utf-8`**。用错了别人打开是乱码。

## 八、JSON：只用标准库就够

```python
# ---- 本段讲：标准库 json 的常用参数 ----
# dumps = 对象 → 字符串；loads = 字符串 → 对象；dump/load 是"直接读写文件"的版本（多一个文件参数）。
# 参数速记：ensure_ascii=False 保中文、indent=2 美化、sort_keys=True 便于 diff、default=str 兜底不可序列化对象。
# parse_float=Decimal 表示解析浮点时用 Decimal，避免金额出现二进制浮点误差（对应 Java 用 BigDecimal 反序列化）。
# Java 对照：dumps ≈ ObjectMapper.writeValueAsString，loads ≈ readValue。
import json

# 序列化
data = {"name": "张三", "amount": 100.5, "tags": ["a", "b"]}   # dict 字面量，等价 Java 的 Map

json.dumps(data)                                    # → str   ← 返回 JSON 字符串，不落盘
json.dumps(data, ensure_ascii=False, indent=2)      # 中文 + 美化   ← indent 用空格缩进，便于人看
json.dumps(data, sort_keys=True)                    # 键排序（便于 diff）   ← 输出稳定，适合做快照/对比
json.dumps(data, default=str)                       # 遇到不可序列化对象时转 str   ← 类似 Jackson 自定义 Serializer 的兜底

# 反序列化
obj = json.loads('{"a": 1}')                        # 字符串 → dict（数字自动转 int/float）
json.loads('{"a": 1}', parse_float=Decimal)         # 金额用 Decimal，避免浮点误差   ← 需先 from decimal import Decimal

# 文件
with open("a.json", "w", encoding="utf-8") as f:    # 写文件同样要显式编码
    json.dump(data, f, ensure_ascii=False, indent=2)   # dump（无 s）= 直接写进文件对象

with open("a.json", encoding="utf-8") as f:         # 读文件
    data = json.load(f)                             # load（无 s）= 直接从文件对象解析
```

### 常见异常

```python
# ---- 本段讲：JSONDecodeError 携带的定位信息 ----
# 解析失败时不要只打印 "JSON 格式错误"，应把行号/列号一起带上，排查快得多。
# e.msg 是原因，e.lineno / e.colno 是行号列号（从 1 开始），e.pos 是字符偏移（从 0 开始）。
# Java 对照：Jackson 抛 JsonProcessingException，用 e.getLocation().getLineNr() 拿行号。
try:
    json.loads("{bad json}")                      # 非法 JSON，必抛异常
except json.JSONDecodeError as e:                  # 专门捕获解析错误（ValueError 的子类）
    print(e.msg, e.lineno, e.colno, e.pos)         # 分别打印：原因、行号、列号、字符偏移
```

### 与 Java Jackson 对照

| Jackson | Python json |
|---|---|
| `ObjectMapper.writeValueAsString` | `json.dumps` |
| `ObjectMapper.readValue` | `json.loads` |
| `@JsonProperty("xxx")` | 无（键名就是字段名，或自己组装 dict） |
| `@JsonIgnore` | 不放进 dict 即可 |
| `FAIL_ON_UNKNOWN_PROPERTIES` | 默认忽略未知键（更宽松） |
| `ObjectMapper` 单例 | 无需实例，模块函数 |

> **注意**：`json.loads` 对未知字段是**静默忽略**的，Java 的 Jackson 默认会报错。想严格校验用 pydantic。

## 九、`Decimal`：金额必须用它

```python
# ---- 本段讲：金额必须用 Decimal（项目里最容易被忽略的正确性点） ----
# float 是二进制浮点（同 Java 的 double），0.1 无法精确表示，所以 0.1+0.2 != 0.3。
# Decimal 用十进制存储，能精确表示小数；构造时必须传「字符串」，传 float 会把误差一起带进来。
# quantize 用来定点舍入（这里保留 2 位），rounding=ROUND_HALF_UP 是"四舍五入"（Python 默认是银行家舍入）。
print(0.1 + 0.2)            # 0.30000000000000004   ← 浮点误差
print(0.1 + 0.2 == 0.3)     # False   ← 所以金额绝对不能用 float 比较相等

from decimal import Decimal, ROUND_HALF_UP

a = Decimal("0.1")                            # 用字符串构造，精确
b = Decimal("0.2")                            # 用字符串构造，精确
print(a + b)                # 0.3        ✅   ← 十进制运算，没有误差

# 精确除法 + 舍入
total = Decimal("100") / Decimal("3")         # 结果是无限小数，Decimal 保留 28 位有效数字
print(total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))    # 33.33   ← 保留两位 + 四舍五入

# 从 float 构造是陷阱
Decimal(0.1)                # Decimal('0.1000000000000000055511151231257827')   ← float 的二进制误差被原样带入
Decimal("0.1")              # Decimal('0.1')   ✅ 永远用字符串构造   ← 或者用 Decimal(str(x))
```

```java
// Java 的对应
BigDecimal a = new BigDecimal("0.1");
a.add(new BigDecimal("0.2"));
```

> 项目里做订单、支付金额计算，**Python 必须用 `Decimal`**。这和 Java 用 `BigDecimal` 是同一个道理，但 Python 的 `float` 默认就是 Java 的 `double`，更容易忘记。

## 十、`assert`：只用于内部不变量，不用于校验入参

```python
# ---- 本段讲：assert 只用于内部不变量 ----
# assert 条件, 消息 的语义是"我确信这里条件成立，不成立说明代码有 bug"。
# 它不是校验工具：python -O 运行时所有 assert 会被整条移除，校验会凭空消失。
# Java 对照：assert 同样是可关闭的（需 -ea 开启），所以也不能用于参数校验。
def calc_ratio(a, b):
    assert b != 0, "除数不能为 0"      # ⚠️ 只在调试时生效   ← 断言失败抛 AssertionError，消息就是第二个参数
    return a / b                           # 真正的业务计算；若 b=0 且断言被移除，这里会抛 ZeroDivisionError
```

**关键**：`python -O script.py` 会**移除所有 assert**。所以：

- ❌ 不要用 `assert` 校验用户输入
- ❌ 不要用 `assert` 做权限检查
- ✅ 用它表达"这里不可能发生"的内部假设
- ✅ 用它写测试（pytest 的 `assert` 是特例，pytest 会重写字节码保留它）

## 十一、常见异常速查

| 异常 | 触发场景 | 常见修法 |
|---|---|---|
| `AttributeError` | 对象没有该属性/方法 | 检查拼写、`hasattr`、`getattr(obj, k, default)` |
| `TypeError` | 类型不对 / 参数个数不对 | 打印 `type(x)` |
| `ValueError` | 类型对但值非法（`int("abc")`） | 校验输入 |
| `KeyError` | dict 取不存在的键 | 用 `.get()` |
| `IndexError` | 列表越界 | 检查长度 / 用切片 |
| `NameError` | 变量未定义 | 作用域问题（见 04 篇） |
| `UnboundLocalError` | 函数内赋值导致局部化 | 用 `global/nonlocal` 或改名 |
| `ImportError` / `ModuleNotFoundError` | 包没装 / 路径不对 | 见 07 篇 |
| `FileNotFoundError` | 路径错 / 相对路径基准不是你想的 | 用 `Path.resolve()` 打印绝对路径 |
| `PermissionError` | 权限 / 文件被占用 | Windows 上常见：文件被 Excel 打开 |
| `UnicodeDecodeError` | 编码不匹配 | 显式 `encoding="utf-8"` |
| `RecursionError` | 递归过深 | 改迭代 |
| `RuntimeError` | 通用运行时错误（如 dict 遍历时改大小） | 复制一份再改 |
| `StopIteration` | 生成器耗尽 | 用 `for` 而非手动 `next` |
