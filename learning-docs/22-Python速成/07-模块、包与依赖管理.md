# 07 · 模块、包与依赖管理

> Java 有 `package` + `classpath` + Maven 仓库，三者分工明确。
> Python 的 `module` / `package` / `sys.path` / venv 是**四套机制拼起来的**，且没有强制约束——这是新手最容易混乱的地方。
> 本篇的目标：让你能**准确解释"为什么 import 不到"**。

---

## 一、概念对照

| Java | Python | 说明 |
|---|---|---|
| 源文件 `.java` | 模块 `.py` | 一个 `.py` 文件 = 一个模块 |
| `package com.foo;` | 目录 + `__init__.py` | 目录就是包 |
| `com.foo.Bar` 全限定名 | `foo.bar.Bar` 点分路径 | |
| `classpath` | `sys.path`（一个字符串列表） | 搜索模块的路径列表 |
| Maven 仓库 | `site-packages`（在 venv 内） | 第三方包的安装位置 |
| `import com.foo.Bar;` | `import foo.bar` / `from foo.bar import Bar` | |
| `jar` 包 | wheel（`.whl`）/ sdist（`.tar.gz`） | 分发格式 |

## 二、模块：一个 `.py` 就是一个模块

```text
project/
├── main.py
└── utils.py
```

```python
# ---- 本段讲：模块的基本单位与三种 import 写法 ----
# 这里把 utils.py 和 main.py 两个文件的代码放在同一块里展示（中间的 "# main.py" 是文件分隔线）。
# 关键认知：一个 .py 文件就是一个模块，文件名（去掉 .py）就是模块名，不需要像 Java 那样声明 package。

# utils.py
def add(a, b):
    # 模块级函数；不需要写在 class 里（Python 没有"必须用类包住"的约束）。
    # Java 对应：public static int add(int a, int b)
    return a + b              # 直接返回和；无类型声明，运行时才检查

PI = 3.14159
# 模块级常量；Python 没有 final，靠全大写命名约定表示"别改"。
# Java 对应：public static final double PI = 3.14159;


# main.py
import utils                    # 引入整个模块
# import 后，utils 这个名字成为当前命名空间里的一个模块对象；
# Java 对应 import com.foo.Utils;（但 Java 导入的是类型，Python 导入的是模块对象）
print(utils.add(1, 2))          # 必须用「模块名.成员」访问，来源一眼可见
print(utils.PI)                 # 访问模块级变量同理

from utils import add, PI       # 引入具体名字（推荐）
# 把 add / PI 直接绑定到当前命名空间，后面可以不加前缀直接用。
# Java 没有等价写法（Java 只能导入类型，不能导入方法/字段）
print(add(1, 2))                # 直接调用，简洁但看不出它是从哪个模块来的

from utils import add as plus   # 别名
# 给导入的名字起别名；Java 没有 import 别名机制
import utils as u               # 模块别名（惯例）
# 长模块名常用短别名，便于书写；之后可写 u.add(1, 2)
```

### 三种 import 形式的差异

```python
# ---- 本段讲：三种 import 形式的取舍 ----
# 差别不在"能不能跑"，而在「读代码时能否立刻看出名字的出处」以及「是否污染命名空间」。
import json                     # 需要在用时写 json.dumps —— 明确来源，推荐
# 只把模块对象 json 绑进来；Java 对应 import com.fasterxml.jackson.databind.ObjectMapper;（导入类型）
from json import dumps          # 直接 dumps —— 简洁但可能撞名
# 把函数 dumps 绑到当前命名空间；若本文件也有 dumps，后面的定义会覆盖它，且没有任何警告
from json import *              # ❌ 禁止！污染命名空间，看不出 dumps 从哪来
# 把 json 模块所有公开名字（受 __all__ 控制）一次性倒入；Java 完全没有对应语法
```

> **PEP 8 建议**：优先 `import module`，其次 `from module import name`，**永不 `import *`**（除了 `__init__.py` 里做 re-export 的受控场景）。

### `if __name__ == "__main__":` 是什么

```python
# ---- 本段讲：__name__ 的取值如何区分「被 import」和「被直接运行」----
# Python 没有 Java 的 main 方法入口约定，所以靠这个内置变量手动判断，
# 否则你的测试代码/副作用会在别人 import 时被意外执行。
# utils.py
def add(a, b):
    # 一个普通模块级函数，被 import 时只定义不调用
    return a + b

print(f"utils 被加载，__name__ = {__name__}")
# 这行在模块顶层，所以无论 import 还是直接运行都会执行 —— 用来观察 __name__ 的取值差异。
# {__name__} 是 f-string 插值；Java 里类似 String.format(...)

if __name__ == "__main__":
    # 只有直接 `python utils.py` 运行才执行
    # 直接运行时 __name__ 是字符串 "__main__"；被 import 时是模块名 "utils"
    # Java 里没有等价机制：Java 的 main 只能作为入口，类被引用时不会执行任何"顶层代码"
    print("作为脚本运行")      # 仅在直接运行时出现的副作用
    print(add(1, 2))           # 演示用；import 时不会跑这一行
```

```bash
$ python utils.py
utils 被加载，__name__ = __main__
作为脚本运行
3

$ python -c "import utils"
utils 被加载，__name__ = utils
```

**规则**：模块被 import 时 `__name__` 是模块名；被直接运行时是 `"__main__"`。

对照 Java：Java 里 `main` 方法是入口，一个类可以有 main 也可以被别的类引用，两者不冲突。Python 没有这个机制，所以要**手动加这层判断**，否则你的测试/工具代码会在 import 时被意外执行。

**必须写的场景**：

```python
# ---- 本段讲：把副作用收进 main()，再用 __main__ 判断作为开关 ----
# 这是 Python 脚本的标准骨架：import 时只"提供能力"，直接运行时才"真正干活"。
# 有副作用的模块一定要包起来
def main():
    # 真正的执行逻辑全放在这里；函数体里的 ... 是 Ellipsis，占位符，表示"此处省略实现"
    # Java 对应：public static void main(String[] args) { ... }
    ...

if __name__ == "__main__":
    main()
    # 只有本文件被直接运行时才调用 main()；被 import 时 __name__ != "__main__"，什么都不会发生
```

## 三、包：目录结构

```text
myapp/
├── __init__.py            # 包标识（3.3+ 可以没有，但建议有）
├── config.py
├── api/
│   ├── __init__.py
│   ├── chat.py
│   └── user.py
├── services/
│   ├── __init__.py
│   └── chat_service.py
└── schemas/
    ├── __init__.py
    └── chat.py
```

**这是本项目 `ai-cs-py-chat/app/` 的真实结构**，完全对应 Java 的分层：

```text
app/api/chat.py          ↔  controller/ChatController.java
app/services/chat_service.py ↔ service/ChatServiceImpl.java
app/schemas/chat.py      ↔  dto/ChatRequest.java
app/config.py            ↔  config/LlmProperties.java
app/core/llm.py          ↔  client/LlmClient.java
```

### `__init__.py` 的作用

```python
# ---- 本段讲：__init__.py 的两个用途（标识包 / 做门面 re-export）----
# app/__init__.py —— 空文件就够了（标识这是个包）
# 空文件本身没有代码；3.3+ 起没有它也能当"命名空间包"，但显式放一个更可控、IDE 更友好。
# Java 对应 package-info.java 或"目录 + package 声明"，但 Java 不需要额外空文件

# 也可以用来做"门面"（re-export），让外部 import 更短
# app/schemas/__init__.py
from .chat import ChatRequest, ChatResponse
# 开头的 . 表示"相对当前包"，即 app/schemas/chat.py；
# 把子模块里的类提到包的顶层，外部就能少写一层路径（门面模式）

__all__ = ["ChatRequest", "ChatResponse"]
# 显式声明"本包对外公开的名字"，同时决定 from app.schemas import * 会导出什么。
# Java 没有对应机制：Java 的可见性靠 public / package-private 修饰符
```

```python
# ---- 本段讲：有门面之后，调用方的 import 可以少一层 ----
# 用户侧就可以写
from app.schemas import ChatRequest      # ✅ 简洁
# 因为 schemas/__init__.py 已经把 ChatRequest 提到了包这一层
# 而不是
from app.schemas.chat import ChatRequest
# 直连子模块也能用；区别只是"是否依赖 __init__.py 的门面约定"，
# 重构时改内部文件位置只需改 __init__.py，调用方不动
```

> `__all__` 同时定义了 `from x import *` 时导出什么。

### 绝对导入 vs 相对导入

```python
# ---- 本段讲：绝对导入、相对导入、隐式当前目录导入，三者的区别 ----
# 判断标准很简单：从"项目根"能否唯一确定路径。绝对导入能，相对导入只在包内能。
# app/services/chat_service.py

# ✅ 绝对导入（推荐，清晰，重构友好）
from app.core.llm import get_llm_client
# 从项目根开始写完整路径；只要用 python -m 或 uvicorn 从项目根启动就一定能找到
# Java 对应：import com.example.app.core.LlmClient;（全限定名，本来就只能绝对导入）
from app.schemas.chat import ChatRequest
# 同样从根写起；两个 import 都一眼看出依赖了哪一层

# ✅ 相对导入（同一包内可用，但跨层时容易晕）
from ..core.llm import get_llm_client
# .. 表示"上一级包"，即从 app.services 退到 app，再进 core.llm
# . 表示当前包；.. 表示父包，可以叠加（... 表示祖父包）。Java 完全没有相对导入
from .helper import something
# .helper 指 app/services/helper.py，同包内的兄弟模块

# ❌ 最糟：隐式依赖当前目录
import llm
# 这行能不能跑取决于 sys.path[0] 里有没有 llm.py，换目录启动就报 ModuleNotFoundError
```

**建议**：**统一用绝对导入**。相对导入只在包内部紧密耦合的几个模块间用。绝对导入也让 IDE 的跳转和重构更可靠。

## 四、`import` 找不到？系统性排查

这是 Python 最高频的问题。按顺序查：

### 步骤一：确认解释器

```bash
which python          # 或 where python
python -c "import sys; print(sys.executable)"
```

如果指向的不是 `.venv/Scripts/python.exe`，说明 venv 没激活。

### 步骤二：确认包装在哪

```bash
python -c "import fastapi; print(fastapi.__file__)"
# 正常：.../ai-cs-py-chat/.venv/Lib/site-packages/fastapi/__init__.py
# 异常：.../Python312/Lib/site-packages/fastapi/__init__.py  ← 装到全局了
```

### 步骤三：看搜索路径

```bash
python -c "import sys; [print(p) for p in sys.path]"
```

`sys.path[0]` 是**脚本所在目录**（不是当前工作目录，这是关键差异）。

### 步骤四：确认模块可导入

```bash
python -m pip list | grep fastapi
python -m pip show fastapi
```

### 常见原因表

| 现象 | 原因 | 解决 |
|---|---|---|
| `ModuleNotFoundError: No module named 'app'` | 从错误的目录运行 | 在项目根运行；或用 `python -m app.main` |
| 同上，但明明有目录 | 少了 `__init__.py`（老版本）/ 目录名拼错 | 加 `__init__.py` |
| `ModuleNotFoundError: No module named 'fastapi'` | 包装在别的环境 | 用 `python -m pip install`，别用裸 `pip` |
| 有 `__init__.py` 但仍报错 | 同名文件遮蔽（`json.py` 之类） | 改名；看 `print(module.__file__)` |
| `ImportError: attempted relative import with no known parent package` | 直接运行了包内文件 | 改成 `python -m 包.模块` |
| `ImportError: cannot import name 'X' from 'Y'` | 循环导入 | 见下节 |

### 循环导入（Java 里不存在的问题）

```python
# ---- 本段讲：循环导入的成因（Python 执行到 import 才加载模块）----
# 两个文件互相 import，谁先被加载，谁就会在对方还没定义完时去取名字，于是报 ImportError。
# Java 不会这样：javac 在编译期解析类型，类之间互相引用是常态。
# a.py
from b import B      # ❌ 循环
# 加载 a 时立刻去加载 b；而 b 又反过来要 a 里的 A，此时 A 还没执行到定义语句
class A: ...
# class A: ... 是"空类"简写，类体只有 Ellipsis 占位；等价 Java 的 class A {}

# b.py
from a import A      # ❌ 循环
# 同理，b 被加载时又去要 a.A，形成环
class B: ...
```

Java 允许类之间互相引用（编译期解析），Python 执行到 `import` 那一行才去加载，所以会死循环。

**三个解法**：

```python
# ---- 本段讲：打破循环依赖的三种手段（由轻到重）----
# 解法一：延迟导入（函数内部 import）
def use_b():
    # import 写在函数体里：只有真正调用 use_b() 时才加载 b，
    # 此时模块初始化早已完成，不会再出现"名字还没定义"的窗口
    from b import B      # 用到时才导入
    return B()           # 创建实例；Java 对应在使用处才 new，类加载本身没有这个先后问题

# 解法二：只导入模块，不导入名字
import b                 # 用 b.B 访问
# 导入模块对象时不会立刻去取 B 属性，真正访问 b.B 是在运行时，从而避开初始化期的环
# 缺点：代码里到处是 b. 前缀

# 解法三：架构上解耦（根本解法）
# 把共享的部分抽到第三个模块 common.py，a 和 b 都依赖它
# 依赖关系从"环"变成"树"，这才是长期可维护的方案（也是 Java 项目里的常规做法）
```

## 五、`python script.py` vs `python -m module`

**这是最容易搞混的一组命令。**

```bash
python app/main.py          # ① 直接运行文件
python -m app.main          # ② 作为模块运行
uvicorn app.main:app        # ③ 用导入路径
```

| | ① `python app/main.py` | ② `python -m app.main` |
|---|---|---|
| `sys.path[0]` | `app/` 目录 | 当前工作目录（项目根） |
| `__name__` | `"__main__"` | `"__main__"` |
| 包内相对导入 | ❌ 报错 | ✅ 生效（若 `app` 有 `__init__.py`） |
| 能否 import 同包其他模块 | 需 `sys.path` hack | ✅ 正常 |

**结论**：**只要代码在包里，就用 `python -m`**。

```python
# ---- 本段讲：为什么包内代码必须用 python -m 启动（这是一个纯注释+片段的示例）----
# 这段没有可执行逻辑，只是展示一条会失败的导入语句及其原因。
# app/main.py 里如果写了
from app.core.llm import get_llm_client
# 这是绝对导入，要求 sys.path 里能找到名为 app 的包（即项目根在搜索路径上）

# 那么 python app/main.py 会报 ModuleNotFoundError: No module named 'app'
# 因为 sys.path[0] 是 app/，找不到 app 包
# 必须用 python -m app.main（从项目根执行）
# -m 会把 sys.path[0] 设为当前工作目录（项目根），并让 app.main 以模块身份运行
# Java 对应：java -cp 项目根 com.example.app.Main —— 同样要求 classpath 指向根
```

这就是本项目的启动方式 `uvicorn app.main:app`（等价于在项目根 `import app.main`）。

### 版本约束语法（类似 Maven 的区间）

```toml
"fastapi==0.115.0"        # 精确锁定
"fastapi>=0.115"          # 最低版本
"fastapi>=0.115,<1.0"     # 区间（推荐：防大版本破坏）
```

```xml
<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>[2.15,3.0)</version>

```

### `src/` 布局（库项目推荐）

```text
project/
├── pyproject.toml
├── src/
│   └── mylib/
│       ├── __init__.py
│       └── core.py
└── tests/
```

好处：**强制"安装后才能 import"**，避免"在本地能跑，打包后坏掉"的问题（因为 `src/` 不在 `sys.path` 里）。

服务类项目（如 `ai-cs-py-chat`）用平铺布局就行，不必强制 `src/`。

## 七、依赖管理命令速查

### pip（基础）

```bash
# 永远用 python -m pip 而不是裸 pip（保证装到当前解释器）
python -m pip install fastapi
python -m pip install "fastapi>=0.115,<1.0"
python -m pip install -r requirements.txt
python -m pip install -e .            # 可编辑安装当前项目（开发时）
python -m pip install -e ".[dev]"     # 带 extras

python -m pip list
python -m pip show fastapi
python -m pip freeze > requirements.txt
python -m pip uninstall fastapi
python -m pip index versions fastapi   # 看可用版本
```

### uv（推荐）

```bash
uv init myproject              # 初始化项目（生成 pyproject.toml）
uv add fastapi uvicorn         # 加依赖 + 自动 install
uv add --dev pytest ruff
uv remove fastapi
uv sync                        # 按 lock 文件精确还原环境
uv sync --frozen               # CI 用：lock 过期就报错
uv lock                        # 更新 lock
uv run pytest                  # 在项目环境里跑命令（不用手动激活）
uv run python app/main.py
uv tree                        # 打印依赖树（Maven dependency:tree）
uv pip list
uv python list                 # 看可用的 Python 版本
uv python pin 3.12             # 固定版本（写 .python-version）
```

> 团队协作强烈建议 `uv`：`uv.lock` 是跨平台精确锁文件，解决了 `requirements.txt` 的传播性问题（后者只记录直接依赖的版本，传递依赖会漂移）。

## 九、打包发布（只在要发库时需要）

```bash
uv build                    # 产出 dist/*.whl + *.tar.gz
python -m pip install dist/ai_cs_py_chat-0.1.0-py3-none-any.whl
```

对照 Java 的 `mvn package`：

| Maven | Python |
|---|---|
| `mvn package` → `.jar` | `uv build` → `.whl` |
| `mvn install` → 本地仓库 | `pip install dist/x.whl` |
| `mvn deploy` → Nexus | `twine upload dist/*` → PyPI / 私有 index |
| `<packaging>jar</packaging>` | `[build-system] build-backend` |

**服务类项目不需要打包发布**——直接部署源码 + `pip install -r requirements.txt` 即可，这也是 Python 部署比 Java 简单的原因（没有 fat jar 概念）。

## 十、Docker 部署（与项目 `deploy/` 呼应）

```dockerfile
FROM python:3.12-slim

WORKDIR /app

# 先拷依赖清单，利用层缓存（对应 Java 里先 copy pom.xml）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 再拷源码
COPY app ./app
COPY .env.example .env

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

对照 Java 的 Dockerfile：

```dockerfile
# Java 版
FROM eclipse-temurin:17-jre
COPY target/app.jar app.jar
CMD ["java", "-jar", "app.jar"]
```

**关键差异**：Java 是"构建产物进镜像"（镜像小、启动可预期）；Python 是"源码 + 依赖进镜像"（镜像大、但不用打包步骤）。
