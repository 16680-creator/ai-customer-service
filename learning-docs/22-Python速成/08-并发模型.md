# 08 · 并发模型（**Java 程序员最大的认知差**）

> 这一篇是全目录**最重要**的一篇。
> 你写 Java 的直觉是"加线程池"，在 Python 里这个直觉会让你写出**看起来并发、实际串行**的代码。
> 核心原因只有一句话：**GIL 让纯 Python 代码无法利用多核**。

## 一、先记住这张决策表

| 任务类型 | 特征 | 用什么 | Java 对应 |
|---|---|---|---|
| IO 密集（HTTP、DB、文件） | 大量等待 | **`asyncio`**（单线程协程）或线程池 | `CompletableFuture` + 异步 IO |
| CPU 密集（计算、加解密） | 吃 CPU | **`multiprocessing`** / `ProcessPoolExecutor` | 线程池（Java 没有 GIL） |
| 混合 | 都有 | 异步 IO + 把 CPU 部分丢进程池 | |
| 简单脚本 | 跑一会儿就结束 | 串行，别并发 | |

**一句话记忆**：

```text
Python 的多线程 = 并发（concurrency），不是并行（parallelism）
Python 的多进程 = 真并行
```

## 二、GIL 是什么

**GIL（Global Interpreter Lock）**：CPython 解释器里有一把全局锁，**任何时刻只有一个线程在执行 Python 字节码**。

```text
线程 A  ──[拿GIL]──执行──[每 5ms 或遇 IO 释放]──▶
线程 B  ──────────等待 GIL──────────[拿到]──执行──▶
                                  ↑ 永远在排队，不是同时
```

### 实证：多线程跑 CPU 密集任务没有加速

```python
# ---- 本段讲：用同一份 CPU 任务对比「串行 vs 4 线程」，证明 GIL 让多线程无法加速 ----
# 预期结果：两者耗时几乎相同（甚至多线程更慢），因为同一时刻只有一个线程能执行字节码。
# Java 里同样的代码应当接近 4 倍加速 —— 这是 Java 程序员最先要建立的认知差。
import time                     # perf_counter() 高精度计时；对应 System.nanoTime()
import threading                # 线程 API；对应 java.lang.Thread

def cpu_task(n):
    # 纯计算函数：循环里没有任何 IO，执行期间必须一直占着 GIL
    total = 0                   # 累加器；Python 无需声明类型，赋值即定义（Java 要写 int total = 0;）
    for i in range(n):          # range(n) 是惰性序列；等价 for (int i = 0; i < n; i++)
        total += i * i          # 读-改-写三步，纯 Python 字节码，GIL 不释放
    return total                # 返回 int

N = 5_000_000                   # 单次计算量；下划线只是可读性分隔符

# 串行
start = time.perf_counter()     # 计时起点
for _ in range(4):              # 连续跑 4 次，作为加速比的分母
    cpu_task(N)                 # 丢弃返回值，只关心耗时
serial = time.perf_counter() - start   # 串行总耗时

# 4 个线程
start = time.perf_counter()     # 重新计时
threads = [threading.Thread(target=cpu_task, args=(N,)) for _ in range(4)]
# 列表推导式建 4 个线程；target 是入口函数，args 必须是元组（单参数也别漏逗号）
# Java 对应：new Thread(() -> cpuTask(N))，重复 4 次
for t in threads: t.start()     # 逐个启动；分号可把两条语句写一行（不推荐但合法）
for t in threads: t.join()      # 逐个等待结束；对应 Java 的 Thread.join()
threaded = time.perf_counter() - start # 多线程总耗时

print(f"串行 {serial:.2f}s  多线程 {threaded:.2f}s")   # :.2f = 保留两位小数
# 典型结果：串行 1.20s  多线程 1.24s   ← 没有变快，甚至更慢（锁竞争开销）
```

实际跑一遍：`python code/05_concurrency/01_gil_proof.py`

### 但 IO 密集多线程有效

```python
# ---- 本段讲：换成 IO 任务后，多线程立刻有效（等待时释放 GIL）----
# 关键区别：urlopen 内部是 socket 阻塞读，线程在系统调用上等待时会主动放掉 GIL。
# 于是 8 段网络往返可以重叠，总耗时从 8 次求和变成约 1 次。
import time, threading, urllib.request
# 一行导入多个模块；等价 Java 的三条 import。urllib.request 是标准库同步 HTTP 客户端

def fetch(url):
    # with 保证连接对象无论成功失败都会关闭；对应 Java 的 try-with-resources
    with urllib.request.urlopen(url, timeout=5) as r:
        return len(r.read())    # 读完整响应体并返回字节数；r.read() 这一步会阻塞（并释放 GIL）

urls = ["https://example.com"] * 8   # 重复 8 个相同 URL；列表乘法相当于 Java 的 Collections.nCopies

# 串行：8 次网络往返
t0 = time.perf_counter()        # 计时起点
for u in urls: fetch(u)         # 一次一个，等待完全串起来
print(f"串行 {time.perf_counter()-t0:.2f}s")

# 多线程：等待时释放 GIL，其他线程可以跑
t0 = time.perf_counter()        # 重新计时
ts = [threading.Thread(target=fetch, args=(u,)) for u in urls]
# 每个 URL 一个线程；args=(u,) 的逗号是"单元素元组"语法，不能省
for t in ts: t.start()          # 全部启动
for t in ts: t.join()           # 全部等完
print(f"多线程 {time.perf_counter()-t0:.2f}s")   # 明显快数倍
```

**为什么 IO 能并发**：执行 `socket.recv()` 时线程**释放 GIL**并阻塞在系统调用上，其他线程可以拿 GIL 继续跑。所以"等待"的时间被重叠了。

### GIL 的细节（面试级）

| 问题 | 答案 |
|---|---|
| 为什么有 GIL？ | CPython 的内存管理（引用计数）不是线程安全的，加全局锁最简单 |
| 什么时候释放？ | 每 5ms（`sys.getswitchinterval()`）或遇到阻塞 IO / `time.sleep` |
| Java 有吗？ | 没有。JVM 的线程是真并行 |
| 能绕过吗？ | 用 `multiprocessing`、C 扩展（numpy 会释放 GIL）、或其他解释器（Jython 无 GIL，PyPy 有 GIL） |
| 3.13 的 free-threading 是什么？ | PEP 703 实验性无 GIL 构建（`python3.13t`），生态兼容性还在推进，生产别用 |

> **给你的判断依据**：如果一个 Python 服务的瓶颈是 CPU（比如本地跑模型推理、大 JSON 序列化），它注定要用多进程或换语言。这也是为什么 AI 推理服务多用 gRPC + 独立进程。

## 三、`threading`：怎么写，以及为什么大多数时候不该用

```python
# ---- 本段讲：threading 的最小可用写法（建线程 → start → join）----
# 注意：这里能"并发"只是因为 worker 里有 time.sleep（会释放 GIL）。
# Java 对应：new Thread(runnable).start() + join()，用法几乎一一对应。
import threading                # 线程模块；对应 java.lang.Thread
import time                     # 仅用于 sleep

def worker(name, seconds):
    # 线程入口函数：参数通过 args 元组传入，不能直接写成 worker(x, y)
    print(f"{name} 开始")       # f-string 插值；对应 String.format 或字符串拼接
    time.sleep(seconds)         # 睡一会儿；sleep 期间释放 GIL，其他线程能跑
    print(f"{name} 结束")

threads = [threading.Thread(target=worker, args=(f"T{i}", 1)) for i in range(3)]
# 一次创建 3 个线程：T0/T1/T2，各睡 1 秒。此刻线程还没启动
# Java 对应：IntStream.range(0,3).mapToObj(i -> new Thread(() -> worker("T"+i,1))).toList()
for t in threads:
    t.start()                   # 启动线程；调度由操作系统决定，输出顺序不保证
for t in threads:
    t.join()          # 等所有线程结束
    # join 无参数 = 无限等待；Java 的 join() 同理。不 join 的话主线程可能先打印"全部完成"
print("全部完成")
```

### 共享状态与锁

```python
# ---- 本段讲：共享计数器为什么必须加锁（GIL ≠ 线程安全）----
# counter += 1 会被编译成「取值 / 加一 / 写回」多条字节码，线程可能在中途被切走，
# 导致两次更新互相覆盖。Java 里同样要用 AtomicInteger 或 synchronized。
import threading                # Lock 在这里；对应 java.util.concurrent.locks.ReentrantLock

counter = 0                     # 模块级全局变量；所有线程共享同一份（Java 里相当于 static 字段）
lock = threading.Lock()         # 互斥锁对象；默认不可重入，对应 Java 的 synchronized 语义

def inc():
    global counter              # 声明"要修改模块级的 counter"；不加这句，+= 会报 UnboundLocalError
    # Java 没有这个声明：静态字段直接写类名或直接访问即可
    for _ in range(100_000):    # 循环 10 万次，制造足够多的竞争窗口
        with lock:            # ← 没有这行，结果会小于 100000
            # with 自动 acquire / finally release，比手写 lock.acquire()/release() 安全
            counter += 1        # 临界区：同一时刻只有一个线程能执行这三步
```

> **注意**：`counter += 1` 不是原子操作（读-改-写三步），GIL 只保证单条字节码原子，不保证复合操作。所以**Python 的 GIL 不能替代锁**——这是常见误解。

### 线程池（推荐姿势）

```python
# ---- 本段讲：线程池的两种取结果方式（map 按序 / as_completed 按完成顺序）----
# 与 Java 的对应关系：
#   ThreadPoolExecutor      ≈ Executors.newFixedThreadPool(n)
#   pool.map                ≈ invokeAll 后按顺序 get
#   pool.submit + Future    ≈ ExecutorService.submit 返回 Future
#   as_completed            ≈ ExecutorCompletionService
from concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url):
    # 这里的 ... 是占位符（Ellipsis），表示真实实现省略；对应 Java 接口方法体的 { ... }
    ...

with ThreadPoolExecutor(max_workers=10) as pool:
    # with 退出时自动 shutdown(wait=True)，等价 Java try-with-resources 关闭线程池
    # 方式一：批量提交，按提交顺序取结果
    results = list(pool.map(fetch, urls))
    # map 返回的是生成器，list() 一次性取完；结果顺序 = 输入顺序，与谁先算完无关

    # 方式二：边完成边处理
    futures = {pool.submit(fetch, u): u for u in urls}
    # 字典推导式建立 Future → url 的反向索引；submit 立刻返回，不阻塞
    for fut in as_completed(futures):
        url = futures[fut]              # 用 Future 反查它是哪个 URL 的任务
        try:
            print(url, fut.result())    # result() 取返回值；任务里抛的异常会在这里重新抛出
        except Exception as e:
            # 单个任务失败不影响其他任务继续跑；对应 Java 的 try/catch (ExecutionException e)
            print(url, "失败", e)
```

```java
// Java 等价
ExecutorService pool = Executors.newFixedThreadPool(10);
List<Future<Result>> futures = urls.stream().map(u -> pool.submit(() -> fetch(u))).toList();
```

**与 Java 的差异**：`pool.map` 会按输入顺序返回，和 `CompletableFuture.allOf` 类似但更简洁。`as_completed` 对应 `ExecutorCompletionService`。

### 什么时候用线程而不是 asyncio

- 用的库是**同步阻塞**的（`requests`、`pymysql`、`boto3`），且不能换
- 任务数不多（几十个以内），不想引入 async 全家桶
- 只是想把几个慢操作并行

## 四、`asyncio`：Python 的主流并发方式

### 核心概念

```text
协程（coroutine）    async def 定义的函数，调用后返回协程对象，不立即执行
事件循环（loop）     调度器，一个线程跑一个 loop，轮流执行就绪的协程
await               在此处让出控制权，等 IO 完成后再继续
Task                 被 loop 调度的协程包装
```

**关键**：单线程、单 loop，靠"遇到 await 就切换"实现并发。所以**绝不能在协程里做阻塞操作**——那会卡死整个 loop。

### 基本写法

```python
# ---- 本段讲：asyncio 的最小完整示例（async def / await / gather / asyncio.run）----
# 全程只有一个线程：三个 fetch 在 await 处轮流让出，等待时间互相重叠。
# Java 对应：CompletableFuture.supplyAsync + allOf；但 Java 默认跑在线程池上，Python 跑在单线程 loop 上。
import asyncio                  # 事件循环、gather、sleep 都在这个标准库里

async def fetch(name, seconds):
    # async def 定义协程函数：调用它只返回协程对象，不执行函数体
    print(f"{name} 开始")
    await asyncio.sleep(seconds)          # ← 非阻塞，让出控制权
    # 注意是 await asyncio.sleep，不是 time.sleep；后者会独占线程，loop 无法切换
    print(f"{name} 结束")
    return f"{name} 结果"       # 返回值通过 await / gather 拿到

async def main():
    # 并发执行三个（总耗时 ≈ 最长的 2s，而不是 1+2+2=5s）
    results = await asyncio.gather(
        fetch("A", 1),          # gather 接收协程对象，内部自动包装成 Task 并调度
        fetch("B", 2),
        fetch("C", 2),
    )
    # 返回顺序 = 传入顺序：["A 结果", "B 结果", "C 结果"]，与完成先后无关
    print(results)

asyncio.run(main())
# 创建事件循环 → 运行 main() 到完成 → 关闭循环。整个程序只调用一次，等价于启动 Reactor
```

### `gather` / `wait` / `as_completed` / `TaskGroup`

```python
# ---- 本段讲：四个核心组合子的用法差异（片段，省略了 import 和 fetch 定义）----
# 选型口诀：要全部结果用 gather；要结构化异常用 TaskGroup；要流式处理用 as_completed；要限时用 wait_for。
async def demo():
    # ① gather：等全部完成，任一抛异常则整体抛（除非 return_exceptions=True）
    results = await asyncio.gather(*coros)
    # *coros 是解包：把列表里的多个协程拆成多个位置参数
    results = await asyncio.gather(*coros, return_exceptions=True)   # 异常作为结果返回
    # 加上这个参数后不再抛异常，失败的位置放的是异常对象，调用方自己判别

    # ② 3.11+ TaskGroup：结构化并发，异常处理更清晰
    async with asyncio.TaskGroup() as tg:
        # 退出 async with 时会等组内全部任务结束；任一失败则取消其余，并抛 ExceptionGroup
        # Java 21 对应：try (var scope = new StructuredTaskScope.ShutdownOnFailure()) { ... }
        t1 = tg.create_task(fetch("A", 1))   # 立即排入事件循环，返回 Task
        t2 = tg.create_task(fetch("B", 2))
    # 出块时全部完成，任一失败会取消其余并抛 ExceptionGroup
    print(t1.result(), t2.result())          # 此时读取结果是安全的（任务保证已结束）

    # ③ as_completed：谁先完成先处理
    for fut in asyncio.as_completed([fetch("A",1), fetch("B",2)]):
        # 每次 yield 一个"可 await 的包装"，await 它才拿到返回值
        print(await fut)                     # 对应 Java 的 ExecutorCompletionService.take()

    # ④ 超时
    try:
        await asyncio.wait_for(fetch("slow", 10), timeout=1.0)
        # 最多等 1 秒；超时会取消内部协程并抛 TimeoutError。
        # Java 对应：future.get(1, TimeUnit.SECONDS) 抛 TimeoutException
    except asyncio.TimeoutError:
        print("超时")
```

> 对照：
> - `gather` ↔ `CompletableFuture.allOf`
> - `as_completed` ↔ `ExecutorCompletionService`
> - `wait_for` ↔ `future.get(1, SECONDS)`
> - `TaskGroup` ↔ Java 21 的 StructuredTaskScope

### 并发限流（对照 Java `Semaphore`）

```python
# ---- 本段讲：用 Semaphore 给协程并发数设上限（最常用的限流手法）----
# 为什么需要：asyncio 能瞬间建出上万个 Task，但下游服务扛不住，必须显式限流。
# Java 对应：java.util.concurrent.Semaphore，acquire/release 语义一致。
import asyncio

async def limited(coros, limit=10):
    # coros 是协程列表，limit 是最大并发数（默认参数，Java 需用重载实现）
    sem = asyncio.Semaphore(limit)         # ← 和 Java Semaphore 几乎一样

    async def run(c):
        # 每个协程先抢许可证，抢不到就在这里挂起等待
        async with sem:
            # 进入时 await acquire()，退出时自动 release()（异常也会释放）
            return await c          # c 是协程对象，await 它才真正执行

    return await asyncio.gather(*(run(c) for c in coros))
    # *(生成器)：任务全建出来了，但 Semaphore 保证同时只有 limit 个在跑
    # 结果顺序仍与输入顺序一致（gather 的特性）
```

或者用队列做生产者-消费者：

```python
# ---- 本段讲：用有界队列实现生产者-消费者（天然背压，内存恒定）----
# 与 Semaphore 的差别：Task 数量固定在 2 个，任务再多也不会同时建出上万个 Task。
# Java 对应：ArrayBlockingQueue + 一个生产者线程 + 一个消费者线程。
async def producer_consumer():
    q = asyncio.Queue(maxsize=100)
    # maxsize 是背压的关键：满了以后 put 会挂起生产者，直到有人消费
    # Java 对应：new ArrayBlockingQueue<>(100)

    async def producer():
        for i in range(1000):
            await q.put(i)              # 队列满时自动等待
            # put 是协程；正因为要 await，生产者才不会把内存撑爆
        await q.put(None)               # 哨兵
        # 用 None 作为"毒丸"通知消费者结束，比用取消/超时收尾更干净

    async def consumer():
        while (item := await q.get()) is not None:
            # := 是海象运算符：先赋值给 item，再用 item 参与判断（Python 3.8+）
            # 等价 Java 的 while ((item = q.take()) != null)，但 Java 里括号赋值不合法
            await process(item)         # 处理任务；process 是这里省略定义的协程
            q.task_done()               # 告诉队列"这条已处理完"；配合 q.join() 使用

    await asyncio.gather(producer(), consumer())
    # 两个协程并发跑；生产者遇到队列满会让出，消费者遇到队列空也会让出，互相推进
```

### **最大的坑：在协程里调用阻塞函数**

```python
# ---- 本段讲：一个错误示范 + 三种正确写法（本章最重要的一段）----
# 判断标准只有一句：「这个调用是 await 的吗？」不是 await 的 IO 调用一律是 bug。
# Java 类比：Mono.fromCallable(blocking) 必须 .subscribeOn(boundedElastic())，否则同理卡线程。
import asyncio, time, requests
# 一行导入三个；requests 是纯同步库，没有 async 版本（异步版是 httpx）

async def bad():
    # ❌ 阻塞整个事件循环，所有其他并发请求都会被卡住
    resp = requests.get("https://example.com")     # 同步 HTTP
    # 这里没有 await，函数一直占着唯一的事件循环线程，其他协程一秒都跑不了
    time.sleep(1)                                   # 同步 sleep
    return resp

async def good():
    # ✅ 方案一：用异步库
    import httpx                                    # 函数内 import，避免顶层强依赖
    async with httpx.AsyncClient() as client:
        # async with 负责在退出时关闭连接池（对应 Java 的 try-with-resources）
        resp = await client.get("https://example.com")   # 真异步：等待时把控制权交回 loop
    await asyncio.sleep(1)                          # 非阻塞等待
    return resp

async def also_good():
    # ✅ 方案二：把阻塞调用丢到线程池（Python 的 boundedElastic）
    loop = asyncio.get_running_loop()               # 取当前事件循环；必须在协程内调用
    resp = await loop.run_in_executor(None, requests.get, "https://example.com")
    # 第一个参数 None 表示用默认线程池；后面是"函数对象 + 位置参数"
    # 对应 Java：Schedulers.boundedElastic() 上执行阻塞调用，再切回原线程
    return resp

async def also_good_2():
    # ✅ 方案二简化版（3.9+）
    resp = await asyncio.to_thread(requests.get, "https://example.com")
    # to_thread 内部就是 run_in_executor 的语法糖，日常优先用这个
    return resp
```

> **这条规则和本项目的 Java 侧完全对应**：
> Java 里 `Mono.fromCallable(...)` 必须 `.subscribeOn(Schedulers.boundedElastic())`，否则阻塞调用占用调用方线程。
> Python 里 `await asyncio.to_thread(blocking_fn)` 就是同一件事——**把阻塞调用挪到专门的线程池**。你项目记忆里"必须显式 subscribeOn，否则超时形同虚设"的教训，在 Python 是"必须 to_thread，否则整个服务卡死"。

### 同步库怎么办

```python
# ---- 本段讲：同步数据库驱动怎么办 —— 用 to_thread 包一层，别改协程签名 ----
# sqlite3 没有异步 API，无法 await；正确做法是把整段同步调用塞进线程池。
# Java 类比：把 JDBC 调用包进 Mono.fromCallable(...).subscribeOn(boundedElastic())。
import asyncio
import sqlite3                  # 标准库内置的同步 SQLite 驱动

async def query(sql):
    # 外层保持 async，调用方照常 await，不用感知底层是同步库
    def _run():
        # 内层是普通同步函数，会在工作线程里执行；下划线前缀表示"内部使用"
        conn = sqlite3.connect("app.db")      # 建立连接（阻塞）
        try:
            return conn.execute(sql).fetchall()   # 执行 SQL 并一次性取完结果（阻塞）
            # fetchall 返回 list[tuple]，每行是一个元组
        finally:
            # 无论成功还是抛异常都关闭连接，避免句柄泄漏（对应 Java try-with-resources）
            conn.close()
    return await asyncio.to_thread(_run)
    # 把 _run 丢到默认线程池执行；await 期间事件循环可以继续处理其他协程
```

## 五、`multiprocessing`：CPU 密集的正确解法

```python
# ---- 本段讲：CPU 密集的正确解法 —— 进程池（每个进程一把独立的 GIL）----
# Java 里用线程池就够了，因为 JVM 线程真并行；Python 必须换"进程"才能吃到多核。
# 代价：启动慢、内存不共享、参数/返回值必须可 pickle。
import time
from concurrent.futures import ProcessPoolExecutor   # 进程池；API 与 ThreadPoolExecutor 几乎一致

def cpu_task(n):
    # 与线程版完全相同的纯计算函数；区别只在于它会在子进程里跑
    total = 0
    for i in range(n):
        total += i * i
    return total

if __name__ == "__main__":        # ← Windows 必须！否则子进程会重复执行模块顶层
    # Windows 用 spawn 方式启动子进程：子进程会重新 import 本模块，
    # 若没有这层保护，创建进程的代码会被子进程再执行一遍 → 无限递归/直接报错。
    # Java 没有这个问题：JVM 启动子进程不会重新执行你的 main。
    N = 5_000_000

    t0 = time.perf_counter()      # 串行基准
    for _ in range(4):
        cpu_task(N)
    print(f"串行 {time.perf_counter()-t0:.2f}s")

    t0 = time.perf_counter()
    with ProcessPoolExecutor(max_workers=4) as pool:
        # max_workers 通常取 CPU 核数；开了 4 个进程 = 4 份解释器 = 4 把 GIL
        list(pool.map(cpu_task, [N] * 4))
        # map 会把 N 逐个序列化（pickle）发给子进程，结果再序列化回来
        # list() 强制等待所有结果，否则 with 退出时才收尾，计时不准
    print(f"多进程 {time.perf_counter()-t0:.2f}s")
    # 典型：串行 1.20s  多进程 0.35s  ← 接近 4 倍加速
```

### 多进程的限制（比多线程重得多）

| 限制 | 说明 |
|---|---|
| **必须 `if __name__ == "__main__":`** | Windows 用 spawn 启动方式，会重新 import 主模块 |
| 参数和返回值必须可 pickle | lambda、局部函数、打开的连接、锁对象都传不过去 |
| 启动开销大 | 每进程几十到几百 ms，不适合短任务 |
| 内存不共享 | 每个进程独立内存，只能靠 `Queue`/`Pipe`/共享内存通信 |
| 调试困难 | 子进程异常栈不好看 |

```python
# ---- 本段讲：多进程传函数的限制 —— 必须是"可 pickle 的模块级函数"----
# 原理：子进程是独立的内存空间，函数要序列化后传过去；lambda / 嵌套函数 / 局部闭包都无法序列化。
# Java 没有这个限制：lambda 在同一个 JVM 内直接传引用（但跨进程 RPC 也同样要求可序列化）。
# ❌ 传 lambda 会失败：Can't pickle local object
pool.map(lambda x: x * 2, [1, 2, 3])
# lambda 是匿名函数，没有模块级名字，pickle 只存"模块名 + 函数名"，找不到就无法还原

# ✅ 用模块级函数
def double(x):
    # 定义在模块顶层（不是函数内部），有稳定的 import 路径，子进程能重新找到它
    return x * 2

pool.map(double, [1, 2, 3])   # 只传函数名（函数对象），不要写成 double()
```

### 什么时候真的会用多进程

- 批量图片/文档处理
- 大量文本分词/正则
- 本地 ML 推理的批处理
- **Web 服务的多 worker**：这是最常见的——`uvicorn --workers 4` 用多进程绕开 GIL

### FastAPI 里的正确与错误写法

```python
# ---- 本段讲：FastAPI 的三写法，只有 async def + await 才真异步 ----
# 规则：async def 端点跑在事件循环里；普通 def 端点被 FastAPI 丢到线程池里执行。
# 所以"async def 里写同步代码"是最坏组合 —— 既没并发，又占住了 loop。
# ✅ 正确：全异步链路
@app.post("/api/chat")          # 装饰器注册路由；对应 Spring 的 @PostMapping("/api/chat")
async def chat(req: ChatRequest):
    # req 的类型注解既是文档也是校验规则：FastAPI 会用 pydantic 自动解析 JSON 并校验
    result = await llm_client.acreate(req)      # 异步客户端
    # acreate 内部是真 await，等待 LLM 响应期间 loop 可以处理其他请求
    return result

# ⚠️ 可用但阻塞：普通 def，FastAPI 会丢到线程池（不会卡 loop）
@app.post("/api/chat")
def chat_sync(req: ChatRequest):
    # 注意这里没有 async；FastAPI 检测到是普通函数，会自动用线程池跑它
    result = llm_client.create(req)             # 同步调用，但在线程池里跑
    return result

# ❌ 最糟：async def 里调同步阻塞函数
@app.post("/api/chat")
async def chat_bad(req: ChatRequest):
    result = llm_client.create(req)             # 卡死整个 loop！
    # 这不是"少了个 await"，而是根本没有异步版本可等：同步函数无法被 await，
    # 唯一的修法是换成异步客户端，或用 asyncio.to_thread 包一层。
    return result
```

> **FastAPI 的规则**：`async def` 端点跑在事件循环里；`def` 端点跑在线程池里。所以"用 async 却写同步代码"是最坏组合——比直接写 `def` 还糟。这是 FastAPI 新手第一大坑。

```python
# ---- 本段讲：SSE 流式输出的写法（异步生成器 + yield）----
# 对照 Java WebFlux：async for ≈ Flux 的 onNext，yield ≈ emit。
# 作用：LLM 每吐一个 token 就推给前端，而不是等全部生成完再返回。
# app/api/chat.py 的流式端点 —— SSE 就是"边算边推"
async def stream(req: ChatRequest):
    async def gen():
        # 异步生成器：用 async def + yield 定义，必须用 async for 消费
        # 每被迭代一次就产出一段文本，天然适合"边算边推"
        async for chunk in llm.stream(req):
            # async for 会在每次等待下一个 chunk 时让出控制权
            yield f"data: {chunk}\n\n"
            # SSE 协议要求每行以 "data: " 开头，以两个换行结尾；少一个 \n 前端就收不到
    return StreamingResponse(gen(), media_type="text/event-stream")
    # StreamingResponse 会不断从 gen() 拉数据并 flush 给客户端
    # Java 对应：Flux<ServerSentEvent<String>> 或 SseEmitter
```

## 七、取消、超时与后台任务（对照 `Future.cancel`）

并发不只是"同时跑"，还包括**不想要的时候能停下来**。

### 取消单个任务

```python
# ---- 本段讲：取消一个协程任务（Task.cancel + CancelledError 的正确处理）----
# 注意三点：捕获后必须 raise（否则取消被吞）、清理放 finally、CancelledError 不属于 Exception。
# Java 对应：Future.cancel(true) —— 但 Java 是中断标志，Python 是在 await 点注入异常。
import asyncio

async def long_job():
    try:
        await asyncio.sleep(10)      # 这里是"可取消点"：取消请求会在 await 处抛出
        return "完成"
    except asyncio.CancelledError:
        # CancelledError 3.8+ 继承 BaseException，所以 except Exception 抓不到它
        print("收到取消，做清理")
        raise                       # 必须重新抛出，否则取消语义被吞掉
        # 吞掉（只 print 不 raise）会让调用方误以为任务正常结束，取消信号失效
    finally:
        # finally 无论正常、异常还是取消都会执行；资源释放放这里最稳
        print("释放资源")

async def main():
    task = asyncio.create_task(long_job())
    # create_task 立即把协程排进事件循环，返回 Task（对应 Java 的 submit 返回 Future）
    await asyncio.sleep(0.1)         # 让 long_job 先跑起来一点点
    task.cancel()                    # 请求取消：在下一个 await 点抛出 CancelledError
    try:
        await task                   # 等它真正结束；取消的异常在这里被重新抛出
    except asyncio.CancelledError:
        print("已取消")
```

要点：

- `CancelledError` 在 3.8+ 继承 `BaseException`，`except Exception` **抓不到**，不要用宽泛兜底吞掉取消
- 捕获后必须 `raise`（除非你明确要转成别的结果）
- 清理逻辑放 `finally`
- 不支持取消的阻塞调用（同步库）用 `to_thread` 也只能"放弃等待"，线程本身可能继续跑

### 超时不是取消的替代品

```python
# ---- 本段讲：wait_for 实现超时（超时会取消内部协程，但不是"终止线程"）----
# 陷阱：如果内部是同步阻塞调用，取消无法立刻生效，要等阻塞返回后才抛 —— 又回到"不能在 async 里阻塞"。
try:
    await asyncio.wait_for(long_job(), timeout=1)
    # 最多等 1 秒；超时后 loop 会 cancel 内部 Task 并抛 TimeoutError
    # Java 对应：future.get(1, TimeUnit.SECONDS)
except asyncio.TimeoutError:
    # 捕获超时，做降级/告警；注意 CancelledError 不在这里，它是另一种情况
    ...
```

`wait_for` 超时会取消内部的协程。**但如果内部是同步阻塞调用，取消无法立刻生效**——这又回到"async 里不能阻塞"。

### `shield`：保护不可中断的关键段

```python
# ---- 本段讲：shield 保护"已开始就不能被打断"的关键操作 ----
# 场景：请求被取消时，审计/记账/幂等落库必须写完，否则数据不一致。
# shield 让内层协程不受外层取消影响，但外层仍然立刻收到 CancelledError。
async def save_audit():
    # 真实实现省略；假设它要写数据库，中途中断会留下脏数据
    ...

try:
    await asyncio.shield(save_audit())
    # shield 把内层协程"保护"起来：外层被 cancel 时，内层继续跑完
    # Java 没有直接对应物，最接近的是把任务提交到独立线程池，使其不受当前请求中断影响
except asyncio.CancelledError:
    # 外层请求被取消，但审计写入继续完成
    raise
    # 必须继续往外抛，让调用方知道"这个请求确实被取消了"；
    # 只是内层的写库动作不会被打断
```

用在外层取消会导致数据不一致的场景（记账、审计、幂等落库）。不要滥用：`shield` 会让调用方无法及时释放，仍需自己的超时与上限。

### 后台任务要持有强引用

```python
# ---- 本段讲：后台任务必须被强引用持有，否则可能被 GC 掉且无声无息 ----
# 原因：事件循环对 Task 只保留弱引用；create_task 的结果没人存，就可能被回收。
# Java 里 ExecutorService.submit 返回的 Future 即便不保存，任务也会被执行，没有这个坑。
background: set[asyncio.Task] = set()
# 用 set 存活跃任务；类型注解 set[asyncio.Task] 只是给 IDE/mypy 看的，运行时不检查

def spawn(coro):
    # 统一的"发射后不管"入口：创建任务 → 登记 → 完成后自动移除
    task = asyncio.create_task(coro)      # 排入事件循环，立刻开始调度
    background.add(task)                  # 强引用：保证生命周期内不被回收
    task.add_done_callback(background.discard)
    # 任务完成（正常/异常/取消）后回调 discard，把引用移出集合，避免内存泄漏
    # discard 不关心元素是否存在，比 remove 安全
    return task
```

事件循环只保留弱引用，**不持有返回的 Task 可能被垃圾回收**，任务中途消失且没有明显报错。停机时统一 `cancel()` + `gather(..., return_exceptions=True)`。

### FastAPI 的 `BackgroundTasks` 边界

```python
# ---- 本段讲：FastAPI BackgroundTasks 的正确用法与适用边界 ----
# 它在"响应返回之后"才执行任务，且跑在同一个进程里 —— 进程被重启，任务就丢了。
# Java 类比：@Async 的轻量版；不适合当消息队列用。
from fastapi import BackgroundTasks

@app.post("/notify")            # 注册 POST 路由，对应 @PostMapping("/notify")
async def notify(background: BackgroundTasks):
    # 参数名 background 有类型注解，FastAPI 会自动注入一个 BackgroundTasks 实例（依赖注入）
    background.add_task(send_email, "user@example.com")
    # 只登记"要调用 send_email 和它的参数"，不会立刻执行；send_email 是普通函数即可

    # 先返回响应，再由框架在后台调用 send_email；对应 Java 的 @Async 即发即忘
```

它适合**短小、可丢失、随响应结束**的任务（发通知、写审计）。不适合：

- 长耗时导出
- 必须可靠重试的任务
- 需要进度查询的任务

这些应该进独立队列 + worker，而不是塞在 Web 进程里。

## 八、`queue` / 生产者-消费者

```python
# ---- 本段讲：线程版生产者-消费者（blocking queue，与 Java 行为一致）----
# queue.Queue 是线程安全的阻塞队列：满了 put 阻塞，空了 get 阻塞。
# Java 对应：ArrayBlockingQueue / LinkedBlockingQueue。
# 线程版
import queue                    # 注意是 queue 不是 Queue（Python 3 已重命名）
import threading

q = queue.Queue(maxsize=100)    # 有界队列，容量 100；对应 new ArrayBlockingQueue<>(100)

def producer():
    # 生产者线程：塞 100 个任务再放一个结束信号
    for i in range(100):
        q.put(i)                # 队列满时阻塞等待，自动实现背压
    q.put(None)                 # 哨兵：None 表示"没有更多任务了"

def consumer():
    # 消费者线程：一直取到 None 为止
    while (item := q.get()) is not None:
        # 海象运算符：先取再判断；q.get() 在队列空时阻塞
        print(item)             # 处理任务（这里只打印）
        q.task_done()           # 标记该条已处理完；配合 q.join() 等待全部完成

threading.Thread(target=producer).start()   # 启动生产者；没保存引用，本例不需要 join
threading.Thread(target=consumer).start()   # 启动消费者
```

```python
# ---- 本段讲：进程版队列只需换 import（API 几乎相同，但数据要 pickle）----
# 关键差异：进程间不共享内存，put 的对象会被序列化后经管道传给另一个进程。
# 所以放进去的东西必须可 pickle（不能是连接、锁、lambda）。
# 进程版（数据自动 pickle 跨进程）
from multiprocessing import Queue, Process
# Queue：跨进程队列；Process：进程类，用法与 threading.Thread 类似（target/args/start/join）
```

> 对照 Java 的 `BlockingQueue`（`ArrayBlockingQueue` / `LinkedBlockingQueue`），行为一致：满了阻塞 put，空了阻塞 get。

## 九、几个"不要做"

```python
# ---- 本段讲：六条"不要做"清单（都是踩过的坑，按严重程度排列）----
# 这段是反面清单，不是可运行示例；每条都写了"为什么错 + 正确做法"。
# ❌ 不要在 async 函数里用 time.sleep
async def f():
    time.sleep(1)          # 卡死 loop
    # 正确写法：await asyncio.sleep(1)；前者独占唯一线程，所有并发请求一起等

# ❌ 不要在 async 函数里用 requests / pymysql / boto3（同步客户端）
async def g():
    requests.get(url)
    # 正确写法：换异步库（httpx / aiomysql），或 await asyncio.to_thread(requests.get, url)
    # Java 类比：在 Reactor 线程上做阻塞 JDBC 调用，必须 subscribeOn(boundedElastic())

# ❌ 不要为了"看起来并发"而无脑加线程
#    先测量：瓶颈是 CPU 还是 IO？串行要多久？
# 没有测量就没有优化；很多"慢"其实是串行逻辑本身多余（N+1 查询之类）

# ❌ 不要用多线程写 CPU 密集代码然后疑惑为什么没变快
#    见 02 节实证
# 正确做法：ProcessPoolExecutor 或把热点逻辑交给 C 扩展（numpy 会释放 GIL）

# ❌ 不要在多进程里传不可 pickle 的东西（连接、锁、lambda、生成器）
# 进程间只能传"能被序列化还原"的对象；数据库连接/文件句柄本质上无法跨进程复制

# ❌ 不要忘了 `if __name__ == "__main__":`（Windows 多进程会崩）
# spawn 启动方式会让子进程重新 import 主模块，没有保护就会递归创建进程
```

## 十、对比总结表

| 维度 | Java | Python |
|---|---|---|
| 线程能否真并行 | ✅ | ❌（GIL，纯 Python 代码） |
| 异步模型 | 有（WebFlux / CompletableFuture / 虚拟线程） | asyncio 是主流，不是可选项 |
| CPU 密集 | 线程池 | 进程池（或 C 扩展） |
| 阻塞调用隔离 | `subscribeOn(boundedElastic)` | `asyncio.to_thread` / `run_in_executor` |
| 结构化并发 | Java 21 StructuredTaskScope | 3.11+ `asyncio.TaskGroup` |
| 虚拟线程 | Java 21 有 | 协程是另一条路，但效果接近 |
| 默认 Web 服务器并发 | Tomcat 线程池 | asyncio 单 loop（+ 多 worker 进程） |
| 共享内存 | 直接共享对象 | 线程共享，进程不共享 |
