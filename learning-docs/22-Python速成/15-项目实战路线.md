## 项目一：订单对账工具（命令行，150 行）

**难度**：★☆☆　**耗时**：2-3 小时　**覆盖**：容器 / 文件 / 异常 / 标准库

### 需求

读两个 CSV（系统订单、渠道账单），找出：

1. 系统有、渠道无（漏单）
2. 渠道有、系统无（多单）
3. 两边都有但金额不一致（金额差异）
4. 输出一份对账报告（JSON + 控制台表格）

### 输入样例

```csv
# system.csv
order_no,amount,status
NO001,100.00,PAID
NO002,200.50,PAID
NO003,50.00,REFUNDED

# channel.csv
order_no,amount,channel
NO001,100.00,ALIPAY
NO002,199.50,ALIPAY
NO004,300.00,WECHAT
```

### 输出样例

```json
{
  "missing_in_channel": ["NO003"],
  "missing_in_system": ["NO004"],
  "amount_mismatch": [
    {"order_no": "NO002", "system": 200.50, "channel": 199.50, "diff": 1.00}
  ],
  "summary": {"total_system": 3, "total_channel": 3, "matched": 1}
}
```

### 验收标准

```bash
python reconcile.py system.csv channel.csv -o report.json
# 控制台打印汇总表
# report.json 内容正确
# 金额用 Decimal，不出现 0.30000000000004 之类
```

### 参考骨架

```python
# ---- 本段讲：项目一参考骨架——命令行读两个 CSV，按订单号对账并输出 JSON 报告 ----
# 涉及：argparse / csv / Decimal / set 交并差 / pathlib / json；对应 Java 的 main + POJO + BigDecimal。
import argparse
# ↑ 解析命令行参数；≈ picocli/Spring Shell 的轻量替代
import csv
# ↑ 读写 CSV
import json
# ↑ 输出 JSON 报告
from decimal import Decimal
# ↑ 金额必须用十进制，避免 float 的 0.1+0.2 问题；≈ BigDecimal
from pathlib import Path
# ↑ 路径与文件读写；≈ java.nio.file.Path


class ReconcileError(Exception):
    # ↑ 自定义业务异常；≈ class ReconcileException extends RuntimeException
    pass
    # ↑ 类体为空，行为全部继承自 Exception


def load(path: Path, amount_field="amount") -> dict[str, Decimal]:
    # ↑ 读一个 CSV，返回 {订单号: 金额}；amount_field 允许不同表头
    if not path.exists():
        # ↑ 文件不存在属于可预期错误，抛业务异常而不是让 open 报 FileNotFoundError
        raise ReconcileError(f"文件不存在：{path}")
    out: dict[str, Decimal] = {}
    # ↑ 结果字典；类型注解说明键是 str、值是 Decimal
    with open(path, encoding="utf-8-sig", newline="") as f:
        # ↑ utf-8-sig 吃掉 Excel 的 BOM；newline="" 避免 Windows 下多出空行
        for row in csv.DictReader(f):
            # ↑ 首行作为表头，每行是 dict；≈ 逐行映射成 POJO
            no = (row.get("order_no") or "").strip()
            # ↑ 取订单号；None 用 "" 兜底后再 strip，防止脏数据
            if not no:
                # ↑ 空订单号跳过（空串是 falsy）
                continue
            out[no] = Decimal((row.get(amount_field) or "0").strip())
            # ↑ 金额为空时用 "0"；Decimal 必须用字符串构造，直接传 float 会带入误差
    return out
    # ↑ 返回订单号到金额的映射


def reconcile(system: dict[str, Decimal], channel: dict[str, Decimal]) -> dict:
    # ↑ 核心对账：比较系统订单与渠道账单
    s_keys, c_keys = set(system), set(channel)
    # ↑ 取两边订单号集合；同时赋值两个变量
    return {
        # ↑ 直接构造并返回报告字典
        "missing_in_channel": sorted(s_keys - c_keys),
        # ↑ 差集：系统有、渠道无 ⇒ 漏单；sorted 让输出稳定，便于断言/比对
        "missing_in_system": sorted(c_keys - s_keys),
        # ↑ 反向差集：渠道有、系统无 ⇒ 多单
        "amount_mismatch": [
            # ↑ 列表推导式构造金额差异列表
            {
                "order_no": no,
                "system": str(system[no]),
                # ↑ Decimal 不能直接 JSON 序列化，先转字符串
                "channel": str(channel[no]),
                "diff": str(system[no] - channel[no]),
                # ↑ 用 Decimal 相减，结果精确；再转字符串输出
            }
            for no in sorted(s_keys & c_keys)
            # ↑ 只遍历两边都有的订单（交集），排序保证输出稳定
            if system[no] != channel[no]
            # ↑ 只保留金额不一致的；Decimal 的 != 是精确比较
        ],
        "summary": {
            # ↑ 汇总统计
            "total_system": len(system),
            # ↑ 系统订单数
            "total_channel": len(channel),
            # ↑ 渠道订单数
            "matched": len(s_keys & c_keys)
            # ↑ 交集数量（两边都有的订单）
            - sum(1 for no in s_keys & c_keys if system[no] != channel[no]),
            # ↑ 再减去金额不一致的，得到真正"完全匹配"的数量
        },
    }


def main() -> None:
    # ↑ 命令行入口；≈ public static void main(String[] args)
    parser = argparse.ArgumentParser(description="订单对账工具")
    # ↑ 创建参数解析器并设置帮助描述
    parser.add_argument("system", type=Path)
    # ↑ 位置参数：系统订单 CSV；type=Path 自动转路径对象
    parser.add_argument("channel", type=Path)
    # ↑ 位置参数：渠道账单 CSV
    parser.add_argument("-o", "--output", type=Path, default=Path("report.json"))
    # ↑ 可选参数；-o 是短名，--output 是长名，默认 report.json
    args = parser.parse_args()
    # ↑ 真正解析 sys.argv；≈ 框架帮我们做的绑定

    try:
        # ↑ 读文件可能抛自定义异常，需要捕获
        report = reconcile(load(args.system), load(args.channel))
        # ↑ 先分别加载两侧数据，再对账
    except ReconcileError as e:
        # ↑ 只捕获业务异常；其他 bug 应继续抛出
        print(f"对账失败：{e}")
        # ↑ 友好提示
        return
        # ↑ 直接结束 main（返回码 0，生产可改 sys.exit(1)）

    args.output.write_text(
        # ↑ 写出报告文件（覆盖），自动关闭
        json.dumps(report, ensure_ascii=False, indent=2, default=str),
        # ↑ default=str 兜底：遇到 Decimal 等非标准类型时转字符串
        encoding="utf-8",
        # ↑ 显式 UTF-8，保证中文可读
    )
    print(f"已写出 {args.output}")
    # ↑ 提示输出路径
    print(f"漏单 {len(report['missing_in_channel'])} 笔，"
          f"多单 {len(report['missing_in_system'])} 笔，"
          f"金额差异 {len(report['amount_mismatch'])} 笔")
    # ↑ 相邻字符串字面量会自动拼接；f-string 里取各列表长度做汇总


if __name__ == "__main__":
    # ↑ 仅当作为脚本直接运行时才执行（被 import 时不跑）；≈ Java 的 main 入口判断
    main()
```

**这个骨架可以直接抄，但建议自己先写一遍再对照。** 差异点就是你要学的地方。

## 项目二：库存服务（FastAPI，400 行）

**难度**：★★☆　**耗时**：1-2 天　**覆盖**：OOP / 并发 / FastAPI / 测试 / 类型注解

### 需求

把 Java 侧的库存扣减压测逻辑用 Python 重写一遍，重点验证**并发安全**：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/stock/{sku}` | 查询库存 |
| POST | `/api/stock/{sku}/deduct` | 扣减（body: `{"qty": 1}`） |

- 并发扣减不得超卖
- 用 `asyncio.Lock` 或 DB 层原子更新
- 全部端点要有 Pydantic 模型 + 类型注解

### 关键实现点

**① 并发安全的扣减**

```python
# ---- 本段讲：项目二①并发安全扣减——asyncio.Lock 把"读-判-写"包成临界区 ----
# 为什么需要锁：先读 current 再判断再写回，中间可能被其他协程插入，导致超卖。
import asyncio
# ↑ 提供 Lock 等并发原语

class StockService:
    # ↑ 库存服务；≈ @Service
    def __init__(self):
        # ↑ 构造器：初始化库存表和锁
        self._stock: dict[str, int] = {}
        # ↑ sku → 库存数；内存版存储
        self._lock = asyncio.Lock()          # 单进程内保证原子
        # ↑ 异步互斥锁；注意只在单进程单事件循环内有效

    async def deduct(self, sku: str, qty: int) -> int:
        # ↑ 扣减库存，返回扣后数量；≈ public int deduct(String sku, int qty)
        if qty <= 0:
            # ↑ 参数校验先做，不占用锁
            raise StockError("INVALID_QTY", "数量必须为正")
            # ↑ 业务异常携带错误码，交给全局处理器转 HTTP 响应
        async with self._lock:
            # ↑ 进入临界区：同一时刻只有一个协程能执行下面的代码
            current = self._stock.get(sku, 0)
            # ↑ 读当前库存；不存在默认 0
            if current < qty:
                # ↑ 库存不足：抛异常会立即退出 with，锁自动释放
                raise StockError("INSUFFICIENT", f"库存不足：{sku} 现有 {current}")
            self._stock[sku] = current - qty
            # ↑ 写回扣减后的值；"读-判-写"整体在锁内，所以不会超卖
            return self._stock[sku]
            # ↑ 返回最新库存
```

**② 业务异常 → HTTP 响应的映射**

```python
# ---- 本段讲：项目二②把业务异常映射成 HTTP 响应，等价 @RestControllerAdvice ----
from fastapi import Request
# ↑ 请求对象，用于读取路径等信息
from fastapi.responses import JSONResponse
# ↑ 需要自定义状态码时使用

@app.exception_handler(StockError)
# ↑ 注册 StockError 的处理器；≈ @ExceptionHandler(StockException.class)
async def handle_stock(request: Request, exc: StockError):
    # ↑ 两个参数固定：请求 + 异常实例
    status = 404 if exc.code == "NOT_FOUND" else 200
    # ↑ 条件表达式：查不到返回 404，其他业务错误返回 200（用 code 表达失败）
    return JSONResponse(status_code=status,
                        content={"code": exc.code, "message": exc.message})
    # ↑ 统一响应结构；前端按 code 判断成败，不用解析 HTTP 状态
```

**③ 并发测试（项目的核心验收）**

```python
# ---- 本段讲：项目二③并发压测——同时发 200 个扣减请求，验证恰好成功 100 次 ----
@pytest.mark.asyncio
# ↑ 异步测试标记
async def test_no_oversell(client):
    # ↑ client 是 FastAPI 测试夹具
    # 库存 100，并发扣 200 次，每次 1
    await client.post("/api/stock/SKU1/restore", json={"qty": 100})
    # ↑ 先把库存回补到 100；await 等请求完成

    async def one():
        # ↑ 单个扣减请求的协程
        return await client.post("/api/stock/SKU1/deduct", json={"qty": 1})
        # ↑ 每次扣 1 件

    results = await asyncio.gather(*(one() for _ in range(200)))
    # ↑ 并发发起 200 个请求；gather 按输入顺序收集全部响应
    ok = [r for r in results if r.json().get("code") != "INSUFFICIENT"]
    # ↑ 过滤出"非库存不足"的响应，即成功次数；.get 避免键不存在报错

    stock = (await client.get("/api/stock/SKU1")).json()["stock"]
    # ↑ 查最终库存；先取响应再 json() 再取字段
    assert stock == 0
    # ↑ 100 件全部扣完，库存应为 0
    assert len(ok) == 100          # 恰好成功 100 次，不超卖
    # ↑ 若出现 101 次成功，说明锁/原子性有问题（超卖）
```

### 关键实现提示

**traceId 中间件 + JSON 日志**

```python
# ---- 本段讲：项目三①traceId 中间件 + JSON 日志，等价 Filter + MDC ----
# 关键：用 ContextVar 存 traceId（协程安全的"线程局部变量"），日志格式化器自动带上。
import json
# ↑ 把日志记录序列化成 JSON
import logging
# ↑ 标准日志框架；≈ SLF4J + Logback
import time
# ↑ 计时
import uuid
# ↑ 生成 traceId
from contextvars import ContextVar
# ↑ 协程上下文变量；≈ ThreadLocal，但在 async 下按任务隔离

trace_id_var: ContextVar[str] = ContextVar("trace_id", default="-")
# ↑ 全局上下文变量；未设置时默认 "-"


class JsonFormatter(logging.Formatter):
    # ↑ 自定义格式化器，把每条日志输出成一行 JSON；≈ Logback 的 JsonLayout
    def format(self, record: logging.LogRecord) -> str:
        # ↑ record 里包含级别、logger 名、消息等
        return json.dumps({
            # ↑ 组装结构化字段
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            # ↑ 时间戳，固定格式
            "level": record.levelname,
            # ↑ 日志级别（INFO/ERROR...）
            "logger": record.name,
            # ↑ logger 名称，通常是模块名
            "trace_id": trace_id_var.get(),
            # ↑ 自动取当前请求的 traceId；这是串联日志的关键
            "msg": record.getMessage(),
            # ↑ 已格式化的消息文本
        }, ensure_ascii=False)
        # ↑ 保留中文，避免 \uXXXX


@app.middleware("http")
# ↑ 注册 HTTP 中间件；≈ Filter
async def trace_middleware(request, call_next):
    # ↑ request=请求，call_next=调用后续链路
    tid = request.headers.get("X-Trace-Id") or uuid.uuid4().hex[:16]
    # ↑ 优先沿用上游 traceId，否则生成 16 位十六进制
    token = trace_id_var.set(tid)
    # ↑ 写入上下文变量；返回 token 用于稍后恢复（防止污染下一个请求）
    start = time.perf_counter()
    # ↑ 计时起点
    try:
        response = await call_next(request)
        # ↑ 放行到下游，拿到响应
        response.headers["X-Trace-Id"] = tid
        # ↑ 回写响应头，前端/网关可据此排查
        return response
        # ↑ 返回响应
    finally:
        # ↑ 无论成功失败都要执行收尾
        logger.info("请求完成 path=%s cost=%.1fms",
                    request.url.path, (time.perf_counter() - start) * 1000)
        # ↑ 记录路径和耗时；%s 占位符由 logging 惰性格式化
        trace_id_var.reset(token)
        # ↑ 恢复上下文，避免 traceId 泄漏到后续请求（≈ MDC.clear）
```

**SQLite 会话存储**

```python
# ---- 本段讲：项目三②SQLite 会话存储——上下文管理器封装"提交/回滚/关闭" ----
# 重点：参数化 SQL 防注入；with 块内成功才 commit，异常则 rollback。
import sqlite3
# ↑ 标准库 SQLite 驱动
from contextlib import contextmanager
# ↑ 用生成器写上下文管理器

@contextmanager
def db():
    # ↑ 每次调用创建一个连接，并交给 with 块使用
    conn = sqlite3.connect("chat.db")
    # ↑ 打开（或创建）数据库文件
    conn.row_factory = sqlite3.Row
    # ↑ 让查询结果支持按列名访问（row["role"]），否则只能按下标
    try:
        yield conn
        # ↑ 暂停，把连接交给 with 块；块内代码执行完回到这里
        conn.commit()
        # ↑ 正常结束才提交事务
    except Exception:
        # ↑ with 块内抛异常
        conn.rollback()
        # ↑ 回滚，保证数据一致性
        raise
        # ↑ 继续向上抛，不吞异常；≈ 事务模板方法
    finally:
        conn.close()
        # ↑ 无论提交还是回滚，都关闭连接


def save_message(session_id: str, role: str, content: str) -> None:
    # ↑ 追加一条消息；≈ void saveMessage(...)
    with db() as c:
        # ↑ 自动管理事务与连接
        c.execute(
            # ↑ 执行 INSERT；? 是参数占位符（不是字符串拼接）
            "INSERT INTO messages (session_id, role, content, created_at) "
            "VALUES (?, ?, ?, datetime('now'))",
            (session_id, role, content),
            # ↑ 参数以元组传入，驱动会安全转义；防 SQL 注入
        )


def load_history(session_id: str, limit: int = 20) -> list[dict]:
    # ↑ 读取最近 N 条历史，返回 OpenAI 风格的消息列表
    with db() as c:
        # ↑ 只读操作也复用同一上下文
        rows = c.execute(
            # ↑ 查询指定会话
            "SELECT role, content FROM messages WHERE session_id = ? "
            "ORDER BY id DESC LIMIT ?",
            (session_id, limit),
            # ↑ 同样参数化；LIMIT 也用占位符
        ).fetchall()
        # ↑ 取全部行（此时连接已提交/关闭前的数据）
    return [{"role": r["role"], "content": r["content"]} for r in reversed(rows)]
    # ↑ 查询是倒序取最近 N 条，reversed 恢复正序；列表推导转成 dict 列表
```

## 学习节奏建议

```text
第 1 周：项目一（命令行工具）        → 语法手感
第 2 周：项目二（库存服务）          → 服务端 + 并发 + 测试
第 3 周：项目三（增强现有服务）      → 工程能力
```

每个项目做完，做一次"回头看"：

1. 代码里有多少地方是"用 Java 思维写的 Python"？（比如多余的 class、多余的 getter）
2. 有多少地方用到了本目录讲的惯用法？（推导式、`with`、`dataclass`、`defaultdict`）
3. 哪个坑真的踩到了？（记到自己的笔记里）

第 1 项的答案会逐周下降——**这就是进步的可量化证据**。
