# 16 · 调试与故障排查手册

> Java 排障时你会看线程栈、GC、日志和 APM；Python 排障同样靠证据，只是工具不同。
> 这篇给你一套固定流程，以及 Python 服务最常见故障的定位方法。

---

## 一、固定排查流程

```text
① 稳定复现        记录请求、输入、环境、Python 版本、依赖版本
② 缩小范围        去掉中间件 / 数据库 / 网络，找最小复现脚本
③ 收集证据        完整异常栈、日志、变量值、耗时、线程/任务状态
④ 提出假设        一次只验证一个假设
⑤ 修复并回归      把最小复现写成 pytest，防止再次发生
```

**不要一上来就改代码**。没有最小复现的修复，往往只是把 bug 挪了个位置。

## 二、异常栈：先看最后一行，再找自己的代码

```text
Traceback (most recent call last):
  File "app/services/order.py", line 42, in create_order
    total = sum(item["price"] for item in items)
            ~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

读法：

1. 最后一行：**异常类型 + 具体原因**
2. 从下往上找**第一个属于你项目的文件**
3. 上面的框架栈只用于理解调用链，不要先改框架
4. 有 `The above exception was the direct cause...` 时，**最底层异常才是根因**

在边界记录完整异常：

```python
logger.exception("创建订单失败 order_no=%s", order_no)
# 等价于 logger.error(..., exc_info=True)，只能在 except 块里使用
```

不要只记 `str(e)`——很多异常的消息没有定位价值，栈才有。

## 三、pdb：没有 IDE 也能断点

```python
def calculate(items):
    subtotal = sum(items)
    breakpoint()                 # 运行到这里进入 pdb
    return subtotal * 1.06
```

```bash
python script.py
python -m pdb script.py          # 从脚本启动就调试
```

常用命令：

| 命令 | 作用 | IDEA 对应 |
|---|---|---|
| `n` | 下一行 | Step Over |
| `s` | 进入函数 | Step Into |
| `r` | 执行到当前函数返回 | Step Out |
| `c` | 继续 | Resume |
| `p expr` | 打印表达式 | Evaluate |
| `pp expr` | 美化打印容器 | — |
| `l` | 当前位置源码 | — |
| `w` | 调用栈 | Frames |
| `u` / `d` | 上/下移动栈帧 | — |
| `q` | 退出调试 | Stop |

### 崩溃后进入现场

```python
import traceback

try:
    run()
except Exception:
    traceback.print_exc()
    import pdb
    pdb.post_mortem()            # 在异常发生的位置检查变量
    raise
```

**不要在生产服务里留 `breakpoint()`**。它会让 worker 停在那里，请求全部排队。提交前用 `ruff` 的 `T100` 规则或简单 grep 检查。

## 四、比 print 更好用的检查方式

### 1. f-string 自说明变量

```python
logger.info("处理中 %s", {"order_no": order_no, "amount": amount, "step": step})
print(f"{order_no=}, {amount=}, {step=}")
```

### 2. `vars()` 看对象状态

```python
print(vars(order))              # 普通对象的 __dict__
```

### 3. `traceback` 打印调用链

```python
import traceback
traceback.print_stack(limit=10)
```

### 4. `faulthandler`：卡死时看所有线程在干什么

```python
import faulthandler
faulthandler.dump_traceback_later(30, repeat=True)   # 每 30 秒打印线程栈
```

Linux 还可以：

```bash
kill -SIGUSR1 <pid>     # 需先 faulthandler.register(signal.SIGUSR1)
```

Java 的 `jstack` 看 Java 线程；Python 的 `faulthandler` 看 Python 帧。**它能定位“服务没报错但请求不动”这类问题**。

## 五、asyncio 服务卡死：先开 debug 模式

```python
import asyncio

async def main():
    ...

asyncio.run(main(), debug=True)
```

或通过环境变量：

```bash
PYTHONASYNCIODEBUG=1 uvicorn app.main:app
```

debug 模式会发现：

- 协程创建后从未 await
- 某些 callback 执行过慢
- 事件循环阻塞
- 资源未关闭

### 三种“卡”要分开

| 现象 | 最可能原因 | 检查方式 |
|---|---|---|
| 所有请求都慢，CPU 不高 | 协程里同步阻塞 | 搜 `time.sleep` / `requests` / 同步 DB；用 `to_thread` |
| CPU 100%，请求慢 | 纯 Python CPU 计算 | cProfile；必要时进程池 |
| 只有某个外部调用慢 | 下游/网络/连接池 | 单独计时，检查超时与重试 |

定位阻塞调用：

```python
# 给每一段单独计时，不要只测整个接口
async with timed("db"):
    rows = await asyncio.to_thread(query)

async with timed("llm"):
    text = await llm.chat(...)
```

### 找出创建后未 await 的协程

```text
RuntimeWarning: coroutine 'foo' was never awaited
```

这通常不是无害警告，而是**业务逻辑根本没执行**。例如：

```python
save_order(order)          # ❌ 异步函数只创建了协程对象
await save_order(order)    # ✅
```

## 六、常见故障速查

### 1. 本地能跑，服务器 import 失败

```bash
python -c "import sys; print(sys.executable); print(*sys.path, sep='\n')"
python -c "import fastapi; print(fastapi.__file__)"
python -m pip list
```

依次检查：

1. 启动命令是不是在正确的工作目录
2. 包内代码是否用了 `python path/to/file.py`（应改 `python -m package.module`）
3. 当前解释器是不是装依赖的那个
4. 本地文件是否遮蔽标准库或第三方包（`json.py`、`typing.py`、`fastapi.py`）
5. CI/容器里是否漏装依赖

### 2. Windows 正常，Linux 失败（或反过来）

重点检查：

- 路径分隔符和大小写：Linux 文件名**大小写敏感**
- 文件编码：统一显式 UTF-8
- 多进程启动方式：Windows spawn，Linux 默认 fork
- 换行：脚本统一 LF
- 环境变量与 `.env` 路径

### 3. 测试通过，生产失败

常见差异：

| 维度 | 测试 | 生产 |
|---|---|---|
| 依赖 | Fake/Mock | 真网络、真权限、真超时 |
| 数据 | 少量、规整 | 空值、脏数据、大数据量 |
| 并发 | 顺序执行 | 多请求/多 worker |
| 环境 | 本机环境变量 | 容器环境变量、代理、时区 |
| 文件系统 | 可写临时目录 | 只读目录、不同用户 |

**修复方向**：在测试里补“并发、超时、异常输入、真实契约”，而不是简单把 mock 全部换成真实服务。

### 4. 内存持续增长

按顺序排查：

1. 全局字典/列表是否无限增长
2. `lru_cache` 的 key 是否包含高基数字段（如 user_id + 时间戳）
3. 请求结束后是否还持有 response、connection、生成器
4. 是否把大对象塞进日志上下文或 trace
5. 多 worker 下是每个进程都占一份，还是总量真的异常

```python
import tracemalloc
tracemalloc.start()
# 执行业务
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:10]:
    print(stat)
```

### 5. JSON / Pydantic 报 422

不要只看 `"message": "field required"`，重点看 `loc`：

```json
{"loc": ["body", "history", 0, "content"], "msg": "Field required"}
```

含义是 `history[0].content` 缺失。打印**实际收到的请求体**，别只看前端代码“我以为会发”。

## 七、最小复现脚本怎么写

一个合格的最小复现应该：

- 不依赖 Spring/前端/数据库/真实 LLM
- 50 行以内
- 能反复执行且结果稳定
- 失败后能直接改成测试

```python
# repro.py
from decimal import Decimal

def calc_discount(amount: Decimal, rate: Decimal) -> Decimal:
    return amount * rate

def test_calc_discount():
    assert calc_discount(Decimal("100"), Decimal("0.85")) == Decimal("85.00")

if __name__ == "__main__":
    print(calc_discount(Decimal("100"), Decimal("0.85")))
```

排障完成后把它移动到 `tests/`，补上异常输入和边界条件。**一次故障至少沉淀一条回归测试**。

## 八、线上排查安全边界

- 不在生产开 `debug=True`、pdb、交互式 shell
- 日志脱敏：API key、token、手机号、身份证、完整订单地址
- 不为了排障把日志级别永久调成 DEBUG；按需开启并设置恢复时间
- 不在请求路径里执行大对象 `deepcopy`、全量 dump 数据库
- 对生产只做只读诊断；重启、改配置、清缓存走变更流程
