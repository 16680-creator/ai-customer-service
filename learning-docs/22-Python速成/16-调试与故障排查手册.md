# 16 · 调试与故障排查手册

> Java 排障时你会看线程栈、GC、日志和 APM；Python 排障同样靠证据，只是工具不同。
> 这篇给你一套固定流程，以及 Python 服务最常见故障的定位方法。

---

## 一、固定排查流程

```text
① 稳定复现        记录请求、输入、环境、Python 版本、依赖版本
② 缩小范围        去掉中间件 / 数据库 / 网络，找最小复现脚本
③ 收集证据        完整异常栈、日志、变量值、耗时、线程/任务状态
④ 提出假设        一次只验证一个假设
⑤ 修复并回归      把最小复现写成 pytest，防止再次发生
```

**不要一上来就改代码**。没有最小复现的修复，往往只是把 bug 挪了个位置。

## 二、异常栈：先看最后一行，再找自己的代码

```text
Traceback (most recent call last):
  File "app/services/order.py", line 42, in create_order
    total = sum(item["price"] for item in items)
            ~~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

读法：

1. 最后一行：**异常类型 + 具体原因**
2. 从下往上找**第一个属于你项目的文件**
3. 上面的框架栈只用于理解调用链，不要先改框架
4. 有 `The above exception was the direct cause...` 时，**最底层异常才是根因**

在边界记录完整异常：

```python
# ---- 本段讲：在异常边界记录「完整异常栈」 ----
# logger.exception 会自动附带当前异常的类型、消息和完整调用栈，
# 等价于 Java 里的 log.error("创建订单失败 order_no={}", orderNo, e)。
# 它必须在 except 块内部调用：内部依赖 sys.exc_info() 取「正在处理的那个异常」。
logger.exception("创建订单失败 order_no=%s", order_no)    # %s 是 logging 的惰性占位符（类比 SLF4J 的 {}），只有日志真的输出时才格式化，避免无谓字符串拼接
# 等价于 logger.error(..., exc_info=True)，只能在 except 块里使用
# Java 对照：异常对象要作为最后一个参数传入，Python 则隐式取当前异常；因此不要额外再传 e。
```

不要只记 `str(e)`——很多异常的消息没有定位价值，栈才有。

## 三、pdb：没有 IDE 也能断点

```python
# ---- 本段讲：内置断点 breakpoint() 与 pdb 调试器 ----
# Python 3.7+ 的 breakpoint() 默认调用 pdb.set_trace()，作用类似 IDEA 里打断点后 Debug 运行。
# 区别：断点是「写死在源码里」的，不需要 IDE，任何机器（包括服务器容器）都能进入交互式调试。
# 代价：它会让当前线程停住等待输入，所以绝不允许留在生产代码中。
def calculate(items):            # 定义函数；参数无类型也能跑，这里假定 items 是数字序列
    subtotal = sum(items)        # 内置 sum 对可迭代对象求和，等价 Java 的 items.stream().mapToInt(...).sum()
    breakpoint()                 # 运行到这里进入 pdb
    return subtotal * 1.06       # 含税价；停在上一行时可用 p subtotal 查看变量，n 单步，c 继续
```

```bash
python script.py
python -m pdb script.py          # 从脚本启动就调试
```

常用命令：

| 命令 | 作用 | IDEA 对应 |
|---|---|---|
| `n` | 下一行 | Step Over |
| `s` | 进入函数 | Step Into |
| `r` | 执行到当前函数返回 | Step Out |
| `c` | 继续 | Resume |
| `p expr` | 打印表达式 | Evaluate |
| `pp expr` | 美化打印容器 | — |
| `l` | 当前位置源码 | — |
| `w` | 调用栈 | Frames |
| `u` / `d` | 上/下移动栈帧 | — |
| `q` | 退出调试 | Stop |

### 崩溃后进入现场

```python
# ---- 本段讲：崩溃后「进入案发现场」而不是只看日志 ----
# 思路：捕获异常 → 打印栈 → 用 pdb.post_mortem() 停在异常抛出点检查变量 → 再原样向上抛。
# Java 对照：相当于在 catch 里调用 IDE 的「Drop Frame / Evaluate」，但这里是纯命令行。
import traceback                 # 标准库，负责格式化/打印异常栈；不需要额外安装

try:                             # try/except 是 Python 的异常处理结构，等价 Java 的 try/catch
    run()                        # 执行可能出错的业务逻辑（这里的 run 是示例占位函数）
except Exception:                # Exception 是绝大多数业务异常的基类，类似 Java 的 RuntimeException 层级
    traceback.print_exc()        # 把完整调用栈打印到 stderr，包含文件名、行号、源码行和异常类型
    import pdb                   # 局部导入：只有真正崩溃时才加载调试器，平时不引入开销
    pdb.post_mortem()            # 在异常发生的位置检查变量
    raise                        # 不带参数的 raise 会原样重抛当前异常，保留原栈；Java 是 throw e;（会重置栈）
```

**不要在生产服务里留 `breakpoint()`**。它会让 worker 停在那里，请求全部排队。提交前用 `ruff` 的 `T100` 规则或简单 grep 检查。

## 四、比 print 更好用的检查方式

### 1. f-string 自说明变量

```python
# ---- 本段讲：两种「比裸 print 更好」的变量检查方式 ----
# 第一种：结构化日志，一次带出多个字段；第二种：f-string 的 = 语法，自动输出「变量名=值」。
logger.info("处理中 %s", {"order_no": order_no, "amount": amount, "step": step})    # 只传一个 dict 占位，日志里能看到三个字段；比手写字符串拼接更易检索
print(f"{order_no=}, {amount=}, {step=}")    # Python 3.8+ 调试语法：等价于打印 "order_no=值, amount=值, step=值"，不用手写变量名
```

### 2. `vars()` 看对象状态

```python
# ---- 本段讲：用 vars() 一次性查看对象的所有属性 ----
# Python 普通对象的实例属性都存在 __dict__ 字典里；Java 没有等价物，通常只能靠 IDE 查看字段或写 toString。
# 注意：使用 __slots__ 的类、内置类型（int/list）没有 __dict__，vars() 会抛 TypeError。
print(vars(order))              # 普通对象的 __dict__，输出形如 {'order_no': 'NO001', 'amount': Decimal('100.00')}
```

### 3. `traceback` 打印调用链

```python
# ---- 本段讲：主动打印「当前调用链」而不是异常栈 ----
# 适用于没有异常、但你想知道「这段代码是被谁调进来的」的场景。
# Java 对照：new Throwable().printStackTrace() 或 Thread.currentThread().getStackTrace()。
import traceback                       # 标准库：栈信息的格式化工具
traceback.print_stack(limit=10)       # 打印当前调用栈，limit=10 只保留最近 10 层，避免刷屏
```

### 4. `faulthandler`：卡死时看所有线程在干什么

```python
# ---- 本段讲：服务「卡死但不报错」时，定时导出所有线程的 Python 栈 ----
# faulthandler 是 C 层实现的看门狗，即使主线程被阻塞、GIL 被占住也能输出栈。
# Java 对照：jstack <pid> 定时抓 thread dump；这里是进程内自动定时打印。
import faulthandler                                      # 标准库，无需安装，开销极低
faulthandler.dump_traceback_later(30, repeat=True)   # 每 30 秒打印线程栈；repeat=True 表示持续打印而不是只打一次
```

Linux 还可以：

```bash
kill -SIGUSR1 <pid>     # 需先 faulthandler.register(signal.SIGUSR1)
```

Java 的 `jstack` 看 Java 线程；Python 的 `faulthandler` 看 Python 帧。**它能定位“服务没报错但请求不动”这类问题**。

## 五、asyncio 服务卡死：先开 debug 模式

```python
# ---- 本段讲：开启 asyncio 的 debug 模式，暴露「协程泄漏 / 回调过慢」 ----
# debug=True 会让事件循环记录协程的创建位置、检测从未 await 的协程、警告执行过久的回调。
# Java 对照：类似打开 Reactor/Netty 的泄漏检测（-Dio.netty.leakDetection.level=paranoid）。
import asyncio                   # 标准库的异步运行时，提供事件循环、Task、gather 等

async def main():                # async def 定义协程函数；调用它只会得到协程对象，必须 await/run 才执行
    ...                          # 省略号是合法的 Python 表达式，占位表示「这里还有业务代码」

asyncio.run(main(), debug=True)  # 创建事件循环 → 运行 main 到结束 → 关闭循环；debug=True 打开调试检查
```

或通过环境变量：

```bash
PYTHONASYNCIODEBUG=1 uvicorn app.main:app
```

debug 模式会发现：

- 协程创建后从未 await
- 某些 callback 执行过慢
- 事件循环阻塞
- 资源未关闭

### 三种“卡”要分开

| 现象 | 最可能原因 | 检查方式 |
|---|---|---|
| 所有请求都慢，CPU 不高 | 协程里同步阻塞 | 搜 `time.sleep` / `requests` / 同步 DB；用 `to_thread` |
| CPU 100%，请求慢 | 纯 Python CPU 计算 | cProfile；必要时进程池 |
| 只有某个外部调用慢 | 下游/网络/连接池 | 单独计时，检查超时与重试 |

定位阻塞调用：

```python
# ---- 本段讲：按「阶段」分别计时，定位到底是 DB 慢还是 LLM 慢 ----
# 只测整个接口只能知道「慢」，分段计时才知道「慢在哪」；这是排障的最小证据。
# timed(...) 是自定义的异步上下文管理器（示例里未展开），进入/退出时自动记录耗时。
# 给每一段单独计时，不要只测整个接口
async with timed("db"):                # async with 等价 Java 的 try-with-resources，但支持 await 的进入/退出
    rows = await asyncio.to_thread(query)    # to_thread 把同步阻塞的 DB 调用丢到线程池，避免卡住事件循环

async with timed("llm"):               # 第二段：外部大模型调用
    text = await llm.chat(...)         # await 挂起当前协程等待网络返回，期间事件循环可处理其他请求
```

### 找出创建后未 await 的协程

```text
RuntimeWarning: coroutine 'foo' was never awaited
```

这通常不是无害警告，而是**业务逻辑根本没执行**。例如：

```python
# ---- 本段讲：「调用了 async 函数却没 await」这个高频坑 ----
# async def 的函数调用后返回的是「协程对象」，不 await 它就永远不会执行，业务逻辑等于没写。
# Java 对照：类似返回了 CompletableFuture 却没 join/get，任务根本没被调度。
save_order(order)          # ❌ 异步函数只创建了协程对象；运行时会警告 coroutine was never awaited
await save_order(order)    # ✅ 真正驱动协程执行，并等待它完成（只能在 async 函数内部使用）
```

## 六、常见故障速查

### 1. 本地能跑，服务器 import 失败

```bash
python -c "import sys; print(sys.executable); print(*sys.path, sep='\n')"
python -c "import fastapi; print(fastapi.__file__)"
python -m pip list
```

依次检查：

1. 启动命令是不是在正确的工作目录
2. 包内代码是否用了 `python path/to/file.py`（应改 `python -m package.module`）
3. 当前解释器是不是装依赖的那个
4. 本地文件是否遮蔽标准库或第三方包（`json.py`、`typing.py`、`fastapi.py`）
5. CI/容器里是否漏装依赖

### 2. Windows 正常，Linux 失败（或反过来）

重点检查：

- 路径分隔符和大小写：Linux 文件名**大小写敏感**
- 文件编码：统一显式 UTF-8
- 多进程启动方式：Windows spawn，Linux 默认 fork
- 换行：脚本统一 LF
- 环境变量与 `.env` 路径

### 3. 测试通过，生产失败

常见差异：

| 维度 | 测试 | 生产 |
|---|---|---|
| 依赖 | Fake/Mock | 真网络、真权限、真超时 |
| 数据 | 少量、规整 | 空值、脏数据、大数据量 |
| 并发 | 顺序执行 | 多请求/多 worker |
| 环境 | 本机环境变量 | 容器环境变量、代理、时区 |
| 文件系统 | 可写临时目录 | 只读目录、不同用户 |

**修复方向**：在测试里补“并发、超时、异常输入、真实契约”，而不是简单把 mock 全部换成真实服务。

### 4. 内存持续增长

按顺序排查：

1. 全局字典/列表是否无限增长
2. `lru_cache` 的 key 是否包含高基数字段（如 user_id + 时间戳）
3. 请求结束后是否还持有 response、connection、生成器
4. 是否把大对象塞进日志上下文或 trace
5. 多 worker 下是每个进程都占一份，还是总量真的异常

```python
# ---- 本段讲：用 tracemalloc 抓「内存分配到哪一行」 ----
# 它统计的是 Python 层对象分配，不含 C 扩展和解释器自身，所以不能直接等于进程 RSS。
# Java 对照：JFR 的 OldObjectSample / heap dump 里的支配树，但 tracemalloc 更轻量。
import tracemalloc                          # 标准库：跟踪 Python 内存分配，默认只记录最近 25 帧
tracemalloc.start()                         # 开始跟踪；应在执行业务之前调用，否则拿不到基线
# 执行业务
snapshot = tracemalloc.take_snapshot()      # 拍一份当前分配的「快照」，记录每条分配来自哪个文件哪一行
for stat in snapshot.statistics("lineno")[:10]:    # 按源码行聚合，取占用最大的前 10 条
    print(stat)                             # 输出形如 "file.py:42: 8523 KiB"，直接指出泄漏热点
```

### 5. JSON / Pydantic 报 422

不要只看 `"message": "field required"`，重点看 `loc`：

```json
{"loc": ["body", "history", 0, "content"], "msg": "Field required"}
```

含义是 `history[0].content` 缺失。打印**实际收到的请求体**，别只看前端代码“我以为会发”。

## 七、最小复现脚本怎么写

一个合格的最小复现应该：

- 不依赖 Spring/前端/数据库/真实 LLM
- 50 行以内
- 能反复执行且结果稳定
- 失败后能直接改成测试

```python
# ---- 本段讲：一个「能当测试用」的最小复现脚本长什么样 ----
# 特点：零外部依赖、逻辑单一、自带断言、可直接运行也可被 pytest 收集。
# Java 对照：相当于一个只有 main + JUnit 断言的单文件复现类。
# repro.py
from decimal import Decimal        # 用 Decimal 而非 float，避免 0.1+0.2 这类二进制浮点误差（Java 是 BigDecimal）

def calc_discount(amount: Decimal, rate: Decimal) -> Decimal:    # 类型注解只用于提示和静态检查，运行时不强制
    return amount * rate           # 复现「折扣计算」这一条最小业务规则

def test_calc_discount():          # 函数名以 test_ 开头，pytest 会自动收集执行，无需继承任何基类
    assert calc_discount(Decimal("100"), Decimal("0.85")) == Decimal("85.00")    # assert 失败即用例失败；Java 是 assertEquals

if __name__ == "__main__":         # 仅当直接运行本文件时成立；被 import 时不执行（Java 是 public static void main）
    print(calc_discount(Decimal("100"), Decimal("0.85")))    # 手动运行时的输出，便于肉眼确认
```

排障完成后把它移动到 `tests/`，补上异常输入和边界条件。**一次故障至少沉淀一条回归测试**。

## 八、线上排查安全边界

- 不在生产开 `debug=True`、pdb、交互式 shell
- 日志脱敏：API key、token、手机号、身份证、完整订单地址
- 不为了排障把日志级别永久调成 DEBUG；按需开启并设置恢复时间
- 不在请求路径里执行大对象 `deepcopy`、全量 dump 数据库
- 对生产只做只读诊断；重启、改配置、清缓存走变更流程

## 九、异步死锁完全诊断指南

### 场景：asyncio 事件循环永远阻塞

```python
# ---- 本段讲：async 函数里混入同步阻塞调用 = 整个事件循环被卡死 ----
# 事件循环是单线程的：一个协程同步阻塞，所有协程都得不到调度。这不是「死锁」但表现一样。
# Java 对照：在 Netty EventLoop 线程里做阻塞 I/O，同样会拖垮整个 reactor。
# ❌ 错误：在 async 函数里调用 sync I/O
async def get_user(user_id: int):      # 第一次定义：演示错误写法
    import time                        # 局部导入，仅为示例完整
    time.sleep(1)  # ← 死锁！整个事件循环卡住了；这 1 秒内其他请求全部停摆
    return {"id": user_id}             # Python 直接返回 dict 作为「对象」，无需先定义 DTO 类

# ✅ 正确：用 to_thread 把阻塞操作放进线程池
async def get_user(user_id: int):      # 同名函数覆盖上一个定义，作为正确示范
    import asyncio                     # 标准库异步运行时
    await asyncio.to_thread(time.sleep, 1)    # 把同步函数丢到默认线程池执行，await 期间事件循环可继续处理其他协程
    return {"id": user_id}             # 返回结构与上面保持一致，调用方无需改动
```

### 诊断死锁的三个工具

#### ① 开启 asyncio 调试日志

```python
# ---- 本段讲：打开 asyncio 调试日志，看「哪个回调耗时过久」 ----
# 日志里会出现 "Executing <Task...> took 2.123 seconds"，直接指向阻塞点。
import asyncio                     # 事件循环与协程调度
import logging                     # 标准库日志；asyncio 内部也走 logging，所以要先配置级别

# 启用 asyncio 调试
logging.basicConfig(level=logging.DEBUG)      # 全局日志级别调成 DEBUG，否则看不到 asyncio 的调试输出
asyncio.run(main(), debug=True)               # debug=True 打开慢回调告警、协程创建栈记录等检查

# 或命令行
# PYTHONASYNCIODEBUG=1 python script.py      # 环境变量等价于 debug=True，适合不改代码临时排查
```

会输出：
```
DEBUG:asyncio:handle_connect ((127.0.0.1, 8000)) took 2.123 seconds
```

#### ② 用 faulthandler 看卡在哪里

```python
# ---- 本段讲：注册信号，让运维「按需」触发线程栈导出 ----
# 信号是操作系统级别的通知：kill -SIGUSR1 不会杀进程，而是回调你注册的函数。
# Java 对照：kill -3 <pid> 触发 JVM 打印 thread dump；Python 需要自己注册信号处理函数。
import faulthandler                   # 能在 C 层安全输出栈，避免 Python 层死锁时无法打印
import signal                         # 标准库：注册操作系统信号处理器（仅类 Unix 有效）

def dump_traceback(signum, frame):    # 信号回调签名固定为 (信号编号, 当前栈帧)，由解释器传入
    print("\n=== 所有线程栈 ===")      # 先打分隔标记，方便在日志里定位
    faulthandler.dump_traceback()     # 输出所有线程的 Python 调用栈到 stderr

signal.signal(signal.SIGUSR1, dump_traceback)    # 把 SIGUSR1 绑定到上面的函数；Windows 没有 SIGUSR1，不能直接用

# 运行服务
# 在另一个终端: kill -SIGUSR1 <pid>    # 每执行一次就抓一次栈，无需重启服务
```

#### ③ 实时监控事件循环

```python
# ---- 本段讲：用「心跳协程」探测事件循环是否被卡住 ----
# 原理：每秒调度一次；如果 sleep 醒来后发现当前任务没变（说明这一秒内循环没跑别的），就是可疑阻塞。
# 注意：这只是探测手段，不能替代 faulthandler；它本身也跑在同一个事件循环上，真死锁时同样无法执行。
import asyncio                          # 异步运行时

async def monitor_loop():               # 监控协程，通常用 create_task 后台运行
    """每秒检查事件循环是否卡住"""       # 文档字符串：不是注释，但同样描述函数用途
    loop = asyncio.get_running_loop()   # 取当前正在运行的事件循环；未在协程内调用会抛 RuntimeError
    
    async def check():                  # 内层协程：一次心跳检查
        last_check = asyncio.current_task()    # 记录当前 Task 对象，用于和 1 秒后比较
        await asyncio.sleep(1)                 # 让出控制权 1 秒；若循环被阻塞，这里会延迟返回
        # 如果 1 秒后还是同一个任务 → 死锁
        if asyncio.current_task() is last_check:    # is 比较对象身份（类似 Java 的 ==），判断调度是否停滞
            print("⚠️  事件循环可能死锁！")          # 输出告警；生产应换成日志 + 指标
    
    while True:                         # 无限循环，持续监控（由 task 取消来结束）
        await check()                   # 每轮等待一次心跳

asyncio.create_task(monitor_loop())     # 把监控协程注册为后台任务；当前协程继续往下执行，不阻塞
```

## 十、内存泄漏定位完整案例

### 真实案例：ai-cs-py-chat 的缓存泄漏

**症状：** 72 小时后服务 OOM

**诊断步骤：**

```python
# ---- 本段讲：内存泄漏诊断第一步——「两份快照对比」思路（本块为操作步骤演示） ----
# 下面不是一次能跑通的完整程序，而是诊断流程的分步说明：开跟踪 → 跑一段时间 → 拍快照 → 看排序结果。
# Java 对照：间隔一段时间各取一次 heap dump，用 MAT 比较可疑对象的增长。
# 1. 收集内存快照
import tracemalloc          # 标准库内存跟踪器，只统计 Python 对象层的分配

tracemalloc.start()         # 第 1 步：启动跟踪（必须在泄漏发生前开，否则没有基线）

# 运行业务 1 小时
time.sleep(3600)            # 第 2 步：让业务跑足够久，让泄漏累积到可观测的量级（示例用 sleep 模拟）

# 对比快照
snapshot = tracemalloc.take_snapshot()      # 第 3 步：拍快照，记录当前所有活对象的分配来源
top_stats = snapshot.statistics("lineno")   # 第 4 步：按「源码行号」聚合排序，占用大的排前面

for stat in top_stats[:10]:     # 第 5 步：逐行打印前 10 条——泄漏热点几乎总在前几名
    print(stat)
    
# 输出示例：
# /app/services/chat_service.py:42: 8523 KiB          ← 第 42 行分配的对象还活着 8.5MB
#   self._cache_dict[key] = response  # <- 泄漏源头    ← 这行是往缓存字典写值：只进不出 = 泄漏
```

**根因分析：** 缓存字典无限增长

**修复方案：**

```python
# ---- 本段讲：修复缓存泄漏的三种方案，从「无界」到「有界」再到「有过期时间」 ----
# 核心原则：任何缓存的容量必须有上界，否则等价于一个慢性 OOM。
# Java 对照：无界 HashMap → 有界 LRU（LinkedHashMap/accessOrder 或 Guava Cache）→ 带过期（Caffeine expireAfter）。
from functools import lru_cache       # lru_cache：标准库自带的 LRU 缓存装饰器，等价 Guava 的 maximumSize

# ❌ 旧实现：纯字典，无限制
class ChatService:
    def __init__(self):               # 构造函数，等价 Java 的构造器；self 相当于 this
        self._cache = {}  # 会无限增长   # 下划线开头表示「内部私有」约定；每次命中新 key 都新增条目，永远不淘汰

# ✅ 新实现：用 lru_cache，固定大小
class ChatService:
    @lru_cache(maxsize=1000)          # 装饰器：方法结果按参数缓存；超过 1000 条就淘汰最久未访问的（LRU）
    def get_cached_response(self, session_id: str):
        ...                           # 省略的真实计算/请求逻辑；命中缓存时根本不会执行到这里

# ✅ 更好：用 TTL 缓存
import time                           # 取当前时间戳用（time.time）
from collections import OrderedDict   # 有序字典：记住插入顺序，是手写 LRU/TTL 的基础容器

class TTLCache:
    # max_size 限总量防 OOM，ttl（秒）限存活时间防「旧数据一直不过期」——对应 Caffeine 的
    # maximumSize + expireAfterWrite 双约束。
    def __init__(self, max_size: int = 1000, ttl: int = 3600):
        self.cache = OrderedDict()    # 值存成 (value, 过期时间点) 的元组
        self.ttl = ttl                # 存活秒数
        self.max_size = max_size      # 最大条目数
    
    def get(self, key):
        if key in self.cache:                 # dict 的 in 是 O(1)，等价 Java 的 map.containsKey
            value, expire_at = self.cache[key]    # 解包元组：同时取出值和过期时间点
            if time.time() < expire_at:       # 未过期才返回
                return value
            del self.cache[key]               # 已过期：惰性删除（等到访问时才清理，不靠后台线程）
        return None                           # 未命中或已过期统一返回 None；Java 里常返回 Optional.empty()
    
    def set(self, key, value):
        if len(self.cache) >= self.max_size:      # 容量已满
            self.cache.popitem(last=False)    # 弹出「最先插入」的条目（FIFO 淘汰）；last=True 则弹最新
        self.cache[key] = (value, time.time() + self.ttl)    # 写入值和「当前时间 + ttl」作为过期点
```

## 十二、Java 开发者常踩的 Python 坑汇总

| 坑 | 表现 | 原因 | 修复 |
|----|------|------|------|
| 对象修改影响原数据 | `b = a; b.append(1)` 导致 `a` 也变了 | 列表是引用 | `import copy; b = copy.deepcopy(a)` |
| 多个对象共享状态 | 所有实例的 list 字段都一样 | 默认参数是编译时求值 | 使用 `None` + 在 `__init__` 里创建 |
| 文件句柄泄漏 | 打开文件后忘关 | 没用 `with` | 始终用 `with open(...) as f:` |
| 导入循环 | `ImportError: cannot import name X` | 模块 A import B，B import A | 延迟导入或重组模块 |
| 字符编码乱码 | 读写 Windows 文件乱码 | 默认系统编码 | 显式 `encoding="utf-8"` |
| 异步调用漏 await | 协程对象创建但不执行 | `coroutine` 不是自动执行 | 搜代码里所有 `async def` 的调用点，补 `await` |
