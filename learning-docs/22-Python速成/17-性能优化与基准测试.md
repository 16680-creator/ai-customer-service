# 17 · 性能优化与基准测试

> Java 里你会看 JMH、JFR、GC 日志；Python 同样需要测量，只是工具链换成 `timeit`、`cProfile`、`tracemalloc`。
> 原则只有一句：**先找瓶颈，再优化；优化后必须复测。**

---

## 一、先分清是哪一类慢

| 类型 | 典型表现 | 优先手段 |
|---|---|---|
| 算法慢 | 数据量翻倍，耗时增长远超 2 倍 | 换数据结构/算法 |
| Python 执行慢 | CPU 单核 100%，大量循环 | 减少 Python 层工作、向量化、C 扩展、进程池 |
| IO 等待 | CPU 低，请求时间长 | 并发、连接池、批量 IO、减少远程调用 |
| 内存压力 | 内存上涨、频繁 GC、机器 swap | 流式处理、生成器、限制缓存、分页 |
| 下游慢 | 自身代码耗时短，DB/LLM/HTTP 长 | 索引、超时、缓存、降级 |

**不要用多线程解决所有“慢”**。GIL、下游限流、连接池上限都可能让线程越多越慢。

## 二、基准测试的正确姿势

### 1. 微基准：`timeit`

```python
from timeit import timeit

t_loop = timeit(
    "out = []\nfor x in data: out.append(x * 2)",
    setup="data = list(range(10000))",
    number=100,
)
t_comp = timeit("[x * 2 for x in data]",
                setup="data = list(range(10000))", number=100)

print(t_loop, t_comp)
```

注意：

- `setup` 里的初始化不计入耗时
- `number` 要足够大，减少计时误差
- 比较时保持相同输入、相同运行环境
- 至少跑 3 轮，看中位数/最小值，不只看一次

### 2. 接口/业务基准：`perf_counter`

```python
import time

samples = []
for _ in range(5):
    start = time.perf_counter()
    business()
    samples.append(time.perf_counter() - start)

samples.sort()
print(f"min={samples[0]:.4f}s median={samples[2]:.4f}s max={samples[-1]:.4f}s")
```

### 3. 必须控制变量

- 用同一批数据、同一 Python 版本、同一依赖版本
- 冷启动和热缓存分开测
- 网络测试要区分下游波动，最好用固定 Fake Server
- 不要在 IDE debugger 打开时测性能
- 本机结果用于**相对比较**，不要直接当生产 QPS

## 三、cProfile：先找最耗时的函数

```bash
python -m cProfile -s cumulative script.py
python -m cProfile -o profile.pstats script.py
```

```python
import pstats
pstats.Stats("profile.pstats").strip_dirs().sort_stats("cumulative").print_stats(20)
```

关键列：

| 列 | 含义 |
|---|---|
| `ncalls` | 调用次数 |
| `tottime` | 函数自身耗时，不含子调用 |
| `cumtime` | 函数及子调用总耗时 |
| `percall` | 每次调用平均耗时 |

读法：

- `tottime` 高：函数本身计算重，优化循环/算法
- `cumtime` 高但 `tottime` 低：慢在下游函数，继续往下看
- `ncalls` 异常高：是否在循环里重复做可以提出的工作

### 常用优化顺序

```text
减少调用次数  >  换算法/数据结构  >  减少 Python 层循环  >  并发/多进程  >  微优化语法
```

## 四、内存：`tracemalloc`

```python
import tracemalloc

tracemalloc.start()
before = tracemalloc.take_snapshot()

run_business()

after = tracemalloc.take_snapshot()
for stat in after.compare_to(before, "lineno")[:10]:
    print(stat)
```

它回答的是“**哪里分配了内存**”，不是“进程总 RSS 为什么这么大”。第三方 C 扩展、解释器自身、多进程内存不在同一个口径里。

### 大文件/大数据的默认写法

```python
# ✅ 流式：内存与文件大小基本无关
def iter_orders(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            if line.strip():
                yield parse(line)

total = sum(o.amount for o in iter_orders(path))
```

避免：

```python
lines = open(path, encoding="utf-8").readlines()   # 全量进内存
rows = [parse(line) for line in lines]             # 又复制一份
```

## 五、最常见的性能改进

### 1. 成员判断：list → set

```python
# 100 万次 list 查找是 O(n²) 风险
valid = set(valid_ids)
result = [x for x in ids if x in valid]
```

### 2. 重复计算：缓存

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def get_config(tenant: str):
    return load_config(tenant)
```

缓存必须同时考虑：

- key 是否高基数（会不会无限增长）
- 数据变更后如何失效
- 多 worker 是否各自缓存
- 是否缓存了不该共享的用户数据

### 3. 循环内重复工作：提到循环外

```python
# ❌ 每行都编译正则、创建连接、读配置
for line in lines:
    value = re.compile(pattern).search(line)

# ✅
compiled = re.compile(pattern)
for line in lines:
    value = compiled.search(line)
```

### 4. N+1 查询：批量替代逐条

```text
100 个订单 -> 100 次商品查询 + 100 次库存查询
改为：一次 IN 查询商品 + 一次 IN 查询库存，在内存中 join
```

**Python 微优化通常省不过一次数据库往返**。

### 5. 字符串拼接：join

```python
text = "".join(parts)
```

### 6. JSON 序列化：先减少字段，再换库

输出前先问：

- 是否真的需要返回全部字段？
- 是否重复序列化同一对象？
- 是否在 debug 日志关闭时仍提前构造大 JSON？

确实成为瓶颈时再评估 `orjson`。引入第三方库前要有基准数据。

## 六、并发优化的边界

| 场景 | 可用手段 | 注意事项 |
|---|---|---|
| 多个独立 HTTP/DB 请求 | `asyncio.gather` | 限制并发，避免打垮下游 |
| 大量同步库 IO | `asyncio.to_thread` | 线程池大小有限 |
| CPU 密集批处理 | `ProcessPoolExecutor` | 进程启动与序列化成本 |
| Web 服务 | 多 worker | 每 worker 独立内存与缓存 |
| numpy/PIL 等 C 扩展 | 有时可线程并行 | 是否释放 GIL 取决于具体实现 |

**并发的目标是缩短等待，不是让下游承受更多流量**。对外部服务加并发前，先设置 `Semaphore`、超时和降级。

## 七、一个可复用的优化记录表

```text
问题：订单导出 10 万行耗时 42s，内存峰值 1.8GB
基线：cProfile 显示 70% 在逐行 dict 转换，25% 在字符串拼接
假设：全量列表导致内存与复制开销
改动：list -> generator，分批写 CSV，每批 1000 行
结果：耗时 18s，内存峰值 120MB
回归：新增 10 万行导出测试；校验首尾行、总行数、金额格式
代价：调用方从接收 list 改为消费 iterator
```

记录“**改动、收益、代价**”，否则很容易把局部优化变成全局复杂度。

## 八、不要做的优化

- 为了省几个字符牺牲可读性
- 没测量就把所有函数改缓存
- 用全局大字典当“无限缓存”
- 为了并发把同步代码全部机械改 async
- 只看本机毫秒数，不看生产 P95/P99 和错误率
- 在测试里用 sleep 等性能结果，导致 CI 不稳定
