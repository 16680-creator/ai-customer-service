# 17 · 性能优化与基准测试

> Java 里你会看 JMH、JFR、GC 日志；Python 同样需要测量，只是工具链换成 `timeit`、`cProfile`、`tracemalloc`。
> 原则只有一句：**先找瓶颈，再优化；优化后必须复测。**

---

## 一、先分清是哪一类慢

| 类型 | 典型表现 | 优先手段 |
|---|---|---|
| 算法慢 | 数据量翻倍，耗时增长远超 2 倍 | 换数据结构/算法 |
| Python 执行慢 | CPU 单核 100%，大量循环 | 减少 Python 层工作、向量化、C 扩展、进程池 |
| IO 等待 | CPU 低，请求时间长 | 并发、连接池、批量 IO、减少远程调用 |
| 内存压力 | 内存上涨、频繁 GC、机器 swap | 流式处理、生成器、限制缓存、分页 |
| 下游慢 | 自身代码耗时短，DB/LLM/HTTP 长 | 索引、超时、缓存、降级 |

**不要用多线程解决所有“慢”**。GIL、下游限流、连接池上限都可能让线程越多越慢。

## 二、基准测试的正确姿势

### 1. 微基准：`timeit`

```python
# ---- 本段讲：timeit 微基准——对比「for+append」和「列表推导式」 ----
# timeit 是标准库微基准工具，等价 Java 的 JMH：它自动多轮执行、把 setup（数据准备）排除在计时外。
# 对比时务必保证两个参数用同样的 setup 和 number，否则没有可比性。
from timeit import timeit     # 只导入函数本身，调用时写 timeit(...) 即可

# 第一项：命令式写法。第一个参数是要计时的代码字符串，
# 内部换行用 \n 表示；setup 先建好 1 万个元素的列表但不计时；number=100 表示整段跑 100 遍。
t_loop = timeit(
    "out = []\nfor x in data: out.append(x * 2)",
    setup="data = list(range(10000))",
    number=100,
)
# 第二项：列表推导式，逻辑等价；CPython 有专用字节码优化，通常明显快于循环+append。
t_comp = timeit("[x * 2 for x in data]",
                setup="data = list(range(10000))", number=100)

print(t_loop, t_comp)     # 打印两个总耗时（秒），比值就是相对速度
```

注意：

- `setup` 里的初始化不计入耗时
- `number` 要足够大，减少计时误差
- 比较时保持相同输入、相同运行环境
- 至少跑 3 轮，看中位数/最小值，不只看一次

### 2. 接口/业务基准：`perf_counter`

```python
# ---- 本段讲：业务级基准——多次采样后取 min/median/max ----
# 微基准测的是「一行代码」，业务基准测的是「一个函数/接口」；等价 JMH 的 @Benchmark 包住整段业务。
# 关键做法：跑 5 轮取中位数，避开第一次的冷启动噪声（类加载、缓存填充），类比 JMH 的 warmup 轮。
import time                  # 提供 perf_counter 高精度单调时钟，等价 Java 的 System.nanoTime

samples = []                 # 收集每一轮的耗时，之后排序取统计量
for _ in range(5):           # 5 轮采样；_ 表示循环变量不用
    start = time.perf_counter()          # 计时起点（浮点秒）
    business()                            # 被测业务（示例占位）
    samples.append(time.perf_counter() - start)    # 差值即本轮耗时，追加进样本列表

samples.sort()               # 原地升序排序，samples[2] 就是 5 个数的中位数
# :.4f 保留 4 位小数；samples[0] 最快（近似无噪声下限），samples[-1] 最慢
print(f"min={samples[0]:.4f}s median={samples[2]:.4f}s max={samples[-1]:.4f}s")
```

### 3. 必须控制变量

- 用同一批数据、同一 Python 版本、同一依赖版本
- 冷启动和热缓存分开测
- 网络测试要区分下游波动，最好用固定 Fake Server
- 不要在 IDE debugger 打开时测性能
- 本机结果用于**相对比较**，不要直接当生产 QPS

## 三、cProfile：先找最耗时的函数

```bash
python -m cProfile -s cumulative script.py
python -m cProfile -o profile.pstats script.py
```

```python
# ---- 本段讲：用 pstats 读取离线性能报告，按累计耗时降序排热点 ----
# cProfile 可把结果落盘，事后用 pstats 分析；等价 Java 里把 profiler 快照（.hprof）离线打开。
import pstats
# Stats 载入 .pstats 文件；strip_dirs() 去掉长路径只留文件名；
# sort_stats("cumulative") 按 cumtime（含子调用的总耗时）降序，等价按调用树总耗时排热点；
# print_stats(20) 只打印前 20 行，避免报告刷屏。
pstats.Stats("profile.pstats").strip_dirs().sort_stats("cumulative").print_stats(20)
```

关键列：

| 列 | 含义 |
|---|---|
| `ncalls` | 调用次数 |
| `tottime` | 函数自身耗时，不含子调用 |
| `cumtime` | 函数及子调用总耗时 |
| `percall` | 每次调用平均耗时 |

读法：

- `tottime` 高：函数本身计算重，优化循环/算法
- `cumtime` 高但 `tottime` 低：慢在下游函数，继续往下看
- `ncalls` 异常高：是否在循环里重复做可以提出的工作

### 常用优化顺序

```text
减少调用次数  >  换算法/数据结构  >  减少 Python 层循环  >  并发/多进程  >  微优化语法
```

## 四、内存：`tracemalloc`

```python
# ---- 本段讲：用 tracemalloc 抓内存快照，前后对比看谁在分配 ----
# tracemalloc 相当于 Java 的堆分配采样（VisualVM/JProfiler 的 allocation 视图），
# 但只统计 Python 对象层的分配，不含 C 扩展与进程 RSS。
import tracemalloc

tracemalloc.start()                       # 开始记录分配（有额外开销，只在测量期间开启）
before = tracemalloc.take_snapshot()      # 取「基线」快照，作为对比起点

run_business()                            # 执行被测业务（示例占位）

after = tracemalloc.take_snapshot()       # 再取一张快照
# compare_to 做差集，得到从 before 到 after 新增的分配；
# "lineno" 按「文件:行号」聚合，[:10] 只取增量最大的前 10 处。
for stat in after.compare_to(before, "lineno")[:10]:
    print(stat)                           # 每行形如「文件名:行号: 净增 KiB（次数）」
```

它回答的是“**哪里分配了内存**”，不是“进程总 RSS 为什么这么大”。第三方 C 扩展、解释器自身、多进程内存不在同一个口径里。

### 大文件/大数据的默认写法

```python
# ---- 本段讲：大文件用「流式」处理，内存占用与文件大小基本无关 ----
# yield 把函数变成生成器（等价 Java 的 Stream/Iterator），只按需产出当前一行。
# ✅ 流式：内存与文件大小基本无关
def iter_orders(path):
    with open(path, encoding="utf-8") as f:    # with 保证句柄用后自动关闭（等价 try-with-resources）
        for line in f:                         # 逐行迭代文件，不会一次性把整个文件读进内存
            if line.strip():                   # 跳过空行/纯空白行
                yield parse(line)              # 解析当前行并「产出」，随后挂起等下一次取值

total = sum(o.amount for o in iter_orders(path))   # 边产出边累加，全程只驻留一行
```

避免：

```python
# ---- 本段讲：反面写法——readlines 一次性把整个文件读进内存，列表推导又复制一份 ----
lines = open(path, encoding="utf-8").readlines()   # 全量进内存
rows = [parse(line) for line in lines]             # 又复制一份
# 最坏情况内存约为文件内容的数倍：这是新手常踩的坑，应改用上面的生成器流式处理。
```

## 五、最常见的性能改进

### 1. 成员判断：list → set

```python
# ---- 本段讲：成员判断改用 set——把 O(n) 线性查找降成 O(1) 哈希查找 ----
# 100 万次 list 查找是 O(n²) 风险
valid = set(valid_ids)                    # 一次性把合法 id 建成 set（等价 Java new HashSet<>(list)，O(n)）
result = [x for x in ids if x in valid]   # 之后每次 in 都是 O(1)，整体从 O(n²) 降到 O(n)
```

### 2. 重复计算：缓存

```python
# ---- 本段讲：缓存重复计算——lru_cache 装饰器 ----
# 等价 Java 的 Spring @Cacheable：命中直接返回，未命中才真正调用函数。
from functools import lru_cache           # 标准库自带的「最近最少使用」缓存装饰器

@lru_cache(maxsize=1024)                  # 最多缓存 1024 个不同参数组合，超出按 LRU 淘汰
def get_config(tenant: str):              # 以参数作为缓存 key（故参数必须可哈希）
    return load_config(tenant)            # 只有真·未命中时才会执行这行
```

缓存必须同时考虑：

- key 是否高基数（会不会无限增长）
- 数据变更后如何失效
- 多 worker 是否各自缓存
- 是否缓存了不该共享的用户数据

### 3. 循环内重复工作：提到循环外

```python
# ---- 本段讲：把循环内的重复工作提到循环外——正则只编译一次 ----
# ❌ 每行都编译正则、创建连接、读配置
for line in lines:
    value = re.compile(pattern).search(line)   # 每轮都重新编译正则，纯浪费（等价 Java Pattern.compile 放进循环）

# ✅
compiled = re.compile(pattern)                 # 循环外编译一次（等价 Java 预先 Pattern.compile 复用）
for line in lines:
    value = compiled.search(line)              # 循环内只做匹配，复用已编译对象
```

### 4. N+1 查询：批量替代逐条

```text
100 个订单 -> 100 次商品查询 + 100 次库存查询
改为：一次 IN 查询商品 + 一次 IN 查询库存，在内存中 join
```

**Python 微优化通常省不过一次数据库往返**。

### 5. 字符串拼接：join

```python
# ---- 本段讲：字符串拼接一律用 join，别在循环里 += ----
text = "".join(parts)   # 一次性分配结果串，O(n)；等价 Java 的 String.join("", parts)
```

### 6. JSON 序列化：先减少字段，再换库

输出前先问：

- 是否真的需要返回全部字段？
- 是否重复序列化同一对象？
- 是否在 debug 日志关闭时仍提前构造大 JSON？

确实成为瓶颈时再评估 `orjson`。引入第三方库前要有基准数据。

## 六、并发优化的边界

| 场景 | 可用手段 | 注意事项 |
|---|---|---|
| 多个独立 HTTP/DB 请求 | `asyncio.gather` | 限制并发，避免打垮下游 |
| 大量同步库 IO | `asyncio.to_thread` | 线程池大小有限 |
| CPU 密集批处理 | `ProcessPoolExecutor` | 进程启动与序列化成本 |
| Web 服务 | 多 worker | 每 worker 独立内存与缓存 |
| numpy/PIL 等 C 扩展 | 有时可线程并行 | 是否释放 GIL 取决于具体实现 |

**并发的目标是缩短等待，不是让下游承受更多流量**。对外部服务加并发前，先设置 `Semaphore`、超时和降级。

## 八、缓存优化实战：从 O(n) 到 O(1)

### 场景：每次都查询 10 万条记录

```python
# ---- 本段讲：给高频查询加缓存，把每次都打 DB 的 O(n) 变成命中缓存 O(1) ----
# ❌ 每次都全量扫描
async def get_user_credits(user_id: int) -> int:   # 异步函数（等价 Java 返回 CompletableFuture 的方法）
    rows = db.query("SELECT credits FROM users WHERE id = ?", user_id)   # 每次调用都真的查库
    return rows[0]["credits"] if rows else 0       # 有记录取积分，否则返回 0（三元表达式）

# ✅ 添加缓存
from functools import lru_cache                    # 缓存装饰器

@lru_cache(maxsize=10000)                          # 最多缓存 1 万个不同 user_id
def get_user_credits(user_id: int) -> int:         # 注意：这里改成了同步函数，不再 async
    rows = db.query("SELECT credits FROM users WHERE id = ?", user_id)   # 仅未命中时才执行
    return rows[0]["credits"] if rows else 0       # 返回值会被缓存，下次同 id 直接返回
```

**性能对比：**
```
无缓存:     1000 次查询耗时 850ms (平均 0.85ms/次)
LRU缓存:    1000 次查询耗时 2ms   (平均 0.002ms/次) ← 425倍加速！
```

### 缓存失效策略（对标 Spring Cache 的 @CacheEvict）

```python
# ---- 本段讲：三种缓存失效策略——TTL 过期、LRU 容量淘汰、主动清空 ----
# 对照 Java/Spring Cache：等价 @CacheEvict / @Cacheable(expire) 的失效控制。
# 策略1：按时间（TTL）
class TTLCache:
    def __init__(self, ttl_seconds: int = 300):   # 默认 300 秒过期（等价 Caffeine expireAfterWrite）
        self.data = {}                             # 存 key -> (value, 创建时间)
        self.ttl = ttl_seconds                     # 过期秒数
    
    def get_or_none(self, key: str):               # 取缓存；不存在或已过期都返回 None
        if key not in self.data:                   # 未命中：没有这个 key
            return None
        value, created_at = self.data[key]          # 命中：解包出值和写入时间
        if time.time() - created_at > self.ttl:     # 判断是否超过 TTL
            del self.data[key]                      # 过期就顺手删掉，避免堆积
            return None
        return value                               # 未过期，返回缓存值

# 策略2：按容量（LRU）
from functools import lru_cache
@lru_cache(maxsize=1000)  # 超过 1000 项后自动淘汰最旧的

# 策略3：主动失效
def update_user_credits(user_id: int, new_credits: int):   # 写入新积分后必须让缓存失效，否则读到脏数据
    get_user_credits.cache_clear()  # 清空整个缓存
    # 更好的方案：只清特定 key
    cache_key = (user_id,)                          # lru_cache 的 key 是「参数元组」，单参数就是 (user_id,)
    if cache_key in get_user_credits.cache_info():
```

## 九、查询优化：索引、批量、预加载

### 冷门痛点：N+1 查询

```python
# ---- 本段讲：N+1 查询——逐条查 vs 批量查后在内存里关联 ----
# ❌ 循环查询（N+1 问题）
orders = db.query("SELECT * FROM orders LIMIT 100")            # 第 1 次查询：拿到 100 个订单
for order in orders:
    user = db.query("SELECT * FROM users WHERE id = ?", order.user_id)   # 每个订单再查一次用户，共 100 次
    # 1 次查 orders + 100 次查 users = 101 次查询

# ✅ 批量查询 + 内存关联
orders = db.query("SELECT * FROM orders LIMIT 100")            # 仍然第 1 次查订单
user_ids = {o.user_id for o in orders}                          # 集合推导式：去重出所有涉及的用户 id
users = {u.id: u for u in db.query("SELECT * FROM users WHERE id IN (...)", user_ids)}   # 第 2 次：一次 IN 查全部用户，建成 id->用户 字典
results = [{**order, "user": users[order.user_id]} for order in orders]   # 字典解包展开 order 的键，再补 user 字段（内存 join）
# 2 次查询搞定
```

### 对照 Java 的 JPA join

```java

@Entity
public class Order {

// Python 同等效果

        SELECT o.*, u.* FROM orders o
```

## 十、异步 I/O 的天花板在哪

### 误解：async 能让所有东西都快

```python
# ---- 本段讲：async 不是万能加速——只对 I/O 密集有效，对 CPU 密集反而添开销 ----
# ❌ 异步 CPU 计算（没有加速，反而有开销）
async def compute_hash(data):                     # 声明成 async，但内部是纯 CPU 计算
    return hashlib.sha256(data).hexdigest()       # 一直占着事件循环，其他协程饿死；应改用进程池

# ✅ 异步 I/O（网络、文件、数据库）
async def fetch_data():
    async with httpx.AsyncClient() as client:     # async with 异步上下文管理器（等价 try-with-resources 的异步版）
        return await client.get("https://api.example.com")   # await 期间让出事件循环，可并发跑其他请求
```

### 基准测试：证明天花板

```python
# ---- 本段讲：用基准数据证明 async 的天花板——CPU 密集无用、I/O 密集大加速 ----
import asyncio                                  # 异步事件循环（等价 Java 的 Executor/协程抽象）
import time                                     # 主要用 perf_counter 计时
import hashlib                                  # 哈希库，用来制造纯 CPU 计算

# CPU 密集任务（无法被 async 加速）
async def cpu_bound():
    for i in range(1000000):                    # 100 万次纯计算
        hashlib.sha256(str(i).encode()).hexdigest()   # 全程占着事件循环，协程无法让出

# I/O 密集任务（async 有明显加速）
async def io_bound():
    tasks = [asyncio.sleep(0.1) for _ in range(100)]   # 造 100 个各睡 0.1s 的协程（模拟 100 个 IO 等待）
    await asyncio.gather(*tasks)                        # 并发等待，总耗时≈0.1s 而非 100×0.1s

# 运行测试
import timeit

cpu_time = timeit.timeit(lambda: asyncio.run(cpu_bound()), number=1)   # 跑 1 次，测 CPU 任务耗时
print(f"CPU 任务耗时: {cpu_time:.2f}s")

io_time = timeit.timeit(lambda: asyncio.run(io_bound()), number=1)     # 跑 1 次，测 I/O 任务耗时
print(f"I/O 任务耗时: {io_time:.2f}s (100 个 0.1s 的操作并发执行)")

# 输出：
# CPU 任务耗时: 1.23s (单线程执行)
# I/O 任务耗时: 0.12s (并发加速 ≈ 100 倍)
```

**结论**：
- **I/O 密集** → async 很有效
- **CPU 密集** → 用进程池，不要用 async

## 十一、基准测试的陷阱

### 坑1：测试环境和生产环境差异

```python
# ---- 本段讲：基准测试头号陷阱——测试环境与生产环境不一致 ----
# ❌ 这个基准不可信
import timeit
timeit.timeit(lambda: calculate_discount(100, 0.85), number=1000000)   # 用一个小数字、单线程跑一遍就下结论

# 问题：
# - 数据太小（100 vs 真实的百万级金额）
# - 数据太规整（永不出错 vs 真实的脏数据）
# - 单线程（vs 真实的多 worker 并发）
# - 本机 SSD（vs 生产的网络 I/O）

# ✅ 更真实的基准
async def benchmark_real():
    # 使用真实的请求数据分布
    test_data = await load_production_sample()     # 用生产采样数据，避免「玩具数据」失真

    # 多 worker 并发
    tasks = [process_order(data) for data in test_data * 10]   # 复制成 10 倍并发的协程列表

    start = time.perf_counter()                    # 计时起点
    await asyncio.gather(*tasks)                   # 并发跑完所有协程（* 把列表展开成位置参数）
    duration = time.perf_counter() - start         # 总耗时

    # 用单次平均耗时作为指标，等价 JMH 的 AverageTime 模式
    return duration / len(tasks)  # 平均耗时
```

### 坑2：热身不够导致结果波动

```python
# ---- 本段讲：热身不足会让结果剧烈波动——先预热再计时 ----
# 注意：CPython 没有 JIT，但缓存填充、首次导入等冷启动效应同样存在，
# 对照 JMH 的 @Warmup，正式测量前先跑若干轮把状态跑热。
# JIT 编译和缓存预热
def benchmark_with_warmup():
    # 第一轮：预热（JIT、缓存填充）
    for _ in range(100):
        func()                                     # 只跑不测，让各类缓存就位

    # 第二轮：真正的计时
    start = time.perf_counter()          # 预热耗时不计入，这里才作为计时起点
    for _ in range(10000):
        func()                           # 正式测量 1 万次
    return time.perf_counter() - start   # 返回总耗时
```

### 坑3：忘记考虑内存分配

```python
# ---- 本段讲：又一个内存分配陷阱——循环里 += 拼字符串 vs join 一次性构造 ----
# 列表拼接 vs join（对照 Java 的 StringBuilder）
import timeit                                  # 微基准工具

# ❌ 低效（每次拼接都复制）
def concat_slow():
    s = ""
    for i in range(1000):
        s += f"item_{i},"                       # 每次 += 都新建整个字符串，O(n²)（等价 Java 循环里用 String.concat）
    return s

# ✅ 高效（一次性构造）
def concat_fast():
    return ",".join(f"item_{i}" for i in range(1000))   # 生成器 + join，一次分配，O(n)（等价 StringBuilder）

print(f"低效版: {timeit.timeit(concat_slow, number=1000):.3f}s")   # 跑 1000 遍取总耗时
print(f"高效版: {timeit.timeit(concat_fast, number=1000):.3f}s")

# 输出：
# 低效版: 0.456s
# 高效版: 0.032s   (14 倍差异！)
```
