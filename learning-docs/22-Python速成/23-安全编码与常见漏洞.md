# 23 · 安全编码与常见漏洞

> Java 开发者熟悉 SQL 注入、XSS、CSRF、越权；Python 里这些问题一样存在，只是危险 API 换了名字。
> 这篇按“输入 → 执行 → 存储 → 输出 → 依赖 → AI”走一遍，给出可落地的写法。

---

## 一、先把信任边界画出来

```text
不可信：HTTP 请求体、query、header、上传文件、URL 参数
不可信：LLM 输出、RAG 检索到的文档、第三方 API 返回
半可信：网关透传的身份头（必须验证签名/来源）
可信：进程内已校验的 Pydantic 模型、密钥管理器注入的配置

```

**核心原则**：跨过边界必须校验；进入核心业务后使用明确模型；输出到客户端前按上下文转义/裁剪。

## 二、输入校验：Pydantic 不是装饰器，是边界

```python
# ---- 本段讲：用 Pydantic 模型在“输入边界”做校验 ----
# 把不可信的 HTTP/JSON 输入转成受约束的强类型对象，越界的请求在入口就被拒绝。
# 为什么重要：Python 没有 Java 的编译期类型检查，手动取值极易漏校验；Pydantic 就是入口守卫。
# Java 对应：Spring 的 @Valid + @NotNull/@Size/@Pattern 等 Bean Validation 注解。
from pydantic import BaseModel, ConfigDict, Field   # BaseModel=DTO 基类；Field=字段级约束；ConfigDict=模型级配置

class CreateOrder(BaseModel):                       # 定义“创建订单”入参模型，等价 Java 里带校验注解的 DTO
    model_config = ConfigDict(extra="forbid")      # 拒绝未声明字段，防 mass assignment
    # extra="forbid"：JSON 里出现模型未声明的字段就直接报错，防止客户端塞入 is_admin 之类字段越权

    order_no: str = Field(min_length=1, max_length=32, pattern=r"^[A-Z0-9-]+$")
    # order_no：订单号。既限长度又用正则限定字符集，杜绝非法字符/超长输入
    amount: Decimal = Field(gt=0, le=Decimal("1000000"))
    # amount：金额。0 < amount <= 1000000；用 Decimal 而非 float，避免浮点精度问题（等价 Java 的 BigDecimal）
    remark: str = Field(default="", max_length=200)
    # remark：备注。可不传默认空串；限制最大长度，防超长文本打爆内存/日志
```

不要：

```python
# ---- 本段讲：反面示例——用 **kwargs 直接透传是危险的 ----
# **kwargs 会把客户端传来的任意字段原样塞进 Order，等于放弃白名单校验。
# Java 对应：相当于把整个 Map 无校验地映射到实体，攻击者就能覆写 is_admin 等敏感属性。
def create_order(**kwargs):                  # **kwargs 收集所有关键字参数，字段名完全由调用方（客户端）决定
    model = Order(**kwargs)      # 客户端可注入 is_admin=True 之类的字段
    # Order(**kwargs) 会把 is_admin/role 等未预期字段一并赋值，造成越权（mass assignment）
```

还要注意：

- 字符串长度上限，防止超长输入打爆内存/日志
- 数值范围上限，防止 `qty=10**9`
- 列表长度上限，防止一次提交十万条
- 枚举用 `Literal` / `Enum`，不要只在前端限制
- 文件上传限制大小、数量、类型，并做真实内容校验

## 三、SQL 注入：只有参数化一条路

```python
# ---- 本段讲：SQL 注入与参数化查询 ----
# 反例用 f-string 拼 SQL，用户输入会变成 SQL 语法；正例用占位符，由驱动负责转义。
# Java 对应：绝不用 Statement 拼字符串，一律用 PreparedStatement 的 ? 占位符。
# ❌ 任何字符串拼接都危险
cur.execute(f"SELECT * FROM orders WHERE no = '{order_no}'")
# f-string 把 order_no 直接插进 SQL；若为 ' OR 1=1 -- 就会改写查询语义，绕过条件

# ✅ 参数化
cur.execute("SELECT * FROM orders WHERE no = ?", (order_no,))
# 第二个参数是值的元组，? 由数据库驱动安全转义；等价 Java 的 PreparedStatement.setString
```

动态排序/表名无法参数化时，用**白名单映射**：

```python
# ---- 本段讲：无法参数化的部分（排序字段/表名）用白名单映射 ----
# ORDER BY 后的列名不能用占位符，所以要先把“用户输入”映射成“固定的安全列名”。
# Java 对应：同样不能把排序字段直接拼进 SQL，要先用枚举/Map 校验再拼接。
SORT_COLUMNS = {"amount": "amount", "created_at": "created_at"}   # 白名单：只允许这几个排序字段
column = SORT_COLUMNS.get(sort_by)                               # 用 get 查表，查不到返回 None
if column is None:                                               # 用户传了白名单外的字段
    raise ValueError("非法排序字段")                             # 直接拒绝，杜绝注入
sql = f"SELECT * FROM orders ORDER BY {column} DESC"             # 此时 column 已来自白名单，拼接才安全
```

`column` 来自白名单而不是用户输入，才是安全的。ORM 的 `text()` / 原生 SQL 同样要参数绑定。

## 四、路径穿越：`resolve` + `is_relative_to`

```python
# ---- 本段讲：路径穿越（../）防护 ----
# 用户传入的文件名若含 ../ 就能跳出上传目录，读到 /etc/passwd 等任意文件。
# 做法：拼出真实路径后 resolve() 归一化，再判断它是否仍落在 BASE 之内。
# Java 对应：Path.normalize() 后判断 startsWith(base)，思路一致。
from pathlib import Path                                        # pathlib 是 Python 推荐的路径库

BASE = Path("/srv/app/uploads").resolve()                       # 允许访问的根目录，resolve 展开符号链接得到绝对路径

def safe_path(user_path: str) -> Path:                          # 把用户输入转成“必定在 BASE 内”的安全路径
    candidate = (BASE / user_path).resolve()                    # / 拼接并 resolve，把 ../ 和软链展开成真实路径
    if not candidate.is_relative_to(BASE):                      # 归一化后若已不在 BASE 目录内（3.9+ 才有此方法）
        raise ValueError("非法路径")                             # 说明发生了穿越，拒绝
    return candidate                                            # 通过校验才返回
```

要点：

- 必须先 `resolve()`，`../` 和符号链接才会被展开
- `is_relative_to` 是 3.9+；低版本用 `os.path.commonpath`
- 不要只检查字符串里有没有 `..`（编码、分隔符、符号链接都能绕过）
- 上传文件名不要直接用于落盘，用服务端生成的 UUID；保留原文件名只作展示
- 下载也要做同样的归属校验，防止越权读别人的文件

## 五、命令注入：列表参数，禁用 shell

```python
# ---- 本段讲：命令注入与 subprocess 的安全用法 ----
# shell=True 会把整串交给系统 shell 解析，用户输入里的 ; | && 就能再执行任意命令（RCE）。
# 正确做法：用列表传参、不开 shell，让子进程逐参数接收，shell 元字符失去作用。
# Java 对应：Runtime.exec(String) 危险，用 ProcessBuilder 传参数列表才安全。
import subprocess                                              # 调用外部命令的标准库

# ❌ shell=True + 拼接用户输入 = 远程命令执行
subprocess.run(f"convert {user_file} out.png", shell=True)
# user_file 若为 "a.png; rm -rf /"，整串会被 shell 当成两条命令执行

# ✅ 列表参数，不经 shell
subprocess.run(["convert", user_file, "out.png"], check=True, timeout=30)
# 第一个元素是可执行文件，其余是独立参数；check=True 非零退出码抛异常，timeout=30 超时终止
```

即便用列表参数，也要：

- 参数来自白名单（例如只允许固定子命令）
- 路径先做上一节的穿越校验
- 设置 `timeout`
- 不用用户输入决定可执行文件路径
- 不把 stdout/stderr 直接回显给用户（可能泄露内部路径）

## 六、SSRF：任何“用户给 URL，服务端去请求”的功能都要防

```python
# ---- 本段讲：SSRF——服务端按用户给的 URL 去请求 ----
# 攻击者让服务端去访问 127.0.0.1 / 内网 / 云元数据 169.254.169.254，探测内网或窃取凭证。
# 防护：限制协议 + 域名白名单；但白名单域名也可能解析到内网，仍需额外校验真实 IP。
# Java 对应：同样要对用户可控 URL 做协议/主机白名单，禁止跟随跳转到内网。
from urllib.parse import urlparse                    # 解析 URL，拆出 scheme / hostname 等部分

ALLOWED_HOSTS = {"api.example.com"}                  # 允许访问的域名白名单（首选白名单而非黑名单）

def check_url(url: str) -> None:                     # 校验入口，不通过就抛异常
    parsed = urlparse(url)                           # 把 URL 解析成结构化对象
    if parsed.scheme != "https":                     # 只允许 https，排除 file:// gopher:// 等危险协议
        raise ValueError("只允许 https")
    if parsed.hostname not in ALLOWED_HOSTS:         # 主机名必须精确命中白名单
        raise ValueError("域名不在白名单")
    # 注意：域名解析到内网 IP 仍需额外防护（DNS rebinding）
    # DNS rebinding：校验时域名解析到公网、真正请求时又指向内网 IP，所以要校验实际连接的 IP
```

要防的目标：`127.0.0.1`、`10.0.0.0/8`、`172.16/12`、`192.168/16`、`169.254.169.254`（云元数据）、IPv6 回环与 IPv4-mapped IPv6。

实践建议：

- 首选**域名白名单**，而不是黑名单
- 禁止跟随重定向，或每一跳都重新校验
- 解析后检查实际连接的 IP，而不是只看 URL 字符串
- 出网走统一代理/网关，限制可访问网段
- AI Agent / 爬虫 / 图片抓取尤其危险，默认关闭任意 URL 能力

## 七、反序列化：`pickle` 和 `yaml.load` 都能执行代码

```python
# ---- 本段讲：反序列化漏洞 ----
# pickle 反序列化时能执行任意代码（通过 __reduce__），yaml.load 也能构造任意 Python 对象。
# 因此绝不能用它们处理用户可控数据；改用纯数据格式 JSON，或 yaml.safe_load。
# Java 对应：等价于 Java 反序列化 gadget 链（ObjectInputStream.readObject）的风险。
# ❌ 不可信数据绝对不要
import pickle
pickle.loads(user_bytes)
# pickle.loads 会把“数据”当“指令”执行，攻击者构造的字节流可在服务端执行任意代码

# ❌ 旧式 yaml.load 可构造任意对象
import yaml
yaml.load(user_text)
# 旧版 yaml.load 未指定 Loader 时能实例化任意类，触发代码执行

# ✅
import json
json.loads(user_text)
# JSON 只解析成 dict/list/str 等纯数据，不会执行代码，处理不可信输入首选

import yaml
yaml.safe_load(user_text)
# safe_load 只允许基础类型，禁止构造任意对象
```

同理，不要对不可信数据使用 `eval`、`exec`、`marshal`、`dill`。需要结构化数据就用 JSON + Pydantic。

## 八、密钥与配置

```python
# ---- 本段讲：用 SecretStr 防止密钥被日志/打印泄漏 ----
# SecretStr 包装敏感值，str()/repr() 时只显示掩码，避免密钥意外打进日志。
# 真正要用时显式调用 get_secret_value()，让“取值”成为一个显眼动作。
# Java 对应：类似自定义 toString 脱敏，或 Spring 的 Sensitive 属性处理。
from pydantic import SecretStr                 # 提供带脱敏能力的字符串类型

class Settings(BaseSettings):                  # 配置模型（BaseSettings 可从环境变量/文件读配置）
    llm_api_key: SecretStr          # 打印时自动隐藏
    # LLM 的 API Key，声明为 SecretStr 后不会被直接打印出来
    db_password: SecretStr
    # 数据库口令，同上，避免泄漏到日志

print(settings.llm_api_key)         # SecretStr('**********')
# 直接打印只显示掩码，即使误写日志也不会泄漏真实值
print(settings.llm_api_key.get_secret_value())   # 只在真正连接时取
# 只有明确需要用到密钥的代码路径才显式取值
```

规则：

- `.env` 进 `.gitignore`，仓库只留 `.env.example`
- 生产用环境变量/密钥管理器，不写进镜像和代码默认值
- 日志、异常、监控标签、trace 中都不打密钥
- 密钥一旦提交过 Git 历史，视为泄露，立即轮换，不要只删当前文件
- 不同环境不同密钥，测试不连生产

生成安全令牌用 `secrets`，不要用 `random`：

```python
# ---- 本段讲：用 secrets 生成不可预测的令牌 ----
# secrets 基于操作系统密码学随机源，适合密码、重置链接、会话 ID。
# random 是可预测的伪随机（梅森旋转），绝不能用于安全场景。
# Java 对应：用 SecureRandom，而不是 java.util.Random。
import secrets                                              # 密码学安全的随机数模块
token = secrets.token_urlsafe(32)                           # 生成 32 字节、URL 安全的随机令牌字符串
```

`random` 是伪随机，可预测，适合模拟数据，不适合密码、重置链接、会话 ID。

## 九、认证与越权

- 身份由网关/认证服务签发，Python 服务**验证签名、算法、issuer、audience、exp**，不要自己解 payload 就信
- 不信任客户端传来的 `userId`、`tenantId`、`role`
- 每个资源访问都检查归属：`order.user_id == current_user.id`
- 列表接口也要过滤租户，不要只在前端隐藏
- 管理端接口单独鉴权，不靠“路径不好猜”
- 内部服务调用使用内部凭证/签名，不裸露公网

```python
# ---- 本段讲：资源归属校验（防越权） ----
# 取资源时必须同时校验它属于当前用户，否则换个 order_no 就能读别人的订单。
# 无权限与不存在都返回 404，避免攻击者通过错误码差异枚举资源是否存在。
# Java 对应：Service 层做 owner 校验，等价 @PreAuthorize 或手写 user_id 比对。
def get_order(order_no: str, user: User) -> Order:                  # 入参：订单号 + 当前登录用户
    order = repo.find(order_no)                                     # 按订单号查库
    if order is None or order.user_id != user.id:                   # 不存在，或不属于当前用户
        raise NotFound()          # 不要返回“存在但无权限”，避免枚举
        # 统一抛 NotFound，不区分“没这条”和“不是你的”，防止通过状态码枚举订单号
    return order                                                    # 校验通过才返回
```

## 十、CORS / CSRF / 响应头

```python
# ---- 本段讲：CORS 跨域策略的安全配置 ----
# 明确列出允许的来源、方法与请求头，避免 allow_origins=["*"] 带来的越权读数据风险。
# 带凭证(Cookie)时尤其危险：通配符 + 凭证会让任意站点以用户身份调用接口。
# Java 对应：等价 Spring 的 @CrossOrigin / CorsConfiguration 显式配置。
app.add_middleware(                                          # 注册中间件（FastAPI/Starlette 写法）
    CORSMiddleware,                                          # 跨域资源共享中间件
    allow_origins=["https://app.example.com"],   # 明确来源
    # 只放行自己的前端域名，不用 "*"
    allow_credentials=True,                                  # 允许携带 Cookie 等凭证
    allow_methods=["GET", "POST"],                           # 只放开必要的方法
    allow_headers=["Content-Type", "Authorization"],         # 只放开必要的请求头
)
```

- 不要 `allow_origins=["*"]` 同时 `allow_credentials=True`
- 用 Cookie 做认证时，要 CSRF 防护（SameSite + token）
- 用 `Authorization` header 时，CSRF 风险较低，但仍要防 XSS 偷 token
- 生产加安全响应头：`X-Content-Type-Options: nosniff`、`X-Frame-Options`、CSP（前端）

## 十一、错误信息与日志

```python
# ---- 本段讲：错误响应与日志分离 ----
# 客户端只拿到稳定、无信息量的错误码；细节留给服务端日志，避免泄漏堆栈/SQL/路径。
# Java 对应：全局异常处理器返回统一错误体，堆栈只写日志不返回前端。
# 客户端只看到稳定错误码
return JSONResponse(status_code=500, content={"code": "INTERNAL", "message": "系统繁忙"})
# 只返回通用提示，攻击者拿不到任何内部实现信息

# 服务端记录细节
logger.exception("订单创建失败 order_no=%s", order_no)
# logger.exception 连同堆栈一起写日志；用 %s 占位（惰性格式化），日志里保留可排查的细节
```

不要返回：堆栈、SQL、连接串、内部路径、依赖版本、上游原始错误。攻击者会利用这些信息。

日志脱敏：

```python
# ---- 本段讲：日志脱敏 ----
# 打日志前把敏感字段的值替换成 ***，防止 token/口令进入日志系统被滥用。
# Java 对应：Logback 自定义 Converter 或 MDC 脱敏，思路一致。
SENSITIVE = {"password", "token", "api_key", "authorization", "cookie"}   # 需要脱敏的字段名集合

def mask(data: dict) -> dict:                                             # 接收待打日志的字典
    return {k: ("***" if k.lower() in SENSITIVE else v) for k, v in data.items()}
    # 字典推导式：键名小写后命中敏感集合就把值换成 ***，否则原样保留
```

## 十二、资源耗尽与拒绝服务

- 请求体大小上限（反向代理 + 应用双层）
- 列表/文件/批量接口的数量上限
- 所有外部调用超时、连接池上限、并发上限
- 正则避免灾难性回溯（ReDoS），不要用用户输入拼复杂正则
- 压缩包解压限制总大小与文件数，防 zip bomb
- 分页接口设最大 page_size
- 登录/验证码/短信接口限流，防撞库与短信轰炸

## 十四、AI 应用特有风险

| 风险 | 说明 | 防护 |
|---|---|---|
| Prompt injection | 检索文档/用户输入里藏指令 | 把检索内容标记为“资料”，不让它改变系统规则；关键动作走代码校验 |
| 工具调用越权 | 模型请求调用工具，参数由模型生成 | 工具层做授权与参数白名单，不信任模型 |
| 数据外泄 | 把密钥、其他租户数据拼进 prompt | 上下文按租户隔离，敏感字段不进入 prompt，输出脱敏 |
| 幻觉事实 | 模型编造订单号/金额 | 事实字段由服务端查询后填入，不让模型自由生成 |
| 成本攻击 | 超长输入、无限重试 | 输入/输出 token 上限、用户级限流、预算告警 |
| 不可信 URL | 让模型决定抓哪个 URL | SSRF 防护 + 域名白名单 + 只读工具 |

**一句话**：LLM 的输出等于“不可信用户输入”，不要因为它来自模型就跳过校验。

---

## 十五、Code Review 安全清单

- [ ] 所有 SQL 参数化，动态标识符走白名单
- [ ] 文件路径 `resolve` + 归属校验，文件名服务端生成
- [ ] 无 `shell=True` 拼接用户输入
- [ ] 用户可控 URL 有协议/域名/IP 白名单，禁跟跳转或逐跳校验
- [ ] 无 `pickle.loads` / `yaml.load` / `eval` 处理不可信数据
- [ ] 密钥来自环境/密钥管理器，日志脱敏
- [ ] 身份与租户来自可信凭证，资源访问检查归属
- [ ] CORS 明确来源，Cookie 认证有 CSRF 防护
- [ ] 请求体、列表、上传、分页都有上限
- [ ] 外部调用有超时、并发与重试上限
- [ ] 错误响应不含堆栈和内部细节
- [ ] 依赖锁定，CI 跑漏洞扫描
- [ ] LLM 输出经过校验，工具调用做授权
- [ ] 日志保留审计所需信息，但不含敏感数据
