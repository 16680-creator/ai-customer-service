## 零、先给结论：电商系统的本质是什么

电商系统的本质是 **「把一次购买意图，安全地变成一次钱货两清」**。所有技术难题都是这句话的副产品：

| 业务诉求 | 技术翻译 | 典型手段 |
|---|---|---|
| 不能超卖 | 并发扣减必须原子 | 条件 UPDATE / Redis 预扣 / 队列串行化 |
| 不能多付钱 | 支付回调必须幂等 | 幂等键 + 状态机 + DB 唯一约束 |
| 不能少发货 | 订单状态必须可追溯 | 状态机收敛唯一入口 + 状态流水表 |
| 价格不能错 | 试算价与实付价必须同源 | 同一段算价代码 + 下单时服务端重算 |
| 大促不能挂 | 流量必须被削峰 | 限流 + 缓存 + 异步 + 降级 |
| 钱要对得上 | 资金必须能对账 | 支付流水表 + T+1 对账 + 差异分类 |

> 一句话面试版：**「电商系统的技术难点不在 CRUD，在三件事——并发下的库存正确性、分布式下的资金一致性、大促下的系统可用性。」**

## 一、业务全景：三个视角

### 1.1 用户视角：一次完整购物旅程（12 步）

```
① 浏览首页/分类
② 搜索 / 点推荐位
③ 进商品详情（商详页）
④ 选规格（颜色/尺码）→ 看库存
⑤ 加入购物车
⑥ 进购物车，勾选商品
⑦ 去结算（结算页：收货地址、优惠券、运费、发票）
⑧ 提交订单 → 生成订单号，进入待支付
⑨ 支付（扫码/跳转/免密）
⑩ 支付成功 → 商家发货 → 物流在途
⑪ 确认收货 → 交易完成（此时才能评价、才能申请售后）
⑫ 售后（退款/退货/换货）
```

**每一步背后的系统动作**（这是面试「讲讲你们的购物流程」的标准答法骨架）：

| 步 | 用户看到 | 系统在做什么 | 一致性要求 |
|---|---|---|---|
| ①~② | 一堆商品 | 读缓存/读搜索索引，**不碰 DB 主库** | 最终一致（商品改了 1~2 秒才看到可接受） |
| ③~④ | 商详页 | 读商品缓存，读库存（可能读缓存镜像） | 库存展示允许"乐观"，允许显示有货但下单失败 |
| ⑤ | 提示"已加入" | 写购物车（DB + 唯一键防重） | **强一致**（用户立刻要看到） |
| ⑥ | 购物车列表 | 读购物车，实时校验商品上下架/价格 | 读侧允许旧价，写侧必须新价 |
| ⑦ | 结算页金额 | **试算价**：服务端算一遍（商品价 + 满减 + 券 + 运费） | 试算只是"参考"，可以不锁库存 |
| ⑧ | "下单成功" | **下单事务**：扣库存 + 算价 + 建单 + 核销券 | **强一致**（这一段是全系统最重的临界区） |
| ⑨ | 支付页 | 创建支付流水，调渠道下单（预下单） | 幂等（用户可能点两次） |
| ⑩ | 订单变"已支付" | 渠道回调 → 校验 → 改订单状态 → 发 MQ | **跨系统最终一致**（靠重试 + 幂等收口） |
| ⑪ | 交易完成 | 履约状态推进 | 强一致（状态机） |
| ⑫ | 售后单 | 售后申请（幂等）→ 审核 → 退款 | 强一致 + 幂等 |

> ⚠️ 关键认知：**只有第 ⑤⑧⑨⑪⑫ 步需要强一致，第 ①②③⑥ 步都是读多写少、可以最终一致。** 这张表答对了，面试官就知道你真的做过。

### 1.2 商家/运营视角（B 端）

- **商品管理**：发布商品（SPU + SKU）、上下架、改价、改库存、类目与属性模板。
- **订单管理**：订单查询、发货（填物流单号）、改地址（仅未发货）、备注、导出。
- **营销管理**：优惠券模板、满减规则、秒杀场次、拼团、预售。
- **售后管理**：审核、退货入库、退款打款。
- **数据看板**：GMV、转化率、客单价、退货率、库存周转。

### 1.3 平台视角（跨域能力）

风控（刷单/薅羊毛）、结算（给商家分账）、发票、客服、搜索推荐、内容（评价/图文）、履约（仓配）、供应链。

## 二、技术地图：按「域」切，不按「技术」切

### 2.1 十个域各自的「一张核心表 + 一个技术点」

| 域 | 核心表（本项目的真实表名） | 最需要讲清的技术点 |
|---|---|---|
| 用户 | `user`、`user_address` | 密码加盐、JWT 无状态、水平分片（本项目 `ai-cs-user` 有 `sharding` 包） |
| 商品 | `product`、`product_category` | 单表 vs SPU/SKU、类目树、商品快照 |
| 搜索 | ES `product_catalog` | 索引与 DB 的同步（CDC）、搜索延迟兜底 |
| 交易 | `cart_item`、`orders`、`order_item` | **订单号生成、状态机、事务边界、幂等** |
| 营销 | `coupon`、`full_reduction_rule` | **叠加规则、并发核销、券的逆向（退券）** |
| 支付 | `pay_transaction` | **回调幂等、渠道抽象、对账** |
| 履约 | 本项目 **❌ 没有** | 发货、物流轨迹、签收超时、自动确认收货 |
| 售后 | `after_sale_application` | **幂等键、资格校验、逆向库存** |
| 消息 | `message`、`notify` | 事务消息、至少一次 + 幂等 |
| 数据 | ClickHouse / 数仓 | 埋点模型、GMV 口径、实时 vs 离线 |

## 四、一致性光谱：把"强一致 / 最终一致"标在地图上

这是电商架构面试的**分水岭问题**。

### 4.1 三级光谱

| 级别 | 含义 | 电商里的位置 | 手段 |
|---|---|---|---|
| **强一致（ACID）** | 同一事务内要么全成功要么全失败 | 下单（扣库存 + 建单 + 核销券）、支付回调落库、状态机迁移 | 单库事务 / Seata AT / 状态机 CAS |
| **最终一致（可对账）** | 短暂不一致可接受，但最终必须收敛，且**能发现不收敛** | 支付成功 → 订单变已支付（MQ）、商品改价 → 搜索索引更新（CDC）、下单 → 通知推送 | 事务消息 + 消费幂等 + 定时对账 |
| **弱一致（可丢）** | 丢了不影响交易 | 埋点、浏览历史、推荐位曝光、销量统计展示 | 异步批量、采样 |

### 4.2 本项目里真实的分界线

- **下单是强一致**：`OrderCreateTxService.java:78-79` 同时挂 `@GlobalTransactional` 与 `@Transactional`，说明作者明确把"扣库存 + 建单 + 核销券"视为一个整体。
- **支付成功到订单变已支付是最终一致**：`PaySuccessMessageProducer.java:47-53` 发事务消息 → `PaySuccessListener.java:27-31` 消费 → `OrderServiceImpl.java:117-164` 改状态。中间任何一步失败，都靠 RocketMQ 重试（`maxReconsumeTimes=8`）+ 消费侧幂等（`:126-129` 已 PAID 直接返回）收敛。
- **商品改价到搜索可见是最终一致**：`ProductCdcConsumer.java:23` 监听 `c-product-sync`，`:59` 写 ES。延迟期间用户在搜索结果里看到旧价格 → 点进商详页读的是 DB/缓存的新价 → 下单时服务端再算一次 → **所以"搜索显示旧价"是可接受的设计，不是 bug**。
  - ⚠️ 但这个设计有一个真实风险：如果用户按搜索页显示的旧价下单，实付价更高，会产生客诉。**正确做法是在结算页明确提示"价格已更新"。**

### 4.3 面试标准答法（背下来）

> "我们把一致性分成三段看：
> **第一段是下单**，库存扣减、建单、核销券必须在同一个事务里，我们用 Seata AT，本地有 undo_log 做反向补偿；这一步不能最终一致，否则会出现'库存扣了但订单没生成'。
> **第二段是支付**，渠道回调改订单状态，我们走 RocketMQ 事务消息 + 消费幂等，允许秒级延迟，但靠 `pay_transaction` 流水表 + 定时对账保证一定收敛。
> **第三段是商品到搜索**，走 CDC 异步同步，允许秒级旧数据，因为下单时服务端会重新算价。"

## 五、读多写少 vs 写多读少：为什么电商是"读的战争"

| 场景 | 读写比（经验值） | 优化方向 |
|---|---|---|
| 商品详情 | 1000 : 1 | 多级缓存（本地 + Redis）、静态化、CDN |
| 搜索 | 500 : 1 | ES 索引、只读副本 |
| 购物车 | 10 : 1 | DB 直读，可加短 TTL 缓存 |
| 下单 | 写为主 | 缩短事务、异步化非核心步骤 |
| 支付回调 | 写为主 | 幂等 + 快速返回 |
| 库存查询 | 100 : 1 | Redis 镜像（⚠️ 镜像与 DB 一致性是难点） |

**本项目对应实现**：

- 商品详情用 `@Cacheable(...PRODUCT_DETAIL, key="#id", sync=true)`（`ProductServiceImpl.java:109`）→ 防缓存击穿用 `sync=true`。
- 商品列表**故意不缓存**（`ProductCacheConfig.java:18-20` 注释：参数组合多 + 高频变化）。
- 库存有 Redis 镜像 `stock:{id}`，但**DB 是权威源**（`ProductServiceImpl.java:233-240` 的注释记录了历史事故：曾只扣 Redis 不回写 DB）。

> ⚠️ 这里有个必须讲清的点：**库存为什么不能只信 Redis？** 因为 Redis 可能因为主从切换丢数据、可能因为内存淘汰丢 key、可能因为运维误删。库存是钱，必须落 DB。Redis 只做"快速判断"和"预扣"，不做"最终事实"。

## 六、电商八大技术难题（全模块的"钩子"清单）

后面 9 篇就是把这 8 个逐个拆开。

### 难题 1：超卖（`02` 篇）

- 现象：库存 100，卖了 120。
- 三种错法：先查后减（并发窗口）、缓存扣但 DB 没扣、分布式锁粒度过大。
- 正解：`UPDATE product SET stock = stock - N WHERE id = ? AND stock >= N` → 判断影响行数。
- 本项目：`ProductServiceImpl.java:195-199`（正确）✅

### 难题 2：重复下单 / 重复支付（`03`、`04` 篇）

- 现象：用户点两次 → 两个订单；渠道回调两次 → 扣两次款（或状态乱）。
- 正解：**三层幂等**——① 客户端按钮置灰 + `Idempotent` 注解挡并发；② Redis `SET NX` 占位；③ DB 唯一键 / 状态机 CAS 终审。
- 本项目：`Idempotent.java:12-17`（三层幂等的注释就是教科书级）、`AfterSaleServiceImpl.java:57-64`（业务幂等）、`order-init.sql:112`（DB 唯一键）✅

### 难题 3：订单状态乱（`03` 篇）

- 现象：已取消的订单又变成已支付。
- 正解：状态机 + 唯一迁移入口 + 迁移时带前置状态条件（`UPDATE ... WHERE status = 'PENDING_PAY'`）。
- 本项目：`OrderStateMachineConfig.java:24-29` ✅

### 难题 4：分布式事务（`03` 篇）

- 现象：扣了库存但订单没建；建了订单但库存没扣。
- 三种解法：2PC（Seata AT）、TCC、本地消息表 + 最终一致。
- 本项目：Seata AT（`application.yml:33-48`）+ 事务消息（支付）+ `@TransactionalEventListener(AFTER_COMMIT)`（通知）—— **三种都用在了合适的地方**，这是很好的面试素材。

### 难题 5：优惠券叠加与并发核销（`05` 篇）

- 现象：一个用户把一张券用两次；满减和券叠加后金额为负。
- 正解：算价顺序固定 + 券状态 CAS + `payAmount = max(0, ...)`。
- 本项目：`PromotionServiceImpl.java:52-54`（max ZERO）、`:111-133`（四校验）⚠️ 但缺 CAS 扣减（见 `05` 篇改造）。

### 难题 6：搜索与 DB 不一致（`06` 篇）

- 现象：商品下架了还能搜到；改价后搜到旧价。
- 正解：CDC + 幂等 upsert + 删除兜底 + 定时全量对账。
- 本项目：`ProductCdcConsumer.java:17-18`（注释写清幂等策略）✅

### 难题 7：对账（`04` 篇）

- 现象：用户说付了，订单说没付。
- 正解：流水表 + 主动查单 + T+1 账单比对 + 差异四分类（长款/短款/单边/金额不符）。
- 本项目：只有"主动查单 + 流水比对"雏形 ❌ 无账单文件。

### 难题 8：大促稳定性（`07` 篇）

- 现象：大促 0 点系统 502。
- 正解：容量评估 + 限流 + 缓存预热 + 队列削峰 + 降级预案 + 预案演练。
- 本项目：网关有限流（`RateLimitFilter.java:71-74`）但**默认关闭**（`RateLimitProperties.java:28` `enabled = false`）⚠️

## 七、边界：本项目不做什么（面试被问"你们为什么不做 X"时用）

| 不做 | 理由 | 什么时候该做 |
|---|---|---|
| 微前端 / 多端（小程序/App） | 单应用 24 视图规模，团队单人 | 多团队并行、多端差异化 |
| 自建推荐系统（协同过滤/向量召回） | 样本量不够，冷启动无解 | 日活 > 10 万且有足够行为数据 |
| 自建支付通道 | 需要牌照 | 永远不自建，接渠道 |
| 履约域（仓配） | 无实体仓，超出"软件项目"范围 | 有实体商品与仓库 |
| 商家端 B 端 | 单商户模型 | 多商户平台（需要分账、结算、抽佣） |
| 分库分表（订单） | 单表数据量未到千万级 | 单表 > 2000 万行或写入 QPS 打满 |

> 面试话术：**「这些我们都评估过，结论是现阶段不做，触发条件是 ___。」** 说出触发条件，比说"没必要"专业得多。

## 八、面试：全景题怎么答（3 分钟版）

**问：「介绍一下你们的电商系统架构。」**

> "我们是微服务架构，一共 10 个 Java 服务 + 1 个 Python AI 服务 + 1 个前端，网关统一鉴权、限流、熔断。
> 按业务域分：商品服务管 SPU 和库存，订单服务管购物车、订单、售后，支付服务管收银台和渠道回调，搜索服务管商品索引和向量检索。
> 一条主链路是：用户在商城页浏览 → 加购（DB 唯一键防重）→ 结算页试算价 → 提交订单。**下单是整个系统最重的临界区**，我们把它放在一个 Seata 全局事务里，依次是：取购物车、逐项扣库存（条件 UPDATE 防超卖）、算价（满减 + 券）、建单、核销券、发一条 30 分钟的延迟消息做超时取消。
> 支付是跨系统的最终一致：渠道回调进来先做金额校验，再用 RocketMQ 事务消息把'支付成功'这个事实投出去，订单服务消费后改状态，消费侧靠'已支付直接返回'做幂等，重试 8 次进死信队列，另外有一个定时任务做主动查单和对账兜底。
> 最后是观测：全链路 OTLP 追踪，每个服务有 actuator + Prometheus 指标，日志走 Loki。"

**为什么这个答法好**：有域划分、有主链路、有临界区、有一致性策略、有兜底、有观测。
