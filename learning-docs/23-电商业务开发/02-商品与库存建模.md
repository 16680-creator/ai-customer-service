# 02 - 商品与库存建模

> 目标：能设计出「支撑多规格 + 不超卖 + 高并发可扩展」的商品与库存模型，并说清本项目的单表模型缺什么、怎么演进。
> 本篇是全模块最"数据建模"的一篇，面试里 80% 的电商建模题都能在这里找到答案。

---

## 零、先给结论

商品建模的核心矛盾是 **「一个商品有多个可售单元」**：

- 用户在详情页看到的是 **"iPhone 15"**（一个商品概念）；
- 下单时要选的是 **"iPhone 15 / 黑色 / 256G"**（一个具体可售单元）。

如果你把这两件事塞进一张表，就会出现「同一商品 6 个规格 → 6 条几乎一样的记录 → 改一次描述要改 6 次 → 搜索里出现 6 个重复结果」。

> 结论：**卖"是什么"和卖"哪一件"必须分开建模。** 这就是 SPU / SKU 的由来。

| 概念 | 全称 | 回答的问题 | 举例 | 关键属性 |
|---|---|---|---|---|
| **SPU** | Standard Product Unit | 这是什么？ | iPhone 15 | 标题、卖点、类目、品牌、详情图文 |
| **SKU** | Stock Keeping Unit | 卖的是哪一件？ | iPhone 15 黑 256G | 规格组合、价格、**库存**、条码 |
| **库存** | Inventory | 这件还有几件？ | 黑 256G 还有 12 件 | 可售、锁定、实占 |

一句话面试版：**「SPU 是商品的概念，SKU 是库存的载体；价格和库存挂在 SKU 上，文案和类目挂在 SPU 上。」**

## 一、SPU / SKU 建模：从单表到三表

### 1.1 单表模型（本项目现状）

```sql
-- deploy/mysql/product-init.sql:23-41（实测，节选关键列）
CREATE TABLE product (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    name         VARCHAR(200) NOT NULL,     -- 商品名称
    description  TEXT,
    price        DECIMAL(10,2) NOT NULL,    -- 价格
    stock        INT          NOT NULL DEFAULT 0,  -- 库存
    category_id  BIGINT,
    image        VARCHAR(512),
    status       TINYINT      NOT NULL DEFAULT 1,  -- 0-下架 1-上架
    sales        INT          NOT NULL DEFAULT 0,
    deleted      TINYINT      NOT NULL DEFAULT 0,  -- 逻辑删除
    PRIMARY KEY (id),
    KEY idx_category_id (category_id),
    KEY idx_name (name)
);
```

对应实体 `ai-cs-product/src/main/java/com/aics/product/entity/Product.java:19-37`（`name/description/price/stock/categoryId/image/imageDescription/status/sales`）+ `:45-46` `@TableLogic deleted`。

**这个模型的适用边界**：

| 场景 | 是否够用 | 原因 |
|---|---|---|
| 单一规格商品（书、耳机、充电宝） | ✅ 够用 | 一个商品一个价一个库存 |
| 多规格商品（衣服尺码、手机颜色+容量） | ❌ 不够 | 要么拆成 N 个"商品"，要么无法表达规格 |
| 拼团/秒杀独立价格 | ❌ 不够 | 价格只有一列 |
| 多仓库存 | ❌ 不够 | 库存只有一列 |

> ⚠️ 诚实标注：**本项目是单表模型，全仓 Java 代码里 `sku`/`spu` 0 命中**（2026-11-19 实测）。面试时说"我们是单规格商品模型，简化了 SKU"，比假装有 SKU 强。

### 1.2 三表模型（标准答案）

```sql
-- ① SPU：商品概念
CREATE TABLE spu (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    title       VARCHAR(200)  NOT NULL,
    sub_title   VARCHAR(256),
    category_id BIGINT        NOT NULL,
    brand_id    BIGINT,
    status      TINYINT       NOT NULL DEFAULT 0,   -- 0 下架 1 上架
    create_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- ② 规格与规格值（颜色、尺码…）
CREATE TABLE spec (
    id        BIGINT PRIMARY KEY AUTO_INCREMENT,
    spu_id    BIGINT       NOT NULL,
    name      VARCHAR(32)  NOT NULL,      -- "颜色"
    sort      INT          NOT NULL DEFAULT 0
);
CREATE TABLE spec_value (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    spec_id  BIGINT       NOT NULL,
    value     VARCHAR(32) NOT NULL,       -- "黑色"
    sort      INT         NOT NULL DEFAULT 0
);

-- ③ SKU：可售单元，价格和库存挂这里
CREATE TABLE sku (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    spu_id      BIGINT        NOT NULL,
    sku_code    VARCHAR(64)   NOT NULL,   -- 商家编码，唯一
    spec_json   JSON          NOT NULL,   -- {"颜色":"黑色","容量":"256G"}
    price       DECIMAL(10,2) NOT NULL,
    stock       INT           NOT NULL DEFAULT 0,
    status      TINYINT       NOT NULL DEFAULT 1,
    UNIQUE KEY uk_sku_code (sku_code),
    KEY idx_spu_id (spu_id)
);
```

**为什么 `spec_json` 用 JSON 而不是规格关联表？**

| 方案 | 优点 | 缺点 |
|---|---|---|
| JSON 列 | 查询快、写入简单、规格变化不用改表 | 无法用索引精确筛"所有黑色" |
| 规格关联表（sku_spec_value） | 可精确筛选、可做规格聚合 | 多一次 join、写放大 |

> 业界常见做法：**JSON 存展示用，关联表存筛选用**；或者直接 JSON + 把高频筛选维度（颜色/尺码）单独冗余成列建索引。

### 1.3 迁移路径（面试可能追问"你怎么平滑改"）

1. **加表不改老表**：新建 `spu` / `sku`，`product` 保留不动。
2. **数据搬迁**：每个 `product` 生成 1 条 `spu` + 1 条 `sku`（`sku.spec_json = '{}'`，`price`/`stock` 原样搬）。用脚本 + 校验（`SELECT count(*)` 一一对应）。
3. **双写期**：下单链路先读新表；老接口（`GET /product/list`）内部改为 join SPU+SKU 后返回，**对外契约不变**。
4. **切读**：`ProductServiceImpl` 里 `getProductList` 改为查 SPU，`getProductDetail` 返回 `spu + skuList`；前端 `ProductView.vue` 详情页加规格选择。
5. **下线老表列**：确认无读方后，`ALTER TABLE product DROP COLUMN stock`。

> 关键点：**每一步都可回滚，且对外 HTTP 契约不变**。这是"平滑迁移"的标准答法。

## 二、库存模型：三个数字而不是一个

很多项目只有 `stock` 一列，结果出现「下单未支付时库存被占用，但取消后没还回来」或「并发下超卖」。

### 2.1 标准三字段

```sql
stock        INT NOT NULL,  -- 可售库存（用户能买到的）
locked_stock INT NOT NULL,  -- 锁定库存（已下单未支付）
sold_stock   INT NOT NULL,  -- 已售库存（已支付/已发货）
-- 恒等式：总库存 total = stock + locked_stock + sold_stock
```

**为什么需要 locked？** 因为"下单"和"支付"之间有时间窗（本项目 30 分钟）：

- 下单：`stock -= N`、`locked += N`
- 支付成功：`locked -= N`、`sold += N`
- 超时/取消：`locked -= N`、`stock += N`
- 发货：`sold` 不变（已经算卖了）

### 2.2 本项目的简化版

本项目只用一列 `stock`（`product-init.sql:28`），语义是 **"可售库存"**：

- 下单扣减：`stock = stock - N`（`ProductServiceImpl.java:195-199`）
- 取消/退款回补：`stock = stock + N`（`:220-223`）
- **没有 locked 概念**：下单即视为"已占用"，超时任务把库存还回去（`OrderService.cancelExpiredOrder` → `doCancelOrder` → `restoreStock`）。

> 这个简化在"下单即锁库"的前提下是自洽的。它省掉了 `locked_stock` 的维护成本，代价是**无法回答"当前有多少库存在途（已下单未支付）"** —— 运营想看这个数字就只能查订单表实时聚合。

面试时如果被问"你们库存模型"，标准答法：**「我们是下单即扣减的单列库存模型，本质上是把 locked 合并进了扣减动作，靠 30 分钟超时任务做归还。如果要支持预售/多仓/在途统计，就需要拆成 stock/locked/sold 三列。」**

## 三、五种扣减时机：什么时候减库存？

这是电商面试的**必考题**。答案是「看业务，没有唯一正解」。

| # | 时机 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| 1 | **加购物车时扣** | 绝不会超卖 | 恶意占库存成本极低（加购不付款），库存利用率差 | 基本不用 |
| 2 | **提交订单时扣**（下单扣减） | 简单、防超卖效果好 | 未支付订单占库存，需要超时归还 | **中小电商主流**，本项目 |
| 3 | **支付成功时扣** | 库存利用最大化 | 支付成功才发现没货 → 必须退款，体验差 | 库存充足的标品 |
| 4 | **预扣 + 支付确认（两阶段）** | 兼顾防超卖与利用率 | 实现复杂，需要 locked_stock | 大促、秒杀、预售 |
| 5 | **不扣，发货时扣** | 无占库存问题 | 严重超卖 | 只在"先卖后采"的定制/生鲜里出现 |

**本项目的选择**：时机 2 —— `OrderCreateTxService.java:93-95` 在下单事务里逐项调 `productClient.deductStock`。理由写在 `:88-92` 的注释里：扣库存是 Seata AT 分支事务，本地有 `undo_log` 可以反向补偿。

### 追问：「下单扣减 + 30 分钟超时，如果超时任务挂了怎么办？」

三层兜底（本项目真的三层都有）：

| 层 | 实现 | 证据 |
|---|---|---|
| 延迟消息（首选，准时） | RocketMQ delayLevel 16 ≈ 30min | `OrderCreateTxService.java:144-146` |
| 定时扫描（兜底，滞后） | `@Scheduled(fixedDelay=300000)` | `OrderTimeoutScheduler.java:29` |
| 调度平台（可观测，可手动补偿） | `@XxlJob("orderTimeoutScanJob")` | `OrderTimeoutScanJob.java:27` |

三层都是**幂等**的（`cancelExpiredOrder` 里非 `PENDING_PAY` 直接 return，`OrderServiceImpl.java:168-176`），所以重复触发不会重复回补库存。

## 四、防超卖：从错到对的四个版本

### 4.1 版本 1（错）：先查后减

```java
// ❌ 典型错误
Product p = productMapper.selectById(id);
if (p.getStock() >= qty) {
    p.setStock(p.getStock() - qty);
    productMapper.updateById(p);
}
```

**为什么错**：`select` 和 `update` 之间有窗口。100 件库存、200 个并发请求，全部读到 `stock=100`，全部通过判断，最后 `stock` 可能是 -100。

> 这就是**丢失更新（lost update）**。注意：即使把这段代码包在 `@Transactional` 里也一样错——事务只保证隔离级别，MySQL 默认 RR 下两个事务各自读到快照 100，都能更新成功。

### 4.2 版本 2（可行但重）：悲观锁

```sql
SELECT stock FROM product WHERE id = ? FOR UPDATE;  -- 行锁
-- 校验后 UPDATE
```

能防超卖，但：① 持锁时间长，热点商品行锁排队；② `FOR UPDATE` 在 Seata AT 下会产生额外锁冲突；③ 死锁风险（多商品下单顺序不一致时）。

### 4.3 版本 3（本项目，推荐）：条件更新（乐观 + 原子）

```java
// ✅ ai-cs-product/src/main/java/com/aics/product/service/impl/ProductServiceImpl.java:195-199
int rows = productMapper.update(null, new LambdaUpdateWrapper<Product>()
        .eq(Product::getId, productId)
        .ge(Product::getStock, quantity)      // WHERE stock >= qty
        .setSql("stock = stock - " + quantity) // SET stock = stock - qty
        .setSql("sales = sales + " + quantity));
```

生成的 SQL 是：

```sql
UPDATE product SET stock = stock - 5, sales = sales + 5
WHERE id = 1001 AND stock >= 5;
```

**为什么对**：`stock = stock - 5` 是**数据库层面的原子读改写**，加上 `WHERE stock >= 5` 让"库存不足"变成"影响 0 行"。InnoDB 的行锁保证同一行的并发 UPDATE 串行执行，不需要应用层加锁。

`rows == 0` 时再区分两种原因（`:200-208`）：

```java
if (rows == 0) {
    Product product = productMapper.selectById(productId);
    if (product == null) throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND, "商品不存在");
    throw new BusinessException(ResultCode.PRODUCT_STOCK_INSUFFICIENT,
            "商品库存不足，当前库存: " + product.getStock());
}
```

> 这一步很关键：**影响行数为 0 不等于库存不足**，也可能是商品被删了。区分开才能给用户正确的错误提示。

### 4.4 版本 4（秒杀级）：Redis 预扣 + 异步落库

当 QPS 到 10 万级，`UPDATE product` 的行锁会成为瓶颈（同一行串行）。这时上 Redis：

```lua
-- Lua 脚本保证原子：判断 + 扣减 一步完成
local stock = redis.call('GET', KEYS[1])
if not stock or tonumber(stock) < tonumber(ARGV[1]) then return -1 end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```

然后把"扣减成功"的请求丢进 MQ 异步落库。

**但它引入了新问题**：Redis 扣了、DB 落库失败怎么办？→ 必须能对账（Redis 剩余 vs DB 库存），且要有"库存回滚补偿任务"。**本项目没有做**（见 §六 缺口表）。

## 五、库存与缓存：为什么 Redis 只能当镜像

### 5.1 本项目的双写结构

```
[写路径] 下单 → deductStock → ① UPDATE DB（权威） → ② SET Redis stock:{id}（镜像）
[读路径] 加购 → CartServiceImpl.availableStock → 优先 Feign 拿 product.stock → 回落 Redis
                                              ↓
                              商品详情 → @Cacheable(product:detail, 30min)
```

证据：

- 扣减后回写镜像：`ProductServiceImpl.java:210-211`
- 回补后回写镜像：`:227-228`
- 建品时初始化镜像：`:72-73`
- 购物车读库存（先用 Feign 的真实 stock，失败才读 Redis）：`CartServiceImpl.java:158-176`
- 库存校准接口（DB 全量刷 Redis）：`ProductServiceImpl.java:232-241` + `ProductController.java:154-158`

### 5.2 历史事故的教训（这段注释值钱）

```java
// ai-cs-product/src/main/java/com/aics/product/service/impl/ProductServiceImpl.java:234-236
// 运维校准：历史订单曾只扣 Redis 镜像、从不回写 DB，导致 Redis 与 DB 不一致。
// 切换为「DB 权威源」后，部署完成时全量把 DB 同步到 Redis，使镜像立即对齐。
```

> **面试金句**：「我们踩过一个坑——早期是 Redis 扣减为主、DB 异步回写，结果 Redis 主从切换丢了几条扣减记录，DB 里库存虚高，超卖了 30 多件。后来改成 **DB 是唯一权威源，Redis 只做镜像**，并且提供了 `/product/stock/sync` 校准接口。」

### 5.3 三个必须回答的问题

**Q1：为什么不只信 Redis？**
Redis 可能丢数据（主从异步复制、内存淘汰、误删 key）。库存是钱，丢了就是资损。

**Q2：为什么还要 Redis 镜像？**
因为购物车、商品列表要频繁判断"有没有货"，这些读请求量是下单的 100 倍。全打到 DB 会拖垮。镜像是"快速判断"，DB 是"最终裁判"。

**Q3：镜像和 DB 不一致时以谁为准？**
**DB**。所以扣减走 DB（`deductStock` 直接 `UPDATE ... WHERE stock >= N`），镜像只是事后同步。这样即使镜像脏了，也不会超卖。

> 反过来说：**如果扣减走的是 Redis，超卖风险就引入了**（本项目没有这样做，是对的）。

## 六、商品缓存设计：为什么列表不缓存

`ai-cs-product/src/main/java/com/aics/product/config/ProductCacheConfig.java:16-21` 的注释是教科书级的：

```
- product:detail     商品详情，TTL 30 分钟；更新/删品/扣补库存主动驱逐
- product:categories 分类列表，TTL 10 分钟；创建分类主动驱逐
- 分页商品列表不缓存：参数组合基数高且库存/销量高频变化，命中率低、失效面大
```

配套实现：

| 操作 | 缓存动作 | 证据 |
|---|---|---|
| 查详情 | `@Cacheable(sync = true)`（防击穿：并发同时未命中只放一个查库） | `:109` |
| 改商品 | `@CacheEvict(key = "#id")` | `:119` |
| 删商品 | `@CacheEvict(key = "#id")` | `:159` |
| 扣库存 | `@CacheEvict(key = "#productId")` | `:191` |
| 补库存 | `@CacheEvict(key = "#productId")` | `:217` |
| 建分类 | `@CacheEvict(allEntries = true)` | `:244` |
| 查分类 | `@Cacheable(key="'all'", sync=true)` | `:256` |

**为什么扣库存要驱逐详情缓存？** 因为 `ProductVO` 里有 `stock` 字段（`toVO` `:276`）。不驱逐的话，用户会看到旧库存。

**这个设计有个小瑕疵**：高频扣库存会让详情缓存频繁失效（缓存雪崩风险）。更好的做法是**库存不进详情缓存**（详情缓存只放文案/图片，库存单独实时查），这样扣库存就不用驱逐缓存。本项目没这么做，可以主动在面试里说。

## 七、商品快照：为什么订单要冗余商品信息

`deploy/mysql/order-init.sql:49-61`：

```sql
CREATE TABLE order_item (
    order_id      BIGINT       NOT NULL,
    order_no      VARCHAR(32)  NOT NULL,       -- 冗余，便于按订单号直查
    product_id    BIGINT       NOT NULL,
    product_name  VARCHAR(200) NOT NULL,       -- 快照！
    product_price DECIMAL(10,2) NOT NULL,      -- 成交单价快照！
    quantity      INT          NOT NULL,
    subtotal      DECIMAL(10,2) NOT NULL,
    ...
);
```

**为什么必须快照？** 三个真实场景：

1. 商家 3 天后把商品名改成"无线蓝牙耳机 Pro Max"，用户看订单详情时不能显示新名字。
2. 商品涨价到 299，用户当时 199 买的，订单必须显示 199。
3. 商品被删除（`@TableLogic` 逻辑删除），如果订单只存 `product_id`，详情页就 join 不出数据了。

> 面试金句：**「订单是法律凭证，必须冻结成交那一刻的事实。所以 order_item 冗余了商品名和单价，购物车也冗余了 product_name/product_price（`order-init.sql:12-13` 注释写的是"加入时单价"）。」**

注意购物车的语义不同：购物车是"意向"，**加购时的价格只是参考**，结算时要重新算价（`PromotionServiceImpl.calculatePrice`）。所以购物车快照是"为展示方便"，订单快照是"为永远正确"。

## 八、类目建模：树怎么存

本项目 `product_category`（`product-init.sql:10-20`）用 **parent_id 邻接表**：

```sql
CREATE TABLE product_category (
    id        BIGINT NOT NULL AUTO_INCREMENT,
    name      VARCHAR(128) NOT NULL,
    parent_id BIGINT NOT NULL DEFAULT 0,   -- 0 为顶级
    sort      INT    NOT NULL DEFAULT 0,
    description VARCHAR(512),
    KEY idx_parent_id (parent_id)
);
```

种子数据（`:44-50`）是两级：`数码配件(1)` → `耳机音箱(4)` / `手机配件(5)`。

**四种树存储方案对比**：

| 方案 | 表结构 | 查子树 | 查祖先 | 适用 |
|---|---|---|---|---|
| **邻接表**（本项目） | `parent_id` | 递归 CTE 或多次查 | 逐层往上查 | 层级浅（≤3 层） |
| 路径枚举 | `path = '/1/4/'` | `WHERE path LIKE '/1/4/%'` | 拆字符串 | 层级浅、读多 |
| 嵌套集 | `lft` / `rgt` | `WHERE lft BETWEEN ? AND ?` | `WHERE lft < ? AND rgt > ?` | 读极多写极少 |
| 闭包表 | 单独 `category_path(ancestor, descendant, depth)` | join 一次 | join 一次 | 层级深、读写都多 |

> 电商类目一般 **2~3 层**，邻接表够用。面试若追问"查一个类目下所有商品（含子类目）"，答：**先递归查出子类目 ID 集合，再 `WHERE category_id IN (...)`**；类目树可以全量缓存（本项目 `product:categories` TTL 10 分钟，`:256-260`）。

## 九、本项目 vs 标准模型：差距清单

| 能力 | 本项目 | 标准电商 | 影响 |
|---|---|---|---|
| SPU/SKU | ❌ 单表 | ✅ 三表 | 不支持多规格 |
| 规格（颜色/尺码） | ❌ 无 | ✅ spec + spec_value | 无法选规格 |
| 多仓库存 | ❌ 单列 | ✅ 库存按仓拆分 | 无法支持多仓发货 |
| locked/sold 拆分 | ❌ 只有 stock | ✅ 三列 | 看不到"在途库存" |
| 独立价格（拼团/秒杀） | ❌ 一列 price | ✅ 价格表/活动价 | 无法做活动价 |
| 商品属性（可筛选） | ❌ 只有 description | ✅ attr + attr_value | 无法按属性筛选 |
| 品牌 | ❌ 无 | ✅ brand 表 | 无法按品牌筛选 |
| 商品审核流 | ❌ 直接上架 | ✅ draft→audit→online | 无 B 端管控 |
| 库存流水（谁扣的） | ❌ 只有日志 | ✅ stock_log 表 | 库存对不上时无法追溯 |

> ⚠️ 最后一条特别重要：**库存流水表**。生产环境库存对不上时，唯一能查清"谁在什么时候扣了几件"的办法就是流水表（`sku_id / change_type / before / after / biz_no / operator / create_time`）。本项目只有 `log.info("库存扣减成功...")`（`ProductServiceImpl.java:212`），日志会被轮转清理，**不可作为审计依据**。

## 十、面试：本篇衍生题清单（附答法要点）

### Q1：SPU 和 SKU 有什么区别？

> SPU 是商品概念（iPhone 15），SKU 是可售单元（iPhone 15 黑 256G）。**价格和库存挂 SKU，文案和类目挂 SPU。** 好处是详情页只有一份文案，列表页不会出现 6 个重复商品。

### Q2：你们商品表怎么设计的？

> 我们是单规格模型：`product` 单表，`price` 和 `stock` 直接挂在商品上，加了 `category_id` 关联两级类目，`deleted` 做逻辑删除。**如果要支持多规格，我会拆成 spu/sku 两张表，sku 上用 JSON 存规格、价格和库存下移到 sku。**

### Q3：怎么防超卖？

> 用条件更新：`UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?`，判断影响行数。影响 0 行再回查区分"商品不存在"和"库存不足"。**不用先查后改，因为查和改之间有并发窗口；也不用 SELECT FOR UPDATE，因为行锁会排队，热点商品扛不住。**

### Q4：怎么处理下单未支付的库存占用？

> 下单时就扣库存，同时发一条 30 分钟延迟消息；超时任务把订单取消并回补库存。另外还有 `@Scheduled` 定时扫描和 XXL-Job 调度两条兜底通道，三条路径都幂等。

### Q5：库存放 Redis 还是 DB？

> **DB 是权威源，Redis 只是镜像。** 扣减必须走 DB 的条件更新；Redis 镜像用于购物车和列表的高频"有没有货"判断。我们踩过坑：早期以 Redis 为主异步回写 DB，主从切换丢数据导致超卖，后来改回 DB 权威源，并加了 `/product/stock/sync` 校准接口。

### Q6：商品详情缓存怎么设计的？为什么列表不缓存？

> 详情用 `@Cacheable` + `sync=true` 防击穿，TTL 30 分钟，更新/删品/扣补库存都 `@CacheEvict`。**列表故意不缓存**：分页参数组合基数太高（页码 × 类目 × 关键词 × 状态），而且库存销量高频变化，缓存命中率低、失效面大，得不偿失。

### Q7：商品下架了，用户的购物车里还有，怎么办？

> 购物车列表返回时做**实时校验**：`CartServiceImpl.addToCart` 里会查商品状态，`currentStock` 拿实时库存（`CartServiceImpl.java:178-196`）。购物车渲染时对"已下架/无货"的商品置灰并提示。**购物车不做删除，因为用户可能只是暂时不买。**

### Q8：如果让你加 SKU，改动量多大？

> 三块：① 数据层新增 spu/sku/spec 表并迁移存量数据（一个 product → 一个 spu + 一个 sku）；② 商品服务接口加 `skuList`，详情页返回规格矩阵；③ 交易层 `cart_item` 和 `order_item` 的 `product_id` 改为 `sku_id`，扣库存接口参数从 `productId` 改成 `skuId`。**对外 HTTP 契约可以保持不变，靠双写期过渡。**
