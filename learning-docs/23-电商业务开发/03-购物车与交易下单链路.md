# 03 - 购物车与交易下单链路

> 目标：把「加购 → 结算 → 下单」这条链路讲到每一行代码、每一个事务边界都能指出来。
> 这是电商面试**最深的一条线**：订单号、幂等、状态机、分布式事务、超时取消、锁，全在这条链上。

---

## 零、先给结论

下单是全系统唯一的「多资源写临界区」：一次下单要同时改 **购物车（读）、库存（远程写）、订单（本库写）、订单项（本库写）、优惠券（本库写）**，还要发 **延迟消息**。

> 一句话面试版：**「下单 = 一个全局事务 + 一把用户级分布式锁 + 一条延迟消息。锁在事务外，消息在事务内，事务不跨越 MQ。」**

## 二、购物车：为什么它比看起来复杂

### 2.1 数据模型

`deploy/mysql/order-init.sql:8-21`：

```sql
CREATE TABLE cart_item (
    id            BIGINT NOT NULL AUTO_INCREMENT,
    user_id       BIGINT NOT NULL,
    product_id    BIGINT NOT NULL,
    product_name  VARCHAR(200) NOT NULL,   -- 快照（"加入时"的商品名）
    product_price DECIMAL(10,2) NOT NULL,  -- 快照（"加入时"单价）
    quantity      INT NOT NULL DEFAULT 1,
    selected      TINYINT(1) NOT NULL DEFAULT 1,
    create_time   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_product (user_id, product_id),   -- ★ 关键
    KEY idx_user_id (user_id)
);
```

**为什么必须有 `uk_user_product`？**

没有它，用户点 5 次「加入购物车」就会出现 5 行相同商品 → 购物车页重复、结算时数量不对、并发下还可能脏读。有了唯一键后有两种处理：

| 策略 | 行为 | 本项目 |
|---|---|---|
| `INSERT ... ON DUPLICATE KEY UPDATE quantity = quantity + N` | 一条 SQL 完成"有则加、无则插" | ❌ 未用 |
| 先查再分支（查到就 update，查不到就 insert） | 需要处理并发插入冲突 | ✅ 本项目 |

本项目 `CartServiceImpl.addToCart`（`:58-111`）：

```java
// ai-cs-order/src/main/java/com/aics/order/service/impl/CartServiceImpl.java:87-108
CartItem existing = cartItemMapper.selectOne(new LambdaQueryWrapper<CartItem>()
        .eq(CartItem::getUserId, userId)
        .eq(CartItem::getProductId, productId));
if (existing != null) {
    int newQuantity = existing.getQuantity() + quantity;
    if (newQuantity > availableStock) {   // ★ 合并后要重新校验库存
        throw new BusinessException(ResultCode.ORDER_STOCK_INSUFFICIENT,
                "库存不足，购物车已有 " + existing.getQuantity() + " 件，最多再加 "
                        + (availableStock - existing.getQuantity()) + " 件");
    }
    existing.setQuantity(newQuantity);
    cartItemMapper.updateById(existing);
} else {
    ... insert
}
```

> ⚠️ **已知并发缺陷（可以主动在面试说）**：先查后插在并发下会撞唯一键，抛 `DuplicateKeyException`（500）。正确做法是 `INSERT ... ON DUPLICATE KEY UPDATE`，或者捕获 `DuplicateKeyException` 后降级为 update。本项目没做。

**为什么合并后必须重新校验库存？**
假设库存 10 件，用户购物车已有 8 件，再加 5 件。如果只校验 `5 <= 10` 就放行，购物车里就变成 13 件 > 库存 10。所以校验的是 **合并后的总量**（`:92`）。

### 2.2 快照与实时：购物车的双重身份

| 字段 | 语义 | 结算时用哪个 |
|---|---|---|
| `product_name` / `product_price` | 加入时的快照，**只用于展示** | 不用 |
| 库存 | 不存，实时查 | **实时**（`currentStock` `:178-196`） |
| 价格 | 存了，但结算时**重新算** | **实时**（`PromotionServiceImpl.calculatePrice`） |

> 面试追问「购物车价格什么时候更新？」标准答法：**「购物车展示用快照，减少商品服务的读压力；进入结算页时用实时价格重算，并把差异提示给用户（'部分商品价格已变化'）。这条规则的意义是：展示可以旧，成交必须新。」**

### 2.3 库存读取的三级降级

`CartServiceImpl.java:158-197` 有两个方法，语义不同：

```java
// availableStock：加购时用，优先用刚拿到商品信息里的 stock
private int availableStock(Long productId, Integer productStock) {
    if (productStock != null) return productStock;         // ① 已有实时值
    String stockStr = redis.get("stock:" + productId);
    if (stockStr != null) { ... if (v >= 0) return v; }    // ② Redis 镜像
    return Integer.MAX_VALUE;                              // ③ 放行（不阻断加购）
}

// currentStock：改数量时用，强制回源
private int currentStock(Long productId) {
    try {
        ProductRemoteDTO remote = productClient.getProduct(productId);
        if (... getStock() != null) return remote.getData().getStock();  // ① Feign 实时
    } catch (Exception e) { log.warn(...); }
    String stockStr = redis.get("stock:" + productId);     // ② Redis 兜底
    if (stockStr != null) { ... if (v >= 0) return v; }
    return Integer.MAX_VALUE;                              // ③ 放行
}
```

**两个细节值得说**：

1. `if (v >= 0) return v;` —— 注释写「历史脏数据（负数）视为无效」（`:167`、`:191`）。这是踩过坑的痕迹：曾经 Redis 里出现过负数库存。
2. 最终 `return Integer.MAX_VALUE` —— **fail-open**。商品服务挂了，加购不阻断，把"库存不足"的判断推迟到下单（下单才是权威校验）。这是正确的取舍：**加购失败的用户流失成本 > 加购成功但下单失败的体验损失**。

## 三、结算试算：为什么它不锁库存

`CartController.checkoutConfirm`（`:78-131`）做四件事：

```java
List<CartItem> items = cartItemMapper.selectBatchIds(dto.getCartItemIds());   // :82
BigDecimal totalAmount = items.stream()...reduce(ZERO, BigDecimal::add);     // :85-87
PriceCalcBO priceCalc = promotionService.calculatePrice(totalAmount, userId, null); // :90
List<CouponAvailability> coupons = promotionService.getAvailableCoupons(userId, totalAmount); // :93-94
```

然后组装 `CheckoutConfirmVO`：商品项、商品总额、满减（是否命中/规则名/金额）、可用券列表（含不可用原因）、应付金额（`:96-129`）。

**四个设计点**：

1. **不锁库存**。结算页可以被刷新 100 次、可以在多个 tab 同时打开。如果试算就锁库存，恶意用户能把库存锁死（"加购-结算-不付款"循环）。所以**试算只是"参考价"，真正的库存在下单事务里扣**。
2. **券传 `null`**：试算时不指定券（`:90`），因为用户还没选。选了券后前端可以再调一次试算，或者本地计算展示。
3. **返回"不可用原因"**：`CouponVO.reason`（`:124`）由 `PromotionServiceImpl.getAvailableCoupons` 填充（如"未满 199 元"）。这是好的产品设计——**告诉用户差多少才能用**。
4. **试算与下单用同一套算价代码**（`promotionService.calculatePrice`）。如果两处各写一遍，就会出现"结算页显示 180，下单扣 200"的客诉。

> ⚠️ 本项目的真实风险：试算与下单之间有**时间差**（用户可能在结算页停留 10 分钟）。期间商品可能涨价/券可能被用掉/满减活动可能结束。下单时 `calculatePrice` 会重新算，**但前端没有提示"价格已变化"**。这是可以主动说的改进点。

## 四、下单事务：八步逐行拆解

`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:78-158`：

```java
@GlobalTransactional(rollbackFor = Exception.class, name = "order-create")   // :78
@Transactional(rollbackFor = Exception.class)                                // :79
public OrderVO doCreateOrder(Long userId, List<Long> cartItemIds, Long couponId, String paymentMethod) {
```

### Step 1：读购物车（`:82-85`）

```java
List<CartItem> cartItems = cartItemMapper.selectBatchIds(cartItemIds);
if (cartItems.isEmpty()) {
    throw new BusinessException(ResultCode.ORDER_CART_EMPTY);
}
```

> ⚠️ **安全缺陷（面试可主动提）**：`selectBatchIds` 只按主键查，**没有校验 `cartItemIds` 是否属于当前 `userId`**。理论上用户 A 可以传用户 B 的 cartItemId 下单（越权）。正确做法是加 `eq(CartItem::getUserId, userId)`。这是很典型的"看起来能跑，但有安全洞"的代码。

### Step 2：扣库存（`:87-95`）

```java
for (CartItem item : cartItems) {
    productClient.deductStock(item.getProductId(), item.getQuantity());
}
```

注释（`:88-92`）写得非常好，值得逐句读：

```
学习要点（Seata AT）：扣库存是 Feign 调用 product 的分支事务——XID 随请求头传播，
product 侧数据源代理生成 undo_log；任一环节失败（如库存不足），
全局事务二阶段回滚时按 undo_log 反向补偿已提交的分支，无需手写「失败回滚」。
注意：MQ 不是 Seata 资源，全局回滚时下方延迟消息已发出——但消费侧
cancelExpiredOrder 查不到订单会直接返回，天然幂等安全。
```

**三个必须理解的点**：

| 点 | 解释 |
|---|---|
| XID 怎么传 | Seata 通过 `RootContext` + Feign 拦截器把 XID 放进 HTTP header（`TX_XID`），product 侧的数据源代理读到后把本地事务注册为分支 |
| undo_log 是什么 | product 库里的 `undo_log` 表（`deploy/mysql/seata-undo-log.sql:25`），记录 before-image，二阶段回滚时用它反向生成补偿 SQL |
| 为什么 MQ 不是资源 | RocketMQ 没有实现 Seata 的 `ResourceManager` 接口，全局回滚不会撤消息。所以靠**消费侧幂等**兜底 |

**循环扣库存的顺序问题**：多商品下单时按 `cartItems` 的顺序扣。如果两个用户以相反顺序下单同一批商品，可能死锁（A 锁 P1 等 P2，B 锁 P2 等 P1）。**正确做法是按 productId 排序后再扣**。本项目没排序 —— 又一个可以说的改进点。

### Step 3：算价（`:97-101`）

```java
BigDecimal totalAmount = cartItems.stream()
        .map(item -> item.getProductPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
PriceCalcBO priceCalc = promotionService.calculatePrice(totalAmount, userId, couponId);
```

注意 `item.getProductPrice()` 用的是**购物车快照价**，不是实时价！这是本项目的真实缺陷：

> ⚠️ **价格风险**：如果商品在加入购物车后涨价，用户会按旧价下单。正确做法是下单时通过 Feign 拿商品实时价重新计算。本项目的 `deductStock` 只扣库存不返回价格。这是"看起来对、实际有资损风险"的典型代码。详见 [05-营销与优惠计算](./05-营销与优惠计算.md) §五。

### Step 4：建订单（`:103-117`）

```java

order.setUserId(userId);
```

`timeoutMinutes` 来自配置（`:61-62`）：


> **默认 30 分钟**，可通过 `order.timeout-minutes` 覆盖。这个值要和延迟消息的 `delayLevel` 对齐（见 Step 7）。

### Step 5：建订单项（`:119-130`）

```java
for (CartItem item : cartItems) {
    OrderItem orderItem = new OrderItem();
    orderItem.setOrderId(order.getId());
    orderItem.setOrderNo(orderNo);              // 冗余订单号
    orderItem.setProductId(item.getProductId());
    orderItem.setProductName(item.getProductName());
    orderItem.setProductPrice(item.getProductPrice());
    orderItem.setQuantity(item.getQuantity());
    orderItem.setSubtotal(item.getProductPrice().multiply(BigDecimal.valueOf(item.getQuantity())));
    orderItemMapper.insert(orderItem);

```

> ⚠️ 这里用的是 `for + insert`，N 个商品 = N 次 SQL。商品数量多时（比如一次买 20 件）性能一般。批量插入（`insertBatchSomeColumn` 或 `foreach`）更好。

### Step 6：核销券（`:132-141`）

```java
if (couponId != null && priceCalc.getCouponAmount().compareTo(BigDecimal.ZERO) > 0) {
    Coupon coupon = couponMapper.selectById(couponId);
    if (coupon != null) {
        coupon.setStatus(CouponStatus.USED.getCode());
        coupon.setUseTime(LocalDateTime.now());
        coupon.setOrderNo(orderNo);
        couponMapper.updateById(coupon);
    }
}
```

> ⚠️ **并发核销缺陷（必考）**：`selectById` → `updateById` 之间没有状态条件。两个并发请求都读到 `UNUSED`，都能改成 `USED`，**同一张券被用两次**。正确做法：
> ```sql
> UPDATE coupon SET status='USED', use_time=NOW(), order_no=?
> WHERE id=? AND user_id=? AND status='UNUSED';
> -- 判断影响行数 == 1
> ```
> 这也解释了为什么 `coupon` 表需要 `idx_status`（`order-init.sql:77`）。

### Step 7：发延迟消息（`:143-146`）

```java
rocketMQTemplate.syncSend("order-timeout-topic",
        MessageBuilder.withPayload(orderNo).build(),
        5000, 16); // delayLevel 16 ≈ 30min
```

**RocketMQ 延迟消息的级别表**（固定 18 级）：

| delayLevel | 延迟 |
|---|---|
| 1~10 | 1s、5s、10s、30s、1m、2m、3m、4m、5m、6m |
| 11~18 | 7m、8m、9m、10m、20m、**30m**、1h、2h |

第 4 个参数就是 delayLevel。代码里用 16 = 30 分钟，正好等于默认的 `order.timeout-minutes:30`。

> ⚠️ **两处需要注意**：
> 1. RocketMQ 4.x 只支持 18 个固定级别；5.x 支持任意时间（`deliverTime`）。本项目用级别，所以 `timeout-minutes` 改成本表外的值时会对不齐。
> 2. `syncSend` 是同步发送，超时 5000ms。如果 MQ 挂了，**会抛异常导致整个下单事务回滚**（这其实是好的：宁可下单失败，也不要产生"永远不会被取消"的订单）。

### Step 8：组装返回（`:148-157`）


## 五、订单号生成：一个必考的小问题

`OrderCreateTxService.java:160-164`：

```java
private static final AtomicInteger SEQUENCE = new AtomicInteger(0);   // :51

private String generateOrderNo() {
    String timestamp = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"));
    int seq = SEQUENCE.incrementAndGet() % 10000;
    return timestamp + "01" + String.format("%04d", seq);
}
```

格式：`yyyyMMddHHmmss` + `"01"`（渠道/业务码）+ 4 位序号，共 20 位。

### 五种订单号方案对比

| 方案 | 示例 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **时间 + 进程内 seq**（本项目） | `2026111914301201 0001` | 可读、有含义、实现简单 | **多实例撞号**；seq 到 10000 回绕 | 单实例/低并发 |
| UUID | `550e8400-...` | 全局唯一，无中心 | 不可读、索引碎片（随机） | 内部主键 |
| 雪花算法 Snowflake | `1789...`（19 位） | 趋势递增、唯一、高性能 | 依赖机器 ID 管理、时钟回拨 | **互联网主流** |
| 号段模式（DB） | `20261119 + 递增` | 唯一、可控、可读 | 依赖 DB，需要预分配 | 订单/发票 |
| Redis INCR | `ORDER20261119 000123` | 简单唯一、自增 | 依赖 Redis 可用性 | 中小项目 |

### 本项目的问题与修法

**问题**：`AtomicInteger` 是 JVM 进程内的（`:51`）。部署 2 个实例时，13:30:12 这一秒里实例 A 的第 1 单和实例 B 的第 1 单会生成**完全相同的订单号**。

**兜底**：`orders` 表有 `UNIQUE KEY uk_order_no`（`order-init.sql:42`），第二个插入会 `DuplicateKeyException` → 500 错误。所以是"偶发下单失败"而不是"数据错乱"。

**修法（推荐）**：雪花算法。如果用 MyBatis-Plus，自带 `IdWorker.getIdStr()`（基于 Snowflake），一行搞定：

```java
private String generateOrderNo() {
    // 雪花 ID 保证多实例唯一；前缀保留可读性
    return "ORD" + IdWorker.getIdStr();
}
```

> 面试标准答法：**「我们用的是`时间戳+业务码+序号`，老实说这个方案在多实例部署时会撞号，靠数据库唯一键兜底报错。如果重做，我会用雪花算法——趋势递增、多实例唯一、还能减少 B+ 树页分裂。」** 这个答法比"我们用了雪花"更有说服力，因为你讲出了取舍和兜底。

## 六、订单状态机：为什么不能写 if-else

### 6.1 状态与事件

`ai-cs-order/src/main/java/com/aics/order/enums/OrderStatus.java:13-17`：

### 6.2 五条合法迁移

画成图：

```
                PAY              REFUND_REQUEST        REFUND_SUCCESS
PENDING_PAY ──────────▶ PAID ──────────────▶ REFUNDING ─────────────▶ REFUNDED
```

### 6.3 状态机的适配器：`OrderStateTransitionService`

`statemachine/OrderStateTransitionService.java:21-35`：

```java
public OrderStatus transit(String currentStatus, OrderEvent event) {
    OrderStatus current = parse(currentStatus);          // DB 字符串 → 枚举
    synchronized (orderStateMachine) {                    // ★ 状态机不是线程安全的
        orderStateMachine.stop();
        orderStateMachine.getStateMachineAccessor().doWithAllRegions(access ->
                access.resetStateMachine(new DefaultStateMachineContext<>(current, null, null, null)));
        orderStateMachine.start();
        boolean accepted = orderStateMachine.sendEvent(MessageBuilder.withPayload(event).build());
        if (!accepted) {
            throw new BusinessException(ResultCode.BAD_REQUEST,
                    "订单状态不允许迁移: " + current.getCode() + " --" + event + "--> ?");
        }
        return orderStateMachine.getState().getId();
    }
}
```

**为什么需要 `synchronized`？** Spring StateMachine 的实例是**单例**，内部持有当前状态。如果不加锁，两个并发迁移会互相污染状态。所以每次迁移都要 `reset` 到 DB 里的真实状态再 `sendEvent`。

> ⚠️ **这个实现是"能用但不优雅"**：`synchronized` 让所有订单的状态迁移串行化，高并发下是瓶颈。更好的做法是把迁移规则写成纯函数（`Map<Status, Map<Event, Status>>`），不依赖 StateMachine 实例状态。面试可以主动说这一点。
>
> 注释 `:12-13` 也承认了：**"DB status 是唯一事实源，不用内存 persister"**。

### 6.4 状态机的真正价值：并发安全

看 `confirmPay`（`OrderServiceImpl.java:117-164`）：

```java
if (OrderStatus.PAID.getCode().equals(order.getStatus())) {
    log.info("订单已支付，忽略重复确认: orderNo={}", orderNo);   // :126-129 幂等
    return;
}
try {
    order.setStatus(orderStateTransitionService.transit(order.getStatus(), OrderEvent.PAY).getCode());  // :131
} catch (BusinessException e) {
    log.warn("订单状态不允许支付确认，忽略: ...");                  // :132-135 非法迁移放行
    return;
}
```

**两个防御层次**：

1. **已 PAID → 直接返回**（幂等）。支付回调重复投递时不会报错。
2. **其他非法态 → catch 后 return**（忽略）。比如订单已 CANCELLED，此时来支付回调，`transit` 抛异常，被吞掉，订单仍是 CANCELLED。

> ⚠️ **但这里有一个真实的风险**：如果订单已取消（CANCELLED），用户却真的付了钱（比如在取消前扫码），回调进来被"忽略"，就变成"用户付了钱但订单是取消状态"——**需要退款**。本项目没有处理这个场景（没有"支付成功但订单已取消 → 自动退款"的逻辑）。这是一个很好的面试主动暴露点。

## 七、幂等：三层防线

### 7.1 三层结构（`ai-cs-common` 的注释就是标准答案）

`ai-cs-common/src/main/java/com/aics/common/idempotent/Idempotent.java:12-17`：

```
三层幂等中的第一层加速挡，DB 唯一键仍是终审；
业务异常立即释放 key；
重复调用抛 IdempotentRejectException(409)；
Redis 故障 fail-open 放行。
```

| 层 | 手段 | 位置 | 作用 |
|---|---|---|---|
| **① 分布式锁**（业务级） | Redisson `lock:order:create:{userId}` | `OrderCreateLockService.java:44-63` | 同一用户并发下单快速失败 |
| **② 幂等注解**（接口级） | `@Idempotent(key=..., ttlSeconds=300)` | `IdempotentAspect.java:55-73` | 同参数重复请求 409 |
| **③ DB 约束/状态机**（终审） | `uk_order_no`、`uk_idempotency_key`、`status` CAS | DDL + `transit` | 前两层失效也兜得住 |

### 7.2 分布式锁的三个关键设计

`ai-cs-order/src/main/java/com/aics/order/lock/OrderCreateLockService.java`：

```java
RLock lock = redissonClient.getLock(KEY_PREFIX + userId);      // :45  key = lock:order:create:{userId}
acquired = lock.tryLock(0, TimeUnit.SECONDS);                  // :49  waitTime=0，快速失败
if (!acquired) throw new BusinessException(TOO_MANY_REQUESTS, "您有订单正在创建中，请勿重复提交");
...
if (acquired && lock.isHeldByCurrentThread()) lock.unlock();   // :59-61
```

注释（`:17-24`）解释了为什么用 Redisson 而不是手写 SETNX：

| 特性 | 手写 SETNX | Redisson |
|---|---|---|
| 看门狗续期 | ❌ 需要自己起定时任务 | ✅ 不指定 leaseTime 时 30s 持有 + 每 10s 续期 |
| 可重入 | ❌ 同线程二次加锁会死锁 | ✅ 用 Hash 记录重入次数 |
| 安全解锁 | ❌ 可能解掉别人的锁（需 Lua 校验 value） | ✅ `isHeldByCurrentThread()` |

**`waitTime = 0` 的理由**（注释 `:24`）：**"同一用户的并发下单请求直接快速失败，而不是排队等锁"**。

> 这是很重要的产品判断：用户连点两次"提交订单"，第二个请求应该立刻告诉他"正在创建中"，而不是让他等 3 秒然后生成两个订单。

### 7.3 锁的粒度：为什么是 userId 不是 orderNo

- 下单时**还没有 orderNo**（订单号是下单过程中生成的），所以不能按订单号加锁。
- 按 `userId` 加锁，把"同一用户的并发下单"串行化。不同用户互不影响，粒度合适。
- 为什么不按 `productId`？因为下单涉及多个商品，按商品加锁要加 N 把锁（容易死锁），而且**库存扣减已经用 DB 条件更新保证了原子性**，不需要应用层锁。

### 7.4 锁为什么在事务外层

`OrderServiceImpl.java:51-60` 的注释说得非常清楚：

```java
/**
 * 创建订单（入口）：分布式锁防重 + 委托 OrderCreateTxService#doCreateOrder 执行全局事务。
 *
 * <p>锁在全局事务外层：同一用户的并发下单请求快速失败，拿到锁才进入
 * {@code @GlobalTransactional} 边界，避免锁内空占事务资源。</p>
 */
public OrderVO createOrder(...) {
    return orderCreateLockService.withCreateLock(userId,
            () -> orderCreateTxService.doCreateOrder(userId, cartItemIds, couponId, paymentMethod));
}
```

**如果锁放在事务内会怎样？**

```
加锁 → 开事务 → 扣库存 → ... → 提交事务 → 解锁
                     ↑
              这段时间锁一直被持有（可能几百 ms 到几秒）
```

锁持有时间 = 整个事务时长。而**放在事务外**：

```
加锁 → 开事务 → ... → 提交事务 → 解锁
```

看起来锁还是覆盖了事务……**真正的区别是**：如果 `doCreateOrder` 内部抛异常，事务回滚发生在 `action.get()` 返回之前还是之后？

答案是：`@GlobalTransactional` 的提交/回滚发生在 `doCreateOrder` 方法返回/抛出时，即 `action.get()` 内部完成。所以**两种写法锁的覆盖范围几乎一样**。

> 但外层写法有一个真实好处：**`createOrder` 本身不是事务方法**，它只是"锁 + 委托"。如果将来要在锁内加非事务动作（比如记录一条"下单请求日志"），不会误入事务。更重要的是**语义清晰**：读代码的人一眼能看出"锁管的是调用，事务管的是数据"。

### 7.5 `@Idempotent` 的实现细节

`ai-cs-common/src/main/java/com/aics/common/idempotent/IdempotentAspect.java`：

```java
String redisKey = properties.getKeyPrefix() + resolveKey(...);        // :55  key = prefix + SpEL 求值
Boolean ok = ops.setIfAbsent(redisKey, TOKEN, ttl);                   // :61  SET NX EX
if (Boolean.FALSE.equals(ok)) throw new IdempotentRejectException(...); // :67  409
// Redis 异常时 fail-open（:63）
// 业务异常时删除 key（:71-73），允许用户重试
```

**为什么是 fail-open？** 如果 Redis 挂了，幂等挡失效 → 请求正常通过 → 由 DB 唯一键/状态机兜底。反过来如果是 fail-close，Redis 一挂整个下单功能就不可用。**库存/幂等这类"非资金直接操作"的辅助能力，宁可放行也不要全站熔断。**

## 八、超时取消：三条通道 + 幂等

### 8.1 三条通道

| 通道 | 触发方式 | 准点性 | 证据 |
|---|---|---|---|
| ① 延迟消息 | MQ 到点投递 | **准**（秒级） | `OrderCreateTxService.java:144-146` |
| ② 定时扫描 | `@Scheduled(fixedDelay=300000)` | 滞后（最多 5 分钟） | `OrderTimeoutScheduler.java:29` |
| ③ 调度平台 | XXL-Job `orderTimeoutScanJob` | 可控（可手动触发） | `OrderTimeoutScanJob.java:27` |

**为什么三条都要？**

- ① 是主路径，最准时。但**如果 MQ 丢消息或者发送失败**，就没有 ①。
- ② 是兜底，只要应用活着就会扫。但**多实例部署时每个实例都会扫**（需要靠幂等去重）。
- ③ 是运维通道，可以在"怀疑有漏单"时手动触发，也便于观测和告警。

**②和③共用同一个方法**（`OrderTimeoutScanJob.java:30` 直接调 `scheduler.scanExpiredOrders()`），所以逻辑只有一份。

### 8.2 幂等的三道保险

```java
// ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:168-176
public void cancelExpiredOrder(String orderNo) {
    Order order = orderMapper.selectOne(...eq(Order::getOrderNo, orderNo));
    if (order == null || !OrderStatus.PENDING_PAY.getCode().equals(order.getStatus())) {
        return;   // ★ 已支付或已取消，忽略
    }
    doCancelOrder(order, OrderEvent.TIMEOUT);
}
```

1. **订单不存在 → return**。这条很关键：延迟消息可能在订单事务回滚后到达（消息已发出但订单没落库），此时查不到订单，直接返回（`OrderCreateTxService.java:91-92` 的注释解释了这个场景）。
2. **非 PENDING_PAY → return**。已支付、已取消都跳过。
3. **状态机**兜底：即使前面判断漏了，`transit(CANCELLED)` 从非 PENDING_PAY 状态会抛异常。

### 8.3 取消时要回滚什么

`doCancelOrder`（`OrderServiceImpl.java:222-247`）：

```java
order.setStatus(transit(order.getStatus(), event).getCode());   // :223 状态机迁移
order.setCancelTime(LocalDateTime.now());                       // :224
orderMapper.updateById(order);                                  // :225

// ① 归还库存
for (OrderItem item : items) productClient.restoreStock(item.getProductId(), item.getQuantity());  // :228-232
// ② 关闭渠道订单（让二维码失效）
closePayChannel(order);                                         // :235
// ③ 退回优惠券
coupon.setStatus(UNUSED); coupon.setUseTime(null); coupon.setOrderNo(null);  // :238-246
```

**这三件事必须都做**，少一件就有资损：

| 少做 | 后果 |
|---|---|
| 不还库存 | 库存永久泄露（越卖越少） |
| 不关渠道单 | 用户还能拿旧二维码付款 → 付了钱订单已取消 |
| 不退券 | 用户券白扣了 → 客诉 |

> ⚠️ `closePayChannel` 是"尽力而为"（`:249-266` 注释 + try-catch 只 warn）。如果关单失败，靠支付服务侧的超时兜底（支付服务查单时会发现订单已取消）。这个设计是对的——**关单失败不能阻断取消**，否则用户就永远取消不了订单。

## 十、面试：本篇衍生题清单

### Q1：下单流程讲一下

> 六步：① 校验购物车非空；② 逐项扣库存（Feign → 商品服务，Seata AT 分支事务）；③ 算价（商品总额 → 满减 → 券）；④ 建订单（状态 PENDING_PAY，过期时间 now+30min）；⑤ 建订单项（快照商品名和单价）；⑥ 核销券 + 发 30 分钟延迟消息。
> **整段在一个 `@GlobalTransactional` 里，外面包了一把以 userId 为 key 的 Redisson 锁做防重。**

### Q2：为什么用 Seata 不用 TCC / 本地消息表？

> 三个理由：① 库存扣减是"简单的一步操作"，用 AT 的 undo_log 反向补偿就够了，TCC 要写 try/confirm/cancel 三个方法，成本不划算；② 我们只有一个跨服务写操作（扣库存），参与方少，AT 的全局锁冲突可控；③ AT 对业务代码零侵入，只要加注解 + 建 undo_log 表。
> **如果参与方多、或者有非事务资源（比如调外部支付），TCC 或本地消息表更合适。我们支付链路用的就是事务消息，不是 Seata。**

### Q3：分布式锁为什么放事务外层？

> 因为锁的职责是"防重复提交"，不是"保证数据一致性"，后者由事务负责。分开之后语义清晰：**锁管调用，事务管数据**。另外如果锁在事务方法内部，锁的获取会占用事务连接，连接池压力更大。

### Q4：用户连点两次提交订单会发生什么？

> 第二把锁 `tryLock(0)` 直接失败，抛 `TOO_MANY_REQUESTS`，前端提示"您有订单正在创建中"。即使锁失效（比如 Redis 抖动），`@Idempotent` 会挡；再失效，订单号唯一键 `uk_order_no` 兜底。

### Q5：订单超时怎么处理的？

> 三条通道：下单时发 RocketMQ 延迟消息（delayLevel 16 ≈ 30 分钟）；`@Scheduled` 每 5 分钟扫一次过期订单；XXL-Job 提供手动触发的调度任务。三条都走同一个 `cancelExpiredOrder`，靠"非 PENDING_PAY 直接返回"保证幂等。
> 取消时会做三件事：还库存、关渠道单（让二维码失效）、退优惠券。

### Q6：订单状态怎么保证不乱？

> Spring StateMachine 定义 5 条合法迁移，所有状态变更必须走 `OrderStateTransitionService.transit()`。DB 的 `status` 字段是唯一事实源，状态机实例每次迁移前都 reset 到 DB 状态。**非法迁移直接抛异常，业务方 catch 后忽略**（比如已取消的订单收到支付回调）。

### Q7：支付回调重复了怎么办？

> 三层：① `confirmPay` 里"已 PAID 直接 return"；② MQ 消费侧幂等（同一 orderNo 重复消费只生效一次）；③ 状态机保证 PAID → PAID 不是合法迁移，会抛异常被吞掉。

### Q8：为什么订单项要冗余商品名和价格？

> 订单是法律凭证，必须冻结成交时的事实。商品改名、涨价、下架、删除都不应该影响历史订单的展示。同理购物车也冗余了 `product_name` / `product_price`，但语义不同——**购物车是展示快照，订单是法律快照**。
