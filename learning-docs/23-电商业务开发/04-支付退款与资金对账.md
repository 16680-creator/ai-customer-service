# 04 - 支付退款与资金对账

> 目标：把"用户扫码付钱"到"钱进商户账户"的每一步说清楚，包括**回调丢了怎么办**、**重复回调怎么防**、**退款怎么不重复退**、**对账怎么发现单边账**。
> 支付是电商里**唯一直接碰钱**的链路，面试官会在这里追问到底。

---

## 零、先给结论

支付系统要解决的不是"调通一个接口"，而是四个永恒问题：

| # | 问题 | 本质 | 本项目的答案 |
|---|---|---|---|
| 1 | **渠道怎么抽象** | 支付宝/微信/银联的签名、字段、报文完全不同 | 策略模式：`PayChannel` 接口 + 4 个实现 + 工厂分派 |
| 2 | **回调丢了怎么办** | 渠道通知是"至少一次"，也可能一次都不来 | 主动查单兜底（`syncByQuery`）+ 定时补偿（`/pay/compensate`） |
| 3 | **两边数据不一致怎么办** | 支付成功但订单没变已支付（单边账） | 事务消息（流水落库 ⇒ 消息必达订单）+ 对账报告 |
| 4 | **重复通知怎么防** | 渠道会重复推、网络会重试 | 三层幂等：流水状态机 + 订单状态机 + MQ 消费幂等 |

> 一句话面试版：**「支付的核心不是调用，而是"最终一致 + 可对账"。所以每一笔支付都必须有一张自己的流水表，任何状态变化都以流水为锚点。」**

**关键设计：支付服务不改订单状态。** `PayController.java:28` 的注释写得很明确：

> 「订单信息通过 `OrderPayClient` 从订单服务获取；支付状态变更由订单服务落库。」

**为什么？** 订单的状态机在订单服务（`OrderStateMachineConfig`），如果支付服务也去改 `orders` 表，就有两个写入口，状态机形同虚设。**单一写入口是状态机的前提。**

## 二、渠道抽象：策略模式 + 工厂

### 2.1 接口设计

`ai-cs-pay/src/main/java/com/aics/pay/channel/PayChannel.java:28-69`：

```java
public interface PayChannel {
    String STATUS_PENDING = "PENDING";   // :31
    String STATUS_SUCCESS = "SUCCESS";   // :34
    String STATUS_CLOSED  = "CLOSED";    // :37

    String getMethod();                                   // :42  渠道标识 MOCK/ALIPAY/WECHAT/UNIONPAY
    PayResult createPayment(PayContext context);          // :47  渠道下单
    String queryPayment(String orderNo);                  // :52  主动查单
    NotifyResult parseNotify(NotifyContext context);       // :58  解析回调（验签+解密）
    void closeOrder(String orderNo);                       // :63  关单（让二维码失效）
    RefundResult refund(String orderNo, BigDecimal amount); // :68  退款
}
```

**六个方法覆盖了支付渠道的全部差异**。接口注释（`:22-25`）点出核心：**"把各渠道差异（签名/字段/报文）封装在实现内部"**。

### 2.2 工厂：为什么用 List 注入

`channel/PayChannelFactory.java`（52 行）：

```java
// :34-37 构造注入所有实现，按 getMethod() 建 Map
public PayChannelFactory(List<PayChannel> channels) {
    this.channelMap = channels.stream()
            .collect(Collectors.toMap(PayChannel::getMethod, Function.identity()));
}

// :40-47 未命中抛 ORDER_PAYMENT_METHOD_INVALID
public PayChannel getChannel(String method) {
    PayChannel channel = channelMap.get(method);
    if (channel == null) throw new BusinessException(ResultCode.ORDER_PAYMENT_METHOD_INVALID, ...);
    return channel;
}
```

**这个写法的价值**：新增一个支付渠道（比如"云闪付小程序"）只需要**新建一个 `@Component` 实现类**，工厂、Controller、回调、退款全部不用改。

> 面试金句：**「新增渠道 = 新增一个实现类，零改动既有代码。这就是开闭原则在支付域的落地。」**

### 2.3 四个渠道实现的差异对照

| 渠道 | 文件（行数） | 下单方式 | 回调验签 | 金额单位 | 退款接口 |
|---|---|---|---|---|---|
| **Mock** | `MockPayChannel.java`（104） | 内存记账，直接返回 codeUrl | 无（模拟） | 元 | `:84` 内存改状态 |
| **支付宝** | `AlipayChannel.java`（223） | `alipay.trade.precreate`（当面付扫码） | `AlipaySignature.rsaCheckV1`（RSA2，`:142`） | 元（字符串） | `alipay.trade.refund`（`:179-195`） |
| **微信** | `WechatNativeChannel.java`（237） | Native 下单，返回 `code_url` | 平台证书验签（`:153` 取 `Wechatpay-Signature`） | **分**（`:185-187` 元转分） | `/v3/refund/domestic/refunds`（`:176-195`） |
| **银联** | `UnionpayChannel.java`（266）+ `UnionpaySignature.java`（134） | 云闪付二维码 | 银联签名（134 行的独立验签类） | 分 | `:176` |

**金额单位是最容易踩的坑**：微信/银联用「分」，支付宝用「元」。`WechatNativeChannel.java:185-187`：

```java
int fen = yuanToFen(refundAmount);
amount.setRefund((long) fen);
amount.setTotal((long) fen); // 本项目为全额退款，total=refund；部分退款时 total 应为原订单实付金额
```

> ⚠️ 注释自己承认了限制：**只支持全额退款**。部分退款时 `total` 必须是原订单金额，否则微信会报 `PARAM_ERROR`。这是很好的面试主动暴露点。

## 三、支付流水：为什么必须有这张表

### 3.1 表结构

`ai-cs-pay/src/main/java/com/aics/pay/config/PaySchemaInitializer.java:22-40`（启动时建表）：

```sql
CREATE TABLE IF NOT EXISTS `pay_transaction` (
    `id`             BIGINT NOT NULL AUTO_INCREMENT,
    `order_no`       VARCHAR(32)  NOT NULL,
    `user_id`        BIGINT       NOT NULL,
    `payment_method` VARCHAR(20)  NOT NULL,
    `trade_no`       VARCHAR(64)  DEFAULT NULL,   -- 渠道交易号
    `pay_amount`     DECIMAL(10,2) NOT NULL,
    `status`         VARCHAR(20)  NOT NULL DEFAULT 'PENDING',
    `notify_count`   INT          NOT NULL DEFAULT 0,  -- 收到几次通知
    `pay_time`       DATETIME     DEFAULT NULL,
    `refund_time`    DATETIME     DEFAULT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_order_no` (`order_no`),   -- ★ 一个订单一条支付流水
    KEY `idx_user_id` (`user_id`)
);
```

> ⚠️ 注意：**`pay_transaction` 不在 `deploy/mysql/` 的任何 init.sql 里**（全目录 grep = 0 命中），是应用启动时用 `JdbcTemplate` 建的。注释（`:11`）也说了"生产可改用 Flyway/Liquibase"。这是个**架构异味**：DDL 分散在 Java 代码里，版本不可追溯。面试可以主动说。

### 3.2 五个作用

| 作用 | 怎么用 |
|---|---|
| **幂等锚点** | `uk_order_no` 唯一键，同一订单只能有一条流水；`markSuccess` 里判 `已 SUCCESS 则 return false` |
| **对账依据** | `/pay/compensate` 扫 `status=SUCCESS` 的流水，对比订单状态，找单边账 |
| **审计** | `notify_count` 记录收到几次通知，能看出渠道重试强度 |
| **状态机** | PENDING → SUCCESS / CLOSED / REFUNDING → REFUNDED |
| **渠道追溯** | `trade_no` 关联支付宝/微信的流水号，退款/客服查单要用 |

### 3.3 状态机（五态）

```
        createOrUpdatePending
                 │
                 ▼
             ┌─────────┐  markSuccess   ┌─────────┐  markRefunding  ┌───────────┐  markRefunded  ┌──────────┐
             │ PENDING │ ─────────────▶ │ SUCCESS │ ──────────────▶ │ REFUNDING │ ─────────────▶ │ REFUNDED │
             └─────────┘                └─────────┘                 └───────────┘                └──────────┘
                 │
                 │ markClosed（订单超时/取消）
                 ▼
             ┌────────┐
             │ CLOSED │
             └────────┘
```

实现（`service/impl/PayTransactionServiceImpl.java`）：

| 方法 | 行号 | 幂等规则 |
|---|---|---|
| `createOrUpdatePending` | `:31-49` | 不存在则 insert；已 PENDING 则更新金额/渠道；**已 SUCCESS/CLOSED 则什么都不做** |
| `markSuccess` | `:53-70` | `tx == null \|\| 已 SUCCESS` → return false（幂等） |
| `markClosed` | `:74-82` | 仅 PENDING 可关 |
| `markRefunding` | `:86-94` | 仅 SUCCESS 或 PENDING 可进退款中 |
| `markRefunded` | `:98-107` | 无条件置 REFUNDED（幂等） |
| `getByOrderNo` | `:111-114` | 供订单服务/对账查 |

> ⚠️ **`markSuccess` 的并发缺陷**：`getByOrderNo` → 判断 → `updateById`，没有 CAS。两个并发回调都读到 PENDING，都会 update，`notify_count` 加两次。正确做法：
> ```sql
> UPDATE pay_transaction SET status='SUCCESS', trade_no=?, pay_time=NOW(), notify_count=notify_count+1
> WHERE order_no=? AND status='PENDING';
> -- 判断影响行数
> ```

## 四、回调处理：验签 → 落流水 → 通知订单

### 4.1 入口：一个 Controller 收所有渠道

`controller/PayCallbackController.java:35-45`：

```java
@PostMapping("/callback/{paymentMethod}")
public Map<String, String> payCallback(@PathVariable("paymentMethod") String paymentMethod,
                                       HttpServletRequest request) {
    try {
        payNotifyService.processNotify(paymentMethod, buildNotifyContext(request));
        return Map.of("code", "SUCCESS", "message", "OK");
    } catch (Exception e) {
        log.warn("支付回调处理失败: method={}, err={}", paymentMethod, e.getMessage());
        return Map.of("code", "FAIL", "message", ...);
    }
}
```

**两个设计要点**：

1. **URL 里带渠道名**（`/callback/alipay`、`/callback/wechat`），一个 Controller 处理全部渠道。渠道差异通过 `paymentMethod` 分派到对应的 `PayChannel.parseNotify`。
2. **返回体格式因渠道而异**。支付宝要求返回纯文本 `success`；微信要求 `{"code":"SUCCESS"}` 或 HTTP 200/204。本项目统一返回 `{"code":"SUCCESS"}` —— **对支付宝可能不兼容**，这是一个真实的对接风险，面试可以主动提。

`buildNotifyContext`（`:47-65`）收集三类信息：

```java
params   ← request.getParameterMap()                      // 表单参数（支付宝风格）
headers  ← 只取 WECHAT_HEADERS 里声明的 5 个（:27-30）      // 微信签名头
body     ← Content-Type 含 json 时读 InputStream           // 微信 v3 是 JSON body
```

`WECHAT_HEADERS`（`:27-30`）：
```java
"Wechatpay-Timestamp", "Wechatpay-Nonce", "Wechatpay-Signature",
"Wechatpay-Serial", "Wechatpay-Signature-Type"
```

> 注意：**只读 JSON body 时用 `request.getInputStream()`**（`:62`）。如果先读过 `getParameterMap()`，某些容器会把 body 消费掉，导致后续读不到。这里顺序是先 params 再 body，实际上有风险（Servlet 规范里 `getParameter` 会触发 body 解析）。生产环境更稳的做法是加 `ContentCachingRequestWrapper`。

### 4.2 核心：`PayNotifyService.processNotify`

`service/PayNotifyService.java:32-44`：

```java
public void processNotify(String paymentMethod, NotifyContext context) {
    PayChannel channel = payChannelFactory.getChannel(paymentMethod);   // :33
    NotifyResult result = channel.parseNotify(context);                 // :34  验签+解密

    if (result == null || !result.isSuccess()) {                        // :36-40
        log.warn("支付通知为非成功状态，不更新订单: orderNo={}, ...");
        return;   // ★ 非成功状态直接忽略（用户取消/支付失败也会回调）
    }

    notifyOrderSuccess(result.getOrderNo(), paymentMethod, result.getAmount(), result.getTransactionId()); // :42
}
```

**`!result.isSuccess()` 直接 return 很重要**：支付渠道在"用户取消支付"、"支付失败"时也会回调。如果把这些当成成功处理，就会把没付钱的订单标记为已支付。

### 4.3 验签：安全红线

`channel/PayChannel.java:55-58` 的注释写死了契约：

> 「解析渠道异步通知：验签（+微信解密）后返回标准化支付结果。**验签失败必须抛出异常，防止伪造通知。**」

各渠道实现：

| 渠道 | 验签方式 | 证据 |
|---|---|---|
| 支付宝 | `AlipaySignature.rsaCheckV1(params, alipayPublicKey, "UTF-8", "RSA2")` | `AlipayChannel.java:142` |
| 微信 | 平台证书验签（取 `Wechatpay-Signature` 头） | `WechatNativeChannel.java:147-153` |
| 银联 | 独立签名类 `UnionpaySignature`（134 行） | `UnionpayChannel.java` |

> **面试必答**：为什么必须验签？因为回调 URL 是公开的。任何人都能 `curl -X POST /api/pay/callback/mock` 发一个"支付成功"的假报文。不验签 = 任何人都能白嫖下单。

### 4.4 通知订单：两套实现（新旧对比）

`PayNotifyService.java:57-73`：

```java
/**
 * tx-message 模式：本地事务（流水 markSuccess）移入
 * PaySuccessTransactionListener#executeLocalTransaction，由事务消息机制保证
 * 「流水落库成功 ⇒ 消息必达 order」；feign 模式为旧同步回调（回查期 Feign 失败即丢事件）。
 */
private void notifyOrderSuccess(String orderNo, String paymentMethod, BigDecimal amount, String tradeNo) {
    if (txNotifyEnabled) {                                    // :65 默认 true
        paySuccessMessageProducer.sendSuccess(PaySuccessMessage.builder()
                .orderNo(orderNo).paymentMethod(paymentMethod).amount(amount).tradeNo(tradeNo)
                .build());
        return;
    }
    // 旧模式（保留对比）
    payTransactionService.markSuccess(orderNo, tradeNo, amount);   // :71
    orderPayClient.confirmPay(orderNo, paymentMethod, amount, tradeNo);  // :72
}
```

开关在 `:28-30`：

```java
/** 支付成功通知模式：tx-message=RocketMQ 事务消息（默认），feign=旧同步回调（保留对比） */
@Value("${aics.pay.tx-notify.enabled:true}")
private boolean txNotifyEnabled;
```

**两套模式的致命差异**：

| 模式 | 步骤 | 失败场景 | 结果 |
|---|---|---|---|
| **feign（旧）** | ① 本地 markSuccess → ② Feign 调订单 confirmPay | ①成功、②失败（网络抖） | **流水 SUCCESS 但订单永远 PENDING_PAY = 单边账** |
| **tx-message（新）** | ① 发半消息 → ② 本地 markSuccess → ③ COMMIT → ④ 订单消费 | ②失败 | 半消息 ROLLBACK，什么都没发生（安全） |
| | | ③失败（COMMIT 前宕机） | Broker 回查 `checkLocalTransaction`，按流水状态决定 |

> 这就是为什么必须用**事务消息**而不是普通 Feign 调用：**"本地事务"和"发消息"必须原子**。这是分布式事务的经典场景（本地消息表 / 事务消息 / 最大努力通知三选一）。

### 5.1 发送端

### 5.2 监听器（本地事务执行器 + 回查器）

`mq/PaySuccessTransactionListener.java:34-68`：

```java
@RocketMQTransactionListener     // :34  rocketmq-spring 2.3.0：txProducerGroup 属性已移除
public class PaySuccessTransactionListener implements RocketMQLocalTransactionListener {

    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {   // :40-53
        PaySuccessMessage payload = ...;
        try {
            payTransactionService.markSuccess(payload.getOrderNo(), payload.getTradeNo(), payload.getAmount());
            return RocketMQLocalTransactionState.COMMIT;      // 流水落库成功 → 消息可见
        } catch (Exception e) {
            return RocketMQLocalTransactionState.ROLLBACK;    // 失败 → 半消息删除
        }
    }

    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {                 // :56-68
        PayTransaction tx = payTransactionService.getByOrderNo(payload.getOrderNo());
        if (tx == null) return ROLLBACK;                          // 流水不存在 → 回滚
        return switch (tx.getStatus()) {
            case "SUCCESS" -> COMMIT;                             // 流水已成功 → 提交
            case "PENDING" -> UNKNOWN;                            // 未决 → 稍后再查
            default -> ROLLBACK;                                  // CLOSED/REFUNDING → 回滚
        };
    }
}
```

### 5.3 完整时序（面试可手画）

```
支付服务                          RocketMQ                     订单服务
    │                                 │                            │
    │ ① sendMessageInTransaction      │                            │
    │ ───────────半消息──────────────▶ │（存入 RMQ_SYS_TRANS_HALF_TOPIC）
    │                                 │                            │
    │ ② executeLocalTransaction 回调   │                            │
    │ ◀───────────────────────────────│                            │
    │    markSuccess（流水 PENDING→SUCCESS）                        │
    │                                 │                            │
    │ ③ COMMIT ──────────────────────▶ │ 消息转正                     │
    │                                 │ ──────pay-success-topic───▶ │
    │                                 │                            │ ④ confirmPay
    │                                 │                            │    状态机 → PAID
    │                                 │                            │    publishEvent
    │                                 │                            │
    │ （如果 ③ 之前宕机）              │                            │
    │                                 │ ⑤ 定时回查 checkLocalTransaction
    │ ◀───────────────────────────────│                            │
    │    查流水：SUCCESS→COMMIT / PENDING→UNKNOWN / 其他→ROLLBACK    │
```

**面试金句**：**「事务消息解决的是"本地事务和消息发送的原子性"。它的本质是"两阶段 + 回查兜底"：先发半消息（对消费者不可见），再执行本地事务，成功就 COMMIT、失败就 ROLLBACK、超时就回查。回查必须幂等，且只认落库状态。」**

### 5.4 消费端

`ai-cs-order/src/main/java/com/aics/order/listener/PaySuccessListener.java:27-41`：

```java
@RocketMQMessageListener(

        consumerGroup = "pay-success-consumer-group",

public class PaySuccessListener implements RocketMQListener<PaySuccessMessage> {
    @Override

```

注释（`:16-21`）说明三件事：重试耗尽进 `%DLQ%pay-success-consumer-group`、下游幂等、至少一次投递 + 幂等消费。

**`maxReconsumeTimes = 8`**：超过 8 次进死信队列。为什么不无限重试？因为如果是"订单不存在"这种永久性错误，重试 1000 次也没用，只会堵住队列。进 DLQ 后靠人工/定时任务处理。

## 六、订单侧：`confirmPay` 的四道防线

`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:117-164`：

```java
@Transactional(rollbackFor = Exception.class)
public void confirmPay(String orderNo, String paymentMethod, BigDecimal amount, String tradeNo) {
    Order order = orderMapper.selectOne(...eq(Order::getOrderNo, orderNo));   // :118-119
    if (order == null) { log.warn(...); return; }                             // :120-123   ① 订单不存在

    if (OrderStatus.PAID.getCode().equals(order.getStatus())) {                // :126-129   ② 已支付幂等
        log.info("订单已支付，忽略重复确认: orderNo={}", orderNo);

    }
    try {
        order.setStatus(orderStateTransitionService.transit(order.getStatus(), OrderEvent.PAY).getCode()); // :131  ③ 状态机
    } catch (BusinessException e) {
        log.warn("订单状态不允许支付确认，忽略: ...");  return;                  // :132-135  ③'

    orderMapper.updateById(order);                                            // :147

    eventPublisher.publishEvent(new OrderPaidEvent(orderNo, order.getUserId()));  // :151

    // 清除购物车中已下单商品
    ... cartItemMapper.delete(...)                                            // :154-161
}
```

### 四道防线的作用

| # | 防线 | 防的是什么 |
|---|---|---|
| ① | 订单不存在 → return | 消息在订单事务回滚后到达（订单没落库） |
| ② | 已 PAID → return | 渠道重复回调 / MQ 重复投递 |
| ③ | 状态机迁移失败 → catch 后 return | 订单已取消/已退款，此时来支付回调 |
| ④ | **金额不一致 → 抛异常** | **篡改金额（比如 199 的订单只付 1 分钱）** |

> **第 ④ 条是安全红线**，`compareTo != 0` 用的是 `BigDecimal.compareTo`（忽略 scale）。如果用 `equals`，`199.0` 和 `199.00` 会不相等，导致正常回调被拒。

### `@TransactionalEventListener(AFTER_COMMIT)` 的意义

`event/OrderPaidEventListener.java:16-40`：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // :30
public void onOrderPaid(OrderPaidEvent event) {
    ...
    rocketMQTemplate.convertAndSend("notify-topic", notify);          // :33-36
    // :38-40 投递失败只 warn
}
```

注释（`:16-21`）说得非常清楚：

> 「事务回滚 listener 不执行」→ 所以用户**不会收到假的"支付成功"通知**。

**这是 Spring 事件机制最容易被考的点**：

| 注解 | 执行时机 | 事务回滚时 |
|---|---|---|
| `@EventListener` | 立即（仍在事务内） | **仍会执行** ← 会发出假通知 |
| `@TransactionalEventListener(phase = BEFORE_COMMIT)` | 提交前 | 不执行 |
| `@TransactionalEventListener(phase = AFTER_COMMIT)` | **提交后** | **不执行** ← 正确 |
| `@TransactionalEventListener(phase = AFTER_ROLLBACK)` | 回滚后 | 只在这里执行（做补偿） |

> 面试标准答法：**「我们在事务内只 publishEvent 发布领域事实，真正的 MQ 投递放在 `@TransactionalEventListener(AFTER_COMMIT)`。这样如果订单事务因为清购物车失败而回滚，用户不会收到"支付成功"的通知。」**

## 七、退款：本项目做到哪一步

### 7.1 已实现：两段迁移 + 回补库存

`OrderServiceImpl.refundConfirm`（`:178-201`）：

```java
@Transactional(rollbackFor = Exception.class)
public void refundConfirm(String orderNo) {
    Order order = orderMapper.selectOne(...);
    if (order == null) throw new BusinessException(ORDER_NOT_FOUND, "仅已支付订单可退款");

    // 退款是两段迁移：先校验 PAID -> REFUNDING，库存回补成功后再落 REFUNDED
    order.setStatus(transit(order.getStatus(), OrderEvent.REFUND_REQUEST).getCode());  // :188
    orderMapper.updateById(order);                                                     // :189

    for (OrderItem item : items) productClient.restoreStock(item.getProductId(), item.getQuantity());  // :192-196

    order.setStatus(transit(order.getStatus(), OrderEvent.REFUND_SUCCESS).getCode());  // :197
    orderMapper.updateById(order);                                                     // :198
}
```

**为什么是"两段迁移"（PAID → REFUNDING → REFUNDED）而不是直接 PAID → REFUNDED？**

因为中间有一步"回补库存"，这一步可能失败（商品服务挂了）。如果直接跳到 REFUNDED，回补失败就变成了"钱退了但库存没回来"。两段式的好处：**如果卡在 REFUNDING，说明退款在路上，可以被定时任务补偿重试。**

> 这是一个非常好的设计模式：**长事务拆成"中间态 + 终态"**，中间态就是"待补偿"的标记。

### 7.2 渠道退款：有实现但没接上

四个渠道都有 `refund` 实现：

| 渠道 | 实现 | 说明 |
|---|---|---|
| 支付宝 | `AlipayChannel.java:179-195` | `AlipayTradeRefundRequest` + `AlipayTradeRefundModel`，`:185` `setRefundAmount(refundAmount.toPlainString())` |
| 微信 | `WechatNativeChannel.java:176-195` | `RefundService.create`，`:182` `outRefundNo = "REFUND-" + orderNo + "-" + System.currentTimeMillis()` |
| 银联 | `UnionpayChannel.java:176` | 银联退款报文 |
| Mock | `MockPayChannel.java:84` | 内存改状态 |

**但是**：全仓库只有一个 REST 入口能触发退款 —— `controller/MockPayController.java:68-79` `POST /pay/refund`（只调 Mock 渠道）。

> ⚠️ **真实缺口**：`PayController` 没有 `/pay/refund` 端点（`pay` 模块的 `PayController.java` 只有 create/status/close/compensate 四个，`:56/91/116/126`）。真实渠道的 `refund()` 方法**没有任何调用方**。也就是说：**支付宝/微信退款实现了但接不上，只能全额退款（Mock）跑通。**
>
> 面试时可以说：「退款我们做了渠道抽象和全额退款的主流程，但部分退款、退款申请审批、退款回调（`refund-notify`）都还没做。如果要补，第一步是加 `POST /pay/refund`，第二步是加退款状态回查，第三步是接渠道的退款结果通知。」

### 7.3 `outRefundNo` 的幂等设计

`WechatNativeChannel.java:182`：

```java
request.setOutRefundNo("REFUND-" + orderNo + "-" + System.currentTimeMillis());
```

> ⚠️ **这里有问题**：`System.currentTimeMillis()` 让每次调用的 `outRefundNo` 都不同。而微信的幂等键就是 `outRefundNo`——**同样的退款重试会变成"两笔不同的退款申请"**（虽然微信会用 `out_trade_no + 金额` 二次校验，但仍可能报错或重复退）。
>
> **正确做法**：`outRefundNo = "REFUND-" + orderNo`（固定），或者用退款单号 + 重试次数。**幂等键必须可重现**，这是幂等设计的第一原则。

### 8.2 `syncByQuery` 的实现

`PayNotifyService.java:46-55`：

```java
public boolean syncByQuery(String orderNo, String paymentMethod) {
    PayChannel channel = payChannelFactory.getChannel(paymentMethod);
    String channelStatus = channel.queryPayment(orderNo);          // :48 主动查渠道
    if (PayChannel.STATUS_SUCCESS.equals(channelStatus)) {         // :49
        log.info("查单兜底命中已支付: ...");

    }
    return false;

```

> ⚠️ 注意 `notifyOrderSuccess(orderNo, paymentMethod, null, null)` —— **金额和 tradeNo 传 null**。这意味着通过查单兜底触发的确认**跳过了金额校验**（`confirmPay` 里 `amount != null` 才校验，`OrderServiceImpl.java:138`）。这是一个安全弱点：如果渠道返回的金额与订单不符（比如用户改了金额），查单路径不会发现。
>
> 正确做法：`queryPayment` 应该返回结构化结果（含金额），而不是只返回一个状态字符串。**接口设计缺陷**，面试可以主动说。

### 8.3 "为什么需要查单兜底"的三种真实场景

| 场景 | 说明 |
|---|---|
| 渠道回调丢失 | 网络抖动、我们服务重启中、网关 502。渠道重试几次后放弃 |
| 我们处理回调失败 | 验签通过但下游（订单服务）挂了，返回 FAIL，渠道过一会再推，但可能超时不再推 |

> **面试金句**：**「支付回调是"最优路径"，不是"唯一路径"。生产系统必须假设回调可能永远不到，所以一定要有主动查单 + 定时对账。」**

### 9.2 真实生产对账长什么样

| 维度 | 本项目 | 生产级 |
|---|---|---|
| **对账源** | 只有自己的流水表 | **渠道账单文件**（支付宝/微信每日 CSV/对账单 API） |
| **对账方向** | 单向（流水 vs 订单） | **三向**：渠道账单 ↔ 支付流水 ↔ 订单 |
| **对账时机** | 手动调 `/pay/compensate` | **T+1 定时**（凌晨拉昨日账单）+ 准实时（小时级） |
| **差异分类** | 只有一种（流水成功/订单未付） | **长款**（渠道有我们没有）、**短款**（我们有渠道没有）、**金额不符**、**状态不符** |
| **差异处理** | 只报告 | **自动补单 / 自动退款 / 人工工单** |
| **幂等** | - | 对账任务幂等，可重复跑 |
| **可观测** | 返回 JSON | 差异率指标 + 告警（差异率 > 0.01% 就报） |

### 9.3 三向对账的四种差异（面试必答）

```
        渠道账单（支付宝/微信）
              │ ①
              ▼
         支付流水（pay_transaction）
              │ ②
              ▼
          订单（orders）
```

| # | 差异 | 含义 | 处理 |
|---|---|---|---|
| ① | **渠道有，我们无**（长款） | 用户付了钱，但我们没记录（回调全丢 + 查单也没查） | **补流水**（拿渠道的 trade_no 补建），再补订单 |
| ② | **我们有，渠道无**（短款） | 我们记了成功，但渠道说没收到钱 | **极严重**，通常是伪造回调（验签漏了）或测试数据 |
| ③ | **金额不符** | 渠道 199.00，我们 199.01（精度/汇率/优惠差异） | 人工核查，可能是并发改价 |
| ④ | **状态不符** | 渠道 SUCCESS，我们 PENDING / CLOSED | 补单（类似本项目 `paySuccessButOrderNotPaid`） |

> **面试金句**：**「对账的本质是"发现不一致"，不是"保证一致"。分布式系统里不一致一定会发生，关键是能不能在资金损失扩大前发现它。所以我们要求：任何涉及钱的链路，必须能回答"这笔钱现在在哪"。」**

### 9.4 支付的"最终一致"边界

| 步骤 | 一致性要求 | 手段 |
|---|---|---|
| 用户付钱 → 渠道记账 | **强一致**（渠道内部保证） | 渠道自己的事务 |
| 渠道记账 → 我们落流水 | **最终一致**（秒级） | 回调 + 查单兜底 |
| 流水成功 → 订单 PAID | **最终一致**（秒级） | 事务消息 + MQ 重试 + 对账 |
| 订单 PAID → 通知用户 | **最终一致**（可有延迟） | AFTER_COMMIT + MQ |
| 订单 PAID → 发货 | **最终一致**（业务上可接受分钟级） | 履约域（本项目 ❌ 未做） |

> 关键：**除了"渠道内部记账"，我们这边没有任何一步是强一致的。** 所以面试千万别说"我们保证支付强一致"，那是错的。正确的说法是"**支付链路最终一致，靠回调 + 查单 + 对账三层保证**"。

## 十一、面试：本篇衍生题清单

### Q1：支付流程讲一下

> ① 前端调 `/pay/create`，支付服务 Feign 查订单，校验归属 + 状态必须 PENDING_PAY；② 工厂按 `paymentMethod` 选渠道，渠道下单拿到二维码；③ 落支付流水（PENDING）；④ 用户扫码付钱；⑤ 渠道回调 `/pay/callback/{method}`，验签后把流水标记 SUCCESS，然后发**事务消息**到 `pay-success-topic`；⑥ 订单服务消费，`confirmPay` 里状态机 PENDING_PAY → PAID，`@TransactionalEventListener(AFTER_COMMIT)` 发通知。
> 如果回调没来，前端轮询 `/pay/status` 会触发主动查单兜底；再兜不住，`/pay/compensate` 定时扫 PENDING 流水补。

### Q2：为什么要用事务消息，不用普通 MQ 或 Feign？

> 因为"流水落库"和"通知订单"必须原子。用 Feign：本地 markSuccess 成功了、Feign 失败 → 流水 SUCCESS 但订单永远 PENDING，形成单边账。用普通 MQ：消息发了但本地事务回滚 → 订单收到"支付成功"但流水没落库，无法对账。
> **事务消息 = 半消息 + 本地事务 + 回查**，保证"本地成功 ⇒ 消息必达；本地失败 ⇒ 消息不存在"。

### Q3：重复回调怎么处理？

> 三层：① 流水 `markSuccess` 里"已 SUCCESS 返回 false"；② 订单 `confirmPay` 里"已 PAID 直接 return"；③ 订单状态机保证 PAID → PAID 不是合法迁移。另外 `pay_transaction` 有 `uk_order_no` 唯一键，不可能出现两条流水。

### Q4：回调丢了怎么办？

> 两条兜底：① 前端轮询 `/pay/status`，如果订单还是 PENDING 就主动调渠道查单（`syncByQuery`），查到已支付就补通知；② `/pay/compensate` 扫全量 PENDING 流水做查单兜底。
> **"回调是最优路径不是唯一路径"，这是支付系统的基本假设。**

### Q5：怎么防止伪造回调？

> 每个渠道的 `parseNotify` 都必须验签：支付宝用 `AlipaySignature.rsaCheckV1`（RSA2），微信用平台证书验 `Wechatpay-Signature`。验签失败直接抛异常，Controller 返回 FAIL。
> 另外还有金额校验（`confirmPay` 里 `compareTo != 0` 抛异常）—— 即使验签被绕过，金额也篡改不了。

### Q6：新增一个支付渠道要改什么？

> 只需要新建一个 `PayChannel` 实现类加 `@Component`。`PayChannelFactory` 是构造注入 `List<PayChannel>` 然后按 `getMethod()` 建 Map，所以新实现会自动被注册。Controller、回调、退款、对账**全部不用改**。这就是策略模式 + 工厂的价值。

### Q7：退款怎么做的？

> 两段迁移：PAID → REFUNDING（先标记"退款中"）→ 回补库存 → REFUNDED。中间态的意义是"如果卡在这里，说明退款在路上，可以被补偿任务重试"。
> 渠道侧四个渠道都实现了 `refund()`，但目前只有一个 Mock 的 REST 入口，真实渠道退款还没接上——这是明确的待补项。

### Q8：对账怎么做？

> 我们现在是"雏形"：扫 SUCCESS 流水，逐笔 Feign 查订单状态，如果订单不是 PAID 就记进 `paySuccessButOrderNotPaid` 报告。
> 生产级要做**三向对账**：渠道账单文件 ↔ 支付流水 ↔ 订单。四种差异要分开处理：长款（渠道有我们无）补流水、短款（我们有渠道无）告警、金额不符人工核、状态不符补单。T+1 定时跑 + 差异率告警。

### Q9：支付为什么不能强一致？

> 因为跨越了不可控的外部系统（支付宝/微信）。用户的付款动作在渠道内部完成，我们只能通过"回调 + 主动查单"异步感知。**能保证的边界是：我们内部（流水 → 订单 → 通知）最终一致，且任何时刻都能通过流水表回答"这笔钱在哪"。**

### Q10：`@TransactionalEventListener` 和 `@EventListener` 有什么区别？

> `@EventListener` 在 publishEvent 时同步执行，此时事务还没提交；如果后续回滚，listener 已经跑完了（会发出假通知）。`@TransactionalEventListener(phase = AFTER_COMMIT)` 会在事务提交后才执行，回滚则不执行。**涉及外部副作用（发 MQ、发短信）的都必须用 AFTER_COMMIT。**
