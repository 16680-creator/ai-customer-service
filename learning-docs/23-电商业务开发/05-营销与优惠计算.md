# 05 - 营销与优惠计算

> 本篇把促销从「满减、优惠券」拆成业务规则与并发安全两件事。以本仓库现有实现为例：目前只有满减规则和用户选券，**不是完整营销平台，也没有秒杀、积分、会员等级或规则引擎**。

---

## 零、先给结论

营销计算不是简单地把几个金额相减。一个可靠的优惠链路至少要回答：

1. 订单金额采用商品原价、活动价还是会员价作为门槛基数？
2. 满减与券能否叠加？如果叠加，先后顺序是什么？
3. 结算页预览后商品、库存、规则或券状态变了，最终应付价如何确定？
4. 并发下同一张券如何避免被两个订单同时使用？
5. 重复提交、超时取消后，优惠资格如何释放且不重复发放？

> 面试版结论：**「优惠展示是试算，订单创建时必须以服务端重新计算并原子占用资格为准；金额用 BigDecimal，资格核销靠条件更新/唯一约束，不能依赖前端传来的折扣金额。」**

## 一、促销系统的业务边界

### 1.1 常见优惠类型

| 类型 | 例子 | 关键规则 | 主要风险 |
|---|---|---|---|
| 直降 / 活动价 | 原价 200，活动价 169 | SKU、活动时段、库存 | 展示价与成交价不一致 |
| 满减 | 满 300 减 50 | 参与商品范围、门槛基数、是否叠加 | 临界金额、规则重叠 |
| 优惠券 | 满 100 减 15 | 归属用户、有效期、门槛、状态 | 重复核销、越权使用 |
| 折扣 | 8 折、最高减 100 | 折扣基数、封顶、精度 | 舍入规则不一致 |
| 包邮 / 凑单 | 满额免运费 | 运费是否计入门槛 | 订单拆分导致金额变化 |
| 积分 / 会员权益 | 积分抵现、会员折扣 | 账户余额、等级快照、权益叠加 | 账本并发、规则组合爆炸 |
| 秒杀 / 限时购 | 限时限量 | 资格、库存、限购、流量控制 | 超卖、刷接口、热点竞争 |

以上是行业常见能力地图，不代表当前项目已实现。项目当前可核实的促销模型只有 `Coupon` 和 `FullReductionRule`：`ai-cs-order/src/main/java/com/aics/order/entity/Coupon.java:19-36`、`ai-cs-order/src/main/java/com/aics/order/entity/FullReductionRule.java:19-32`。源代码中没有积分、活动中心或秒杀实现；不要把本表当作本项目功能清单。

### 1.2 营销域通常拆成四类职责

1. **规则配置**：运营人员配置活动时间、参与范围、门槛、优惠值、叠加策略。
2. **资格发放**：确定用户是否能领取，限制总量、每人限领和渠道。
3. **价格试算**：根据购物车和用户权益算出可展示方案，不产生最终扣减。
4. **订单核销**：订单创建时重新校验规则并占用券/活动名额；支付、取消、退款等事件推进资格状态。

当前项目只覆盖一部分：满减规则读取、可用券查询、结算试算和下单时更新券状态；没有活动配置后台、发券链路、会员/积分账本或统一营销编排。证据：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:39-57`、`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:61-83`、`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:132-141`。

## 二、本项目的优惠计算：满减 + 用户选券

### 2.1 计算顺序

`PromotionServiceImpl` 的类注释声明顺序为「原价 → 满减（取最优）→ 优惠券（用户选择）→ 应付金额」：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:21-24`。

```text
商品原价合计
  └─ 满减：筛选时间有效且门槛满足的规则，选减免金额最大的一条
       └─ 优惠券：仅当用户指定的券归属本人、未使用、未过期且满足门槛时抵扣
            └─ 应付金额 = max(0, 原价 - 满减 - 券)
```

对应实现：`calculatePrice` 先调用 `applyFullReduction`，再 `applyCoupon`，最后累计 discount 并把应付金额下限设为 0：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:39-56`。

### 2.2 满减规则

规则筛选条件是 `enabled=true`、`startTime <= now`、`endTime >= now`；之后用订单金额筛掉未达门槛规则，再按 `reductionAmount` 取最大的一条：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:88-106`。

| 满减规则 | 门槛 | 减免 | 订单 350 元时是否满足 |
|---|---:|---:|---|
| 满 100 减 10 | 100 | 10 | 是 |
| 满 300 减 50 | 300 | 50 | 是 |
| 满 500 减 100 | 500 | 100 | 否 |

示例规则种子是满 100 减 10、满 300 减 50、满 500 减 100：`deploy/mysql/demo-data.sql:141-145`。按当前实现，350 元时取减免最大的一条，即减 50，而不是叠加减 60。这个选择是当前代码的策略，不是所有电商平台的通用规则。

### 2.3 优惠券资格

Coupon 字段包括归属用户、名称、面额、门槛、状态、过期时间、使用时间和关联订单号：`ai-cs-order/src/main/java/com/aics/order/entity/Coupon.java:19-36`。状态枚举只有 `UNUSED`、`USED`、`EXPIRED`：`ai-cs-order/src/main/java/com/aics/order/enums/CouponStatus.java:11-19`。

可用券列表查询筛选本人持有、状态 UNUSED 且过期时间晚于当前时间的券，再计算金额门槛；未达门槛时返回不可用原因：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:61-83`。

用户指定 couponId 后，计算逻辑再次检查归属、状态、有效期和门槛：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:111-133`。但如果券不存在或不满足条件，当前实现静默地不抵扣，而非返回明确错误：`:116-119`、`:121-132`。这会让用户提交了券却仍按原价下单，界面和预期可能不一致。

### 2.4 试算不是价格承诺

结算接口从选中的购物车项计算合计，调用优惠服务返回满减和可用券：`ai-cs-order/src/main/java/com/aics/order/controller/CartController.java:79-130`。该接口调用 `calculatePrice(totalAmount, userId, null)`，所以返回的 `payAmount` 不包含用户之后选择的券：`:89-94`。

前端只展示 `usable` 的券选项并在提交订单时发送 couponId：`ai-cs-frontend/src/views/CheckoutView.vue:29-38`、`ai-cs-frontend/src/views/CheckoutView.vue:74-78`、`ai-cs-frontend/src/views/CheckoutView.vue:105-115`。下单服务再次根据购物车快照价调用 `calculatePrice`：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:98-101`。因此最终应付金额来自服务端重算，而不是前端提交一个可篡改的 payAmount。

> ⚠️ 当前模型用购物车保存的 productPrice 作为下单金额输入：`OrderCreateTxService.java:98-101`。如果商品涨价后购物车快照仍旧，可能按旧价下单。生产系统应明确价格策略：下单时重新读商品/活动价格，或将购物车价格视为报价并设置有效期；不能含糊地把快照价称为当前价。

## 三、金额精度与规则计算

### 3.1 金额使用 BigDecimal

金额禁止用 `double` 做累加或比较，因为二进制浮点无法精确表示很多十进制小数。订单和促销实体使用 `BigDecimal`：`ai-cs-order/src/main/java/com/aics/order/entity/Order.java:23-33`、`ai-cs-order/src/main/java/com/aics/order/bo/PriceCalcBO.java:13-29`；数据库金额列使用 `DECIMAL(10,2)`：`deploy/mysql/order-init.sql:28-33`。

```java
// 推荐：字符串构造，明确两位小数
BigDecimal price = new BigDecimal("19.90");
BigDecimal subtotal = price.multiply(BigDecimal.valueOf(quantity));

// 比较金额用 compareTo，而不是 equals（scale 不同也可能数值相同）
if (subtotal.compareTo(threshold) >= 0) {
    // 满足门槛
}
```

示例是通用写法，不是对本项目新增代码的描述。当前满减与券的金额判断均通过 `compareTo`：`PromotionServiceImpl.java:75-80`、`PromotionServiceImpl.java:97-99`、`PromotionServiceImpl.java:121-125`。

### 3.2 舍入必须成为业务规则

如果有折扣率，需要约定计算精度、舍入模式和舍入时机，例如：

```java
BigDecimal discount = original
        .multiply(new BigDecimal("0.85"))
        .setScale(2, RoundingMode.HALF_UP);
```

同一笔订单的前端展示、订单服务、支付流水和渠道金额必须采用一致的最终金额。分账或多币种场景要进一步确定以「分」为内部最小单位，或者统一使用定点金额类型。当前项目金额字段为 DECIMAL(10,2)，支付渠道间元/分换算是支付域问题，见 [04-支付退款与资金对账](./04-支付退款与资金对账.md)。

### 3.3 叠加与互斥要显式建模

推荐将优惠规则拆为：

- **资格**：用户、商品、类目、渠道、时间、订单状态。
- **优惠计算**：固定减、折扣率、封顶、包邮等。
- **互斥组**：同组最多选一个，例如「平台券」与「店铺券」是否可同时使用。
- **优先级**：先算活动价还是满减，券门槛按原价还是优惠后金额判断。
- **成本归属**：平台承担、商家承担或共同承担。

当前实现只有满减+用户指定一张券，满减先算、券再对满减后的金额验门槛：`PromotionServiceImpl.java:45-54`、`PromotionServiceImpl.java:121-125`。没有互斥组、成本分摊、规则优先级配置，也没有通用规则引擎；不要把几个 if 语句包装成规则平台。

## 四、发券、试算、占用、核销、退回

### 4.1 推荐状态流

生产系统可将券生命周期设计为：

```text
发放 → UNUSED → RESERVED（订单待支付占用） → USED（支付成功）
                      │
                      ├─ 订单取消/支付超时 → UNUSED 或 EXPIRED
                      └─ 占用超时 → 释放任务恢复资格
```

本项目 Coupon 当前只定义 UNUSED/USED/EXPIRED 三种状态：`ai-cs-order/src/main/java/com/aics/order/enums/CouponStatus.java:11-19`，没有 RESERVED。订单创建时把券改为 USED，订单取消时再把 USED 改回 UNUSED 并清理使用时间和订单号：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:132-141`、`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:237-245`。这意味着「下单即核销」，并非「支付成功才核销」。

### 4.2 并发核销不能只做先查后改

下单代码先 `selectById`，再 set status=USED 并 `updateById`，没有 WHERE status='UNUSED' 的条件更新，也没有检查受影响行数：`OrderCreateTxService.java:133-141`。两笔并发订单可能都读到 UNUSED，并都认为自己用券成功。

更可靠的做法是条件更新：

```sql
UPDATE coupon
SET status = 'USED', use_time = NOW(), order_no = ?
WHERE id = ? AND user_id = ? AND status = 'UNUSED' AND expire_time > NOW();
```

只有影响行数为 1 的请求取得券资格；为 0 则视为已被占用、过期或不属于该用户。SQL 是改造示意，尚未在本仓库实现。还需结合订单事务回滚行为和数据库唯一约束；Redis 锁可以降低竞争，但数据库条件更新才是最终裁决。

### 4.3 下单取消和超时释放

取消订单会尝试关闭支付渠道、恢复库存并退回 USED 券：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:222-247`。超时取消由延迟消息和数据库扫描兜底触发，细节见 [03-购物车与交易下单链路](./03-购物车与交易下单链路.md)。

生产设计还需确认：

- 支付成功与超时取消并发时，哪个状态迁移获胜？
- 已支付订单取消时是否能退券？退款后券是退回、作废还是发新券？
- 延迟消息重复消费时，释放动作是否幂等？
- 券过期时间恰好等于当前时间时，边界采用 `>` 还是 `>=`？

当前券有效性使用 `expireTime.isAfter(now)`，即过期时间必须严格晚于当前时刻：`PromotionServiceImpl.java:121-125`。时区和统一时钟仍应由业务明确，尤其是活动结束边界。

## 五、活动规模上来以后：工程化常用模式

> 以下是行业常见方案，不代表本项目已落地。

### 5.1 活动规则与版本

规则保存 `start_at/end_at`、状态、适用范围和版本。运营发布时校验时间区间、优惠成本上限、规则互斥关系；订单记录实际命中的活动 ID、规则版本、计算输入与结果，方便客服解释和审计。不要只保存「折后金额」而丢失计算依据。

### 5.2 限领与库存

发券限领可用数据库唯一键 `(campaign_id, user_id)` 防止同一用户重复领取；全局券库存可用原子条件扣减或 Redis Lua 预扣，再以数据库账本对账。高并发时要定义预扣失败、消息失败、用户取消和过期释放的补偿流程。

### 5.3 缓存策略

规则读取可以缓存，但发布/下线必须有明确失效机制和版本号；券资格是用户私有且状态会变化，不宜把长 TTL 缓存当权威。缓存命中只能优化查询，最终核销仍要由数据库原子更新裁决。

### 5.4 防刷与风控

常用措施包括用户/设备/账号维度限流、验证码或行为校验、每人限领、设备与账号关联风险、异常退款/批量注册检测。不要只用 IP 限流：企业代理和移动网络会造成误伤。项目网关有 RateLimitFilter，但默认 enabled=false，线上是否开启需看环境配置：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RateLimitProperties.java:25-46`。

### 5.5 指标和运营分析

至少看领取人数、领取成功率、核销率、活动成本、客单价变化、退款率、异常失败率和资格争议量。指标要能按活动、渠道、用户分群查询；涉及资金优惠的报表要能回溯订单快照。当前模块没有完整营销报表或活动预算核算实现（❌）。

## 七、面试题（至少先把这些讲透）

### Q1：满减和优惠券如何计算？
答题要点：先定义金额基数和叠加顺序；本项目先筛有效满减并取最大减免，再验用户指定优惠券，最后将应付金额下限设为 0。别把此策略说成通用规则。证据：`PromotionServiceImpl.java:45-54`、`:88-106`。

### Q2：为什么结算页展示的应付金额不是最终承诺？
答题要点：预览和下单之间商品价、规则、券状态、库存都可能变化；预览用于用户选择，提交时服务端重算并原子占用资格；价格变化需明确拒绝或提示用户确认。项目结算预览无 couponId：`CartController.java:89-94`，下单再次计算：`OrderCreateTxService.java:98-101`。

### Q3：怎么防止一张券被并发使用两次？
答题要点：`UPDATE ... WHERE status='UNUSED' AND user_id=?`，检查影响行数；唯一约束处理领券重复；Redis 锁可作削峰但 DB 是最终裁决。项目当前先读后 updateById，无 CAS：`OrderCreateTxService.java:133-141`。

### Q4：订单取消后优惠券怎么处理？
答题要点：定义券是否已占用、是否过期、是否已支付；释放动作必须幂等；已支付退款与未支付取消采用不同策略。项目取消时 USED→UNUSED：`OrderServiceImpl.java:237-245`。

### Q5：满减门槛应按优惠前还是优惠后金额？
答题要点：这是业务规则，不存在唯一正确答案；商品范围、运费、其他优惠是否计入都需清晰定义；规则顺序必须稳定并可解释。本项目先满减，再用满减后的金额检查券门槛：`PromotionServiceImpl.java:45-54`、`:121-125`。

### Q6：金额为什么用 BigDecimal？`equals` 和 `compareTo` 有何不同？
答题要点：避免二进制浮点误差；BigDecimal 构造优先字符串/整数最小单位；compareTo 比数值，equals 同时比较 scale。项目促销门槛用 compareTo：`PromotionServiceImpl.java:75-80`。

### Q7：为什么券失效时不应静默按原价下单？
答题要点：用户看到的价格与成交价格不一致会产生客诉；返回明确业务错误并提供刷新试算；项目当前 invalid coupon 静默不抵扣：`PromotionServiceImpl.java:116-132`。

### Q8：活动开始/结束时间的边界怎么定义？
答题要点：统一时区、用服务端时间、定义开始包含/结束包含规则、避免各服务本地时钟偏差；本项目规则筛选 start<=now 且 end>=now：`PromotionServiceImpl.java:88-94`。

### Q9：高并发抢券怎么设计？
答题要点：资格校验、限领、库存原子扣减、幂等请求、异步发放和补偿；热点缓存只优化，不替代账本；监控超发和库存差异。

### Q10：为什么不能一上来做通用营销规则引擎？
答题要点：先从明确的优惠类型/叠加关系建模；规则 DSL、版本发布、回滚、冲突校验都增加复杂度；当规则变化频繁且跨业务复用时再引入。当前只有满减与券逻辑，尚无引擎：`PromotionServiceImpl.java:39-57`。

### Q11：如何支持优惠成本分摊？
答题要点：记录优惠承担方与金额，拆分平台/商家成本；订单快照保存活动规则版本，退款按原订单成本分摊规则反向计算；财务对账基于明细而非重新跑当前规则。

### Q12：促销数据如何验证效果？
答题要点：先定对照口径和指标（领取/核销/增量销售/毛利/退款），防止把自然销量误当活动增量；按活动版本留审计明细；成本预算设硬上限和告警。
