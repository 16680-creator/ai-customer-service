# 06 - 搜索、推荐与商品数据同步

> 电商搜索至少有三条不同链路：商品关键词检索、商品相似推荐、知识库混合检索。先把对象与数据流分开，再谈 ES、向量库和 CDC，避免把「项目里有 RRF」误说成「商品搜索已完成」。

---

## 零、先画出数据流

```text
商品管理写入 MySQL product
       │
       ├─ 商品详情/类目缓存与向量索引（当前有实现，向量库为内存版）
       │
       └─ binlog → Canal → RocketMQ c-product-sync → ProductCdcConsumer → ES product_catalog
                                              （消费端实现）       （部署缺口）

用户搜索 ──→ 商品关键词检索（应返回商品列表、筛选、排序；当前链路未完整接通）
      ├────→ 商品语义/相似检索（ProductVectorService）
      └────→ 推荐排序（当前是价格区间 + 关键词 + 销量启发式）
```

本项目消费者的注释说明 MySQL `product` CDC 到 ES `product_catalog`，使用商品 id 作稳定 document id，并以定时对账兜底：`ai-cs-search/src/main/java/com/aics/search/cdc/ProductCdcConsumer.java:14-18`。但 `ProductCdcConsumer` 需要 Canal 产生事件，Canal Server/Adapter 编排未落地：`learning-docs/14-数据工程与OLAP/04-CDC与实时同步链路.md:19`。因此「消费代码存在」不等于「数据同步链路在部署环境端到端可用」。

## 一、先区分三类搜索/推荐

| 能力 | 用户意图 | 常用手段 | 本项目现状 |
|---|---|---|---|
| 关键词商品搜索 | 按品牌、型号、名称精确找商品 | ES BM25、同义词、拼写纠错、过滤聚合 | ⚠️ 有 CDC 消费端，但未证实完整商品搜索 API/UI 闭环 |
| 商品相似推荐 | 找相似价格、相似类目或相似语义商品 | 规则召回、向量召回、协同过滤、排序 | ⚠️ 有同价位规则推荐和向量相似服务；不等于个性化推荐 |
| 知识库混合检索 | 在客服知识库中找答案片段 | BM25 + 向量召回 + RRF | ✅ 已实现，但作用对象是知识库文档，不是商品目录 |

本项目 `HybridSearchServiceImpl` 执行 ES 关键词与向量双路检索，按知识库标识过滤、RRF 融合，并在一路为空/异常时降级：`ai-cs-search/src/main/java/com/aics/search/hybrid/HybridSearchServiceImpl.java:19-32,49-73`。这一能力适合作为商品混合检索的工程参考，但不能直接作为商品搜索已实现的证据。

## 二、商品搜索的索引建模

### 2.1 商品文档不是数据库行的简单复制

典型商品搜索文档应按查询形态整理字段，而不是把所有表字段原样塞进 ES：

```json
{
  "productId": 1001,
  "title": "降噪蓝牙耳机 X",
  "brand": "Example",
  "categoryPath": ["数码", "音频", "耳机"],
  "price": 199.00,
  "status": 1,
  "stockState": "IN_STOCK",
  "sales": 120,
  "tags": ["蓝牙", "降噪"],
  "updatedAt": "2026-11-19T10:00:00+08:00"
}
```

上面是设计示例，不是本项目当前 mapping。商品表当前只有名称、描述、价格、库存、类目、图片、状态、销量等字段，没有 SPU/SKU 独立模型：`ai-cs-product/src/main/java/com/aics/product/entity/Product.java:19-46`。搜索文档若未来支持 SKU，应明确一个搜索结果对应 SPU、SKU，还是可售卖变体，并记录 productId/SKU id 的回查规则。

### 2.2 字段类型和分析器

- `title/name`：中文分词 + 精确子字段（keyword）用于排序和聚合。
- `brand/category/tags`：keyword 过滤与聚合；类目路径可以保存祖先 id，便于筛选子树。
- `price/sales/updatedAt`：数值/日期字段，支持范围、排序和新鲜度策略。
- `status/deleted`：索引阶段过滤下架、逻辑删除商品；服务端响应前仍需校验可售状态。
- `description`：全文检索字段；长文本需控制权重，避免压过标题。
- `suggest`：独立维护联想词/拼写建议，不能把热门词缓存误当搜索结果。

字段设计必须和页面查询一致：关键词、类目、品牌、价格区间、排序和分页是常见组合。价格与库存会频繁变化，要评估同步延迟容忍度；成交确认依旧回到商品/订单服务校验，不能以 ES 作为库存权威。

### 2.3 搜索 API 的分页和筛选

生产接口通常要包含 query、filters、sort、page/size、traceId，并限制最大 page size。对高页码场景，ES `from/size` 深分页成本高，可评估 `search_after`；但它需要稳定排序字段与 PIT/一致性策略。项目知识库 `/search/hybrid` 先取 `page * size` 再内存分页，默认最大 size 100：`ai-cs-search/src/main/java/com/aics/search/controller/SearchController.java:41-62`。这是知识库接口的现状，不应不加评估地复制到海量商品目录。

## 三、本项目的商品数据同步：CDC → MQ → ES

### 3.1 消费端行为

`ProductCdcConsumer` 订阅 RocketMQ topic `c-product-sync`：`ai-cs-search/src/main/java/com/aics/search/cdc/ProductCdcConsumer.java:23-24`。开关 `aics.cdc.product.enabled` 默认 false；开关关闭、事件为空、表名不是 product 或 data 为空时直接跳过：`:29-40`。

每行事件按 id 作为 ES document id。DELETE 或 `deleted=1` 执行删除；重复删除忽略；其他事件以 `index` 覆盖写入；ES 异常会抛出 `IllegalStateException` 触发 RocketMQ 重试，避免静默丢失：`ProductCdcConsumer.java:43-64`。

| 设计点 | 当前做法 | 好处 | 需要继续验证 |
|---|---|---|---|
| 幂等 | 稳定 ES id，重放覆盖 upsert | 重复消息不重复造文档 | 同 id 旧事件晚到仍可能覆盖新版本 |
| 删除 | DELETE / deleted=1 都删除 | 兼容物理删除与逻辑删除 | 逻辑删除字段/映射要与表一致 |
| 失败 | 抛异常让 MQ 重试 | 暂时性 ES 故障不丢事件 | 重试耗尽、DLQ 告警和人工重放流程 |
| 开关 | `aics.cdc.product.enabled` 默认 false | 可控启停 | 环境配置必须显式打开并有启动检查 |
| 修复 | 注释声明定时对账兜底 | 可发现漏同步 | 本仓库是否部署了该对账任务需另外确认 |

### 3.2 生产级同步链路的组成

```text
MySQL binlog (ROW)
  → Canal/CDC connector（持久化位点）
  → MQ（按 productId 分区或保证顺序）
  → consumer（幂等 upsert + 版本检查）
  → Elasticsearch
  → 周期对账（MySQL 权威数据 vs ES）
  → 差异修复/重放 + 指标告警
```

Canal 账号脚本只授予 SELECT、REPLICATION SLAVE、REPLICATION CLIENT，并注明不授予业务 DML：`deploy/mysql/canal-init.sql:1-4`。但 `14-数据工程与OLAP/04-CDC与实时同步链路.md:19` 明确指出 Canal Server/Adapter 容器编排未落地。当前项目证据支持「消费者已实现」，不支持「完整 CDC 基础设施已部署」。

### 3.3 乱序、重复和重建

稳定 document id 解决重复写入的实体重复问题，不自动解决乱序覆盖。例：价格先改到 200 的事件延迟，后到的 180 事件先写入 ES，随后旧事件覆盖为 200。生产方案可以在文档带数据库版本/更新时间并比较版本、按商品 id 保序、或由消费者回查权威 MySQL；需考虑重试后时序和删除 tombstone。

全量重建建议使用新索引版本：

1. 创建 `product_catalog_vN` 与 mapping。
2. 记录 CDC 位点并开始缓冲/消费增量。
3. 扫描 MySQL 快照写入新索引，使用稳定商品 id。
4. 重放快照期间的增量，按版本解决新旧覆盖。
5. 做数量、关键字段和抽样查询对账。
6. 原子切换 alias，观察错误率后保留旧索引一段回滚窗口。

这是一套建议流程，不是当前项目已经具备的自动化重建能力。

## 四、商品向量检索与推荐的现状

### 4.1 内存向量存储：适合演示，不是生产持久化

商品向量配置使用 `SimpleVectorStore.builder(embeddingModel).build()`：`ai-cs-product/src/main/java/com/aics/product/config/VectorStoreConfig.java:14-20`。这是内存版；进程重启后的持久化、扩缩容一致性和跨实例共享不能想当然。项目 `ProductVectorService` 用商品 id/name 等 metadata 建向量文档，并提供文本相似查询：`ai-cs-product/src/main/java/com/aics/product/service/impl/ProductVectorService.java:50-64,77-108`。

在生产环境选型前先明确：数据规模、更新频率、过滤需求、召回延迟、向量维度、持久化与备份、是否需要与 ES 关键词结果融合。向量检索能改善语义召回，但不能替代类目/价格/状态过滤及交易服务的可售校验。

### 4.2 当前推荐是规则排序，不是个性化算法

`ProductRecommendServiceImpl` 按基准价 ± tolerance 召回上架商品，可选类目；关键词需全部命中名称/描述；排序依次为关键词命中数、价格距离、销量：`ai-cs-product/src/main/java/com/aics/product/service/impl/ProductRecommendServiceImpl.java:22-30,44-89`。默认浮动比例 15%、默认返回 3 条：`:36-40`。推荐理由只拼真实价格、命中词和销量：`:163-189`。

所以面试中应称为「同价位、关键词约束的可解释规则推荐」，不能称「协同过滤/个性化推荐/机器学习排序」。向量服务能做相似商品召回，但目前没有用户行为召回、曝光点击训练闭环或在线排序证据。

### 4.3 推荐系统的常见分层

```text
召回：热门 / 类目 / 同价位 / 向量近邻 / 用户行为协同过滤
  → 粗排：过滤下架、库存、重复、已购等候选
  → 精排：相关性、价格、销量、个性化特征
  → 重排：多样性、去重、业务规则、广告/自然结果配额
  → 解释与埋点：曝光、点击、加购、下单、退款
```

从小到大落地：先规则召回并记录曝光/点击；有稳定数据后离线评估排序；再考虑协同过滤或学习排序。没有行为数据和在线实验时，复杂模型往往不可验证。

## 五、混合搜索：RRF 可以解决什么

本项目知识库检索分别取 ES BM25 与向量结果各 Top-20，融合常数 RRF_K=60：`HybridSearchServiceImpl.java:40-44,49-73`。RRF 对每路第 rank 位贡献 `1/(k+rank)` 并按分数降序取 TopK：`ai-cs-search/src/main/java/com/aics/search/hybrid/RrfMerger.java:8-18,35-46,58-73`。它不直接相加 BM25 与 cosine 分数，适用于量纲不可比的多路召回。

商品混合检索可用同样模式融合关键词和向量排名，但仍需处理：

- 双路结果 id 的统一（SKU id vs 商品 id）。
- 过滤条件在召回前还是融合后执行，避免无库存/下架商品挤占 topK。
- 多路超时与单路降级的超时预算。
- 去重、分页稳定性、召回覆盖率与排序指标。
- 价格/库存等实时字段由权威服务校验，而非信任陈旧索引。

## 六、线上搜索质量与可观测

| 指标 | 目的 | 示例切分 |
|---|---|---|
| 搜索请求量与 P95/P99 | 容量和延迟 | query 长度、过滤条件、客户端版本 |
| 零结果率 | 找出词典、拼写和索引缺口 | 类目、品牌、query |
| 点击率 / 加购率 / 转化率 | 评估排序是否有用 | 结果位置、召回来源、实验组 |
| 索引延迟 / 消费 lag | 判断商品变更多久可搜索 | MQ topic、分区、消费者组 |
| DLQ 数量 / 重试率 | 发现持续同步故障 | 错误类型、ES index |
| 数据差异率 | 验证读模型完整性 | MySQL 状态、ES doc count、抽样字段 |

注意位置偏差：排在第一的商品通常更容易被点击，不等于它相关性更好。排序优化需要离线标注集或线上 A/B 实验，至少记录 query、候选来源、最终排序、曝光和点击。

## 九、面试题

### Q1：为什么商品搜索不直接查 MySQL？
答题要点：复杂全文相关性、分词、聚合和多条件检索更适合搜索引擎；MySQL 仍是业务权威源。搜索索引是读模型，成交时要重新校验状态、价格和库存。

### Q2：CDC 消息为什么必须幂等？
答题要点：MQ 通常至少一次投递，消费者超时或重启会重放；固定业务 id 作 ES document id，让 upsert/delete 可重复执行。项目的稳定 id 证据：`ProductCdcConsumer.java:17-18,49-60`。

### Q3：幂等 upsert 为什么还可能写出旧数据？
答题要点：重复同一版本安全，不代表不同版本乱序安全；要用单调版本、事件顺序、权威回查或可比较更新时间解决旧事件覆盖新状态。

### Q4：如何保证下架商品不再出现在搜索结果？
答题要点：CDC 删除/状态过滤、查询层可售过滤、索引延迟监控与定时对账共同兜底；强时效场景可在结果回查商品服务，但要控制批量查询成本。

### Q5：关键词与向量召回为什么用 RRF？
答题要点：BM25 分数与向量相似度量纲不一致，直接相加需归一化且敏感；RRF 只融合排名，提升多路共识结果。本项目知识库的实现见 `RrfMerger.java:8-18,35-46`。

### Q6：搜索索引与商品数据库不一致怎么办？
答题要点：先确认消费 lag、DLQ、ES 错误和事件位点；再做抽样/全量对账、幂等重放或重建索引；保证切换可回滚。搜索层可最终一致，订单成交不可依赖陈旧索引。

### Q7：规则推荐和个性化推荐的区别？
答题要点：规则推荐使用明确业务特征和可解释排序；个性化需要用户/上下文特征和行为反馈，需离线评估与实验。项目当前基于价格区间、关键词、销量：`ProductRecommendServiceImpl.java:22-30,73-89`。

### Q8：商品向量库用内存版有哪些生产问题？
答题要点：重启丢失、实例间不共享、无法作为持久读模型、扩缩容状态不一致；需要持久化存储、索引重建、备份恢复和版本切换设计。

### Q9：商品价格和库存应该以 ES 还是 MySQL 为准？
答题要点：ES 可承载搜索体验所需的近实时快照；交易服务必须回到权威数据校验并处理竞争条件。索引延迟可接受性需要按业务设 SLA。

### Q10：如何衡量搜索体验？
答题要点：P95/P99、零结果率、点击/加购/转化率、索引延迟、DLQ 与数据差异率；按 query、类目、排序位置分层，避免只看总体点击率。
