# 07 - 高并发与大促稳定性

> 大促不是单纯把 QPS 打高，而是让流量、库存、订单、支付、消息、搜索和降级策略一起经受可控验证。本篇把容量评估、压测方法、秒杀设计与故障处置串成一套演练流程；所有容量数字必须来自实测，不能用理论值冒充生产结果。

---

## 零、先给结论

电商大促稳定性的目标不是「所有请求都成功」，而是明确：

1. 哪些路径必须保护（下单、扣库存、支付回调）。
2. 哪些能力允许降级（推荐、评价、非核心搜索特征、营销说明）。
3. 哪些数据是权威的（订单、支付流水、商品库存），哪些只是读模型（ES、缓存、推荐结果）。
4. 超载时如何快速失败、排队、限流、熔断和恢复。
5. 变更前如何压测，事故中如何止损，恢复后如何核账。

本项目已有网关路由级 Redis 限流、GET 重试、断路器与统一 fallback：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java:169-186`；但电商下单/秒杀的专用压测脚本和实测基线目前未见，不能宣称「大促能力已验证」。

## 一、先拆电商流量，不要拿总 QPS 做容量设计

| 业务路径 | 读/写特征 | 主要瓶颈 | 可降级性 |
|---|---|---|---|
| 首页/活动页 | 高读、缓存友好 | CDN、缓存、热点商品 | 可返回静态/简化内容 |
| 搜索/筛选 | 高读、ES 查询复杂度变化大 | ES CPU、分片、深分页 | 可退化到关键词或缩小过滤能力 |
| 商品详情 | 高读、缓存命中关键 | Redis、图片 CDN、商品服务 | 可展示缓存快照但标明价格/库存需确认 |
| 加购/购物车 | 中高读写、用户态 | DB 连接池、热点用户 | 可提示稍后重试，不应丢写入确认 |
| 下单/扣库存 | 写密集、必须防超卖 | DB 锁、跨服务事务、Seata | 不可假成功；需限流/排队/快速拒绝 |
| 支付回调 | 写入少但高重要性 | 回调幂等、订单状态竞争 | 必须可重试、可查单、可补偿 |
| 推荐/个性化 | 可异步、容忍较旧结果 | 向量检索、特征服务 | 直接降级到规则/热门商品 |
| 消息/通知 | 可异步 | MQ lag、消费失败 | 可延迟，但必须可追踪和补偿 |

峰值不能简单等同于日均流量乘一个拍脑袋系数。先按业务漏斗拆分：活动访问人数 → 商品点击率 → 加购率 → 下单转化率 → 支付转化率；每一步分别估算目标窗口内的请求量、重试放大和热点集中度。

### 1.1 容量估算的变量

```text
目标请求率 = 目标窗口内请求总数 / 窗口秒数
峰值请求率 = 目标请求率 × 峰谷系数 × 重试放大系数
服务实例数 ≈ 峰值请求率 / 单实例安全吞吐
资源预算 = 实例数 × 单实例 CPU/内存/连接池占用
```

这些是估算公式，不是结果。必须用真实数据校准单实例安全吞吐和数据库/MQ/ES 的资源上限，再留故障余量。对订单下单，还要单独估算每个请求会触发多少 DB 写、跨服务调用、消息发送和锁竞争。

### 1.2 数据库连接池是全局预算

多服务各自配置连接池上限时，不能只看单服务值；总连接数近似为 `实例数 × 每实例 pool size`，还要给管理连接、批处理、迁移与故障切换留空间。项目性能报告列出每服务 HikariCP 最大连接为 10 的配置事实，但明确它是静态配置，不能替代压测：`docs/27-性能基线报告.md:143-151`。

## 二、压测前先定目标、数据和边界

### 2.1 三类指标

| 指标组 | 常见指标 | 读法 |
|---|---|---|
| 用户体验 | p50/p95/p99、首屏/首字节、下单耗时 | 看尾延迟，不只看平均值 |
| 正确性 | 超卖数、重复订单、重复扣券、支付/订单差异、库存账差 | 错一单也可能不可接受 |
| 资源与稳定性 | CPU、堆/GC、线程池队列、DB 连接、Redis 延迟、MQ lag、ES 拒绝数 | 用于解释瓶颈和恢复能力 |

建议先写 SLI/SLO：例如下单接口成功率、确认支付回调延迟、搜索 p95、商品索引延迟。具体阈值由业务和环境确定，不照抄示例数值。

### 2.2 测试前置条件清单

- 被测版本、配置、实例数、JDK/容器资源可追溯。
- 测试数据分布接近真实：商品热度长尾、热点 SKU、不同库存档位、用户行为比例。
- 测试环境隔离，确认不会发真实支付、短信或邮件。
- 压测机与被测机分离；同机结果只能作相对比较。项目负载测试 README 有明确警告：`scripts/loadtest/README.md:30-34`。
- 先用低流量 smoke test 验证认证、数据、清理和结果统计。
- 定义停止条件：错误率、延迟、数据库/Redis/MQ 资源达到保护阈值时立即停止。
- 留好观测面板、日志 traceId、业务核账脚本和回滚负责人。

项目当前已提交的 k6 资产覆盖网关限流与 SSE 对话，不是完整电商负载模型：`scripts/loadtest/README.md:10-16`。文档还说明 JMeter 登录/下单场景是按学习文档用 GUI 搭建，仓库没有提交 `.jmx`：`:30-34`。

## 三、压测类型与推荐顺序

| 类型 | 目的 | 电商示例 | 成功条件 |
|---|---|---|---|
| Smoke | 验证脚本/链路/数据 | 少量用户浏览、加购、下单 | 请求路径和业务断言正确 |
| Load | 验证目标容量 | 按预期漏斗混合浏览/搜索/下单 | 达到目标负载，SLO 与正确性满足 |
| Stress | 找到拐点和失效模式 | 逐步增加下单/搜索并发 | 记录拐点、保护是否生效、恢复时间 |
| Spike | 验证瞬时突增 | 开售时流量从低到峰值 | 队列/限流吸收冲击，权威写不被破坏 |
| Soak | 找资源泄漏与慢性退化 | 稳态运行数小时 | 内存、连接、队列不持续恶化 |
| Failover/Chaos | 验证依赖故障 | Redis/ES/MQ/某实例不可用 | 降级边界与恢复补偿符合预期 |

每轮记录测试版本、数据规模、场景权重、并发模型、持续时间、硬件、配置、观察窗口和原始报告。若没有这些元数据，数字无法复现，也不能用于简历或容量承诺。

### 3.1 到达率模型与并发用户模型

- 恒定到达率适合验证限流和服务处理速率，系统变慢时仍尝试按计划送流量。
- 虚拟用户模型适合模拟用户会等待响应再继续操作的会话。
- SSE/支付轮询等长请求要区分「并发连接数」和「每秒请求数」。

项目 `gateway-rate-limit.js` 使用 constant-arrival-rate 30 req/s 持续 30 秒，p95 阈值 500ms，并把 429 视为限流预期：`scripts/loadtest/k6/gateway-rate-limit.js:10-25,28-33`。SSE 脚本则阶梯增加到 20 VU，并区分 waiting 与整条流耗时：`scripts/loadtest/k6/sse-chat.js:13-30`。这两个脚本示范了场景建模，但不能替代电商交易压测。

## 四、面向电商的压测场景设计

### 4.1 关键场景矩阵

| 场景 | 负载分布 | 必须断言的业务结果 |
|---|---|---|
| 商品浏览 | 热门商品占大头，长尾随机 | 返回状态正确、缓存命中与下游资源正常 |
| 搜索筛选 | 常见词、零结果词、复杂过滤混合 | 结果无越权/下架商品，零结果率和延迟可观测 |
| 加购 | 新增、重复加购、改数量并发 | 用户/商品唯一约束和数量规则正确 |
| 下单 | 多 SKU、热点 SKU、库存不足、重复请求 | 不超卖、不跨用户读购物车、不重复建单 |
| 优惠券 | 同券多请求、同用户重复领券 | 只能成功核销一次，失败反馈清晰 |
| 支付回调 | 重复回调、乱序回调、查单兜底 | 订单只迁移一次，金额一致，可补偿 |
| 取消/超时 | 延迟消息重复、定时扫描同时触发 | 库存/优惠释放幂等，不能取消已支付订单 |
| 依赖异常 | ES 慢、Redis 错、MQ lag、服务实例重启 | 核心写链路保护，非核心功能按预案降级 |

### 4.2 不要只验证 HTTP 200

下单压测必须在结束后核账：订单数量、每笔订单的用户与商品项、库存扣减总量、支付状态、券状态、取消恢复量。业务不变量比单接口响应码更重要。例如「库存不能为负」「成功订单商品数量总和不超过初始库存」「同券不能绑定两笔有效订单」。

当前下单链路通过商品服务扣减库存，再计算购物车快照价格、写订单和订单项、更新优惠券、发延迟消息：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:78-146`。其中购物车项按传入 ids 批量查询而没有在该段按 userId 过滤：`:80-85`；券是先读再 updateById，缺少 CAS：`:132-141`。这些已知风险说明在压测前应先加正确性断言和隔离测试，不能单纯提高并发掩盖竞态。

## 五、秒杀/热点库存的设计题

> 本项目没有秒杀实现。以下是常见方案比较，不是现状陈述。

### 5.1 典型链路

```text
活动资格/限购校验
  → 网关/活动维度限流
  → Redis Lua 原子预扣热点库存 + 用户限购标记
  → 返回排队/受理结果（不要假装订单已支付）
  → MQ 异步创建订单/扣 DB 权威库存
  → 支付成功或超时取消
  → 失败补偿 Redis 预扣与资格占用
  → 对账修复缓存/DB 差异
```

常见控制包括活动预热、随机/签名参数防刷、用户限购、令牌/排队、热点隔离、库存分桶、降级静态页、数据库条件更新。Redis 预扣降低数据库瞬时竞争，但会引入缓存与数据库不一致、消息丢失、消费者积压和补偿复杂度。要定义预扣库存、可售库存、数据库库存三者的账务语义。

### 5.2 方案选型

| 方案 | 适用条件 | 优势 | 代价/风险 |
|---|---|---|---|
| DB 条件更新扣减 | 中低并发、简单交易 | 数据权威、事务直观 | 热点行锁竞争明显 |
| Redis Lua 预扣 + MQ | 突发很高、允许排队 | 快速削峰 | 补偿、对账、消息积压需治理 |
| 库存分桶/多行拆热点 | 单 SKU 热点锁成为瓶颈 | 分散写冲突 | 读取汇总与桶分配更复杂 |
| 排队/预约/分阶段放量 | 极端热点且允许延后结果 | 控制峰值和公平性 | 用户体验变成异步等待 |

选择标准：目标流量与容忍排队时间、库存一致性要求、部署环境复杂度、运维团队是否能持续处理补偿；不要只因为「秒杀要 Redis」就直接引入一套不可观测的预扣系统。

## 六、降级与熔断：保护核心交易

### 6.1 核心路径优先级

- **必须正确**：下单归属校验、库存扣减、订单状态迁移、支付金额校验、支付回调幂等。
- **可以延后**：消息通知、搜索索引更新、行为埋点、推荐特征更新。
- **可以降级**：相似推荐、个性化排序、部分搜索过滤、客服辅助信息。
- **必须明确失败**：库存不足、价格变化未确认、支付渠道不可用、幂等请求冲突。

### 6.2 本项目已有韧性措施

网关路由配置对 GET 请求最多重试 2 次，仅针对 500/502；每条路由有独立断路器并统一 forward `/gateway-fallback`，再叠加 Redis 分布式限流：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java:169-186`。电商 order/cart/pay/product 路由均应用这套组合：`:123-147`。

限流键优先可信用户 id，未认证回退客户端 IP：`RouteConfig.java:151-166`。旧的本地内存限流 `RateLimitProperties.enabled` 默认 false，因为多实例配额不共享；注释说明其被每路由 RequestRateLimiter 替代：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RateLimitProperties.java:23-31`。应区分「旧本地限流关闭」与「路由 Redis 限流是否配置/运行」，不要误读成全网关都没有限流。

### 6.3 8 条降级预案

1. **推荐超时**：切换同类/热门规则列表；埋点采样可延后。
2. **向量服务不可用**：退化到关键词检索，保留类目、状态过滤。
3. **ES 查询过载**：限制复杂过滤/深分页，返回缓存热门结果或明确提示稍后重试。
4. **Redis 故障**：核心下单不可盲目切到无保护模式；根据架构决定数据库条件更新限流或拒绝超载流量。
5. **MQ 积压**：优先保证下单/支付状态写入；暂停非关键通知与画像事件，监控 lag 与 DLQ。
6. **支付渠道异常**：新支付请求快速失败或暂缓创建支付单；保留订单可重试状态，开放主动查单/补偿。
7. **库存服务故障**：拒绝确认订单，不能以缓存库存伪造扣减成功。
8. **数据库连接池耗尽**：入口限流、缩短慢查询/事务、暂停非核心任务；不要无限增加 pool size。

所有降级都需有触发阈值、责任人、开关、恢复条件和演练记录。仅写在文档里而未配置/演练，应标记为计划，不能称为已实现。

## 七、故障演练与恢复流程

### 7.1 事件处理顺序

1. 识别影响：错误率、尾延迟、支付成功但订单未支付、库存差异、MQ lag。
2. 降低新增压力：活动限流、关闭非核心接口、停止异常重试风暴。
3. 保留证据：版本/配置变更、traceId、关键时间线、队列位点、数据库快照。
4. 恢复依赖后先小流量验证，观察错误率、队列追平和资源恢复。
5. 对账修复订单、支付、库存、券和索引；修复动作必须幂等且有审计。
6. 复盘根因、检测缺口、止损策略和自动化回归，不以「重启后好了」结案。

### 7.2 练习故障注入

- ES 暂停响应：观察商品搜索降级与写库是否受影响。
- RocketMQ consumer 延迟：观察 CDC lag、订单超时任务及通知是否堆积。
- Redis 访问超时：观察限流和锁的失败策略，确认不会无控制放行高风险写请求。
- 订单服务单实例重启：确认网关重试只作用于安全 GET，写请求不被盲目重放。
- 支付回调重复投递：验证流水状态和订单状态只迁移一次。
- 压测中杀掉消费者：检查重试、DLQ、告警、恢复和重放的完整链路。

故障演练只在隔离环境进行；涉及真实支付或生产数据需要变更审批、回滚预案和明确授权。

## 九、面试题

### Q1：如何估算大促容量？
答题要点：从业务漏斗与峰值窗口拆每条 API 的到达率，叠加重试和热点集中；用单实例压测结果推算实例数，再校验 DB/MQ/Redis/ES 的总预算并留故障余量。区分估算值和实测值。

### Q2：为什么平均延迟不够？
答题要点：尾部用户受排队、锁竞争、GC、下游抖动影响；看 p95/p99、超时和错误率，还要关联 CPU、线程池队列、连接池等待。

### Q3：秒杀如何防超卖？
答题要点：入口资格/限流、原子预扣、异步削峰、DB 条件扣减、幂等下单、失败补偿、最终对账；明确哪一个存储是账本权威。

### Q4：库存 Redis 和数据库不一致怎么办？
答题要点：定义缓存预扣语义和数据库权威；消息事件幂等、补偿可重放；通过定期对账修复差异，不能只靠缓存 TTL。

### Q5：大促时哪些接口先降级？
答题要点：按业务价值和正确性分级，先关推荐/非核心分析/部分复杂筛选；下单、库存和支付校验要么正确成功，要么明确失败。

### Q6：为什么不对所有请求自动重试？
答题要点：写请求可能已经执行但响应丢失，重试会重复建单/扣库存/支付；只对可证明幂等的请求重试，并用幂等键/状态机/唯一约束保护。

### Q7：网关限流和服务内限流有什么区别？
答题要点：网关可在入口保护整个集群并按用户/IP 配额；服务内限流保护特定资源/业务操作。分布式限额需共享状态，不能用每实例本地配额假装全局一致。

### Q8：压测后如何证明订单链路正确？
答题要点：除 HTTP 指标外，核订单、订单项、库存、券、支付流水和取消恢复数量，检查不变量；将核账结果与脚本报告同版本归档。

### Q9：如何压测长连接和到达率？
答题要点：SSE/长连接关注并发连接与首字节/整流耗时；到达率模型适用于限流，VU 模型适合会等待响应的用户旅程。脚本需定义断言和预期阈值。

### Q10：什么情况下可以写「系统支持 X QPS」？
答题要点：说明版本、机器规格、数据规模、场景、持续时间、延迟/错误阈值、依赖资源和核账结果。静态配置或理论换算不能写成实测吞吐。
