# 09 - 面试题库：系统设计 8 题 + 故障排查 12 题

> 设计题考「边界与取舍」，故障题考「定位顺序与止损」。每题给出白板结构、常见失分点，以及能引用的本项目证据。凡项目未实现的能力，只用「业界常见做法」表述，不冒充现状。

# 第一部分：系统设计 8 题

## 设计题通用答题骨架

```text
1. 需求澄清：用户角色 / 核心动作 / QPS 与数据量量级 / 一致性要求 / 是否已有系统
2. 核心数据模型：实体、主键、状态、生命周期
3. API 与链路：同步/异步、读写分离、缓存位置
4. 一致性：权威源、事务边界、幂等、补偿、对账
5. 容量与瓶颈：热点、锁、索引、连接池、消息积压
6. 失败设计：超时、重试、限流、降级、可观测
7. 演进路线：MVP → 加固 → 规模化
```

白板先画主链路，再逐点加保护；不要一开始堆组件名。

## 设计题 1：设计商品详情与库存展示

**要点**
- 商品主数据 MySQL，详情页读多写少，可用缓存；列表页不适合缓存全部参数组合。
- 价格/库存是高频变化字段，展示值与成交确认分离；详情页缓存需说明 TTL 与失效策略。
- 图片放对象存储 + CDN；大字段不塞进主表热查询。

**本项目证据**
- 详情缓存 30 分钟、分类 10 分钟、列表刻意不缓存：`ai-cs-product/src/main/java/com/aics/product/config/ProductCacheConfig.java:18-20`。
- 详情 `@Cacheable(sync=true)` 防击穿：`ai-cs-product/src/main/java/com/aics/product/service/impl/ProductServiceImpl.java:109`。

**失分点**：把缓存库存当成交依据；缓存穿透/击穿/雪崩全用小 TTL 糊过去。

## 设计题 2：设计购物车

**要点**
- 表：user_id、product_id/SKU、quantity、选中态、加入时价格快照。
- 唯一键 `(user_id, sku_id)`，重复加购走合并；批量查询必须校验归属。
- 价格在结算时重算；下架/库存不足要给出可解释状态。
- 大促时购物车写放大要评估，必要时合并写入或异步落库。

**本项目证据**
- `uk_user_product` 唯一键：`deploy/mysql/order-init.sql:19-21`。
- 加购流程（合并 + 库存校验）：`ai-cs-order/src/main/java/com/aics/order/service/impl/CartServiceImpl.java:58-111`。
- 下单批量取购物车项时缺 userId 过滤：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:80-85`（⚠️ 需修）。

**失分点**：购物车价格直接当成交价；用客户端传的 item id 不校验归属。

## 设计题 3：设计下单与库存扣减

**要点**
- 事务边界：本地事务尽量短，跨服务用 Saga/TCC/事务消息；库存扣减必须原子条件更新。
- 幂等：请求号 + 唯一键；防重：用户级锁只是加速，不是唯一保障。
- 超时释放：延迟消息 + 定时扫描双通道，都必须幂等。
- 多 SKU 扣减按稳定顺序，减少死锁。
- 记账与对账：订单项快照、库存变动流水。

**本项目证据**
- 用户级创建锁包在全局事务外层：`ai-cs-order/src/main/java/com/aics/order/service/impl/OrderServiceImpl.java:50-60`。
- Seata 全局事务 + 本地事务：`OrderCreateTxService.java:78-95`。
- 条件更新扣库存：`ProductServiceImpl.java:190-211`。
- 超时双通道：`ai-cs-order/src/main/java/com/aics/order/task/OrderTimeoutScheduler.java:16-54` + `OrderCreateTxService.java:143-146`。

**失分点**：锁放在事务内空占资源；扣库存不排序；发布 MQ 却以为随事务回滚（MQ 不是 Seata 资源，证据见 `OrderCreateTxService.java:87-95` 注释）。

## 设计题 4：设计支付与回调

**要点**
- 支付流水表（订单号、渠道交易号、金额、状态、通知次数、支付/退款时间）。
- 渠道抽象 + 工厂；回调验签、金额核验、商户单号校验。
- 幂等：流水状态机 + 唯一约束；重复回调快速成功应答。
- 订单侧通过可靠消息或主动查单推进状态；补偿扫描兜底。
- 对账：订单、内部流水、渠道账单三向。

**本项目证据**
- 渠道抽象：`ai-cs-pay/src/main/java/com/aics/pay/channel/PayChannel.java:31-68`。
- 流水幂等：`ai-cs-pay/src/main/java/com/aics/pay/service/impl/PayTransactionServiceImpl.java:53-70`。
- 事务消息：`ai-cs-pay/src/main/java/com/aics/pay/mq/PaySuccessTransactionListener.java:34-68`。
- 查单兜底金额校验缺口：`ai-cs-pay/src/main/java/com/aics/pay/service/PayNotifyService.java:46-55`（⚠️）。

**失分点**：信任前端支付成功跳转；回调无幂等；退款号每次重算。

## 设计题 5：设计秒杀（当前项目未实现）

**要点**
- 活动资格与限购、活动维度限流、热点隔离。
- 预扣：Redis Lua 原子扣减 + 用户限购标记；异步下单削峰。
- 账务：预扣、DB 权威库存、支付/取消/超时补偿、对账。
- 公平性与防刷：排队/令牌、设备与账号风控、验证码。
- 失败可解释：售罄、排队失败、下单失败分别返回不同语义。

**本项目只可引用**：网关 Redis 分布式限流与断路器：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RouteConfig.java:169-186`。项目没有秒杀代码，面试要明确说「这是设计题方案，我项目里没做」。

**失分点**：只讲 Redis 扣库存不提补偿；忽略限购与刷接口；把预扣成功当订单成功。

## 设计题 6：设计订单状态机与售后

**要点**
- 状态与事件分离；迁移表集中定义；非法迁移拒绝并告警。
- 迁移入库需 CAS（当前状态作为条件）以防并发覆盖。
- 售后申请：资格校验（归属/已支付/时间窗/进行中申请）、幂等键、状态推进、退款联动。
- 证据留痕：申请原因、凭证摘要、run id。

**本项目证据**
- 订单状态机：`ai-cs-order/src/main/java/com/aics/order/statemachine/OrderStateTransitionService.java:21-35`（进程内 synchronized，跨实例需 CAS ⚠️）。
- 售后幂等按 idempotencyKey 先查后插 + DB 唯一键：`ai-cs-order/src/main/java/com/aics/order/service/impl/AfterSaleServiceImpl.java:57-96`、`deploy/mysql/order-init.sql:112-113`。

**失分点**：状态用 if-else 散落各接口；幂等只靠查询（并发下仍可能重复，需唯一约束兜底）。

## 设计题 7：设计商品搜索与索引同步

**要点**
- MySQL 权威、ES 读模型；CDC → MQ → consumer，稳定 id 幂等 upsert。
- 顺序问题用版本/更新时间/分区有序解决；全量重建走新索引 + alias 切换。
- 消费失败重试、DLQ、告警、对账修复；查询层校验可售状态。
- 混合检索可用 BM25 + 向量 + RRF，但要处理过滤与去重。

**本项目证据**
- CDC 消费者与幂等：`ai-cs-search/src/main/java/com/aics/search/cdc/ProductCdcConsumer.java:14-64`。
- Canal 部署缺口：`learning-docs/14-数据工程与OLAP/04-CDC与实时同步链路.md:19`。
- RRF 融合（知识库场景）：`ai-cs-search/src/main/java/com/aics/search/hybrid/RrfMerger.java:8-46`。

**失分点**：把知识库 hybrid 说成商品搜索已完成；只说「上 ES」不提对账与重建。

## 设计题 8：设计多租户/多店铺订单后台（业务边界题）

**要点**
- 数据隔离：租户字段 + 行级过滤/独立 schema/独立库，按规模与合规选择。
- 权限：功能权限 + 数据权限（可看哪些店铺/订单）；操作审计。
- 订单查询：按店铺、状态、时间分页，导出配额与脱敏。
- 结算：商家/平台成本分摊与对账口径。

**本项目证据**：项目是单商家/自营式的订单与商品服务，未见多租户或商家端实现，也没有店铺维度字段（❌）。可引用的只有订单归属校验以 userId 为界：`OrderServiceImpl.java:78-95`。

**失分点**：把多租户简化成加一列 tenant_id 就完事，忽略权限、索引、迁移与审计。

# 第二部分：故障排查 12 题

## 排查通用顺序

```text
1. 确认影响面：哪些接口、哪些用户、何时开始
2. 看最近变更：发布、配置、DDL、流量、依赖升级
3. 看入口指标：错误率、4xx/5xx、429、延迟分位
4. 看依赖：DB 连接/慢 SQL、Redis、MQ lag、ES 拒绝、下游超时
5. 看资源：CPU、堆/GC、线程池队列、连接池、磁盘
6. 止损优先：限流、降级、回滚、扩容
7. 保留证据后恢复，再核账与复盘
```

下面每题按「现象 → 先查什么 → 常见根因 → 本项目抓手」组织。

---

### 故障 1：下单接口大量超时

- 先查：网关 p95/p99、订单服务线程池与 DB 连接、商品服务扣库存耗时、Seata 事务耗时、Redis 锁等待。
- 常见根因：事务过长、锁内做远程调用、慢 SQL、下游商品服务雪崩、连接池耗尽。
- 本项目抓手：下单锁包住整个全局事务调用：`OrderServiceImpl.java:50-60`；扣库存是事务内远程调用：`OrderCreateTxService.java:93-95`。

### 故障 2：库存出现负数

- 先查：是否所有扣减都走条件更新；是否有代码直接 `updateById` 覆盖 stock；Redis 与 DB 是否被分别扣减。
- 常见根因：先查后改、缓存扣减漏回写 DB、补偿时重复回加。
- 本项目抓手：扣减用 `setSql` + `.ge(stock, quantity)`：`ProductServiceImpl.java:195-208`；`syncStockCache` 注释记录了「只扣 Redis 镜像不回写 DB」的历史事故：`ProductServiceImpl.java:233-241`。

### 故障 3：用户 A 看到用户 B 的订单/购物车

- 先查：所有按 id 的查询是否带当前用户；批量查询是否二次过滤。
- 常见根因：只信任客户端 id、内部接口未传 userId、缓存 key 没带用户维度。
- 本项目抓手：下单取购物车项缺少 userId 过滤：`OrderCreateTxService.java:80-85`（⚠️）；订单详情已带 userId：`OrderServiceImpl.java:78-95`。

### 故障 4：明明支付成功，订单还是待支付

- 先查：渠道回调是否到达/验签通过、支付流水状态、事务消息是否 COMMIT、订单 confirmPay 是否异常、补偿扫描结果。
- 常见根因：回调验签失败、金额校验不一致被拒、消息未投递、订单状态已被取消。
- 本项目抓手：`PayNotifyService.notifyOrderSuccess` 双路径：`ai-cs-pay/src/main/java/com/aics/pay/service/PayNotifyService.java:57-73`；confirmPay 金额不一致抛错：`OrderServiceImpl.java:115-164`。

### 故障 5：同一订单重复支付/重复记账

- 先查：创建支付单是否可重复、渠道交易号唯一约束、回调幂等、订单状态机是否拦重复迁移。
- 常见根因：重复点击创建多笔支付单、回调无条件更新、状态更新无 CAS。
- 本项目抓手：`markSuccess` 对已 SUCCESS 返回 false：`PayTransactionServiceImpl.java:53-70`；`confirmPay` 已 PAID 直接返回：`OrderServiceImpl.java:126-129`。

### 故障 6：订单超时没有自动取消，库存被长期占用

- 先查：延迟消息是否发送/消费、消费组是否积压、定时扫描是否在跑、取消逻辑是否抛异常被吞。
- 常见根因：MQ 不可用、消息延迟级别配错、扫描任务每实例都在跑或都不跑、幂等判断写反。
- 本项目抓手：发送延迟消息 delayLevel 16：`OrderCreateTxService.java:143-146`；`@Scheduled` 5 分钟扫描：`OrderTimeoutScheduler.java:28-54`（多实例下每个实例都跑，需幂等）。

### 故障 7：优惠券被用了两次 / 用户说券没用上

- 先查：核销是否 CAS、affected rows 是否判断、取消退券是否重复、券无效时是否给用户提示。
- 常见根因：先查后改、退券无条件 USED→UNUSED、失效静默不抵扣导致「看起来没用」。
- 本项目抓手：无 CAS 的核销：`OrderCreateTxService.java:132-141`；无效券静默返回：`ai-cs-order/src/main/java/com/aics/order/service/impl/PromotionServiceImpl.java:111-133`。

### 故障 8：结算页价格与实付不一致

- 先查：试算与下单是否同一段价格逻辑、价格来源（购物车快照 vs 商品当前价）、满减规则时间边界、券状态变化。
- 常见根因：两套计算代码、快照价过期、规则在两次请求之间上下线。
- 本项目抓手：下单使用购物车 productPrice 计算：`OrderCreateTxService.java:97-101`；试算接口不传 couponId：`ai-cs-order/src/main/java/com/aics/order/controller/CartController.java:79-101`。

### 故障 9：搜索里商品价格/状态是旧的

- 先查：MQ 消费 lag、DLQ、消费开关 `aics.cdc.product.enabled`、ES 索引是否被旧事件覆盖、Canal 是否在跑。
- 常见根因：CDC 未部署、开关关闭、消费异常后进 DLQ、乱序覆盖。
- 本项目抓手：开关默认 false：`ProductCdcConsumer.java:29-40`；Canal 编排未落地：`learning-docs/14-数据工程与OLAP/04-CDC与实时同步链路.md:19`。

### 故障 10：网关一片 429 / 或限流完全没生效

- 先查：限流键维度（用户/IP）、Redis 令牌桶是否共享、每路由是否都挂了 RequestRateLimiter、本地限流开关含义。
- 常见根因：匿名用户全落到同一 NAT IP、Redis 不可用、只看 `RateLimitProperties.enabled=false` 误判为「无限流」。
- 本项目抓手：`RateLimitProperties.enabled` 默认 false 指旧本地限流：`ai-cs-gateway/src/main/java/com/aics/gateway/config/RateLimitProperties.java:23-31`；每路由 Redis 限流：`RouteConfig.java:181-185`；限流键：`RouteConfig.java:151-166`。

### 故障 11：支付回调大量重试 / 渠道报警

- 先查：回调响应是否符合渠道格式、处理耗时是否超渠道超时、异常是否返回 FAIL、幂等逻辑是否抛错。
- 常见根因：回调里做重逻辑（查远程订单、发 MQ 同步等待）、返回体错误、重复通知未快速短路。
- 本项目抓手：回调控制器按渠道路径返回 SUCCESS/FAIL：`ai-cs-pay/src/main/java/com/aics/pay/controller/PayCallbackController.java:34-45`。

### 故障 12：服务重启后大量请求失败（优雅停机/发布）

- 先查：是否开启优雅停机、超时时间、注册中心摘除时机、网关重试是否只对 GET、长连接是否被强制断开。
- 常见根因：写请求被盲目重试、滚动发布同时停多个实例、连接池重建抖动。
- 本项目抓手：订单与支付 application.yml 均配置 graceful shutdown 与 30s 阶段超时：`ai-cs-order/src/main/resources/application.yml:2-7`；网关仅对 GET 重试：`RouteConfig.java:174-180`。
