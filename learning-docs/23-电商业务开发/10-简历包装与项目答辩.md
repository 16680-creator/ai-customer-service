## 二、项目一页纸（可直接改写成简历项目段）

```markdown
### AI 智能客服平台（个人项目 / 12 模块微服务）        2026.07 - 至今
技术栈：Java 17 · Spring Boot 3.2 · Spring Cloud Alibaba · MySQL · Redis · RocketMQ
        · Elasticsearch · Seata AT · Vue 3 · K8s（已写清单，未全量部署）

- 交易链路：购物车 → 结算试算 → 下单 → 支付 → 售后的闭环。
  下单以「用户级 Redisson 锁（事务外）+ Seata AT 全局事务」保证不重复下单与库存一致，
  库存用条件更新（stock >= qty）防超卖；超时取消走「RocketMQ 延迟消息 + 定时扫描」双通道。
- 支付一致性：抽象支付宝/微信/银联/Mock 四渠道（策略 + 工厂），
  回调验签 + 支付流水幂等（status 状态推进 + order_no 唯一键），
  成功事件走 RocketMQ 事务消息 + 主动查单 + 补偿扫描三层兜底。
- 售后与客服：售后申请按 idempotencyKey + DB 唯一键幂等；客服 Agent 以显式状态机编排工具，
  写操作需二次确认（Token + 摘要 + 超时），支持人工转接与轨迹审计。
- 商品与搜索：商品详情 30 分钟缓存（sync 防击穿）、列表不缓存；
  商品变更经 CDC → RocketMQ → ES 做索引同步，消费端以商品 id 幂等 upsert（Canal 编排未落地）。
```

**写作要点**

1. 每行一个能力，动词开头，技术点后紧跟「为了什么」。
2. 只写有代码证据的东西；「未落地」的部分要么不写进简历，要么在面试中主动说明。
3. 不写 QPS/P95 数字——性能基线尚未实测（`docs/27-性能基线报告.md:3-9`）。

## 三、每条经历的三层讲法

以「订单超时双通道」为例：

| 层 | 内容 | 证据 |
|---|---|---|
| 做过 | 下单成功后发送 RocketMQ 延迟消息（delayLevel 16 ≈ 30min）；另有 `@Scheduled` 每 5 分钟扫描超时待支付订单兜底 | `ai-cs-order/src/main/java/com/aics/order/service/impl/OrderCreateTxService.java:143-146`、`ai-cs-order/src/main/java/com/aics/order/task/OrderTimeoutScheduler.java:28-54` |
| 懂原理 | 延迟消息只保证「尽快触发」，不保证必达；DB 扫描兜底；两条通道都要求幂等（重复取消不重复回库存/退券），因为 MQ 不是 Seata 资源，全局回滚不会撤回已发送消息 | `OrderCreateTxService.java:87-95` 注释、`OrderServiceImpl.java:166-176` |
| 有取舍 | 没用「只靠延迟消息」（丢失即永久占库存）；也没用「只靠扫描」（延迟最长 5 分钟且全表扫）。代价是双路径都要测幂等，扫描在多实例下每实例都跑 | `OrderTimeoutScheduler.java:16-34` |

用同样格式准备下列 6 条，基本覆盖电商面试主线：

1. 用户级下单锁与事务边界
2. 库存条件更新防超卖
3. 支付渠道抽象与回调幂等
4. 事务消息 + 查单 + 补偿
5. 订单状态机收敛
6. 商品缓存与索引同步

## 五、6 个 STAR 案例（可直接背）

### STAR 1：下单重复提交与库存一致

- **S**：并发点击/超时重试可能重复下单并重复扣库存。
- **T**：保证同一用户不并发建单，库存不超卖。
- **A**：Redisson 用户级锁放在事务外层、`tryLock(0, …)` 快速失败；事务内 Seata 全局事务；库存条件更新 `stock >= qty` 并检查 affected rows。
- **R**：并发下单被快速拒绝并给出明确提示；库存由数据库条件更新裁决；单测覆盖成功/不足/不存在三态（`ProductServiceTest.java:268-312`）。
- **边界**：订单号仍是进程内计数器、券核销无 CAS，这两点我在面试里会主动说。

### STAR 2：支付成功但订单未支付

- **S**：渠道回调可能重复、丢失或乱序，订单状态更新可能失败。
- **T**：支付与订单最终一致且不重复记账。
- **A**：支付流水 `markSuccess` 状态幂等（已成功返回 false）；本地流水事务成功后发 RocketMQ 事务消息，回查本地状态决定 COMMIT/ROLLBACK；另有主动查单与补偿扫描。
- **R**：重复回调不会重复推进；成功流水可被扫描发现「未变 PAID」的订单并纳入补偿报告（`PayCompensationServiceImpl.java:55-71`）。
- **边界**：`syncByQuery` 传 null 金额会跳过金额校验，我把它列为待修缺陷。

### STAR 3：超时订单占用库存

- **S**：用户下单不支付，库存与优惠券被长期占用。
- **T**：到期自动取消并释放资源，且不能误取消已支付订单。
- **A**：延迟消息主路径 + 5 分钟定时扫描兜底；取消先做状态迁移过滤（仅 PENDING_PAY），再恢复库存、关闭支付、退券。
- **R**：两条通道都走同一幂等取消逻辑；已支付订单不会被取消。
- **边界**：扫描在多实例下每个实例都执行，依赖幂等而非分布式调度；XXL-Job 为可选通道。

### STAR 4：售后申请重复提交

- **S**：Agent 或用户重试可能重复创建售后单。
- **T**：同一请求只产生一条申请记录。
- **A**：以 runId + action 生成 idempotencyKey，先查命中直接返回首次结果，同时数据库 `uk_idempotency_key` 唯一约束兜底；资格校验链为「订单存在/归属 → 已支付 → 无进行中申请」。
- **R**：重复提交返回首单结果，并发下唯一键保证不双写（`AfterSaleServiceImpl.java:57-96`、`deploy/mysql/order-init.sql:112-113`）。

### STAR 5：商品变更如何进入搜索

- **S**：搜索读模型与商品主库不一致。
- **T**：商品变更近实时反映到 ES，且可重放、可修复。
- **A**：MySQL binlog → Canal → RocketMQ `c-product-sync` → 消费者按商品 id 幂等 upsert / delete，失败抛异常触发 MQ 重试。
- **R**：重放不产生重复文档；ES 故障不静默丢消息。
- **边界**：Canal 容器编排未落地（`14/04:19`），目前这条链路是「消费端就绪、基础设施未部署」，我不会说成线上跑通。

### STAR 6：把 AI 客服用在交易场景

- **S**：用户咨询「我要退款」需要查订单、判断资格、提交申请。
- **T**：让 LLM 能用工具完成只读查询与受控写操作。
- **A**：工具分级（READ 直接执行、WRITE 需二次确认）；订单定位工具在存在多笔可售后订单时返回候选列表让用户选择；写操作带 runId 与幂等键，全链路记录轨迹。
- **R**：写操作不会被模型单方面提交；重复确认不会产生第二个售后单。
- **证据**：`ai-cs-chat/…/tool/OrderLocatorTool.java:39-45,92`、`CreateAfterSaleTool.java:33-39`。

## 六、必被追问的 12 个刁钻问题与答法

| 追问 | 答法骨架 | 不要说 |
|---|---|---|
| 你的下单 QPS 是多少？ | 目前只有静态配置与压测脚本，没有电商场景实测；我能给你静态限流参数（5 QPS/用户、突发 10）和压测计划 | 编一个数字 |
| 用户级锁能防住重复下单吗？ | 只能挡住同实例同用户并发，跨天/跨实例仍需幂等键 + 唯一约束 | 「有锁就够了」 |
| 订单号会重复吗？ | 当前是进程内 AtomicInteger，多实例/重启有碰撞风险，属于待改项 | 「不会重复」 |
| 你是否真的支持 SKU？ | 不支持，商品是单表模型；要支持需要 SKU 表 + 库存维度改造 | 「支持多规格」 |
| 秒杀做过吗？ | 没做过实现，但我能给出预扣 + 异步下单 + 补偿 + 对账的设计 | 「做过」 |
| 对账做到什么程度？ | 内部支付流水 vs 订单的单向检测；没有渠道账单文件三向对账 | 「T+1 自动对账」 |
| 券并发核销怎么保证？ | 当前代码是先读后 updateById，没有 CAS，我正在改成条件更新 + affected rows | 「用了分布式锁」 |
| 分布式事务怎么选型？ | Seata AT 适合短事务且能接受全局锁；MQ 不是 Seata 资源，所以超时消息要消费侧幂等 | 「全用 Seata 就行」 |
| 事务里调远程接口有问题吗？ | 会放大锁持有时间并扩大失败面；更稳的是本地事务 + 可靠事件/补偿 | 「没问题」 |
| 你如何证明缓存有效？ | 有 30 分钟 TTL 与 sync 防击穿配置，但没有命中率实测数据 | 「命中率 99%」 |
| K8s 部署完整吗？ | 只有 8 份服务清单，缺 order/pay/mq，也没有前端清单 | 「全套上 K8s」 |
| 这个项目是公司的还是自己的？ | 个人项目，代码在 GitHub，按模块拆分，标准与公司项目对齐 | 含糊其辞 |

## 七、30 秒 / 3 分钟 / 10 分钟三版叙事

**30 秒**
> 这是我做的 AI 智能客服电商平台，12 个 Spring Boot 微服务。电商侧覆盖商品、购物车、下单、支付、售后；交易一致性用「事务外的用户级锁 + Seata 全局事务 + 库存条件更新 + 延迟消息与定时扫描双通道」保证；支付侧抽象四个渠道，用流水幂等和事务消息保证支付成功必然推进订单。搜索侧通过 CDC 把商品变更同步到 ES。项目没做秒杀、SKU 和履约，这些是我下一步的改造项。

**3 分钟**：按「业务链路 → 三个一致性难点 → 我在哪里做过取舍 → 已知缺陷与下一步」展开，每段挂 1~2 个文件证据。

**10 分钟**：在 3 分钟基础上加白板：下单时序图（含事务边界与锁位置）、支付回调幂等三层、商品同步链路与对账修复。
