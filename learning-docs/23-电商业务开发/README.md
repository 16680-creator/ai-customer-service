# 23-电商业务开发

> 面向"去电商公司做后端/全栈"的**业务 + 技术 + 面试**三合一模块。
> 与 `18-银行金融开发` 同级：`18` 是行业方向（银行），本模块是行业方向（电商）。

---

## 一、这个模块解决什么问题

前 22 个模块把"技术域"铺满了（Java、Spring、MySQL、Redis、MQ、ES、AI、前端、运维、性能、稳定性、数据、云原生、架构），
但**没有任何一篇讲"电商这门生意在技术上长什么样"**。实测证据（2026-11-19，全库 308 个 .md 检索）：

| 关键词 | 全库命中 | 说明 |
|---|---|---|
| `电商` | 13 处，且集中在 JD 描述、银行渠道、Prompt 示例里 | 没有一篇以电商为主线的文档 |
| `秒杀` / `seckill` | **0** | 电商面试第一高频场景，全库零覆盖 |
| `SKU` / `SPU` | **0** | 商品模型的行业标准术语，全库零覆盖 |
| `履约` | **0** | 交易后半段（发货/签收/完成）零覆盖 |
| `物流` | 4 处 | 全在 `ai-cs-chat` 的实体注释与 `@Tool` 描述里 |
| `购物车` | 有（`CartServiceImpl` 相关文档） | 但只讲代码，不讲业务规则 |
| `超卖` | 17 处 | 分散在并发/Redis/数据库各篇，未成体系 |
| `优惠券` | 19 处 | 分散在营销/DDL/面试题，未讲叠加与并发核销 |

而项目里**电商代码是真实存在的**（`ai-cs-product`、`ai-cs-order`、`ai-cs-pay`、`ai-cs-search` 四个服务 + 17 个订单测试类），
所以本模块的做法是：**用本仓库真实代码当教材，用行业标准当标尺，把差距逐条写出来**。

> 写作纪律（对齐 `19-求职与面试总纲/README.md:20-26`）：
> ① 不编造数据；② 每个技术断言必须能落回 `文件:行号`；③ 严格区分"本项目已实现 ✅ / 有代码但有缺陷 ⚠️ / 完全没做 ❌"。

## 三、三条学习路径

### 路径 A：系统型（推荐，2 周）

```
01 全景（建立地图）
   ↓
02 商品库存 ──→ 03 交易下单 ──→ 04 支付对账 ──→ 05 营销
   ↓                ↓                ↓
06 搜索推荐      07 高并发/大促（横切，回头再读一遍 02/03）
   ↓
08 题库自检（错题回对应篇）→ 09 设计题（白板默写）→ 10 简历映射
```

### 路径 B：面试急救（5 天）

`01`（半天，只为建立共同语言）→ `08`（1.5 天）→ `09`（2 天）→ `10`（1 天）。
遇到底层细节答不上时，回 `02/03/04` 精确补。

### 路径 C：只补工程缺口（1 周，配合 `00/05` 缺口台账）

`02` 的库存扣减改造 + `03` 的订单号与分页 + `04` 的退款流水 + `05` 的券核销 CAS，
每项都是"代码可改、测试可写"的实活，改完直接进作品集。

## 五、学完自检（可勾选）

- [ ] 能在 3 分钟内画出电商主链路，并标出「哪一步必须强一致、哪一步可以最终一致」。
- [ ] 能说清 SPU/SKU 的区别，并给出 `product` 单表改成 SPU+SKU 的 DDL 与迁移步骤。
- [ ] 能说出至少 3 种库存扣减时机，并解释各自在"超卖 / 少卖 / 用户体验"三方面的代价。
- [ ] 能解释"结算页试算价"和"下单实付价"为什么必须是同一段代码。
- [ ] 能写出订单状态机的 5 条合法迁移，并说明为什么状态迁移要收敛到唯一入口。
- [ ] 能解释支付回调的幂等三层（网关限流 / Redis 幂等键 / DB 唯一约束或状态机）。
- [ ] 能说出 T+1 对账的 4 类差异（长款、短款、单边账、金额不符）各自的定位手法。
- [ ] 能说出优惠券并发核销的 3 种实现与各自代价（悲观锁 / CAS / 分布式锁）。
- [ ] 能给出大促前的容量评估表（QPS × 单请求资源 × 安全系数）。
- [ ] 能把本项目 4 个电商服务讲成 3 分钟叙事，且每个数字都能在代码里指出来。
