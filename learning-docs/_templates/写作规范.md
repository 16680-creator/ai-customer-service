# learning-docs 写作规范（全库通用 · v1）

> 适用范围：`learning-docs/` 下**除 `24-源码分析` 之外**的所有模块（00~23、常见业务相关）。
> `24-源码分析` 有自己的 `_templates/写作规范.md`（更严，因为要逐行核对框架源码）。
> 本规范是 24 那套写法的**降级适配版**：结构完全对齐，证据来源放宽到「框架源码 / 本项目源码 / 可复现实测」三级。
> 一句话目标：**让读者读完能复述流程、能判断对错、能定位问题；任何结论都能被查证。**

---

## 0. 为什么要有这份规范

`24-源码分析` 与其它模块的差距不在"知识点多少"，而在四件事：

| 24 做到了 | 其它模块原来的问题 |
| --- | --- |
| 先给现象，再给地图，最后才进细节 | 上来就是"一、二、三"的条目罗列，读者不知道这些条目解决什么问题 |
| 每个结论都落到具体类/方法/行号 | 结论是"Spring 会做 X"，问"哪一行"就答不出 |
| 每张图都写"读图说明"，指出关键箭头 | 要么没图，要么图是装饰 |
| 每篇都有面试问答 + 动手练习 + 自测题 | 读完不知道自己会不会 |

本规范把这四件事变成硬性要求，适用于**任何主题**，包括没有源码可读的工程题（如 18-银行金融、19-求职、12-性能工程）。

---

## 1. 读者画像与文风

**读者画像**：会写 Spring Boot 业务的 Java 后端（1~3 年经验），看得懂代码，但没系统读过框架实现，遇到"为什么配了不生效""线上为什么卡"就靠搜索。

**文风五条**：

1. **先结论，后细节**：每一节第一句话就回答"这一节解决什么问题、结论是什么"。
2. **术语首次出现必须解释**，写成「`BeanDefinition`（Bean 的"图纸"，描述类名、作用域、属性，此时对象还没创建）」这种形式。禁止假设读者知道缩写。
3. **每个判断都要能追问到"依据"**：源码行号 / 配置项 / 命令输出 / 异常栈，四者至少有一个。写不出依据的判断，删掉。
4. **不写"魔法""黑科技""一行搞定"**；写"由哪个组件、在什么时机、用哪个方法完成"。
5. **对比用表格，流程用 Mermaid，配置用代码块 + 生效验证方式**。三种体裁不要混着用。

**禁止出现的表达**：

- "众所周知""简单来说就是这样"（等于没解释）
- "底层原理很复杂，我们不需要关心"（读者就是来关心这个的）
- "配置上就好"却不给生效判据
- 只贴代码不解释（每个代码块后面至少 3 句说明）

## 3. 证据分级（本规范最核心的一节）

任何技术论断都必须挂一个证据等级，写在结论附近（不要求显式标注等级，但必须能看出属于哪级）：

### A 级：框架源码（最强）

- 只允许引用 **`24-源码分析/assets/source/` 里已入库的摘录**（905 份，文件名即类名 `.java.md`，每行带原始行号）。
- 锚点写法：`[[源码:AbstractBeanFactory.java#L230-L260]]`；单行写 `#L249`。
- 代码块写法：

  ````text
  ```java (src: AbstractBeanFactory.java#L230-L245)
  ...原文逐字符复制，缩进保留...
  ```
  ````

  代码块内**不许加中文注释**，讲解全部写在块外的正文。
- 想引用的类不在库里：要么换一个已在库的类，要么降级为 B/C 级证据，**不许自己编行号**。

### B 级：本项目源码（很强，且最贴业务）

- 引真实文件路径 + 行号，例如 `ai-cs-order/src/main/java/.../OrderServiceImpl.java#L120-L136`。
- 引用前必须真的用工具读过该文件，确认当前行号；行号会随代码变化，所以同一篇里引用的行号**必须当次核对**。
- 适合回答"我们项目里是怎么做的"，是 02/03/04/23 这些模块的主力证据。

### C 级：可复现实测（够用，必须可复现）

- 格式：给出**完整命令/代码**，紧跟**真实输出**（自己跑出来的，不是想象的），再写"怎么读这个输出"。
- 例：`jstat -gc <pid> 1000` 的输出、`EXPLAIN` 的执行计划、`curl` 的响应、异常栈的前 5 行、Redis `INFO memory` 片段。
- 不许写"输出大概是……"。没跑过就不要贴。

### 明确禁止

- 编造类名、方法名、行号、配置项、版本号、性能数字。
- 用"我记得/应该是"充当依据。
- 把某公司某次面试的传闻写成通用结论。

## 4. 每篇正文的标准结构（12 节，缺节要补）

````markdown
# NN.M 标题（如：3.2 事务失效的六种真实原因）

> **一句话结论**：……（一句话说清本篇最终要证明的事，点名关键类/组件/配置）
> **阅读前置**：需要先懂 X、Y（给出本库内的链接）
> **证据基线**：Spring Framework 7.1.0 / 本项目 ai-cs-order 当前 main；预计阅读 40 分钟

## 0. 先看现象（3 分钟上手）

## 1. 整体地图（先图后码）

## 2. 关键概念/关键类逐个拆

## 3. 原理与证据逐段精读

## 4. 一次完整执行时序（端到端）

## 5. 设计取舍：为什么是这样，不那样

## 6. 踩坑与调试手法

## 7. ⚠️ 版本差异

## 8. 面试高频问与答（≥10 问）

## 9. 动手练习（含验收标准）

## 小结

## 自测题（≥10 题，带折叠答案）
````

### 各节写法要求

| 节 | 必须做到 | 常见废稿 |
| --- | --- | --- |
| 0 现象 | 给 2~3 个**真实会遇到的症状**（报错原文/线上表现/配置不生效），结尾一句"这些现象指向同一件事：…" | 没有现象，直接讲定义 |
| 1 地图 | 一张 Mermaid（`flowchart`/`sequenceDiagram`/`stateDiagram-v2`）+ 表格式"组件 / 责任 / 谁来调它" + **读图说明** | 只有图没有文字，或图里全是英文缩写没人解释 |
| 2 概念/类 | 表格：名称 / 所在模块 / 角色 / 关键方法。每个术语一句话职责 | 大段抄 Javadoc |
| 3 原理与证据 | 分 3.1/3.2… 小节；每段「是什么 → 为什么这么设计 → 换成另一种写法会怎样 → 常见坑」。A/B/C 级证据按 §3 规则挂 | 只贴代码 / 只讲结论 |
| 4 时序 | `sequenceDiagram`（`autonumber`）+ 读图说明指出最关键 1~2 个箭头；写清"哪一步失败会报什么错" | 步骤 1~10 平铺，看不出关键路径 |
| 5 取舍 | 表格：方案 / 优点 / 代价 / 本项目怎么选。给"可扩展点清单" | 写"这是设计模式"就结束 |
| 6 踩坑 | 表格：现象 / 根因 / 验证手段 / 解法。至少 5 条，含 2 条调试手法（断点位置、日志关键字、命令） | 只列"注意事项" |
| 7 版本差异 | 表格：老版本 / 当前基线 / 变化点 / 迁移动作。没有差异就写"本篇结论在 X 版本起未变"，并说明据以判断的来源 | 整节删掉 |
| 8 面试 | ≥10 问，**只列问题**，答案放自测题；问题要能区分"背过"和"懂了" | 5 个问题 + 直接给答案 |
| 9 练习 | ≥5 条，每条绑定本篇某个具体分支，写清**验收标准**（能观察到什么） | "请自行尝试" |
| 小结 | 5~8 条 bullet，最后一条给可操作归纳（如"这类问题只有四种根因"） | 复述目录 |
| 自测题 | ≥10 题，每题 `<details><summary>参考答案</summary>` 内 2~4 句，点名具体类/方法/配置 | 只有题目没答案，或答案"见上文" |

### 篇幅与拆分

- 正文 **400~1200 行**（源码类主题可到 1500）。内容密度优先，不灌水也不硬压。
- 一个主题塞不进 1200 行就拆成 `01-xxx.md` / `02-xxx.md`，并在 README 里说明拆分理由。
- 原文件已存在时**保持原路径与原文件名**（其它模块的 README 有链接），只替换内容；确需改名时同步全库改链接。

## 5. 图表规范

- 统一用 Mermaid，禁止 ASCII 大图（README 的目录树除外）。
- 图后必须有 `> **读图说明**：…` 引用块，指出 1~2 个最关键的箭头/分叉，并说明"看错哪个箭头会得出错误结论"。
- 节点文字包含 `()` `[]` `#` `<` 等字符时必须加引号：`A["beanFactory.getBean()"]`。
- 图里不用未解释的缩写；必要时在图下补一个术语表。
- 一张图只表达一件事；超过 15 个节点就拆图。

---

## 6. 代码块规范

- 行内代码用于类名/方法名/配置项：`` `TransactionInterceptor` ``。
- 代码块必须标语言：`java` / `yaml` / `sql` / `bash` / `text` / `xml` / `json` / `mermaid` / `powershell` / `python` / `typescript` / `vue`。
- 代码块 ≤60 行；超了拆块或用单独一行 `...` 省略（省略号必须独占一行）。
- 有 A 级证据的代码块必须标 `(src: 文件#L起-L止)`；B 级证据在块前用一行文字给出文件路径与行号；C 级证据在块后紧跟真实输出。
- 示例代码要能跑：要么给完整 `main`/测试方法，要么说明"示意，省略 import"。

---

## 7. 命名与目录

- 文件名：中文短语或 kebab-case，**新增文件不得含大写字母**；已存在的大写文件名（如 `01-Java17核心特性.md`）保持不动，避免断链。
- 目录：`NN-主题/NN-子主题/NN-篇名.md`；子主题下必须有 `README.md`。
- 每个 README 必须含：学习目标（能做什么，不是"了解"）/ 文章顺序（Mermaid + 读图说明）/ 依赖关系（前置、后续、跨模块）/ 学完能做到什么（可验证的行为）/ 检查点清单。

---

## 8. 旧稿迁移规则（本规范专有条目）

这次是**改写已有文档**，不是从零写。所以：

1. **旧稿只当素材，不当事实**。任何数字、端口、类名、配置项、版本号，都要当次核对（看 pom / 看目录 / 看配置文件 / 看源码）。
2. **旧稿里正确的知识点要保留**（尤其是踩坑经验、项目约定），但必须重新组织进 12 节骨架，不能整段搬运。
3. **发现旧稿写错了**：不要悄悄删掉，写进 `## 7. ⚠️ 版本差异` 或 `## 6. 踩坑`，注明"旧版本/旧文档曾这样写，现在的实际情况是…"。读者最需要知道"我记住的那条是不是过时了"。
4. **缺失的现象、时序、失败信息要真的补上**：能跑就跑，能读代码就读代码。
5. **不许保留"文档索引式"叙述**（"本文档介绍…，共分五部分"）。读者要的是原理，不是目录。

---

## 9. 质量红线（违反即退稿）

1. 编造任何类名 / 方法名 / 行号 / 版本号 / 输出 / 性能数字。
2. 引用 `assets/source/` 里不存在的文件做 A 级证据。
3. 12 节结构缺节（0/1/3/4/6/7/8/9 为强制，2/5 缺失需在文首说明理由）。
4. `<300` 行还宣称"完整覆盖"。
5. 只贴代码不解释、只画图不讲实现。
6. Mermaid 图没有读图说明。
7. 自测题 < 10 题 / 没有折叠答案。
8. 用旧版本结论冒充当前基线（未经核对就写版本行为）。
