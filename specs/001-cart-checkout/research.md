# 技术调研：电商购物车结算流程

**日期**: 2026-08-01
**状态**: 完成

---

## R1: 库存防超卖方案

**决策**: Redis 预扣 + 数据库乐观锁双重保障

**理由**:
- Redis DECR 原子操作实现库存预扣，单机 10W+ QPS 满足 1000 并发需求
- 数据库层使用 `UPDATE stock SET count = count - #{n} WHERE sku_id = #{id} AND count >= #{n}` 乐观锁兜底
- 支付超时/取消时 Redis INCR 归还 + 数据库回补

**备选方案**:
- 纯数据库悲观锁（SELECT FOR UPDATE）：并发性能差，1000 并发下锁等待严重
- 纯 Redis 无数据库校验：Redis 宕机数据丢失风险

---

## R2: 订单超时自动取消方案

**决策**: RocketMQ 延迟消息（30 分钟级别）

**理由**:
- 项目已引入 RocketMQ 5.x，原生支持延迟消息
- 下单时发送 30 分钟延迟消息，到期后消费者检查订单状态，未支付则取消
- 比定时任务轮询更精确，比 Redis Key 过期回调更可靠

**备选方案**:
- 定时任务扫表（每分钟）：有最大 1 分钟误差，且扫表对数据库有压力
- Redis Key 过期事件（Keyspace Notifications）：不可靠，Redis 不保证过期事件一定投递
- 时间轮（HashedWheelTimer）：单机方案，服务重启丢失

---

## R3: 优惠计算引擎设计

**决策**: 策略模式 + 固定计算顺序（满减 → 优惠券）

**理由**:
- 规格明确：满减取最优一条，优惠券仅可用一张，满减与优惠券可叠加
- 计算顺序固定：原价 → 满减（取最优） → 优惠券（用户选择） → 应付金额
- 策略模式预留扩展点，未来新增折扣/赠品只需添加新策略

**备选方案**:
- 规则引擎（Drools）：过重，当前规则简单不需要
- 硬编码 if-else：不可扩展，违反开闭原则

---

## R4: 支付集成方案

**决策**: 抽象 PaymentStrategy 接口 + 三种实现（微信/支付宝/银行卡）

**理由**:
- 规格要求支持 3 种支付方式且未来可扩展
- 统一下单接口返回支付跳转 URL/参数，前端根据支付方式跳转
- 支付回调统一入口，通过订单号关联，幂等处理

**备选方案**:
- 第三方聚合支付（如 Ping++）：引入额外依赖和费用，当前规模不需要
- 仅支持一种支付方式：不满足规格要求

---

## R5: 购物车存储方案

**决策**: MySQL 持久化 + Redis 缓存

**理由**:
- 购物车需要跨设备、跨会话持久化，必须数据库存储
- Redis 缓存热点购物车数据，减少数据库查询
- 写操作先更新数据库再删除缓存（Cache Aside 模式）

**备选方案**:
- 纯 Redis 存储：数据可靠性不足
- 纯 MySQL 无缓存：高频读取场景性能不够

---

## R6: 订单编号生成方案

**决策**: 时间戳 + 机器标识 + 序列号（Snowflake 变体）

**理由**:
- 全局唯一、趋势递增、可读性好
- 格式：`yyyyMMddHHmmss` + 2位机器号 + 4位序列号 = 20位数字
- 使用 Hutool IdUtil 或自定义实现，无需额外中间件

**备选方案**:
- UUID：无序，不利于数据库索引
- 数据库自增：暴露业务量，分布式环境不适用
- Redis INCR：依赖 Redis 可用性
