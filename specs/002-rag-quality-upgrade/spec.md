# 功能规格：RAG 检索质量升级五件套

**功能分支**: `002-rag-quality-upgrade`
**创建日期**: 2026-08-12
**状态**: 草稿
**输入**: 需求描述: "RAG 检索质量升级：1) Rerank 重排序（召回 Top-20 → bge-reranker 精排 Top-5）；2) 混合检索（ES BM25 + 向量语义，RRF 融合）；3) 引用溯源（回答带出处元数据 + 前端卡片）；4) 文档格式扩展（Tika 支持 Word/Excel/HTML/Markdown）；5) 知识库增量同步（文档变更 → RocketMQ → 自动重新向量化）"

## 用户场景与测试 *（必填）*

### 用户故事 1 - 客服回答更精准（优先级：P1）

用户向 AI 客服咨询售后问题时，系统先召回候选资料，再通过重排序把最相关的资料排在前面，最终回答基于精排后的 Top-5 资料生成，减少答非所问。

**此优先级的原因**：Rerank 是 RAG 精度提升性价比最高的一步，直接影响客服回答质量，是其他功能（引用溯源）的地基。

**独立测试**：可以在知识库中混入相似但不相关的资料，验证重排序后真正相关的资料进入回答上下文。

**验收场景**：

1. **假设** 知识库中有 20 条与"退款"相关程度不同的资料，**当** 用户提问"订单怎么退款"，**则** 系统检索并重排序后仅将最相关的 5 条资料用于回答
2. **假设** Rerank 服务不可用，**当** 用户提问，**则** 系统自动降级为向量检索原始排序结果，不影响回答功能
3. **假设** 用户提问与知识库完全不相关，**当** 触发检索，**则** 系统如实告知"没有这方面的资料"，不编造内容

---

### 用户故事 2 - 精确型号与语义查询混合检索（优先级：P1）

用户用"型号 ABC-123 的保修期"这类同时含精确型号和语义描述的查询，系统同时做关键词检索和语义检索，融合排序后给出同时命中型号与语义的结果。

**此优先级的原因**：仅向量检索对型号/订单号等精确串效果差，混合检索是客服场景检索质量的刚需。

**独立测试**：用含型号/编号的查询与纯语义查询分别验证，混合检索结果在两者场景下都不劣于单一检索。

**验收场景**：

1. **假设** 用户输入"型号 ABC-123"，**当** 触发搜索，**则** 结果中精确包含该型号的资料排在融合结果前列
2. **假设** 用户输入"怎么申请退款"，**当** 触发搜索，**则** 语义相关的资料仍能排在融合结果前列
3. **假设** 关键词检索或向量检索其中一路失败，**当** 触发搜索，**则** 另一路结果正常返回，不整体失败

---

### 用户故事 3 - 回答可查证（引用溯源）（优先级：P1）

客服回答问题时，用户和坐席能看到回答依据的知识文档卡片（文档名、页码、相似度、片段），可点开核对原始资料。

**此优先级的原因**：客服回答必须可查证、可复核，是客服场景合规要求，也是用户信任的基础。

**独立测试**：RAG 回答接口返回引用元数据；前端展示引用卡片，点击可查看原文片段。

**验收场景**：

1. **假设** 用户基于知识库提问，**当** 收到 AI 回答，**则** 回答同时返回命中的资料卡片（文档名/页码/相似度/内容片段）
2. **假设** 无命中资料，**当** 收到回答，**则** 引用列表为空，回答明确提示暂无资料
3. **假设** 流式回答结束，**当** 用户查看回答，**则** 引用卡片在流结束后展示在回答下方

---

### 用户故事 4 - 多格式文档入库（优先级：P2）

运营人员直接上传 Word/Excel/HTML/Markdown 格式的客服手册、价目表、帮助文档，系统自动解析内容并入知识库供 RAG 检索，无需先转成 PDF/TXT。

**此优先级的原因**：办公文档实际多为 Office/HTML/Markdown 格式，扩展格式覆盖能显著降低知识入库门槛。

**独立测试**：分别上传 docx、xlsx、html、md 文件，验证解析内容正确且可被检索命中。

**验收场景**：

1. **假设** 上传 .docx 客服手册，**当** 入库完成，**则** 文档内容被解析、分块并写入知识库，可被语义检索命中
2. **假设** 上传 .xlsx 价目表，**当** 入库完成，**则** 表格内容被解析为文本并入库
3. **假设** 上传 .html/.md 帮助文档，**当** 入库完成，**则** 内容被解析入库
4. **假设** 上传不支持的格式，**当** 触发入库，**则** 返回明确错误提示，不影响已有数据

---

### 用户故事 5 - 知识库自动增量同步（优先级：P2）

运营在知识库后台创建/更新/删除文档后，系统自动异步同步向量数据，无需人工触发"重新向量化"，且文档操作失败不影响文档管理功能。

**此优先级的原因**：当前向量化与文档 DB 操作同步耦合，大文档会阻塞接口；异步化是规模化运营的前提。

**独立测试**：创建/更新/删除文档后，观察向量库数据异步更新；验证 DB 操作与向量化解耦。

**验收场景**：

1. **假设** 运营创建一篇新文档，**当** 保存成功，**则** 文档立即入库（DB），向量化异步执行，稍后 RAG 可检索到
2. **假设** 运营更新文档内容，**当** 保存成功，**则** 向量数据自动重新生成，检索到最新内容
3. **假设** 运营删除文档，**当** 删除成功，**则** 对应向量数据被异步清理，不再被检索命中
4. **假设** RocketMQ 消息服务短暂不可用，**当** 文档保存成功，**则** 文档 DB 操作不受影响，向量同步在消息恢复后补偿

---

### 边界情况

- Rerank 服务超时/失败时降级为原始检索排序，回答仍可用
- 混合检索单路失败时降级为单路结果
- 引用溯源在非 RAG 普通对话中不返回引用
- 超过上传大小限制的文件被拒绝并提示
- 知识库同步消息重复投递时保证幂等（重新向量化天然幂等；删除重复执行无副作用）
- 删除文档时向量已不存在则忽略，不报错

## Clarifications

### Session 2026-08-12

- Q: Rerank 服务不可用时如何处理？ → A: 降级为向量检索原始排序，不阻断回答
- Q: 混合检索的 ES 索引数据从哪来？ → A: 知识文档入库时同步写入 ES 关键词索引（与向量写入同一链路）
- Q: 知识库增量同步的生产/消费端归属？ → A: ai-cs-knowledge 文档变更后发消息，同模块消费者异步执行向量化/删除（解耦 DB 事务与向量化耗时）

## 技术背景

### 问题陈述

当前 RAG 检索链路存在五个短板：① 仅用向量相似度取 Top-5，粗排质量有限，回答精度受制于召回排序；② ai-cs-search 仅做向量检索，对型号/订单号等精确串查询效果差；③ RAG 回答不带出处，用户无法核验回答依据；④ 知识库仅支持 PDF/TXT 入库，运营文档格式覆盖不足；⑤ 文档向量化与 DB 操作同步耦合，大文档阻塞接口、无异步补偿。

### 设计目标

- 检索链路升级为"召回 Top-20 → 精排 Top-5"，显著提升回答精度
- 搜索服务支持关键词 + 语义双路检索与融合排序，兼顾精确与语义
- 回答可查证：返回命中资料元数据，前端以卡片展示出处
- 文档解析支持 Office/HTML/Markdown 等主流格式
- 文档变更与向量化解耦，通过消息异步同步，天然可重试、可补偿

## 需求 *（必填）*

### 功能需求

- **FR-001**：知识库语义检索必须支持两阶段检索：先召回 Top-20 候选，再用重排序模型精排取 Top-5 用于回答
- **FR-002**：重排序服务不可用时，检索必须降级为向量检索原始排序，回答功能不中断
- **FR-003**：搜索服务必须同时支持关键词检索（BM25）与向量语义检索，并将两路结果按 RRF 算法融合排序
- **FR-004**：混合检索单路失败时，必须降级返回另一路结果，不整体失败
- **FR-005**：RAG 回答（含流式）必须返回命中资料的引用元数据（文档名、页码、相似度、内容片段）
- **FR-006**：无命中资料时，引用列表为空且回答明确提示无资料
- **FR-007**：聊天前端必须在 RAG 回答下方以卡片形式展示引用来源，可查看资料片段
- **FR-008**：知识库文件入库必须支持 .docx/.xlsx/.html/.md 格式解析（Tika），并保留原有 PDF/TXT 支持
- **FR-009**：不支持的格式入库必须返回明确错误提示
- **FR-010**：知识文档创建/更新/删除后，必须通过 RocketMQ 消息触发异步向量化或向量清理
- **FR-011**：向量同步消息必须幂等：重复投递不产生重复向量或错误
- **FR-012**：知识文档删除时，对应向量数据必须被清理，不再被检索命中

### 关键实体

- **引用项（CitationItem）**：RAG 回答的引用来源，包含文档名、页码、相似度、内容片段、元数据
- **重排结果（RerankedHit）**：重排序后的命中项，包含原始文档与重排分数
- **混合检索结果（HybridHit）**：RRF 融合后的检索结果，包含文档、融合分数、各单路排名
- **知识同步消息（KnowledgeSyncMessage）**：文档变更事件，包含动作（CREATE/UPDATE/DELETE）、文档 ID、知识库标识、内容

## 非功能需求

### 性能要求

- RAG 检索（召回 + 重排）在 2 秒内完成（重排 20 条以内）
- 混合检索响应时间不超过 2 秒
- 知识同步消息消费延迟不超过 5 秒（消息可用时）

### 可观测性要求

- **响应时间**: RAG 对话 P95 延迟 < 5s（含 LLM 生成）
- **可用性**: Rerank/混合检索降级不影响核心对话可用性
- **日志**: 检索链路（召回数、精排数、融合结果数）必须有结构化日志
- **代码覆盖率**: 新增核心逻辑单元测试覆盖率 >= 60%

### 安全要求

- Rerank/Embedding API Key 不得硬编码，必须走配置（Nacos/环境变量）
- 引用片段返回前不做额外权限校验（知识库本身为公开内部资料）

### 可扩展性要求

- Rerank 实现应抽象为接口，支持未来替换其他重排序模型
- 混合检索融合算法应独立成组件，支持调整 RRF 常数 k
- 文档格式扩展应基于 Tika 自动探测，新增格式零代码

## 成功标准 *（必填）*

### 可衡量的结果

- **SC-001**：RAG 回答基于精排 Top-5 资料生成，重排序后命中相关性提升（精排 Top-5 与召回 Top-5 对比，人工评估相关命中率不下降）
- **SC-002**：含精确型号/编号的查询，混合检索结果相关命中率不低于纯向量检索
- **SC-003**：RAG 回答 100% 携带引用元数据（有命中时），前端可正常渲染引用卡片
- **SC-004**：docx/xlsx/html/md 四种格式上传入库成功率 100%（格式合法前提下），且入库后可被检索命中
- **SC-005**：文档创建/更新/删除后，向量数据在消息可达后自动同步，无需人工干预
- **SC-006**：任一外部依赖（Rerank/ES/MQ）不可用时，核心对话与文档管理功能不受影响

## 假设与约束

### 假设

- 硅基流动提供 bge-reranker-v2-m3 重排序 API 且已在配置中提供 API Key
- ES 8.12 与 RocketMQ 5.1.4 已在基础设施中可用（docker-compose 已部署）
- 知识库文档为内部公开资料，检索不涉及用户级数据权限
- 知识同步消息内容体携带文档全文（文本形式），无需消费端回源查询 DB

### 约束

- Rerank 精排数量固定为 Top-5，召回数量固定为 Top-20（可通过配置调整）
- 混合检索 RRF 常数 k 取 60（标准默认值），可配置
- 前端引用卡片仅支持展示文本片段，不支持附件/图片预览（后续迭代）
- ES 关键词索引仅覆盖知识文档文本内容，不含业务订单/商品数据
