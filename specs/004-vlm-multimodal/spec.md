# 功能规格：多模态图生文（VLM）

**功能分支**: `004-vlm-multimodal`
**创建日期**: 2026-08-13
**状态**: 草稿
**模块**: `ai-customer-service:ai-cs-chat / ai-cs-product / ai-cs-frontend / ai-cs-common`
**输入**: 需求描述: "多模态图生文（VLM）：用户上传图片（商品截图/报错页/订单页/故障照片），客服机器人先用视觉模型（硅基流动 Qwen2.5-VL，OpenAI 兼容协议）理解图片内容生成文本描述，再接入现有 RAG 链路（Hybrid/改写/GraphRAG）检索知识库，最后由 DeepSeek 生成回答。支持 SSE 流式输出。同时回填 product 服务的 ImageDescriptionService 占位实现，让商品图片自动生成描述增强向量检索。"

## 用户场景与测试 *（必填）*

### 用户故事 1 - 对话中上传图片提问（优先级：P1）

用户遇到问题时，把截图或照片（报错页、订单页面、商品实物、故障照片）直接发到对话里，机器人"看懂"图片内容后，结合知识库给出针对性回答，而不是让用户用文字描述画面。

**此优先级的原因**：客服场景大量问题天然以图片为载体（"这个报错怎么回事""这张订单对不对""这个商品是不是正品"），纯文本无法承载；图片理解是多模态客服的核心价值，收益直接。

**独立测试**：调用图片对话接口，输入一张图片（URL）+ 可选文字描述，校验返回回答与引用溯源；回答内容需体现对图片关键信息（文字/型号/状态）的理解。

**验收场景**：

1. **假设** 用户上传一张"下单失败，错误码 E10086"的截图，**当** 图片对话执行，**则** 回答基于图片中的错误码与知识库对应处理方案生成，引用含该方案资料
2. **假设** 用户上传图片并附带文字"这个怎么解决"，**当** 图片对话执行，**则** 系统同时利用图片内容与文字提问生成回答
3. **假设** 用户只上传图片、未附文字，**当** 图片对话执行，**则** 系统仍能基于图片内容给出回答（不强制要求文字）

---

### 用户故事 2 - 图片理解无缝接入现有 RAG 链路（优先级：P1）

图片被理解成文本描述后，必须复用现有的检索增强能力（Hybrid 混合检索、查询改写/HyDE、GraphRAG），而不是另起一套对话逻辑；视觉模型不可用时不能影响原有纯文本对话。

**此优先级的原因**：RAG 链路已投入大量建设（003 六件套），图片理解必须"接进来"而非"重造"，否则造成能力割裂与重复建设。

**独立测试**：图片对话接口在检索阶段可与纯文本一样选择 Hybrid / 改写模式；视觉模型不可用时，图片对话自动降级为纯文本对话或返回明确提示，原有 `/chat/send`、`/chat/rag` 行为不变。

**验收场景**：

1. **假设** 图片理解得到"型号 ABC-123 报错 E10086"，**当** 对话开启 Hybrid 模式，**则** RAG 检索基于该描述文本执行混合检索，命中知识库对应资料
2. **假设** 视觉模型服务不可用，**当** 用户发起图片对话，**则** 系统返回明确提示"当前无法识别图片，请文字描述"，不导致整个对话服务崩溃
3. **假设** 用户发起普通文本对话（不带图），**当** 对话执行，**则** 行为与存量完全一致，不受视觉能力影响

---

### 用户故事 3 - 商品图片自动生成描述增强检索（优先级：P2）

商品图片上传后，系统自动用视觉模型生成文本描述，写入商品检索字段，让用户"按图找商品/按外观描述搜商品"时能命中。

**此优先级的原因**：商品图描述是纯文本向量检索无法覆盖的盲区，补上后让商品搜索从"只能按名称/类目"扩展到"按外观语义"；且 `ImageDescriptionService` 占位接口已预留，接入成本低。

**独立测试**：调用商品图片描述接口，输入商品图 URL，校验返回非空文本描述；描述能体现商品外观/品类特征；视觉模型不可用时返回 null 且不影响商品主流程。

**验收场景**：

1. **假设** 上传一张"黑色头戴式降噪耳机"商品图，**当** 触发图片描述生成，**则** 返回包含品类与外观特征的文本描述，并写入商品可检索字段
2. **假设** 视觉模型不可用或图片无法识别，**当** 生成描述，**则** 返回 null 或空，商品创建/更新流程不中断

---

### 边界情况

- 视觉模型服务超时/限流/不可用：图片对话降级为纯文本（有文字）或返回明确提示（仅图片），不得抛 5xx
- 图片 URL 无效/不可访问：返回明确错误，不进入视觉调用
- 图片过大（超过 5MB）或格式不支持（非 jpg/png/webp/gif）：上传阶段即拒绝，与商品图限制一致
- 图片内容为敏感/违规内容：视觉调用前或结果返回后做安全过滤，返回合规提示
- 仅图片无文字且视觉不可用：返回"当前无法识别图片，请文字描述"提示
- 商品图描述生成失败：返回 null，商品流程不中断，可后续重试
- 所有视觉 LLM 调用必须复用弹性治理（超时/重试/熔断），禁止裸调

## 技术背景

### 问题陈述

当前 AI 客服对话链路（`ai-cs-chat`）只接受文本输入，存在两个盲区：

1. **对话盲区**：客服场景大量问题以图片为载体（报错截图、订单页面、商品实物、故障照片），用户无法直接发图提问，被迫用文字转述画面，信息损耗大、体验差；
2. **检索盲区**：商品图、知识库配图等图片内容没有文本化，纯文本向量检索无法覆盖"按外观/画面内容检索"的需求；`ai-cs-product` 的 `ImageDescriptionService` 目前是占位实现（`NoopImageDescriptionService` 直接返回 null）。

### 设计目标

- 对话支持图片输入：视觉模型理解图片生成文本描述，再走现有对话/检索链路
- 图片理解与最终回答**两段式解耦**：VLM 负责"看懂图"，LLM 负责"组织回答"，最大化复用 003 已落地的 RAG 能力
- 商品图片自动生成文本描述，回填 `ImageDescriptionService`，增强向量检索
- 全链路可降级：视觉能力是"增强项"，不可用时核心对话/商品流程不受影响
- 复用现有图片上传（MinIO）与 SSE 流式输出通道

## 技术能力规格

### 核心接口

| 接口名称 | 职责 | 关键方法 |
|---------|------|---------|
| `VisionChatService` | 图片理解 + 对话编排（理解→检索→回答） | `chatWithVision(VisionChatRequest) → VisionChatResponse`、`chatWithVisionSse(...) → SseEmitter` |
| `ImageDescriptionService` | 商品图片文本描述（回填占位实现） | `describe(imageUrl) → String` |

### 核心类

| 类名 | 包 | 职责 | 关键字段/方法 |
|------|------|------|-------------|
| `VisionChatServiceImpl` | ai-cs-chat/service/impl | 图片对话主流程：调 VLM 描述 → 组检索 → 调 LLM 回答 | `chatWithVision()` |
| `VisionChatModel`（Bean，配置类内装配） | ai-cs-chat/config | 指向硅基流动多模态模型的 ChatModel，与 DeepSeek 文本模型隔离 | `call(prompt)` |
| `SiliconFlowImageDescriptionService` | ai-cs-product/service/impl | 商品图描述真实实现，替换 `NoopImageDescriptionService` | `describe()` |
| `VisionChatRequest` / `VisionChatResponse` | ai-cs-chat/dto | 图片对话请求/响应 DTO | `imageUrl`、`message`、`answer`、`citations` |

### 核心枚举

- **无新增枚举**：复用 `RetrievalMode`（检索模式）、`ResultCode`（错误码新增图片相关码位）

### 数据模型

- **`VisionChatRequest`**：图片对话请求（sessionId、imageUrl、message、hybrid、rewrite）
- **`VisionChatResponse`**：图片对话响应（answer、citations、imageDescription）
- **商品描述字段**：`product` 表新增/复用描述字段（如 `imageDescription`），用于向量检索

## 需求 *（必填）*

### 功能需求

- **FR-001**：对话接口必须支持携带图片 URL，视觉模型理解图片后生成文本描述
- **FR-002**：图片对话的检索阶段必须可复用现有 RAG 能力（Hybrid / 查询改写），行为与纯文本 RAG 一致
- **FR-003**：图片对话必须支持 SSE 流式输出（逐 token 推送），与现有 `/chat/stream/sse` 一致
- **FR-004**：图片对话必须支持"图片 + 可选文字"组合输入；仅图片无文字时也能基于图片内容回答
- **FR-005**：视觉模型不可用时，图片对话必须降级（有文字→纯文本；仅图片→明确提示），不得抛 5xx
- **FR-006**：图片 URL 无效或不可访问时，必须返回明确错误，不进入视觉调用
- **FR-007**：图片上传必须复用 MinIO 文件存储，限制格式（jpg/png/webp/gif）与大小（≤5MB）
- **FR-008**：商品图片必须支持自动生成文本描述并写入商品可检索字段，用于增强向量检索
- **FR-009**：商品图描述生成失败时返回 null，商品创建/更新主流程不中断
- **FR-010**：所有视觉 LLM 调用必须复用弹性治理（超时/重试/熔断），禁止裸调

### 关键实体

- **VisionChatRequest / VisionChatResponse**：图片对话实体
- **商品图片描述**：商品实体扩展字段（imageDescription）
- **Media（图片）**：复用 Spring AI 多模态消息中的图片载体（URL 形式）

## 非功能需求

### 性能要求

- 视觉理解阶段（图片 → 文本描述）：≤ 5 秒，超时降级
- 图片对话整体响应（理解 + 检索 + 生成）：P95 延迟 ≤ 8 秒（流式首 token ≤ 5 秒）
- 商品图描述生成：单图 ≤ 5 秒，失败不影响商品主流程

### 可观测性要求

- **响应时间**: 图片对话链路 P95 延迟 ≤ 8s
- **可用性**: 视觉模型不可用时 100% 降级，核心文本对话可用性不受影响
- **日志**: 视觉调用必须有结构化日志（图片 URL 脱敏、耗时、降级原因、模型名）
- **代码覆盖率**: 新增核心逻辑（降级分支、请求校验、描述编排）单元测试行覆盖率 ≥ 60%

### 安全要求

- 图片 URL 必须做 SSRF 防护（限制仅允许 MinIO 内网地址/白名单域名）
- 图片内容敏感信息（手机号、身份证等 PII）在视觉结果与回答中必须脱敏
- 图片对话必须做内容安全过滤（违规图片返回合规提示，不生成回答）
- 视觉模型 API Key 必须走 Nacos 配置，禁止硬编码

### 可扩展性要求

- 视觉模型通过配置切换（model/base-url/api-key），与 DeepSeek 文本模型解耦
- 图片对话支持后续扩展为多图、视频帧（Media 列表天然支持）
- 商品图描述服务抽象为接口，支持替换不同视觉模型实现

## 集成规格

### 依赖模块

- **ai-cs-chat**：核心宿主（视觉模型装配、图片对话、检索编排）
- **ai-cs-common**：`FileStorageService`（MinIO 图片上传）、`Result`/`ResultCode`/`BusinessException`

### 被依赖模块

- 无新增反向依赖；chat 不依赖 product 内部类，product 的图片描述通过接口内部实现

## 假设与约束

### 假设

- 硅基流动已开通多模态视觉模型（如 Qwen2.5-VL），API Key 已在 Nacos 配置，OpenAI 兼容协议可复用现有 `OpenAiChatModel`
- MinIO 图片上传能力已在 `ai-cs-common` 就绪（`FileStorageService`），图片对话直接复用
- DeepSeek 不支持视觉，因此"看图"（硅基流动）与"回答"（DeepSeek）必须分属两个模型，两段式是既定架构
- 图片对话为单图场景起步，多图作为后续扩展

### 约束

- 不引入新的微服务模块，能力落在 ai-cs-chat / ai-cs-product / ai-cs-frontend 现有模块
- 视觉能力为"增强项"：不可用时核心对话/商品流程不受影响，存量接口行为不变
- 图片格式与大小限制与商品图一致（jpg/png/webp/gif，≤5MB）
- 视觉模型 API Key、base-url、model 通过 Nacos（`aics.vision.*`）配置，禁止硬编码
