## 用户场景与测试 *（必填）*

### 用户故事 1 - 售后 Agent 一站式闭环（优先级：P1）🎯 MVP

用户输入"我昨天买的耳机坏了，想换货，另外帮我看看有没有同价位降噪更好的"，系统自动完成：输入安全检查 → 意图识别（售后 + 商品推荐）→ 订单工具定位当前用户订单 → 售后规则 RAG 判断换货资格 → 商品检索工具召回同价位降噪耳机 → 风险判断要求用户确认 → 创建换货申请 → 生成结果摘要并留审计记录。

**此优先级的原因**：这是文档 3.1 P0 的核心目标场景，串起订单、商品、消息、通知全部微服务，形成跨服务业务闭环。

**独立测试**：以固定售后数据集驱动状态机，逐步断言每个状态迁移与工具调用参数。

**验收场景**：

1. **假设** 用户输入"我昨天买的耳机坏了，想换货，另外帮我看看有没有同价位降噪更好的"，**当** Agent 执行，**则** 依次完成意图识别（售后+推荐）、订单定位、规则校验、商品召回，并在写操作（创建换货申请）前向用户展示操作摘要并要求确认
2. **假设** 用户确认换货申请，**当** Agent 收到确认，**则** 携带幂等键调用订单服务创建售后申请，成功后生成包含订单、商品、规则引用、推荐结果的摘要并持久化审计记录
3. **假设** 用户拒绝确认，**当** Agent 收到拒绝，**则** 流程进入 CANCELLED，不执行任何写操作，并解释放弃原因
4. **假设** 用户订单不满足换货条件（如超出质保期），**当** 规则校验完成，**则** Agent 引用具体规则条款解释原因，不创建申请，必要时提供转人工入口

---

### 用户故事 2 - 意图识别与输入安全（优先级：P1）

系统对每条用户输入先做安全检查（Prompt 注入、违规内容），再识别意图（售后 / 商品推荐 / 普通咨询 / 转人工 / 其他），识别结果带置信度与抽取参数（结构化输出）。

**此优先级的原因**：输入安全是接真实业务工具的前置门禁；意图识别是 Agent 路由的第一步，错误路由会直接导致错误操作。

**独立测试**：用固定意图数据集（含售后、推荐、普通咨询、转人工及对抗样本）验证分类正确率与注入拦截率。

**验收场景**：

1. **假设** 用户输入含"忽略之前的指令"等注入文本，**当** 进入安全检查，**则** 输入被拦截或降级为普通对话，不触发任何工具调用
2. **假设** 用户输入"我要退货"，**当** 意图识别，**则** 识别为售后意图且置信度达到阈值，抽取参数含操作类型=退货
3. **假设** 用户输入"帮我推荐 300 元以内的降噪耳机"，**当** 意图识别，**则** 识别为商品推荐意图，抽取预算与品类参数
4. **假设** 用户输入"转人工"，**当** 意图识别，**则** 直接进入转人工流程

---

### 用户故事 3 - 订单定位与归属校验（优先级：P1）

Agent 通过订单工具定位当前用户订单：优先按用户输入的订单号匹配，否则按用户最近订单匹配；找到多个候选订单时向用户列出候选并要求选择；工具返回前必须校验订单归属当前用户。

**此优先级的原因**：订单是售后操作的对象，归属校验不严会直接导致越权操作（文档 5.5 验收：订单归属校验覆盖率 100%）。

**独立测试**：分别验证按订单号命中、按最近订单命中、多候选、无订单、越权订单号五种情况。

**验收场景**：

1. **假设** 用户提供了订单号且属于当前用户，**当** 调用订单工具，**则** 返回该订单详情，状态机进入规则校验
2. **假设** 用户未提供订单号，**当** 调用订单工具，**则** 返回用户最近订单；用户有多个近期订单时返回候选列表并询问用户选择
3. **假设** 用户提供的订单号不属于当前用户，**当** 调用订单工具，**则** 拒绝访问并提示，不进入任何后续步骤
4. **假设** 用户没有任何订单，**当** 调用订单工具，**则** 明确告知无订单，引导进入商品推荐或转人工

---

### 用户故事 4 - 售后规则 RAG 资格判断（优先级：P1）

Agent 从售后规则知识库检索与当前申请（换货/退货/退款）相关的规则，结合订单状态、购买时间判断是否满足条件，回答必须引用具体规则条款；无依据不得编造。

**此优先级的原因**：规则判断是"能不能换"的决策依据，必须可追溯、可复核（文档 5.5 验收：规则回答必须返回引用）。

**独立测试**：用固定售后规则语料构造满足/不满足/证据不足三类用例，验证引用与结论一致。

**验收场景**：

1. **假设** 订单在换货期内且商品状态符合规则，**当** 规则校验，**则** 返回"满足换货条件"并附规则条款引用
2. **假设** 订单超出换货期，**当** 规则校验，**则** 返回"不满足"并引用具体条款说明期限
3. **假设** 知识库未命中任何规则，**当** 规则校验，**则** 如实告知依据不足，不编造规则，引导转人工

---

### 用户故事 5 - 同价位商品召回与推荐解释（优先级：P2）

商品推荐工具按"同价位 ± 阈值 + 品类 + 用户附加条件（如降噪）"召回在售商品，推荐解释必须基于真实商品属性（价格、描述、类目），不允许模型编造参数。

**此优先级的原因**：目标场景包含"帮我看看有没有同价位降噪更好的"，且推荐解释的合规性（不编造）是客服场景底线。

**独立测试**：固定商品数据，验证价格区间过滤、属性条件过滤、解释字段全部来自商品真实字段。

**验收场景**：

1. **假设** 用户订单耳机价格 199 元，**当** 商品推荐工具执行，**则** 召回 199 元 ± 阈值内且描述含降噪的在售耳机，按相关度排序
2. **假设** 召回结果为空，**当** 推荐工具返回，**则** 如实告知无匹配商品，不编造商品
3. **假设** 推荐结果生成解释，**当** 用户查看，**则** 解释中的价格、名称、参数均来自商品真实字段

---

### 用户故事 6 - 写操作二次确认与幂等（优先级：P1）

退款、换货、退货等高风险写操作执行前必须向用户展示操作摘要（订单、商品、数量、原因、影响）并要求明确确认；每次 Agent 执行生成 runId，写操作携带幂等键，重复确认/重试不产生重复申请。

**此优先级的原因**：这是 Human-in-the-loop 的核心门禁，验收要求"高风险写操作未经确认执行次数 = 0"。

**独立测试**：验证确认前不执行、确认后执行一次、同一幂等键重复提交只生效一次、拒绝后不执行。

**验收场景**：

1. **假设** 状态机到达 CONFIRM_ACTION，**当** 用户尚未确认，**则** 不调用任何写操作工具，仅展示操作摘要等待确认
2. **假设** 用户确认，**当** Agent 执行创建申请，**则** 携带幂等键调用订单服务；同一 runId 的确认重复提交不产生第二个申请
3. **假设** 用户拒绝，**当** Agent 处理，**则** 流程进入 CANCELLED 并记录拒绝原因
4. **假设** 创建申请请求超时后重试，**当** 使用相同幂等键重试，**则** 服务端返回首次结果，不重复创建

---

### 用户故事 7 - 人工转接上下文移交（优先级：P1）

不满足规则、用户愤怒（负面情绪）、执行失败或用户主动要求时转人工；转人工工单携带订单信息、情绪、问题摘要和已执行步骤；通知服务向坐席侧推送转人工事件。

**此优先级的原因**：人工兜底是客服系统的最后保障，上下文移交质量直接决定坐席接管效率（验收：转人工时携带订单、情绪、问题摘要和已执行步骤）。

**独立测试**：分别以规则不满足、负面情绪、执行失败、用户主动要求四种触发条件验证工单内容完整性与通知事件。

**验收场景**：

1. **假设** 换货资格不满足，**当** Agent 决策，**则** 生成转人工工单，工单包含订单号、商品、不满足原因、已执行步骤清单
2. **假设** 用户表达愤怒（如"太差了""投诉"），**当** 情绪识别，**则** 触发转人工并标记高优先级
3. **假设** 创建换货申请连续失败达到重试上限，**当** Agent 降级，**则** 转人工并附失败原因与已执行步骤
4. **假设** 转人工工单创建成功，**当** 通知服务处理，**则** 向坐席端推送转人工事件，包含工单编号

---

### 用户故事 8 - 执行轨迹与审计（优先级：P1）

每次 Agent 执行记录 run 与 step 级轨迹（步骤类型、工具名、输入摘要、输出摘要、耗时、状态），支持按 runId 检索和回放；敏感参数不进普通日志，保留摘要或脱敏。

**此优先级的原因**：审计留痕是宪法第 14 条全链路留痕要求，也是"按 runId 检索和回放"验收标准。

**独立测试**：驱动一次完整执行后，按 runId 查询到全部步骤且顺序、状态正确。

**验收场景**：

1. **假设** Agent 完成一次完整执行，**当** 按 runId 查询轨迹，**则** 返回全部步骤（意图识别、订单定位、规则校验、商品召回、确认、执行），顺序与状态正确
2. **假设** 执行中某步骤失败，**当** 查询轨迹，**则** 失败步骤状态为 FAILED 且记录错误摘要，后续步骤未执行
3. **假设** 轨迹含用户地址等敏感参数，**当** 查看普通日志，**则** 不出现明文，仅出现摘要或脱敏值

---

### 边界情况

- 输入安全检查拦截后不触发任何工具调用，仅返回安全提示
- 意图置信度低于阈值时走默认普通对话路由，不执行工具
- 订单定位失败/无订单时不进入售后流程
- 规则校验证据不足时不编造规则
- 商品推荐无结果时如实告知
- 用户确认超时（可配置）默认不执行写操作
- Agent 步骤数超过上限、总执行超时后中止并降级（解释或转人工）
- 模型调用失败时以兜底话术响应，不中断会话
- 同一会话多次 Agent 执行各自独立 runId，互不影响

## 技术背景

### 问题陈述

项目已具备 RAG、订单工具、商品语义推荐、消息、通知、用户与订单微服务，但缺少可靠的业务编排层：当前依赖模型单次 Tool Calling，无显式状态、步骤上限、补偿、确认和恢复机制；写操作工具未形成体系，缺审批与幂等机制；转人工仅停留在会话状态位，无上下文移交与工单。

### 设计目标

- 以显式状态机驱动售后流程（START → CLASSIFY_INTENT → LOCATE_ORDER → CHECK_POLICY → COLLECT_EVIDENCE → CONFIRM_ACTION → EXECUTE_AFTER_SALE → COMPLETED / CANCELLED / HANDOFF），不依赖模型自由 ReAct
- 工具注册中心统一管理订单、商品、售后命令等工具，所有写操作工具声明"需确认"风险等级
- 意图、参数、下一步动作使用结构化输出（Java Record / JSON Schema）接收
- 每次执行生成 runId，写操作携带幂等键，支持超时重试不重复执行
- 转人工携带订单、情绪、问题摘要与已执行步骤，经通知服务推送坐席侧
- 全链路执行轨迹与审计记录持久化，可按 runId 回放

## 功能需求

- **FR-001**: 输入安全检查：检测 Prompt 注入与违规内容，命中即拦截或降级，拦截不触发任何工具调用
- **FR-002**: 意图识别：输出意图类型（AFTER_SALE / PRODUCT_RECOMMEND / NORMAL_CHAT / HUMAN_HANDOFF / OTHER）、置信度与结构化参数，支持多意图（如售后+推荐）
- **FR-003**: Agent 状态机：显式状态定义、状态迁移规则、每状态允许的工具集、最大步骤数/总超时可配置
- **FR-004**: 订单定位工具：按订单号或最近订单定位当前用户订单，多候选时返回候选列表，归属校验 100% 覆盖
- **FR-005**: 售后规则 RAG：基于规则知识库判断资格，回答必须引用规则条款，证据不足不编造
- **FR-006**: 商品推荐工具：同价位（±阈值可配置）+ 品类 + 附加条件召回在售商品，推荐解释基于真实字段
- **FR-007**: 写操作确认：高风险写操作展示摘要并要求确认；确认/拒绝记录（agent_confirmation）；确认超时可配置
- **FR-008**: 幂等与补偿：每次执行生成 runId，写操作携带幂等键（idempotencyKey），服务端按幂等键去重，失败可重试
- **FR-009**: 售后申请命令：ai-cs-order 提供换货/退货/退款申请创建接口，校验订单归属、状态与资格，返回申请单号
- **FR-010**: 转人工：触发条件（规则不满足/负面情绪/执行失败/用户要求）生成 handoff_ticket，携带订单、情绪、问题摘要、已执行步骤
- **FR-011**: 通知推送：转人工事件与处理进度经 ai-cs-notify WebSocket 推送
- **FR-012**: 轨迹审计：agent_run / agent_step / agent_confirmation / handoff_ticket 持久化，可按 runId 查询回放
- **FR-013**: 失败降级：模型调用失败、工具失败、超限时给出可解释响应或转人工，不中断会话
- **FR-014**: 配置化：最大步骤数、单步超时、总超时、确认超时、情绪触发阈值、重试次数均通过配置管理

## 非功能需求

### 性能要求

- Agent 单次执行（含 LLM 调用与工具调用）P95 延迟 < 15 秒（受模型调用延迟支配，工具调用部分 P95 < 500ms）
- 轨迹写入与查询接口 P95 < 200ms

### 可观测性要求

- **响应时间**: 工具调用 P95 < 500ms
- **吞吐量**: 单实例支持 50 并发 Agent 执行
- **资源占用**: 单实例内存 < 1GB
- **代码覆盖率**: 新增代码单元测试行覆盖率 >= 40%、分支覆盖率 >= 30%（宪法第 2-1 条门禁）
- **可用性**: Agent 执行失败不导致服务不可用，模型调用降级后服务可用性 >= 99.9%

### 安全要求

- 写操作未经用户确认执行次数 = 0（强制门禁，测试必须覆盖）
- 工具端重新校验资源归属（订单属于当前用户），不能只信模型参数
- 敏感参数（地址、电话等）不进入普通日志，轨迹中保留摘要或脱敏值
- 输入安全检查先于一切工具调用

### 可扩展性要求

- 新增售后场景（如退款）时状态机与工具注册支持扩展而不改动核心引擎
- 意图、情绪识别模型可替换（配置化）

## 集成规格

## 假设与约束

### 假设

- 售后规则以知识库文档形式维护（种子文档随本功能交付），规则字段含条款编号、适用场景、条件、期限
- 换货期限等规则参数以种子文档内容为准，MVP 不做规则引擎后台管理
- 情绪识别 MVP 采用 LLM 结构化输出（愤怒/满意/中性/负面），不做独立情绪模型
- 转人工 MVP 仅生成工单与通知事件，不实现坐席工作台
- 订单服务已有订单查询能力，按用户/订单号查询可复用；售后申请为新表新接口

### 约束

- 遵守项目宪法：SDD 流程、TDD（Red → Green → Refactor）、覆盖率门禁（行 >= 40%、分支 >= 30%）
- 遵守依赖方向：chat/knowledge/search/message/notify/user/order/product → common；微服务间只经 Feign/HTTP
- 代码注释与文档中文，类/变量英文命名，日志英文
- 统一 Result<T> / ResultCode / BusinessException，SpringDoc 注解齐全
- 数据库表变更统一输出到 deploy/mysql/（幂等 SQL，IF NOT EXISTS）
- 不引入新第三方框架（状态机用自研轻量实现，避免引入 Spring StateMachine 等新依赖——需经技术栈扩展评审）
